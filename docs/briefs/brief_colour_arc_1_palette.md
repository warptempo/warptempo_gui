## Part B — the colour derivation

The app derives every colour but a handful of base roles at one site: `src/gui/render.h`'s palette block (THE SCAFFOLD comment around line 150–200, THE RELIEF SET around line 296–340, `scaled_word` at line 230, `geometric_mean_word`, `relative_luminance` and `highlight_text_ink` around line 377–420). The renderer must derive the same way, in Python, in `tools/palette/colour.py`.

- B1. `relief_quartet(ground)` → (hilight, light3d, shadow, dkshadow) as byte triples, THE BRANCH BY THE GROUND'S RELATIVE LUMINANCE (architect 2026-10-03), the luminance computed exactly as `relative_luminance` does (read it: which linearization, which weights) and the threshold the app's one number, `kHighlightTextLuminanceThreshold` = 0.17912878474779, the equal-contrast point (one number for the text rule and this rule; state at the function that the threshold is shared with `highlight_text_ink` and why: a ground the label white reads against is a dark ground):
  - a DARK ground (luminance at or below the threshold) keeps the app's ratio rule EXACTLY as `scaled_word` and `geometric_mean_word` compute it — Hilight = ground × 196/100, Shadow = ground × 5/8, DkShadow = ground × 21/100, each channel rounded half up and clamped at 255 by `scaled_word`'s integer arithmetic (port that arithmetic, not a float approximation); 3DLight = the per-channel geometric mean of the ground and the Hilight, rounded as `geometric_mean_word` rounds;
  - a LIGHT ground takes Windows' fractions (architect 2026-10-03): Hilight #FFFFFF; 3DLight halfway from the face to white per channel, the half rounded DOWN so #C0C0C0 lands on #DFDFDF ((192 + 255) / 2 = 223.5 → 223); Shadow two thirds of the face per channel, rounded to nearest (192 × 2/3 = 128 exactly); DkShadow #000000.
- B2. The theme's `bevel_hilight` / `bevel_light` / `bevel_shadow` / `bevel_dkshadow` `"auto"` defaults become `relief_quartet` of the GROUND (the app's scaffold derives the relief set from the ground, not from a button face; today's `button_face × 1.75` Redmond97 rule is retired — the README row says what `auto` does now). A theme may still set any of the four by hand; a hand value wins over the rule for that key alone.
- B3. THE HIGHLIGHT'S TEXT BY LUMINANCE. Wherever the renderer paints chrome text over a filled highlight (the `menu.highlight` `"fill"` face at least; grep for every site that puts a label over `accent` or `selected_fill`), the ink is `highlight_text_ink`'s rule: luminance above the threshold → black, else the label colour. The trim arrow glyph (A2) is the same rule over the ground. The flags' black label is their own rule and is NOT this one (the owner comment at kMarkerFlagLabel, render.h around line 579). If a theme key currently sets that ink by hand (`menu.highlight.label`), keep it as an override and make its default the rule.
- B4. THE CHECKS, THE PYTHON STATIC_ASSERT: module-level `assert`s in colour.py next to `relief_quartet`, run at import like the app's static_asserts (one line each, naming the scheme): from #C0C0C0 the quartet is exactly FFFFFF / DFDFDF / 808080 / 000000 (Windows 95 Standard); from #303030 it is exactly 5E5E5E / 434343 / 1E1E1E / 0A0A0A (the app's dark ground, render.h's static_asserts); the highlight ink is white on #000080 and black on #C0C0C0 and black on #FFFFE1 (INFO). render.py's existing one-line log of a render names the quartet it derived and which branch took it, so a mock's colours are visible without opening the PNG.
