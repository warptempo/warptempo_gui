# Input Conventions (modality, bare-e mouse key, type names, naming symmetry)

Moved verbatim from CLAUDE.md in the 2026-07-25 slim-down (project feature-complete). This file is now the authoritative home for this detail; CLAUDE.md carries only a digest and a pointer here. Keep it current with landed rulings.

### Modality is the Modal Dialog
Modal surfaces are REAL DIALOGS since 2026-08-12 (architect: "we should institute real modals" — kdenlive's own dialog model achieved IN-WINDOW: no new Wayland surface, painted by the one renderer over an inert window) AND THEY LIVE ON THE BOTTOM ROW since 2026-08-13 (architect, scrapping the centered box he had ratified the day before: "it looks sloppy — no compositor drop shadow, and faking one wouldn't work"). THE ROW YIELDS WHOLE while a prompt or a dialog editor stands: the transport four, the four arrows, the clock and the status chain all stand down, nothing negotiates for space, and the row paints the modal instead — so the modal is never a tier in the status chain and the chain needs no modal term. NOTHING ABOUT THE RENDERER MOVED with it — one window, one surface, one frame, one painter, exactly as on the day before; only the modal's RECTANGLE moved from the window's centre to the row, which is emphatically NOT the real-window attempt recorded below. The box's own chrome (ground, 1px border, the 11px content pad, the window-margin clamp) is retired with the box; the modal now paints on the ROW'S ground at the ROW'S pads, and only the FIELD keeps sampled chrome. The design record and the surviving constants are kdenlive-redesign.md's dialog section. EVERYTHING ON THE ROW IS FLUSH LEFT (architect 2026-08-13 at his live look, retiring the right-aligned cluster of hours earlier: "right now you have to read the bottom left and then the bottom right — your eyes have to go the whole distance of the screen. Everything should be just flushed left"). A PROMPT is its message at the row's left pad, one pad, then one REAL BUTTON per response in painted order; an EDITOR is its label, its field, one pad, then its two. NOTHING OVERFLOWS THE LANE and the primacy is the STATUS CHAIN'S OWN: THE BUTTONS STAY WHOLE AND THE CONTENT GIVES — a prompt with no reachable button is a modal with no way out, while a clipped message is still readable to its clip — so the cluster's left edge is capped at the rightmost start that still leaves the last button and its reserved focus halo inside the right pad, and whatever precedes it CLIPS (the message) or SHRINKS (the field) against that cap. The focus ring's 2px band stays RESERVED on both ends of the cluster as well as between neighbours, so moving the focus still reflows nothing. Each button wears its response's PLAIN WORD ("Save" / "Discard" / "Cancel" / "Retry" / "Yes", with the dismiss-only error notice keeping its "OK") AND NAMES ITS KEY ON A TOOLTIP. THE BRACKETED ACCELERATOR SPELLING IS RETIRED FOR THE SECOND TIME AND WITH ITS REASON RECORDED, so it is not proposed a third (2026-08-13, at the same look: "the brackets now look odd... a normal button would use an underline for the character... I guess what we could do is do tooltips for the buttons. So we don't do underscores or underline or brackets or anything like that. We just do a tooltip just like the regular icon tooltips") — it went with the bottom-strip line on 2026-08-12, came back with the row hours later, and left again the same day. EVERY MODAL BUTTON THEREFORE CARRIES A TOOLTIP, through the roster's own machinery end to end: the same 700ms dwell, the same box, the same painter and the same one `AppState::redesign_tooltip` state, whose OWNER now names one of two surfaces (Roster or Dialog, the encoding stated once at that field; each surface's hover walk arms the dwell for its own, and the dwell is independent of the press arm, so holding a button neither starts nor stops a hint). The TEXT is the roster's own format, "<word> (<key>)", with the roster's own accelerator spelling — a bare letter LOWERCASE, which here is not merely convention but the truth about the surface, the prompt match being codepoint-exact on the lowercase letter — and it is DERIVED from what the button dispatches (`modal_dialog_button_hint`, app_state.h: a prompt button's response char, whose two sentinels are Delete and Escape; an editor button's `editor_ok`, which IS the session's Enter or Escape), never hand-listed beside the words. So the six read "Save (s)" / "Discard (Delete)" / "Cancel (Escape)" / "Retry (r)" / "Yes (y)" / "OK (Escape)", and an editor's two "OK (Enter)" / "Cancel (Escape)". The hint hangs ABOVE the lane like the bottom row's other buttons', its painter running after the modal's so the box it hangs off is the one that frame drew. NOTHING ABOUT THE MATCHING MOVED through any of the three spellings — response_keys and the codepoint-exact lowercase compare are untouched, so a typed capital still does not answer. The buttons take the toolbar row's button size (the 32px box — the dialog's OWN constants since the 2026-08-12 relayout deleted that row, kModalBtnBoxPx, paint_handler.cpp) in the icon row's face colors (the architect's explicit mix), and A PROMPT'S LAST BUTTON WEARS THE PASSIVE FOCUS FACE FROM ITS RAISE (2026-08-13, the day's second modal ruling — SUPERSEDING "no button wears the crop's highlighted default face; this prompt system has no Enter answer, so a default would be an invention", which this file and PromptState both carried from the buttons' first day). A prompt DOES have an Enter answer now and it is that focused button, and what makes it safe is not an empty ring but two facts: the last button is always the ESCAPE SENTINEL by construction (all four raisers put '\x1b' last — Save/Discard/CANCEL, Retry/Discard/CANCEL, Yes/CANCEL, and the error notice's lone OK, which IS the sentinel), so the free answer is the non-destructive one; and the PAINTED GATE below already consumes every key until the prompt has been on screen, so an Enter queued behind a raise still answers nothing. THE BUTTON FACES AND THEIR ACT WERE SETTLED 2026-08-13 (architect: "the modal buttons should basically look like the icons, but with a resting outline"), in four parts. (1) THE RESTING OUTLINE: a dialog button at rest wears a 1px `kRedesignLine` #535659 frame at the icon row's corner radius over the bare row ground — no fill, nothing else — and that value is not a new constant and not a re-sample, being both this product's chrome-line grey and the grey modal_popup.png measures on its own non-default buttons, two facts that agree. (2) THE OTHER FACES ARE THE ICON ROW'S, un-re-derived and read off `paint_icon_row` itself through the shared `redesign_face_box`: HOVER swaps the resting grey for the 1px `kRedesignAccent` frame, PRESSED adds the interior at `kRedesignClickMix` (30% accent over the row ground) under that frame, and there is NO selected and NO disabled face — a dialog button is live for as long as its dialog stands, so the icon row's selected fill and its disabled mix have no counterparts here and were deliberately not invented. (3) THEY ACT AT THE RELEASE ("everything else acts on lift"), which is what makes the click face real: a plain left press ARMS the button and paints it, the lift ON THAT SAME BUTTON runs the act, and a lift elsewhere dispatches nothing. THE ARM SURVIVES THE POINTER SLIDING OFF — THE FEINT (architect 2026-08-13, SUPERSEDING the same day's "sliding off cancels through the hover walk, and sliding back on does NOT re-arm"): "if the user feints — clicks a button and then drags away before the mouse goes up — then that button receives the passive focus as well. And while the button is being held, but away from the button's hit area, the button looks like a hover — a passive focus with the hover. And then when they release it, it goes into being a passive focus." So the arm is ONE index for the life of the hold and the hover walk only answers whether the pointer is INSIDE it: inside is the pressed face and a committing release, outside is the passive-plus-hover face and a release that commits nothing and leaves the button passively focused, and sliding back ON restores the pressed face and its committing release — nothing was cancelled, so nothing has to be re-armed. The reason is in the ruling itself: a button that keeps a lit face while held away is still engaged, and a dead arm could not light anything. BOTH GATES HOLD AT THE RELEASE, not just at the press (`PromptState::painted` for the prompt claim, the owner tag for both), and the painter drops the arm on every edge that changes the dialog, so an arm can never outlive the surface it was made on. The arm is `AppState::modal_dialog_pressed` and deliberately NOT the roster's `redesign_pressed`: that field indexes the roster, and its face survives the pointer wandering off precisely because its chord already fired at the press — both facts are wrong for an act that has not happened yet. (4) THE KEYBOARD FOCUS RING, the modal's one face with no icon-row counterpart and so the one that needed sampling; it has TWO STRENGTHS since later that day (architect, from kdenlive), and BOTH ACT. PASSIVE focus is ASSIGNED and never walked onto — a prompt's raise puts it on the last button, and a feint puts it on the button that was held away — and it paints `kModalFocusFill` #2d4655 under a 1px `kModalFocusLinePassive` #4882a1 and NO halo. ACTIVE focus is reached ONLY by a deliberate keyboard walk (Tab, its two reverse spellings, Left, Right) and paints the same fill under the ordinary accent outline PLUS the 2px `kModalFocusRing` #284c61 halo OUTSIDE the box; there is no route back down to passive except a new passive assignment. That ring's space is RESERVED around every button and painted for one, so moving the focus reflows nothing (32 + 2 + 2 fits the row's 50px content band at every scale — both terms ride `gui_scale_factor`, leaving 9 authored px of vertical margin against the ring's 2). THE LADDER IS A COMPOSITION OF THREE INDEPENDENT FACTS, not an enumeration, and the painter writes it as one: the FILL says the focus (either strength wears it; a live press, pointer-inside or keyboard, outranks it with the icon row's 30% click mix), the OUTLINE says who is CLAIMING the button (accent for the pointer, a live arm or the active walk; the passive line when only an assigned focus does; the resting `kRedesignLine` otherwise), and the HALO is the active strength alone. Two rungs therefore fall out rather than being written, and both read like omissions unless named: ACTIVE FOCUS PLUS HOVER IS IDENTICAL TO ACTIVE FOCUS (the outline is already accent), and PRESSED outranks every fill above it. THE PASSIVE LINE HAS ITS OWN CROP — focus_passive.png, whose horizontal scan through a passively focused "Cancel" reads ground, 1px #4882a1, then the #2d4655 interior with no outer band at all, against the active scan's 2px #284c61 + 1px #3daee9 over the same fill. TAB cycles the whole ring INCLUDING an editor's text field (one field and two buttons is three stops, wrapping); on a PROMPT, which has no field, it cycles the buttons alone. LEFT/RIGHT move between BUTTONS ONLY and are INERT in the field, the arrows belonging to the text there. BARE ENTER AND BARE SPACE PRESS THE FOCUSED BUTTON DOWN AND COMMIT IT AT THE KEY'S RELEASE (architect 2026-08-13: "in kdenlive, pressing Enter when a button has focus pushes down the button. It doesn't automatically commit the action... we move the playhead when the user lifts up the mouse key, so we should do that here as well") — the keyboard's own act-at-release, matching the pointer's, over `AppState::modal_dialog_key_pressed`; the act cannot fire twice under a hold by two independent facts (the two keys never arm platform repeat while the focus is on a button, and the press body refuses a synthesized repeat outright), and the release re-asks the dialog's gates through the SAME shared dispatch the pointer's two release arms use. WITH FOCUS IN THE FIELD neither key reaches the ring at all, so Enter keeps its commit and Space still types a space. IT IS THE PLATFORM'S ONE KEY-RELEASE CONSUMER: releases were platform-internal until this landed, and `set_on_key_release` delivers the press's own key identity, ungated on Super (a release binds nothing on its own — gating it would strand exactly the arm whose press got through before Super went down). A HELD TAB WALKS THE RING REPEATEDLY (architect 2026-08-13 at his live test: "a held tab does not key repeat. It should") AND IS THE ONLY KEY THAT REPEATS ON A MODAL SURFACE — the ring's walk is a continuous step gesture in exactly the sense the marker cycle is, and its shapes are read here from the same `modal_ring_tab_shape` the gate and the completion arm read rather than re-spelled. The cause of its not repeating was two arms of `repeat_eligible`, neither of which had anything to do with the ring: a blanket `app.prompt.active` refusal at the top, and an in-editor arm that repeats only the classifier's MotionEditKey and PrintableKey, which the Tab family (NotEditorKey) is not — so the global marker-cycle line further down, which does admit the family, was unreachable under any editor. THE PROMPT'S BLANKET REFUSAL STAYS for every other key, and the reason is recorded at the site: a prompt's one-key answers must be one-shot, a held response key repeating being exactly the destructive shape the painted gate exists to prevent, while the ring's walk is safe under a hold precisely because it decides nothing. A REPEATING WALK IS COHERENT WITH THE ONE AUTOCOMPLETE MODEL and needs no term for it: the first fire in a field with a live completion completes and is consumed, and no later fire can complete again — the buffer is already AT its completion, so the advancement test answers false and every subsequent fire walks, including after the ring wraps back onto the field. AN EDITOR DIALOG OPENS WITH FOCUS IN THE FIELD (the user is there to type, which is also what keeps the editors' keyboard contract byte-identical), A PROMPT WITH PASSIVE FOCUS ON ITS LAST BUTTON (2026-08-13, retiring "a prompt opens with NO button focused" and the no-focus stop in its cycle with it — the supersession and the two safeties are recorded above and at PromptState). The state is `AppState::modal_dialog_focus` plus `modal_dialog_focus_active`, whose -1 means THE FIELD on an editor and, on a prompt, a cold value only — the window between a raise and the paint that assigns the focus, which the painted gate makes unreachable by input — and it resets structurally in `paint_modal_dialog` alone: with the stash when no dialog stands, on any change of the stash's owner, and on a prompt's FIRST PAINT (which rides the `painted` bit, so a prompt replacing a prompt cannot inherit the previous question's focus either). THE ADMITTED KEY SET GREW BY EXACTLY ONE SHAPE for all of this: bare Tab, from "the settings and load editors only" — where it was already admitted as their autocomplete — to "any dialog editor", so the commit-title and BPM editors, which complete nothing, can enter the ring. Everything else is byte-identical: Left, Right and Enter were always admitted as editor keys and change meaning only while focus is on a BUTTON, a state that did not exist before; the FIELD's Tab OFFERS ITS AUTOCOMPLETE FIRST wherever there is one — THE ONE AUTOCOMPLETE MODEL, architect 2026-08-13 at the day's end ("how about first tab autocompletes, second tab (or tab on a non-matching string, i.e. a string that does not autocomplete) moves focus? And we revert the settings editor to that model also — we should use one model for all autocompletes"), which retired the TYPED `=` trigger the settings editor had worn for a few hours of that day and put its value completion back on Tab beside the load editor's. THE COMPLETION REPORTS WHETHER IT ADVANCED THE BUFFER and that answer alone decides: advanced, the key is consumed; did not, the key falls through to the ring. "Second Tab" and "Tab on a string that completes to nothing" are THE SAME CONDITION, so the model carries NO press counter, NO timer and NO last-key bit — after a completion the next Tab cannot advance (the settings editor's value side is no longer empty, the load editor's buffer is already at the longest common prefix) and walks by that one test. Consequences: both completing editors reach their ring by Tab (the hours-old residual that had left the load editor's ring Tab-unreachable is CLOSED by the same rule, and the `h` history view — where the buffer is a commit spelling or a member number with nothing to complete against — gets a working ring there for the first time), a Tab with focus ON A BUTTON never completes at all since a button has no field, and SHIFT+TAB NEVER COMPLETES EITHER — IT WALKS THE RING BACKWARDS (architect, later the same day: "also, shift+tab should cycle backward"), the forward arm's exact inverse over the same stops with the same wrap, shift meaning "go back" and never "complete". THE REVERSE SPELLINGS ARE THE LIVE MARKER CYCLE'S, not a third convention for the same physical gesture: Shift+Tab and IsoLeftTab, the latter SHIFT-AGNOSTIC because that keysym rides the Tab key's shift level and a layout may deliver the reverse either way (`is_tab_cycle` and the `h` view's diff-flag cycle read it identically), ctrl and alt refused on every arm — and all three sites that must agree about a Tab (the gate's admission, the ring's walk, the completion arm that fires on the FORWARD shape alone) read ONE predicate, `modal_ring_tab_shape`, rather than three hand-kept lists. The gate's admitted set grew by exactly that family and nothing else, the ring's bare-exact modifier guard is widened for exactly that shape — on this rule's own untightened-families precedent (`is_tab_cycle`, Ctrl+Z's shift-selects-redo, the editors' motion arm: the modifier is a real binding there, and here shift is the reverse walk's binding) — and everything else in the ring stays bare-exact. The model's authoritative statement is at `route_modal_editor_key`'s Tab arm (input_key_dispatch.cpp) and every other site points at it. Esc, Ctrl+S and Ctrl+Q are untouched; and on a prompt Tab, Left, Right and Enter were all consumed no-ops before the ring, so nothing was taken from anything. NO KEY REACHES THE FIELD WHILE THE FOCUS IS ON A BUTTON (architect 2026-08-13, at his live test: "hit Tab twice more to reach Cancel, then press Space. I expect Cancel to be pressed, but instead a space character is added to the text field even though the text field has now lost focus"). Not typing, not motion, not editing: the buffer and the selection are preserved untouched and the keys simply do not arrive, which is what focus MEANS everywhere else in this product. Anything the ring does not itself claim is a CONSUMED NO-OP — except the modal contract's own three commands, bare Esc, Ctrl+S and Ctrl+Q, which work from a focused button exactly as they do from the field. AND THE FIELD PAINTS NO CARET AND RUNS NO BLINK THERE, the same test's other half ("the blinking caret, the I-beam, continues to blink in the text field even though it has lost focus"): one term, the ring's own -1, read by the painter and by the tick's blink poll alike, so an unfocused field neither draws a caret nor wakes the loop twice a second to toggle one nobody draws. THE SELECTION HIGHLIGHT IS DELIBERATELY NOT GATED — it is buffer state, not focus, and it must still be there when the walk comes back. The walk COMING BACK restarts the blink phase (`text_editor::touch_blink`, made public for that one caller), so a re-focused field shows its caret at once instead of possibly landing in the dark half of a period it kept running through. ONE ORDERING FIX RODE WITH ALL THIS: the editor buttons' act synthesizes the session's own Enter/Esc INTO the editor's key route, which offers every key to the ring first, so it now returns the focus to the FIELD before dispatching — with the focus left on a button the ring would have claimed the synthesized Return as that button's own press, and while it ACTIVATED at the press (2026-08-13's first shape) that loop was unbounded recursion. The pointer path never hit it (it reaches the act with the focus in the field); the keyboard's Enter on an editor dialog's OK button had no other end. Returning to the field is the act's own semantics besides: a red-flash refusal leaves the user where the fix is typed. A PROMPT ANSWERS ONLY AFTER IT HAS PAINTED (2026-08-13, codex round 13): one dispatch batch arrives whole before the loop paints, so a key queued behind the raise itself could answer a question that had never been on screen (Ctrl+Q tearing an editor down into the unsaved-close prompt, a Delete right behind it discarding the work) — `PromptState::painted` is false at every raise (through the state's ONE raise route, `present`) and set true by the prompt branch of `paint_modal_dialog` in the same iteration and buffer the frame commits, and while it is false the prompt CONSUMES EVERY KEY (responses, Esc, Delete and the paste-confirm's Ctrl+Q hatch alike) and its pointer response claim answers nothing (the veil still swallows the press; the claim needs the gate because the button rects it reads are the previous paint's publication, and the save-failed rung's restatement leaves live-keyed rects at coordinates the new layout no longer uses). THE FOUR EDITOR DIALOGS ARE DELIBERATELY NOT GATED — a queued key types into the buffer, non-destructive and self-evident once painted, the destructive shape being the prompt's one-key answers, and THE ONE POINTER RESIDUAL IS CLOSED (2026-08-13, with the move onto the row): a press on a stale PROMPT rect could cancel an editor that had just opened, and `ModalDialogGeometry::owner` — None/Prompt/Editor, written by the PAINTER alone and required to agree with the surface owning input at each of the two press claims — refuses it as a consumed no-op. It cost one enum and no generation machinery, because PUBLISHED GEOMETRY MAY ONLY SELECT; LIVE STATE DECIDES: hit geometry stays the painted stash (the displayed basis, screen and hit agreeing always) and the tag is that model's re-validate-at-dispatch half, with no deferral and so no input lag — the mismatch span is one dispatch batch, reachable only by a queued burst, which is exactly what must be refused (the doctrine is recorded at ModalDialogGeometry, app_state.h; the field claim needs no tag term, a prompt publishing a zero field and a false DialogEditorText.valid) — and the whole rule, with the second-surface contrast, lives at PromptState (app_state.h). AN EDITOR dialog is its prefix as the LABEL at the row's left pad, the buffer in a DARK INSET FIELD (editor.png's look, vertically centred in the lane — the existing text_editor machinery whole: selection, caret, click-to-caret, byte-identical editing; the invalid red flash RECOLORS THE FIELD in the marker-flag red pair), plus OK + Cancel after it, and THE FIELD TOOK THE BUTTONS' CHROME 2026-08-13 (architect at his live test: "give the text editor the same rounded corner as the buttons have, the same corner radius, and the same outline — the breeze blue highlight — when it's hovered and when it has the focus") — the same `kIconCornerRadiusPx` through the same shared `redesign_face_box`, so field and button describe their corners with one expression; REST keeps the field's own sampled `kModalFieldBorder` over its dark ground, and HOVER (a new pointer fact resolved on the buttons' own hover walk against the published field rect, `AppState::modal_dialog_field_hovered`) and FOCUS (which needs no term of its own, `modal_dialog_focus < 0` already meaning the field on an editor dialog) each swap that 1px border for `kRedesignAccent` with the ground untouched. THE FIELD'S FOCUS INDICATOR IS THE OUTLINE ALONE, deliberately, where a BUTTON's is fill + outline + a 2px halo: the field's dark inset ground is what makes typed text readable, a button's focus fill would destroy that, and a halo would need reserved room the field — the surface that already absorbs the row's shrink — has none of. The red flash's 1px top edge is CLIPPED TO THE ROUNDED INTERIOR rather than dropped, so the invalid state keeps the fill-under-an-edge anatomy it shares with the flag editor instead of reading differently on the two surfaces that share the one red. AND THE FIELD SCROLLS HORIZONTALLY since the same day (architect, same test — a Tab-recalled `notes=` value is longer than the field and "the viewport in the text field is always stuck on the left edge of the text... it should allow me to, just like in a regular text editor, use left and right or home and end to go to the end of the string"): the standing "the dialog editors do not scroll" accepted cost is RETIRED, and the mechanism is THE FLAG EDITOR'S, not a second one — the same `text_editor::State::view_offset_px` and the same minimal-travel rule (scroll only as far as the caret demands and in whichever direction it left the window, then clamp to the run's own travel, with the caret's column reserved at the right edge), whose contract now lives at that one declaration for both surfaces. Its HOME is the editor session rather than the painter or the modal stash, which is what makes the reset free: `enter`/`deactivate` already zero it, so it resets when a dialog opens and dies with the edit, and since each of the four dialog editors owns its own State a change of the stash's owner is structurally a change of offset. THE PUBLISHED CLICK-TO-CARET ORIGIN CARRIES IT (`AppState::DialogEditorText::text_origin_x` is the window x byte 0 PAINTS at, pad and offset both spent), so the click, the F2.1 text drag and the double-click word select all land on the right byte on a scrolled field with no knowledge that it scrolled; the field's clip — narrowed to the band between the pads — hides the overflow, and the published byte geometry stays the painter's unclipped truth. THE TOP-STRIP FLAG EDITOR IS UNTOUCHED BY BOTH: it is not a dialog, its geometry is `FlagEditorBox`, and it had the scroll first. dispatching the session's own Enter and Esc through the one modal key route — button-is-its-chord. THOSE TWO NEVER WORE BRACKETS (architect 2026-08-13: "Enter and Escape are universal; on an editor you don't want to reroute letters") and name their keys on their tooltips like every other modal button now, and the FIELD absorbs the shrink on a narrow window exactly as it did in the box, at the same floor. The TOP-STRIP FLAG EDITOR IS DELIBERATELY NOT A DIALOG: it is positional, editing the marker where it stands, and stays the pointer-transparent unrolled flag. The FOUR dialog editors — the settings editor, the bpm editor (top_flag_editor with Kind::BpmBracket), the load editor (`load_editor`, Kind::LoadInPlace, opened by bare `'` to load a `renders/` entry in place by name — the standalone `load_render_entry_in_place`, a running-render-guarded wholesale load-in-place that replaces the retired render-view Ctrl+Alt+C), and, since 2026-08-07, the COMMIT-TITLE editor (`commit_title_editor`, Kind::CommitTitle, opened by Ctrl+S while the `h` history view stands (Ctrl+Alt+R until 2026-08-08, when the architect moved the Save-and-Commit act onto the SAVE button's chord — the act runs the ordinary save as its first step; github-recheck.md owns the move), prefilled with the checkpoint's default `Update <id>` message and committing the Save-and-Commit act under whatever it holds — it REPLACED that act's confirmation prompt, so the prompt count went down as the editor count went up; github-recheck.md owns it) — and every prompt. While a dialog editor is open, only the editor's own keys plus bare Esc, Ctrl+S, and Ctrl+Q get through (`modal_editor_key_blocked`, the sibling of the read-only allowlist — the keyboard contract is BYTE-IDENTICAL across the move to the dialog); the pointer meets THE VEIL: the window behind the modal is FULLY INERT — every press, motion and wheel outside the modal's surface is consumed (no dim layer: the palette is fully opaque by ruling and kdenlive's own parent window stays undimmed, so inertness is behavioral), the modal's own pointer surfaces being the editor's FIELD (click-to-caret and the F2.1 text drag, through the painter-published geometry) and its BUTTONS, and the cursor is the Arrow over veil, surface and buttons alike. THE OLD BOTTOM-STRIP POINTER MODEL IS SUPERSEDED BY THE VEIL, recorded loudly: a click outside the modal CONSUMES and the modal closes only by its own buttons and keys (the architect's words: "once I've done that pop-up modal, I can't do anything else in the window behind it") — WITH ONE DERIVED EXCEPTION since 2026-08-11, THE MODAL-TRAP FIX (architect, from the road: an accidentally opened settings editor on GLASS, with no physical keyboard, was an EXIT-LESS STATE — the Quit button did nothing): a plain left press on a roster button whose chord the editors' modal contract ADMITS AS A COMMAND dispatches through the ordinary one dispatch body — membership DERIVED from the admission (`modal_editor_admits_command_chord`, input_pointer.cpp, the contract's Esc/Ctrl+S/Ctrl+Q command tail restated for the pointer; today that resolves to QUIT and SAVE), never hand-listed, so the two buttons are their chords exactly where the chords are admitted (Ctrl+S saves with the editor open, Ctrl+Q runs the teardown and the close route) and every other press stays swallowed. The two menu ANCHORS carry no chord, so no press can open a popup under an editor and the popup/editor structural exclusion stands; the pointer-transparent flag editor never blocked these presses and needed nothing. Faces are untouched: the modal gates stay deliberately absent from `redesign_button_enabled` (a modal greying the chrome would be a fourth face nobody asked for), so the admitted pair already wears the enabled face — face and press agree where the press acts. Playback stops when any modal surface opens and cannot restart until it closes. The TOP-strip flag editor (FlagPayload, iter grammar included) IS KEYBOARD-MODAL TOO (architect 2026-07-28, REVERSING the long-standing "deliberately not modal — commands punch through" ruling): it admits exactly the same set, so an unbound chord is now structurally inert rather than a command that discarded the edit on its way to running. It keeps red-flash-or-exit-without-commit. ### Text is UTF-8 in Free Text, ASCII in Grammars
Architect-ruled 2026-08-02, retiring the "non-ASCII is unsupported" project line as a fossil of the deleted cairo monospace path — HarfBuzz on Liberation Sans renders Latin-script UTF-8 correctly today, so the restriction had outlived its cause. THE SCOPE IS TWO-SIDED. FREE TEXT takes UTF-8 verbatim: the five editors' buffers (the commit title among them since 2026-08-07 — a commit message is free text, and git carries UTF-8), the free-text settings values (`title`, `bpm`, `notes`, `url`, `cover`, `audio_player`), and the whole load/display/edit/recall/save round trip, which is byte-identical end to end (the old `autocomplete_value` recall-strips-non-ASCII exception is CLOSED, since the filter that caused it is the one that relaxed). STRUCTURAL GRAMMARS STAY ASCII, unrelaxed and unquestioned: marker labels (`is_valid_label_format`'s ranges, which also enforce lowercase), every numeric spelling, the settings keys and value vocabularies, the canonical-line payload grammar. Marker FLAG TEXT is therefore ASCII by construction — nothing composed into a flag box comes from a free-text field — which is what lets `cap_marker_label` walk it by byte (render.h, kMarkerLabelGlyphBudget). Render-entry identifiers are FILESYSTEM PATHS, bytes rather than text, and are untouched by the ruling.

TWO EXCLUSIONS, both accepted rather than deferred: NO FONT FALLBACK (one face; an uncovered codepoint draws .notdef — the one-face rule is the model, and Pango stays out of the tree), and NO BIDI OR COMPLEX SHAPING (single-direction LTR runs only). A third belongs with them: GRAPHEME CLUSTERS ARE OUT OF SCOPE — the editors move by CODEPOINT, so a combining mark carets and deletes on its own.

THE MECHANISM IS THREE PARTS, each with one owner. (a) The INCOMING FILTER is `text_editor::replace_selection` alone: printable ASCII and well-formed multi-byte UTF-8 pass; ASCII control bytes and malformed sequences (a lone continuation byte, an overlong form, a truncated tail, a surrogate) drop one byte at a time so the good text around them survives. Its malformed arm HAS A LIVE PRODUCER since the system clipboard landed the same day: a Ctrl+V hands another application's bytes to this filter unexamined — the platform reads the pipe and passes the payload through whole, deliberately, because one incoming filter is the design and a second one at the platform boundary would be the duplicate predicate the topology forbids. (b) The TYPED PATH needs no boundary fix: `xkb_state_key_get_utf32` already hands over a full codepoint, so a compose or dead-key sequence arrives whole and the editor UTF-8 encodes it into one insertion. (c) EDITOR INTERNALS index by BYTE but MOVE BY CODEPOINT — Left/Right, BackSpace/Delete, the Ctrl word walks (bytes ≥ 0x80 classify as word, which makes the byte walks boundary-safe without a decoder), the double-click run selector, and the click-to-byte search, which cannot return a mid-codepoint index because `byte_offsets_px` gives a cluster's interior bytes its START pen and the nearest-boundary tie keeps the lower index. `cursor_pos` and `selection_anchor` are codepoint boundaries by construction; the per-Kind caps are BYTE caps. The contract is authoritative at the head of `text_editor.h`.

A hand-edited file carrying malformed bytes still LOADS VERBATIM — no new refusal, no migration; those bytes shape as .notdef or garbage, which the architect accepted.

### The Clipboard is the System Clipboard
Architect-ordered 2026-08-02, restoring the Wayland clipboard half of what `e0c988c` removed as collateral when the in-session file load was killed. Drag-and-drop and the file load STAY DEAD — nothing of them came back, and the `wl_data_device` listener's four DnD slots are inert stubs that exist only because libwayland aborts on a NULL slot. Primary selection (middle-click paste) is out of scope: `zwp_primary_selection` is not bound.

THE REACH IS EXACTLY WHAT IT ALREADY WAS — no new chord, no new binding, no new gate. `Ctrl+C` / `Ctrl+X` / `Ctrl+V` inside the editors (ctrl-exact, as the strict-modifier rule below has them, and already admitted editor keys) and the readout's `Ctrl+C` are the whole vocabulary; the ruling moved only where the bytes go and come from. Copy and cut publish the selected text straight to the compositor, and the readout copy does likewise. THE PAYLOAD HAS ONE REPRESENTATION, the platform's `clipboard_send_text_` — which must exist anyway to service the compositor's later `send` event, and which owns the self-paste short circuit. `AppState::text_clipboard`, the session-only string the editors used before this, is DELETED: every reader it ever had was a pass-through handing it back to `clipboard_set_text`, so a second copy bought nothing but drift risk, and a copy site now composes its string, hands it over, and keeps none of it. (The phase-reset propagate clipboard is a different concept and is untouched.) A paste asks the platform: our own payload while we still hold the selection (the self-paste short circuit — reading our own selection back through the pipe would deadlock the single-threaded loop against itself), another application's text once somebody else has taken it. AN EMPTY ANSWER IS A CONSUMED NO-OP — no offer, no acceptable text mime, or a failed read all mean there is nothing to paste, and pasting nothing must not delete the selection instead. That closed a real pre-arc edge as a side effect: `Ctrl+V` with nothing ever copied used to delete the selection.

THE PROTOCOL SIDE. `wl_data_device_manager` is CORE protocol, so it needed no library, no pkg-config entry and no generated stub; it is a REQUIRED global under the `xdg-decoration` precedent (see validation_topology.md's platform-startup row), with v2 as the bind floor and v3 the cap. The accepted mimes are `text/plain;charset=utf-8` preferred and bare `text/plain` as fallback, compared case-insensitively because the charset parameter is (GTK and Qt applications disagree on the spelling), and the EXACT offered token is what `receive` is handed back. The read is synchronous — a keyboard-triggered short string can afford it — deadline-bounded at one second and capped at 1 MiB, with every failure returning nothing rather than a partial paste. `set_selection` rides the serial of the triggering key event, cached at `on_keyboard_key`. The lifetime rules (an announcement is not a claim; one teardown, two exits; NULL is a real selection event; ownership is a bit, not an object) are authoritative in the clipboard section header of `platform_wayland.cpp`.

### Why the Editors Need No Stray-Modifier Class
A key that wears a stray modifier on a shape the editor owns (Ctrl+Escape, Ctrl+Enter, Ctrl+Shift+V, Ctrl+Alt+A) is simply NotEditorKey like any other unbound chord, and drops at the keyboard-modal gate before anything can act on it. It was not always this simple: while the flag editor was non-modal its NotConsumed tail CANCELLED the in-progress edit on the way to global dispatch, so "unbound" and "not ours" could not be allowed to look alike — a `KeyClass::StrayModifierKey` named the first and claimed it inert. THE MODALITY RULING DELETED THAT MACHINERY (2026-07-28, hours after it landed): with the tail gone both classes end in nothing happening, the only residual difference being one wasted repaint of unchanged pixels, so the enumerator was removed and the classifier returned to its plain form with the two arms simply modifier-exact (bare for the session keys, ctrl-exact for the chords). RECORDED BECAUSE THE REASONING GENERALIZES: a destructive fall-through is what forces a codebase to distinguish "unbound" from "unowned"; remove the destruction and the distinction stops paying rent. Prefer removing the surface to maintaining the class that guards it.
