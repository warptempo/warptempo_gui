# The Kdenlive Redesign (row-by-row)

Chartered 2026-07-30, implementation began 2026-07-31. The architect works TOP-DOWN, row by row, by dropping screenshot crops into `tmp/screenshots/kdenlive/redesign/` and pointing the planner at them — every state a surface has (rest, hover, clicked, ...) gets its own crop. Do not run ahead of the screenshots. Design parity is "loosely held, with room for tailoring to our needs"; workflow parity stays Ableton. Design and testing happen at 100% `gui_scale`; 1920x1080 remains the only supported resolution.

## The standing rulings (apply to every row)

- THE CSS FLOAT MODEL (architect 2026-07-31, ruled at the row-1 live test): the architect describes rows in CSS box vocabulary — content dimensions, margins, borders, padding — and a stated dimension NEVER includes a border. A flat button with nothing stated fills its whole row; the first row starts at the very top; NO margin/inset/gap exists unless he states one ("I will tell you when there's spacing — don't assume that"). Adjacent buttons get a 2px gap that is an INVISIBLE SEPARATOR, not margin.
- CORRECT CAPITALIZATION (architect 2026-07-31 row-by-row; GENERALIZED 2026-08-01; COMPLETED 2026-08-02): with the rows complete, ALL GUI-facing text uses proper capitalization — and the terminal stderr/stdout pass landed 2026-08-02 (text-only, otherwise byte-identical, the wide frozen touch recorded per file), so the all-lowercase rule is fully retired. The completed rules live in conventions.md.
- THE REDESIGNED ROWS ARE WHEEL-INERT: one band test at wheel_context (returns the inert class above the area tests); future rows join by extending the band.
- BUTTONS DISPATCH THEIR CHORDS THROUGH on_key (a synthesized GuiInputState — the button IS its chord): every gate the keyboard route passes (loading/blank, keyboard-modal, read-only, the arm's own refusals) applies identically and nothing can drift. The exception is a button whose action is not a chord dispatch, and re-derived from `kToolbarChords` against the roster that is the PAIR SETTINGS AND NAVIGATION, the two menu openers each toggling its own dropdown, which no keyboard chord does (Settings alone from 2026-07-31, joined by Navigation when the second menu landed 2026-08-02; Quit is not one of them — it joined the table once Ctrl+Q's route was verified byte-equivalent). Everything else on rows 1 through 4 dispatches.
- ICONS are in-tree Breeze paths rendered by src/gui/icons.{h,cpp} (an SVG d-string subset interpreter over cairo paths, GUI-only; provenance SVGs committed verbatim under assets/icons/breeze/, read by no code). Icon colors are the SVGs' own, hard-coded per the color ruling.

- THE SCREENSHOTS OVERRIDE ALL PRIOR COLOR WORK (architect 2026-07-30/31; the shrink COMPLETED with rows 5-6): every color a redesign row touched is HARD-CODED from its sampled crop (constexpr, not a key) — and the rows ultimately touched everything, waveform and markers included. The shrink's endpoint arrived 2026-08-02: colors.conf AND ITS MACHINERY RETIRED WHOLE (the loader, the grammar, the ~/.config read all deleted; the last two live keys — the chrome erase and the scanner line — hardcoded at their conf-identical values, zero pixel change; the record is the render.h palette header, the deleted keys' values git history).
- THE SANS FACE IS THE PRODUCT'S ONLY FAMILY (the redesign's default, and since row 7 the only one): cairo toy selector "sans" (fontconfig → Liberation Sans on the target) at 12pt through the points×4/3 convention (16px at 100%), scaled on gui_scale alone (redesign_font_size_px, render.h — the product's ONE text size). The monospace face is DELETED WHOLE (row 7, 2026-08-01) and the font_size key with it.
- ALL REDESIGNED TEXT GOES THROUGH THE SHAPING CHOKEPOINT (`src/gui/text_shape.h`, HarfBuzz over the cairo font's own FT face): the shaped run is the single width truth — measurement, paint, truncation and hit geometry all read the same run. No Pango, no cross-font fallback, no bidi — one wide-coverage face is the model.
- ALL DIMENSIONS RIDE THE gui_scale AXIS (`gui_scale_factor()`, render.h — the product's ONE scale axis since row 7 deleted the font axis; push plumbing at the three application points, recorded at the accessor's declaration). Crop-measured 100% values are the authored constants; every conversion rounds with std::nearbyint. Fills land on integer pixel bounds; axis-aligned 1px strokes, when a row ever has them, take the cairo +0.5 half-pixel alignment so nothing axis-aligned antialiases.
- HIT GEOMETRY IS PUBLISHED BY THE PAINTER where a rect depends on shaped text (the displayed-basis doctrine applied to proportional surfaces): the painter stashes the rect it painted; pointer code reads the stash and never re-shapes.
- BUTTON HOVER STAYS LIVE UNDER KEYBOARD MODALS (2026-07-31, from the Settings-button staleness bug: the prompt and bottom-strip-editor motion gates returned before the hover recompute, freezing a lit pill until the first post-close motion): the recompute now runs in those modal branches too — the argument is that button hover is a SEPARATELY MAINTAINED POINTER FACT ("the pointer is over this rect" is true or false whoever owns the keyboard), NOT that those surfaces pass pointer input through: only the top-strip FlagPayload editor is pointer- and wheel-transparent, while the settings editor, the render-commit editor and the BpmBracket kind swallow every press outside their own text row (`modal_bottom_strip_editor_active`, which is also the wheel swallow). The marker hover popup's modal suppression was its own ruled exception, and it is gone with the popup. Active pointer GESTURES still freeze hover. Accepted residual: a lit pill under a prompt advertises a press the prompt will swallow. No close-edge hook exists or is needed. THE TOOLTIP IS EXCLUDED FROM THAT RESIDUAL (2026-08-03): the same recompute refuses to start a dwell while a prompt or a keyboard-modal editor is up, because a floating hint hanging past the strip is a second surface rather than a face — the tooltip record below carries the rule.
- THE UNFOCUSED-WINDOW GROUND (architect 2026-07-31): the crops' #292c30 is the FOCUSED Breeze header shade; on window deactivation rows 1-2 swap their ground to kRedesignRowGroundUnfocused #202326 (matching the labwc titlebar's own darkening; row 3 already lives on that value and never swaps; nothing else changes color, hard swap, no fade). Plumbing: the xdg_toplevel configure states array yields XDG_TOPLEVEL_STATE_ACTIVATED → GuiPlatform::window_activated(), an EDGE-ONLY activation hook (resizes re-deliver the same set) mirrors into app.window_activated and damages the top strip. THE FACE MIXES FOLLOW THE CURRENT GROUND: the disabled 0.322 and the click 0.30 are RATIOS the crops pin (the sampled #2f5368 is exactly mix(accent, ground, 30%) — a relationship, not a fifth sample; the kRedesignClick literal is replaced by kRedesignClickMix), so focused paint reproduces both crop samples bit-for-bit and unfocused paint derives consistently.

## The floating surfaces — the shift tooltips and the settings dropdown (landed 2026-07-31)

DISARMED BY every ordinary dismissal (bare Esc, an item activating, the anchor click that closes its own menu, a press anywhere else that closes the popup, the wheel, Ctrl+Q, the WM close, a resize) through the one close owner, because a dismissal the user MEANT must end the mode, or Esc would put away a menu the next pointer twitch reopens; DISARMED BY ANY POINTER PRESS and ANY KEY PRESS, at the tops of `on_button_press` and `on_key`, which is what covers the dismissals that never reach the close owner at all — a view-bar press or a `;` arriving with no popup open — and which needs NO exception list, because the one press that must keep the mode is the anchor press and it re-arms through `toggle_dropdown`'s open a few lines later, while no keyboard chord opens a dropdown at all; DISARMED BY the pointer leaving row 1's band with no menu up, which is what keeps the mode from outliving the visit (wander down to the waveform and Settings needs a click again); and DISARMED BY the pointer leaving the window, on the platform's existing pointer-leave hook beside the row's other face clears, since no motion event follows that edge. THE "NO MENU OPEN" GATE ON ALL FOUR OF THOSE DISARMS is the one place this rule can go wrong, and it lives inside `disarm_menu_row` rather than at any caller: with a menu OPEN the band no longer contains the pointer as soon as it moves into the popup, leaving the WINDOW is explicitly not a dismissal (the popup stays up, as `clear_dropdown_press` states), and a press or a chord arriving while a popup stands belongs to the POPUP, whose own routes call the close owner — so a standing menu is still the mode and the two blanket disarms can never get in front of it. THE TWO MOTION HALVES ARE SPLIT BECAUSE THEIR GUARD LISTS ARE OPPOSITE, and that is the second correction of the same day's first form, which had both inside one function in the no-gesture tail: THE OPEN HALF (`open_menu_row_anchor_on_hover`) keeps that tail and every guard it confers — its placement IS its guard list, so every condition it must not fire under is a branch that already returned above it (the open dropdown, the prompt, the editor text drag, the two bottom-strip keyboard-modal editors, every live gesture and pending), nothing is restated, no guard is added, and that tail is EXACTLY the reachability the anchors' own press claim has, so the hover opens a menu in precisely the states in which a click opens one — including the one asymmetry the press claim already carries, the pointer-transparent FLAG editor, which gates neither route, and which both routes END, since the discard sits in `toggle_dropdown`'s open path they share rather than at the press claim. THE EXIT HALF (`update_menu_row_exit`) runs at the TOP of `on_motion`, above every branch, because a modal owning the pointer is a reason not to OPEN a menu and no reason whatsoever to forget that the pointer left the row: in the tail it could not run while a prompt, an editor or an editor text drag owned motion, so the pointer could walk off row 1 under one of them and carry an invisible armed mode out of the visit. Running it during a live gesture costs nothing and changes no rule — the gesture's own press already disarmed — and it stays correct with a menu open through the same `disarm_menu_row` gate. The mode paints nothing and damages nothing; what it changes is what the next motion does.
