# Region, Scrub, the Esc Bindings, x / Shift+X

Moved verbatim from CLAUDE.md in the 2026-07-25 slim-down (project feature-complete). This file is now the authoritative home for this detail; CLAUDE.md carries only a digest and a pointer here. Keep it current with landed rulings.
Continues from marker-ui.md.

THE REGION SIMPLIFICATION (architect-chartered 2026-07-30, the kdenlive redesign's opening arc; landed the same day): the region highlight is TRIM-ONLY FREE SCRATCH — "a temporary selection of what could potentially become a trim region" — and nothing else. The selection no longer paints a span, the cursor playhead is never suppressed, and the whole two-forms model (the region as the playhead's SPAN form, the split half-triangles, exactly-one-form-visible, the cursor/stem suppressions, the never-span-less guarantee and its producer analysis) is RETIRED. RegionProvenance is deleted whole — `RegionState` is `{active, a_frame, b_frame}` and nothing branches on where a span came from. The trim-window highlight coupling is retired with it: no route publishes the trim window as a region any more (`sync_region_to_trim_window` and both wrappers are deleted), the trim window's permanent display being its always-painted bar and endcaps, which are ALWAYS painted now that trim is always-set (normalization-and-boundaries.md owns that model).

TWO GESTURES HAVE BEEN CALLED "THE SCRUB"; ONLY ONE KEEPS THE NAME (architect 2026-07-28, stated here because this file is the docs map's designated scrub owner). (1) THE AUDITION SCRUB — the one-shot waveform press, `scrub_press_at` / `scrub_act_at` / `scrub_launch_at`: stop a live session, else launch one at the clicked column. It owns the word, it is the only thing `src/` names "scrub", and since the Space region launch's retirement (2026-07-30) the scrub presses are `scrub_launch_at`'s ONLY caller class. TWO PRESSES REACH IT since 2026-08-01: the LOWER-HALF PLAIN LEFT press (the original entry — the lower half is still the left button's whole scrub surface, its boundary the press test's own `y >= area.y + area.h/2` — the one expression, `waveform_lower_half` in input_pointer.cpp, since the pointer cursor's Scrub zone below became its second reader; the 1px channel-split line that drew that boundary from 2026-08-01 is RETIRED, architect 2026-08-03, so the gesture split is unmarked IN PAINT again — the two channel bands meet flush there and no pixel announces the threshold, and it is the CURSOR that names the surface now), and the BARE-EXACT RIGHT press ANYWHERE in the waveform, full height (the right button's first and only binding in the product; a modified right press is the standing strict no-op, and no gesture may be in flight — the gate is `any_pointer_gesture_active`, since a captured drag still delivers button events under the pointer lock; a right press outside the flag editor's box closes it exactly as a left press does — one shared owner since the architect ruled the divergence closed at his live pass, 2026-08-01). Both entries share the one derive-column-and-act body — the scrub is the REGION'S PREVIEW GESTURE by ruling ("user can click scrub region to preview"): it touches no selection, no region, no cursor and no follow state, so a scratch span rests through it and the user auditions the span by clicking inside it. (2) THE PLAYHEAD STEP — the horizontal ARROW keys, one painted column per press, TWO-LANE by the selection (see selection-model.md's lane model): with an EMPTY selection it is the waveform lane — stop playback, clear the focus, dissolve a resting region, move the playhead one column; with a NON-EMPTY selection it is the MARKER lane — the same press carries the FOCUSED marker (a position nudge in either column's home view; W+target is a consumed refusal), and the playhead rides along VISIBLY because every such route re-lands it on the committed focus. LANE EXIT IS ANY DESELECTING ROUTE (Home/End, a waveform click, a trim setter's deselect, an undo restore that empties the selection); a marker-lane press that refuses is a consumed no-op, never a waveform-lane step.

EVERY CURSOR THE PRODUCT SHOWS IS A NAMED CURSOR FROM THE USER'S OWN XCURSOR THEME (architect 2026-08-03, revising his own ruling of earlier the same day): THE SPEAKER IS RETIRED — the custom-drawn Breeze `player-volume` glyph, its ARGB32 wl_shm buffer, that buffer's dedicated pool and the whole `build_speaker_cursor` path are DELETED WHOLE, along with the `icons::Icon::PlayerVolume` entry and its committed SVG (kIconCount 14 back to 13; git history is the record, and the product now ships no cursor art and draws no cursor pixels). The architect weighed authoring our own set — outline, shadow, a de-plussed magnifier — against reading the theme's, and chose the theme's outright: a cursor is desktop furniture, and the one the user already recognises is better than the one we would draw. SEVEN KINDS, SEVEN NAMES, all present in Breeze_Light and in Adwaita: Arrow `left_ptr`, Scrub `crosshair`, Pan `grab`, Zoom `zoom-in`, TrimResize `ew-resize`, TrimBoundBegin `left_side`, TrimBoundEnd `right_side` (the last pair joined 2026-08-03 with the endcap split below — `left_side` / `right_side` are the arrow-with-a-bar shapes a window manager shows on a window's left or right edge, which is exactly the act they mark, extending ONE boundary). Each is a `wl_cursor_theme_get_cursor` lookup at init plus its own never-re-attached `wl_surface`, carrying THE HOTSPOT THE FILE DECLARES — never a centre we compute. What the code reads is `wl_cursor_image`'s INTEGER `xhot`/`yhot` out of the XCursor binary, at the size the theme load resolved (XCURSOR_SIZE, else the freedesktop 24), and the installed Breeze_Light serves that default request from its 32x32 images: `left_ptr` 4,4, `crosshair` 17,17, `grab` 16,16, `zoom-in` 15,15, `ew-resize` 16,15, `left_side` 4,15, `right_side` 27,15. The pointer-ish shapes are centred (grab exactly, crosshair and zoom-in within a pixel), `left_side` and `right_side` sit hard against their OWN edge — which is the whole point of an edge cue — and `left_ptr` sits at its tip; no rule we could compute produces all three, which is why the declaration is taken verbatim (and the numbers scale with the resolved size, so they are the default load's rather than constants). The lookup is ONE per-kind loader driven by a small `{kind, xcursor name}` table (`load_theme_cursor` / `load_cursor_theme`, platform_wayland.cpp), not seven copies of the arrow's old one-off. A MISSING NAME DEGRADES TO THE ARROW, PER KIND, with one stderr line naming the cursor that was missing — the theme load's own failure shape, which is the precedent: a theme without these names is a poor environment, not a broken one, and nothing about the product stops working. THE SIZE RIDES THE THEME'S AXIS (XCURSOR_SIZE, else the freedesktop 24), NOT gui_scale: gui_scale is the product's one scale axis for everything the WINDOW paints and a cursor is not painted by the window, so every kind loads at one size and the pointer does not resize as it crosses a zone boundary. THE PLATFORM STRUCTURE THAT SURVIVED THE SPEAKER is the part that turned out to be right: the `GuiCursorKind` enum, the REMEMBERED kind, `apply_cursor_kind` as the one applier with the capture guard inside it (the capture's hide is still the only `set_cursor` outside it, and the release restores the remembered kind rather than the arrow), and `set_cursor_kind`'s apply-only-on-change.

THE CURSOR PROMISES THE GESTURE, which is the whole rule and the whole design constraint, and it is why there is ONE zone map DERIVED FROM THE PRESS PATH rather than a list of situations invented beside it (`pointer_cursor_kind`, input_handler.h — one owner, two callers). The zones, each taken from the branch that actually claims the press: the waveform's LOWER half plain is Scrub (sharing the press's own `waveform_lower_half`); the waveform EITHER HALF with ALT held is Pan, because the captured grab-pan arms anywhere inside the waveform; the waveform EITHER HALF with CTRL held is Zoom, and so is the RULER band on a plain hover — the two surfaces share a cursor because they share a gesture, `arm_strip_drag_at`'s two entries; the TRIM BAR splits three ways (below); everything else is the Arrow. THE TRIM ENDCAPS ARE NOT THE BRIDGE (architect 2026-08-03, splitting what had been one band-wide TrimResize and closing both mismatches the cursor round recorded): an ENDCAP extends ONE boundary and takes its own bound's shape — the BEGIN cap `left_side` (TrimBoundBegin), the END cap `right_side` (TrimBoundEnd) — while the inter-cap BRIDGE keeps `ew-resize`, because the bridge drag moves BOTH bounds together and the move is what the caps are being distinguished from; CTRL and CTRL+SHIFT over the bar take the SAME PAIR matched to the bound each one writes (ctrl is BEGIN, ctrl+shift is END), because those clicks set a bound and arm a single-bound drag on it — boundary extension by another route, and the reason they no longer show the Arrow. AND THE CUE NOW READS THE ROUTER'S OWN OWNERS rather than the band: `hit_test_trim_endcap` and `point_in_trim_bridge_span` for the plain hover (the second hoisted out of `route_trim_bar_press`'s inline body when the cursor needed the same verdict — one owner, two consumers, the endcap test's twin) and `trim_bound_click_frame` for the two ctrl clicks (hoisted out of `set_trim_bound_at_click`, which keeps only the write), so a point on the band that would ARM NOTHING — the bar's outside on a trimmed-in window, or a ctrl click the STRICTLY-INSIDE guard would consume as a no-op — shows the Arrow, and cue and gesture agree BY CONSTRUCTION rather than by proximity. THE MODIFIER ARMS OUTRANK THE PLAIN ZONES ON THE WAVEFORM exactly as the press path ranks them. SHIFT IS NOT IN THE MAP over the waveform: it forms a region, which has no themed cursor worth borrowing, so it takes the Arrow like everything unnamed — and, being a modifier the waveform binds, it still refuses the Scrub cue exactly as it always did; the one place a shift combination IS named is ctrl+shift on the trim bar, a real bound-set claim rather than an unbound stray. EVERY REFUSAL APPLIES TO EVERY KIND, not just to Scrub — the prompt, the three bottom-strip modal editors, an open dropdown, a loading or empty audio state, and any live pointer gesture — which is what makes the cues HOVER-ONLY: no cursor changes during any drag, captured or not. ONE CONSEQUENCE IS STATED AND NOT FIXED: a live TRIM drag therefore shows the Arrow rather than keeping the endcap or bridge cue it started under, because the gesture refusal is uniform and does not except the gesture whose own cue it is. READ-ONLY IS PER-ZONE, each following its own gesture: the strip drag and the pan are navigation and do not refuse in a locked tab, an audition is not a mutation so the scrub does not either, but the TRIM drags DO refuse there (the band-level read-only return at the plain trim-bar press) and the endcap and bridge cues refuse with them — as do the two ctrl cues, through their own route, `trim_bound_click_frame`'s first gate being that tab's read-only bit, so the zone map tests nothing itself. THE FLAG editor refuses nothing — it is pointer-transparent by ruling, so a scrub still acts under an open one and the cursor may not lie about that. THE SCRUB ZONE IS THE LEFT PRESS'S, NOT `scrub_act_at`'s: the bare RIGHT press scrubs the waveform's FULL HEIGHT and is deliberately unmarked, because a scrub cue over the whole waveform would promise the left button something the upper half does not do. THERE IS NO PRESSED-STATE CURSOR AND NO "grabbing", deliberately (architect, explicitly): the alt-pan takes a pointer capture and the capture HIDES the cursor, which is what buys unlimited travel, and the strip drag does the same while painting a stem line that shows where the gesture is — a pressed cursor would flash for one frame and then be invisible for the whole gesture. MODIFIERS TAKE EFFECT AT ONCE (architect's bug report, fixed the same day): with modifiers now SELECTING between kinds rather than merely suppressing one, deriving the cursor on motion alone left the wrong promise on screen for as long as the user held still, so the platform fires a hook at `wl_keyboard.modifiers` — the modifier edge itself, which the compositor sends when that state changes and not on ordinary key presses — and main.cpp wires it to `refresh_pointer_cursor`, which re-runs the ONE zone map at the remembered pointer position with the new modifiers and does nothing else at all: no hover recompute, no damage, no gesture logic. THE ACCEPTED STALENESS IS NARROWER NOW rather than gone: a state change with NEITHER motion NOR a modifier edge under it — a load completing under a resting pointer, a menu closing by Esc — still shows at the next event of either kind. There is deliberately no tick hook: a cursor that repainted from a timer would be a second owner of the same fact.

THE PLAIN WAVEFORM PRESS splits by HALF (the scrub area, architect-designed 2026-07-23). The UPPER half is the placement press: it CLEARS THE SELECTION, drops the playhead at the clicked column (`playhead_frame_at_click_column` through the live-domain clamp; marker-BLIND — no snap magnet), reseeks a live scanner, suppresses follow for the session, and arms the region drag (`arm_region_drag_at`), which dissolves any resting highlight AT MOUSE-DOWN — so the old span vanishes on press whether the gesture stays a click or becomes a fresh drag. Past the shared 8px press-becomes-drag gate the drag extends a REGION: a span of ACTIVE-DOMAIN playable frames (`RegionState`, session-only, never serialized, outside selection AND undo — a SPAN, never markers), painted as an OPAQUE GROUND RECOLOR (`kWaveformRegionCanvas` since row 6, before the plate blit, so the waveform ink composites over it untouched — the Ableton read) with the CURSOR PLAYHEAD PAINTING STRAIGHT ACROSS IT like any other ink (2026-07-30 — the region is not a playhead form and suppresses nothing) — AND THE DRAG CARRIES THE PLAYHEAD (architect 2026-07-30, the live-test refinement: "the playhead move along with the drag ... more intuitive"): each motion event writes the cursor to the clamped moving endpoint, so the playhead visibly rides the pointer through the drag (playback untouched — the press's reseek stands, no per-motion reseek; a sliver release leaves the playhead where the drag put it). Endpoints are unordered (drag order); the painter and `x` normalize. Sub-threshold rested spans dissolve at release (the sliver rule). A SHIFT-exact waveform press FORMS a region in one act: it CLEARS THE SELECTION and spans from the playhead (nothing selected) or from the selected marker FURTHEST from the click (argmax |pos − click|, the longest side) to the clicked column, arms the drag at the far endpoint (`arm_region_drag_preserving` — a motionless release keeps the formed span), moves no playhead AT THE PRESS (its ruled shape), stops no playback, seeds no double-click, read-only allowed, slivers refused — though its DRAG carries the playhead like the plain former's does (the one shared motion path, 2026-07-30). BOTH FORMERS DESELECT AT PRESS, AND THEY ARE THE ONLY FORMERS LEFT (the delete demotions and the trim-window sync died 2026-07-30), so A REGION RESTS ONLY BESIDE AN EMPTY SELECTION — structurally, verified with no counterexample: every selecting route clears a resting region before a selection can rest. That derivation is what deleted the phase-reset overlay's mirrored region gates as dead code (the band and `Selection::phase_overlay_subject` — a region and a focused overlay subject cannot coexist; recorded at the band, paint_handler.cpp). Esc mid-drag does nothing at all (pointer gestures have no cancel, 2026-07-29: release/button-lost/Ctrl+Q/resize/WM-close end a gesture through the release bodies and what stands stands; undo is the mitigation). Gutter presses arm nothing; region endpoints hold PLAYABLE live-domain frames only (every former clamps through clamp_playhead_to_live_domain). The coupling is ONE-WAY, REGION → TRIM through `x` alone (the 2026-07-23 downward-only rule's surviving edge — selection no longer produces a region at all, and nothing flows upward: the plain-drag region SELECTS NOTHING, and trim never selects, only ever emptying the selection).

THE REGION'S WHOLE LIFECYCLE: formed by the two waveform formers above; PREVIEWED by either scrub press (the lower-half left or the full-height right — both leave it resting); CONSUMED by `x` (below — which clears it after the write, its job done, and LANDS THE PLAYHEAD ON THE COMMITTED TRIM START, architect 2026-07-30: "on trim X move playhead to trim start"); CLEARED BY BARE ESC (2026-07-30 — the fifth Esc binding, below; the one clear that moves no playhead and changes no selection) AND BY EVERYTHING ELSE that moves the playhead or changes the selection — the route inventory lives at `clear_region_highlight`'s declaration (input_handler.h) and is unchanged in membership from the two-forms era: the navigation jumps (Tab family + `c` through the one jump tail, the waveform-lane playhead step, Home/End, the settings playhead key), every marker click (unconditional — the result-size split died with the extent), `enter_text_edit`, both position nudges' commit tails, both marker drops, the three membership-wholesale routes (undo/redo's visual tail, the `p` swap, the propagate paste), the settings engine-commit, and the in-place structural clears (file load/adopt, Ctrl+Tab, the S/T switch — active-domain endpoints die with the domain — and the kick validator's live-domain reclamp). THE DELIBERATE KEEPERS: the scrub presses (the lower-half left press and, since 2026-08-01, the full-height right press — one body, both region-inert), Space (which no longer reads the region at all and touches nothing), and pure viewport moves (paging, zoom steps, pans, bare `0`). SPACE ALWAYS PLAYS FROM THE PLAYHEAD (architect 2026-07-30: "play issues from playhead OR scrub" — the region left-bound launch is deleted); auditions do not move the cursor, and there is NO LOOPING ANYWHERE (same ruling, normalization-and-boundaries.md).

WHAT PAINTS (2026-07-30, the one-form model): the cursor playhead (the white kPlayheadStem head + full-height stem form, since row 5 — the head sits on the MARKER lane's bottom rows with its tip on the waveform boundary, having moved down out of the ruler at the row-5 live test, and the ruler pass paints it there for the tick columns it needs) paints UNCONDITIONALLY at the resting cursor column — whatever the selection, whatever the region; a cursor on a marker simply passes under that marker's flag (the z-order flip). The scanner is unchanged. A selection's cue is its members' BRIGHTENED FLAGS (kMarkerFlagFillSel — selection is the class ladder's brighter pair since row 5; the retired kSelectedStem singleton stem and the ink-triangle group cue were the pre-row-5 forms), plus the visible cursor landed on the focus. The region paints its ground recolor and nothing else — `render_split_playhead` is deleted, and the degenerate one-column span simply paints no ground (zero width) while the cursor stands wherever it stands.

`x` IS SET-ONLY AND CONSUMES THE SPAN: a live region → set trim to it (active-domain lo/hi through `active_domain_to_source_frame` — one snap, monotone — then the shared walls and the `auto_clear_crossed_trim` commit tail, which under always-set trim resets a crossed pair to the full window), then DESELECT (x is a trim setter; every setter deselects, 2026-07-29) and CLEAR THE REGION (2026-07-30 — the span's whole job was aiming this gesture; the always-visible bar/endcaps show the result); a DEGENERATE result — the inverse-mapped, wall-clamped pair coming out `end <= begin`, reachable for a narrow span over ~16x bracket-legal compression — REFUSES OUTRIGHT, writing nothing (ARCHITECT-CONFIRMED 2026-07-29; the refusal tests the pair x would write, so it is blind to where the span came from); NO region → silent no-op. `Shift+X` IS THE MAXIMIZER (2026-07-30, trim always-set): it expands the window to the full song behind an already-full identity guard (an already-maximized press stops nothing, repaints nothing, triggers nothing — the refusal-gated stop rule), touches no region and no selection (it is a trim CLEARER-class route, not a setter). Both are read-only-refused at the keyboard gate alone. The plain trim-bar click that never becomes a drag is a CONSUMED NOTHING (2026-07-30 — its entire act was publishing the now-retired window highlight); the endcap/bridge DRAG takes the setter's deselect and the trim-mutation stop at its FIRST ACCEPTED bound change (input_trim.cpp), and the ctrl / ctrl+shift bound-set clicks keep their in-handler stop and deselect. `x`/`Shift+X`, the endcap/bridge drags, the bound-set clicks, and Home/End are trim's whole interface.

BARE ESC IS BOUND IN SIX PLACES AND NOWHERE ELSE (architect 2026-07-29, contortion ruling 5, four places; the REGION CLEAR joined 2026-07-30 at the live-test debrief and the MENU ROW'S DROPDOWN 2026-07-31 — this file is the docs map's Esc owner; membership at the authoritative src enumeration, input_handler.cpp). The six: (1) THE FOUR EDITORS — flag, BPM bracket, settings, render-commit — where Esc closes / cancels the edit through `route_modal_editor_key`; (2) THE PROMPTS, where Esc activates the rightmost response; (2b) THE MENU ROW'S DROPDOWN (2026-07-31), where Esc dismisses the open menu — ranked directly under the prompt gate and above the region clear, and it cannot collide with the editors because a popup and an editor are structurally never open together — a claim held up by TWO mechanisms, one per class: the popup opens only from row 1, and while one of the three BOTTOM-STRIP editors (settings, render-commit, BPM bracket) is up the press that would open a menu dies at their swallow arms, while the pointer-transparent FLAG editor, which swallows nothing and so does let that press through, is ENDED by the open (`toggle_dropdown`'s open path discards the edit exactly as a press outside its box does). BOTH MENUS ARE THIS ONE PLACE: Settings and Navigation share one popup state and one keyboard gate, so the second dropdown (2026-08-02) joined the binding rather than adding a seventh; (3) THE EDITOR TEXT-DRAG ESC HATCH — a bare-exact Escape ends an in-flight text-selection drag, a sub-part of the editor class (the drag-modal gate is NOT an Esc binding — it tests only Ctrl+Q, so mid-gesture Esc is swallowed with every other key by the gate's general drag-modality); (4) THE REGION CLEAR (2026-07-30): with a RESTING region and nothing modal open, bare Esc dissolves the highlight — and only that; it ranks ABOVE the render cancel (a visible span absorbs the press rather than an Esc aimed at a highlight silently killing an in-flight preview — with a region resting, cancelling render work takes two presses) and it can never CANCEL a drag: mid-gesture Esc is swallowed by the drag-modal gate before this arm can see it, so a drag in flight continues and its span survives ("clear but not cancel", structural); (5) THE RENDER / BATCH CANCEL (`handle_escape_cancels` → `cancel_archival_session`), its own binding class, ARCHITECT-CONFIRMED 2026-07-29. Everywhere else bare Esc is a no-op: it never deselects and never moves the playhead (the old accepted cost — no route clearing a span without also moving the playhead — retired with the new binding, which is exactly that route). The whole selection/region Esc ladder and the demote-as-a-concept died 2026-07-29 (the Esc ladder's history and the deleted rungs are in git and the 2026-07-29 commits; none of that machinery exists to re-propose). Modified Escape remains unbound everywhere, at every Escape reader.
