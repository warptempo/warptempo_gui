# Touch: One Unified Mode (wl_touch as the Pointer)

> Touch phase 1, architect-ratified 2026-08-11 — the touch arc's first CODE surface (row 8, the bottom toolbar, was its first GUI surface). This file is the arc's record the way kdenlive-redesign.md is the redesign's. The phase-1 code shipped UNVERIFIED ON SILICON: the authoring laptop has no touchscreen and the target is the Pi rig's ROADOM panel, so everything was written to be inert without the capability and correct by construction, with every judgment call recorded. THE PANEL HAS SINCE ARRIVED: the glass sessions of 2026-08-11 produced the first field-driven revisions — see The Phone Model section below, which carries the Second Glass record and the one ruled divergence phase 2 added. Retune the constants on glass, not on argument.

### The Unified-Mode Ruling

THE PREMISE IS ONE UNIFIED MODE, the architect's one settled ruling for the arc: same look, same behavior, same interaction language for mouse and touch. Phase 1 makes it literal — TOUCH IS THE POINTER, translated whole at the platform boundary (`platform_wayland.cpp`), and the GUI cannot tell which device produced an event. No touch mode, no flag, no detection, no GUI-side branch. Everything inherits by construction: every gate, refusal, modal claim, read-only rule, hit test and gesture the pointer has applies to a finger with zero new GUI semantics — stated here once rather than re-proven per gesture. ONE RULED DIVERGENCE since the second glass session (2026-08-11): a one-finger DRAG that starts on the WAVEFORM pans instead of translating — the PHONE MODEL, its own section below the authoritative statement; taps, holds, and every other surface keep the phase-1 translation whole.

### The Binding

`wl_touch` is CORE protocol — wl_seat's third capability, the `wl_data_device_manager` precedent: the same wayland.xml, no new library, no pkg-config entry, no generated stub. It is bound from the existing seat listener when `WL_SEAT_CAPABILITY_TOUCH` is advertised and released on capability loss (through the hard-end contract below). It is NOT a required global and NOT a required capability: absence is SILENCE — no stderr, nothing degraded. The laptop simply has no glass; a seat without touch is the ordinary case, not a poor environment. Touch events arrive batched under `wl_touch.frame` and are processed per frame like pointer frames: down/up edges dispatch at arrival (the button model), motion coalesces to the frame boundary (the captured-relative-motion model), so a sensor-rate panel costs one delivery per frame.

### The Translation Contract (One Finger IS the Pointer)

The bare-`e` precedent — a key translated at the boundary into the left mouse button — applied to glass. The translation state is the platform's own, keyed on the touch id; the GUI sees ordinary pointer deliveries. The phase machine and the AUTHORITATIVE edge inventory live at the touch state block in `platform_wayland.h` (the `transport_repeat` precedent: one list at the state, each fire site keeping only its own clause); the shape:

- FIRST touch-down (no touch state live) opens the DISAMBIGUATION WINDOW: {id, position, deadline} remembered, NOTHING delivered — plus, since the phone model, the down point's PAN-ZONE answer captured once (the zone query, in The Phone Model below). The window exists to tell tap from drag from two fingers.
- The window RESOLVES TO POINTER on: expiry (`kTouchDisambiguateMs`) or the finger lifting inside it (a tap). Motion beyond the slop (`kTouchSlopPx`) FORKS on the captured zone answer since the phone model: on the pan surface it resolves to SINGLE-FINGER NAV (no pointer events, ever — The Phone Model below), elsewhere to POINTER as before. Pointer resolution delivers the synthesized enter-motion at the ORIGINAL down point, then the left press there, then any queued motion — and for the tap, the release immediately after. THE TOUCH HOLD BIT IS RAISED BEFORE THE ENTRY MOTION (codex round 2), so every delivery in the resolution burst — the pre-press motion included — reads the primary button held: the finger has factually been down since the window opened, and that held reading is what the GUI's armed hover-open guard keys on (below). From then on touch motion is pointer motion and touch up is the release.
- A touch-up that ends a pointer translation delivers the release on the logical left's 1→0 edge and then THE TRANSLATION END ON THAT SAME EDGE, which FORKS ON PHYSICAL POINTER FOCUS since codex round 3 (one owner, `deliver_touch_translation_end`, shared by the touch-up site and the hard-end contract): with NO mouse focused on the surface, an ORDINARY pointer leave (`GuiPointerLeaveReason::OrdinaryLeave`) — the finger left the glass, which IS a leave, and the remembered-position machinery and the menu-row band rules already handle ordinary leaves with nothing special-cased; with the physical pointer FOCUSED, an ordinary restore MOTION at the mouse's last platform-tracked position (`pointer_x_`/`pointer_y_`, which touch never writes) INSTEAD of the leave — the finger lifted, so the unified pointer is now where the mouse is, and the motion re-derives hover, the menu-row exit test and the loop-settled cursor from truth (the round-3 cursor-residue fix: before the fork, a resolved touch left the finger zone's cursor kind applied to the real wl_pointer, and a `pointer_in_window=false` lie besides, until the resting mouse next moved). The restore motion runs the ordinary motion path WHOLE, deliberately unmarked — so with the menu row ARMED and the mouse resting on an anchor it hover-opens that menu, and with a menu OPEN and the mouse resting on the other anchor it hover-switches: judged the armed mode's own defining semantics for a pointer standing at that position, not surprises to suppress (suppression would need a "restore" mark on the motion, a device branch in spirit; recorded at the definition too). WHEN A SIBLING SOURCE STILL HOLDS the logical left (physical BTN_LEFT or bare-`e`), the release is suppressed and THE WHOLE END IS TOO — leave and restore alike (codex round 2): the unified pointer has not meaningfully left — the mouse is still there, mid-press — and the leave hook's clears are not mere hover cleanup (they disarm the row-8 held-arrow repeat and destroy an open popup's live press claim, state that belongs to the still-held press, not to the finger that lifted). A suppressed end can strand a hover face where the finger last was — the accepted-glitch class, self-healing on the next pointer event. The hard-end contract takes the same edge rule and the same fork.
- THE LOGICAL LEFT BUTTON IS ONE BIT WITH THREE SOURCES: `pointer_left_held_ || synth_left_held_ || touch_left_held_` — the evdev model for devices sharing BTN_LEFT, extended from the bare-`e` pair. A press is delivered only on the OR's 0→1 edge and a release only on its 1→0 edge, so the sources never double-deliver, and `current_mods()` ORs all three into `primary_button_held` (without which a touch drag would tear on its first motion). Each source's hold ends on ITS OWN stream's edges only: the keyboard edges end the synth hold, pointer-capability loss ends the physical and synth holds, the touch edges end the touch hold.
- The resolution press is a pointer-button press in full: it kills an armed key repeat (layer 1 of the repeat contract — the edge list at `on_keyboard_key` now names three press producers) and flushes both staged motions ahead of itself (the `flush_deferred_motion` invariant, which the touch delivery sites joined).
- Physical keyboard modifiers ride along to touch deliveries exactly as to a mouse: `current_mods()` is the one modifier truth, so Shift+tap is a Shift+click with no new code.

### The Disambiguation Constants (Ruled Retunables)

All three live in `platform_wayland.cpp`'s anonymous namespace, with the full tuning rationale at the site:

- `kTouchDisambiguateMs` = 60 — the one-finger-or-two window. Sampled on the timerfd tick beside the key-repeat deadline (the run loop's one deadline-sampling spot) plus lazily at every touch event's arrival, so expiry lands within one tick (≤ ~16 ms) of the mark; the window is a feel bound, not an exact timer.
- `kTouchTrimHoldMs` = 500 — the MERGED TRIM BAND's own Pending deadline, the trim move's "beat" (The Trim Move below): a band down STRETCHES the disambiguation window to this value, so the band's expiry — which resolves to the trim move, not the pointer — is a real held beat. Born of the field regression the hold's first cut shipped (2026-08-11, the same day): riding the 60 ms window made the "hold" shorter than an aimed drag's natural dwell — a finger landing from rest takes well over 60 ms to cover its first 8 px — so nearly every deliberate band drag expired into the trim move before its motion reached the slop fork, and the band's region former was unreachable from glass (a > 60 ms band tap likewise stopped being a click). Inside the stretched window every other meaning keeps the Pending arms' own shapes — slop crossing → pointer, lift → tap, second finger → two-finger nav — and the stretch costs only trim-move latency, the band having traded hold-unlocks-the-pointer away. 500 ms is the desktop long-press convention (labwc's own repeat delay is 575 ms, the same order).
- `kTouchSlopPx` = 8.0 — physical px; resolves the window early on motion (a finger already dragging should not wait the window out — and since the phone model that resolution FORKS on the down point's pan-zone answer, The Phone Model below) and, reused, is the navigation gestures' latch. It DELIBERATELY EQUALS the GUI's one generic press-becomes-drag gate (`kDragMovedThresholdPx`; stated rather than shared — the platform sits below the GUI model), so a slop-crossing resolution's queued motion crosses the GUI's own drag gate in the same burst as the press: a touch drag becomes a drag the moment it resolves.

### Two Fingers = Pan + Zoom (Navigation-Class)

Both fingers down inside the window (or landing in one frame) is the NAVIGATION gesture: per-frame centroid horizontal delta pans, per-frame finger-distance ratio zooms ABOUT THE CENTROID's column — the strip drag's dual-axis semantics. The gesture never delivers pointer events.

THE DELIVERY SHAPE TAKEN, and why (the phase-1 brief offered the strip-drag pointer entries as the preferred shape with a recorded fallback; this is the fallback, taken at the family's deepest shared point): a narrow platform-to-GUI hook set wired in main.cpp (`GuiPlatform::set_touch_nav_hooks` → `GuiInputHandler::apply_touch_nav_update` / `end_touch_nav`, the `set_keyboard_intent_cancel_hook` wiring precedent; since the phone model the set carries the pan-zone query as its third member — its contract in The Phone Model below — and since the fourth glass session the trim-move members too, The Trim Move below) whose per-frame update drives `Viewport::apply_strip_drag_zoom` — the strip-drag family's own application chokepoint — so the level clamp, the viewport clamp (`clamp_viewport_start`), the synchronous per-frame rebuild and the either-axis follow suppression all come from the one owner. The family's POINTER-PRESS ARM (`arm_strip_drag_at` / `StripDragState`) is deliberately not driven, for two structural reasons recorded at the declaration: (1) the arm unconditionally CAPTURES THE REAL POINTER — it would hide and lock the mouse cursor during a touch gesture, and the capture's release warps the mouse and rewrites the platform's tracked pointer position to the gesture's restore x, corrupting real mouse state from glass; (2) a `strip_drag.active` gesture is TERMINATED by `on_motion`'s button-lost arm the moment any real mouse motion arrives without a held button — which is every mouse motion during a two-finger touch — so a nudged mouse would kill a live pinch. No ctrl-modified pointer press is faked anywhere (modifier state belongs to xkb).

The mechanics, all at their sites:

- The ZOOM mapping is LOGARITHMIC and constant-free: `new_level = level − log2(dist_ratio)`, so doubling the finger gap is exactly one zoom level in and the content between the fingers scales with the fingers. Pre-clamped into `[kMinZoom, effective_max_zoom_level]` exactly as `apply_strip_drag_at` pre-clamps (the chokepoint's `level_changed` contract names both callers).
- The PAN is folded into the same placement: the content under the PREVIOUS centroid column is placed at the CURRENT centroid column under the new level — one `apply_strip_drag_zoom` call does both axes. PER-FRAME ANCHORED (the ratified semantics), so there is no persistent song anchor and no edge-trick rebind to need.
- THE LATCH is the platform's, the strip drag's own press-becomes-drag model in the touch's own unit: nothing is delivered until the centroid travels `kTouchSlopPx` (Chebyshev) from the two-finger start OR the finger distance changes by that same slop, and the crossing update folds the whole accumulated delta — so a two-finger tap navigates nothing and costs the GUI nothing (the end hook fires only if an update was delivered).
- THE REFUSAL ANSWER IS THE WHEEL'S, per frame: the gesture is the wheel's navigation-class sibling — it delivers no pointer events, punches through the keyboard-modal flag editor exactly as the wheel does, and navigates the wheel's two surfaces — so `wheel_context` (the SINGLE wheel routing predicate) is asked at each frame's centroid. That refuses under the prompt, an open dropdown, the bottom-strip modal editors, loading/empty audio and ANY live pointer gesture, and applies only over the waveform or the top strip. A modal opening mid-gesture freezes it (the wheel's own behavior), and a live mouse gesture freezes it too, so two devices cannot write the viewport at once in that direction; the converse — a mouse gesture ARMING while a touch gesture is mid-flight — is accepted as the user's own two-handed act (each writer is incremental over live state and every write clamps through the one chokepoint). The wheel's dismissal pair (dropdown close, tooltip hide) is deliberately NOT copied — this is a refusal, not a press act — but every applied frame CLEARS THE DOUBLE-CLICK CANDIDATE (the C8 rule: navigation that moves content between two taps must not let the second tap consume as a double-click).
- One finger lifting ENDS the gesture (any end commits) — and the end DELIVERS THE STAGED FINAL FRAME FIRST: Wayland orders the `up` before the terminating `wl_touch.frame`, so motion batched with the lift is still staged when the end runs, and that motion is the user's own final leg (the any-end-commits family). This is what lets a short pinch whose only latch-crossing motion batches with the up act at all. The survivor is IGNORED until all fingers lift (the drain phase). A third finger is ignored. No pinch-vs-pan mode split: both axes live simultaneously, the strip drag's own model. The end is the grab-pan release's own tail — one predictor resync; each applied frame already rebuilt synchronously.
- The gesture joins neither the platform's key-repeat disarm list nor the transport hold's edge list: those are ruled event-edge enumerations (key press / pointer press / completed wheel emission) and a two-finger frame is none of them. Recorded as a judgment rather than an omission — a codex round can contest it.

### The Phone Model: One Finger Pans the Waveform (Second Glass Session, 2026-08-11)

THE RULING (architect, at the rig's second glass session, 2026-08-11, his words condensed): "one finger drags the pan — that's how my phone works. One finger drags, two fingers zoom. Remove the stems from the waveform, at least as far as the touch screen goes — try that as an intermediate." Phase 2 therefore accepts a DELIBERATE touch-scoped divergence from the unified premise on ONE surface, the WAVEFORM: a one-finger DRAG whose down point lies there is NAVIGATION — the finger drags the pan — not a pointer drag. Everywhere else (the marker lane, the ruler, the trim bar, every strip and button) the phase-1 translation is untouched; the architect explicitly praised marker-lane drags and the ruler under a finger.

THE SECOND GLASS RECORD, the succession that produced the ruling: the FIRST glass session's field report (same day) was zoom excellent, pan unusable — finger-distance jitter leaking into the per-frame ratio — and the remedy tried first was a zoom ENGAGEMENT HYSTERESIS (`kTouchZoomEngagePx` = 20, commit 26963af3): the field verdict was pan still caught and zoom got STICKIER — "the previous way was much better" — so it was REVERTED WHOLE the same day (5e1d7d11; do not re-propose the hysteresis on this gesture) and the PHONE MODEL is the ratified successor: the two axes are split by FINGER COUNT rather than by per-axis engagement thresholds — one finger pans (one finger has no distance, so no zoom and no jitter to leak), two fingers zoom.

THE ZONE QUERY: a third hook on `set_touch_nav_hooks` (`pan_zone(x, y)` — the family's one owner grew a member rather than a sibling setter appearing), asked ONCE per touch stream at the FIRST finger's down; the answer is captured beside the down point and the window's resolution forks on it. main.cpp wires it to `GuiInputHandler::touch_point_in_pan_zone` — the WAVEFORM AREA, GEOMETRY ONLY: every refusal (modal, prompt, dropdown, loading/empty audio, live pointer gesture) stays at the nav body's per-frame `wheel_context` answer, exactly where the two-finger gesture keeps it, so a refused pan FREEZES like a refused pinch rather than falling back to a pointer drag. `waveform_area` reads only the window dims and the strip heights, so the answer is VIEW-INDEPENDENT — in particular the `h` history view pans by the same answer, and that mode admits pan/zoom (the wheel class), so the view needed nothing new (verified at the query's declaration).

THE RESOLUTION FORK — the disambiguation window's ends under the phone model:

- SLOP-CROSSING MOTION with the down point IN the pan zone → SINGLE-FINGER NAV: delivered through the SAME nav update hook — the finger is the centroid, `dist_ratio` pinned at 1.0 (no distance, no zoom), so the GUI nav body needed NO change and got none — latched and folded exactly as the two-finger latch is (the seed measures its latch from the DOWN point in the same Chebyshev metric, so the first delivered frame folds the whole accumulated delta). No press is ever delivered — the window's whole purpose. The platform shape chosen: single-finger nav is a Nav SUB-STATE (`touch_nav_single_`), not a sixth phase, so the frame delivery, the latch, the end path, the drain and the hard-end arm are shared verbatim rather than duplicated per switch arm.
- TAP (up inside the window) → the ordinary click burst, UNCHANGED: a tap places the playhead, and A TAP ON A STEM STILL SELECTS. The ratified intermediate deliberately scopes to DRAGS — pan replaces stem-DRAGGING from the waveform — and whether stems leave the waveform ENTIRELY (for every device, or only under touch) is the ARCHITECT'S OPEN QUESTION, recorded here, not decided in phase 2.
- WINDOW EXPIRY with the finger stationary → the ordinary pointer resolution, UNCHANGED — with ONE later exception: since the fourth glass session (2026-08-11, The Trim Move below) the MERGED TRIM BAND's expiry resolves to the trim-move gesture instead, and a band down STRETCHES the window itself to the beat (`kTouchTrimHoldMs`), so that expiry is a real held beat rather than the 60 ms mark. Everywhere else **HOLD UNLOCKS THE POINTER**: press-and-hold past the 60 ms window, then drag, is still the old pointer drag on the waveform — which is what keeps the lower-half SCRUB hold and every press-and-hold gesture alive on glass. The rig's road vocabulary in one line — scroll is a one-finger drag, zoom is two fingers, playback rides hold and tap, and a held beat on the band moves the trim window.
- Outside the pan zone: everything exactly as phase 1.

THE UPGRADE, AND THE RECORDED ASYMMETRY: a SECOND finger landing during single-finger nav UPGRADES it to the two-finger gesture IN PLACE — the same hook stream, the delta bases REBASED to the join (the centroid jumps from the finger to the pair's midpoint at the join; folding that jump would pan by half the finger gap), so pan continuity is preserved and zoom is relative to the join; the latch state carries (a live pan does not re-latch), and an undelivered staged single-finger frame is dropped at the join — a sub-frame sliver the rebase supersedes. The REVERSE deliberately does NOT happen: a finger lifting from two-finger nav ENDS the gesture and the survivor drains — no downgrade to single-finger nav. Upgrade yes, downgrade no: a lift is an end, the any-end-commits family.

ENDS: finger up = the nav end (commits; the end hook fires iff an update was delivered — the existing rule), and hard ends run through the SAME `hard_end_touch_stream` Nav arm as two-finger nav, staged-frame drop included. No release, no leave, no translation end on any of them: single-finger nav never held the logical button — nothing pointer-shaped ever started.

### The Ignore Rules

- A SECOND finger landing while a pointer translation is LIVE (post-resolution) is IGNORED whole — recorded (the touch-point count), not routed: mid-gesture finger-count changes do not mutate a committed gesture (the any-end-commits family).
- A second finger landing INSIDE the window resolves to the two-finger gesture, and no press was ever delivered — nothing to unwind, the window's whole purpose.
- A THIRD finger during the navigation gesture is ignored; a finger landing during the drain is ignored.
- When the translating finger lifts while an ignored finger is still down, the remaining fingers are DRAINED — ignored until the glass is clear — rather than opening a fresh window: the survivor of a committed gesture does not become a new gesture (a judgment recorded at the phase machine; the alternative would let a sloppy two-finger lift re-arm as a fresh press).

### The Hard Ends

`wl_touch.cancel` (the compositor claims the touches) and TOUCH capability loss share ONE contract (`hard_end_touch_stream`, the pointer-capability-loss precedent):

- a live pointer translation gets its release DELIVERED at the last position — one delivered release on the logical edge, a commit, not a vanish (a vanished hold would latch the drag-modal gate with no event left to lift it) — then the focus-forked translation end on the release's own edge, exactly as the finger's own lift delivers it (`deliver_touch_translation_end`, the one owner: the ordinary leave, or the restore motion at a focused mouse — The Translation Contract above; a sibling-held logical left suppresses release, leave and restore alike here too: whatever happened to the glass, the mouse is still mid-press and its live press claim is not this stream's to destroy);
- a live NAV gesture — single- or two-finger, one arm since the phone model — ENDS through its end path (commits, iff anything was applied) — but its STAGED FINAL FRAME IS DROPPED, unlike the finger's own lift, which delivers it first: the compositor's claim means that motion retroactively was not ours. The asymmetry with the translation's release is deliberate and recorded at `end_touch_nav_gesture` (the end split): the release MUST deliver because a vanished hold would latch the drag-modal gate with no event left to lift it, while dropped nav motion wedges nothing — the gesture is stateless per frame and holds nothing in the GUI open;
- an unresolved disambiguation window is dropped silently (nothing was delivered, so there is nothing to end);
- all touch state is forgotten either way, through the one forget (`forget_touch_state`).

When a touch end delivers a leave at all — the translation end's no-focus arm (a focused mouse gets the restore motion instead) — it is ORDINARY, never CapabilityLoss: that reason names the wl_pointer stream's own death, and a touch edge says nothing about the mouse. Shutdown (`destroy_wayland_state`) is NOT an input edge: the proxy is released with no deliveries, exactly as the keyboard and pointer teardowns there deliver nothing. The pointer- and keyboard-capability edges never reach into touch state, and touch edges never reach into theirs.

### Touch Never Writes the Pointer's Fields

A deliberate split, recorded at the state block: `pointer_x_`/`pointer_y_` are wl_pointer's own — the wheel emits there, the bare-`e` press lands there, the capture machinery rewrites them — and every touch delivery carries its own explicit coordinates, so the unified "one pointer" view lives in the DELIVERIES while each device's platform state stays self-consistent. Touch likewise does not clear `pointer_position_unknown_` (a touch says nothing about where the mouse cursor is drawn) and gates NO DELIVERY on `pointer_focused_` (wl_touch delivers only to the touched surface; a mouse-focus bit is not its business). The split has ONE deliberate reader since codex round 3: the translation end (`deliver_touch_translation_end`) reads `pointer_focused_` — and `pointer_x_`/`pointer_y_` on the focused arm — because the end is a MOUSE question ("is the mouse resting in the window, and where"), not a touch delivery to gate. Consequence, accepted: a stray mouse click during a touch session routes at the MOUSE's last known position, which is that click's honest answer.

### No Hover Under Touch — Cues, Not Functions

A finger has no resting position: contact is a press (after the window, when the stream resolves to the pointer at all — a pan-zone drag is navigation and never presses) and lift is the translation end — a leave, or the restore motion at a focused mouse (the round-3 fork, The Translation Contract above) — so the hover-derived surfaces simply never fire FROM GLASS: button hover faces, the 700 ms shift-tooltip dwell, and the menu-row armed-hover open all want a pointer that rests where nothing is pressed, and a finger never supplies one (the restore motion re-derives them at the MOUSE's resting position, never the finger's). These are CUES, not functions: every act they advertise is reachable by its chord or its press, so nothing is lost. For the faces and the dwell nothing was special-cased to make this true — it falls out of the end-on-lift contract — but THE ARMED HOVER-OPEN NEEDED ONE REAL GUARD (codex round 2 caught the original claim overclaiming): the armed mode deliberately survives an ordinary leave through row 1's band, so a finger lift there keeps it, and the next tap's resolution burst delivers a pre-press entry motion that reached the hover-open and sprang an anchor's menu one event before the same burst's press toggle-closed it — a tap on Settings/Navigation visibly did nothing. The fix is device-blind, two halves: the platform raises the touch hold before delivering the entry motion (the finger has been down since the window opened, so the whole burst honestly reads the primary button held), and the GUI's hover-open refuses under a held primary button (on_motion's no-gesture tail) — a guard that also closes the mouse's own latent case, a held press that armed no gesture sliding along the armed row. So the claim stands BY THE GUARD, not by nature, and the tap opens the menu through the press path exactly as a click does. THE GUARD IS A THREE-MEMBER FAMILY RULE, built one member at a time across rounds 2-3 and stated whole at the close walk in `input_pointer.cpp`: NO ROW-1 HOVER ACT FIRES WHILE THE PRIMARY BUTTON IS HELD — the armed hover-OPEN (round 2, above), the open-menu anchor-SWITCH, and the open-menu hover CLOSE (both round 3; the close was the last unguarded member, added at the planner's judgment on the coder's flag). The SWITCH case: with a menu already OPEN, the burst's held entry motion reached the open-dropdown branch's hover anchor-switch — Settings open, tap Navigation: the motion switched to Navigation and the burst's press then found its own menu open and toggle-closed it, so the tap closed the popup instead of switching to it — and the identical held-primary guard now refuses the switch (the tap switches through the PRESS's own toggle, as a click does). That guard also fixes the mouse's own latent bug at that branch, confirmed at the site: press-hold an item (or the anchor press's drag-into-the-box claim) and slide across the other anchor, and the switch fired mid-press — toggle_dropdown's close wipes the whole Dropdown struct, destroying the popup's live press claim out from under the held button. The CLOSE case changes no tap outcome — press-anywhere-closes at on_button_press already closes the menu on the burst's own press, so the tap nets the same result by the cleaner path — while for the mouse a mid-press slide across a non-anchor (Quit, the view bar's three) now keeps the popup's live press claim exactly as the switch guard keeps it. Every unheld hover act is untouched. Two recorded edges of the same coin: whatever a resting HELD pointer does today (a pressed button's face, a dwell that elapses under a held press) a held finger does identically — the unified premise means there is no touch-specific answer either way — and a finger lifting with a mouse resting in the window delivers the translation end's RESTORE MOTION at the mouse's own position (the round-3 focus fork, in The Translation Contract above), so the resting mouse's hover face and cursor are re-derived from truth on the lift itself rather than stranded at the finger's zone; the leave — and the face loss it briefly carried for a coincidentally resting mouse, recorded here as an accepted glitch between rounds 2 and 3 — now fires only when no mouse is focused, where there is no face to lose. The one strand left in the accepted-glitch class is the sibling-suppressed end (a mouse held mid-press when the finger lifts), which delivers nothing and self-heals on the next pointer event.

(An inherited oddity stood here until the trim surface arc: a one-finger ruler drag WAS the strip drag, whose machinery captures the real pointer — so a touch ruler-drag hid the mouse cursor and the release warped the mouse to the anchor stem's column. The ruler's strip-drag entry is DELETED with the merge below, so the only pointer-capturing gestures reachable from glass are now the waveform's hold-then-ctrl and hold-then-alt shapes, which need a keyboard anyway; the record stays because the class — a touch-driven pointer gesture that captures the mouse — is real and returns whenever such a gesture gains a bare plain-drag surface.)

### The Trim Surface Arc (Third Glass Session, 2026-08-11)

THE RULING (architect, the third glass session — a REDESIGN OF THE GESTURE ECONOMY from glass experience, his ranking: pan #1, zoom #2, region-draw #3, trim-move #4, the rare one; his words: "make the timestamp lane the same as the trim — a click on the timestamp translates into trim... drop zoom support there because zoom is already well supported in the waveform, touch and non-touch... let's experiment with making the region draw a drag on the trim bar"). BOTH DEVICES, UNIFIED — this arc is not touch-scoped code, it is the pointer surface reshaped with the finger in mind, and touch inherits all of it with ZERO new touch code:

- THE RULER MERGED INTO THE TRIM SURFACE: the trim bar, the ruler and their gap are ONE input band (`top_trim_surface_area`), every trim gesture and the span-framing double-click answering over its whole height — the endcap grab included, a fatter finger target being half the arc's point. The ruler's strip-drag ZOOM entry is DELETED (`arm_strip_drag_at` is one-entry again — the ctrl-waveform press); the ruler's PAINT is untouched.
- PLAIN DRAG ON THE BAND = REGION DRAW: anchor at the press column, playhead riding the moving end, the waveform placement press's region arm re-expressed on the band (its press-time acts deferred to the drag threshold so the band's motionless click stays a consumed nothing — `RegionDragState::band`). The BRIDGE (move-both-bounds) drag is DISPLACED off the plain press — to CTRL+DRAG at this session, and onto ALT+DRAG at the fourth (the section below); the ctrl+CLICK bound-set stays, split from the drag by the band's own 8px threshold.
- ON GLASS that means: a quick one-finger drag on the band is a plain pointer drag after the window (the band is NOT the pan zone) = region draw; a drag from an endcap = extend that bound; a tap = nothing (the double-click's first click). ### The Trim Move (Fourth Glass Session, 2026-08-11)

THE RULING (architect, the fourth glass session, closing the third's recorded gap): his VOCABULARY split — ctrl = zoom (the waveform's ctrl-drag), ALT = move/pan (alt-drag pans the waveform) — so MOVING the trim window is ALT+DRAG on the merged band, and on glass "hold for a beat and then drag on the trim bar moves the trim bar — including the timestamp region."

THE MOUSE HALF, unified-pointer code with no touch in it: the bridge (pair) drag's modifier SWAPPED ctrl → alt (the arm moved to on_button_press's alt branch, `point_in_trim_bridge_span` unchanged; the cursor map's TrimResize rides the alt arm now). The ctrl/ctrl+shift BOUND-SET CLICKS ARE UNTOUCHED — ctrl in-span keeps its deferred motionless-release BEGIN set (the pending is now purely that deferral's vehicle: a threshold crossing DISARMS, the drag it used to become being alt's), ctrl off-span the at-press set + single-bound drag, ctrl+shift the END set — so ctrl's cursor cue is the bound-set pair alone. Alt's pointer count grew by one: alt+drag pan, alt+wheel pan, alt bridge drag.

THE TOUCH HALF — HOLD-A-BEAT-THEN-DRAG ON THE BAND MOVES THE TRIM WINDOW: a band down STRETCHES the Pending window to the BEAT (`kTouchTrimHoldMs` = 500; the hold's first cut rode the 60 ms disambiguation window and broke the band's quick drag in the field the same day — the constants list above carries the record) and that window's EXPIRY on the MERGED TRIM BAND resolves to a TRIM-MOVE gesture instead of the ordinary pointer — a new hook-family member (the touch-nav precedent: a SECOND zone query answering `top_trim_surface_area` beside the pan-zone one, captured at the first finger's down, plus begin/update(x)/end hooks wired in main.cpp to THE BRIDGE-MOVE MACHINERY'S OWN BODY — `begin_trim_drag(both=true)` at the down x, `update_trim_drag` per frame, `commit_trim_drag` at the end — so both bounds ride the dragged columns and the drag's whole commit regime is inherited verbatim: stop at first accepted change, rigid-delta walls, release column snap, crossed/coincident reset, park-at-release, setter deselect). Nothing pointer-shaped ever starts — no press, no hold bit, no release, no translation end (the single-finger nav's model). Refusals live in the BEGIN (prompt, ALL FIVE editors — the pointer-transparent flag editor included, since every pointer press closes one before any claim runs and this gesture skips the press path — dropdown, loading/empty audio, live pointer gesture, the `h` view), the zone query staying GEOMETRY ONLY, so a refused hold-drag FREEZES for the stream exactly as a refused pan does. Hard ends take the nav shape — staged final frame dropped — but the end itself ALWAYS fires: the GUI-side trim drag holds the drag-modal gate open and must commit (`end_touch_trim_move`, the recorded split).

THE BAND'S THREE TOUCH MEANINGS, closing the arc's recorded gap: TAP = the click (a lift anywhere inside the band's stretched window — the double-click's first click; two taps frame the span), QUICK DRAG (slop inside that window — anywhere short of the held beat) = the plain pointer drag = the REGION former (and from an endcap, that bound's extend — the cap's quick-drag hit), HOLD-A-BEAT-THEN-DRAG = the TRIM MOVE. THE BAND'S HOLD NO LONGER UNLOCKS THE GENERAL POINTER there — the one surface that trades the hold-unlocks-the-pointer escape away (The Phone Model's expiry clause carries the same statement): an endcap FINE-GRAB on glass goes through the endcap's QUICK-drag hit instead, and every other press-and-hold gesture on glass is off the band and keeps the unlock. Two accepted consequences, recorded: a resting mouse in the window wears the live trim gesture's own TrimResize cue for the gesture's life (the cue-exception rule reading the drag's record, whatever drives it), and — the cross-device edge, the nav gestures' class — the drag state being `app.trim_drag` itself, a stray mouse release or lost-button motion mid-gesture commits it early through the pointer paths: the user's own two-handed act, every end a commit either way.
