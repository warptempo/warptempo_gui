### Load-Lenient, Render-Normalizing Boundaries
Gestures move freely and NOTHING POPS, ever: markers and trim bounds may sit arbitrarily close, overlap exactly, and cross during gestures on both columns, and no commit opens a modal — the defect-resolution funnel is RETIRED (directive #11, architect 2026-07-15). Ambiguous authored states are NORMALIZED at the render/preview boundary instead of refused or force-resolved: every ambiguous tempo resolves to 1.00. The chokepoint is `resolve_warp_markers_for_render` (staged pipeline and output invariants at its header, `warp_frame_map_build.h`), which every render path AND the target-view recompute funnel through, so display and render cannot disagree: (1) filter to survivors (disabled + cascade), (2) collapse each EXACT-same-frame surviving group to ONE plain enabled 1.00 owner, no labels (a def dying in a collapse makes its refs dangling, normalized in turn — deterministic cascade), (3) silently seed a plain 1.00 owner at frame 0 when no survivor sits there — MANDATORY CORRECTNESS: `build_warp_frame_map` seeds {0,0} and attributes the opening segment to the first resolved marker wherever it sits, so a missing frame-0 SURVIVOR (disabled-at-0 included) would otherwise render silently wrong bytes; the seed is decided on the surviving list by explicit ruling and is silent (the documented default, not ambiguity), (4) materialize passes through the ref-OPAQUE inheritance walk — a surviving enabled label ref terminates the walk with the 1.00 fallback (a ref owns a duration equation, not a rate), (5) normalize label refs: dangling, or implied effective tempo outside the authored per-marker envelope [0.125, 8.0] (`kRefImpliedTempoMin/Max`, scale-free so hover mirrors it without seeing the settings scale) → a plain 1.00 owner at its own frame. Every normalization except the seed prints ONE stderr line per timestamp PER RESOLVE (no dedup or session state — a resting ambiguous store re-prints on each preview recompute, the intended signal). The DISPLAY surfaces (`marker_effective` / `resolved_marker_payload`) share the walk and the envelope constants: a normalized ref RESOLVES to the exact `1.00` literal it renders as, and so does a ref-hit pass, with no source marker to name in either case (the `= 1.00 (undefined label)` / `= 1.00 (extreme label ratio)` READOUT SPELLINGS retired 2026-08-29 with the readout itself — nothing displays a resolved value now, `j` copies the payload and Shift+`j` goes to its source; the ctrl+c copy notice left the popup text 2026-07-20; the copy behavior itself is unchanged). The GUI STORE stays the authored truth — coincident-group members still paint, hover, and Tab-pick individually; the collapse is render-domain (accepted display split, stderr the signal). NORMALIZATION-RED (2026-07-21, opus session): a marker that renders as the 1.00 fallback ALSO paints its FLAG red (the marker lane's own red pair kMarkerFlagFillRed/kMarkerFlagEdgeRed since row 5 — the retired kAccent pair's successor) — a display cue alongside the stderr, revising the pure stderr-is-the-signal rule for the coincident case (an earlier attempt reddening the wave SEGMENT was reverted — a floating red span had no bound and read oddly, the marker flag is the bounded cue). The red set is computed SILENTLY GUI-side from the COMMITTED store (a memoized generation-keyed helper, `warp_red_flag_set_cached` / `phase_reset_red_flag_set_cached` in warp_frame_map_view; committed-store + generation memo = a red flag HOLDS through a marker drag and re-evaluates only at commit, mirroring the displayed-map wait): the ref/pass fallbacks via `marker_effective` (source_idx == -1 with a ref reason — UndefinedLabel/ExtremeRatio — OR the `from_ref` bit, so a PASS reddens only when it inherits from a ref, NOT when it inherits a real value from a synthetic prior — the frame-0 seed or a collapsed owner), and the exact-frame collapse via a same-frame count of 2+ effectively-enabled members reddening EVERY member (the overlapping stack reads as ONE red flag, matching the single stderr line). No frozen resolver out-param is needed (the 1730d99 out-param was reverted as redundant); the frozen touches here are TWO granted siblings on `MarkerEffective`, each a value the walk already computed and discarded: the `from_ref` bool (2026-07-21) and `owner_idx` (2026-07-22, 2aa5738 — the ref-opaque backward walk's terminal owner as a raw store index, -1 whenever no raw owning marker exists; its sole consumer was the tempo drag's label-coupling guard, so it went caller-less with contortion ruling 8 and is now DELETED — 2026-07-29, under an explicit surgical freeze approval; `from_ref` beside it stays, its normalization-red consumer being alive, and `resolve_inherited_tempo`'s defaulted `owner_index` out-parameter stays as an unused capability). Phase resets get the SAME red on a coincident enabled collapse (a same-frame count on the phase-reset store — the symmetric sibling; no marker_effective analog, phase resets carrying no tempo/labels). Selection is NOT a color class and never masks red (2026-07-27, the kSelected/kSelectedOutline deletion: a selected red marker keeps its red pair, so the normalization cue always shows); the frame-0 seed is silent and unreddened; no new flag-cache fingerprint field (the red set only changes on a generation bump the flag cache already keys on). Phase reset column: exact-equal enabled resets collapse to one event inside `build_phase_reset_source_frames`, one stderr line per timestamp (positions are whole frames, so sub-frame spacing IS equality). `kFingerprintVersion` was bumped to 7 with this contract (extreme refs previously rendered their unclamped ratio). The marker stores are ALWAYS time-sorted at rest, ties legal with stable order; every time-mutating gesture routes through `reorder_markers_by_time` + `remap_marker_indices_after_reorder` (`app_state.h`). Rapid keyboard gestures COALESCE their undo granularity through a HYBRID OF TWO RULES (architect 2026-08-01, superseding the pure repeat-identity model's separate-presses clause on the live complaint that rapid manual taps each pushed their own entry): (1) REPEAT IDENTITY for a HELD key OR A HELD BUTTON — a hold's synthesized repeats collapse into ONE undo entry with the burst's OPENER, NO clock consulted, so a hold coalesces at any compositor repeat delay/rate; and (2) THE TAP WINDOW for consecutive PHYSICAL PRESSES (each acting at its own press) — a same-kind physical press within `kTapCoalesceMs` of the last ACCEPTED coalesce event merges too, PROVIDED THE SUBJECT STILL STANDS (the stamped selection plus TWO OF THE THREE VIEW TAGS AN ENTRY IS FILED UNDER, the A/B tab and the S/T audio view — the tap arm's structural stand-in for the repeat contract's event-edge disarms, without which a different marker's nudge could merge into the first marker's entry, or a `t` between two taps could leave the burst filed under the view it opened in while the last press was authored in the other; the W/P column needs no term of its own because a column switch clears the selection and both eligible families refuse without one, so the selection term already sees it). Either way a single Ctrl+Z reverts the whole burst; presses beyond the window, or after a subject change, are separate entries. AND A BURST THAT NETS TO ZERO POPS ITS OWN ENTRY (architect 2026-09-01, THE BYTE-EQUAL POP — not a new rule but the accepted commit-on-NET-CHANGE principle extended to the one path that skips the push): every PUSH site in the product gates on net change, and the marker drag's commit states the reason for all of them — *"pushing an undo entry there would record a snapshot byte-equal to the live store, a no-op history entry that both undo and redo restore invisibly"* — but a MERGED press skips the push and skipped that gate with it, so a tap Right then a tap Left inside `kTapCoalesceMs` left the burst's surviving entry byte-equal to the live store: one Ctrl+Z that changed nothing, silently, over a dirty dot that stayed lit against a store equal to the file (the frame-0-anchored painted lattice makes the pair exactly reversible and `reorder_markers_by_time` is stable, so the store comes back row for row; the same hole stood on all three eligible kinds). The MERGE TAIL now asks the producers' own question POST-MUTATION — the coalesce verdict is computed ahead of the act and cannot know where the press lands — at the ONE SEAM all three kinds share, `Undo::record_gesture`, which every eligible route reaches post-mutation on its accepted path and which now takes the press's own merge verdict as a parameter (the three call sites: the two position nudges' shared commit tail, and both arms of the Up/Down cent step). WHAT IT COMPARES is the ENTRY'S SNAPSHOT AGAINST THE LIVE STORE, BOTH COLUMNS, EXACTLY — every field of every row, serialized and session-only alike, no epsilon and no re-rounding, through the row enumerations at the head of undo.cpp, which are ONE PER COLUMN WITH TWO READERS since this landed (the post-restore touched-set matcher's own two lambdas were hoisted into them rather than a second field list being spelled). The entry's engine-settings block needs no term: the three eligible kinds write no engine setting, and every engine-settings writer either pushes an entry (which clears the stamp) or resets the history whole, so it is provably the live block wherever the question is asked. On equality the entry comes OFF the undo stack (`UndoHistory::pop_undo_top_with_saved_ref`, push's partial inverse and the saved reference's one owner) and the stamp is cleared, so the burst dissolves as if it had never happened and the NEXT press opens its own entry; the saved reference moves one entry forward with it, which is what puts the DIRTY DOT back out when the wobble happened over a saved baseline — and A REFERENCE STANDING AT DISTANCE 0 WHEN THE TOP POPS IS ORPHANED INSTEAD (`saved_valid` false, the belt of 2026-09-02): it named the live state the merged press just walked away from, which the pop leaves nowhere on the timeline, and stepping it to +1 would point one redo ahead over the redo stack the burst's first push emptied — clean by an empty walk; the arm is unreachable while the save clears the stamp (a save inside a burst ends it, so no merge can pop over a reference at 0) and stays as the belt the arithmetic owes itself. COMMAND ADJACENCY SURVIVES STRUCTURALLY rather than numerically: the platform repeat contract's event-edge disarms (layer (1) at `maybe_fire_repeat`, now recorded there as LOAD-BEARING for undo correctness) kill a KEY hold at any intervening pointer-button press, completed wheel emission, or key press, and the BUTTON burst dies at THE ONE PHYSICAL KEY EDGE — the platform delivery in main.cpp's `set_on_key` hook, upstream of `on_key`'s synthetic callers, which spans "a key command happened" whole because a key command runs at its PRESS (that burst's authoritative edge inventory is at `AppState::ChromePress`) — so no synthesized repeat on either surface can arrive after an intervening command — and the one route the disarms cannot see (state changing under an async worker publish flipping a refusal mid-hold, no command in between) is closed from BOTH ENDS by two stamp rules, the second added 2026-07-29 by the final codex round's MEDIUM 2. The two-category boundary rule (architect-ruled, #11 form): a state the GUI lets the user COMMIT always LOADS and always RENDERS — normalized to 1.00 / no-trim where ambiguous, with stderr lines as the signal; a state the GUI can NEVER produce is ADVERSARIAL and hard-fails the load, stderr only, FIRST error only (no friendly listing — fixing one defect can create another, so one-shot completeness is futile, and adversarial input earns no user-friendliness). The design premise: the GUI assumes a non-adversarial user — gestures are never guarded mid-flight, and ambiguous states are RESOLVED BY THE RENDER (1.00 / no-trim, stderr lines), not reported, gated, or force-walked. ### The Sweep's Minimum Trim Span — RETIRED (architect 2026-08-19, one day after it landed)

THE FLOOR IS GONE AND NOTHING REPLACED IT. `kMinTrimSpanFrames` — 65536 whole source frames, about 1.49 s at 44100 Hz, derived as the resolved tempo-scale CEILING (16, from `kTempoMaxCents/100` = 4.00 times `kScaleMax` = 2.0 twice) times the engine window `kN` = 4096, so that a swept window's TARGET span could never fall below one analysis window at either end of the value bracket — stood from 2026-08-18 to 2026-08-19 and is DELETED whole, constant and application together. The architect's ruling: the enforced minimum was DISTRACTING in the hand, and the span it enforced was TOO SHORT to be worth the machinery holding it up; the degenerate cases get the NO-BACKSTOP TREATMENT the wind-down applies to every rare non-silent fault.

SO THE SWEEP AUTHORS ANY SPAN, walls apart, with no width rule between its two ends (`write_trim_from_sweep`, input_trim.cpp). Two degenerate shapes follow, and each is answered somewhere that already existed rather than by a new guard:

* A COINCIDENT PAIR (begin == end) is answered by THE ENDCAP DRAG'S OWN ESCAPE, NOW GLOBAL: the sweep's release runs the shared commit tail like every other former, and `auto_clear_crossed_trim`'s `end <= begin` compare resets the pair to the WHOLE SONG — the same compare that has always caught a handle dragged onto its twin. ONE OWNER for every former; no arm was added for the sweep and none is wanted. That compare is now the single statement of "a collapsed trim means the whole song", and the coincident-reset row in validation_topology.md covers the sweep by pointing at it.
* A TINY BUT NON-EMPTY PAIR simply rests and renders. THE RENDER BOUNDARY OWNS HONORABILITY, as it always has: `validate_trim_frames` refuses only a pair whose TARGET span rounds below one output sample, and a refusal there means RENDER UNTRIMMED (one stderr line at both orchestrators), never a failed render. The stage that actually holds the map decides, at the moment it holds it, instead of a gesture-time constant guessing on its behalf.

WHAT THIS MEANS FOR A SUB-`kN` WINDOW, stated plainly because the floor's whole argument was about it: a trim smaller than the engine's analysis window is now authorable, and it RENDERS TRIMMED AND SHORT rather than failing — `plan_trim` has no window-size refusal, only the four in its own vocabulary (end at or before begin, begin at or past the source end, end past the source end, target span below one output sample). The engine treats its head exactly as a full render's own head is treated — which, said truthfully (measured 2026-09-02, the truthfulness deep dive's item D), is that it ZEROES the two frames whose read starts before the first sample rather than padding them on the left the way it pads a partial tail on the right, so the render fades in 0 → 1 over `3·R_s` = 3072 samples (70 ms at 44.1 kHz) and its head phase is seeded from silence. A window that begins at least three hops into the piece throws that ramp away with its own pre-roll; one whose begin sits inside the first three hops (`A0` clamps at 0) keeps exactly the ramp the full render has. The engine-side record, the history and the accepted cost are at `stft_container.h`'s output-timing contract and its analysis guard. A render that comes out audibly degenerate at that size is the user's own doing and the product does not step in front of it.

THE FOURTH OF THOSE FOUR — THE SUB-SAMPLE TARGET SPAN — CARDS SINCE 2026-09-02 (architect, deep dive item L): `Trim window too small to render; rendered untrimmed`, a NORMAL card at the preview's dispatch and at the two archival chords' press (messaging.md's inventory entry and render-pipeline.md's trim section carry the shape and the one verdict owner). IT DOES NOT REOPEN THE FLOOR and is the opposite move: the window rests exactly as drawn, the render is still untrimmed rather than failed, and what changes is only that the outcome is now SAID instead of printed to a terminal the architect is not reading. It is the one refusal of the four a resting store can reach — the other three are adversarial or breach shapes — so nothing above needs a second sentence, and the ruling's whole content is that a hairline trim bar over a full-length render is the misleading screen the success rule cards.

THE FLOOR'S ONE ARGUMENT WORTH KEEPING, as a note to whoever proposes the next span rule here: it was a FLAT COUNT OF SOURCE FRAMES rather than a duration precisely because a duration paints a variable width in TARGET view, where the same source window is stretched or squeezed by the resolved tempo-scale product — two rules wearing one number. Any future span rule must be ONE NUMBER IN BOTH VIEWS or it is not one rule. But the ruling above is that there should be no such rule at a gesture at all.

THE RELEASE-TIME SLIVER DISSOLVE RETIRED AHEAD OF IT (2026-08-18) AND STAYS RETIRED: a jitter drag that crosses the 8 px gate used to rest a two-pixel highlight and dissolve it at the release; it now commits the two-pixel TRIM it drew, nothing dissolving it and nothing widening it. `Shift+[` is the way back from anything a stroke leaves behind — trim has no undo. Both retirements are kept as seeds at region-scrub-esc.md rather than here.

### Why the Window Exists (architect 2026-08-19)

WHY TRIM EXISTS AT ALL IS NOT RESTATED HERE — it is stated once, in render-pipeline.md's prepost-trim section: the window is there to MAKE A TARGET-VIEW SEGMENT RENDER FAST, so a passage can be iterated on instead of the whole piece being synthesized again for every change. This file owns where the pair may REST and how it COMMITS — always set, ordered, walled, crossed pairs resetting, the setter's deselect and the playhead park — and every one of those rules is about a window whose job is that render.
