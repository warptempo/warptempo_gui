The feature: bare `h` (also the icon row's twelfth button, Icon::VcsDiff behind a separator gap, selected while the mode stands) opens a read-only view of how the live in-memory authoring state differs from the piece's committed checkpoints, `,`/`.` walk the checkpoints (and are the icon row's fourteenth and fifteenth buttons since 2026-08-05, Icon::GoPrevious / Icon::GoNext in that same group — the walk's pointer surface, greyed and pointer-dead outside the view), Ctrl+H REVERTS the selected differences into the live state (the row's thirteenth button, Icon::DocumentRevert, between the history button and the walk pair — its own section below), the marker lane paints the delta as green/red diff flags, `'` loads a viewed (or pasted) commit's whole sidecar state in place in memory, and Ctrl+Alt+R — the Render button, wearing "Save and Commit"/Icon::VcsCommit while the mode stands — SAVES the piece and publishes the current state as a new checkpoint. ## Transport and trust

LOCAL GIT, THE READ/WRITE SPLIT AS TWO ENTRY POINTS. The module (`src/gui/history_diff.{h,cpp}`) shells to git with an argv exec (no shell anywhere — corpus paths carry spaces) against the constexpr repo root. `run_git_capture` passes ONLY reads — `log`, `show`, `ls-tree`, `rev-parse`, `rev-list`, `diff-tree`, `status`, `remote get-url` — and `run_git_mutate` (round 5, the commit act's fenced writer and its ONLY site) passes ONLY `add`/`commit`/`push`; both inventory comments are authoritative, and the fence is which function a call site names. No fetch, no credential in the program: every read is against the LOCAL branch (`HEAD` since round 5 — the product is a commit producer, and a checkpoint whose push failed must still be visible history; `origin/main` would hide it until the next successful push), and the push authenticates through the machine's own SSH setup. main.cpp's `SIG_IGN` SIGCHLD auto-reap (the audio-player precedent) makes `waitpid` return ECHILD, so success is INFERRED, and since the codex round the inference is honest per class: captures are a TRI-STATE (a CLOEXEC self-pipe distinguishes could-not-exec from ran; the load-in-place path additionally cross-checks each captured blob against `ls-tree -l`'s own byte count, so a failed or truncated `show` can never stage a sidecar state the commit never held), and mutations are judged by REPOSITORY OBSERVATIONS THAT OUTRANK THE TRANSPORT (codex round 2): the commit verdict FINDS THE COMMIT CARRYING THE CHECKPOINT BY CONTENT SIGNATURE — over a bounded `rev-list before..refs/heads/<captured branch>` walk (cap 10; the range names the captured branch's own ref, never the symbolic HEAD — round 4), the commit whose message is the act's exact title, whose own diff touches a non-empty SUBSET of the three literal paths and nothing else, and whose resulting three blobs equal the bytes the act wrote (subset not equality: a checkpoint that changes two of three sidecars is the ordinary case; the bytes leg proves completeness) — so a concurrent unscoped commit that consumed the staged sidecars is never attributed or pushed, the checkpoint is found even under another commit landed on top, and the verdict runs REGARDLESS of the transport result (git moves HEAD before post-commit hooks, so a deadline-killed hung hook can sit over a checkpoint that landed — it is found and pushed, the anomaly noted). THE IDENTITY IS CONTENT, NOT AUTHORSHIP (codex round 3, the contract stated honestly rather than overclaimed): every leg is a fact about what a commit CARRIES, none about who ran the git, and content-equivalent commits are DELIBERATELY INTERCHANGEABLE — publishing one publishes the intended state, and the byte legs are what make that safe (nothing carrying different sidecar state can be substituted, no foreign path can ride along). An act-unique message trailer was considered and DECLINED: mechanism plus a permanent oddity in every checkpoint message, to distinguish commits whose content is identical, against a producer (the architect's wrapper) retired for checkpoints as of 2026-08-04. The pre-flight's Clean arm forks on the remote-tracking ref: caught-up → NothingToCommit; behind with the captured branch tip's bytes confirmed → push the existing checkpoint (the retry-after-timeout route, and the correct answer to a terminal-committed unpushed branch). The push verdict is the remote ref catching up, transport discarded — and CONTAINMENT MUST BE OBSERVED, never inferred from silence (round 3): the walk is `rev-list --count`, whose successful run ALWAYS prints a number ("0" is containment), so an empty or non-numeric answer is a FAILURE and the two verdict sites take it as such — the push reports the checkpoint unconfirmed (never `Committed`), the clean arm treats the branch tip as unpublished and falls through to the push with its own stderr line. THE TRI-STATE SURVIVES THE REF READ TOO (round 4): `rev-parse --verify` answers "" for a ref that is ABSENT and for a read that could not be MADE, so an empty first read is followed by a POSITIVE-WITNESS probe of `refs/heads/<captured branch>` — a ref the act cannot be running without — and the witness printing means the repository answers queries (so the target ref is genuinely absent → Missing), while a witness that is also empty means UNAVAILABLE; without it an unreadable repository routed as an ordinary "the remote does not carry it", omitting the clean arm's "could not read" line and printing `Push failed` where the transport had not failed. AND THE WITNESS ADJUDICATES ONLY A READ THAT RAN (round 5): the target probe returns the capture's own verdict beside the object name, so a probe that COULD NOT EXECUTE is Unavailable on the spot with no witness probe run at all — a witness proves the repository answers NOW and can never reach backwards to prove an earlier invocation executed, and letting it convert a could-not-exec target read into "absent" manufactured exactly the false negative the tri-state exists to prevent (`Push failed` reported over a tracking ref that carries the checkpoint, and "committed locally and still unpushed" printed without an observed Missing). The one false unavailable, recorded: a captured branch deleted mid-act, which costs a fall-through push — and that push is NOT refused by the branch's absence (round 5, correcting the recorded consequence): the refspec sends an object name the act already holds, so git resolves no local branch to send it and can create or update the remote branch with the local one gone (verified live). The conservative routing is safe because a redundant push moves nothing at the remote, not because the missing branch would stop it. WHAT THAT FALL-THROUGH PUSH ACTUALLY DOES at the remote (round 4, correcting "a no-op if the remote did carry it"): it is a no-op only at TIP-EQUALITY (`Everything up-to-date`); a DESCENDANT remote tip — which containment also calls carrying it — makes the explicit `<sha>:refs/heads/<branch>` refspec a backward move and git REJECTS it as a non-fast-forward, safely, since nothing forces, and a rejected push does not update the remote-tracking ref either (both verified live), so the verdict reads what that ref already said. Nothing at the remote is lost or rewound in either case, which is the claim the fall-through rests on. And the local-checkpoint line no longer claims "still unpushed" over an unobservable containment: the clause is printed only after an observed Missing. THE PUSH CONSUMES THE VALIDATED DESTINATION (round 3, the real TOCTOU close): the guard runs at init for the mode and again at the mutating boundary for the act, and the URL that second asking validates is PINNED into the push child's own config — a `-c remote.origin.pushurl=` clear followed by `-c remote.origin.pushurl=<validated>`, both halves needed because the key is multi-valued (a lone `-c` ADDS a destination; the empty value clears the list), which in the multi-pushurl case replaces the whole validated set with one confirmed member. The named remote stays in the argv so the remote-tracking ref still updates. The other two terms of the publication are bound with it: the attributed commit is pushed BY SHA (`<sha>:refs/heads/<branch>`, no force anywhere — a remote ahead is an ordinary fast-forward refusal; the recorded trade is that a commit sitting on top of the checkpoint stays unpublished, the user's own to push), and the branch is read ONCE at act start — the act's ONLY reading of the symbolic HEAD for a VALUE — and serves the refspec, the tracking-ref observation AND every source-side observation the act makes (the `before` read, the attribution walk's tip, the clean arm's byte confirmation all name `refs/heads/<captured>`; round 4 closed the gap where they still followed HEAD, which let a mid-act checkout have the walk attribute a commit made on ANOTHER branch and the pinned push then publish that branch's ancestry onto the captured one — verified live). THE ONE OBSERVATION THAT CANNOT BE SPELLED IS CHECKED INSTEAD (round 5, completing that binding): `git status` takes no ref and always answers for whatever HEAD points at, so the pre-flight compares the `##` header it already demanded as its ran-witness against the captured name and a MISMATCH FAILS THE ACT CLOSED with one line naming both branches — never Clean, never Dirty, nothing committed or pushed, the written sidecars left in the working tree as after any other failure here. Without it the clean arm could end the act on another branch's answer (reproduced live: captured `main` carries the old bytes, a topic branch already carries the new ones, a checkout lands between capture and probe, the freshly written bytes match the topic tree exactly → `status` says CLEAN, captured `refs/heads/main` resolves with `origin/main` caught up to it, and NothingToCommit returns before the byte confirmation ever runs — the user told the checkpoint already carries bytes the captured branch does not have). Header grammar verified live in every shape (`## main`, `## main...origin/main [ahead 1, behind 2]`, `## HEAD (no branch)` = detached and compares as the captured detached "", `## No commits yet on main`): the cut is on `...` then on a space, both unambiguous because a refname may contain neither two consecutive dots nor a space, so `feat/a.b.c` parses whole; any shape the parse has not seen simply mismatches and fails closed. The commit itself necessarily lands wherever git is checked out, and needs no pinning: if a checkout intervened the walk over the captured ref's range finds nothing and the act returns CommitFailed having published nothing, which is the honest outcome. A detached HEAD keeps the HEAD spelling (there is no branch ref to name) and publishes nothing, saying so. The one destination rewrite the guard cannot see, recorded at its site: `url.<base>.insteadOf` redirects a URL when git USES it while `remote get-url` reports the raw config value — pre-existing, and unclosable by pinning. `run_git_mutate` carries a 30s deadline whose expiry kills the child's whole process group (setpgid; git's own ssh/hook children die with it) under a pre-fork non-interactive environment (GIT_TERMINAL_PROMPT=0, ssh BatchMode, stdin /dev/null), and shares the capture's exec self-pipe so could-not-start is a real verdict on both entry points. Tree listings are NUL-separated (`ls-tree -z`) so a UTF-8 base name survives `core.quotePath`.

`projects_repo` (settings.md owns the key's full record; a REQUIRED key like every other since 2026-08-04, the one-day optional exception retired at the architect's live pass) names WHICH repository is the projects home; the local clone is the transport, and init's guard normalizes the setting against the clone's FETCH URL AND EVERY EFFECTIVE PUSH URL (`remote get-url` + `--push --all` — a configured pushurl must match too, or the checkpoint act could publish to an unconfirmed repository; scheme, scp `git@host:path`, trailing `.git` all compare equal), refusing a mismatch with one stderr line, and — at the pre-push asking — handing the first validated push URL back as the destination that asking's caller pins. An empty value never matches — the feature's opt-out. Which repository, not how fresh: the guard never checks staleness.

## The match and the walk

THE MATCH IS BY COMMITTED FILE NAME UNDER `projects/` (architect 2026-08-03; narrowed from the whole tree 2026-08-04 — the repo-layout convention is `<repo>/projects/`, one folder per piece, and a theoretical other user builds their own repo with a `projects/` folder): the loaded source's sidecar base name (the loader's own `stem()` derivation, mirrored — it strips only the last extension, load-bearing for period-heavy titles) is resolved against HEAD's tree filtered to `projects/`; exactly one directory may carry the sidecars. The walk is `git log` — UNCAPPED since 2026-08-07, the `-n 20` term deleted with the ruled depth — over `:(glob)projects/**/<base>.<ext>` pathspecs with the basename's wildmatch metacharacters ESCAPED, every mutation/status pathspec wears `:(literal)` magic (a filename carrying `*?[` can never widen a checkpoint), and each commit's snapshot paths resolve from THAT commit's own tree — preferring HEAD's own matched directory, taking a sole other, and otherwise REFUSING as ambiguous (through `read_commit_sidecars`) rather than silently showing one piece's history as another's. THE WALK IS LOAD-GATED (architect 2026-08-04): membership is THE LOAD-IN-PLACE GATE ITSELF — `load_commit_sidecars_strict`, the exact resolution + scratch staging + three strict frozen loaders the `'` act runs, ONE predicate with no relaxed variant — applied eagerly to every candidate at init, so every checkpoint the mode can step to is one `'` can load. A candidate that refuses (a missing sidecar, a parse refusal, an ambiguous per-commit path resolution) leaves the walk at entry, ONE stderr line counting the hidden ones; the corner's `n/N` counts the ELIGIBLE list, and the gate keeps each member's three sidecar snapshots as its then side, so no delta ever runs git. The per-commit `Ambiguous` display machinery is RETIRED with the gate — an ambiguous commit is never shown at all, and the ambiguity refusal survives only as the `'` act's own arm for a PASTED spelling naming a commit outside the walk. ACCEPTED TRADES, recorded: basename matching cannot see history across a SOURCE RENAME, and every legacy-format checkpoint leaves the walk under the gate exactly as the `examples/`-era commits left it under the round-5 narrowing (the walk heads at the first load-clean commit until the first commit act). A piece with NO committed history — or none whose sidecars pass the strict load — cannot open the mode at all; its bootstrap stays a manual act.

THE WALK IS PREFETCHED AT STARTUP AND ARRIVES ONE COMMIT AT A TIME (architect 2026-08-07), which is the same ruling as the uncapping and its precondition. The load gate costs a `rev-parse` + `ls-tree` + three `show`s + three strict parses PER CANDIDATE, and running that at every `h` is what made the entry stall — and what the depth of 20 was really buying. So the whole git half moved off the entry onto `GuiHistoryPrefetch` (`src/gui/history_prefetch.{h,cpp}`), a background worker shaped exactly like the checkpoint worker's (own thread, condition variable, an eventfd the run loop polls as its SIXTH pollfd and FOURTH completion-fd registration) with one difference in the traffic's direction: a scan produces MANY results, so what crosses is a mutex-held QUEUE of tagged messages and the eventfd is a plain coalescing counter — a POLLIN means "the queue has something", never how much, and the drain empties it. THE GIT ITSELF STAYED IN `history_diff.cpp` (`scan_history_walk`, `resolve_history_walk_header`, `read_history_branch_tip_sha`), so the read/write fence is still "which function a call site names" and the worker file owns only threading. A run does exactly what init() did, in order — the projects-home guard, the base-name derivation, the tip-tree match, the uncapped `log`, then the strict load gate per candidate — publishing THREE message kinds: a HEADER (the guard/base/directory verdict, or the unavailable reason, plus the branch tip the run was built against), one MEMBER per ELIGIBLE commit in walk order, and a DONE carrying the candidate and hidden counts. The counted stderr line prints at the DONE, once per run, in its old wording; an ineligible candidate produces no member message.

THE STORE IS MAIN-THREAD STATE, written only by the drain and the kick, so `GuiHistoryDiff` holds a pointer into it and reads it from paint and input with no lock. `init()` SPLIT accordingly: the git half is gone and what remains is the BINDING (the store plus the generation this visit entered against), the header — taken from the store, or COMPUTED SYNCHRONOUSLY right there by `resolve_history_walk_header` when a visit opens before the worker's own header has arrived, two git calls and no strict load, so every entry refusal keeps its exact shape and stderr line — and the LIVE half, unchanged: freeze the now side, and now grow the delta caches lazily rather than sizing them once. `commit_count`, `sha_at` and the member texts index the store's deque.

THE WALK GROWS DURING A VISIT, and that is the streaming working rather than a hazard: members arriving while the mode stands appear live, `n/N` grows, the `,` wall moves outward, the lane repaints. Four things make it sound. (1) The DELTA CACHES became `std::deque<std::optional<...>>` per reading — deque `push_back` never moves the elements already in it, which is `delta_at`'s pointer-stability contract restated for a growing list; every holder of a returned pointer is function-local and re-asks (re-derived by grep 2026-08-07). (2) The ITERATIVE PAIRING IS APPEND-STABLE BY CONSTRUCTION: index i pairs with i−1 or the live now side at 0, both NEWER than i, and every arrival is OLDER than everything already delivered, so no cached delta is ever invalidated by an append. (3) The FLAG-CACHE FINGERPRINT carries the member count as its twentieth field and the history block's seventh — the arrival that matters most (member 0 into an empty walk) moves no other field, so without it the lane would sit blank over a delta it now has. (4) The HEAD DELTA's rule changed from "measured once at entry" to "measured once": with no member 0 to measure it RESTS TRUE — the conservative face, Save-and-Commit greyed while the answer is unknown — and is measured at the first arrival that delivers it, static thereafter. One measurement site either way (`GuiInputHandler::measure_history_head_delta`).

EMPTY-WALK ENTRY IS ALLOWED, terminal zero is not: a header that is good with no member yet and a run still streaming OPENS the view (`0/0`, blank lane) and populates live, while a run DONE with zero eligible members refuses entry with today's own line — "No commit touches …" when the `log` produced no candidate, "None of the N commit(s) … passes the strict sidecar load" otherwise. Refusing on emptiness alone would make entry a race. A `,` / `.` step past the current wall stays a clamped consumed no-op; it may become steppable a moment later.

THREE KICKERS THROUGH ONE FUNNEL (`GuiInputHandler::kick_history_prefetch`): the startup load's tail (main.cpp, where the source path and `projects_repo` settle), the checkpoint completion for the two outcomes that MOVED HEAD (`Committed`, `CommittedNotPushed` — the other three moved no ref, so the standing store is still true), and the `h` entry when the store is STALE. STALENESS is three terms — the source path, the `projects_repo` and the branch tip the run was built against, the last compared against a live `rev-parse` — with a run STILL IN FLIGHT for the same subject counting as fresh, which is what covers the window before its header (and its tip) has arrived. A KICK WHILE THE VIEW STANDS IS DEFERRED to the exit owner, never dropped and never run: the visit is bound to a generation and a restart would clear the deque its indices name out from under it. A kick while a run is mid-flight SUPERSEDES: the generation bumps, the store clears, and the run abandons at its next CANDIDATE boundary (one atomic checked at the loop's top — the finest grain that costs nothing). Messages are TAGGED with their generation and the drain drops any that do not carry the current one, so a superseded run's late members and its DONE change nothing; the kick also empties the queue, so the tag catches only what the worker pushed between that clear and its next abandon check.

ACCEPTED, RECORDED: the prefetch's git READS may overlap the checkpoint act's MUTATIONS, since both run on their own workers. A read that races sees the repository partway through, and the answer is the re-warm rather than a lock — the act's completion kicks a fresh run, rebuilding whatever raced. No VIEW can be reading a half-mutated walk either, `h` being refused outright while a checkpoint publishes. One collateral fix the two threads forced: `load_commit_sidecars_strict`'s scratch directory was named pid + short SHA, which two threads asking about ONE commit (the worker gating it while the `'` act loads it) would collide on, the loser's RAII guard removing the winner's staged files mid-load; the leaf carries a process-wide atomic serial now, so it is per-CALL rather than per-commit.

## The diff model

WHICH TWO SIDES A DELTA COMPARES IS THE COMPARE MODE'S ANSWER (the section below; the cumulative reading is described here, and the iterative one substitutes the NEXT-NEWER ITEM for the now side — a commit, or this same frozen now side at the newest index — through the same mechanism). The CUMULATIVE NOW side is the live in-memory state serialized through the save writers' own string halves (`format_warpmarkers_text` / `format_phaseresetmarkers_text` / `format_settings_text` — the round-1 split; byte-identical to a Ctrl+S, no disk touched) and is FROZEN AT init(); the mode's mutation gate is what keeps the frozen snapshot honest (authoring is blocked while the mode stands, so it cannot go stale by construction). Then-vs-now is an in-tree line LCS (DP with prefix/suffix peeling and a cell cap) typed into per-commit deltas: warp added/removed/changed carrying each line's VERBATIM tempo token (the flag shows the sidecar's own spelling, never a re-derivation), phase resets added/removed/changed (their line is frame plus disable prefix, so a `#` toggle pairs as a genuine change, symmetric with warp), and the `scale=` tokens from both sides (THE ONLY SETTINGS KEY THE MODE DISPLAYS — a recorded asymmetry: every other settings delta is deliberately invisible). A same-frame remove+add pair IS the changed entry — it feeds the double flag. WALK MEMBERSHIP IS LOAD-GATED (2026-08-04, superseding the old two-tier "diff is parse-free / load-in-place is parse-gated" answer): everything visible is loadable, so both sides of every diff are loader-clean text with all three files present, and the diff mechanism stays line-based with NO leniency arm left — the drop-unparseable-lines arm with its counters (`GuiHistoryLineCounts`), the missing-file-reads-as-empty-side arm, and the per-commit `Ambiguous` state are all DELETED as dead code (the architect's no-legacy rule: the program never imports leniently; an old-format checkpoint is hand-edited, never tolerated). The extraction's boolean is the parse's own optional shape, not a tolerance. The one degraded arm kept is an ALLOCATION guard, not a format leniency: a loader-clean sidecar past the DP cell caps diffs coarsely as replaced whole. Deltas compute lazily against the snapshots the gate kept and cache per (commit, compare reading); stepping revisits and reading switches alike are free, and no delta runs git at all.

## The two compare modes (2026-08-05)

A CHECKPOINT HAS TWO INTERESTING OTHER SIDES, and the architect ruled that the view offer both rather than choose. The reading the mode shipped with is named CUMULATIVE — the viewed checkpoint against the FROZEN LIVE NOW SIDE, which answers "how does what I have now differ from that checkpoint" and is the reading a restore or a load-in-place is about. The new one is ITERATIVE, and it COMPARES FORWARD, TOWARD NOW (architect 2026-08-05, superseding his walk-parent pairing of earlier that day): the viewed checkpoint is the OLD side and THE NEXT-NEWER ITEM the new one — the next-newer ELIGIBLE WALK MEMBER at every index but the newest, and THE FROZEN LIVE NOW SIDE at the newest, which has no committed successor. It answers "what happened AFTER this checkpoint", one step at a time, which is what a walk backwards through the history is asking at each stop. ITERATIVE IS THE DEFAULT AT EVERY ENTRY — RATIFIED at the architect's live pass (2026-08-05), the reading he kept, and the bit is a plain member initializer on `AppState::HistoryMode::compare`, so the whole-struct reset at both edges applies it and no visit inherits the last one's reading.

THE COLOR GRAMMAR IS ONE RULE ACROSS BOTH, which is the pair's whole reason for fitting: the NEWER side is always the diff's now side, so green `[+]` is what the newer side has and red `[-]` what the older side had and the newer dropped. In cumulative the newer side is the session; in iterative it is the next step forward — the newer checkpoint, or the session itself at the newest index. Nothing in the lane, the flag texts, the double-flag pairing or the colors knows which reading it is drawing — `rebuild_history_diff_flags` reads whatever delta it is handed.

THE MECHANISM IS THE SAME TYPED LINE DIFF, taken off the walk position: `compute_commit_delta` (history_diff.cpp) runs the identical LCS + extraction + same-frame pairing over whichever pair of texts the reading names, and `delta_at` picks the pair — cumulative = the member's kept snapshots against `now_`, iterative = the member's kept snapshots against the NEXT-NEWER member's (or against `now_` at index 0). Both sides are LOADER-CLEAN in both readings, since walk membership is the strict whole-set load and the gate kept every member's three sidecar texts; so a delta still runs NO GIT AT ALL, in either reading. THE `scale` PAIR RIDES THE SAME SUBSTITUTION (then = the older side's token, now = the newer's), so the corner line says the same kind of thing in both. CACHED PER (INDEX, COMPARE) — one DEQUE of optionals per reading, grown to membership as the prefetch delivers (2026-08-07, replacing the vector sized once at init: a deque's `push_back` moves no element already in it, which is what keeps `delta_at`'s returned pointer good under a growing walk) — so a switch back is as free as a step back and no delta is ever recomputed.

THE TWO READINGS COINCIDE AT THE NEWEST INDEX, deliberately and by construction: both are the newest checkpoint against the live now side there, so A SESSION FRESHLY LOADED RIGHT AFTER A COMMIT SHOWS A BLANK LANE IN BOTH READINGS — the architect's stated purpose for turning the direction forward. Nothing has to know: the two are simply the same delta, computed and cached twice in their own slots rather than aliased, since the coincidence is a property of the pairing and not a rule any reader should carry. The visible cost is that a switch at `1/N` redraws the same lane and moves only the lit tab; accepted, and it is the honest face of the pairing.

EVERY INDEX HAS A FORWARD PARTNER, so THE EMPTY-DELTA SPECIAL CASE IS DELETED — the walk-parent pairing's oldest-member arm, its structural no-diff-run and the reasoning that justified it are gone from the model, the header and the docs alike. The walk's OLDEST end is now an ordinary index whose partner is the member one newer, and its NEWEST end is where the live state is. AND THE NEXT-NEWER MEMBER MAY SPAN COMMITS THE LOAD GATE HID: that is the walk's own honesty rather than a defect of the pair, since an ineligible commit is not steppable, not loadable and not shown, and the nearest checkpoint the mode CAN show is the only one whose delta has two reachable sides. It applies BETWEEN COMMITTED NEIGHBOURS only — the newest index's partner is the live state, which nothing can hide.

THE TABS SELECT THE MODE, and it is the Render-button hijack applied to a whole row (kdenlive-redesign.md's row-3 record): while the view stands row 3 stops being the A/B tabs and becomes this bit's radio — tab A reads "Iterative", tab B "Cumulative" (and since 2026-08-07 two further slots carry the LOCAL walk's same two readings — the local-walk section below owns that growth; everything in this paragraph holds for all four) (sentence-case ordinary labels, not the Render row's two named title-case exceptions), the selected face marks the live reading, a press on the other switches and a press on the lit one is a consumed nothing. THE LOCK SLOTS ARE GONE WHOLE in there — not drawn, not reserved in the width, no rect published — because a padlock reports a TAB's read-only bit and these are not tabs; which also makes the press path's lock branch unreachable in the mode without testing for it. ITS HOTKEY IS CTRL+TAB — THE TABS' OWN CHORD, FOLLOWING THE SURFACE (architect 2026-08-05, SUPERSEDING his same-day "there is no hotkey, the surface is repurposed while the keys are not"): in the mode that chord steps the reading through the one switch owner instead of switching tabs — a TOGGLE over the pair, and since 2026-08-07 a FORWARD-WITH-WRAP CYCLE over the four, the toggle's natural generalization, which is the mode-bit-selects-the-command shape Ctrl+Alt+R already has, and outside the mode it is byte-identical to before. ## The local walk — the undo history as a second walk (2026-08-07)

THE VIEW READS TWO WALKS NOW. The architect's motivation is one sentence: "the local history feature will be helpful for understanding undo/redo history." So beside the COMMIT walk — the piece's committed sidecar checkpoints — the mode grew a LOCAL one over THE SESSION'S OWN UNDO STACK, read through the identical delta machinery, and row 3 became FOUR tabs in that order: **Iterative / Cumulative / Iterative (Local) / Cumulative (Local)**. The axis is `GuiHistoryWalkSource` (Commit | Local, history_diff.h), COMMIT is the default at every entry (a plain member initializer, applied by the whole-struct machinery exactly as the compare bit's is), and the two walks keep SEPARATE POSITIONS — `index` is the commit walk's, `local_index` the local one's — so each is a place a visit can come back to rather than one place with a changing subject.

A MEMBER IS ONE UNDO ENTRY'S STATE, serialized through the save writers' own string halves. With N = `app.history.undo_stack.size()`, member index i (newest first) is `undo_stack[N-1-i]`, and that entry's snapshots are the state BEFORE the event it records; the three texts are `format_warpmarkers_text(entry.snapshot)`, `format_phaseresetmarkers_text(entry.phase_reset_snapshot)` and the settings file formatted from that entry's ENGINE settings plus ONE CAPTURED GUI HALF. That capture is the piece that had to be added: `NonEngineSettingsSnapshot` is a call-shaped borrowing type, so `GuiHistoryGuiSide` (opaque in the header, ViewState living in app_state.h) holds it by value, `capture_history_gui_side` takes it at the mode's entry with the save path's own active-tab overlay, and `format_history_settings_text` is the one formatter BOTH the frozen now side and every local member go through. Which is why a local delta can only differ in the ENGINE block: GUI-kind keys are history-less, so using the same half on both sides means the view's own navigation cannot show up as a settings difference — and `scale=`, the one settings key the mode displays, is an engine key anyway.

THE ITERATIVE READING IS EXACTLY ONE EVENT, and that is the pairing's derivation rather than a coincidence: index i pairs FORWARD with i−1 (the frozen live now side at i = 0), and the state before event i−1 IS the state after event i — so the delta at index i is EVENT i'S OWN CHANGE. Every index has a forward partner for the commit walk's own reason (the newest end is where the session is). CUMULATIVE is the same pairing it is over there: member i against the frozen live now side, "how far back does this take me". Both feed `compute_commit_delta` — which stopped being file-local for exactly this, a copy of it being the second grammar this module refuses everywhere else — with an EMPTY sha, and both are cached per (index, reading).

THE NOW SIDE IS SHARED, ONE CAPTURE PER VISIT: `GuiHistoryDiff::init` freezes it and `GuiHistoryLocalWalk::init` takes it through `now_side()`, so the two walks structurally cannot disagree about what "now" is.

THE STACK IS ALL BUT FROZEN WHILE THE VIEW STANDS, which is the frozen-now-side derivation run again: every route that could push, pop or evict an undo entry is an authoring route, so the two allowlists consume it or one of the mode's three mutators closes the view as part of itself — WITH ONE ADMITTED PRODUCER, the S→T view switch's iteration-bracket push (admitted on the read-only gate's own argument, brackets being session-only). The member count is therefore captured at init and the caches are plain vectors sized once (where the commit walk needs deques for its streaming growth), and THE INDEXING IS FROM THE BOTTOM, which is what makes that push harmless: an append leaves every captured position naming the entry it named, the new entry is simply not in the walk, and the frozen now side is the state before it, so index 0's forward pairing is still exactly event 0's change. A SHRUNKEN stack — no producer at all — answers no delta rather than being read at indices that now name other events. The one shape neither term catches is an EVICTING push (a stack at `UndoHistory::kCap` when that switch fires: the size holds while every position shifts by one), which is recorded at `member_at` as an accepted corner — 500 undo entries, brackets standing, an S→T switch made inside the view, and the cost is a lane showing its neighbour's delta until the visit ends. Member texts are serialized LAZILY on first ask, so `h` pays nothing for a five-hundred-entry stack.

(1) AN `affects_persistence == false` ENTRY SHOWS A BLANK LANE — the iteration bracket's session-only snapshot serializes identically on both sides, so there is nothing for a delta to say about it. Honest rather than a gap: the walk shows what the commit history would. (2) THE REDO STACK IS DELIBERATELY EXCLUDED — the walk is what is BEHIND you, the commit walk's own shape, and redo is the branch you stepped off; including it would need a second index origin and a signed position to answer a question the undo members already answer one step at a time.
