## Transport and trust

LOCAL GIT, THE READ/WRITE SPLIT AS TWO ENTRY POINTS. The module (`src/gui/history_diff.{h,cpp}`) shells to git with an argv exec (no shell anywhere — corpus paths carry spaces) against the repository root DERIVED FROM THE LOADED SOURCE (the paragraph below; every call takes it as a parameter, so `run_git_capture` and `run_git_mutate` each carry a `root` beside their argv). `run_git_capture` passes ONLY reads — `log`, `show`, `ls-tree`, `rev-parse`, `status`, `rev-list`, `remote get-url` — and `run_git_mutate` (the commit act's fenced writer and its ONLY caller) passes ONLY `add`/`commit`/`push`; the fence is which function a call site names. No fetch, no credential in the program: every read is against the LOCAL branch (the product is a commit producer, and a checkpoint whose push failed must still be visible history; `origin/main` would hide it until the next successful push), and the push authenticates through the machine's own SSH setup. main.cpp's `SIG_IGN` SIGCHLD auto-reap (the audio-player precedent) makes `waitpid` return ECHILD, so THE PROGRAM CANNOT READ CHILD EXIT CODES, and the two entry points answer that differently. CAPTURES ARE A TRI-STATE: a CLOEXEC self-pipe distinguishes could-not-exec from ran, each caller carries its own output-shaped witness (the pre-flight asks `status --porcelain --branch`, whose header line only a successful run emits; the load-in-place cross-checks each captured blob against `ls-tree -l`'s own byte count, so a failed or truncated `show` can never stage a sidecar state the commit never held), and "ran with empty output" is never read as success. THE RULE IS THAT A SUCCESS NEEDS AN OUTPUT-SHAPED WITNESS, and after the 2026-08-09 rounds every reader of this module honours it in the same direction: the scan's emptiness verdict rests on `rev-list --count` printing "0" (bytes, not silence) and on the enumeration MATCHING that count; the per-commit touched-directory `show` accepts its answer only in a well-formed shape — NUL-terminated framing, every record one of this piece's sidecars under `projects/`, none repeated, at most a folder's three — and an empty or malformed answer REFUSES rather than resolving. THE ONE PLACE AN EMPTY OUTPUT IS LEGITIMATE CONTENT is the load-in-place's BLOB reads, where an empty sidecar is a valid whole file in both marker grammars; that is why they call `run_git_capture` directly and why the tree listing's stated byte length is carried alongside as the second witness. THE DIRECT CALLERS ARE SEVEN (re-derived by grep 2026-08-11, the count having stood at four and then five while the inventory was edited rather than re-derived), and past the blob reads they split two ways: FOUR judge the SHAPE of what arrived, which `git_output`'s length test cannot do — the scan's `rev-list --count`, the evidence `show`, the commit act's status pre-flight and the push verify's containment walk — while TWO want the RAN-versus-COULD-NOT-RUN bit itself, a question about the invocation rather than the output: the ROOT DERIVATION, whose two refusals are exactly those two states, and `resolve_ref_capture`, which hands the verdict on beside the object name. MUTATIONS ARE ADVISORY AND THE ACT DECIDES ITS FAILURES ON THEM (architect 2026-08-09, THE STRICT MODEL): `run_git_mutate` reports only that the child was STARTED and ran to its own end — false means it could not start (exec or pipe failure) or outlived the deadline, AND NOTHING MORE: the child's exit status is UNREADABLE (main() ignores SIGCHLD, so waitpid answers ECHILD), so a nonzero-exiting child inside the deadline returns TRUE. False is still a failure the act reports (CommitFailed, CommittedNotPushed) with git's first line carried along; a child-reported failure is caught instead by OBSERVATION (the tip-move check at the commit, the containment verify at the push — 2026-08-09, codex round 11's HIGH: failures may decide on the advisory return OR an observation, successes only ever on observations). SUCCESS IS STILL NOT THE TRANSPORT'S TO CLAIM: `Committed` is asserted only where the remote-tracking ref was OBSERVED to carry the checkpoint, and an unanswerable observation is `Unconfirmed`, never a yes. THE GRADED MACHINERY THAT STOOD HERE FROM 2026-08-04 TO 2026-08-09 IS DELETED WHOLE — the content-signature attribution walk over `before..refs/heads/<branch>` with its title, path-subset and byte legs (`find_checkpoint_commit`, `commit_carries_our_bytes`, `commit_touches_only`), the checkpoint-subject selector, the committed-but-unpushed retry family and the positive-witness ref grading (`resolve_ref_witnessed`, whose job was to keep an ABSENT ref and an UNREADABLE repository from sharing an answer; plain reads now, and the two share `Unavailable`) — all of it superseded by the ruling that SANCTIONED USE IS STRICT-EXACT INTENDED USE. `run_git_mutate` carries a 30s deadline whose expiry kills the child's whole process group (setpgid; git's own ssh/hook children die with it) under a pre-fork non-interactive environment (GIT_TERMINAL_PROMPT=0, ssh BatchMode, stdin /dev/null), and shares the capture's exec self-pipe so could-not-start is a real verdict on both entry points. Tree listings are NUL-separated (`ls-tree -z`) so a UTF-8 base name survives `core.quotePath`.

THE CLONE YOU OPEN FROM IS THE CLONE THAT COMMITS (architect 2026-08-11, SUPERSEDING the compiled-in absolute path this module held from the arc's first day). That path rested on the single-laptop premise the whole product rests on — the same footing as labwc and 1920x1080 — and the premise stopped being true: there are TWO HOSTS now, the x86 laptop and a Raspberry Pi ROAD RIG, and a fixed `/home/b/.warptempo/warptempo_gui` forced the rig to replicate the laptop's directory layout by hand before the history view would work at all. So the root is DERIVED: `git -C <the source's parent folder> rev-parse --show-toplevel`, canonicalized, through `resolve_repo_root_for_source` (history_diff.h) — which is the FOLDER LAW CARRIED ONE LEVEL UP, the same move that made the source's own parent the project directory in 2026-08-09. There is NO settings key, NO environment variable, no fallback search, no walk up from the binary and NO cached global: the answer travels as a value, out of `GuiHistoryWalkHeader::repo_root` and down through every consumer as a parameter, which is also what keeps it safe for the prefetch worker and the checkpoint worker to ask on their own threads. `GuiHistoryDiff::repo_root()` is the session's copy and the two in-view mutating routes take it from there — `'` hands it to `load_commit_sidecars_strict`, Save and Commit carries it onto the checkpoint job. TWO REFUSALS, told apart by the capture tri-state and nothing else (exit codes being unreadable here): a `rev-parse` that RAN and printed nothing is the ruled NOT-A-CLONE, one stderr line naming the source's own directory whose fix is a clone or a file move, exactly the shape the not-under-`projects/` refusal already has; one that could NOT RUN, or that named something which is not a directory, is A READ THAT DID NOT ANSWER and rides `GuiHistoryWalkHeader::read_failed` into a NOT-OK `GuiHistoryScanResult`, the "an unread history never passes for an empty one" shape, so a repository this program never managed to question can never establish an empty walk and light Save and Commit against a baseline nobody read. THE PROJECTS-HOME GUARD IS UNCHANGED and still asks WHICH repository — it now asks it of the derived clone's remotes, which is the question it always meant. `read_history_branch_tip_sha` takes the SOURCE rather than a root and derives its own, both its callers (the prefetch worker before a run, the `h` entry's staleness test) asking before any header exists; an `h` entry therefore pays two `rev-parse`s on the main thread instead of one, and a run pays one derivation twice, which is nothing beside a six-child load gate per candidate.

`projects_repo` (settings.md owns the key's full record; a REQUIRED key like every other since 2026-08-04, the one-day optional exception retired at the architect's live pass) names WHICH repository is the projects home; the local clone is the transport, and init's guard normalizes the setting against the clone's FETCH URL AND EVERY EFFECTIVE PUSH URL (`remote get-url` + `--push --all` — a configured pushurl must match too, or the checkpoint act could publish to an unconfirmed repository; scheme, scp `git@host:path`, trailing `.git` all compare equal), refusing a mismatch with one stderr line, and — at the pre-push asking — handing the first validated push URL back as the destination that asking's caller pins. An empty value never matches — the feature's opt-out. Which repository, not how fresh: the guard never checks staleness.

## The match and the walk

THE MATCH IS BY COMMITTED FILE NAME UNDER `projects/` (architect 2026-08-03; narrowed from the whole tree 2026-08-04 — the repo-layout convention is `<repo>/projects/`, one folder per piece, and a theoretical other user builds their own repo with a `projects/` folder): the loaded source's sidecar base name (the loader's own `stem()` derivation, mirrored — it strips only the last extension, load-bearing for period-heavy titles) is what the walk matches on, anywhere under `projects/`; the tip-tree resolution that once turned that name into the piece's ONE directory is gone with the three arms (the law below), and where the piece lives is a separate question answered from the source path. The walk is `git log` — UNCAPPED since 2026-08-07, the `-n 20` term deleted with the ruled depth — over `:(glob)projects/**/<base>.<ext>` pathspecs with the basename's wildmatch metacharacters ESCAPED, every mutation/status pathspec wears `:(literal)` magic (a filename carrying `*?[` can never widen a checkpoint), and each commit's snapshot paths resolve AT THE DIRECTORY THE COMMIT TOUCHED (2026-08-09) — a per-commit `git -c diff.renames=false show -z --format= --name-only` over the same pathspecs, one extra child per candidate and the deliberate price of ONE resolution owner shared by the walk and by `'`, so a member can never display one folder's snapshot and load another's. THE ANSWER IS FIRST CHECKED FOR SHAPE — NUL-terminated framing (a mid-record child death cannot produce it), every record one of this piece's sidecars at a directory strictly below `projects/`, none repeated, at most a folder's three — and only then read: ONE directory is the answer; TWO OR MORE refuses as ambiguous; NONE, or any malformed shape, refuses too, and there is no fallback of any kind behind it (through `read_commit_sidecars`) rather than silently showing one piece's history as another's. THE WALK IS LOAD-GATED (architect 2026-08-04): membership is THE LOAD-IN-PLACE GATE ITSELF — `load_commit_sidecars_strict`, the exact resolution + scratch staging + three strict frozen loaders the `'` act runs, ONE predicate with no relaxed variant — applied eagerly to every candidate at init, so every checkpoint the mode can step to is one `'` can load. A candidate that refuses (a missing sidecar, a parse refusal, an ambiguous per-commit path resolution) leaves the walk at entry, ONE stderr line counting the hidden ones; the corner's `n/N` counts the ELIGIBLE list, and the gate keeps each member's three sidecar snapshots as its then side, so no delta ever runs git. The per-commit `Ambiguous` display machinery is RETIRED with the gate — an ambiguous commit is never shown at all, and the ambiguity refusal survives only as the `'` act's own arm for a PASTED spelling naming a commit outside the walk. THE SOURCE'S FOLDER IS THE PROJECT DIRECTORY, AND THAT IS THE WHOLE RULE (architect 2026-08-09, `resolve_history_walk_header`). A piece lives in its own folder under the clone's `projects/` with its source inside it, so the folder holding the source is the folder its checkpoints belong in — nothing to match, nothing to synthesize, nothing to disambiguate. Containment is decided on CANONICAL paths (`weakly_canonical` on the source, then `relative` against the canonical repo root, then the first component), so a symlinked corpus resolves in and a `..` that leaves the clone resolves out, and a source named as a bare filename canonicalizes against the working directory — which is what makes launching from inside the folder answer that folder. The parent must be STRICTLY below `projects/`: one folder per piece, so a source loose at the corpus root has no folder of its own and refuses like any other. THE LAW REPLACED A THREE-ARM PRECEDENCE THE SAME DAY IT WAS WRITTEN (a committed tip-tree match, then this, then a synthesized `projects/<base name>`), and it earned the deletion of everything those arms needed: the tip-tree listing, `sole_directory_of` with its ambiguity refusal, and the checkpoint act's `create_directories` step, the remaining folder existing by construction because the source is in it.

CONTINUITY RIDES THE BASENAME, NOT THE FOLDER, which is what the deleted committed-match arm used to answer: the walk's pathspecs are `:(glob)projects/**/<base>.<ext>`, so a piece's history is every commit that touched a file by that name ANYWHERE under `projects/`, and a folder renamed, re-nested or made fresh today still walks back through every checkpoint the piece ever had. The folder decides what is WRITTEN next; the name decides what is SEEN. CONTAINMENT WAS THE WRONG EVIDENCE FOR WHICH FOLDER A COMMIT IS ABOUT, and that is why the per-commit rule changed with the law: the act is pathspec-scoped and never deletes the folder a piece has moved out of, so a commit CONTAINS every folder the piece has ever lived in. Preferring the session's own directory whenever the tree carried the base name there made a checkpoint written from a BACKUP copy display the ORIGINAL folder's untouched blobs as its own state, and `'` on that SHA load them; and it made pre-rename-era commits carry two candidate folders and hide as ambiguous, so a renamed folder DID cost history. Asking what the commit CHANGED answers both, a checkpoint changing exactly the folder it was made from. AND THE CONTAINMENT FALLBACK WENT WITH IT, later the same day and for that reason carried one step further: kept as the answer for "no touch evidence", it LAUNDERED SILENCE INTO SUCCESS on every shape that produces silence. Measured, both: a pasted spelling naming an ordinary commit that touched only unrelated files answered nothing, fell back, found the session's directory in that commit's TREE and loaded all three blobs — a reported SUCCESSFUL load of a snapshot the commit is not about; and a `show` that RAN AND FAILED is ran-with-empty too, so the same fallback fired with nothing verified. Under sanctioned use every candidate is an act-made commit touching exactly one folder's three files, so the fallback only ever served shapes the model does not have, which made DELETING it the conversion rather than guarding it — the day's own ruling applied once more. The walk-side consequence is nearly unreachable and that is the point: a candidate came off a `log` over these very pathspecs, so an empty answer there is a CONTRADICTION (object damage, or a merge git listed and would not diff) and is hidden, counted, blunt. `head_directory` went with the fallback, out of `resolve_commit_paths` and out of the two loaders above it. IT MUST BE `show` AND NOT `log -1`: `-1` limits how many commits a WALK reports, not which commit is asked about, so `log -1 <sha> -- <pathspecs>` on a commit that touched nothing matching walks on to the nearest ANCESTOR that did and answers ITS paths — measured live, a commit touching only unrelated files answered the previous checkpoint's sidecar paths, which through `'` with a pasted spelling is a successful load of the WRONG snapshot, the false established success this module refuses everywhere. `git show` names ONE commit and walks no ancestry (not "diffs against the first parent" — for a merge the default display is a COMBINED diff; what matters here is that it never reports another commit's paths). Measured on every shape: a ROOT commit answers its own paths, a two-folder commit answers both, and a DELETION-only commit answers the folder it emptied (whose blobs the tree then lacks, which the missing-sidecar refusal reports). THE SHAPE CHECK IS DERIVED FROM WHAT A CHECKPOINT CAN BE, not assumed: the act writes one folder's three sidecars and commits pathspec-scoped to exactly those three, so a commit touches a NONEMPTY SUBSET of one folder's three — a subset, because `git commit` records only what changed, and a checkpoint whose phase resets and settings came out byte-identical touches ONE file (measured: an ordinary second checkpoint with only the warp markers moved reports exactly one path). An "exactly three" signature would therefore refuse the product's own commonest commit, so the rule is recognized-and-unrepeated-and-at-most-three, plus the framing, which is what a truncation actually breaks. THE RESIDUAL IS ADVERSARIAL AND ACCEPTED: a child dying exactly ON a record boundary leaves a well-framed PREFIX, so a multi-directory answer could still read as the single directory it began with — reaching it needs an unsanctioned multi-directory commit AND a deterministic death at that byte, the hand-broken-repository category, and no second read is added to chase it. AN EMPTY ANSWER IS NOT A MERGE AND NOT ANY OTHER SINGLE THING: it has THREE producers — a commit touching none of these paths, a merge git would not diff, and a `show` that ran and failed — indistinguishable by design and folded into one outcome and one message, because nothing downstream can tell them apart and nothing should guess. (The "merge" reading was never even reliable: the default merge display is a COMBINED diff, so an EVIL merge that changed a sidecar relative to both parents DOES emit the path and resolves or hits ambiguity like any other commit. Moot now that silence refuses everywhere.) THE RENAME CONFIG IS PINNED IN THE ARGV, `-c diff.renames=false`, on the pinned-pushurl precedent: rename DETECTION would make the answer depend on the user's own `diff.renames` — measured, a `git mv` of a project folder answers the NEW directory alone with detection on and BOTH with it off. Pinned off is raw adds and deletes, one answer whatever the clone is configured to do, AND IT COSTS THE SANCTIONED PATH NOTHING, verified end to end: a folder renamed in a FILE MANAGER makes no commit, and the act's next checkpoint is pathspec-scoped to the three NEW paths, so it adds them and deletes nothing — the old folder stays in the tree, which is exactly what keeps the pre-rename era's commits resolvable. That commit answers the new directory alone under the pin, so HELP's folder-rename promise never rode rename detection at all. A `git mv` done by hand in a terminal answers two directories and takes the ambiguity arm: unsanctioned, blunt, correct. THE ACCEPTED TRADE, architect-ruled: nothing refuses a checkpoint made from a COPY of a piece — a backup folder holding the same source name — and its commits land in that folder and interleave, by basename, into the one walk. That interleave is now GENUINELY VISIBLE, each member showing the folder it was actually written from rather than a phantom unchanged state; it is undoable and the user's own act, and guarding it would be defensive code against a practice the corpus does not have, which the sanctioned-use model rules out. THE RENAME CHAIN IS WALKABLE for the same reason: A -> B -> C leaves A's and B's files behind in every later commit, and the touched-directory rule still reads each era's own folder, so a piece keeps its whole past across any number of renames.

THE HEADER'S REFUSALS ARE THEREFORE FOUR, in the order it asks them: THE CLONE (the source in no git repository, or a derivation that could not answer — 2026-08-11, the paragraph above, replacing the old existence probe on the compiled-in path), the PROJECTS-HOME GUARD (unchanged, below), the empty base name, and A SOURCE NOT IN A FOLDER UNDER `projects/` — one plain stderr line naming the path, whose fix is A FILE MOVE rather than anything in a terminal. The clone comes first because every question under it is asked OF a repository and there is none until it answers. They are the HISTORY VIEW'S refusals alone: loading a source is untouched, and any file anywhere still opens, edits, renders and saves. The committed-tree refusals (an unreadable tip listing, an ambiguous match) are gone with the arms — so the header's ONLY GIT is the root derivation's one `rev-parse --show-toplevel` and the guard's two `remote get-url` reads, where the piece lives being answered from the source path and the filesystem alone.

ACCEPTED TRADES, recorded: basename matching cannot see history across a SOURCE RENAME, and every legacy-format checkpoint leaves the walk under the gate exactly as the `examples/`-era commits left it under the round-5 narrowing (the walk heads at the first load-clean commit until the first commit act). AND A PIECE WHOSE EVERY CHECKPOINT REFUSES THE GATE OPENS THE MODE ANYWAY, at `0/0` over a blank Remote lane (architect 2026-08-09; the entry-gate paragraph below owns the ruling) — the gate decides MEMBERSHIP and never ENTRY, so Save and Commit is reachable from an empty walk and writes the checkpoint that ends it.

THE WALK IS PREFETCHED AT STARTUP AND ARRIVES ONE COMMIT AT A TIME (architect 2026-08-07), which is the same ruling as the uncapping and its precondition. The load gate costs a `rev-parse` + a `show` for the touched directory + `ls-tree` + three `show`s for the blobs + three strict parses PER CANDIDATE (six children each since 2026-08-09, when the touched-directory evidence read joined; the evidence read moved AHEAD of the `ls-tree` when the containment fallback died, so a candidate the evidence refuses now costs TWO children instead of three, the tree listing being needed only once a directory has been named — its blob sizes are the truncation witness), over a `rev-list --count` and a `git log` for the run, and running that at every `h` is what made the entry stall — and what the depth of 20 was really buying. THE GIT ITSELF STAYED IN `history_diff.cpp` (`scan_history_walk`, `resolve_history_walk_header`, `read_history_branch_tip_sha`), so the read/write fence is still "which function a call site names" and the worker file owns only threading. A run does exactly what init() did, in order — the projects-home guard, the base-name derivation, the source's own folder, the uncapped `log`, then the strict load gate per candidate — publishing THREE message kinds: a HEADER (the guard/base/directory verdict, or the unavailable reason, plus the branch tip the run was built against), one MEMBER per ELIGIBLE commit in walk order, and a DONE carrying a `GuiHistoryScanResult` — whether the run's own reads ANSWERED, the refusal reason when they did not, and the hidden count (the candidate count went with the terminal-zero refusal messages on 2026-08-09, its only reader; the ok-plus-reason half arrived the same day, below). The counted stderr line prints at the DONE, once per run, in its old wording; an ineligible candidate produces no member message. IT PRINTS ON AN EMPTY WALK TOO since 2026-08-09 — the `!members_.empty()` term went with the entry refusal that had been naming the number instead, and a run that hid EVERY candidate is exactly when the count explains something, the view opening at `0/0` with no other account of why.

THE STORE IS MAIN-THREAD STATE, written only by the drain and the kick, so `GuiHistoryDiff` holds a pointer into it and reads it from paint and input with no lock. `init()` SPLIT accordingly: the git half is gone and what remains is the BINDING (the store plus the generation this visit entered against), the header — taken from the store, or COMPUTED SYNCHRONOUSLY right there by `resolve_history_walk_header` when a visit opens before the worker's own header has arrived, the guard's two git reads and no strict load, so every entry refusal keeps its exact shape and stderr line — and the LIVE half, unchanged: freeze the now side, and now grow the delta caches lazily rather than sizing them once. `commit_count`, `sha_at` and the member texts index the store's deque.

THE WALK GROWS DURING A VISIT, and that is the streaming working rather than a hazard: members arriving while the mode stands appear live, `n/N` grows, the `,` wall moves outward, the lane repaints. Four things make it sound. (1) The DELTA CACHES became `std::deque<std::optional<...>>` per reading — deque `push_back` never moves the elements already in it, which is `delta_at`'s pointer-stability contract restated for a growing list; every holder of a returned pointer is function-local and re-asks (re-derived by grep 2026-08-07). (2) The ITERATIVE PAIRING IS APPEND-STABLE BY CONSTRUCTION: index i pairs with i−1 or the live now side at 0, both NEWER than i, and every arrival is OLDER than everything already delivered, so no cached delta is ever invalidated by an append. (3) The FLAG-CACHE FINGERPRINT carries the member count as its twentieth field and the history block's seventh — the arrival that matters most (member 0 into an empty walk) moves no other field, so without it the lane would sit blank over a delta it now has. (4) The HEAD DELTA's rule changed from "measured once at entry" to "measured once": with no member 0 to measure it RESTS TRUE — the conservative face, Save-and-Commit greyed while the answer is unknown — and is measured at the first arrival that delivers it, static thereafter. THE WINDOW HAS A SECOND EXIT SINCE 2026-08-09: a run reporting DONE having delivered NOTHING answers COMMIT-WORTHY (`head_delta_empty` false), since with no eligible baseline there is by definition everything to checkpoint — and without that arm the act would stay greyed forever on exactly the empty walk that needs it. ENTRY IS GATED ON WHAT WENT UNANSWERED, AND ON NOTHING ELSE (architect 2026-08-09, SUPERSEDING "empty-walk entry is allowed, terminal zero is not"). The header's questions are which repository, which piece, which source — the clone the source is in, the projects-home guard, the base name, the source's own folder — and a refusal there is still one stderr line and a consumed `h`; the scan's own read joined them as the second such question later the same day (the paragraph below). MEMBERSHIP IS NEVER ONE OF THEM: a walk with no eligible member opens the view at `0/0` over a blank Remote lane whether its scan is still streaming or has FINISHED empty, populating live in the first case and RESTING in the second. THE OLD REFUSAL DEADLOCKED THE PRODUCT, which is why it went: SAVE AND COMMIT LIVES ONLY INSIDE THIS VIEW, so refusing entry on an empty walk made the one act that can CREATE an eligible member unreachable from exactly the state that has none — and retiring a settings key empties every piece's walk at a stroke, every committed sidecar then failing the strict load. The blank lane is the honest display of a piece with no eligible checkpoint behind it, and the first checkpoint after a schema change is an ordinary in-app act. AN UNREAD HISTORY IS NOT AN EMPTY ONE, and that distinction had to be BUILT when emptiness stopped refusing (2026-08-09, codex round 13's MEDIUM). While an empty walk refused entry the two were indistinguishable to the user, so a `git log` capture that could not run folded into "no candidates" and ended the run silently; now an empty walk OPENS and tells Save and Commit there is EVERYTHING to checkpoint, which is a confident answer about a history nothing ever read — the capture contract's own "an empty output is never a success witness" carried to the walk's end. So the DONE gained the header's ok-plus-reason shape (`GuiHistoryScanResult`, history_diff.h): a `log` that RAN and listed nothing is the ruled empty success, while a read this program could not get an answer out of ends the run NOT ok with one recorded reason (captures carry no deadline — that fence is the MUTATING entry point's). THE EMPTY VERDICT RESTS ON AN OUTPUT-SHAPED WITNESS, and that took two goes. Routing the `log` through `git_output` was the first mistake — its reading is "ran AND said something", and a successful `log` over a piece with no checkpoint exits 0 with ZERO BYTES, so every genuinely empty history became a FAILED scan and the empty-walk arm went unreachable, re-deadlocking the bootstrap the empty walk exists for. Reading the same `log` through `run_git_capture` fixed that and left the mirror defect: exit codes are unreadable here, so an executed-but-FAILED `log` is also silent, and believing THAT silence opens `0/0` and lights the act over a history nothing established was empty. So the gate is `git rev-list --count <branch> -- <the three pathspecs>`: it prints a number on success, "0" IS the ruled empty history, and an unparseable or absent count is the failure arm. Above zero the `log` enumerates and is back on `git_output`, where silence now contradicts the count and is a failure like any other. One extra child per RUN. AND THE ENUMERATION MUST MATCH THE WITNESS EXACTLY, which is the other half of the same lesson: a `log` that prints a PREFIX and then dies passes any non-empty test and silently truncates the walk — measured, with an older object damaged it printed the newest SHA and exited 128, and nothing here can see that status. So every line must be a full 40-hex object name AND the number of them must EQUAL the count that witnessed the read; either failing is a contradiction between two reads of one history, reported as such ("N counted, M listed"). The count parser refuses malformed bytes on its own terms too — a digit-length bound and `errno` around the conversion, so a token of a thousand nines cannot saturate into a plausible count. The store keeps `run_failed()` and `scan_failure_reason()` beside `run_done()` (both cleared at `kick`), and the two halves of the refusal read them: `GuiHistoryDiff::init` returns UNAVAILABLE with that reason on the header refusal's own one stderr line, and `walk_finished_empty()` answers false so the head delta keeps its conservative greyed face for a run that fails WHILE THE VIEW STANDS. THE STALENESS TEST IS DELIBERATELY UNTOUCHED: a failed run is not re-kicked by pressing `h` again, so the mode stays refused until an ordinary re-kick answers (the branch tip moving, a checkpoint completing, another source) or the program is relaunched — a capture that cannot exec is a broken environment, and the sanctioned-use ruling puts that fix in the terminal. The counted hidden line needs no term for any of it: EVERY arm that ends a run not ok returns before a single candidate has been gated, so the hidden count is structurally zero whichever one fired (`GuiHistoryScanResult`, history_diff.h, enumerates them and is the one site that does). AND A FAILURE ARRIVING AFTER THE VIEW OPENED ENDS THE VISIT (2026-08-09, codex round 14's MEDIUM): recording the failure silently left the reader in a permanent blank `0/0` with the act greyed and no account of why, and that `0/0` face is a LIE — it says "no checkpoints" where the truth is "unknown". So the arrival hook prints the recorded reason in init's own one-line shape and CLOSES the view through the one exit owner, band restore and lane republication included, and the next `h` meets init's stable refusal with the same line. It raises no modal, nothing asynchronous in this product does; it is a visit ending because its premise failed. ONE PRODUCER, narrow by construction: a view opened mid-scan whose run then fails, a run that had already failed refusing at init and never opening a view. It is also the ONE closer that is not a user act and the one that can fire with a POPUP up, which a standing Navigation menu is left to survive — row 1's own surface, its items live commands in the editor too (`close_history_mode`'s inventory owns both facts).

THREE KICKERS THROUGH ONE FUNNEL (`GuiInputHandler::kick_history_prefetch`): the startup load's tail (main.cpp, where the source path and `projects_repo` settle), the checkpoint completion for every outcome that MAY have committed — four of the six, everything but `WriteFailed` and `NothingToCommit`, which provably run no commit (`CommitFailed` can follow a landed commit under a hung hook, and `Unconfirmed`'s verify arm runs only past a moved tip), and the `h` entry when the store is STALE. STALENESS is three terms — the source path, the `projects_repo` and the branch tip the run was built against, the last compared against a live `rev-parse` — with a run STILL IN FLIGHT for the same subject counting as fresh, which is what covers the window before its header (and its tip) has arrived. A KICK WHILE THE VIEW STANDS IS DEFERRED to the exit owner, never dropped and never run: the visit is bound to a generation and a restart would clear the deque its indices name out from under it. A kick while a run is mid-flight SUPERSEDES: the generation bumps, the store clears, and the run abandons at its next CANDIDATE boundary (one atomic checked at the loop's top — the finest grain that costs nothing). Messages are TAGGED with their generation and the drain drops any that do not carry the current one, so a superseded run's late members and its DONE change nothing; the kick also empties the queue, so the tag catches only what the worker pushed between that clear and its next abandon check.

ACCEPTED, RECORDED: the prefetch's git READS may overlap the checkpoint act's MUTATIONS, since both run on their own workers. A read that races sees the repository partway through, and the answer is the re-warm rather than a lock — the act's completion kicks a fresh run, rebuilding whatever raced. No VIEW can be reading a half-mutated walk either, `h` being refused outright while a checkpoint publishes. One collateral fix the two threads forced: `load_commit_sidecars_strict`'s scratch directory was named pid + short SHA, which two threads asking about ONE commit (the worker gating it while the `'` act loads it) would collide on, the loser's RAII guard removing the winner's staged files mid-load; the leaf carries a process-wide atomic serial now, so it is per-CALL rather than per-commit.

## The diff model

WHICH TWO SIDES A DELTA COMPARES IS THE COMPARE MODE'S ANSWER (the section below; the cumulative reading is described here, and the iterative one substitutes the NEXT-NEWER ITEM for the now side — a commit, or this same frozen now side at the newest index — through the same mechanism). The CUMULATIVE NOW side is the live in-memory state serialized through the save writers' own string halves (`format_warpmarkers_text` / `format_phaseresetmarkers_text` / `format_settings_text` — the round-1 split; byte-identical to a Ctrl+S, no disk touched) and is FROZEN AT init(); the mode's mutation gate is what keeps the frozen snapshot honest (authoring is blocked while the mode stands, so it cannot go stale by construction). Then-vs-now is an in-tree line LCS (DP with prefix/suffix peeling and a cell cap) typed into per-commit deltas: warp added/removed/changed carrying each line's VERBATIM tempo token (the flag shows the sidecar's own spelling, never a re-derivation), phase resets added/removed/changed (their line is frame plus disable prefix, so a `#` toggle pairs as a genuine change, symmetric with warp), and the `scale=` tokens from both sides (THE ONLY SETTINGS KEY THE MODE DISPLAYS — a recorded asymmetry: every other settings delta is deliberately invisible). A same-frame remove+add pair IS the changed entry — it feeds the double flag. WALK MEMBERSHIP IS LOAD-GATED (2026-08-04, superseding the old two-tier "diff is parse-free / load-in-place is parse-gated" answer): everything visible is loadable, so both sides of every diff are loader-clean text with all three files present, and the diff mechanism stays line-based with NO leniency arm left — the drop-unparseable-lines arm with its counters (`GuiHistoryLineCounts`), the missing-file-reads-as-empty-side arm, and the per-commit `Ambiguous` state are all DELETED as dead code (the architect's no-legacy rule: the program never imports leniently; an old-format checkpoint is hand-edited, never tolerated). The extraction's boolean is the parse's own optional shape, not a tolerance. The one degraded arm kept is an ALLOCATION guard, not a format leniency: a loader-clean sidecar past the DP cell caps diffs coarsely as replaced whole. Deltas compute lazily against the snapshots the gate kept and cache per (commit, compare reading); stepping revisits and reading switches alike are free, and no delta runs git at all.

## The two compare modes (2026-08-05)

A CHECKPOINT HAS TWO INTERESTING OTHER SIDES, and the architect ruled that the view offer both rather than choose. The reading the mode shipped with is named CUMULATIVE — the viewed checkpoint against the FROZEN LIVE NOW SIDE, which answers "how does what I have now differ from that checkpoint" and is the reading a restore or a load-in-place is about. The new one is ITERATIVE, and it COMPARES FORWARD, TOWARD NOW (architect 2026-08-05, superseding his walk-parent pairing of earlier that day): the viewed checkpoint is the OLD side and THE NEXT-NEWER ITEM the new one — the next-newer ELIGIBLE WALK MEMBER at every index but the newest, and THE FROZEN LIVE NOW SIDE at the newest, which has no committed successor. It answers "what happened AFTER this checkpoint", one step at a time, which is what a walk backwards through the history is asking at each stop. ITERATIVE IS THE PROGRAM-START STATE, NOT A PER-VISIT DEFAULT (architect 2026-08-08, superseding the 2026-08-05 per-entry ratification): the reading is `AppState::history_cumulative`, a SESSION PREFERENCE living outside the HistoryMode struct precisely so the whole-struct reset at the mode edges cannot touch it — off (= Iterative) when the program opens, flipped by bare `u` or the row-4 Cumulative toggle, kept across visits for the life of the run, forgotten at close, never serialized. A visit INHERITS the running bit; the session-preference model's full record is below at the toggle's own paragraph.

THE COLOR GRAMMAR IS ONE RULE ACROSS BOTH, which is the pair's whole reason for fitting: the NEWER side is always the diff's now side, so green `[+]` is what the newer side has and red `[-]` what the older side had and the newer dropped. In cumulative the newer side is the session; in iterative it is the next step forward — the newer checkpoint, or the session itself at the newest index. Nothing in the lane, the flag texts, the double-flag pairing or the colors knows which reading it is drawing — `rebuild_history_diff_flags` reads whatever delta it is handed.

THE MECHANISM IS THE SAME TYPED LINE DIFF, taken off the walk position: `compute_commit_delta` (history_diff.cpp) runs the identical LCS + extraction + same-frame pairing over whichever pair of texts the reading names, and `delta_at` picks the pair — cumulative = the member's kept snapshots against `now_`, iterative = the member's kept snapshots against the NEXT-NEWER member's (or against `now_` at index 0). Both sides are LOADER-CLEAN in both readings, since walk membership is the strict whole-set load and the gate kept every member's three sidecar texts; so a delta still runs NO GIT AT ALL, in either reading. THE `scale` PAIR RIDES THE SAME SUBSTITUTION (then = the older side's token, now = the newer's), so the corner line says the same kind of thing in both. CACHED PER (INDEX, COMPARE) — one DEQUE of optionals per reading, grown to membership as the prefetch delivers (2026-08-07, replacing the vector sized once at init: a deque's `push_back` moves no element already in it, which is what keeps `delta_at`'s returned pointer good under a growing walk) — so a switch back is as free as a step back and no delta is ever recomputed.

THE TWO READINGS COINCIDE AT THE NEWEST INDEX, deliberately and by construction: both are the newest checkpoint against the live now side there, so A SESSION FRESHLY LOADED RIGHT AFTER A COMMIT SHOWS A BLANK LANE IN BOTH READINGS — the architect's stated purpose for turning the direction forward. Nothing has to know: the two are simply the same delta, computed and cached twice in their own slots rather than aliased, since the coincidence is a property of the pairing and not a rule any reader should carry. The visible cost is that a reading switch at `1/N` redraws the same lane and moves only the row-4 Cumulative lamp (the lit tab, while the tabs were the reading's selector); accepted, and it is the honest face of the pairing.

EVERY INDEX HAS A FORWARD PARTNER, so THE EMPTY-DELTA SPECIAL CASE IS DELETED — the walk-parent pairing's oldest-member arm, its structural no-diff-run and the reasoning that justified it are gone from the model, the header and the docs alike. The walk's OLDEST end is now an ordinary index whose partner is the member one newer, and its NEWEST end is where the live state is. AND THE NEXT-NEWER MEMBER MAY SPAN COMMITS THE LOAD GATE HID: that is the walk's own honesty rather than a defect of the pair, since an ineligible commit is not steppable, not loadable and not shown, and the nearest checkpoint the mode CAN show is the only one whose delta has two reachable sides. ## The local walk — the undo/redo timeline as a second walk (2026-08-07; the STATES model 2026-08-08)

THE VIEW READS TWO WALKS NOW. The architect's motivation is one sentence: "the local history feature will be helpful for understanding undo/redo history." So beside the COMMIT walk — the piece's committed sidecar checkpoints — the mode grew a LOCAL one over THE SESSION'S OWN UNDO/REDO TIMELINE, read through the identical delta machinery, and row 3's two tabs became the WALK SELECTOR, **Remote** and **Local** (the row carried the two axes' product as four tabs, then as two labelled groups, for one day of 2026-08-07..08 before the architect split them apart — the reading is row 4's Cumulative toggle now; the compare-modes section above owns that succession). The axis is `GuiHistoryWalkSource` (Commit | Local, history_diff.h), COMMIT is the default at every entry (a plain member initializer, applied by the whole-struct machinery — where the READING deliberately is not, living on AppState and surviving the visit since 2026-08-08), and the two walks keep SEPARATE POSITIONS — `index` is the commit walk's, `local_index` the local one's — so each is a place a visit can come back to rather than one place with a changing subject.

A MEMBER IS ONE STATE OF THE TIMELINE, NOT ONE UNDO ENTRY (architect 2026-08-08, superseding the undo-stack-only walk). With U = the undo stack's size and R = the redo stack's, BOTH CAPTURED AT `init`, the walk carries **N = U + R + 1** members, newest first — every state Ctrl+Z and Ctrl+Shift+Z can reach, plus the one the session is standing in:

| index k | member |
|---|---|
| `k < R` | A FUTURE state, `redo_stack[k]`. Counter-entries are pushed as the user undoes, so `redo_stack[0]` is the FURTHEST future and `redo_stack.back()` the nearest — the vector already runs newest-first. |
| `k == R` | THE LIVE MEMBER, the state the session is standing in. The walk already holds it as the frozen now side, so nothing is captured or serialized for it; its three texts are that side's own. |
| `k > R` | A PAST state, `undo_stack[U + R - k]`, whose snapshots are the state BEFORE the event that entry records (`k = R+1` is the stack's top, one Ctrl+Z away; `k = N-1` is `undo_stack[0]`, the state at file open). |

Both stacks carry all three snapshot pieces (the carry-everywhere shape at `UndoEntry`, which `restore_history_entry` reproduces field for field on the counter-entry it pushes), so one body reads either: the three texts are `format_warpmarkers_text(entry.snapshot)`, `format_phaseresetmarkers_text(entry.phase_reset_snapshot)` and the settings file formatted from that entry's ENGINE settings plus ONE CAPTURED GUI HALF.

THE ENTRY LANDS ON THE LIVE MEMBER, which is the one place the two walks' entry positions differ: the commit walk opens at 0 because its newest member is where the session is, while the local walk's 0 is the furthest FUTURE state, so the one entry owner writes `local_index = local.live_index()` (the captured redo count) after binding the walk — an assignment the entry makes rather than a default the initializer could carry, only a bound walk knowing where its live member is. With no redo entries the two coincide. So `.` walks INTO FUTURE STATES whenever redo entries exist, and the architect's own example — set a marker, move it, Ctrl+Z, open the view — reads `2/3` on the state on screen instead of the `1/1` the undo-stack-only walk answered about a session holding three states. That capture is the piece that had to be added: `NonEngineSettingsSnapshot` is a call-shaped borrowing type, so `GuiHistoryGuiSide` (opaque in the header, ViewState living in app_state.h) holds it by value, `capture_history_gui_side` takes it at the mode's entry with the save path's own active-tab overlay, and `format_history_settings_text` is the one formatter BOTH the frozen now side and every local member go through. Which is why a local delta can only differ in the ENGINE block: GUI-kind keys are history-less, so using the same half on both sides means the view's own navigation cannot show up as a settings difference — and `scale=`, the one settings key the mode displays, is an engine key anyway.

THE ITERATIVE READING IS EXACTLY ONE EVENT, and that is the pairing's derivation rather than a coincidence — THE COMMIT WALK'S FORWARD PAIRING VERBATIM: member k against member k−1, the next-newer member, so the two bracket exactly one event; at the LIVE member the delta is the change the next REDO would apply, at the first past member what Ctrl+Z would revert. AT k = 0 THERE IS NOTHING NEWER, so the member PAIRS WITH ITSELF and `compute_commit_delta` answers empty — the same blank the commit walk shows at its newest index right after a commit, computed rather than short-circuited so there is one pairing expression and no second route to an empty delta. CUMULATIVE MEASURES AGAINST THE LIVE MEMBER whatever the position ("how does my session differ") — then = this member, now = live for a past member and for the live member itself, and FOR A FUTURE MEMBER (k < R) THE SIDES SWAP: then = live, now = this member, the future state being the NEWER of the two. That swap is what keeps THE NEWER SIDE IS GREEN one exceptionless colour rule across the whole timeline instead of a rule with a redo exception, and at the live member itself both sides are the same state, so the lane is blank there in BOTH readings. Both feed `compute_commit_delta` — which stopped being file-local for exactly this, a copy of it being the second grammar this module refuses everywhere else — with an EMPTY sha, and both are cached per (index, reading).

THE NOW SIDE IS SHARED, ONE CAPTURE PER VISIT: `GuiHistoryDiff::init` freezes it and `GuiHistoryLocalWalk::init` takes it through `now_side()`, so the two walks structurally cannot disagree about what "now" is.

THE TIMELINE IS FROZEN WHILE THE VIEW STANDS — BOTH STACKS since 2026-08-08, when the walk grew to the whole timeline — which is the frozen-now-side derivation run again: every route that could push, pop or evict an entry on EITHER stack is an authoring route, so the two allowlists consume it or one of the mode's three mutator chords closes the view as part of itself (the redo stack rides the same argument, its only writers being a push, which clears it, and the two restores). IT IS EXCEPTIONLESS BY CONSTRUCTION SINCE LATER THE SAME DAY: the premise shipped with ONE ADMITTED PRODUCER, the S→T view switch's iteration-bracket push (admitted on the read-only gate's own argument, brackets being session-only), and that push is DELETED with the architect's ruling that ITERATION MODE IS TARGET-LEGAL — entering target view no longer exits the mode or wipes anything, so the admitted view switches write no store at all. Nor can the bit move in here: `i` is not on the keyboard allowlist and the icon row's iteration button greys with it. BOTH sizes are therefore captured at init and the caches are plain vectors sized once (where the commit walk needs deques for its streaming growth), and THE PAST MEMBERS INDEX FROM THE BOTTOM of the undo stack — the shape that made that push harmless and that would make any future append harmless: an append leaves every captured position naming the entry it named and the new entry is simply not in the walk.

THE PREMISE STANDS ON THAT DERIVATION ALONE — no runtime check backs it. `member_readable` re-reads BOTH stacks' SIZES on every ask (the shared bounds precondition of the two member readers, `member_at` and `member_state`), and those terms are a BOUNDS PRECONDITION on the subscript about to be performed rather than a check of the premise: a stack shorter than its captured size answers NOTHING (a blank lane) instead of being read at indices that now mean other events. Both are tested whichever arm the index takes, the count that bounds it being built from both. A PER-ENTRY PUSH SERIAL — a monotonic stamp on `UndoEntry`, captured per walked position at init and compared on every read, written for the EVICTING-push shape the admitted producer could reach (a stack at `UndoHistory::kCap` when that view switch fired: the bottom entry goes and every position slides down one WHILE THE SIZE HOLDS, so no count can see it and an identity can) — LIVED FOR ONE DAY of 2026-08-07 and was DELETED by the architect once that producer died at the root: "nanosec was a granularity change for an external cause; push-serial is a new mechanism altogether, targeting possible future features in a nearly feature-complete project." A producer-less mechanism, not a granularity change. Do not re-propose it. Member texts are serialized LAZILY on first ask, so `h` pays nothing for a five-hundred-entry stack.

TWO RECORDED CONSEQUENCES. (1) A MEMBER PAIR THAT SERIALIZES IDENTICALLY SHOWS A BLANK LANE — an `affects_persistence == false` event (the iteration bracket's session-only snapshot) changes nothing any sidecar would carry, so there is nothing for a delta to say about the pair that brackets it. Honest rather than a gap: the walk shows what the commit history would. (2) THE REDO STACK WAS DELIBERATELY EXCLUDED UNTIL 2026-08-08 — the reasoning being that a walk is what is BEHIND you, the commit walk's own shape, and that including redo would need a second index origin and a signed position. THE ARCHITECT SUPERSEDED IT with the complaint the states model answers (set a marker, move it, Ctrl+Z, open the view and it read `1/1` about a session holding three states), and the objection went with it: there is ONE index origin here, the newest state, and the live state is a member like any other.

## The multi-selection and the revert act (2026-08-05)

THE VIEW GAINED A WAY TO PUT DIFFERENCES BACK (architect, the arc's last feature): a MODE-LOCAL MULTI-SELECTION over the diff flags, and CTRL+H, which applies each selected flag's INVERSE to the live store and closes the view. RECORDED CONSEQUENCE: a ctrl press removing the last member rests on the focus alone, that flag still lit and still the subject — the same state a plain click leaves, the live column's focus repair having no analog here. THE ACT (`GuiInputHandler::run_history_revert`). THE SUBJECT is the selected ordinals, else the focused one alone; with neither there is no subject and the chord is not admitted at all. The COLUMN is the active one by construction (the lane paints only that half of a delta), so the store is chosen once. THE PER-CLASS INVERSE: an ADDED flag DELETES the live marker at its exact frame (none there = nothing happens for that flag, never a refusal); a REMOVED flag PUTS THE THEN SIDE BACK, replacing a live occupant at its frame or inserting fresh; a CHANGED double flag SETS the live marker at that frame to the THEN side — the same insert-or-replace primitive as the removed arm, so the two share one body. Blind in BOTH compare readings: the then side is whatever the displayed delta's then side is. COINCIDENCE IS WALKED BY BOTH ARMS (one flag is one LINE and coincident lines are legal): every arm consumes the NEXT PRE-ACT OCCUPANT at its frame and a marker this act inserted is never a later arm's target — one per-frame skip counter, so two `[-]` flags at one frame restore TWO markers and a `[+]` flag never eats one a `[-]` flag in the same subject just put back. A WRITE THAT CHANGES NOTHING IS NOT A CHANGE: a replace whose occupant's canonical LINE already equals the then side's writes nothing and counts nothing — reachable in the iterative reading, whose delta is between two commits and blind to the live store. THE THEN VALUE TRAVELS AS TEXT AND THE FROZEN PARSER JUDGES IT — the flag carries the removed line's payload token verbatim (`HistoryDiffFlag::then_token` / `then_disabled`, filled from the same delta entry the label is built from), the act reconstitutes the sidecar LINE and hands it to `parse_single_canonical_line`, so pass markers, label definitions, references and typed scales all restore with no vocabulary of their own here and there is no second grammar to drift. The phase reset column needs no trip: frame plus the disable bit IS its line. A restored warp marker arrives as a FRESH `GuiWarpMarker`, session-only iter/bpm scratch at its defaults, exactly as a load delivers it. It CLEARS THE LIVE SELECTION (store indices, which it inserts and removes under), pushes ONE undo entry over the one store it touched and marks dirty — all three only when the state actually DIFFERED, so a subject that found nothing to do, and one whose every member found the live state already carrying its then side, both leave no entry behind. It STOPS A LIVE AUDITION UNCONDITIONALLY and up front, outside that three — the mode's own regime (its Tab cycle, its Home/End and its `c` stop the same way) and a formality in here besides, the entry owner having stopped any session running before `h` under a view that offers no transport to start another.
