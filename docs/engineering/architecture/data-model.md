# Authored Data Model (frames, tempo cents, value vocabularies)

Moved verbatim from CLAUDE.md in the 2026-07-25 slim-down (project feature-complete). This file is now the authoritative home for this detail; CLAUDE.md carries only a digest and a pointer here. Keep it current with landed rulings.

### Authored Domain is Whole Source Frames (int64_t)
Authored positions — marker times on both columns and both trim bounds — are whole source frames held in `int64_t` everywhere at rest: in-memory stores, sidecar files, walls, validators. A fractional authored position is unrepresentable by type; mid-gesture positions are free doubles, and `snap_authored_frame` (`app_state.h`: banker's `std::nearbyint`, then exact cast) is the ONLY double-to-authored conversion route in the product tree — every gesture commit funnels through it (the standalone migration tool carries its own equivalent `nearbyint`). Ties are real at 44.1 kHz (the 5 ms zoom level is 220.5 frames/px, a half-frame tie on every odd pixel), so banker's is load-bearing. There is no seconds or millisecond-grid representation anywhere in the data path; MM:SS.mmm timestamps are display-only renderings (`format_timestamp(frame / sr)`) on GUI text surfaces. ONE serialization domain in `src/parser/frame_format.h`: the AUTHORED pair (`format_authored_frame` = plain integer text, `parse_authored_frame` = the CANONICAL spelling only: digits, no sign/point/exponent/leading zeros, int64 overflow refused — the spelling IS the grammar; the migration tool guarantees corpus canonicality) is the single on-disk position form, and any other position text — fractional, negative, non-finite, or a non-canonical integer spelling like `44100.0`/`6e+05` — is adversarial load-fatal. (The old RENDER-DISPLAY pair and the `.renderwarpmarkers`/`.renderphaseresetmarkers` sidecars are retired: positions on a render's target axis are computed live by the GUI through the snapshot map and never serialized.) Walls are exact integer comparisons — every authored position, both marker columns and both trim bounds, shares the one inclusive `[0, total-1]` domain (the trim end's former exclusive `total` wall was unified 2026-07-18; an end bound stored at `total` is adversarial load-fatal, no migration) — literally the same compare at gesture time and at the adversarial load guard. THE INCLUSIVE END IS THE AUTHORED DOMAIN'S, AND THE RENDERED CROP IS END-EXCLUSIVE ON ITS TARGET IMAGE (recorded 2026-09-02, the truthfulness deep dive's item K, accepted): the trim's end frame `e` is the last frame INSIDE the authored window — the frame `End` lands on, the frame the endcap sits on, the frame the overlay's right edge derives from — while the kept output is `[llrint(tgt(b)), llrint(tgt(e)))`, so `e`'s own target span — `1 / (tempo · marker_scale · settings_scale)` output samples, the LOCAL SEGMENT SLOPE at `e` rather than `1/tempo`, of which the 23 µs at 44.1 kHz is the unity case — is the first thing NOT rendered. The two are not in conflict, they are two domains: the trim is already a rounded quantity on the target axis — the crop's begin and end are both `llrint` of mapped positions and the pre-roll anchors on hop multiples to keep the phase null past the first reset — so the exclusive end is one more sample of that same rounding class. Its one visible edge is in target view under a sub-window, where `End` parks the playhead one sample past the preview buffer's last frame and `Space` then plays nothing. The crop is `trimmer.cpp`'s (`plan.post.samples`), and it is why the full-window translation is load-bearing (render-pipeline.md). Field naming is `*_frame`.

Authored TEMPO is 100-based INTEGER CENTS held in `int64_t` everywhere at rest — the value-domain sibling of the frames ruling above; an off-grid or fractional tempo is unrepresentable by type. Its bracket is `[kTempoMinCents, kTempoMaxCents]` = [25, 400] (i.e. [0.25, 4.00]), exact integer compares at every bracket surface. The `N.NN` spelling (one-plus digits, one dot, exactly two decimals, no leading zeros) is the TEXT INTERFACE only: `format_tempo_cents` / `parse_tempo_cents` (`value_format.h`) are the single serialization pair (direct digit-to-cents, no strtod, byte-identical to the historical min-2-padded form), and `tempo_from_cents(int64_t)` — double overload deleted — is the ONE cents-to-double boundary, and it is crossed in exactly TWO PLACES (re-grepped 2026-08-29): the PARSER'S FRAME-MAP BUILDER — the DSP slope product in `build_warp_frame_map` and the implied-tempo bracket references and default bases derived beside it, all `warp_frame_map_build.cpp` — and the GUI'S BPM DERIVATION, one scale divisor (`input_handler.h`). TWO SITES THAT LOOK LIKE CROSSINGS AND ARE NOT: the RENDER FINGERPRINT serializes `tempo_cents` as the `int64_t` it is (`put_i64`, render_cache.cpp), so no double enters the key at all; and the BPM CELL'S RESCALE works in the CENTS DOMAIN rather than through two conversions, the /100s cancelling and a conversion pair only adding rounding (recorded at the site). Every OTHER value is a double via `src/parser/value_format.h` under BRACKETED vocabularies (the constants there are the SoT): both scales `[kScaleMin, kScaleMax]` = [0.5, 2] (multiplicatively symmetric; the floors bound the resolved product to >= 1/16, which the pixel-nudge guarantee is computed from; scale staying full-double is the recorded tempo/scale asymmetry at the WarpMarker struct), bpm `[10, 400]`, `bpm_beats` int in [1, 9999] and — since 2026-09-06 — spelled ONE WAY PER VALUE like every other field of that grammar (no leading zeros; `parse_bpm_bracket`, warpmarkers.h, refuses `0210` exactly as it refuses a bound that is not the writer's own spelling, which is what makes the popup's byte cap a derived bound rather than a chosen one), iteration deltas in [-400, +400] integer cents (session-only, never serialized; a bound typed into its cell's editor red-flashes when the base tempo plus the bound leaves the tempo bracket or crosses its partner — the endpoints bound every cell — while the arrows' step clamps at the same walls). Iter state has a hard lifecycle: exiting iteration mode wipes every bracket, and the exit routes are TWO, re-derived by grep on `wipe_iter_state` 2026-09-10 — the `i` toggle's OFF branch and the iteration sweep's success tail — all through the one chokepoint `GuiFlagEditor::wipe_iter_state` (`enter_bpm_mode`'s FORCED ITER-OFF was the third until that evening, when the architect ruled the swap out — *"we should card the exit, because it is still one button automatically affecting the other"*: the BPM opener (bare `m` then, `Ctrl+B` since 2026-09-15) is REFUSED under a lit lamp now, at the keyboard gate with the lock's own card and on the BPM Iterations button's greyed face, and bare `i` is the mode's one exit; marker-ui.md's Iteration Mode section carries the pair) (Shift+I is retired; the S→T audio-view toggle LEFT this list on 2026-08-07 when iteration mode became target-legal, and the mode and its brackets survived the view switch in both directions until 2026-09-13, when the mode became target-only and the switch back to source became one of the lock's refusals — tempo-and-home-view.md carries the ruling and the granted target-view exception the first and third routes take; exiting the mode IS the clear; THE WIPE PUSHES NOTHING since 2026-09-10, brackets having left the undo domain whole with the iteration lock — it pushed one undo entry until then, so plain undo could deliberately restore a bracket set, and no undo can now). THE LOAD IN PLACE IS NOT A ROUTE (architect 2026-09-02, the four-tier review's R-13 — "iteration mode is where you stand"): `apply_recipe_in_place` leaves BOTH sweep-mode bits alone (they are view state, like the S/T and W/P bits it already leaves alone) and resets no bracket — the two sidecar roads' markers carry none by construction (the grammar has no bracket field; `GuiWarpMarkers::load` upcasts a parsed `WarpMarker` into a `GuiWarpMarker` whose session-only fields keep their defaults) and no snapshot carries one either (every push strips the session-only iter fields — `strip_iter_fields`) — and until 2026-09-10 that was also what let Ctrl+Z put the outgoing markers back WITH their brackets under a mode that never changed (before 2026-09-02 the body reset every bracket and turned both bits off inline, a fourth exit route beside the chokepoint that undo then contradicted: the brackets came back under a mode the load had switched off). THE RULING IS VACUOUS UNDER THE ITERATION LOCK and is kept as the record of why the body carries no bracket reset: a load in place is REFUSED while grid iterations stands, by key and by button on both of its roads (the render player's own, and the `h` view's — the view cannot even open under a lit lamp), so no load can arrive under a lit mode for the ruling to govern. A lit mode over a bracketless store shows the blank form on every eligible flag and greys Render on `NoBracketAuthored`. The bpm scratch wipe the body still runs is a statement over a set already at its defaults (bpm mode is exactly its editor session, and no load road runs beside an editor), never a mode exit. THAT SAME PROPERTY — the mode never resting without its modal editor — is what makes the BPM opener/`i` exclusion's second direction need no arm: while BPM mode stands the editor owns the keyboard and no key, `i` included, reaches a dispatch. THE BASE CANNOT MOVE UNDER A BRACKET AT ALL SINCE 2026-09-10 (architect, the iteration lock): a bracket exists only while grid iterations is lit, and while it is lit THE PIECE IS LOCKED — the tempo step and the flag editor's payload commit are both refused (`authoring_locked`, app_state.h; marker-ui.md's Iteration Mode section owns the lock) — so the window a bound was authored inside is the window it still sits in. THE RETROACTIVE CLAMP IS RETIRED WITH ITS THREE CALLERS. It stood from 2026-08-02 as the ONE owner `clamp_iter_bracket_to_tempo_bracket`, called by the two base-tempo authoring surfaces right after they wrote a new base, folding the surviving bounds into `[kTempoMinCents - base, kTempoMaxCents - base]` so that no cell a sweep can enumerate could leave the tempo bracket and land in a sidecar the strict tempo parse hard-rejects; its silent/loud labour division and its one accepted residue — a degenerate `[0, 0]` bracket where the base rested exactly on a tempo wall, the one road to a resting two-zero pair that did not mean blank — went with it. THE WALLS ARE NOW HELD BY THE TWO BOUND ROADS ALONE, which is what they always did for themselves: the arrows' step lands through `iter_bound_step_landing` inside that window as it steps, and the bound editor's commit REFUSES outside it, LOUD (red flash, a card naming the wall) because a typed bound is authored input arriving at its own surface. (Tempo changes never cleared a bracket either — architect 2026-07-19, reversing an earlier tempo-step clear — and there is no tempo change under a bracket left to state it of.) Eligibility LOSS clears at both authoring surfaces: Ctrl+N's owner→pass and ref→pass branches reset the marker's bracket in the same undo entry, and the flag editor's commit — which types no bound, the cells being the bracket's only authoring surface — unconditionally resets the bracket whenever the committed marker is iter-ineligible. BOTH ARE BELTS WITH NO PRODUCER SINCE 2026-09-10 and are kept as belts: neither surface can be reached while a bracket stands (the lock refuses Ctrl+N and the payload editor alike), so the optionals they reset are already empty, and the store's rule is stated where a surface could otherwise break it. THE HIDDEN-BRACKET CLASS THEY GUARDED IS CLOSED AT THE SOURCE INSTEAD: no undo entry can carry a bracket — every push strips the session-only iter fields from the snapshot it takes (`strip_iter_fields`) and nothing pushes while the lamp is lit — so there is no restore that could resurrect one against a different frozen base, and *"a bracket exists only on a marker that is on screen or it is gone for good"* is a property of the code (marker-ui.md's Iteration Mode section). BPM state (owner, beats, bounds, endpoint — likewise session-only, never serialized) has the same hard lifecycle: it wipes history-less on every bpm-mode exit (the exit_bpm_mode chokepoint, all off-routes funnel there) and on sweep dispatch (render_bpm_sweep's success tail wipes and closes the mode; a guard-bailed sweep deliberately keeps values and mode for correction), so re-entering either mode always seeds blank — and since 2026-08-24 the BPM editor's blank is the EMPTY STRING rather than `[]` (`format_bpm_bracket_text`, warpmarkers.h): there is no bracket to fill, the whole `<beats>@[<lo>,<hi>]` being typed from nothing, so the two modes' blank forms deliberately no longer match (iter's `[]` is a real token of its own grammar). THE SECTION RULE (arc step 5, architect-designed 2026-07-23) governs the `m` sweep and both propagate spans: a marker OWNS the section from itself to the next marker that PARTICIPATES IN THE RENDER, a marker trailed only by disabled ones running to the SONG END. The EFFECTIVE-PARTICIPATION form reached the two propagate spans on 2026-08-01 and THE `m` SWEEP ON 2026-08-24, so the rule now has ONE form and ONE OWNER: `section_end_index` (warpmarkers.h, beside `effective_disabled`), with `section_end_frame` the frame-returning wrapper the propagates read and the index itself what the sweep records. A disabled marker is dropped before the warp map is built and is therefore not a render boundary at all; its span belongs to the preceding enabled marker. For the propagates that is what lets the resets under it copy, clear, and paste with the section they musically belong to (the old next-in-STORE extent left that span owned by nobody — the architect's reported drop — and silently mis-scaled captured resets against truncated durations); for the sweep it is what keeps the span DURATION honest, a raw next-in-store boundary having measured the last section short whenever a disabled marker sat at its edge and so mistuned every derived cell tempo. The `m` sweep keeps its span-based bookkeeping (`bpm_endpoint`; a DISABLED MARKER IS INVISIBLE TO THE CELL and is left exactly as it rests — `bpm_cell_warp_markers`, the cell's one owner, skips `effective_disabled` in BOTH of its loops, so the sweep neither converts one inside the span to a pass nor rescales one outside it, render-pipeline.md owning that ruling) — the `m` gate takes a non-empty CONTIGUOUS run of selected markers (first = owner; `bpm_endpoint = section_end_index(last)`, == store size being the song-end sentinel through the commit gate, the sweep, and the descriptor; every selected section included, the old excluded-endpoint-section model retired; the span may end PAST disabled markers, which the cell rewrite then leaves untouched, and the gate's `label_ref` refusal is scoped to EFFECTIVELY-ENABLED refs for the same reason), the Ctrl+P copy takes the SAME non-empty CONTIGUOUS run (codex round 4: the paste's lockstep label matching assumes one contiguous label sequence, and unlabeled gaps align on both sides; effective-disabled selected markers contribute no block), the paste destination walk gives the store-final ENABLED labeled marker the same song-end extent (its EOF clamp load-bearing; since 2026-08-01 a labeled marker trailed only by disabled ones owns to the song end too — the newly reachable branch of the same guard), and disabled markers are excluded from bpm eligibility (`bpm_popup_eligible_marker` gains !disabled — for an owning marker raw equals effective, the cascade only reaching refs). Out-of-bracket on disk is adversarial load-fatal (the GUI can never author it); typed values red-flash at editor commit; the bpm derivation refuses (never clamps) an out-of-bracket derived tempo or scale; and BOTH SWEEPS' per-cell computed mutations are BRACKETED, by two different means. THE BPM CELL REFUSES, NEVER CLAMPS: `bpm_cell_warp_markers` (`input_handler.h`) rescales every effectively-enabled owning marker outside the span by the owner's own change and returns `nullopt` the moment a rescaled value leaves `[kTempoMinCents, kTempoMaxCents]`, because a clamped section would deform the very shape the rescale exists to preserve — one stderr `Rejected cell` line, the sweep running short and saying so on its `Rendered N of M` card. THE GRID ITERATION CELL CANNOT LEAVE THE BRACKET AT ALL: its value is the integer sum `base + delta`, both bracket endpoints rest inside `[kTempoMinCents - base, kTempoMaxCents - base]` because the two bound roads put them there (the step's landing clamps, the editor's commit refuses), and THE BASE CANNOT MOVE UNDER THEM while the lamp stands, so every cell between them lands in the tempo bracket by construction and no downstream backstop is load-bearing for that sum (recorded at the cell loop, `input_key_dispatch.cpp`) — which is also what keeps a cell sidecar's `N.NN` spelling inside the vocabulary the strict promote parse at the `'` load-in-place accepts. `playback_speed` IS RETIRED WHOLE (architect 2026-08-27): the key, its ten-preset on-disk vocabulary (`playback_speed_presets.h`, deleted), the `playback_speed=` editor arm and the GUI's variable-speed playback machinery all went together, the architect running 1.0 everywhere in his one live project. What was there: a preset-only spelling matched by exact TEXT, authored solely through the settings editor, storing-only in target view. What STAYS is the playback engine's source-to-output RATE ratio, which is a different thing — AAudio may grant a rate the source is not recorded at, and the render body's one increment rescales for that whatever the speed was (`playback_common.h`). A `.settings` still carrying the key is load-fatal in both products by the ordinary unknown-key refusal. Writing: tempo through `format_tempo_cents`; scale and bpm shortest padded to minimum decimals — scale 4, bpm 0 — so historical fixed-decimal forms re-serialize byte-identically. The old producer discipline (compute in integer cents, convert once) is now STRUCTURAL: tempo producers (the bare Up/Down step, the bpm derivation's rounded-cents entry, the sweep's per-cell base + delta) do plain integer arithmetic on cents, and the type forbids leaving the grid. The bare Up/Down tempo authoring steps one cent per press and clamps constructively at the cents bracket edges (there is no tempo wheel). The bpm-derived scale is full double precision (no decimal quantization — the shortest round-trip writer makes in-memory and on-disk agree bit-exactly); Sources below 44100 Hz refuse to load, and sources are STEREO-ONLY — `channels != 2` refuses beside the floor in both product loaders (mono-for-sale is locked stereo; convert once outside, e.g. ffmpeg; the probe/parser layer stays capability-complete, and the stereo invariant makes every product-written wav payload even, so the RIFF odd-payload pad byte is unreachable — recorded at `WavWriter::close`). Sources are WAV-ONLY, 16/24-bit PCM (FLAC support and Float32 WAV input removed — a FLAC file takes the unknown-magic refusal with the convert-once hint; a Float32 wav takes the unsupported-format refusal). Sidecars are sample-rate-bound by construction; old-format files fail loudly and convert only through `tools/migrate_sidecar_to_frames`.

### The Marker Comment: the Measure (architect 2026-08-19; rebranded and tightened 2026-08-20; warp-only 2026-09-14; the measure alone again 2026-09-15)
EVERY WARP MARKER LINE may carry a COMMENT, appended to the otherwise whitespace-free canonical line as `<canonical line><space>//<measure>` — `44100|1.05 //12`, `#66150|1.00 //+1/4`. THE SEPARATOR IS THE FIRST ` //` ON THE LINE, which is unambiguous by construction: the canonical prefix cannot contain a space, so no earlier candidate exists and everything past it is the comment. It is the ONE place a space may appear in a marker grammar. The writer emits NO comment when the measure is blank; the empty comment `//` and a comment carrying a COMMA anywhere (the retired `//<measure>,<magnification>` form included, no migration) are ADVERSARIAL and load-fatal in both binaries, refused by the split before the measure's judge is asked. The split's ONE owner is `split_marker_comment` (`src/parser/marker_measure.h`). PHASE-RESET LINES CARRY NO COMMENT (below).

**THE PHASE-RESET RETIREMENT (architect approval 2026-09-14).** From 2026-08-19 to 2026-09-14 the suffix rode EVERY marker line on BOTH sidecars. On 2026-09-14 the architect ruled that PHASE RESETS LOSE MEASURES WHOLE — a phase-reset line is a canonical frame with an optional `#` and nothing else, a ` //` on one load-fatal in both binaries (grammar, sidecar, flag box, editor road, painter, hit rects, value step and drag, and the `h` view's extraction, labels and revert all lost the phase measure). The comment is therefore WARP-ONLY, and the naming-symmetry asymmetry is recorded at `PhaseResetMarker` and `render_phase_reset_flags`. MAGNIFICATION IS NO MARKER FIELD (architect approval 2026-09-15): the comment carries the measure alone; magnification is its own column, the magnification level markers sidecar below.

**THE FREE-UTF-8 COMMENT CLASS IS RETIRED (architect 2026-08-20, one day after it landed).** The field was a FREE-TEXT COMMENT from 2026-08-19: 1..`kMaxMarkerCommentBytes` = 99 bytes of well-formed UTF-8, control-free, and it was recorded here and at marker-ui.md as the FIRST relaxation of "TEXT IS UTF-8 IN FREE TEXT AND ASCII IN GRAMMARS" on the marker side and as the product's first non-ASCII painted surface. The architect rebranded it the next day into the MEASURE — a score position, then serving the score-video jump that sunset on 2026-08-21 (marker-ui.md carries the record) — and a measure is a VALUE, so the field returns to the ASCII-grammar class every other structural grammar in the product sits in. Both claims retire with it: there is no marker-side relaxation of the UTF-8/ASCII rule, and the product paints no non-ASCII surface. The retirement is recorded rather than deleted because the RULING the carve-out rested on (one face, no font fallback, no Pango) is unchanged. NO MIGRATION AND NO LENIENCY SHIM: no ` //` suffix was ever written into the project history, so the tightening strands nothing in the `h` walk, the `'` loads or the `h` view's revert.

THE MEASURE GRAMMAR, ASCII only, ONE canonical spelling per value (the `frame_format.h` discipline), enforced IDENTICALLY at load and at the editor commit. NO SPACES, TWO FORMS. **DIRECT** — `<M>`: M a decimal integer in [1, 999] with no leading zeros and no sign. **OFFSET** — `+<W>` or `+<n>/<d>`: W obeying M's rules (so `+0` is refused — offsets are strictly positive), or a PROPER fraction with 1 <= n <= d−1, d <= 16, no leading zeros on either, and gcd(n, d) == 1, so `+4/8` is REFUSED and its one spelling is `+1/2`; an offset is EITHER whole OR a proper fraction, never both, no fraction reaching a whole measure. **THE SPACED FORMS ARE RETIRED** (architect approval 2026-09-14, the header's FIFTH frozen reopen): the direct fraction `<M> <n>/<d>` and the mixed offset `+<W> <n>/<d>` stood from 2026-08-20 and are refused like any bad token — a larger offset skips a measure (`+1`) and places another marker. Nothing on disk carried either. **THE SECTION QUALIFIER IS RETIRED** (architect approval 2026-08-21, the score-video sunset — the header's third frozen reopen): from 2026-08-20 to 2026-08-21 a direct form could carry `<S>:` (`2:12`) to disambiguate a printed-numbering restart for the score-video jump's map lookup; the jump left the product whole and the architect ruled the number alone serves — "the context will already be a clue", a repeat or a restart being disambiguated by where the marker sits. `2:12` is refused like any bad token, and a resolved measure is the plain RATIONAL, not a (section, rational) pair. **THE CEILINGS ARE THE SCORE'S, NOT AN ABSURD-VALUE CLAMP'S** (architect approval 2026-09-05, the header's FOURTH frozen reopen): they stood at 99999 and 99 from the 2026-08-20 rebrand, wide enough that no real number could reach them, which is all a clamp against a stray digit run has to be; the architect ruled them down to what music spells — "999 measures is more than any sheet music; the finest fraction I could place a marker on is a sixteenth" — so that the byte bound below, and every editor cap derived from it, advertise exactly what the grammar can commit. The tightening is the cost and it is paid the ordinary way: a sidecar carrying `1000`, `+1000` or `1 1/17` is ADVERSARIAL and load-fatal in both binaries from that date, and no project history carries such a token, so nothing is stranded and there is no migration. THE BYTE BOUND IS `kMaxMarkerMeasureBytes` = 6, and it is TIGHT rather than a policy cap: the longest canonical token spellable is the fractional OFFSET `+15/16` — the sign over the widest reduced fraction under the denominator ceiling (`15/16`, `12/13` and their kin all reach five bytes), the whole forms `999` and `+999` narrower. (It read 12 for the 99999/99 ceilings, 14 for the one day the retired qualifier made `99:99999 98/99` the widest, and 10 while the spaced `+999 15/16` stood.) LOAD-FATAL, first error only, identically in both binaries: anything off the grammar, anything past the bound, and a comment the split refuses. Every one is GUI-UNPRODUCIBLE, which keeps the two-category rule exact — an EMPTY COMMIT REMOVES the measure rather than storing one, the writer emits no comment for a blank measure, and the editor's commit runs the SAME validator the readers do. THE CRLF TRIPWIRE SURVIVES: the grammar admits no whitespace at all, so a `\r` reaching either validator is refused like any other stray byte.

`+` RESOLUTION IS NOT VALIDITY, and the authoritative statement of it is at `marker_measure.h` rather than here. In short: a `+` adds to the IMMEDIATE PREDECESSOR marker's RESOLVED measure on the warp column and only that one (no fallback scan); chains resolve, so `12`, `+1`, `+1` resolves the third to 14; a BROKEN LINK — a predecessor with no measure, or one itself unresolvable — leaves this marker UNRESOLVED. An unresolved `+` still commits, saves, loads and paints; resolution gates the CONSUMERS alone. GRAMMAR IS VALIDITY; RESOLUTION IS NOT — load-lenient, act-strict, so re-ordering markers can never make a file refuse to load.

ONE SPELLING OF THE SPLIT AND THE GRAMMAR, in `src/parser/marker_measure.h` (header-only, both binaries, the frame_format.h precedent; it succeeds the deleted `marker_comment.h`): `split_marker_comment`, `parse_marker_measure`, `format_marker_measure`, `validate_marker_measure` and `measure_is_steppable` plus the bound, WITH NO MIRROR ANYWHERE — the membership is enumerated at that header and is not counted here, a count being the part that goes stale. What the list must cover: the warp file parser, the GitHub recheck's delta extractor and per-side cascade pass and the `h` view's revert reconstitution (all three through the parser's own per-line entry point), and the MEASURE EDITOR'S commit and byte cap. `parse_single_canonical_line` carries a `bool accept_comment` parameter for exactly that reason: the whole-file loop, `extract_warp_entry`, `warp_side_effective_disabled` and the revert pass TRUE, while the FLAG EDITOR'S candidate parse passes FALSE, which is what keeps a ` //` typed into the payload buffer a red-flashing grammar error — the measure has its own editor. (`src/parser/marker_magnification.h` keeps the one-digit LEVEL grammar and its range owner `kMarkerMagnificationMax` = 4; the magnification level markers parser, below, is its reader.)

THE FIELD IS HOMED ON THE SERIALIZED BASE (`WarpMarker::measure`), because it must round-trip through the file and both readers are shared: the CLI parses it and never re-serializes anything, while the GUI store upcasts the base whole. It reaches no further — no engine marker carries it (`MarkerForRender` holds none), and the render fingerprint serializes resolved fields only, so editing a measure can never invalidate a completed render. It IS authored content: undo-domain through `warp_row_fields_differ`, dirtying, carried by `'` and shown by the `h` view's diff.

### The Magnification Level Marker Sidecar (architect 2026-09-15)
THE THIRD MARKER COLUMN, DISPLAY-ONLY, in `<stem>.magnificationlevelmarkers` beside `.warpmarkers` and `.phaseresetmarkers`. Magnification was a field of the warp marker, and a picture tied to tempo sections could not show a two-measure blast inside one section, so the picture's gain is its own column, decoupled from tempo. ONE LINE PER MARKER, `[#]<frame>|<level>` and nothing else: `#` the disabled prefix (the phase-reset column's), `<frame>` the canonical authored frame (`frame_format.h`), one `|`, and `<level>` EXACTLY ONE ASCII digit 0–4 through `marker_magnification.h`'s grammar — REQUIRED on every line, no blank level and no inheritance. The parser (`src/parser/magnificationlevelmarkers_parse.{h,cpp}`, both binaries) is the phase-reset parser's discipline exactly: never throws, the empty file the no-markers form, a blank line fatal, no whitespace or CR anywhere, `path_free_reason` with the warp column's contract, line-tagged diagnostics, and only a DECREASING frame refused (equal frames load). The column's frames meet the shared `[0, total−1]` wall (`first_past_eof_wall_defect`, disabled rows included). Anything else is ADVERSARIAL and load-fatal, first error only, identically in both binaries.

WHAT A LEVEL MEANS is the GUI's waveform gain profile (`build_waveform_gain_profile`, `magnificationlevelmarkers.h`): level 0 before the first ENABLED marker, each enabled marker's level holding to the next enabled marker's frame, DISABLED markers invisible, and on equal frames THE LAST IN STORE ORDER WINS; a level-0 marker is how the picture returns to unmagnified. The profile is memoized per store generation and gated by the zoom (`effective_waveform_gain_profile`, zoom-viewport-strip.md). NO RENDER READS THE COLUMN: it is outside `render_fingerprint`, `compute_live_render_fingerprint`, every engine input and the target preview's request, so a level change dirties the tab and never touches a render. The CLI requires and strictly parses the file and renders without it.

THE SIDECAR SET IS FOUR AND ALL-OR-NOTHING (architect 2026-09-15: "we never support legacy — strictly migrate to the new and require manual update"): `.warpmarkers`, `.phaseresetmarkers`, `.magnificationlevelmarkers` and `.settings` are REQUIRED FILES, EVEN IF EMPTY, and the GUI writes all four on every save. A folder with NO sidecar is a new project whose first open writes the four templates (the magnification template empty, the phase-reset one's shape); a folder with ANY sidecar must carry all four, a missing one refusing naming the file with nothing written. One owner, `sidecar_set_presence` (`settings_io.h`, beside the one extension list `kSidecarExtensions`), read by the load (fatal) and its dry run (the picker's and Revert's card) alike. The column rides every road a sidecar does: the undo entry's third snapshot, the render entry's sidecar set, the three loads in place (in the one undo entry), the `h` walk's strict load and the checkpoint.
