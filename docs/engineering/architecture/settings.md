# Settings Schema and Editors

Moved verbatim from CLAUDE.md in the 2026-07-25 slim-down (project feature-complete). This file is now the authoritative home for this detail; CLAUDE.md carries only a digest and a pointer here. Keep it current with landed rulings.

### Engine Settings are Typed
`app.engine_settings` (declared in `engine_settings.h`) is the single in-memory source of truth for the engine-relevant settings keys. There is no string-shaped passthrough vector, and there is NO `output_format` key (removed 2026-07-15 like `limiter`, no legacy — a `.settings` still carrying it fails the strict load as an unknown key): the wav is the only render product. FUTURE-PROOFING (architect-ruled): every archival render — GUI disk route AND the CLI, never the preview buffer route — also writes the FULL framemap pair (`<wav-stem>.warpframemap` + `.phaseresetframemap`, exactly the engine's input, via the shared `map_output` writers, byte-identical between products) into `~/.cache/warptempo_gui/<pid>/`; the pair is STRICTLY INERT — no product path reads it back; the intended consumer is a hypothetical future diff-capable algorithm; the `RenderCache` lifecycle owns cleanup (dir removed at GUI shutdown, dead-PID orphans — CLI dirs included — swept at the next GUI launch); the write is non-fatal (one stderr line on failure). MIDI tempo-map support is removed entirely. The limiter is UNCONDITIONAL and is NOT a settings key (removed 2026-07-15, no legacy: a `.settings` still carrying `limiter=` fails the strict load as an unknown key); output is always the limited 24-bit PCM deliverable — the `limiter=false` Float32 clean-render path and its filename prefix are gone, as is Float32 WAV INPUT (sources are 16/24-bit PCM WAV only) and the WavWriter's non-PCM24 write support. The peak parameters are non-settings constants in `src/prepost/peak_limiter.h`. All three boundaries are strict:

- File load (`read_settings_file` in `src/parser/settings_file.{h,cpp}`, the whole-file strict schema run VERBATIM by both GUI and CLI — a sidecar set is loadable in both products or neither): any violation aborts the source load with the first error, same shape as a corrupt audio file — unknown key, keyless non-comment line, duplicate of ANY key, malformed or out-of-vocabulary value (GUI-kind keys included: off-preset playback_speed, out-of-range gui_scale, out-of-vocabulary zoom), missing ANY canonical key — EVERY key is required (the parser-side `kCanonicalSettingsKeys` list in settings_file.cpp, the requirement twin of `kSettingsOrder`; the program writes all keys, so a file short of one is hand-damaged and refuses; there is no absent state and no load-side default). `projects_repo` was the schema's one optional key for a single day (2026-08-03..04) — the architect RETIRED the exception at his live pass ("(architect approval 2026-08-04)" at the settings_file.{h,cpp} sites): the corpus has one live project and it carries the line, so the key joined `kCanonicalSettingsKeys` like every other, and a `.settings` written without it is load-fatal in both products by the ordinary missing-key refusal (hand-edit recovery, no migration — the standing convention; checkpoints committed before the key exist refuse the load-in-place-from-a-commit by the same gate). `kDefaultProjectsRepo` (settings_file.h) survives as the first-open template stamp and the pre-load member default only — explicitly NOT a load fallback. Persisted viewport/playhead values are NOT range-checked at load (display scratch — the runtime clamps own them; the guard was removed 2026-07-15); a slowing map legitimately persists positions past the source total; the check is SKIPPED when the map cannot build — tripwire-class only, since the resolver normalizes marker arrangements and never refuses — and the runtime clamps own the values then); the persisted zoom-vocabulary constants (`kMinZoom`/`kMaxZoom`) live in `settings_file.h` so that refusal is also identical in both binaries.
- Editor commit (`GuiSettingsEditor::commit`): unknown engine keys and invalid values red-flash and don't commit.
- Render dispatch: `req.engine_settings` is copied from `app.engine_settings`; the typed struct cannot hold malformed values by construction.

`kSettingsOrder` in `settings_io.cpp` is the SoT for the on-disk write order and the first-open template; key MEMBERSHIP is `kEngineKeys` via `is_canonical_engine_key` (`engine_settings_io.cpp`; the table pairs each key with its `EngineField` and doubles as the key-to-field lookup), `validate_engine_setting` is the single per-`(key, value)` engine validator used by the schema readers and editor commit alike, and `format_engine_field_value` is the single engine-field byte serializer — the key-keyed `format_engine_setting_value` (autocomplete) and every settings writer delegate to it. The two strict readers share one lexical scanner (`warptempo_settings::scan_settings_file`, `settings_file.h`), and its lexing is BYTE-EXACT: each line splits at its first `=` verbatim — no BOM, blank-line, `#`-comment, or whitespace tolerance anywhere (the marker parsers are equally byte-exact; `strip_bom` is deleted product-wide; the migration tool keeps its own legacy latitude) — with the duplicate rule and the required-key tail existing once. Adding a new engine key touches: `EngineSettings` (new field with member default) and `EngineField` (`engine_settings.h`), `kEngineKeys` and `validate_engine_setting` (`engine_settings_io.cpp`), `kSettingsOrder` (`settings_io.cpp`), `kCanonicalSettingsKeys` (`settings_file.cpp`). Six edits, four files.

`kSettingsOrder` also carries GUI-kind keys — view state, `playback_speed`, `gui_scale`, `audio_player` — that never enter `EngineSettings` or the engine block; they persist through the `.settings` file but are not engine input. The settings editor sets EVERY key that can appear in a `.settings` file: GUI-kind commits route through `GuiSettingsEditor::commit_gui_setting`, which hands (key, value) to `validate_gui_setting` (settings_file.{h,cpp}, parser-side — the GUI-kind sibling of `validate_engine_setting` and the SINGLE grammar/vocabulary owner, called by the whole-file reader AND the editor, so a spelling is loadable iff it commits; it is STATE-FREE — the load-side trim walls stay in `first_past_eof_wall_defect`, and the editor keeps its own wall compare and active/inactive routing on top; the read-only-tab trim refusal that stood beside them is DELETED, architect 2026-08-07) and applies the typed result through the key's own GESTURE CHOKEPOINT — `set_playback_speed`, `set_follow_mode`, `handle_active_audio_view_toggle`, `toggle_active_markers_view`, `switch_active_tab_view_to`+trigger, `move_playhead_to` / `apply_zoom_change` / assign-then-`clamp_viewport_start` (the ACTIVE-tab playhead-cursor commit joins the navigation-jump class since 2026-07-29 — no exemptions: it clears the selection AND the region before the move, the Home/End sequence verbatim, the rationale at the arm), and the trim commit tail through its one owner `commit_trim_mutation` (incl. `auto_clear_crossed_trim`; the arm's inline three-call copy was converted 2026-08-02) — never a parallel writer. Per-tab keys naming the INACTIVE tab write that tab's stored band (load-shaped values; the Ctrl+Tab restore clamps own them; a crossed resulting trim pair RESETS to that tab's full window with one stderr line, the load convention under always-set trim); TRIM WRITES COMMIT IN A READ-ONLY TAB LIKE EVERY OTHER PER-TAB KEY (architect 2026-08-07): the red-flash refusal that fired when the NAMED tab was read-only is deleted, trim being BAND rather than authored content — it sits in `ViewState` beside `viewport_start` / `zoom` / `playhead_cursor` / `read_only`, all four of which were already allowed, and the gestures the refusal mirrored stopped refusing the same day. It covered both arms (the guard read the named tab's band, not the active one), so a parked `tab_b_trim_*=` typed from a writable tab A while B is locked commits too. The ruling's home is `read_only_key_blocked` (input_key_dispatch.cpp). THE SURFACE ITSELF IS GONE ON A LOCKED ACTIVE TAB, though, which is the same day's second ruling and closes the asymmetry the first one exposed: THE SETTINGS EDITOR DOES NOT OPEN IN A READ-ONLY TAB (architect 2026-08-07). It authors the ENGINE SETTINGS, which the lock protects by the ruling's own vocabulary, and its two doors reached different gates — bare `;` was already off the read-only allowlist, while the SETTINGS DROPDOWN's six items call `open_prefilled` and reached no gate at all, so the menu was a live route to every engine key from a locked tab. The refusal lives at `GuiSettingsEditor::open`, the ONE chokepoint both doors funnel through, and is a SILENT CONSUMED NO-OP rather than a greyed menu item: the dropdown items' never-grey rule is standing (they dispatch, and their commands' own refusals answer). The modal playback stop moved inside that opener to sit past the gate, so a refused click stops no audition — the `open_load_editor` precedent, and it took the caller-side stops with it (the inventory at `stop_playback_for_modal_open`). CONSEQUENCE FOR THE TRIM KEYS ABOVE: on a locked ACTIVE tab the relaxation is UNREACHABLE, the surface being gone rather than the rule — the arm's deleted guard stays deleted, this opener being the one owner — while a typed `tab_B_trim_*=` from an unlocked active tab with B locked stays legal, which is the case the relaxation serves. The four per-tab trim keys ALWAYS EMIT ACTUAL FRAMES (always-set trim, architect 2026-07-30): the `-1` unset spelling is DELETED from the frozen grammar under an explicit same-day grant (recorded at each settings_file.{h,cpp} site) — a trim value is a canonical whole source frame and nothing else, `-1` refusing like any malformed value in both products (a pre-arc sidecar carrying one is adversarial and load-fatal; hand-edit is the ruled recovery, no migration tool by ruling), and the first-open template stamps the full window [0, total-1] on both tabs. Both trim keys' ACTIVE-TAB commits keep the SETTER DESELECT (architect 2026-07-30, "a typed commit is a commit"); an inactive-tab commit writes the parked band only and deselects nothing (the trim-window highlight publish died with the region simplification — a setter WRITES a bound, and the crossed-commit tail now RESETS to the full window, full-window-first so the one-frame [0,0] never self-resets). Numeric settings VALUES are pinned to ONE canonical spelling each — the exact bytes their writer emits: playback_speed by text membership (above); tab_X viewport/playhead through `parse_authored_frame` (digits only, no sign/point/leading zeros — the %lld output); tab_X_zoom by the min-0 `format_value_double` round-trip gate then the continuous vocabulary `[kMinZoom, kMaxZoom]` = [1,17] (the zoom level is a real-valued double — see the continuous-zoom paragraph; `0`, `0.5`, and any non-shortest spelling refuse — no sentinel, no migration); gui_scale by canonical integer digits (parse_authored_frame lexing — no sign/point/leading zeros, exactly the writer's %d) range-checked to [50, 200]; the settings scale and marker scale by a `format_value_double(v, 4)` round-trip gate (the min-4 padded shortest form is the one spelling; the session-only bpm-bracket bounds gate at min-0 likewise); `parse_value_double` (value_format.h) still rejects any ASCII alphabetic byte first (no exponents, no inf/nan; the caller-less `parse_double_strict` — font_size's parser, kept a while as an unused primitive — was DELETED from parse_text_util.h 2026-08-02 under grant, its deletion record at the site). The free-text fields (title, notes, cover, url, audio_player, projects_repo) keep caps verbatim AND CARRY UTF-8 (architect 2026-08-02, the relaxation: a free-text value is text, so any well-formed UTF-8 loads, displays, edits, recalls and saves BYTE-IDENTICALLY — the old "recall strips non-ASCII" exception at autocomplete_value is CLOSED with the editor filter that caused it, and the title's three refusals are byte-safe under it because '"' and '/' cannot occur inside a multi-byte sequence; the STRUCTURAL grammars around them — keys, value vocabularies, numeric spellings, marker labels — stay ASCII, and there is no font fallback or bidi, so an uncovered glyph draws .notdef) — title with three refusals (empty, a wrapping double-quote pair, '/') and NO input latitude (the file boundary is byte-exact; the settings editor still trims its typed line — interactive latitude, not file latitude, and its trim is ASCII-whitespace-only in the "C" locale so it cannot split a character); bools share `parse_bool_token` schema-wide, and its vocabulary is exactly `{true, false}` (the writer's two spellings). GUI-kind commits are history-less like their gestures: no undo, no dirty, one stderr line, deactivate; a same-value commit no-op-deactivates like the engine no-op gate. Autocomplete's bare-Tab recall works for every key, byte-identical to what a Ctrl+S would write (shared `format_nonengine_value` serializer + `recall_gui_setting_value`, settings_io.cpp); `GuiSettingsEditor::autocomplete_value` REPORTS WHETHER IT ADVANCED THE BUFFER, which is what makes Tab one model across every dialog editor — the completion is offered first and a Tab it refuses (no `=` yet, a value side already typed — every second Tab — or an unknown key) walks the modal's focus ring instead, while Shift+Tab walks that ring backwards and is never offered the completion at all (architect 2026-08-13, "we should use one model for all autocompletes"; the typed-`=` trigger of a few hours that day is reverted with it, so an `=` is an ordinary character again, and the authoritative statement is at `route_modal_editor_key`'s Tab arm, input_key_dispatch.cpp). Playback is always already stopped during a commit (the editor is modal; its open stopped playback). THREE GUI-kind keys have no gesture at all — `gui_scale`, `audio_player`, and `projects_repo` — their settings-editor commits assigning directly. The settings dropdown lost its opener with it — six items now. gui_scale stands alone as the product's one scale axis.) `gui_scale` (2026-07-30, the kdenlive redesign's prerequisite lever) is the GUI's rendering scale as an integer percent in [50, 200] (the ceiling shrank from 400 under a granted frozen touch, architect 2026-07-31 — 200, the 4K case, is the realistic ceiling; THE FLOOR CAME DOWN 100→50 under a second granted frozen touch, architect 2026-08-10, the range arm and its error string in settings_file.cpp being the whole parser-side change — below 100% the per-metric floors in `scaled_px` (render.h) stop being defensive and start firing, every authored 1px border/edge/pad/separator rounding to 0 at s = 0.5 under banker's rounding, so the two unfloored 1px lines found in the sweep — the row-2 and row-4 group separators — took floors of 1, the marker-flag editor's caret column moved onto the shared floor form, and the PLAYHEAD HEAD's per-row half-width took a floor of 1 through a new shared accessor `playhead_head_half_px` so its bottom row paints 3px wide instead of collapsing onto the 1px stem; a floor, not a pin — at 100% and above every scaled half is already ≥ 1 and nothing moves. The 12pt text is deliberately NOT floored: it scales straight to 6pt at 50%), default 100 — 100 the design baseline (1920x1080, the one supported resolution) — and is LIVE since 2026-07-31: pushed through set_gui_scale_percent at the three application points and applied live by the editor commit through apply_gui_scale (the resize-path rebuild); its consumers are the REDESIGNED rows — since row 7 (2026-08-01) that is EVERY row of the product, the whole surface riding this one axis (kdenlive-redesign.md). THE FOUR RENDER-ENVIRONMENT ATTESTATION KEYS — `libm_hash`, `libmvec_hash`, `fftw3_hash`, `fftw3_threads_hash` — LEFT THE SCHEMA 2026-08-09 under a granted frozen touch, recorded at the settings_file.{h,cpp} sites ("architect approval 2026-08-09"), and the whole surface went with them: the load-time comparison, the advisory notice ("Render libraries changed since last save…"), its `o` acknowledge and re-stamp, the CLI's equivalent stderr line, the first-open template's current-hash stamp, the settings editor's four recall/commit arms, and the `AuthoringSnapshot` / render-entry carriage. THE RULING: with `-ffp-contract=off` in the build, library drift is measured and bounded at inaudible classes (the -38 dBFS / two-samples limiter class recorded in HELP's Reproducibility section), and anything material would fail loudly through the limiter knife-edge rather than silently — so the check communicated a significance that no longer exists, and it is a rare-fault backstop of exactly the kind the wind-down deletes rather than keeps. The `o` key is untouched: it was never this prompt's key in the product's own keymap, only its sole prompt RESPONSE, and bare `o` remains the active tab's read-only toggle.

THE MACHINERY WENT WITH THE SURFACE, WHOLE: `src/parser/env_fingerprint.{h,cpp}` is DELETED and off `WARPTEMPO_PARSER_SOURCES` (that list has no fftw dependency of its own now, the version-symbol read having gone with the CLI's stderr line), and so is the RENDER-CACHE IDENTITY TERM — the render fingerprint used to open with the stat-identity digests of the four libraries mapped into the rendering process, and now names authored state and recipe only. ONE RULING COVERS BOTH (architect 2026-08-09, overruling the one-day reading that kept the cache term as a silent-wrong guard): that term's only protection was byte-identity of reused previews across a library epoch, and a reuse that crosses one differs at exactly the inaudible class the retired notice guarded — so the argument that killed the attestation kills the cache term identically. Nothing is released as completed, so the continuity break costs nothing. `kFingerprintVersion` BUMPED 19 -> 20 at the deletion, on the 18 -> 19 entry's own rule: any change to the key's byte SHAPE forces a fresh namespace, since a post-change key opening with the source path could otherwise byte-collide with a pre-change key whose first digest serialized those same bytes. Accepted cost as at every bump — every pre-bump cache entry and `.fingerprint` sidecar goes unreachable, a one-time cold cache.

THREE ACCEPTED CONSEQUENCES, recorded because all three are permanent. (a) A `.settings` still carrying any of the four is LOAD-FATAL in both products by the ordinary UNKNOWN-key refusal — the `font_size` precedent verbatim: no leniency arm, no migration tool, no bespoke diagnostic, hand-edit is the whole recovery, and a save cannot be the other half of it since a file that refuses to load never produces the session a save would be written from. (b) EVERY CHECKPOINT COMMITTED BEFORE THIS CHANGE DROPS OUT OF THE `h` HISTORY WALK PERMANENTLY: walk membership IS the load-in-place gate (`load_commit_sidecars_strict`), so a commit whose `.settings` carries the retired keys is hidden at init with one counted stderr line. The `font_size` deletion already had this consequence and the architect re-accepted it 2026-08-09. A rider from later that day: the walk emptying does NOT lock the piece out of the feature — the view opens on an empty walk at `0/0`, and Save and Commit rebuilds the walk from the first checkpoint written under the new schema (github-recheck.md's entry-gate paragraph owns the ruling; the refusal it replaced would have made a schema retirement unrepairable from inside the program). (c) A CACHED OR COMPLETED PREVIEW MAY NOW BE REUSED ACROSS A LIBRARY UPGRADE: with the environment term out of the key, the two reuse rungs and the `.fingerprint` up-to-date rung can serve an artifact rendered under an older glibc or FFTW, and the difference is bounded at the inaudible classes the ruling accepts (the -38 dBFS / two-samples limiter class in HELP's Reproducibility section). Byte-comparison across a library epoch is the user's own discipline — re-render what you keep comparing, which is what that section already says (architect 2026-08-09).

Render entries carry the SAME sidecar set a source does: `<basename>.warpmarkers` / `.phaseresetmarkers` (authored domain, iter/bpm variation applied at dispatch) plus a full standard-schema `<basename>.settings` and `.fingerprint` written by `do_render`'s load-in-place-critical tail for wav renders (`active_audio_view=T` always; the landing tab = dispatch tab carries the recipe trim and dispatch-moment view keys; live session prefs are captured at dispatch through `AuthoringSnapshot`). The set is written ONCE and never touched again. There is NO in-app render-view player (the stateless render-entry audio player was removed): auditioning is EXTERNAL — `l` ("Listen to renders") launches the `audio_player` binary over every wav under `renders/` in numeric order via posix_spawnp — and the sole transfer of a render back into authoring is the `'` load editor (`GuiRendersDir` — renamed from GuiRenderView — is the pure `renders/` enumerator feeding `l` and the editor's autocomplete). THAT EDITOR HAS THREE SUBJECTS and this file owns exactly one of them: outside the `h` history view it takes a RENDER-ENTRY identifier, and inside it the viewed walk's own vocabulary — a commit spelling, or (since 2026-08-08) a LOCAL member NUMBER whose act carries no sidecar set at all, only the markers and the engine block an undo entry holds (github-recheck.md owns both in-mode arms). Nothing below this paragraph describes them. `load_render_entry_in_place` (input_key_dispatch.cpp) re-reads a named entry's frozen set — the marker pair plus the whole standard-schema `.settings` — reading and validating the wav's existence and all three sidecars BEFORE any store mutation (returns false untouched on any failure → the editor red-flashes; since 2026-08-02 each genuine-failure arm — the running-batch self-guard, a missing/non-regular wav, and each of the three sidecar read/validate failures — also names its cause and path on ONE stderr line, first-error-only by construction, while the caller's unknown-id refusal stays silent behind the flash: a typo is not a fault), then applies THE RECIPE AND NOTHING ELSE.

**A LOAD IN PLACE WRITES EXACTLY WHAT ITS ONE UNDO ENTRY RESTORES** (architect 2026-08-24, in his words: *"load in place should overwrite elements which have undo — so trim is excluded also"*). That is the WARP STORE, the PHASE RESET STORE and the ENGINE SETTINGS — what `Undo::push_undo_both` captures — and nothing beside them. EVERYTHING ELSE STAYS LIVE: both tab bands untouched, TRIM INCLUDED (trim has no undo; `Shift+[` is its recovery), the S/T bit, the W/P bit, the A/B tab, the camera, `follow`, `playback_speed`, `gui_scale`, `audio_player` and `projects_repo`. A recipe is a set of markers and an engine block; where the user is standing when he loads one is his own, and undo/redo and the `h` view are how he then inspects what the load changed. The rule has ONE home in code — `GuiInputHandler::apply_recipe_in_place` (declared in input_handler.h, defined in input_key_dispatch.cpp), the single body BOTH sidecar-sourced load-in-places run, the render entry's and the `h` view's commit load (github-recheck.md owns that arm; the third, the Local-member load, carried this shape from the start, an undo entry being all it ever had to give). The entry sidecar still carries every view key and both bands, because the schema is strict and a `.settings` is a whole state the CLI and a plain source load read whole — the load-in-place simply reads past them.

THE RETIRED RULE, recorded because it stood from the feature's birth until this date: the load-in-place applied the whole file 1:1 with a fresh source load of those sidecars, through the shared `apply_settings_engine_and_prefs`, so every field a load sets was set identically — both tab bands (via `view_state_from_settings_tab`, DELETED with its last caller), `active_audio_view` (which every entry sidecar writes as `T`), `active_markers_view`, `active_tab_view`, and all session prefs. In practice that yanked the architect out of source+warp into target+warp and restored the DISPATCH-MOMENT camera on the dispatch tab, three things he had not asked for. Its side effects went with it: `playback.set_speed`, `set_gui_scale_percent` and `paint_handler.on_resize` no longer run at a load tail, and `apply_settings_engine_and_prefs` has the source load as its only caller. Two consequences worth stating: `zoom_recall_level` (bare `0`'s per-session return level) now SURVIVES a load in place — it is the camera's, and the camera does not move, which supersedes the 2026-08-18 reading that dropped it as a discontinuity — and `Undo::push_undo_both`'s `tab_override` parameter lost its last producer and is deleted, the entry filing under the live tab like every other.

The load-in-place is an in-memory act, not a literal mv+load: the WORKFLOW is unchanged — one cross-file undo entry, dirty (Ctrl+S persists), and the `renders/` wipe — it does NOT overwrite the source sidecars on disk or reset undo. It carries the same running-render guard render view had (the load-in-place wipes renders/, which must not race a background sweep). The entry sidecars are trusted (written once at dispatch, never hand-edited): a malformed sidecar fails its own parse, but there is no adversarial content re-attestation — the render worker's source-clobber backstop and the engine tripwires remain the last-ditch guards. A successful load-in-place then wipes renders/ — moved to the desktop trash when `gio trash` is available, deleted otherwise (render-pipeline.md carries the ruling). A finished batch no longer auto-opens anything — its artifacts rest on disk for a later `l` or `'`.
