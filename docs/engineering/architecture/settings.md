### Engine Settings are Typed
`app.engine_settings` (declared in `engine_settings.h`) is the single in-memory source of truth for the engine-relevant settings keys. There is no string-shaped passthrough vector, and there is NO `output_format` key (removed 2026-07-15 like `limiter`, no legacy — a `.settings` still carrying it fails the strict load as an unknown key): the wav is the only render product. FUTURE-PROOFING (architect-ruled): every archival render — GUI disk route AND the CLI, never the preview buffer route — also writes the FULL framemap pair (`<wav-stem>.warpframemap` + `.phaseresetframemap`, exactly the engine's input, via the shared `map_output` writers, byte-identical between products) into `~/.cache/warptempo_gui/<pid>/`; the pair is STRICTLY INERT — no product path reads it back; the intended consumer is a hypothetical future diff-capable algorithm; the `RenderCache` lifecycle owns cleanup (dir removed at GUI shutdown, dead-PID orphans — CLI dirs included — swept at the next GUI launch); the write is non-fatal (one stderr line on failure). MIDI tempo-map support is removed entirely. The limiter is UNCONDITIONAL and is NOT a settings key (removed 2026-07-15, no legacy: a `.settings` still carrying `limiter=` fails the strict load as an unknown key); output is always the limited 24-bit PCM deliverable — the `limiter=false` Float32 clean-render path and its filename prefix are gone, as is Float32 WAV INPUT (sources are 16/24-bit PCM WAV only) and the WavWriter's non-PCM24 write support. The peak parameters are non-settings constants in `src/prepost/peak_limiter.h`. All three boundaries are strict:

- File load (`read_settings_file` in `src/parser/settings_file.{h,cpp}`, the whole-file strict schema run VERBATIM by both GUI and CLI — a sidecar set is loadable in both products or neither): any violation aborts the source load with the first error, same shape as a corrupt audio file — unknown key, keyless non-comment line, duplicate of ANY key, malformed or out-of-vocabulary value (GUI-kind keys included: out-of-range waveform_magnification_level, out-of-vocabulary zoom), missing ANY canonical key — EVERY key is required (the parser-side `kCanonicalSettingsKeys` list in settings_file.cpp, the requirement twin of `kSettingsOrder`; the program writes all keys, so a file short of one is hand-damaged and refuses; there is no absent state and no load-side default). `projects_repo` HAS LEFT THIS SCHEMA (2026-08-27, for the device config below), so a `.settings` CARRYING the line is now unknown-key fatal in both products — hand-edit recovery, no migration, the standing convention, and checkpoints written while the key lived refuse the load-in-place-from-a-commit by that gate. Its schema history is kept because the exception it holds is the reusable one: it was the schema's one OPTIONAL key for a single day (2026-08-03..04) before the architect RETIRED that exception at his live pass ("(architect approval 2026-08-04)" at the settings_file.{h,cpp} sites) — every key is required, with no instance left to argue otherwise. `kDefaultProjectsRepo` survives as the device config template's stamp and moved to device_config.h with the key — explicitly NOT a load fallback, there either. Persisted viewport/playhead values are NOT range-checked at load (display scratch — the runtime clamps own them; the guard was removed 2026-07-15); a slowing map legitimately persists positions past the source total; the check is SKIPPED when the map cannot build — tripwire-class only, since the resolver normalizes marker arrangements and never refuses — and the runtime clamps own the values then); the persisted zoom-vocabulary constants (`kMinZoom`/`kMaxZoom`) live in `settings_file.h` so that refusal is also identical in both binaries.
- Editor commit (`GuiSettingsEditor::commit`): unknown engine keys and invalid values red-flash and don't commit.
- Render dispatch: `req.engine_settings` is copied from `app.engine_settings`; the typed struct cannot hold malformed values by construction.

`kSettingsOrder` in `settings_io.cpp` is the SoT for the on-disk write order and the first-open template; key MEMBERSHIP is `kEngineKeys` via `is_canonical_engine_key` (`engine_settings_io.cpp`; the table pairs each key with its `EngineField` and doubles as the key-to-field lookup), `validate_engine_setting` is the single per-`(key, value)` engine validator used by the schema readers and editor commit alike, and `format_engine_field_value` is the single engine-field byte serializer — the key-keyed `format_engine_setting_value` (autocomplete) and every settings writer delegate to it. The strict readers share one lexical scanner (`warptempo_settings::scan_key_value_file`, `settings_file.h` — `scan_settings_file` IS that function plus the `.settings` canonical required-key list, and the device config below is its other caller, passing its own FIVE-key list; the split landed 2026-08-27 under that day's grant, so the lexing exists once for both files), and its lexing is BYTE-EXACT: each line splits at its first `=` verbatim — no BOM, blank-line, `#`-comment, or whitespace tolerance anywhere (the marker parsers are equally byte-exact; `strip_bom` is deleted product-wide; the migration tool keeps its own legacy latitude) — with the duplicate rule and the required-key tail existing once. Adding a new engine key touches: `EngineSettings` (new field with member default) and `EngineField` (`engine_settings.h`), `kEngineKeys` and `validate_engine_setting` (`engine_settings_io.cpp`), `kSettingsOrder` (`settings_io.cpp`), `kCanonicalSettingsKeys` (`settings_file.cpp`). ### The Device Config (2026-08-27)

FIVE KEYS ARE PER-DEVICE, NOT PER PIECE (architect 2026-08-27, in two steps the same day): `gui_scale` and `audio_player` left the `.settings` sidecar first, and with the project model that evening `projects_path` (the ABSOLUTE folder whose subfolders are the projects — the project model's root, `src/gui/project_model.h`), `projects_repo` (LEAVING the sidecar under the FIFTH parser grant on settings_file.{h,cpp}, architect approval 2026-08-27: ONE user has ONE repository, so the projects home is a fact about the device the GitHub recheck runs on, not about each piece — `app.projects_repo` stays the live field every reader reads, its SOURCE moved and its readers did not) and `last_project` (the folder NAME opened last, written by gui_main at EVERY SUCCESSFUL OPEN, startup's included, gated on a real change; blank until the first) joined them. They live in ONE file, `$XDG_CONFIG_HOME/warptempo_gui/config`, falling back to `$HOME/.config/warptempo_gui/config` — the same resolution shape `RenderCache::init` uses for XDG_CACHE_HOME, and ONE resolver with no `#ifdef` in it: the Android backend points XDG_CONFIG_HOME at the app's private internal directory in `android_main` before `gui_main` runs, exactly as it already did for the cache home. THE REASON is that the two devices that run this product want different answers for the same project: the laptop wants 100 % and audacious, the tablet wants 225 % and no player at all, and a sidecar that travels between them had to be rewritten on the way over and back. The owner is `src/gui/device_config.{h,cpp}` — reader, writer, path resolver, value serializer and the `is_gui_scale_percent` range predicate, all GUI-side, since the CLI never read either key.

THE FILE'S GRAMMAR AND POSTURE ARE THE SIDECAR'S. Same `key=value` line grammar through the SAME lexical scanner (`scan_key_value_file`), EXACTLY the five keys and each of them exactly once, every key REQUIRED — the WRITER emits them in the documented order (`gui_scale`, `audio_player`, `projects_path`, `projects_repo`, `last_project`) while the READER is ORDER-INSENSITIVE, the shared scanner checking membership, duplicates and presence and never position, exactly the sidecar's own posture — one canonical spelling per value, each grammar with ONE owner in device_config.h: `gui_scale` an integer percent in [50, 400] through `parse_authored_frame` then `is_gui_scale_percent`; `audio_player` free UTF-8 verbatim, BLANK being the no-player opt-out and its only spelling, exactly the semantics the sidecar's key carried; `projects_path` non-empty and ABSOLUTE (`is_projects_path`) and otherwise verbatim — existence is NOT a grammar question but startup's own "No project under <projects_path>" answer; `projects_repo` the sidecar's own free-text arm moved verbatim (the recheck normalizes it against the clone's `origin`; blank is legal and never matches); `last_project` EMPTY or exactly ONE path component (`is_last_project_name` — no `/`, not `.` or `..`, no leading or trailing ASCII whitespace, all six bytes of it: space, tab, newline, carriage return, vertical tab, form feed; a separator would compose a path that LEAVES the projects folder, which is the adversarial class and refuses the whole file). A MALFORMED FILE IS FATAL AT STARTUP: the file is program-written, so a violation is a hand edit and therefore adversarial — one blunt terminal line naming the path and the first offending line, and no window at all. No repair, no partial apply, and above all NO fallback to defaults, which would silently discard a value the user typed.

FIRST RUN WITH NO FILE writes the file from a per-backend template and then loads it like any other launch — there is no apply-the-template shortcut that could drift from what the reader accepts. The two templates are a PLATFORM FACT, so the seam answers them: `GuiPlatform::device_config_defaults()` (platform-seam.md), one accessor each backend implements — laptop `gui_scale=100` / `audio_player=audacious` / `projects_path=$HOME/.warptempo/warptempo_gui/projects` (HOME resolved at stamp time into an absolute literal; with no HOME the stamp is refused by the reader's absolute-path grammar, fatal) / `projects_repo=kDefaultProjectsRepo` / `last_project=` (blank), Android `gui_scale=225` / `audio_player=` (blank) / `projects_path=<externalDataPath>/projects` (the activity's own absolute path stamped literally — exactly the folder the sync convention pushes into; a static reading the backend's parked `g_android_app`, since the accessor is asked before any GuiPlatform exists) / the same repo / blank. 225 is the architect's own answer on the glass (2026-08-27): the scale that reproduces the retired rig's 1024 logical pixels on the tablet's panel, with the whole icon row fitting (249 is the fit ceiling there; 250 was the template for one afternoon that day, taken for the finger's sake — a marker flag has to be tappable without the second tap of a double-tap landing on the waveform — and stepped back the same evening for the ~3 authored px it cropped). A missing parent directory is created.

PERSISTENCE IS AT THE COMMIT. Every key is history-less with its own chokepoint — `GuiInputHandler::apply_gui_scale` (reached from the settings editor's `gui_scale=` commit), the editor's `audio_player=` arm, the editor's `projects_repo=` arm, and gui_main's `last_project` write at every successful open — THE FOUR CALLERS of `write_device_config`, each of which WRITES THE CONFIG FILE immediately, atomically, through the same tmp+fsync+rename writer the sidecars use (`projects_path` has no in-app writer: stamped by the template, edited by hand, only read). Ctrl+S carries none of them. A same-value commit stays the no-op it is and writes nothing; a failed write is advisory (one stderr line) and the live value stands for the session. THE LIVE CONFIG HAS ONE OWNER, gui_main's loop: the ONE `DeviceConfig` read at startup outlives every project the process opens (AppState is torn down per reopen — see the loop contract, platform-seam.md), each session's AppState reaches it by pointer (`AppState::device_config`), and every commit writes through it — re-reading the file per session was refused because a failed persist is advisory and would lose a value the user typed within the session. THE READ IS gui_main's, ONCE, before `GuiPlatform::init` — so `set_gui_scale_percent` and the input core's touch-slop push both land before the first configure and the first painted frame, which is strictly earlier than the sidecar road they replace (that one could not run until a source had been parsed on the startup tick, so the tablet's first frame used to paint at 100 % and jump). The settings editor keeps the three editable keys as an authoring surface and the Settings dropdown keeps its "GUI scale" item; the Tab-completion recall answers for them off the live AppState through the device config's own serializer, so recall and file agree byte for byte the way recall and Ctrl+S do for a sidecar key.

A SIDECAR STILL CARRYING `projects_repo=` IS UNKNOWN-KEY FATAL in both binaries, NO migration — the architect hand-edits his files (the retired-key record at `kCanonicalSettingsKeys`, settings_file.cpp, carries all four departures of 2026-08-27).

THE TWO PATH PROMPTS PRINT THE VARIABLE'S NAME (architect 2026-08-27, ONE WAY TO SHOW THE LEVEL): the Open prompt's label is `Open: <projects_path>/` and the load-in-place prompt's is `Load: <projects_path>/<folder name>/tmp/` — the variable's name in literal angle brackets and the folder by its real name (`<projects_path>/550 - 1/tmp/`), never the long path (`kOpenProjectEditorPrefix`, `kLoadEditorPrefixHead`/`Tail`, paint_handler.h; `tmp/` is the batch folder's name since 2026-08-27).

`'` (load in place) is unaffected BY CONSTRUCTION: it writes the two marker stores and the engine block and nothing else, and neither key is in an entry's sidecar any more.

### `playback_speed` is retired (2026-08-27)

The key retired WHOLE that day (architect 2026-08-27): the `.settings` key, the ten-preset on-disk vocabulary in `playback_speed_presets.h` (the file is deleted), the `:playback_speed=` editor arm, its Settings-dropdown item, `GuiPlaybackLifecycle::set_playback_speed`, `GuiPlayback::set_speed`, `playback_set_speed`, the `speed_x1000` atomic, the per-launch speed push and the predictor's speed input. The architect runs 1.0 everywhere in his one live project, and a feature nobody uses is machinery to maintain. WHAT STAYS is the playback engine's source-to-output RATE ratio, which is a different thing and was never the same one: the render body's per-output-frame increment is `source_rate / output_rate` — bare 1 on a JACK graph pinned to the source, 44100/48000 on the tablet's 48 k speaker — so AAudio's granted rate is still rescaled through the fractional read the body already performs (`playback_common.h`). A `.settings` still carrying the key is load-fatal in both products by the ordinary unknown-key refusal.

Render entries carry the SAME sidecar set a source does: `<basename>.warpmarkers` / `.phaseresetmarkers` (authored domain, iter/bpm variation applied at dispatch) plus a full standard-schema `<basename>.settings` and `.fingerprint` written by `do_render`'s load-in-place-critical tail for wav renders (`active_audio_view=T` always; the landing tab = dispatch tab carries the recipe trim and dispatch-moment view keys; live session prefs are captured at dispatch through `AuthoringSnapshot`). The set is written ONCE and never touched again. There is NO in-app render-view player (the stateless render-entry audio player was removed): auditioning is EXTERNAL — `l` ("Listen to renders") launches the `audio_player` binary over every wav under `tmp/` in numeric order via posix_spawnp — and the sole transfer of a render back into authoring is the `'` load editor (`GuiRendersDir` — renamed from GuiRenderView — is the pure batch-folder enumerator feeding `l` and the editor's autocomplete, and since 2026-08-27 the one owner of both output folders' names and paths). THAT EDITOR HAS THREE SUBJECTS and this file owns exactly one of them: outside the `h` history view it takes a RENDER-ENTRY identifier, and inside it the viewed walk's own vocabulary — a commit spelling, or (since 2026-08-08) a LOCAL member NUMBER whose act carries no sidecar set at all, only the markers and the engine block an undo entry holds (github-recheck.md owns both in-mode arms). Nothing below this paragraph describes them. `load_render_entry_in_place` (input_key_dispatch.cpp) re-reads a named entry's frozen set — the marker pair plus the whole standard-schema `.settings` — reading and validating the wav's existence and all three sidecars BEFORE any store mutation (returns false untouched on any failure → the editor red-flashes; since 2026-08-02 each genuine-failure arm — the running-batch self-guard, a missing/non-regular wav, and each of the three sidecar read/validate failures — also names its cause and path on ONE stderr line, first-error-only by construction, while the caller's unknown-id refusal stays silent behind the flash: a typo is not a fault), then applies THE RECIPE AND NOTHING ELSE.

**A LOAD IN PLACE WRITES EXACTLY WHAT ITS ONE UNDO ENTRY RESTORES** (architect 2026-08-24, in his words: *"load in place should overwrite elements which have undo — so trim is excluded also"*). That is the WARP STORE, the PHASE RESET STORE and the ENGINE SETTINGS — what `Undo::push_undo_both` captures — and nothing beside them. EVERYTHING ELSE STAYS LIVE: both tab bands untouched, TRIM INCLUDED (trim has no undo; `Shift+[` is its recovery), the S/T bit, the W/P bit, the A/B tab, the camera, `follow`, `waveform_magnification_level` and `projects_repo` — and `gui_scale` and `audio_player`, which since 2026-08-27 are not in an entry's sidecar at all and so are outside the question by construction. A recipe is a set of markers and an engine block; where the user is standing when he loads one is his own, and undo/redo and the `h` view are how he then inspects what the load changed. The rule has ONE home in code — `GuiInputHandler::apply_recipe_in_place` (declared in input_handler.h, defined in input_key_dispatch.cpp), the single body BOTH sidecar-sourced load-in-places run, the render entry's and the `h` view's commit load (github-recheck.md owns that arm; the third, the Local-member load, carried this shape from the start, an undo entry being all it ever had to give). The entry sidecar still carries every view key and both bands, because the schema is strict and a `.settings` is a whole state the CLI and a plain source load read whole — the load-in-place simply reads past them.

THE RETIRED RULE, recorded because it stood from the feature's birth until this date: the load-in-place applied the whole file 1:1 with a fresh source load of those sidecars, through the shared `apply_settings_engine_and_prefs`, so every field a load sets was set identically — both tab bands (via `view_state_from_settings_tab`, DELETED with its last caller), `active_audio_view` (which every entry sidecar writes as `T`), `active_markers_view`, `active_tab_view`, and all session prefs. In practice that yanked the architect out of source+warp into target+warp and restored the DISPATCH-MOMENT camera on the dispatch tab, three things he had not asked for. Its side effects went with it: `playback.set_speed`, `set_gui_scale_percent` and `paint_handler.on_resize` no longer run at a load tail, and `apply_settings_engine_and_prefs` has the source load as its only caller. Two consequences worth stating: `zoom_recall_level` (bare `0`'s per-session return level) now SURVIVES a load in place — it is the camera's, and the camera does not move, which supersedes the 2026-08-18 reading that dropped it as a discontinuity — and `Undo::push_undo_both`'s `tab_override` parameter lost its last producer and is deleted, the entry filing under the live tab like every other.

The load-in-place is an in-memory act, not a literal mv+load: the WORKFLOW is unchanged — one cross-file undo entry, dirty (Ctrl+S persists), and the `tmp/` wipe — it does NOT overwrite the source sidecars on disk or reset undo. It carries the same running-render guard render view had (the load-in-place wipes tmp/, which must not race a background sweep). The entry sidecars are trusted (written once at dispatch, never hand-edited): a malformed sidecar fails its own parse, but there is no adversarial content re-attestation — the render worker's source-clobber backstop and the engine tripwires remain the last-ditch guards. A successful load-in-place then wipes tmp/ — moved to the desktop trash when `gio trash` is available, deleted otherwise (render-pipeline.md carries the ruling). A finished batch no longer auto-opens anything — its artifacts rest on disk for a later `l` or `'`.
