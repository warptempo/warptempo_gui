### Engine Settings are Typed
`app.engine_settings` (declared in `engine_settings.h`) is the single in-memory source of truth for the engine-relevant settings keys. There is no string-shaped passthrough vector, and there is NO `output_format` key (removed 2026-07-15 like `limiter`, no legacy — a `.settings` still carrying it fails the strict load as an unknown key): the wav is the only render product. FUTURE-PROOFING (architect-ruled): every archival render — GUI disk route AND the CLI, never the preview buffer route — also writes the FULL framemap pair (`<wav-stem>.warpframemap` + `.phaseresetframemap`, exactly the engine's input, via the shared `map_output` writers, byte-identical between products) into `~/.cache/warptempo_gui/<pid>/`; the pair is STRICTLY INERT — no product path reads it back; the intended consumer is a hypothetical future diff-capable algorithm; the `RenderCache` lifecycle owns cleanup (dir removed at GUI shutdown, dead-PID orphans — CLI dirs included — swept at the next GUI launch); the write is non-fatal (one stderr line on failure). MIDI tempo-map support is removed entirely. The limiter is UNCONDITIONAL and is NOT a settings key (removed 2026-07-15, no legacy: a `.settings` still carrying `limiter=` fails the strict load as an unknown key); output is always the limited 24-bit PCM deliverable — the `limiter=false` Float32 clean-render path and its filename prefix are gone, as is Float32 WAV INPUT (sources are 16/24-bit PCM WAV only) and the WavWriter's non-PCM24 write support. The peak parameters are non-settings constants in `src/prepost/peak_limiter.h`. All three boundaries are strict:

- File load (`read_settings_file` in `src/parser/settings_file.{h,cpp}`, the whole-file strict schema run VERBATIM by both GUI and CLI — a sidecar set is loadable in both products or neither): any violation aborts the source load with the first error, same shape as a corrupt audio file — unknown key, keyless non-comment line, duplicate of ANY key, malformed or out-of-vocabulary value (GUI-kind keys included: out-of-vocabulary zoom), missing ANY canonical key — EVERY key is required (the parser-side `kCanonicalSettingsKeys` list in settings_file.cpp, the requirement twin of `kSettingsOrder`; the program writes all keys, so a file short of one is hand-damaged and refuses; there is no absent state and no load-side default). `projects_repo` HAS LEFT THIS SCHEMA (2026-08-27, for the device config below), so a `.settings` CARRYING the line is now unknown-key fatal in both products — hand-edit recovery, no migration, the standing convention, and checkpoints written while the key lived refuse the load-in-place-from-a-commit by that gate. Its schema history is kept because the exception it holds is the reusable one: it was the schema's one OPTIONAL key for a single day (2026-08-03..04) before the architect RETIRED that exception at his live pass ("(architect approval 2026-08-04)" at the settings_file.{h,cpp} sites) — every key is required, with no instance left to argue otherwise. `kDefaultProjectsRepo` survives as the device config template's stamp and moved to device_config.h with the key — explicitly NOT a load fallback, there either. Persisted viewport/playhead values are NOT range-checked at load (display scratch — the runtime clamps own them; the guard was removed 2026-07-15); a slowing map legitimately persists positions past the source total; the check is SKIPPED when the map cannot build — tripwire-class only, since the resolver normalizes marker arrangements and never refuses — and the runtime clamps own the values then); the persisted zoom-vocabulary constants (`kMinZoom`/`kMaxZoom`) live in `settings_file.h` so that refusal is also identical in both binaries.
- Editor commit (`GuiSettingsEditor::commit`): unknown keys and invalid values red-flash and don't commit — and SAY WHY ON A NORMAL CARD since 2026-08-30, all five refusals under one `Settings edit rejected: …` composition read by the stderr line and the card alike (the two `reject` lambdas, the unknown SETTINGS key — the COMMON FALLBACK every road reaches once the device band and the GUI band have declined the key, so its noun is the product's, not the engine's, and the three retired camera postures hear it like any other word that is not a key — the invalid canonical value, and the source-clobber guard, whose path names its basename).
- Render dispatch: `req.engine_settings` is copied from `app.engine_settings`; the typed struct cannot hold malformed values by construction.

`kSettingsOrder` in `settings_io.cpp` is the SoT for the on-disk write order and the first-open template; key MEMBERSHIP is `kEngineKeys` via `is_canonical_engine_key` (`engine_settings_io.cpp`; the table pairs each key with its `EngineField` and doubles as the key-to-field lookup), `validate_engine_setting` is the single per-`(key, value)` engine validator used by the schema readers and editor commit alike, and `format_engine_field_value` is the single engine-field byte serializer — the key-keyed `format_engine_setting_value` (autocomplete) and every settings writer delegate to it. The strict readers share one lexical scanner (`warptempo_settings::scan_key_value_file`, `settings_file.h` — `scan_settings_file` IS that function plus the `.settings` canonical required-key list, and the device config below is its other caller, passing its own TEN-key list; the split landed 2026-08-27 under that day's grant, so the lexing exists once for both files), and its lexing is BYTE-EXACT: each line splits at its first `=` verbatim — no BOM, blank-line, `#`-comment, or whitespace tolerance anywhere (the marker parsers are equally byte-exact; `strip_bom` is deleted product-wide; the migration tool keeps its own legacy latitude) — with the duplicate rule and the required-key tail existing once.
