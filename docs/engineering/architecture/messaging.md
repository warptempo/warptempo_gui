# Messaging — the state cell and the notification cards (architect design 2026-08-29)

This file is the ruling for BOTH halves of the messaging redesign: the STATE CELL, row 8's own text beside the clock, which carries what is true right now; and the NOTIFICATION CARDS, the top-right stack, which carry what just happened. The design record with his words is `tmp/notifications_design.md`; the mockups he picked from are `tmp/previous/messaging_mockups/` (`cards_AB.png`'s look 1 is the card, `bar_ground_AB.png`'s look A the ground he picked for the bar). The cards landed first; a STATUS BAR on the window's foot landed the next day and the tab row's STATUS CHAIN — the four-tier ladder the state strings and the events had shared since 2026-08-13 — was deleted with it (the tab row paints tabs and nothing else); and that same evening the architect ruled the bar off and its state text folded into row 8, where it is.

## The split: state and events

Every message the product emits is one of two things, and the split is the file's opening rule because it decides the surface. STATE is what is true right now, replaced as it changes, never timed out and never cleared by a key press — the progress line and the `h` walk line (the RESOLVED READOUT was the third and retired whole with the bar). STATE LIVES IN ROW 8'S STATE CELL. An EVENT is something that happened: an act was answered with a sentence, or something the user was not watching finished badly. EVENTS ARE NOTIFICATION CARDS. The architect is "not a big fan of notifications": the cards are minimal, and the inventory below is closed.

The split is also why the state surface has NO TIMEOUTS. The retired transient class was an event on a state surface, and it inherited every fault of that: it was hidden under a progress line, REVEALED STALE when the line above it cleared, wiped by the next key press, and invisible altogether under the `h` view's top-tier line. Nothing in the state cell can go stale, because nothing in it is ever a claim about a past moment.

## The state cell — row 8, right of the clock

"Status bars are generally the last row" (architect 2026-08-29) — every DAW and KWave agree, and kdenlive's own is the model: `tmp/previous/screenshots/kdenlive/kden3.png` shows the bar at its foot, `kden2.png` two text cells butted with padding and no separator. Messages were stuffed into the tab row in the first place because the returned Pi rig's 1024x600 had no room; the tablet has room. **A LANE ON THE WINDOW'S FOOT IS WHAT THAT REASONING BUILT, AND IT LASTED ONE DAY.** The architect saw it that evening and ruled it off: he prefers the state text on the toolbar he already reads, and the bar duplicated that panel's own foot. THE STATE TEXT IS ROW 8'S OWN CELL NOW, and the whole tenth lane — `status_bar_area`, `status_bar_content_area`, `kStatusBarContentPx`, the three height accessors, `paint_status_bar` and the window-foot seam `kRedesignBottomLine` — is deleted. The vertical stack is EIGHT lanes again, seven top plus the one bottom row on the foot, and gap 2 got the bar's 33 authored px back the same way it had given them.

THE CELL. `| sep | kTransportSepToClockPx | 02:42.608 | kTransportSepToClockPx | <state text> |` — the clock's own separator-to-digits distance read a second time as the digits-to-text distance, ONE constant and no new number, with NO SEPARATOR between them (kden2's way: two runs and padding alone). **THE TWO GAPS ARE INK TO INK** (architect 2026-08-30, who saw `Rendering...` standing about two pixels further from the digits than the separator stands from them): one authored number read twice still reads wrong, because the SIDE BEARINGS fall on opposite sides of it — the clock's cell is an ADVANCE sum whose last column is air, and the sans run opens with its own left bearing, so the right-hand gap carried a digit's right bearing plus a letter's left one that the left-hand gap does not. Measured at 100 %: 9.0 px of ink on the left against 11.625 on the right. So the text's origin is placed so that (clock ink right → text ink left) EQUALS (separator → clock ink left) — the clock's ink edges from its memoised SPECIMEN (never the live timestamp, which would walk the text as the seconds ran) and the text's left bearing from its own shaped run, through the one ink reader `text_shape::ink_extents_px`. No correction is authored as a number; the cell's reserved WIDTH and its damage box stay the advance's. The text is the row's ordinary label ink `kRedesignLabel` at the row's own size on the one sans face, vertically centred on the row's own baseline like the clock's neighbours — not the clock's, whose authored 1 px nudge is a monospace-cell correction. It is CLIPPED, never ellipsised (a cairo rectangle clip, the folder overlay rows' precedent), where the row's right-hand button cluster begins less one `icon_row_pad_x`. The painter is `paint_bottom_row_buttons_and_clock`'s, laid out with the clock it follows; the `h` walk line keeps its own small composer (`history_walk_line`) beside it.

THE CONTENT is exactly the retired bar's LEFT cell: `queue_progress_text` (`Loading...` / `Rendering...` / `Rendering N of M <label>...` / `Updating...`) or the `h` view's walk line (`n/N <label> Scale: [-]… [+]…`). THE TWO CAN COEXIST AND THE WALK LINE WINS — the recorded coexistence, kept: nothing STARTS a render from inside the `h` view (both render chords are off its allowlist since 2026-08-08), but a render or a target preview dispatched BEFORE the visit runs on through it — bare `h` refuses only for a checkpoint in flight, cancels no render and clears no progress text, and `GuiTargetRender` gates on the `T` audio view, which the mode does not move. So the walk line stands while the view does, and the progress line is back the moment it closes.

THE RESOLVED READOUT RETIRED WHOLE with the bar (architect 2026-08-29). It was the bar's RIGHT cell for that one day, the bottom strip's before that and the tab row's chain's in between — `~= 1.28*1.0112 (from a.23 @ 00:19.208)`, the selected pass or reference marker's resolved tempo. Nothing displays a resolved value any more. The parser's own composer went with the readout: `compute_hover_popup_text` is `resolved_marker_payload` now, returning the payload alone plus the source marker's index, its prefixes and its parenthetical provenance deleted (a granted frozen touch, architect approval 2026-08-29).

THE ROW YIELDS WHOLE TO A MODAL, so the state text is HIDDEN while a prompt, a dialog editor, the render player or the picker stands, and the live string is back the instant it closes — architect-accepted at the fold, and the one thing the separate lane bought that the cell does not. The lane's rect covers the clock cell's as a superset, so a route touching both spells them and pays once. ITS CALLERS SHRANK TO THE PROGRESS LINE'S WRITERS: `input_render_dispatch`'s three and `target_render`'s six. Every call that served the READOUT alone — the selection routes, the marker-value writes, iteration mode's two, the flag editor's, the undo restore's, the drags', the trim commits', the propagate tails', the nudge tail's — is deleted with it. ## The two classes

- NORMAL — a small card that leaves on its own `kNotificationMs` (5000 ms, `gui_input.h`, beside `kHoldBeatMs` and deliberately NOT derived from it: a card's life is neither a hold nor a second tap, and Plasma's own default is what it takes; a duration, so it rides no scale) after ITS PUSH — every card is on screen from that instant since the queue retired (2026-08-30), so there is no later surfacing for a clock to wait for — or at its X, or at a BUMP. The pointer resting on it PAUSES the clock (the remaining life is banked at hover-enter and re-armed at hover-leave; the pointer-left hook ends a hover too; glass has no hover and no finger ever holds a clock). A card whose deadline has already passed when the pointer arrives is NOT banked — the deadlines are polled, so a pointer can land in the gap between the deadline and the tick, and hover pauses a clock rather than resurrecting one: that card leaves on the next poll as an unhovered one would.
- CRITICAL — stands until its X is pressed. No clock, and nothing that comes after takes it down: a later success raises nothing and clears nothing, AND NO BUMP EVER REMOVES ONE (architect 2026-08-30: "critical cards keep standing"). The four checkpoint outcomes (`Checkpoint failed: nothing was committed` / `Checkpoint failed: files written but not committed` / `Checkpoint could not be confirmed` / `Checkpoint committed; push failed`) are its only producers.

No remaining-time bar, no actions, no title/body split, no sound. The glyph is what tells the classes apart at a glance: `dialog-information` on a normal card, `dialog-error` on a critical one.

## The look and the placement

The stack sits top-right, `kPanelPadPx`-class air (the folder overlay's `pad_px`) below ROW 1 (the menu row, whose right-floating view bar carries the S+W / T+P / T+W radios) AND THE SAME NUMBER in from the window's right edge — the two margins are ONE constant read twice (architect 2026-08-29; the right margin was `icon_row_pad_x()` for the cards' first day and read wider than the air above them; a card's INTERNAL pad is a different concept and a different number, the one derived pad below) — newest on top, growing DOWN over whatever lies there (the tab row's right stretch, the icon row's empty right, the thin lanes, the waveform). THE STACK IS UNCAPPED AND EVERY CARD IN IT IS VISIBLE (architect 2026-08-30, retiring the three-card cap and the queue with it: "cards bump each other off the screen — newest on top, the oldest leaving; critical cards keep standing"). What limits it is THE ROOM, counted in one-line cards — `notification_capacity(a)` = `floor((room + gap) / (card + gap))`, at least 1, a pure function of the window and the scale like the room itself: 20 at a 1080 px window and 100 %, 11 on the tablet's 1440 px panel at 225 %, far more than the architect will ever stack. A push past that count BUMPS the oldest NORMAL card and nothing else — never a critical one, and never the card just pushed, which is the answer to the act the user has this instant performed (reachable, not theoretical: the capacity is 4 at 1080 px and 350 %, where four checkpoint verdicts can stand). The capacity counts ONE-LINE cards because no pure function of the window can know a line count, so two overflows escape it — a burst of WRAPPED cards, and CRITICALS the bump will not touch — and both take the same answer, THE PAINTER'S CLIP AT THE ROOM'S FOOT: the overflow paints on down and is cut there rather than over the bottom row, and the painter publishes its rects clipped too, so nothing under that foot is claimed by a card either. One rule, not a second cap.

Every constant a card reads, none of its own but TWO (`notifications.h` — `kNotificationMinWidthPx` and `kNotificationMaxLines`; `kNotificationVisibleMax` was a third until the stack went uncapped 2026-08-30 and the room's own capacity replaced it):
- height = `icon_row_content_h_px()` — the icon row's 46: the 32 px button box plus its 7 px margins — THAT IS THE ONE-LINE HEIGHT, and a card of `n` lines is it plus `(n − 1)` face line-heights (`cairo_scaled_font_extents(font).height`, `nearbyint`ed, read once per paint);
- the gap between cards = `kIconBtnGapPx` (2), which the room's capacity count reads too;
- THE PAD = `notification_pad_px()` (7 at 100%), ONE NUMBER FOR ALL SIX DISTANCES (architect 2026-08-30, his first symmetry pass — he saw the X's side margin exceed its top/bottom margin): left edge → glyph box, glyph box → text, text → X box, X box → right edge, top → boxes, boxes → bottom. Nothing is authored for it: it IS `(notification_card_h_px() − kIconBtnPx) / 2`, the icon row's own centering that the card's height already comes from, so a retune of either moves all six together. Where the difference is odd the integer floor puts the extra pixel BELOW the boxes, the icon row's own arithmetic and not a second rule. The glyph and the X each sit in a `kIconBtnPx` (32) box at that pad, the `kIconGlyphPx` (22) glyph at the box's own `(32-22)/2` inset. `icon_row_pad_x()` and the folder overlay's icon-to-name gap `kRowIconGapPx` — the card's two foreign constants until that day — LEFT the painter with it; the overlay's own rows keep their gap, that being their surface;
- width = the content's (four pads, two boxes, the shaped text) clamped to [`kNotificationMinWidthPx` 240 authored px, a third of the window]; on a window narrower than three floors the floor wins;
- ground `kModalFieldGround` #141618 (the player's and the picker's band ground — "that colour stands out"; the dropdown's ground was rejected as "what's already in use throughout") under a 1 px `kRedesignTabLine` #4c4e51 outline (the popup's own border), through the one popup box painter `paint_popup_chrome` at the popup's radius;
- ink `kRedesignLabel`, the one sans at the redesign's size, the FIRST line's baseline the one-line card's through `redesign_baseline` over that first band;
- THE WRAP (architect 2026-08-30): a sentence that does not fit the text's room GROWS DOWNWARD UNDER THE TWO ICONS to at most `kNotificationMaxLines` (3, an authored count — his "a few"). The glyph box and the X box keep the one-line card's placement and NOTHING REFLOWS beside them; each further line sits one line-height lower; the air under the last line is the first line's own by construction, so the one pad still rules every edge. The WIDTH rule is unchanged — the whole sentence's shaped width inside the same clamp — so a card that fitted one line still does. Breaking is GREEDY AT ASCII SPACES ON MEASURED ADVANCES, each candidate line re-shaped as one run through the shaping chokepoint so the run that is measured is the run that is painted (`notification_text_lines`, the one wrap owner, beside the painter); a break's space and any leading spaces are consumed and every other byte is carried verbatim — the lines are substrings, never a rejoin. A SINGLE WORD WIDER THAN THE ROOM stands alone and clips at the run's right edge, and THE LAST PERMITTED LINE TAKES THE WHOLE REMAINDER and clips the same way — no word is ever silently dropped, only cut where the eye can see the cut. No ellipsis (the folder overlay rows' precedent) and no memo: shaping runs at paint, as the overlay's rows already do;
- the X wears the icon button's hover face — the 1 px `kRedesignAccent` outline through `redesign_face_box`, the icon row's own — while the pointer is in its box; the card's body wears no hover face.

The three glyphs are fresh verbatim transcriptions into the roster (`icons.h`, which `kIconCount` counts — 54 at the cards' landing, 55 since the Copy resolved value button's edit-copy later the same day; that constant is the one authority): `status/22/dialog-information` and `status/22/dialog-error` (symlinks in Breeze Dark onto `data-information` / `data-error`, copied resolved into `assets/icons/breeze/`) and `actions/22/window-close`. The two dialog files are TWO-COLOUR — a rounded plate in a scheme class (`.ColorScheme-Accent` #3daee9, `.ColorScheme-NegativeText` #da4453: the roster's existing `kIconAccent` and `kIconNegativeText`) under a glyph in the literal `#fff` — and the roster paints each path in the table's own ink, so the card's painter colours nothing: the plate is Breeze's own blue or red. Their plates are `<rect rx="2">` elements and take the table's four-number derivation (the `<rect>` precedent tool-rect-selection set), the glyph paths verbatim.

## The layer

Cards paint in `on_redraw`'s step 13, AFTER the flag editor's box and BEFORE the dropdown — above every lane, the waveform, the keyboard slot and the folder overlay's band, BELOW the three surfaces that stay topmost: the dropdown and the tooltip (the two pointer-transient floaters) and the modal row. One painter, `paint_notifications`, unconditional on every frame for the floating surfaces' reason: it PUBLISHES each visible card's rect and X box (`AppState::Notifications::painted`), and a skipped run would strand a stale publication.

## The hit

THE X, AND ONLY THE X, DISMISSES A CARD (architect 2026-08-29, superseding the design's tap-anywhere). A press anywhere on a visible card is consumed whole — arms nothing, moves nothing, lands no playhead, opens no drag, reaches nothing underneath — and the LEFT press on the card's X box dismisses it; any other button over a card is consumed in the veil's own manner. ONE RULE ON BOTH BACKENDS: the router cannot fork on tap versus click (no origin bit rides a press — `GuiInputState` carries modifiers alone), so the rule must be one, and the X's box is the icon row's 32 px button box, already the product's glass target, which is why no finger-fattened body target exists.

The claim sits at `on_button_press`'s head, after the tooltip hide and the menu row's disarm (a press anywhere still does both) and ABOVE EVERY VEIL — the on-screen keyboard's claim, the prompt's, the folder overlay's, the player's, the picker's, the dialog editors' — because a card must be dismissable under any modal. It is not an exception to the veil: a card is not a reach into the veiled surface, it is the message about the act the veil stands over (the record at the retired reach-through's site, `input_pointer.cpp`). The press is the act (content acts the moment its identity is certain; a card press can mean one thing), so the release owes nothing and no arm is left standing.

The geometry a card is HIT by is the geometry it was PAINTED with: the one hit owner reads the publication and then asks the live stack whether that id is still there — which since 2026-08-30 is the whole test, "in the stack", the queue clause having had the queue as its only producer (published geometry may only SELECT; live state decides — `ModalDialogGeometry`'s doctrine) — so a card that expired or was BUMPED between the paint and the press is hit by nothing: it is never dismissed twice, and one already gone is never dismissed at all (`dismiss` asks the same test of its argument), and the press is claimed by nothing and falls through to the surface underneath, whose pixels are what the next paint shows there anyway. A card under the open dropdown's box yields to it (the one pointer-owning surface that paints above the cards), in the one owner `notification_card_at`.

- CURSOR: the zone map's arm 0 — the Arrow over a card, whatever lies under it (the card is opaque to the pointer).
- MOTION: the hover is re-derived at the head of the motion handler, above every branch, like the menu row's exit; the X's face is the only thing it paints. THE OPACITY IS CARRIED BY THE TWO HOVER WALKS A CARD CAN STAND OVER, not by an early return there: the roster's (`recompute_redesign_button_hover`) and the folder overlay band's (`update_folder_overlay_hover`) each ask the one hit owner and answer "nothing under the pointer", so no button beneath a card wears a hover face or starts a tooltip dwell. It has to live at the roster's walk rather than at the motion, because that walk's SECOND caller is the tick and a pointer RESTING on a card is exactly the case; an early return at the motion would also freeze a live gesture whose pointer merely crossed a card.
- WHEEL: swallowed over a card (`wheel_context` answers -1, first and above every veil, as the press claim ranks above them). A card is not a scroll surface and it is opaque, so a detent over one neither reaches the waveform under it nor scrolls a band it overlaps; -1 rather than 0 keeps the platform from growing sub-detent remainder there.
- TOUCH: the one-finger translation delivers the press only once the disambiguation window has resolved to the pointer (a tap, or an off-zone hold or crossing), which is what keeps a two-finger landing off it; and the pan zone answers FALSE on a card (`touch_point_in_pan_zone`), so a finger landing on one resolves to the pointer translation and reaches the claim rather than becoming the phone-model pan.

## The clock and the damage

The clock rides the run loop's existing deadline tick, polled: `GuiNotifications::fire_if_due` at the HEAD of `main.cpp`'s `on_tick`, above every early return that body has — the startup load's, the render player's fork, the loading/blank guard and the playing-only guard. A card is a message about something that has ALREADY happened, so nothing the tick does below it can be a precondition for retiring one, and every one of those returns is a mode a card can stand over: an idle window must still retire an expired card, and the render player's own `No audio device; the wav cannot be played` card must not stand for the whole player session. The tick's software deadlines are FOUR — key repeat and the touch disambiguation window (`GuiInputCore::tick`), the audition's rests, the cards — and none is scheduled; all read `monotonic_ms()`. The same call re-answers the hover from the remembered pointer, so a card that slid up under a resting pointer — which is what a bump or an expiry above it does — starts pausing without a motion.

Damage has one owner, `Viewport::invalidate_notification_stack`: every stack change (a push, the X, an expiry) damages the stack's ROOM — `notification_stack_bound`, the maximum card width from `kPanelPadPx` under row 1 down to that same `kPanelPadPx` above the bottom row's lane — which erases what stood and admits what comes without shaping a glyph off the paint clock; the hover face takes `invalidate_rect` on the X box alone. IT IS THE ROOM AND NO LONGER A TIGHT BOUND since the wrap landed (2026-08-30): it was "three cards of one line each", which a wrapped card outgrows, and no pure function of the window can know a card's line count — that needs a shaped run, and shaping needs the paint's own font. So the damage owner takes the whole space the stack may grow into and THE PAINTER CLIPS TO IT, which is what keeps a contrived stack off the bottom row; a window with no room between row 1 and that lane answers a zero height and paints no card at all.

## The chokepoint, the dedup, the bump

`GuiNotifications::notify` is the ONE writer of a card; every producer below calls it and nothing else pushes. A text identical to a card already in the stack in the same class does not stack a duplicate: THE STACK KEEPS ONE CARD FOR THAT EVENT AND RE-PUSHES IT AT THE TOP with a fresh clock (architect 2026-08-30) — the matching card is removed where it stands, dropping its hover and its banked life exactly as the X's own act does, and the ordinary push then builds the new one and the bump runs as it does for any push. ONE RULE FOR BOTH CLASSES: a critical duplicate moves to the top too, where the dedup used to leave it alone entirely.

THE RE-ARM IN PLACE IS WHAT THAT SUPERSEDES, and the reason is that "in the stack" is not "on screen": an overflowing stack paints past the room's foot and the painter clips it there, so a card can be live and wholly invisible — and a re-arm in place would answer the act the user has this moment performed with nothing visible at all. The top is the one place the answer is certain to be seen, and it is also what a repeat means to the reader: the top says the last time it happened. A HELD KEY firing the same refusal at repeat cadence therefore re-pushes at each repeat — one card, on top, its life starting again at every fire, which is the same picture as a single press held.

THE BUMP replaced the queue on 2026-08-30. A push inserts at the top and starts that card's clock; then, while the stack is past `notification_capacity`, the OLDEST NORMAL card is removed — the walk runs from the back, SKIPS every critical card, and STOPS ABOVE THE CARD JUST PUSHED, so the two things that never leave at a push are a critical card (by the ruling) and the sentence answering the act the user has this moment performed (by that sentence's whole reason for existing). When neither leaves a victim the loop simply stops and the overflow paints past the room's foot, where the painter's clip cuts it. A bumped card that was hovered drops the hover. NOTHING WAITS UNSEEN any more: `expiry_ms` 0 means "no clock" and belongs to critical cards alone, `notification_visible` is "in the stack", and `start_visible_clocks` / `is_visible_index` are deleted with the queue that produced them.

The stack is a member of the per-project `AppState`, so a reopen starts with an empty stack by construction — the chip's own per-project scope, and no clear site exists because none is needed.

## What is notified, and what is not

NORMAL cards, every one a sentence answering an act or reporting a background act's outcome (the `notify` callers, re-grepped 2026-08-29):
- the three phase-reset pastes' `Stopped at …` reports (`phase_reset_propagate.cpp`) and the measure paste's;
- `History is unavailable` — the commit-title editor's Enter into a mode that closed, and the failed-scan arrival that closes the view under the user (with the store's reason appended);
- the `h` view's `'` load refusals, `Load in place refused: …` (the strict sidecar load, the past-EOF wall, the Local walk's number) and `Revert refused: …` — stderr-only until 2026-08-29;
- THE RENDER PLAYER'S LOAD ACT'S OWN REFUSALS, in that same form and since 2026-08-30 (`load_render_entry_in_place`): the running-batch self-guard, a missing or non-regular entry wav, each of the three sidecars failing to read or parse, and the past-EOF wall — one local `refuse` owner composes each sentence once for the card AND for the stderr line, which alone carries the full path. The act said nothing and the CALLER said `Load refused`, a sentence that told the user nothing the dead player did not; that caller now says nothing at all, exactly as the `h` view's arms' caller already did;
- the Open project picker's three refusals (`A checkpoint is still publishing; try again when it finishes`, the project model's sentence, the dry run's reason), the picker staying open;
- Synchronize's refusals (`sync_path is not set` — the device config's key named by its own spelling, and `A synchronization is already running`, a sentence since 2026-08-30) and its worker's every FAILURE — the `Synchronizing to …` dispatch notice was DROPPED at the cards' landing (a process line is state, and the verdict follows within seconds) and A SUCCESS SAYS NOTHING SINCE 2026-08-30 (architect: "if it succeeds, we don't necessarily need [a notice]"), the `Synchronized N files to …` count deleted from the outcome and moved to the silent list below; the two volume-discovery sentences (`No removable volume mounted`, the several-volumes list) went with the discovery itself the same day;
- the render player's `Nothing to play: no renders under render/ or tmp/`, `Only a batch render under tmp/ can be loaded in place; folders and the deliverable carry no recipe`, `Cannot load in place while a render is running` (the load under a running or parked render — silent for the one day the status bar stood at the window's foot and painted through the player's modal, and a card since the state cell moved onto row 8, which the player's own modal row takes whole; `validation_topology.md`'s row), `This wav does not have the source's sample rate and channel count`, `This wav holds no samples`, `No audio device; the wav cannot be played` and the frozen reader's own words (`GuiRenderPlayer::status`, the thin road). THE SIX SHORT ONES WERE LONGER-FORMED on 2026-08-30 (architect, with the wrap: "cryptic one-liners say what they mean") — `No renders to play`, `Only batch renders load in place`, `Render running`, `Not the source's rate and channel count`, `Empty wav`, `No audio device` — none of them a change of meaning, each a sentence a first-time reader can decode;
- `Target render failed` (the preview's failure is an event the user was not watching; a cancelled preview is the product's own doing and says nothing);

## The basename rule

A message that carries a filesystem path names the FILE — its basename, or the batch cell's `N_tag/NN` id — never a full path: the subject is the highlighted row on screen, and the clip is the backstop. Synchronize's sentences name their path RELATIVE TO THE MIRROR'S TWO ROOTS (`<sync path's last component>/<path under it>` on the stick, the path under the project folder in the project — the one composer `shown`, `external_sync.cpp`; the full path stays on stderr), which is `external_sync.h`'s rule 1's naming clause. THE PICKER'S TWO PRODUCERS NAME THEM AT THE WRITER, not at the picker: the PROJECT MODEL's refusals name the FOLDER NAME (`resolve_project`, one `name` for every sentence it composes) and the DRY RUN's name the project folder and the file — `550 - 1/07 - Menuetto.settings` — through the one composer `shown_project_path` (`device_config.h`, beside the `projects_path` key it refuses to spell; `sidecar_present`'s stat refusal takes it too, being one of those reasons by way of the dry run). ONE SENTENCE PER REASON AND NO ROAD FORK: the FATAL roads that also print these words — startup's resolve and `gui_main`'s reopen, both stderr and exit 1 — print the same shortened sentence, the projects path being the device config's one setting and the same for every project on the machine, and startup's own zero case is what names it out loud (`No project under <projects_path>`).
