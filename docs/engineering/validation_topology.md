## The doctrine

Four failure classes, each with ONE owner:

1. **ADVERSARIAL input** (hand-edited/corrupt files, absurd values) → the **LOAD boundary**. First-error hardfail, loud, identical in both binaries ("loadable in both products or neither"). The product contract.
2. **AMBIGUOUS authored state** → the **RESOLVER** (and its phase-reset sibling). Normalizes, never refuses; one stderr line per timestamp per resolve is the signal (directive #11).
3. **LEGAL-BUT-UNHONORABLE state** → the owning stage refuses **CONSTRUCTIVELY** (plan_trim: refusal = render untrimmed, never a failed render).
4. **PROGRAM BUGS (breach)** → the **ENGINE INIT tripwires**: the last point before silently-wrong bytes, validating the actual consumed artifact in both binaries. Breach loudness elsewhere (abort / terminate / stderr+Failed) is justified only where the engine cannot see the breach.
5. **ADVISORY signals**: stderr-and-continue, owning no failure — the fftw-threads single-thread fallback, the framemap-pair write failure (inert future-proofing), the render-env hash mismatch (detection, not prevention). Never fatal.

A predicate may exist at TWO boundaries only when:

- **(a)** the downstream owner cannot catch it — or cannot catch it CLEANLY (sub-frame gap — the engine checks ascent, not spacing; dangling label ref — the engine never consumes refs; apply_post_trim's crop contract — only it holds both buffer and window; the worker's inode-level clobber check — batch paths and write-time races only it can see; map-target FINITENESS — the builder's emission contract, because the orchestrators llrint the final anchor before the engine validates, and llrint on a non-finite value is an invalid conversion with an unspecified result: only the producer refuses it cleanly);
- **(b)** the upstream site has message vocabulary the downstream lacks (the sweep tempo<=0 backstop names the tempo; the engine could only say "not strictly ascending");
- **(c)** an explicit architect symmetry ruling covers it (the past-EOF column pair; the GUI/CLI shared-implementation load checks).

**Type rule**: an error arm (std::expected / optional / bool-false) exists iff a producer exists — reachable, breach-only, or IO, and the classification names which. Total normalizers return plain values (resolve_warp_markers_for_render); partial compilers keep expected (build_warp_frame_map).

**Out-of-topology labels** (things a guard-shaped grep hits that are not guards): LIVE FUNCTIONALITY (cancel checks, capability-loss release tails, the limiter's pass cap), DOMAIN INVARIANT (the clamp chokepoints — constructive, never refuse), DISPLAY-ONLY (`marker_effective` / `compute_hover_popup_text` safe-returns — no bytes, no stderr; only the HOVER half of the second name is history, the row-5 redesign having deleted the hover popup and the whole occlusion resolver with it — the function survives repurposed as the SELECTION READOUT, painted from paint_handler.cpp and its payload copied by Ctrl+C at input_handler.cpp, so the classification is unchanged), INTERACTIVE VOCABULARY (editor red-flash — the same validators the load runs, UI surfacing only: "loadable iff it commits"), ENVIRONMENT PRECONDITION (the CLI's locale/arg checks — guard the launch, not the data), INPUT ROUTING (added 2026-07-28 — the KEYBOARD gates: `read_only_key_blocked`'s allowlist, `modal_editor_key_blocked`, and `text_editor::classify_key`. They decide whether a key reaches a command AT ALL; they never judge data. No error arm, no stderr, no refusal vocabulary, no producer — a gated key is a consumed no-op, and the routing question "does this press run" is upstream of every question this doctrine asks. IT IS A KEYBOARD LABEL AND IT STAYS ONE (architect 2026-08-03): the 2026-08-02 widening had handed it two POINTER members, and keyboard rules should not cover the pointer — both moved to the sibling GESTURE ROUTING below. What the widening added and this label KEEPS is the SETTINGS EDITOR's TRIM ARM read-only refusal: a TYPED route, where Enter commits a `trim=` value, so the pointer/keyboard split does not reach it; it carries a message, unlike a gated key, only because a typed surface must explain a rejection it has already accepted the keystroke for, which changes the surfacing and not the kind. Why it is not INTERACTIVE VOCABULARY instead is recorded at its row in the re-sweep list below. This label carries the routing-gate rule stated once after this list), GESTURE ROUTING (added 2026-08-03 — INPUT ROUTING's POINTER SIBLING, holding the two members that label had acquired: the PLAIN TRIM-BAR PRESS's BAND GATE (`input_pointer.cpp`, the read-only return ahead of `route_trim_bar_press`) and the BOUND-SET CLICK's read-only refusal, which since the 2026-08-03 decider/act split lives in `trim_bound_click_frame` (`input_trim.cpp`) as that function's first gate. THE DEFINING PROPERTY IS INPUT ROUTING'S, ON THE OTHER DEVICE: they decide whether an ACT RUNS AT ALL, they judge no data, and they have no error arm, no stderr, no refusal vocabulary and no producer — a gated press is a silent consumed no-op exactly as a gated key is. IT IS A SIBLING RATHER THAN THE SAME LABEL because the two answer the same question about DIFFERENT INPUT DEVICES: the keyboard label was defined for key dispatch, its rule and its inventories are written about presses reaching commands, and it must not silently acquire pointer members — which is what the widening did and what this split reverses. It is named for what it decides, not for the device, deliberately: a device-shaped name would invite every pointer-side guard to enrol, which is the failure being corrected. A guard is DISQUALIFIED the moment it judges DATA — a value, a window, a domain — rather than permission to run; the moment it produces a message or an error arm; and the moment its subject is where the pointer LANDED rather than whether the act runs, because hit tests, the zone map and the cursor cue derive geometry and gate nothing, and the domain clamps are constructive. The calibration case sits inside one of the members: the STRICTLY-INSIDE guard in the very same decider judges the clicked VALUE against its resting partner, so it is class 3 and not this label (its row is in the re-sweep list). The endcap and bridge press ARMS are deliberately NOT entries of their own — the band gate is the trim bar's ONE read-only decision, and the router's two internal returns, unreachable behind it, were deleted 2026-08-02 under the shared rule below, which this label carries with its instance).

THE TWO ROUTING LABELS SHARE ONE RULE, stated once HERE — not twice — because each now carries exactly one live instance of it, and because out-of-topology means "not a data guard", never "not load-bearing": WHEN A ROUTING GATE IS THE SOLE DEFENSE FOR A MUTATION, THAT FACT IS RECORDED AT THE GATE, and a deeper check covering the same route is either (a)/(b)/(c)-justified or DELETED. INPUT ROUTING's instance is `read_only_key_blocked`'s `is_playhead_step` entry: it is the only read-only defense for BOTH marker-lane arrow routes — the two home-view position nudges, re-derived 2026-07-29 when the third, the W+target tempo-image step, was deleted with the tempo-image family (`position_nudge_prologue` carries no internal check), and it says so. GESTURE ROUTING's landed 2026-08-02 on the pointer side and moved with the label on 2026-08-03: the plain trim-bar press's BAND GATE (`input_pointer.cpp`) is the only read-only defense for the whole trim-bar band — the endcap arm, the bridge arm and the empty band alike — and it says so at the return, naming the router below it as the check-free routee. The 2026-07-28 audit found the converse case and resolved it by deletion — `handle_trim_x` / `handle_trim_shift_x` each carried a `read_only` early return that no press could reach, `x` and `Shift+X` being absent from the allowlist, so the checks were unjustifiable duplicates that also falsified the gate's own "ONLY read-only guard on the keyboard path" inventory. `route_trim_bar_press`'s two internal returns were the same shape and took the same resolution 2026-08-02, its one caller having already returned. Prefer deleting the unreachable check to widening the inventory: one owner per routing decision. The read-only gate's admission standard is itself ruled (architect 2026-07-28) and recorded at the gate: read-only blocks PERSISTENT mutation — what can reach disk or a render — not every store write; bare `t`'s session-only iter wipe is the recorded conforming instance.
