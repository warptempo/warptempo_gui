## Dependencies

Build requires a C++23 toolchain (GCC 12+ or Clang 16+), CMake 3.20+, pkg-config, and the development headers for fftw3. These are the complete dependency set for the headless render interface (`warptempo_cli`); none of the GUI packages below are needed for it.

The default GUI build additionally requires the wayland-scanner tool and the development headers for cairo, wayland-client, wayland-cursor, wayland-protocols, libxkbcommon, and JACK. JACK can be the native jackd2 server or a PipeWire-shimmed JACK provider (modern distros default to the latter).

The `std::expected`-based parser pins the compiler floor at GCC 12 / Clang 16. On distributions whose default compiler is older — Ubuntu 22.04 ships GCC 11, for example — install a newer toolchain (`g++-12` or later) and select it with `-DCMAKE_CXX_COMPILER=g++-12`.

Arch Linux:

```bash
sudo pacman -S base-devel cmake pkgconf \
    cairo fftw \
    wayland wayland-protocols libxkbcommon \
    pipewire-jack
```

Debian / Ubuntu:

```bash
sudo apt install build-essential cmake pkg-config \
    libcairo2-dev libfftw3-dev \
    libwayland-dev wayland-protocols libxkbcommon-dev \
    libjack-jackd2-dev
```

The libwayland-dev package on Debian ships wayland-scanner and the client / cursor headers in one piece.

Fedora:

```bash
sudo dnf install gcc gcc-c++ cmake pkgconf-pkg-config \
    cairo-devel fftw-devel \
    wayland-devel wayland-protocols-devel libxkbcommon-devel \
    pipewire-jack-audio-connection-kit-devel
```

For a headless build — `warptempo_cli` with no GUI — only the core dependencies are needed. Omit the cairo / wayland / wayland-protocols / libxkbcommon / JACK packages from the lists above and configure with `-DWARPTEMPO_BUILD_GUI=OFF` (see the Build section). On Debian / Ubuntu the dependency set reduces to:

```bash
sudo apt install build-essential cmake pkg-config \
    libfftw3-dev
```

A Wayland compositor is required at runtime — there is no X11 backend. Tested compositors include labwc, sway, and Hyprland; GNOME and KDE Wayland sessions should work but are not regularly exercised. The headless CLI needs no compositor and no audio server; it reads and writes files only.

Windows (WSL2): the project builds and runs under WSL2 with a Debian or Ubuntu userland — install the Debian / Ubuntu dependencies above inside the WSL distribution and build normally. The headless CLI behaves as on any Linux host. The GUI is not supported under WSL: WSLg provides a Wayland compositor but routes audio through PulseAudio, not JACK, and the application has no non-JACK audio path.

macOS is not supported: the GUI is a Wayland-native client, and the CLI's render-environment detection is Linux-only (`/proc/self/maps`, glibc identity); macOS builds are not maintained.

## Build

Standard out-of-tree CMake build from the repository root:

```bash
cmake -B build -S .
cmake --build build -j$(nproc)
```

The default build produces one binary: the `warptempo_gui` application (Cairo/Wayland front end over the in-tree parser, engine, prepost, and audio-io sources; all audio container I/O is in-tree — WAV only, no third-party codec). There are no library archives — each binary compiles the shared source lists directly. `-O3 -march=native` is always on for GCC and Clang, so every binary is tuned for the host CPU and is not portable across machines; rebuild on the target host. A rebuilt binary is also a new rendering reference: its output is equivalent to, but not byte-identical with, the previous build's (see Reproducibility below).

One opt-in binary, default OFF:

`warptempo_cli` (`-DWARPTEMPO_BUILD_CLI=ON`) is the headless insurance render path — exactly the terminal `Ctrl+Alt+R`. It takes just the source audio path, reads the project's `.warpmarkers`, `.phaseresetmarkers`, and `.settings` beside it (all three required; the GUI creates them on source load), and writes the warped wav the GUI would render for the same project at the same path — `<title>.wav` beside the source — byte-identical to the GUI by shared pipeline stages. The trim applied is the active tab's (the persisted `active_tab_view` key), matching the GUI. Like the GUI, it also drops the render's frame-map pair into `~/.cache/warptempo_gui/<pid>/` (see Output below).

To build the CLI on a headless host that has none of the GUI's Wayland / Cairo / JACK packages, add `-DWARPTEMPO_BUILD_GUI=OFF -DWARPTEMPO_BUILD_CLI=ON`; the GUI dependency discovery is skipped entirely.

`tools/` holds standalone one-shot utilities with their own CMakeLists, not built with the products — currently `migrate_sidecar_to_frames`, the sole conversion route from the legacy MM:SS.mmm sidecar timestamp format to the current whole-frame format (`migrate_sidecar_to_frames <sample_rate> <file>`, in-place with confirmation).

There is no `make install` target. The binary is self-contained: copy it to anywhere on `$PATH` (typically `~/.local/bin/` or `/usr/local/bin/`) to make it available system-wide.

```bash
install -Dm755 build/warptempo_gui ~/.local/bin/warptempo_gui
```

A `.desktop` file is shipped in `packaging/warptempo_gui.desktop`. To register `warptempo_gui` with the system's application launcher and as a handler for audio files, install it to the user-level application directory and refresh the desktop database:

```bash
install -Dm644 packaging/warptempo_gui.desktop \
    ~/.local/share/applications/warptempo_gui.desktop
update-desktop-database ~/.local/share/applications
```

The shipped `.desktop` file uses the freedesktop `audio-x-generic` icon name, which resolves to whatever the user's active icon theme provides — no icon file is bundled. Replace the `Icon=` line with a different freedesktop name or an absolute path to a custom SVG to override.

## First run

`warptempo_gui` takes a single argument: the path to a source audio file. Source inputs are WAV only (16- or 24-bit PCM) at 44100 Hz or above — lower sample rates refuse to load; anything else — including FLAC, Opus, or MP3 — is converted once at acquisition with an external tool (e.g. ffmpeg) and the converted WAV becomes the project source. Marker and settings files for that audio file live in the same directory as the audio file itself, named by appending `.warpmarkers`, `.phaseresetmarkers`, and `.settings` to the audio file's basename. The sidecars are program-written and strictly validated at load: hand-edited or corrupt sidecar files fail the load with the first error on stderr, and legacy MM:SS.mmm-timestamp sidecars convert once through `tools/migrate_sidecar_to_frames`.

```bash
warptempo_gui "path/to/source.wav"
```

On launch, `warptempo_gui` opens a window, reads any existing `.warpmarkers`, `.phaseresetmarkers`, and `.settings` sidecar files for the given audio file, and presents the source waveform across the full window width. With no sidecar files present, the window opens with a single default warp marker at frame zero carrying tempo `1.00` — an ordinary marker, movable, deletable, and disable-able like any other — and no phase reset markers. With sidecar files present, the prior session state is restored verbatim — viewport, zoom, playhead, active view selectors, and all marker positions and flags.

The examples directory in the repository ships reference movements with complete sidecar files. The Symphony No. 40 mvt I directory (`examples/550 - 1/`) is the recommended first load — it exercises every form and syntax used in the project. The audio file itself is not included (the corpus is commercially licensed); the user supplies the source recording and places it in the example directory under the basename the sidecar files expect.

The conceptual model and hotkey reference are in the sections below.

## Conceptual model

### Engine and frame map

`warptempo_gui` drives a phase vocoder. Internally it is built on a faithful, centered implementation of Prusa-Holighaus phase-gradient heap integration (PGHI) — one phase model. The gradient method enforces phase coherence in both time and frequency without peak-picking or transient detection, which is what lets a high stretch ratio preserve upper-band detail and transient impact rather than dulling them.

FFT size `N` is fixed at `4096`, the canonical PGHI window length, and is no longer a settings field; the synthesis hop `R_s` is derived as `N/4` (75% overlap). At this size the engine's parameters match the authors' released PGHI implementation exactly (`M=2N=8192`, `R_s=1024`, window length 4096; the paper's text states a 4092-sample window, a figure that appears nowhere in the authors' released code), giving the gradient integration its finest frequency resolution and the fullest low-frequency body. The engine inherits the source recording's sample rate. Per-frame phase correction keeps bins coherent within each frame so steady-state content — held strings, sustained winds, room tone — stretches without smearing into a chorused or phasey artifact.

### Relation to the published algorithm

The engine implements Prusa-Holighaus phase-gradient heap integration (ltfatnote050, "Phase Vocoder Done Right") faithfully: origin-centered zero-padded analysis (`M=2N`, matching the paper's ~2x padding), centered finite differences for both phase derivatives, trapezoidal integration in all three propagation directions, the max-heap significance ordering, and the published tolerance (`1e-6`). Where the implementation deviates from or extends the paper, the differences are deliberate and listed here.

- Window length. This engine's defaults match the authors' released reference implementation (github.com/ltfat/pvdoneright) parameter-for-parameter: window length 4096, `M=8192`, synthesis step 1024, tolerance `1e-6`. The paper's text states a 4092-sample window; that figure appears nowhere in the authors' released code, and the discrepancy between the paper and its own implementation is of unknown origin. This engine follows the implementation.
- Variable analysis hop. The paper fixes one analysis step for the whole file (constant stretch ratio). This engine derives the analysis hop per frame from the warp-marker frame map; each half of the centered time-derivative is normalized by its own actual hop, and the frequency-direction step uses the per-frame ratio. This is the extension that makes free-tempo warping possible and is the project's reason to exist.
- Phase resets. The paper has no mid-stream re-grounding; transient handling is left to detection-based methods it cites. This engine's manual phase-reset markers re-seat the synthesis phase to the analysis phase at user-chosen frames — operator judgment in place of detection.
- Output timing contract. The paper does not specify output alignment; this engine pins it. Synthesis trims exactly `N/2` samples from the head — the alignment latency the origin-centered analysis contributes — so source frame 0 maps to output frame 0, and a feature at source frame `S` lands at output sample `tgt(S)` from the frame map. Total output length is the target-frame position of the last source sample. The overlap-add ramps at head and tail are amplitude-only fades that move no alignment. The contract this establishes: any future engine consuming the same warp markers (and, if it supports them, the same phase-reset markers) can match this engine's output 1:1 in frame timing at the start and through the body. The tail's final incomplete-overlap ramp is deliberately outside the contract.
- Remaining boundary choices, unspecified by the paper: the first frame (and the frame each phase reset selects — the frame whose analysis window centers on the authored position) seeds synthesis phase from analysis phase — the seed that serves the timing contract and the reset model above; the first frame's time-derivative uses the forward difference only; the frequency-derivative is one-sided at DC and Nyquist.
- Quiet-bin randomness. The paper assigns unspecified "random values" to sub-tolerance bins. This engine pins the choice: uniform phase in (-pi, pi) from a per-channel deterministically seeded generator, so identical renders are byte-identical — the property the project's verification protocol depends on.
- Real-signal realization. The spectrum is held as the Hermitian half (`M/2+1` bins) rather than the paper's full-`M` complex formulation — mathematically identical for real input and output.

Variable-rate time-stretching with user-placed warp markers exists in other tools — DAWs that ship warp-marker editing on top of their bundled time-stretch algorithm have offered this for years. What separates this project is per-marker tempo locking through label definitions and references. A marker can declare a named label; a later marker can reference that label by name; the two markers and every other reference to the same label render at the same effective tempo, and editing the def's tempo updates every ref that cites it. The mechanism is described in the warp marker model section below. The use case it was built around is the sonata-form exposition/recapitulation relationship in classical orchestral repertoire, where the same musical material returns multiple times across a movement and should hold a coherent tempo relationship across all occurrences regardless of how the surrounding material is edited.

Per-frame phase coherence is what keeps steady-state content clean. It is also exactly what a transient defeats. An attack — oboe entry, pizzicato, timpani strike — is a moment where the spectrum reorganizes within a few hops, and the phase relationships the vocoder has been propagating no longer correspond to the acoustic event arriving. The attack smears across surrounding frames. The mitigation is a phase reset: at a user-chosen position, the synthesis phase is reset rather than propagated, sacrificing local coherence in exchange for a clean transient. Phase reset markers are the authoring surface for this. They are a separate marker collection from warp markers, visible and edited in their own view, because they parameterize a distinct engine concern: warp markers shape the frame map, phase reset markers protect transients.

### View axes

The bottom bar of the window shows three letter pairs: `[S/T] [W/P] [A/B]`. Each pair is an independent toggle. All three combinations are valid; the GUI's state is the product of all three selections plus whatever modes happen to be active on top.

The first pair, **source vs target**, selects the audio domain of the waveform under the playhead. Source view (S) shows the unprocessed source recording with warp markers drawn at the times the user authored them. Target view (T) shows the same audio after the engine has applied the live frame map — the waveform is stretched and compressed to reflect what the render will sound like, with markers drawn at their post-stretch positions. The two views serve different stages of the same authoring task. Source view is where warp markers are authored — placing them, enabling and disabling them, editing their tempo and labels — because pinning a marker's time against an acoustic event, and editing a marker in the very map it deforms, both belong in the unprocessed recording. Target view is where you judge the warp by ear and make the one authoring adjustment that wants to be heard: tempo. Nudge an *owning* marker's tempo up or down with `Up` / `Down` — an owning marker stacked with others on one frame refuses the step here, since that stack renders as a single `1.00`, so fix its tempo back in the warp source view — or drag a marker's flag horizontally to stretch or squish the audio between it and the previous marker — the drag adjusts that *previous* marker's tempo in 0.01 steps, so the dragged marker must follow a tempo-owning marker. Markers stacked on one frame drag as one: grabbing any of them stretches against the marker before the stack. A marker with no earlier marker to stretch against — the very first marker in the store — does not arm the drag; neither does one whose previous marker is inheriting, is a label reference, is itself a stack (which collapses to a single `1.00` owner, so its tempo is not rendered), or owns a label that some earlier marker already references, or supplies the tempo behind such a label through inheriting markers (editing that tempo would move the dragged marker's own image, leaving the drag no stable target). In these cases the click still selects the marker and seats the playhead on it — only the drag is refused. With several markers selected, dragging any of them stretches all of their preceding segments at once: each selected marker's previous marker's tempo moves by the same 0.01 steps, and the group stops together the moment the first of them reaches the 0.25 / 4.00 end. Every selected marker must qualify — if any one of them has no draggable previous marker (the cases above), the drag still arms but holds still: the group is already against that wall. A completed group drag is one undo entry, which is how you take it back. The flag snaps along the tempo grid rather than gliding — 0.01 of tempo per jump — and stops at the 0.25 / 4.00 bracket ends; a completed drag is one undo entry; the drag has no cancel — pressing `Esc` while dragging does nothing at all, and letting go keeps the tempo you dragged to (`Ctrl+Z` reverts it); and the playhead follows the dragged marker's moving image, just as it follows a nudge or a reposition drag. The tempo step and the tempo drag are the only warp edits target view allows; every other warp gesture there is display and navigation only (selection, hover, `Tab` cycling, the readouts), and refuses silently. Target view is always available. Trim narrowed to the section under revision keeps target renders fast enough for this loop to feel immediate.

The second pair, **warp vs phase reset**, selects which marker collection is visible and edited. Warp markers (W) drive the frame map. Phase reset markers (P) protect transients. The two collections are stored, authored, and rendered independently; toggling between them swaps which collection the marker hotkeys operate on but changes nothing else. Authoring proceeds in warp view first, since phase resets have no useful position until the frame map exists. Each collection is edited in its home audio view and only there: warp markers author in source view (see source vs target above), and phase resets author in target view, where the stretch is audible and their `N/2` lead-in aligns to the output-domain overlay. In its away view a collection is display and navigation only — phase resets are read-only in source view, warp markers all-but-tempo in target — so a gesture that would author the away collection refuses silently, exactly as a read-only tab does.

Beyond the data-model difference, both collections want ANTICIPATION — placement a little ahead of the acoustic event rather than dead on it — though for different reasons. Warp markers anticipate to make A/B synchronization reliable: rather than landing exactly on a transient, place the marker slightly earlier, in the fading tail of the previous material. The fading tail is a far more dependable alignment cue than the silence or volume dip just before a transient, because the tail can be placed to start at an audible point, whereas a silence or dip is very hard to line up across the A/B tab pair. The lead-in matters most for label-bearing markers and for markers adjacent to label-bearing ones, where the tempo precision the label mechanism enforces only pays off if the underlying timing is itself precise; it also matters for quiet, slow, or legato onsets where the acoustic event has no sharp attack to pin to — pinning against the louder fade of the prior note beats guessing where the quiet onset begins. The A/B tab pair (described below) is the natural way to set these lead-ins precisely, matching the lead-up across paired sections. Phase reset markers anticipate too, but to give the reset an `N/2` lead-in into the transient. The reset fires at the authored frame — its analysis window centers there — and the overlap-add Hann synthesis takes about `N/2` samples to build the reset's effect to full scale, so authoring the reset `N/2` before the transient lets that lead-in complete right as the transient arrives. In target view, `s` seeds a reset `N/2` before the playhead in target time — clamped to the file start and committed to the nearest whole source frame — and `Space` auditions it by starting playback `N/2` ahead (see the reference); the output-domain overlay depicts the same `N/2` region. The two offsets are deliberate inverses, so dropping with `s` and then pressing `Space` auditions from exactly where the cursor was sitting. This is the only phase-reset drop there is — target view only, like every phase-reset authoring gesture; source view stays read-only for this collection. `N/2` is only the nominal figure, though: if that placement produces an audible discontinuity, nudging the reset with `Left` / `Right` usually clears it — each press moves the reset one painted pixel column (tens of samples even at the finest zoom, more when zoomed out), so drop to the deepest zoom for the smallest available step. Phase resets are still placed only where loud transient content provides masking; quiet, exposed passages should carry one phase reset at their start and nothing else, since a reset during exposed material has nothing to hide behind.

The third pair, **tab A vs tab B**, selects between two snapshots of viewport, zoom, playhead, trim region, and selection. Marker stores and engine settings are shared across both tabs; only navigation state differs. The two-tab layout gets used throughout authoring, not just for aligning sections that exist already. Repeated phrases within a single passage benefit from label-locked tempos, and laying those labels down reliably means parking one tab at the first occurrence and the other at the second, then walking the lead-ins forward together to confirm the matching reference point. The same pattern applies at every scale — phrase repeats, sectional repeats, and the exposition-recapitulation relationship a sonata movement turns on. The second tab earns its place from the first repeated phrase onward.

### Warp marker model

A default warp marker is seeded at the file's first frame on first load, carrying tempo `1.00`. It is an ordinary marker — movable, deletable, disable-able. A render does not require it: when no enabled marker sits at exactly frame zero, the render silently behaves as if a plain `1.00` owner were there (the opening span plays unstretched until the first real marker). More generally, ambiguous marker arrangements never block anything — two or more enabled markers on the same exact frame collapse to a single `1.00` owner for the render, a reference whose definition was deleted renders as `1.00`, and each such normalization prints one stderr line naming the timestamp; what you see in the GUI is your authored store, and the stderr line is the signal that a spot needs attention. The classical phase-vocoder use case — one constant stretch ratio for the whole file — requires no further warp-marker authoring: the global stretch ratio is set entirely through the settings `scale` field, and the frame map remains a single constant. Warp markers as an authoring surface come into play only when the operator wants phrase-level tempo variation. The model below describes that authoring surface.

Each warp marker carries three independent pieces of state.

**Tempo source.** A marker either owns its own tempo or inherits the tempo from the nearest earlier owning marker. An owning marker presents an explicit numeric value; an inheriting marker (a "pass" marker) carries no tempo of its own and resolves its presentation tempo live by walking backward through the marker list. The walk passes over disabled markers and stops at owners; a pass never inherits through a reference — an enabled label reference encountered before any owner ends the walk at the neutral `1.00` instead (a reference owns a duration equation, not a rate, so there is no rate to inherit; the render prints one stderr line per such pass). Because the resolution is live, deleting or disabling an owner re-resolves every dependent pass to the next earlier owner; nothing is frozen on the pass itself.

**Label relationship.** A marker can declare itself a label origin (a `label_def`) or cite an existing label by name (a `label_ref`). A `label_ref` marker inherits its tempo from the named def rather than from positional walk-back. Changing the def's tempo updates every ref that cites it. This is the mechanism for tempo locking across recapitulated material: a sonata-form exposition section receives a `label_def`, the corresponding recapitulation section receives a `label_ref` back to that def, and the two sections will always render at the same tempo regardless of subsequent tempo edits. A reference imposes its definition's target duration on its own segment whatever local stretch ratio that implies, within reason: an implied effective tempo outside `[0.125, 8]` — beyond what any directly authored marker could express — is treated as a mismatch and renders as a plain `1.00` instead, with one stderr line; matching reference segments to their definitions sensibly remains the author's concern. A marker carries at most one of `label_def` or `label_ref`; neither is the unlabeled default.

**Disabled flag.** A marker can be disabled, which silences its tempo contribution as if the marker were not present. Disabling a `label_def` cascades: every `label_ref` citing that def is treated as disabled too. Disabling a non-def marker is local and does not propagate.

An owning marker's tempo is a base value times a scale. The base value is exactly two decimals (the `N.NN` spelling is the on-disk grammar) in the bracket `[0.25, 4.00]` and expresses the headline stretch ratio relative to the source recording — `1.00` is no stretch, `1.05` is 5% faster, `0.95` is 5% slower. The base value's precision is deliberately coarse; the user authors at the resolution they would set a metronome, not finer. The scale is a separate full-precision multiplier in the bracket `[0.5, 2.0]`, defaulting to `1.0000` (written shortest round-trip, padded to at least four decimals). The intended use is fine-tuning a marker's effective tempo to approximate a neighboring section's effective tempo when that neighbor uses a `label_ref` — the user reads off the neighbor's resolved `base*scale` from its hover popup and applies a matching scale to the marker being authored. The user can use scale for anything else they want inside the bracket; out-of-bracket values are rejected at the editor with a red flash. The reference example in `examples/550 - 1/` shows both fields in use across a complete movement.

Phase reset markers carry two pieces of state: a position and a disabled flag. They have no tempo, no labels, no scale, no mode. The engine concern they parameterize is *where to reset* — re-grounding the synthesis phase at the transient that opens the segment. The reset fires at the authored position, with the analysis window centered on it. A marker at 00:00.000 parses, loads, saves, and derives like any other — it lands on the engine's first analysis frame, where synthesis phase is seeded from analysis phase anyway, so it is inert but harmless.

## Output and the limiter

There is no output-format choice: the render product is always the finished wav (there is no `output_format` settings key). As future-proofing, every archival render — GUI `Ctrl+Alt+R`, the sweeps' batch cells, and the CLI — also writes the full frame-map pair beside nothing: `<wav-stem>.warpframemap` and `<wav-stem>.phaseresetframemap` land in `~/.cache/warptempo_gui/<pid>/` (batch cells under a subdirectory mirroring their batch folder), together exactly the engine's input for the full (untrimmed) render, with the phase resets already compiled into the engine's origin-centered query domain. Retrieve them from there between the render and program close; the GUI removes its per-process directory when it exits, CLI-written directories are swept at the next GUI launch, and orphans from dead processes are swept then too, so nothing accumulates. The pair is written all-or-nothing: a write failure removes both files rather than leaving a mixed-generation pair. Trim never affects the pair (always the full maps), and the limiter does not apply to map files.

The wav output is always brought to a delivery ceiling by the built-in limiter — a transparent spectral stage at -0.3 dBFS, then a 0 dBFS lookahead peak limiter with a hard-clip backstop — and written as 24-bit PCM. There is no bypass: the limiter is unconditional and is not a settings key.

## Reproducibility

Rendering is deterministic per machine and binary: the same project rendered twice on the same host with the same build produces byte-identical wav output, every time. This is a hard guarantee — the whole pipeline is fixed-order and free of timing- or scheduling-dependent math.

Across builds and machines the guarantee deliberately weakens to equivalence. A rebuild after a compiler or glibc upgrade, a rebuild on a different CPU, or a build on another machine produces renders that are audibly and structurally identical but not byte-identical: floating-point library results and instruction selection shift by ulps, and on threshold-straddling material the limiter can quantize such a shift into a small localized sample difference (measured at the -38 dBFS / two-samples class on a stress recipe — far below audibility, and ear-verified quality-neutral). Compare renders byte-for-byte only within one host and build; after upgrading or migrating, re-render rather than expecting old files to match.

One related caveat when moving a project directory between machines: a render's recipe fingerprint identifies the full recipe (the naming/provenance settings included) and the render libraries' on-disk identity, not the CPU or build that produced it. Library identities almost never match across machines, so a migrated render normally fails the reuse check and re-renders — but that is incidental protection, not a guarantee. After migrating, re-render anything you intend to keep comparing against.

Render output is hardware-specific (the `-march=native` build targets the host CPU; a different machine is a different reference) and, on one machine, can change when two package families update: the C library's math components (glibc — libm/libmvec) and FFTW (with one residual: the dynamic loader's CPU-dispatch selection ships in the same glibc package as the tracked math libraries, so an ordinary coherent glibc update is expected to move a tracked math library's on-disk identity and so be detected; a hypothetical loader-only byte change is not covered) (Arch: `glibc`, `fftw`; Debian/Ubuntu: `libc6`, `libfftw3-double3`; Fedora: `glibc`, `fftw-libs`). The program detects this instead of asking you to prevent it: an identity fingerprint of each of the four render-relevant libraries — a fold of the mapped file's device, size, modification time, and inode — is recorded in the project settings at save (`libm_hash`, `libmvec_hash`, `fftw3_hash`, `fftw3_threads_hash`), and a load under changed libraries shows an advisory notice — "render libraries changed since last save" — naming the changed libraries. The check compares file identity rather than file contents, so it errs toward flagging: a benign reinstall of an identical library also trips the notice, which is the safe direction (it catches every ordinary upgrade — any change that moves the file's on-disk identity; an in-place byte rewrite that preserves that identity is not something package managers do and is outside what the check caters for). Renders remain fully valid; the notice returns on every load until acknowledged with `o`, which re-stamps the recorded fingerprints (persisted by the next save). Treat an acknowledged change as a reference boundary: renders made before and after may differ at the ulp scale, so re-render anything you intend to keep byte-comparing. GUI and CLI from one build on one system state are byte-identical, unconditionally. Arch Linux is the maintained platform; current glibc distributions (Debian/Ubuntu incl. WSL2, Fedora) are supported best-effort — the library resolver assumes the glibc 2.34+ file layout (older userlands record absent-library sentinels for the math libraries).

The engineering background — why the guarantee is shaped this way, and the performance work that established it — is recorded in `docs/engineering/perf_campaign_2026_07.md`.

## Hotkey reference

The reference is grouped by function. Within the prose of this document a grouped list is the one place a table-like layout earns its place; everything is keyboard unless marked as a mouse gesture. Bindings are case-described: `Ctrl+S` means Control held with the `s` key, `Shift+B` means Shift held with `b`. Where a key does different things in warp view versus phase-reset view, both are given.

Bindings are matched exactly. A key pressed with a modifier this reference does not list for it does nothing at all — there are no near-miss chords that fall back to the unmodified binding, and no gesture has a modified variant that does a related-but-different thing. Two consequences worth knowing: the prompts are case-sensitive, so a `[y]es` prompt wants `y` and not `Y`; and inside a text editor the clipboard chords are `Ctrl+C` / `Ctrl+X` / `Ctrl+V` exactly, so the terminal habit of `Ctrl+Shift+C` does nothing there. Alt is not a keyboard modifier in this program at all any more — it survives only on the mouse, where `Alt`+drag pans and `Alt`+wheel steps the view, and in the five `Ctrl+Alt` chords (the three render chords and the two phase-reset propagate pastes, all documented below).

**Files and session.** The source is chosen on the command line (`warptempo_gui <audio_file>`); there is no in-session file open or drag-and-drop, so switching sources means relaunching, and a load that fails prints the reason and exits. `Ctrl+S` saves all sidecar files. `Ctrl+Q` closes the window, routing through an unsaved-changes prompt when the session is dirty; it also works while the settings prompt or a paste-confirmation prompt is open (it abandons that prompt first, without committing it).

**Playback and playhead.** `Space` starts and stops playback from the cursor to the trim end (`Return` and keypad `Enter` are not playback keys — they open the flag editor on the focused marker; see Warp marker authoring). With a region highlighted, `Space` instead plays from the region's left bound without moving the playhead — an audition, exactly like the lower-half click-to-play; a region sets only the start, so the trim window still governs looping. `Left` and `Right` move the playhead one pixel. With one or more markers selected they move it *in the marker lane* instead: the selected marker (or the whole selection) moves one pixel and the playhead rides along with it, because while a selection exists the marker's own flag is standing in for the playhead — the plain cursor stops being drawn and the focused flag's filled triangle marks the position instead. Dropping the selection hands the playhead back to the waveform, where the arrows step it freely again — any deselecting route does it: a click on the waveform, `Home`/`End`, or clicking the trim chip row. With nothing selected they behave as they always have: move one pixel, drop the focus, dissolve any highlight. Note this is a different thing from the audition scrub on the waveform's lower half, which is unchanged and keeps its own behavior. `Home` and `End` jump the playhead to the trim begin and trim end, and they drop the marker selection as they go — they are taking the playhead out of the marker lane to a spot no flag marks, so the selection goes with it and the ordinary cursor paints again. A keyboard playhead move stops playback; mouse moves are different — a click on the waveform's upper half reseeks live playback to the clicked position instead of stopping it, and a plain drag there selects a region instead of moving the playhead (see Region select and trim); the waveform's lower half is the scrub surface — a click there STOPS playback if a session is running, and a click on a stopped one starts the moving scanner from that spot, so auditioning a new place is stop-then-click (each start is a fresh audition, picking up trim changes) without touching the resting playhead, selection, or highlight; it is a one-shot per click, Ableton-style — holding or dragging does nothing further, and playback simply continues until stopped; `Space` stops it as always (a top-strip click stops playback only when it actually does something — selecting or editing a marker, or setting or highlighting a trim bound; a click that claims no gesture, which is every modified click the strip has no use for, leaves playback alone entirely, as do the empty flag, triangle and marker-text lane spots — and the zoom strip, whose drags and double-click are navigation and never touch playback). `f` toggles follow mode, which scrolls the viewport to keep the playhead in view during playback. Playback speed is set through the settings prompt — `:playback_speed=0.5` — with the ten one-decimal values 0.1 through 1.0 as the only accepted speeds; the default is 0.7. Set in target view, the value stores silently and becomes audible on the return to source view (target view always plays the authored warp at its natural rate).

**Zoom and view.** Zoom is continuous: `=` and `-` (and the plain wheel) step one whole level per press from wherever the zoom rests, and the zoom strip drag below reaches every fractional level in between. The deepest zoom is fixed; the shallowest is the file's own full-song view — zooming all the way out always rests with the whole song visible, exactly filling the width for any file longer than the deepest level's span at the current window width (1.2 s at the 1920 px deployment width; a shorter file rests at the deepest level instead, the remainder of the width showing past-EOF silence). `0` toggles between the working zoom — the fine-tuning view (a zoom level fixes time per pixel, so its span scales with window width: 2.4 s across the waveform at the 1920 px deployment width) — and that full zoom-out. `c` jumps the playhead onto the focused marker when one exists, then snaps to the working zoom centered on it; with no focused marker it just snaps and centers on the playhead. The top strip's uppermost row is the zoom strip: a plain left-drag there swallows the mouse cursor and works both axes at once, anchored on the song position where the click landed — vertical motion zooms (down zooms in) and horizontal motion pans. A dim vertical stem marks the anchor while you drag; if panning pushes it to a screen edge it pins there and takes on that edge's content. Travel is unlimited while the cursor is captured, and on release the cursor reappears at the stem's column. `Ctrl`+drag on the waveform itself does exactly the same as the zoom strip — its full reach without leaving the waveform. Panning alone is `Alt`+drag on the waveform: a smooth grab that also captures the cursor for unlimited travel, the cursor reappearing where the drag left it. Double-click on the zoom strip frames a span: a highlighted region if there is one, otherwise the trim window (completed to the song edges if only one bound is set), otherwise the whole song — with a small margin around a region or trim and none around the whole song. It is one-way and idempotent: a second double-click on the same view does nothing, but any pan or zoom in between re-frames. This differs from the `0` key, which toggles the working zoom against the full-song view; `0` and `c` are unchanged. `PageUp` and `PageDown` page the viewport back and forward by one screen, retaining a small overlap so the edge of the previous view stays visible.

**View toggles.** `t` switches the audio domain between source and target (S/T). A view switch — `t` or `p`, and the `Ctrl+Tab` A/B tab switch too — with several markers selected keeps only the focused one selected, on both sides, with the playhead landed on it: a group left behind in the other view or tab comes back as its focused marker alone. Group work does not cross a switch (select again on the other side, or lean on undo/redo, which re-selects and highlights a whole touched group). `p` switches the marker collection between warp and phase reset (W/P). `o` toggles read-only on the active tab, which locks out marker, tempo, and phase-reset authoring while leaving navigation, playback, and view toggles available. One navigation gesture is not exempt: with a marker selected the horizontal arrows are in the marker lane, where the same press authors, so a locked tab refuses them outright rather than falling back to a plain playhead step. Drop the selection first — a waveform click, or `Home`/`End` — and they navigate again. Read-only means no save: `Ctrl+S` is not admitted in a read-only tab, so with both tabs read-only there is no save at all until a bare `o` unlocks one. One `Ctrl+S` surface is separate and still saves — the one issued while a bottom-strip editor is open. Trim cannot be changed in a read-only tab: the trim chip and bridge drags never enter flight and `x`/`Shift+X` are blocked (region select itself still works — it authors nothing). Both propagation commands — `Ctrl+P` copy and the `Ctrl+Alt+P` pastes — are blocked, as are undo and redo (`Ctrl+Z` / `Ctrl+Shift+Z`); to undo an edit made from a read-only tab, `Ctrl+Tab` to the writable tab first. `Ctrl+Tab` switches the active A/B navigation tab; `Ctrl+Shift+Tab` advances both tabs' marker focus in lockstep and lands on the opposite tab.

**Marker focus and selection.** `Tab` and `Shift+Tab` (the latter also reachable as the ISO left-tab key some layouts send) cycle marker focus forward and backward, moving the playhead onto the focused marker. The view always recenters on the focused marker at the current zoom — follow mode does not gate the cycle. The walk skips disabled markers and operates on whichever collection the W/P toggle has active (trim bounds are not part of the walk — `Home`/`End` jump to them). A plain click on a marker — its flag or its lane text — is the third way to bring the playhead onto a marker: it selects the marker and seats the playhead on it without moving the view at all (unlike `Tab`, which recenters, and `c`, which re-zooms and recenters); it works in both views and both collections, also in a read-only tab. Anything else that changes which marker is focused now brings the playhead along too: opening an editor on a marker (`Enter`, a double-click, or `m`), the `p` swap between the warp and phase-reset collections, `Ctrl+N`, and a propagate paste, which lands on the first reset it created and highlights the created set's span, exactly like undoing a group edit. The reasoning is that with a selection there is no cursor drawn — the focused flag is standing in for the playhead — so a flag that pointed somewhere the playhead was not would simply be lying, and `Space` would play from a spot nothing marked. Opening an editor clears a resting highlight too, exactly as the marker click does, and so do `p` and a propagate paste — of the routes above only `Ctrl+N` leaves a highlight alone unless it was the selection's own span. With several markers selected, a plain flag click on one of them takes effect on release rather than press — wherever a drag could start from that flag: the marker-move drag in the collection's home view, or the group tempo drag in warp target view on a qualifying marker (a writable tab either way; a lane-text click, or a flag click where dragging refuses, collapses at once) — so a drag started from a selected marker's flag acts on the whole selection instead of collapsing it (see Warp marker authoring); releasing without dragging collapses to that one marker as usual. `Alt`+clicking or `Alt`+dragging on a marker does nothing (`Alt`+drag on the waveform pans the view). Clicking an empty spot in the flag or triangle rows works like a waveform click — it clears the marker selection, places the playhead, and a drag from there selects a region; double-clicking an empty spot creates a marker at that position — exactly the `s` drop, so warp gets a copy-previous-tempo marker and phase reset the lead-in seed — in the collection's home view only; a `Shift` press on those rows now does nothing at all; clicking an empty spot in the marker text lane does nothing at all — that lane has no relationship with playback in either direction, like the timestamp lane at the bottom of the window.

**Warp marker authoring (W view, source).** These author warp markers, so they run in warp's home view — warp view in source audio view. In target view every one of them refuses silently except the tempo family — three flavors of one motion, stretching and squishing the waveform: `Left` / `Right` there does NOT move the marker's position (positions are authored in source view only) — it slides the marker's STRETCHED position by adjusting the previous marker's tempo — one pixel where the 0.01 tempo grid allows, otherwise by the smallest 0.01 step in the pressed direction (which can travel several pixels on a long span) — exactly the horizontal tempo drag's action in single steps, with the drag's own requirements (the previous marker must own its tempo — after a pass, a label reference, a disabled marker, or a one-frame stack it refuses; with several selected, all of their previous markers step together, refusing as one if any cannot) — and the two tempo adjustments: `Up` / `Down`, which stays available there on an *owning* marker (a pass or label reference refuses, since it has no tempo of its own to step; an owning marker stacked with others on one frame refuses too — that stack renders as a single `1.00`, so fix its tempo back in the warp source view), and the horizontal tempo drag on a marker whose predecessor owns its tempo (described in the source vs target section above). `s` drops a marker at the playhead copying the previous marker's tempo — so the drop normally splits a section without changing how anything sounds, where a neutral `1.00` drop in the middle of a warped section would audibly change it. Two cases are not silent, both by design. Dropping onto a frame where an enabled marker already sits (which is where the playhead is sitting right after you click a marker) leaves two markers on one frame, and the render collapses any such stack to a single `1.00` — the markers involved turn red immediately, so you see it happen rather than discovering it later. And splitting a *label definition's* section shortens the definition, so every reference to that label changes duration too: a definition's span is its meaning, and halving it halves what the references reproduce. Where there is no usable previous tempo to copy — no earlier marker, a label reference, or a stack of markers on one frame (which renders as a single `1.00`) — the new marker takes `1.00` instead. A pass marker is not one of those cases: it resolves to whatever tempo is actually sounding there, which is exactly what keeps the drop silent. Edit the tempo afterwards in the flag editor if you want a different one. `Ctrl+N` toggles pass (inherit) status on the focused marker. `Ctrl+D` toggles the disabled flag on every selected marker (this works in both W and P views). `Delete` deletes every selected marker — label definitions included, even with live references (the orphaned references render as `1.00` with a stderr line each). `Up` and `Down` nudge the focused marker's tempo by ±0.01 — and with several markers selected they step every selected marker's tempo together by the same ±0.01, refusing the whole press if any selected marker cannot take it: a pass, a label reference, a disabled marker, a stack sharing one frame, or one already at the 0.25 / 4.00 end (the single-marker press keeps its usual behavior, including converting a pass to an owning marker — a label reference is left untouched); a run of group steps is one undo entry, exactly like the single-marker burst. `Left` and `Right` nudge the focused marker's position by one pixel — and with several markers selected, every selected marker moves exactly one pixel on its own column, every press. The trade is deliberate: on-screen movement is always uniform, while the stored spacing quantizes to the pixel grid — at fine zoom that is a fraction of a millisecond and effectively exact, at coarse zoom a pixel is a large slice of audio, and two markers sharing one pixel column will land on the same frame and move together from then on (undo separates them; an exact tie shows the red normalization flags). The group stops as one at the song edges — a press that would push any member past an edge does nothing. A run of group nudges is one undo entry, exactly like the single-marker burst. A plain click on a marker — its flag or its text in the lane above — selects it; dragging the flag moves the marker (no modifier — the drag begins after a few pixels of motion, so a click stays a click; the text is not a drag handle) — and with several markers selected, dragging the flag of any selected marker moves the whole selection together: the spacing between the markers is preserved, the group stops as one at the song edges, the playhead follows the grabbed marker, a highlighted span slides along with the group, and a selected marker's click waits for the release (press-and-release without motion collapses the selection to that marker, exactly the plain click), and the drag has no cancel — `Esc` while dragging does nothing, the release commits where the markers stand, and `Ctrl+Z` is how you put them back; `Return` or keypad `Enter`, or a double-click on the flag or the text, opens the focused marker's flag editor — the canonical-line surface where the whole marker line is edited as text: tempo, `label_def` / `label_ref`, per-marker scale, and (with iteration mode on) the iter bracket; it is the only surface for authoring labels and per-marker scale. The editor opens on a marker-colored background (the invalid-commit flash turns it red) with the whole line selected: typing replaces it, and a bare `Left` or `Right` jumps to the start or end. Inside the editor `Enter` commits (invalid input flashes red and keeps the editor open) and `Esc` exits without committing. While it is open the keyboard belongs to the editor: ordinary text-field gestures work — typing, `Left`/`Right` and `Home`/`End`, `Shift` with those to select, `Ctrl+Left`/`Ctrl+Right` by word, `BackSpace`/`Delete` and their `Ctrl` word-erase forms, `Ctrl+A`, `Ctrl+C`/`Ctrl+X`/`Ctrl+V`, and double-click to select a word. `Ctrl` and `Shift` combine with the motion keys the way they do in any text field. Everything else does nothing at all — `Alt` with anything included, since alt is not a keyboard modifier in this program — so a stray chord can no longer throw the edit away on its way to a command. The two chords that still reach through are `Ctrl+S` (saves, editor stays open) and `Ctrl+Q` (abandons the edit, then the usual close routing). `Esc` is not one of them — it is the editor's own cancel key, handled inside the editor rather than reaching past it. Note there is no undo *inside* the editor: `Ctrl+Z` does nothing there, so an unwanted edit is fixed by retyping or by `Esc` and reopening. The mouse is unaffected — clicking anywhere but the editor's own text closes it without committing, and the click then does its normal work (another marker's flag or text selects that marker; double-clicking the same marker again just reopens the editor). The BPM editor opens with its bracket text selected the same way. Flags carry no text: each marker is a small solid shape — a rectangle with a triangle beneath it whose tip marks the exact frame, centered over it (it may hang up to half off screen at the edges, like the playhead's own triangle, which lives in the same slim lane above the waveform). Marker texts appear in the lane between the trim chips and the flags. When every marker on screen can show its text without one text covering another, all of them show at once — a text longer than nine characters always shows shortened to its first eight plus `…`; hovering the shortened text itself (the text, not the flag) spells it out in full right there, laid over its neighbors while they stay put, and double-clicking the marker (or pressing `Enter` on it) opens the full text in the flag editor the same way. When the visible set does not fit, the lane falls back to one value at a time: the marker you are hovering (a phase reset reads `p.r.`), or else the last-selected marker's value while its flag is on screen — shortened the same way, with the same hover spell-out. An inheriting or label-reference marker additionally shows its resolved value in the bottom strip (the hovered marker's, or the last-selected one's). The flag editor opens in the lane on `Enter` — the text sits on the marker-colored background that flashes red only when an invalid commit is attempted, centered over its marker and always fully on screen. A selected marker also fills the triangle at the bottom of its flag with the waveform's own ink color, so the shape reads as notched while the rest of it keeps whatever color its class calls for — the flag's outline is unchanged. A single selected marker always shows its vertical stem: select it — by click, `Tab`, or any other route — and the stem is there; deselect it, grow the selection past one, or light any span highlight (a region, or the trim window's highlight from the chip row), and it goes — the highlight is the playhead stretched into a span, and only one of the two shows at a time; the marker stays selected and its flag keeps the filled triangle, and the stem returns the moment the highlight clears. The stem is the one-marker focus cue (a multi-marker selection shows the span highlight instead — the same cue, spread), it tracks the flag live while you drag, and disabled markers render in a muted opaque color of their own (selecting one keeps both muted halves — the rectangle and the outline are never masked by selection; it takes the ink triangle like any selected marker, and also reads from the stem, the paint order, and the playhead landing on it). Selecting markers also shifts the playhead's look: with any markers selected the playhead cursor tucks fully behind the selection — its line coincides with the selected marker's stem and its triangle hides behind the marker flag, so the focus cue you see is the single marker's stem, or the span highlight for a group (playback still launches from the resting playhead as normal, the phase-reset lead-in audition included); clicking the waveform deselects and the full playhead returns in the same color (the triangle slips underneath any marker flag it coincides with — marker shapes always paint over the playhead's). A marker that renders as the fallback tempo `1.00` paints its flag red — a `label_ref` to a missing or out-of-range label, a pass that ends up inheriting from a reference, or a stack of markers sharing one frame (which collapse to a single `1.00`, the whole stack reddening as one) — and selecting it does not take that red away — selection never replaces a marker's class colors, so a red flag keeps its red rectangle and ring and its warning is never masked (it takes the ink triangle, like any selected marker); the same red marks a stack of coincident phase resets. The red is a live display cue, so a red stack you drag apart stays red until you release. In a read-only tab flag clicks still select and seat the playhead (dragging and the editor refuse); `Shift`+flag-click selects an inclusive range, file-manager style: it selects every marker between the focused marker — the one last clicked, plain or `Shift` — and the clicked one, in either direction, with the clicked marker becoming the new focus and the playhead seating on it — `Space` still auditions from the range's start, because a highlighted span always plays from its left edge; with nothing focused it just selects and anchors on the clicked marker. `Ctrl`+flag-click toggles one marker's membership in the selection, seating the playhead on whichever marker ends up focused — emptying the selection leaves the playhead where it is. A plain marker click seats the playhead on that marker, and a `Shift`-range or `Ctrl`-toggle click seats it on the marker it leaves focused (`Tab`/`Shift+Tab` and `c` land too, additionally recentering; dropping a new one with `s` seats it there as part of the drop, and a waveform click places the playhead but selects nothing). The playhead then follows the focused marker: a nudge or flag drag carries it along, so `Space` keeps auditioning from the marker (a drag cannot be cancelled — undo is what puts the marker and the playhead back).

**Phase reset authoring (P view, target).** These author phase resets, so they run in phase reset's home view — phase reset view in target audio view. In source view they refuse silently (phase resets are read-only there); selection, hover, `Tab` cycling, and the readouts still work. `s` drops a phase reset in target view only, seeding it `N/2` samples earlier in target time than the playhead (clamped to the file start, snapped to the nearest whole source frame), and the playhead moves back onto the seeded reset — the one drop that relocates the playhead, so the next audition starts at the new reset: the overlap-add Hann synthesis lead-in means a reset's output reaches full scale about `N/2` samples after its authored frame, so placing the reset `N/2` before a perceived transient lands its full-scale output on the transient (this is the offset the output-domain overlay depicts, and it exists only in target view where that overlay does; the overlay shows for a single focused reset and hides while several markers are selected or a highlight is visible). Also in target view only, `Space` auditions that alignment by starting playback `N/2` samples ahead of the playhead without moving it — the resting playhead returns on stop. `Space` does this exactly when a phase reset is *focused* — the same condition that makes the overlay meaningful — so the states that drop the focus (no selected reset, a disabled one, several markers selected, or a visible highlight) also return `Space` to its ordinary behavior of playing from the playhead. It keys on that focus and not on whether the ring is currently *painted*, so scrolling the reset out of view or zooming until the band collapses does not change what `Space` does. `Ctrl+D` toggles the disabled flag on every selected phase reset. `Delete` deletes every selected phase reset. `Left` and `Right` nudge the focused phase reset by one pixel — and with several selected they move the whole selection together by the same step, refusing the press wholesale if any selected reset would leave the song; a run of group nudges is one undo entry, exactly like the single-marker burst.

**Phase-reset propagation (W view, anchored on a warp-marker selection).** These copy a labeled region's phase-reset layout from one occurrence of a label to another. `Ctrl+P` copies: with one or more warp markers selected, it captures the phase-reset layout of each selected marker's own section into the session clipboard — a marker's section runs to the next marker, the final marker's to the end of the song; the selected markers must form one consecutive run (unlabeled markers inside it simply contribute nothing), and a disabled selected marker contributes nothing either. `Ctrl+Alt+P` pastes: anchored on one selected warp marker, it materializes the clipboard's resets onto the destination region, scaled to the destination's durations, after a confirmation prompt. `Ctrl+Alt+Shift+P` pastes state only: it aligns the enabled/disabled state of the destination region's resets to the clipboard, in order, without moving anything and without a prompt. All three apply a 100 ms tolerance when deciding which block a phase reset belongs to: a reset falling within 100 ms before a block's owning warp marker counts as part of that block rather than the one before it. Copy captures such a reset with the block, and paste reproduces it at the same offset before the destination marker (clamped to the start of the file if that offset would fall before time zero). The tolerance is a fixed value, independent of the engine window size. All three are warp-view gestures and work from either audio view — propagate is the one authoring action that starts in the warp view and ends in the phase-reset target view: on completion it drops you into target view with the phase-reset collection active. `Ctrl+Alt+P`, when it materializes at least one reset, selects exactly those it just created — the first one focused, the playhead on it, and the created set's span highlighted, exactly like undoing a group edit — so you can inspect the result by eye without an undo round-trip; `Ctrl+Alt+Shift+P` (it only flips flags on existing resets, creating none) and a `Ctrl+Alt+P` run that materializes nothing (an anchor with no eligible destination blocks) instead leave the phase-reset view's restored selection in place, collapsed to its focused reset if it was a group, with the playhead landed on it. They silently do nothing on an empty clipboard or the wrong selection count.

**Region select and trim.** A plain drag on the waveform's upper half selects a region: the span's background lifts to a lighter shade — the waveform ink itself is unchanged, only the ground behind it recolors — extending live as you drag — it selects no markers (selection flows one way: selected markers can define a highlight, a highlight never selects markers) (the lower half scrubs playback instead — see Playback and playhead). A released highlight narrower than the drag threshold (a few pixels) dissolves — hand jitter never leaves a sliver window. The press first places the playhead at the click and clears the marker selection (as any plain upper-half click does); the drag then extends the region from that point without moving the playhead further, leaving the marker selection empty throughout. While the region is active the playhead cursor splits into two half-triangles, one sitting on each bound — marker flags paint over them, so a highlight defined by a marker selection hides its halves under the two end markers and the lifted background itself is the read — and `Space` plays from the left bound with the moving scanner line still visible across the span, the resting playhead staying exactly where it was (the trim, if set, still governs looping). The region is session-only, and selection flows strictly downward into it: selecting two or more markers by `Shift`-range or `Ctrl`-toggle highlights the span between the earliest and latest selected, but a drag-formed highlight selects nothing — clicking a marker inside one simply selects that marker and dissolves the highlight — always, even when the playhead already sits on that exact marker (`Space` plays a highlighted span from its left edge while it lasts). Dragging one of the selected markers moves the whole group, and the highlighted span slides with it, resting on the group's new span at release — there is no cancel: `Esc` mid-drag does nothing and the release commits, undo being the way back; the group tempo drag and group tempo steps in target view move the span the same way, following the markers' stretched positions. A plain press on the waveform dissolves it the moment the button goes down (strip clicks off any marker leave it alone). `Esc` does nothing to a highlight or a selection at all — it is not a selection or region key (see General) — so a highlight rests until something clears it: the highlight clears on file load, tab switch, the S/T view switch, undo and redo, a settings commit of an engine key (the sound changed under it, and a several-marker selection standing there keeps only its focused marker; the trim keys instead move their own highlight with the bounds), and any command that jumps the playhead — `Tab`, `c`, `0`, the arrow keys, `Home`/`End`, a typed `playhead_cursor` commit for the active tab (which, like `Home`/`End`, also drops the selection — the jump lands on no marker), a plain click on a marker, or dropping one with `s` or the empty-lane double-click (a `Shift`-range or `Ctrl`-toggle click that leaves two or more markers selected immediately re-highlights their span; playing from the region with `Space` keeps it, of course). A plain click on the waveform places the playhead and clears the marker selection (it never selects one); a `Shift` press on the waveform forms a region in one click: with no markers selected it highlights from the playhead to the click; with markers selected it demotes the selection into a region — the markers deselect and the highlight spans from the selected marker furthest from the click to the click (a click inside the selected series takes the longer side). The one-click region moves no playhead, and holding the press turns it into a drag: the far end (the playhead, or that furthest marker) stays anchored while the click side follows the pointer until release — `Esc` while dragging does nothing, so the drag simply carries on and the release rests the span it grew; a span narrower than the drag threshold forms nothing on a motionless release (dragging out from a sub-threshold press still grows a region from the anchor). Deleting two or more selected markers demotes the same way: the region spanning the deleted positions lights up (undo restores the markers; the highlight snaps to the restored group's span). Trim bounds are not selectable items — no clicking, no `Tab` focus, no `Delete`; the whole interface is `x`/`Shift+X`, the chip and bridge drags, and `Home`/`End` navigation. The chip row is also clickable: a plain click anywhere on it (with both bounds set) highlights the trim window — and CLEARS THE MARKER SELECTION as it does: clicking trim means you are ready to move on, the same way clicking the waveform deselects. Every route that sets or highlights the trim window deselects like that — the plain chip click, the two bound-set clicks, `x`, and the chip and bridge drags — so a trim highlight always rests with nothing selected. A click that refuses changes nothing at all: with no trim set, or in a read-only tab for the bound sets, the press leaves your selection exactly as it was. The playhead is never touched by any of it. `Ctrl`+click moves the begin bound to that spot and `Ctrl+Shift`+click the end bound — and holding after the click drags the bound onward like a chip drag; both adjust an existing trim window only, doing nothing when no trim is set (a bound moved onto or across its partner dissolves both, as always), and dragging a chip or the pair slides the highlight along with the moving window. None of it can be cancelled: `Esc` mid-gesture does nothing, the release keeps the bounds where they stand, and trim sits outside undo — so a trim edit is committed the moment you make it. Bare `x` sets the trim from the highlight: with a region highlighted it trims to it — always, replacing any existing trim — the highlight stays, now coupled to the trim window, and the marker selection is cleared with it (`x` sets trim, so it deselects like every other trim setter). With no highlight it does nothing, and it also does nothing when the highlight is too narrow to make a window — a span so compressed that both ends land on the same source frame is refused outright rather than committing a zero-length trim, which would destroy the bounds silently. `Shift+X` clears the trim (nothing set, nothing happens); if the standing highlight was the trim's own, it dissolves with the window, while a highlight you drew or a selection's extent stays. `Shift+X` is the one trim key that does NOT deselect — it clears a window rather than setting one, and a trim highlight was resting beside an empty selection anyway. A plain left-drag on a bound's chip drags that bound, and in the chip row — the second row, just below the zoom strip, marked by the marker-colored bar between the chips when both bounds are set — that bar is the "inside the trim window" signal (the waveform outside the trim no longer dims) — a plain drag strictly between the two chips drags the pair as a fixed-width window, preserving the gap during motion (a drag begins after a few pixels of motion, so a click commits nothing; the marker flag row below is not part of the trim grab region, and bounds are grabbed by their chips — the waveform is for the playhead and region select, never a trim handle). Every trim drag requires both bounds set: a lone bound (reachable through the settings editor's per-bound clear or a load) is gesture-inert — it still paints, `Home`/`End` still navigate to it, and `Shift+X` or the settings editor still clears it — and it renders its completed window: a missing begin fills in at the song start, a missing end at the song end, so a lone begin trims only the tail and a lone end only the head. On the waveform between the bounds `Alt`+drag pans the view like anywhere else on the waveform (the pair's handle is the span between the chips). Trim bounds never intercept plain or `Shift` presses (a click over a bound is just a waveform click). Release snaps each moved bound independently to its painted pixel column, so the stored gap can change by at most one source frame. A bound committed onto or across its partner — equal or crossed — destroys both bounds: the pair vanishes rather than resting inverted (mid-drag crossing is still free; only the release commits). Only two trims fall back to an untrimmed render, each with one stderr line: a lone end sitting on the very first frame, whose completed window collapses to nothing, and any trim — a set pair or a completed lone window — whose rendered span would round below one output sample. Trim is per-tab and excluded from undo and redo.

**Modes (W view, source).** Both modes author warp tempo, so both are entered from warp's home view — warp view in source audio view — and refuse silently in target view. `i` toggles iteration mode; exiting the mode — by any route — clears every iteration bracket, so a bracket exists only while iteration mode paints it. `m` opens BPM mode on the selected markers' sections as a bottom-strip editor session: `Esc` abandons it (wiping the typed values), `Enter` dispatches the sweep and closes it; while the editor is open, `m` is just a typed character. Iteration and BPM modes are mutually exclusive — entering BPM mode forces iteration mode off (clearing its brackets). Both are front ends for the same workflow: render a spread of variants, audition them in an external player (`l`), and commit the one you want as the new baseline (`'`; the render commands below cover listening and committing). They differ only in what they vary and how the variant is expressed.

Iteration mode varies a marker's base tempo by a small additive offset. With the mode on, a warp marker's flag edit accepts an inline bracket appended after the tempo token, `+[<start>,<end>]` with `start <= end` — for example `+[-0.02,+0.00]`, which enumerates the offsets −0.02, −0.01, and 0.00 (the range is stepped in 0.01 increments, inclusive of both ends; each bound is a signed two-decimal value within `[-4.00, +4.00]`, and the base tempo plus either bound must stay inside the tempo bracket `[0.25, 4.00]` or the commit red-flashes). Several markers can each carry a range; `Ctrl+Alt+I` then renders the full Cartesian product, one file per combination, each marker's offset added in exact cents to its own base tempo for that cell, into a batch folder under `renders/` ready to audition. To sweep a marker across a single value rather than a range, give a degenerate range like `+[-0.02,-0.02]` — it is still an iteration cell and still renders through `Ctrl+Alt+I`. The sign is mandatory and exactly two decimal places are required on every value, so `+0.00`, not `0` or `0.0`. Brackets are session-only and never serialized: removing the bracket (or committing the all-zero `+[+0.00,+0.00]`) clears the marker's range, and exiting iteration mode clears them all — a tempo change never clears a bracket on its own, whether from an `Up`/`Down` step or a flag-editor commit, so a later step under a live bracket is not re-gated (staleness accepted, backstopped by the render's own refusal and the strict parse at commit).

BPM mode varies the rendered tempo of an explicit span to hit a range of target BPMs. Select one or more consecutive warp markers and press `m`: the first selected marker owns the span, and the span covers each selected marker's own section — a marker's section runs to the next marker, and the final marker in the piece owns the section to the end of the song — so the last selected marker's section is included. Selected markers inside the span may be disabled; each is converted to a pass in every sweep cell, so the span renders at one tempo. None of the markers in or bounding the span may be a `label_ref` — the span's tempo is rewritten on commit and a reference takes its tempo from its definition — and the owning marker may not be disabled, so `m` is a silent no-op in those cases (a selection that is not one consecutive run is also a no-op). The bottom-strip editor is authored as `<beats>@[<lo>,<hi>]` — for example `36@[210,220]`, meaning the span spans 36 beats and should be rendered once at each integer BPM from 210 to 220 inclusive (BPM bounds live in `[10, 400]`). The beat count and the span's measured duration (owner marker to the span end — the next marker after the selection, or the end of the song) fix the source tempo, so each target BPM resolves to a concrete base-tempo-and-scale pair; a target whose derived base tempo would leave the tempo bracket is refused, never clamped. `Enter` renders the sweep — one file per integer BPM in the range — into a batch folder under `renders/`, wipes the typed values, and closes the mode; re-entering always seeds blank. Committing a BPM cell (via `'`, by the cell's wav entry name — the same commit path as any render) rewrites the span's tempo: the entry's frozen sidecars already carry it, so the owner takes the computed base tempo, every span-internal marker (including disabled ones) is set to pass so the span renders at one tempo, the marker after the span (when the span does not run to the song end) is left unchanged, and the computed scale (full double precision) is written to the settings as the global scale. The settings `bpm` field records the committed render as a descriptor — for example `36 beats @ 220 bpm from 00:32.008 to 00:46.562` — for provenance only; the engine never reads it, though like every engine setting it participates in render identity, so editing it makes the next render fresh.

**Settings.** Bare `;` opens the settings prompt in the bottom strip, where a line is typed as `key=value`. The prompt accepts any printable character, and the line is split on the first `=`, so the value may itself contain `=` — a `url=` carrying a `?v=` query parameter, for instance, commits intact. The key must be whitespace-free; keys with a restricted vocabulary reject an out-of-vocabulary value at commit with a red outline. EVERY key that can appear in a `.settings` file is settable here — the engine keys, and every GUI-kind key (`playback_speed`, `follow`, `font_size`, `audio_player`, `active_audio_view`, `active_markers_view`, `active_tab_view`, and the per-tab `viewport_start` / `zoom` / `playhead_cursor` / `trim_begin` / `trim_end` / `read_only`). A GUI-kind commit behaves exactly like the key's own gesture: it runs the same code, takes effect immediately, is not undoable, and persists on the next `Ctrl+S`. Values follow the file's strict vocabulary (playback speeds are the ten one-decimal values 0.1–1.0; zoom must be a valid zoom level; trim bounds are whole source-frame numbers inside the audio, with `-1` clearing the bound and a bound committed onto or across its partner clearing both — the `.settings` file mirrors this, always carrying the four trim lines with `-1` meaning unset; trim in a read-only tab refuses). Keys for the inactive tab write that tab's stored state, picked up when you switch to it. With a key typed and the value left empty (`notes=`), `Tab` fills in that key's current value for recall and editing — this works for every settable key — and leaves a value you have already started typing untouched. `Enter` commits, `Esc` cancels, and `Ctrl+Q` abandons the edit and closes.

Four settings fields are provenance: they are carried in `.settings` and never read by the engine, though like every engine setting they participate in render identity, so editing one makes the next render fresh. (Of the GUI-kind keys, the preference keys — playback speed, follow, font size, the audio player — are not part of render identity and never force a render; the per-tab trim keys are part of the render recipe, and a trim or view-state commit re-previews exactly like its gesture.) `bpm` is written automatically when a BPM-sweep cell is committed (described under the render dispatches above); `url`, `notes`, and `cover` are free-text fields the operator types through the settings prompt. None of the four is value-validated — any value is accepted verbatim, including empty — though like every settings key the line itself is required (every canonical key is present in every `.settings`; a missing key fails the load). They annotate a render with its source, its target, working notes, or a cover-art reference. Each holds a single line, since the `.settings` format is line-based.

**Render dispatch.** `Ctrl+Alt+R` is the pipeline's destination: a single one-shot render of the current authoring state, written next to the source as a sibling — the wav deliverable named by the `title` setting (`<title>.wav`); the frame-map pair goes to `~/.cache` as described under Output above. It is the only render that lands beside the source rather than inside a `renders/` batch folder — the final deliverable, as opposed to the audition outputs the other dispatches produce. A render dispatch kills the running render and takes its place; `Esc` stops both the running render and any parked command behind it. (A dispatch identical to the running render simply restarts it — the `.fingerprint` reuse below then makes that restart finish immediately when the deliverable is already current, so an accidental re-press is still cheap.) An output path that resolves to the source audio itself is refused with an error rather than overwritten (change the `title` setting). Before rewriting an existing same-title deliverable, it checks that output's `.fingerprint` sidecar: if the sidecar exactly matches the current authoring/render inputs and the on-disk wav identity, the render finishes immediately and writes nothing, because the deliverable has proved it is already current. If there is no matching `.fingerprint` sidecar, the normal render/reuse path publishes the current deliverable through staging and rename, so an old same-title output can still be replaced, but only after that identity check fails. A `.fingerprint` file appears next to deliverable wavs and records the exact render identity used for reuse: source file identity, markers, phase resets, the full engine settings block — the naming/provenance fields (title, bpm, notes, url, cover) included — and trim bounds. Editing any engine setting, provenance included, makes the next dispatch render fresh; those fields change about once per movement, so the occasional redundant re-render is the accepted price of one simple identity rule. It is not audio and is safe to delete; deleting it just prevents that output from proving it is already up to date, so a later `Ctrl+Alt+R` may re-render or republish. Do not hand-edit it. The batch dispatches stage candidates for auditioning rather than producing the final file: the iteration and BPM sweeps are dispatched from their own modes (documented in the Modes group above) and render into a numbered batch folder under `renders/` (`N_iterations` / `N_bpm`; pressing `Esc` between entries drops the remainder). `Ctrl+Alt+Shift+R` renders one miscellaneous cell: the exact same render `Ctrl+Alt+R` would produce, but written as the next numbered wav inside the most recent `N_miscellaneous` folder (a new one is created when the most recent batch folder is not miscellaneous), so one-off keepers accumulate as ordinary `renders/` entries — `l`-auditionable and `'`-adoptable — instead of overwriting the deliverable beside the source. Pressing it again with unchanged state adds another identical cell (cheaply, via the render cache).

**Auditioning renders (`l`).** There is no in-app render browser; you audition the batch outputs in an external player. `l` ("Listen to renders") launches the program named by the `audio_player` setting with every wav under `renders/`, in numeric order (batch folder, then entry). Set `audio_player` in the settings editor — `:audio_player=audacious` (a binary name on `$PATH`) or an absolute path — which commits it directly and persists it on the next `Ctrl+S`; `:audio_player=` (empty value) clears it. It is a global launch preference, also loaded from `.settings` at startup. With no `audio_player` set, or no renders present, `l` shows a one-line bottom-strip status and does nothing. The launch is fire-and-forget — the GUI's own playback is unaffected, and closing the external player has no effect on the GUI.

**Committing a render (`'`).** `'` opens the `commit: ./renders/` bottom-strip editor: type an entry's name and press `Enter` to adopt that render as the new authoring baseline. An entry is named by its path relative to `renders/`: `<batch-folder>/<basename>.wav` (e.g. `1_iterations/01.wav`), always folder-qualified. `Tab` autocompletes: it extends what you have typed to the longest common prefix of the matching entries, completing fully when only one matches, and does nothing when the prefix is ambiguous or matches nothing. The line red-flashes (and stays open) if the name resolves to zero or several entries, or if the chosen entry's wav is missing or a sidecar is malformed. The editor is refused while a render is running or parked (`Esc` cancels the render first), and does not open with no source loaded or an empty `renders/`.

On a successful commit the entry's frozen dispatch-time `.settings` is applied to the live state exactly as a fresh source load of those sidecars would be — markers, engine block, recipe trim, both tab bands, the tab letter, the W/P mode, and the session prefs, with nothing carved out — landing in TARGET view on the entry's dispatch tab at the exact position the project had when the render was QUEUED. The adopt is one cross-file undo entry (the marker pair plus the pre-commit engine settings; the inherited prefs and view state ride outside undo). After it succeeds the `renders/` folder is wiped — the batch outputs are stale once the baseline changes, and the committed render survives through the render cache, not as a folder artifact. Regular renders, iteration cells, and BPM-sweep cells all commit through this same path — for a BPM-sweep cell the frozen sidecars already carry the rewritten span markers, global scale, and `bpm` descriptor, so those commit as part of the same full snapshot.

**General.** `Ctrl+Z` undoes and `Ctrl+Shift+Z` redoes; settings edits and marker edits participate in the same undo history. Undo and redo show you what changed. The touched markers are re-selected (an undone insertion has no surviving marker, so that case clears the selection instead), and if the edit belongs to the other tab the view switches to that tab first. A single touched marker gets the full marker-click treatment: the playhead lands on it (any resting highlight clears — undo and redo start you from a clean span state), the viewport recenters only if it is offscreen, and its stem shows — the ordinary single-selection cue, staying for as long as that marker is the one selected marker and no highlight is active. A change that touched several markers lands the playhead on the group's earliest member and lights the region highlight over the restored group — the highlight's left half-triangle sits on that earliest member — scrolling it into view whenever part of it sits offscreen, zooming out only when the group cannot fit at the current zoom. Trim changes are excluded from undo and redo. Held nudges and tempo steps coalesce: holding the key down (`Left`/`Right` nudges — the target-view tempo-driven slide included — or `Up`/`Down` tempo steps, group steps included) collapses the whole held run into one undo entry, so a single `Ctrl+Z` reverts it; separate presses are separate entries, however quick. **`Esc` does exactly three things**, and nothing else anywhere: it closes an open editor without committing, it dismisses a prompt (taking its rightmost response), and it cancels all render work in one press — the running render, a parked render command waiting behind it, and a pending target-view preview. An open editor or a prompt takes priority, so the first `Esc` closes that and the next one cancels render work. While a pointer gesture is in flight `Esc` is swallowed and does nothing: gestures have no cancel — let go and the gesture commits what stands, then `Ctrl+Z` takes it back (trim, which sits outside undo, commits for good). With nothing open, nothing rendering and nothing being dragged, `Esc` is simply a no-op: it does not deselect markers, does not clear a highlight, and does not move the playhead. To leave a selection, click the waveform or press `Home`/`End`; to clear a highlight, do anything that moves the playhead to a point (a waveform click, an arrow step, `Tab`, `c`) or consume it with `x`.

**Mouse.** The scroll wheel zooms; held with `Alt` it pans the viewport, over the waveform and the whole top strip alike. A plain drag on the waveform selects a region, and `Ctrl`+drag zooms and pans the view like the zoom strip (see Region select and trim, Zoom and view); `Shift`+click on the waveform forms a region from the playhead (or demotes a marker selection), and holding it drags the region's click side live (see Region select and trim); there is no `Ctrl+Alt` pointer or wheel gesture. A single left-click on the waveform's upper half sets the playhead at the click point and clears the marker selection (it never selects one); a click on the lower half scrubs playback — it stops a running session, and on a stopped one the scanner starts there, one-shot per click, the resting playhead staying put (see Playback and playhead); a click on a marker in the top strip — its flag or its lane text, one item — selects that marker and seats the playhead on it without moving the view, and dragging the flag moves the marker with the playhead following — or, when the marker is one of several selected, moves the whole selection together (a flag press on a selected marker commits its click only on release wherever a drag could start there — the move drag in the home view, or the tempo drag in warp target view on a qualifying marker, a writable tab either way — which is what lets the drag keep the group; elsewhere the click collapses at press as always) (double-clicking either part opens the flag editor; `Shift`+clicking range-selects from the focused marker and `Ctrl`+clicking toggles membership, both seating the playhead on the marker they leave focused and highlighting the span of a multi-selection — see Marker focus and selection; `Alt`+clicking or `Alt`+dragging on a marker does nothing) — `Tab`/`Shift+Tab` and `c` also bring the playhead to a marker, recentering the view as they do, a nudge or flag drag carries the playhead along with the focused marker, and dropping a new marker with `s` seats the playhead on it as part of the drop, clearing a resting highlight like any other way of putting the playhead somewhere (see Marker focus and selection). A plain left-drag on the upper half selects a region — never any markers (see Region select and trim). Double-clicking inside any text editor selects the run under the click, the standard desktop way: a word (underscore counts as part of it), a run of punctuation (a `.`, `=`, or `::` selects just that), or a run of spaces — the selection never crosses from one kind into another. Trim bounds are dragged by their begin/end chips and the bridge between them, plain like everything else — a drag begins after a few pixels of motion; the begin chip sits with its left edge on the bound and the end chip with its right edge, so both are fully visible even at the very start and end of the file, each connected to its stem. `Alt`+drag on the waveform pans the view, capturing the cursor for unlimited travel (see Zoom and view). The marker drag and the double-click-to-edit refuse — the flag click still selects — both in a read-only tab and when the marker collection is away from its home audio view (a warp marker in target view, a phase reset in source view; see View axes), with one exception: dragging a warp marker's flag horizontally in target view adjusts the previous marker's tempo instead of moving the marker (the tempo drag — see View axes; it needs a tempo-owning predecessor and a writable tab, and an ineligible press still selects and seats the playhead, arming nothing; with several markers selected it moves all of their previous markers' tempos together, holding still if any selected marker lacks a draggable previous marker); the trim drags refuse in a read-only tab. The `e` key IS the left mouse button: pressing it presses the button at the pointer position, holding it holds the button (so `e`+motion drags, and modifier state rides along exactly as for a physical button), and releasing it releases the button — except while a text editor is open, when `e` types the letter as normal. Modifier state rides along to the button exactly as it would for a physical mouse. The press acts only while the pointer is over the window.
