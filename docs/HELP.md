# warptempo_gui

This is the user guide: install and build, first run, the conceptual model, output and the limiter, and the complete hotkey reference. Reading the conceptual model first will make the reference make sense; the reference is where every key and gesture lives.

## Dependencies

Build requires a C++23 toolchain (GCC 12+ or Clang 16+), CMake 3.20+, pkg-config, and the development headers for fftw3. That is the complete dependency set for the headless render interface (`warptempo_cli`); none of the GUI packages below are needed for it.

The default GUI build additionally requires the wayland-scanner tool and the development headers for cairo, wayland-client, wayland-cursor, wayland-protocols, libxkbcommon, and JACK. JACK can be the native jackd2 server or a PipeWire-shimmed JACK provider (modern distros default to the latter).

The `std::expected`-based parser is what pins the compiler floor at GCC 12 / Clang 16. On distributions whose default compiler is older — Ubuntu 22.04 ships GCC 11, for example — install a newer toolchain (`g++-12` or later) and select it with `-DCMAKE_CXX_COMPILER=g++-12`.

Arch Linux:

```bash
sudo pacman -S base-devel cmake pkgconf \
    cairo fftw \
    wayland wayland-protocols libxkbcommon \
    pipewire-jack
```

Debian / Ubuntu:

```bash
sudo apt install build-essential cmake pkg-config \
    libcairo2-dev libfftw3-dev \
    libwayland-dev wayland-protocols libxkbcommon-dev \
    libjack-jackd2-dev
```

The libwayland-dev package on Debian ships wayland-scanner and the client / cursor headers in one piece.

Fedora:

```bash
sudo dnf install gcc gcc-c++ cmake pkgconf-pkg-config \
    cairo-devel fftw-devel \
    wayland-devel wayland-protocols-devel libxkbcommon-devel \
    pipewire-jack-audio-connection-kit-devel
```

For a headless build — `warptempo_cli` with no GUI — only the core dependencies are needed. Omit the cairo / wayland / wayland-protocols / libxkbcommon / JACK packages from the lists above and configure with `-DWARPTEMPO_BUILD_GUI=OFF` (see the Build section). On Debian / Ubuntu the dependency set reduces to:

```bash
sudo apt install build-essential cmake pkg-config \
    libfftw3-dev
```

A Wayland compositor is required at runtime — there is no X11 backend — and it must offer server-side window decorations (the xdg-decoration protocol): the GUI exits with an error at startup if the compositor does not offer the protocol. labwc, the compositor the program is developed on, always can; so can the other wlroots-based compositors (sway, Hyprland) and KDE Plasma. GNOME's compositor does not implement the protocol, so the GUI will not start there. The headless CLI needs no compositor and no audio server; it reads and writes files only.

Windows (WSL2): the project builds and runs under WSL2 with a Debian or Ubuntu userland — install the Debian / Ubuntu dependencies above inside the WSL distribution and build normally. The headless CLI behaves as on any Linux host. The GUI is not supported under WSL: WSLg provides a Wayland compositor but routes audio through PulseAudio, and the application has no non-JACK audio path.

macOS is not supported: the GUI is a Wayland-native client and has no macOS build at all. The headless CLI is neither built nor tested there and carries no support claim either.

## Build

Standard out-of-tree CMake build from the repository root:

```bash
cmake -B build -S .
cmake --build build -j$(nproc)
```

The default build produces one binary: the `warptempo_gui` application — a Cairo/Wayland front end over the in-tree parser, engine, prepost, and audio-io sources. All audio container I/O is in-tree, WAV only, with no third-party codec. There are no library archives; each binary compiles the shared source lists directly. `-O3 -march=native -ffp-contract=off` is always on for GCC and Clang, so every binary is tuned for the host CPU and is not portable across machines — rebuild on the target host. A rebuilt binary is not a new rendering reference, though: with the same compiler and the same libraries underneath it, a fresh build renders exactly what the previous one did, byte for byte (see Reproducibility below).

One opt-in binary, default OFF: `warptempo_cli` (`-DWARPTEMPO_BUILD_CLI=ON`) is the headless insurance render path — exactly the terminal `Ctrl+Alt+R`. It takes just the source audio path, reads the project's `.warpmarkers`, `.phaseresetmarkers`, and `.settings` beside it (all three required; the GUI creates them on source load), and writes the warped WAV the GUI would render for the same project — `<title>.wav` in the project's own `render/` folder, exactly where the GUI publishes its deliverable (the folder is created for you the first time, as it is in the GUI) — byte-identical to the GUI by shared pipeline stages. The trim applied is the active tab's (the persisted `active_tab_view` key), matching the GUI. Like the GUI, it also drops the render's frame-map pair into `~/.cache/warptempo_gui/<pid>/` (see Output below).

To build the CLI on a headless host that has none of the GUI's Wayland / Cairo / JACK packages, add `-DWARPTEMPO_BUILD_GUI=OFF -DWARPTEMPO_BUILD_CLI=ON`; the GUI dependency discovery is skipped entirely.

There is no `make install` target. The binary is self-contained: copy it anywhere on `$PATH` (typically `~/.local/bin/` or `/usr/local/bin/`) to make it available system-wide.

```bash
install -Dm755 build/warptempo_gui ~/.local/bin/warptempo_gui
```

A `.desktop` file is shipped in `packaging/warptempo_gui.desktop`. To register `warptempo_gui` with the system's application launcher and as a handler for audio files, install it to the user-level application directory and refresh the desktop database:

```bash
install -Dm644 packaging/warptempo_gui.desktop \
    ~/.local/share/applications/warptempo_gui.desktop
update-desktop-database ~/.local/share/applications
```

The shipped `.desktop` file uses the freedesktop `audio-x-generic` icon name, which resolves to whatever the active icon theme provides — no icon file is bundled. Replace the `Icon=` line with a different freedesktop name or an absolute path to a custom SVG to override.

## First run

`warptempo_gui` takes no argument, or one.

With no argument, it opens the project it had open last — the device config's `last_project` — or, when that name is empty or its folder is gone or invalid, the first valid project folder under `projects_path` in name order; with no valid project at all, it refuses on stderr ("No project under `<projects_path>`") and exits. This is the tablet's only road in, and the laptop's own bare launch.

With one argument, the argument must be a project's source `.wav` — a file sitting directly under `projects_path`, in a folder that is itself a project, and resolving as that folder's source (see the project folder model below); anything else refuses with the reason on stderr.

```bash
warptempo_gui "path/to/source.wav"
```

**The project folder model.** `projects_path` is a per-device setting (see Per-device settings, below) whose subfolders are the projects, one folder per project, and a folder's name is the project's name. A folder is a project one of two ways: it carries a sidecar set — any of `<stem>.warpmarkers`, `<stem>.phaseresetmarkers`, `<stem>.settings` — naming its source by that shared stem, and `<stem>.wav` exists beside them; or it carries no sidecar at all and holds exactly one `.wav`, which makes it a new project — that wav is the source, and the first open writes the sidecar template beside it, as it always has. Any other shape refuses to open, with the reason stated (more than one sidecar stem, no wav for the stem, several wavs and no sidecar, no wav at all). A `.wav` sitting in the project root that is not the source is a leftover — the refusal names it and tells you to move it into `render/`. A folder's NAME has to be one the program can remember, too: it writes the name of every project it opens into the per-device config's `last_project=` line (see Per-device settings), and that line holds one plain folder name, so a folder called `.` or `..`, one whose name begins or ends with a space or a tab, or one whose name contains a line break is not a project on any road — it does not appear in the Open project list, the bare launch never falls through to it, and naming its source on the command line refuses. Rename the folder and it is a project again.

Two folders beside the source hold everything the program writes, and neither is itself a project or a candidate source: `render/` holds the deliverable — `<title>.wav` and its `.fingerprint`, written by the render command (`Ctrl+Alt+R`; the CLI writes to the same place) — and it holds nothing else: it is kept to the current `title` setting's one pair, and any other `.wav` or `.fingerprint` in there is deleted the next time the render player lists the folder or a render publishes into it, so renaming the piece does not leave the old deliverable lying around; `tmp/` holds the disposable batch renders — the iteration and BPM sweeps and the miscellaneous cell — that the render player (opened by bare `'` or `l`) walks, its Load in place button loading the highlighted cell in place; the player lists `render/` too.

Source inputs are stereo WAV only, 16- or 24-bit PCM, at 44100 Hz or above — anything else refuses to load with the reason on stderr. Material in any other format or layout — FLAC, Opus, MP3, mono — is converted once at acquisition with an external tool (e.g. ffmpeg), and the converted WAV becomes the project source.

The project's data lives in three sidecar files beside the audio, named by appending `.warpmarkers`, `.phaseresetmarkers`, and `.settings` to the audio file's basename. They are program-written and strictly validated at load: a hand-edited or corrupt sidecar fails the load with the first error on stderr.

**Per-device settings.** Five settings are about the computer you are on rather than about the piece, and they live in their own small file: `$XDG_CONFIG_HOME/warptempo_gui/config` (`~/.config/warptempo_gui/config` when that variable is unset). It holds exactly five lines, written in this order: `gui_scale=` (the GUI's scale axis, an integer percent), `projects_repo=` (the repository that is your projects home for the GitHub recheck), `projects_path=` (the absolute folder whose subfolders are the projects, described above), `last_project=` (the folder name opened last), and `sync_path=` (the folder Synchronize to external storage copies into — see Synchronizing to a stick). The first run on a machine writes the file with values that suit it and you edit from there: on the laptop that is `gui_scale=100`, `projects_repo=github.com/warptempo/warptempo_gui`, `projects_path=$HOME/.warptempo/warptempo_gui/projects`, a blank `last_project=` and a blank `sync_path=`; on the tablet `gui_scale=225`, the same `projects_repo=`, `projects_path=<the app's external files dir>/projects`, and the same two blanks. There used to be a sixth line, `audio_player=`, naming the external program `l` launched; renders are played inside the program now (see Playing renders), so the setting is gone and a config file still carrying that line refuses to start — delete the line by hand. `gui_scale` and `projects_repo` are set the ordinary way, through the settings prompt, and each commit writes the file immediately — `Ctrl+S` has nothing to do with them, and neither does opening a piece. `last_project` is written by the program itself, at every successful open — there is nothing to set by hand. `projects_path` and `sync_path` have no in-app writer at all: each is stamped by the first-run template and from then on is edited by hand only. Both are absolute paths, and neither may begin or end with a space; `sync_path` may also be left empty, which is what an empty one means — this machine has nowhere to synchronize to yet. The file is program-written and strictly validated exactly as a sidecar is: a hand edit that breaks it stops the program at startup with the offending line named on stderr, and no window opens. The point of the arrangement is that a project synced between two machines carries no opinion about either one's screen, and each machine remembers its own place in your work independently.

On launch, the program opens a window, reads any existing sidecar files for the given audio file, and presents the source waveform across the full window width. With no sidecar files present, you start with a single warp marker at frame zero carrying tempo `1.00` and no phase reset markers. With sidecar files present, the prior session is restored verbatim — viewport, zoom, playhead, active view selectors, and all marker positions and flags.

**Opening another project.** `Ctrl+O`, or File → `Open project`, brings up **a list of your projects** in the band above the bottom row — the band the on-screen keyboard uses — with `Cancel` at the right of the bottom row under it. There is nothing to type: the list holds one row per project that is actually a project (a folder that will not open is simply not in it). **Click a project to open it** — one click, or one tap. `Up` and `Down` move the highlight from the keyboard and `Enter` opens the highlighted one; those are the same act as the click. The list is read when it opens, so a project added meanwhile appears the next time; the highlight starts on the project you have open. Scroll the list with the wheel, or drag it with a finger. Opening reopens the program around that folder, exactly as choosing a project at startup does; an unsaved tab asks first, the same prompt `Ctrl+Q` raises; opening the project already open just closes the list, saying `That project is already open`. A folder that turns out not to open, or a sidecar that refuses to load, reports the reason in a notification (see Notifications) and leaves the list open rather than closing it. `Esc` or `Cancel` closes it. On the tablet the gesture is two taps: File → `Open project`, then tap the project. The menu row is the only road to it there — the on-screen keyboard has no `Ctrl`.

**Synchronizing to a stick.** File → Synchronize to external storage mirrors the open project into the folder `sync_path` names (see Per-device settings) — on the laptop that is the stick's own mount folder, something like `/run/media/<you>/<label>` — writing to a folder of the project's own name inside it: the rendered wav file directly — the current title's, which is the only one `render/` keeps — plus each batch of renders under its own folder exactly as it sits in the project — wav files only, nothing else. It is a mirror of that one folder and nothing more: anything already there that is not part of the current set is deleted afterward, so running it again after a fresh render brings the stick back in step rather than piling up old copies, and the folder you named and any other project's folder inside it are left alone. It goes where you told it and looks for nothing: set `sync_path` by hand once per machine, and if it is empty a notification says `sync_path is not set` and nothing runs. The folder has to be there — the command never creates it — so with the stick unplugged, or the path mistyped, a notification names it and says it is not a directory, which is also the answer for anything at that name that is not a real folder. Anything that goes wrong stops the act where it stands with the offending path named in a notification — shown relative to the stick or to the project folder, the terminal carrying the full path — a folder of the project that cannot be read, a full stick, a permission problem. What that leaves behind is worth knowing, since nothing is undone: no deleting happens at all unless every file has copied and the whole of the project's folder on the stick has been read through first, so a failure while copying deletes nothing whatever; the files it had already replaced by then stand as the new copies they are, and the one it broke off on still holds its old version whole. A failure while it is deleting instead leaves what it had already deleted deleted and the rest of it untouched, with a folder it was part-way through removing possibly half gone. A file being replaced is written beside its old copy and put in its place only once it has arrived in full, so a write interrupted by a stick pulled mid-copy costs you the new version and never the old one. Running the command again is how you retry, and it mirrors from wherever the last one stopped. When it works it says nothing at all: no notification, no line — the command is quiet on success exactly as a finished render is, and the only thing it ever tells you is what went wrong. If the folder `sync_path` names, the folder the project would own inside it, or a name inside that folder is a shortcut to somewhere else rather than a real folder or file, the act says so and does nothing: it will not write or delete through one. On the tablet, a stick has to be mounted where apps can see it, and as of 2026-08-28 that OTG stick is not — there is no folder to point `sync_path` at there, so the tablet's stays empty and the command refuses until that changes.

The repository's `projects/` directory ships reference movements with complete sidecar files. The Symphony No. 40 mvt I directory (`projects/550 - 1/`) is the recommended first load — it exercises every form and syntax used in the project. The audio itself is not included (the corpus is commercially licensed); you supply the source recording and place it in the project directory under the basename the sidecar files expect. See the Projects section at the end of this document.

## Conceptual model

### The engine

`warptempo_gui` drives a phase vocoder — a faithful, centered implementation of Prusa-Holighaus phase-gradient heap integration (PGHI, from ltfatnote050, "Phase Vocoder Done Right"). The gradient method enforces phase coherence in both time and frequency without peak-picking or transient detection, which is what lets a high stretch ratio preserve upper-band detail and transient impact rather than dulling them. Per-frame phase correction keeps bins coherent within each frame, so steady-state content — held strings, sustained winds, room tone — stretches without smearing into a chorused or phasey artifact.

The FFT size `N` is fixed at 4096 and the synthesis hop `R_s` is derived as `N/4` (75% overlap). These parameters match the authors' released PGHI implementation (github.com/ltfat/pvdoneright) parameter-for-parameter — window length 4096, `M=2N=8192`, synthesis step 1024, tolerance `1e-6` — giving the gradient integration its finest frequency resolution and the fullest low-frequency body. The engine inherits the source recording's sample rate.

### Relation to the published algorithm

The engine implements the published algorithm faithfully: origin-centered zero-padded analysis (`M=2N`, matching the paper's ~2x padding), centered finite differences for both phase derivatives, trapezoidal integration in all three propagation directions, the max-heap significance ordering, and the published tolerance. Where the implementation deviates from or extends the paper, the differences are deliberate:

- Variable analysis hop. The paper fixes one analysis step for the whole file (constant stretch ratio). This engine derives the analysis hop per frame from the warp-marker frame map; each half of the centered time-derivative is normalized by its own actual hop, and the frequency-direction step uses the per-frame ratio. This is the extension that makes free-tempo warping possible and is the project's reason to exist.
- Phase resets. The paper has no mid-stream re-grounding; transient handling is left to detection-based methods it cites. This engine's manual phase-reset markers re-seat the synthesis phase to the analysis phase at user-chosen frames — operator judgment in place of detection.
- Output timing contract. The paper does not specify output alignment; this engine pins it. Synthesis trims exactly `N/2` samples from the head — the alignment latency the origin-centered analysis contributes — so source frame 0 maps to output frame 0, and a feature at source frame `S` lands at output sample `tgt(S)` from the frame map. Total output length is the target-frame position of the last source sample. The overlap-add ramps at head and tail are amplitude-only fades that move no alignment. This establishes a contract: any future engine consuming the same warp markers (and, if it supports them, the same phase-reset markers) can match this engine's output 1:1 in frame timing at the start and through the body. The tail's final incomplete-overlap ramp is deliberately outside the contract.
- Remaining boundary choices, unspecified by the paper: the first frame (and the frame each phase reset selects — the frame whose analysis window centers on the authored position) seeds synthesis phase from analysis phase, the seed that serves the timing contract and the reset model above; the first frame's time-derivative uses the forward difference only; the frequency-derivative is one-sided at DC and Nyquist.
- Quiet-bin randomness. The paper assigns unspecified "random values" to sub-tolerance bins. This engine pins the choice: uniform phase in (-pi, pi) from a per-channel deterministically seeded generator, so identical renders are byte-identical — the property the project's verification protocol depends on.
- Real-signal realization. The spectrum is held as the Hermitian half (`M/2+1` bins) rather than the paper's full-`M` complex formulation — mathematically identical for real input and output.

### Warp markers, labels, and phase resets

Variable-rate time-stretching with user-placed warp markers exists in other tools — DAWs have shipped warp-marker editing on top of their bundled time-stretch algorithms for years. What separates this project is per-marker tempo locking through label definitions and references. A marker can declare a named label; a later marker can reference that label by name; the two markers and every other reference to the same label render at the same effective tempo, and editing the def's tempo updates every ref that cites it. The mechanism is described in the warp marker model below. The use case it was built around is the sonata-form exposition/recapitulation relationship in classical orchestral repertoire, where the same musical material returns multiple times across a movement and should hold a coherent tempo relationship across all occurrences regardless of how the surrounding material is edited.

Per-frame phase coherence is what keeps steady-state content clean. It is also exactly what a transient defeats. An attack — oboe entry, pizzicato, timpani strike — is a moment where the spectrum reorganizes within a few hops, and the phase relationships the vocoder has been propagating no longer correspond to the acoustic event arriving. The attack smears across surrounding frames. The mitigation is a phase reset: at a user-chosen position, the synthesis phase is reset rather than propagated, sacrificing local coherence in exchange for a clean transient. Phase reset markers are the authoring surface for this. They are a separate marker collection from warp markers, visible and edited in their own view, because they parameterize a distinct engine concern: warp markers shape the frame map, phase reset markers protect transients.

### View axes

The interface carries three independent toggles, each shown in the rows at the top of the window: the source/target pair and the warp/phase-reset pair sit in the icon row as radio buttons (the current side wears the toggled-on face), and the `A`/`B` pair is the tab row itself (the active tab wears the blue top trim). The right end of the topmost row also carries a small blue bar of three view buttons — `S+W`, `T+P`, `T+W` — with the one matching the current view combination lit (none lights in the fourth combination, source+phase; see View toggles in the reference). All combinations are valid; the GUI's state is the product of all three selections plus whatever modes happen to be active on top. The playhead time sits at the left end of the bottom toolbar, just past the transport buttons and the thin line that divides them off, in monospace, and immediately to its right — on that same row, in the row's own lettering — sits the STATE TEXT: whatever the program is busy with (`Loading...`, `Rendering...`, `Updating...`) or, in the history view, where you are in the walk. It is not a message about something that happened and it never times out: it says what is true and changes when it changes, and a line too long to fit is cut where the buttons at the right of the row begin. (A thin STATUS BAR carried this along the very bottom edge of the window for one day in August 2026, with the selected marker's resolved tempo at its right end; both the bar and that readout are gone — the state text belongs on the toolbar you are already reading, and `j` copies a marker's value instead. Notifications and the state text, below, has the whole of it.) Prompts and the one-line editors (settings, BPM, the commit message, and the paste-measures offset) take the whole bottom row while they are open — the clock and the buttons stand aside, and the row carries the question or the text field with its own buttons instead (status messages are unaffected, being on another row now); while one is up, the rest of the window is inert (see Files and session). Those buttons act when the mouse button is released on them. Pressing one and dragging away holds it — the button keeps a lit face and keeps the keyboard on it — and releasing away from it does nothing, while dragging back on and releasing still acts. Tab moves the keyboard between the text field and the buttons (a prompt, having no field, cycles its buttons alone) and `Shift+Tab` moves it the other way round the same ring, the left and right arrows move between buttons once the keyboard is on one, and Enter or Space then presses the focused button down and acts when you let the key go. Holding Tab walks the ring repeatedly, the only key that repeats while a prompt or an editor is up; a prompt's answer keys, and Enter and Space, stay one press each. A prompt opens with its LAST button focused — always the one Escape would pick, so Enter takes the safe answer — and an editor opens with the keyboard in its text field, where Enter and Escape mean what they always did. One prompt opens on its FIRST button instead: the player's "Load ... in place?", where Enter confirms the load, because a load is one Ctrl+Z away and the same confirmation raised on the history view's viewed member answers to Enter the same way. Cancel is still the last button there, so Escape still cancels. While the keyboard is on a button, nothing you type reaches the text field: the text and its selection sit untouched, the cursor stops blinking, and only Escape, `Ctrl+S` and `Ctrl+Q` still do their usual work. Tab back to the field and typing resumes where it left off. The field carries the blue outline while the keyboard is in it or the pointer is over it, and it scrolls sideways to keep the cursor in view, so a value longer than the field is edited the way any one-line text box is — the left and right arrows, Home and End all walk the text and the view follows. Unsaved work shows as an asterisk in the window title, after the project name — the title is the source file's parent folder ("K551 - warptempo_gui", becoming "K551 * - warptempo_gui" while unsaved changes exist).

The first pair, **source vs target**, selects the audio domain of the waveform under the playhead. Source view (S) shows the unprocessed source recording with warp markers drawn at the times you authored them. Target view (T) shows the same audio after the engine has applied the live frame map — the waveform is stretched and compressed to reflect what the render will sound like, with markers drawn at their post-stretch positions. The two views serve different stages of the same authoring task. Source view is where a marker's POSITION is authored — placing it, dragging it, nudging it — because pinning a marker's time against an acoustic event, and moving a marker inside the very map it deforms, both belong in the unprocessed recording. Target view is where you judge the warp by ear and make the adjustments that want to be heard, and everything that does not MOVE a marker is available there: tempo first of all. Nudge an *owning* marker's tempo up or down with `Up` / `Down` — an owning marker stacked with others on one frame refuses the step here, since that stack renders as a single `1.00`, so fix its tempo back in the warp source view; a pass or a label reference refuses too, having no tempo of its own to step. With several markers selected the step moves every selected marker's own tempo together by the same 0.01, refusing the whole press if any one of them cannot take it. The rest of a marker's value and status is editable here too: `Ctrl+D` disables and re-enables, `Ctrl+N` switches a marker between owning its tempo and passing the previous one through, `Delete` removes the selected markers, and `Return` or a double-click on the flag opens the flag editor over the whole canonical line — tempo, labels, per-marker scale, and the iteration bracket. Each of those reshapes the stretched picture the moment it lands, so the waveform redraws and the playhead follows the marker it was standing on into its new place. A marker's MEASURE is editable here as well and changes nothing audible: every marker carries one, in both collections and both views (see Marker measures below) — it names where the marker sits in the score and reaches no part of the engine. Iteration mode is fully available here too — `i` toggles it, the brackets stay on the flags across a view switch either way, `Ctrl+Alt+R` renders the sweep, and a bracket is typed in the flag editor here exactly as it is in source view. What target view does NOT allow is anything that moves a marker: dropping one with `s` and the horizontal arrow nudges are refused with a notification that names the view the act belongs to (`Markers are placed in source view`, `Markers are moved in source view`), and dragging a flag sideways is refused silently — a pointer gesture that never begins is its own answer, and the flag simply does not move. So a flag click there selects the marker and seats the playhead on it — the moment you press, as flag clicks do everywhere — and no drag can begin from it. Selection, `Tab` cycling and the selection readout work as they do anywhere. Target view is always available. Trim narrowed to the section under revision keeps target renders fast enough for this loop to feel immediate.

The second pair, **warp vs phase reset**, selects which marker collection is visible and edited. Warp markers (W) drive the frame map. Phase reset markers (P) protect transients. The two collections are stored, authored, and rendered independently; toggling between them swaps which collection the marker hotkeys operate on but changes nothing else. Authoring proceeds in warp view first, since phase resets have no useful position until the frame map exists. What each collection binds to its home audio view is its markers' POSITIONS: warp positions are authored in source view (see above), and phase resets are authored in target view, where the stretch is audible and their `N/2` lead-in aligns to the output-domain overlay. In its away view a collection is display and navigation only — phase resets are entirely read-only in source view, and warp markers cannot be placed, dragged or nudged in target — so a gesture that would move a marker of the away collection refuses silently, exactly as a read-only tab does. Warp markers' VALUES are a different matter and are edited from either view: tempo, the disabled flag, pass-versus-owning, deleting a marker outright, and the whole flag editor with it. The rule is about placement, and none of those is a placement. The MEASURE goes one step further, being not musical state at all — it names a marker's place in the printed score, reaches neither the engine nor the frame map, and is therefore editable on either collection from either view, wherever the flag is painted (Marker measures, below). (Iteration mode sits outside the rule entirely: the mode is a state rather than an edit, so it toggles and sweeps from either audio view, and the bracket editing it enables rides the flag editor, which opens in either audio view too.)

Beyond the data-model difference, both collections want anticipation — placement a little ahead of the acoustic event rather than dead on it — though for different reasons. Warp markers anticipate to make A/B synchronization reliable: rather than landing exactly on a transient, place the marker slightly earlier, in the fading tail of the previous material. The fading tail is a far more dependable alignment cue than the silence or volume dip just before a transient, because the tail can be placed to start at an audible point, whereas a silence or dip is very hard to line up across the A/B tab pair. The lead-in matters most for label-bearing markers and for markers adjacent to label-bearing ones, where the tempo precision the label mechanism enforces only pays off if the underlying timing is itself precise; it also matters for quiet, slow, or legato onsets, where the acoustic event has no sharp attack to pin to — pinning against the louder fade of the prior note beats guessing where the quiet onset begins. The A/B tab pair (below) is the natural way to set these lead-ins precisely, matching the lead-up across paired sections.

Phase reset markers anticipate to give the reset an `N/2` lead-in into the transient. The reset fires at the authored frame — its analysis window centers there — and the overlap-add Hann synthesis takes about `N/2` samples to build the reset's effect to full scale, so authoring the reset `N/2` before the transient lets that lead-in complete right as the transient arrives. In target view, `s` seeds a reset `N/2` before the playhead in target time — clamped to the file start and committed to the nearest whole source frame — and `Space` auditions it by starting playback `N/2` ahead (see the reference); the output-domain overlay depicts the same `N/2` region. The two offsets are deliberate inverses, so dropping with `s` and then pressing `Space` auditions from exactly where the cursor was sitting. This is the only phase-reset drop there is — target view only, like every phase-reset authoring gesture. `N/2` is only the nominal figure, though: if that placement produces an audible discontinuity, nudging the reset with `Left` / `Right` usually clears it — each press moves the reset one painted pixel column (tens of samples even at the finest zoom, more when zoomed out), so drop to the deepest zoom for the smallest available step. Phase resets are placed only where loud transient content provides masking; quiet, exposed passages should carry one phase reset at their start and nothing else, since a reset during exposed material has nothing to hide behind.

The third pair, **tab A vs tab B**, selects between two snapshots of viewport, zoom, playhead, and trim window. A snapshot holds positions and view settings only — never a selection, which belongs to the moment rather than to the tab. Marker stores and engine settings are shared across both tabs; only navigation state differs. The two-tab layout gets used throughout authoring, not just for aligning sections that exist already. Repeated phrases within a single passage benefit from label-locked tempos, and laying those labels down reliably means parking one tab at the first occurrence and the other at the second, then walking the lead-ins forward together to confirm the matching reference point. The same pattern applies at every scale — phrase repeats, sectional repeats, and the exposition-recapitulation relationship a sonata movement turns on. The second tab earns its place from the first repeated phrase onward.

### Warp marker model

A default warp marker is seeded at the file's first frame on first load, carrying tempo `1.00`. A render does not actually require it: when no enabled marker sits at exactly frame zero, the render silently behaves as if a plain `1.00` owner were there, and the opening span plays unstretched until the first real marker. More generally, ambiguous marker arrangements never block anything — two or more enabled markers on the same exact frame collapse to a single `1.00` owner for the render, a reference whose definition was deleted renders as `1.00`, and each such normalization prints one stderr line naming the timestamp. What you see in the GUI is your authored store; the stderr line is the signal that a spot needs attention.

The classical phase-vocoder use case — one constant stretch ratio for the whole file — requires no warp-marker authoring at all: the global stretch ratio is set entirely through the settings `scale` field, and the frame map remains a single constant. Warp markers as an authoring surface come into play when you want phrase-level tempo variation. Each one carries three independent pieces of ENGINE state, described next, and one piece that reaches the engine not at all: its MEASURE, the bar of the score it sits on (Marker measures, below).

**Tempo source.** A marker either owns its own tempo or inherits the tempo from the nearest earlier owning marker. An owning marker presents an explicit numeric value; an inheriting marker (a "pass" marker) carries no tempo of its own and resolves its presentation tempo live by walking backward through the marker list. The walk passes over disabled markers and stops at owners; a pass never inherits through a reference — an enabled label reference encountered before any owner ends the walk at the neutral `1.00` instead (a reference owns a duration equation, not a rate, so there is no rate to inherit; the render prints one stderr line per such pass). Because the resolution is live, deleting or disabling an owner re-resolves every dependent pass to the next earlier owner; nothing is frozen on the pass itself.

**Label relationship.** A marker can declare itself a label origin (a `label_def`) or cite an existing label by name (a `label_ref`). A `label_ref` marker inherits its tempo from the named def rather than from positional walk-back. Changing the def's tempo updates every ref that cites it. This is the mechanism for tempo locking across recapitulated material: a sonata-form exposition section receives a `label_def`, the corresponding recapitulation section receives a `label_ref` back to that def, and the two sections will always render at the same tempo regardless of subsequent tempo edits. A reference imposes its definition's target duration on its own segment whatever local stretch ratio that implies, within reason: an implied effective tempo outside `[0.125, 8]` — beyond what any directly authored marker could express — is treated as a mismatch and renders as a plain `1.00` instead, with one stderr line; matching reference segments to their definitions sensibly remains the author's concern. A marker carries at most one of `label_def` or `label_ref`; neither is the unlabeled default.

**Disabled flag.** A marker can be disabled, which silences its tempo contribution as if the marker were not present. Disabling a `label_def` cascades: every `label_ref` citing that def is treated as disabled too. Disabling a non-def marker is local and does not propagate.

An owning marker's tempo is a base value times a scale. The base value is exactly two decimals (the `N.NN` spelling is the on-disk grammar) in the bracket `[0.25, 4.00]` and expresses the headline stretch ratio relative to the source recording — `1.00` is no stretch, `1.05` is 5% faster, `0.95` is 5% slower. The base value's precision is deliberately coarse; you author at the resolution you would set a metronome, not finer. The scale is a separate full-precision multiplier in the bracket `[0.5, 2.0]`, defaulting to `1.0000` (written shortest round-trip, padded to at least four decimals). Its intended use is fine-tuning a marker's effective tempo to approximate a neighboring section's effective tempo when that neighbor uses a `label_ref`: select that neighbor and press `j`, which copies its resolved `base*scale` to the clipboard, then apply a matching scale to the marker being authored. Scale can serve any other purpose inside the bracket; out-of-bracket values are rejected at the editor with a red flash and a notification saying why. The reference project in `projects/550 - 1/` shows both fields in use across a complete movement.

Phase reset markers carry two pieces of engine state: a position and a disabled flag. They have no tempo, no labels, no scale, no mode. Like warp markers they may also carry a MEASURE, which is a note about the score rather than a parameter and reaches no engine concern at all. The engine concern they parameterize is *where to reset* — re-grounding the synthesis phase at the transient that opens the segment. The reset fires at the authored position, with the analysis window centered on it.

## Output and the limiter

The render product is a finished WAV: 24-bit PCM, brought to a delivery ceiling by the built-in limiter — a transparent spectral stage at -0.3 dBFS, then a 0 dBFS lookahead peak limiter with a hard-clip backstop. The limiter is unconditional; there is no bypass and no output-format choice.

As future-proofing for later engines, every archival render — the GUI's `Ctrl+Alt+R`, the sweeps' batch cells, and the CLI — also writes the full frame-map pair: `<wav-stem>.warpframemap` (whitespace-separated `<src> <tgt>` frame pairs, precise double breakpoints) and `<wav-stem>.phaseresetframemap` land in `~/.cache/warptempo_gui/<pid>/` (batch cells under a subdirectory mirroring their batch folder). Together they are exactly the engine's input for the full (untrimmed) render of that recipe, with the phase resets already compiled into the engine's origin-centered query domain; trim never affects the pair — a trimmed render feeds the engine a trimmer-translated pair, and the cached pair is deliberately the full one — and the limiter does not apply to map files. Any time-stretch library that accepts a sample-domain warp map could be driven from these files. Retrieve them between the render and program close: the GUI removes its per-process directory when it exits, and CLI-written directories and orphans from dead processes are swept at the next GUI launch, so nothing accumulates. The pair is written all-or-nothing — a write failure removes both files rather than leaving a mixed-generation pair.

## Reproducibility

Rendering is deterministic per machine and binary: the same project rendered twice on the same host with the same build produces byte-identical WAV output, every time. This is a hard guarantee — the whole pipeline is fixed-order and free of timing- or scheduling-dependent math. GUI and CLI from one build on one system state are byte-identical, unconditionally.

Across builds the boundary is not the compiler's code generation but the libraries underneath it. Floating-point contraction is switched off in the build, so how the compiler lays the arithmetic out no longer touches a single output bit: the same project renders byte-identically whether the binary was tuned for this CPU or built generically, and on another machine of the same architecture — same compiler, same glibc and FFTW — it renders those same bytes again. What does move the output is a change in those libraries, and the movement is tiny. For a sense of scale at the far end: a completely different toolchain on a different architecture — a WebAssembly build of the same engine, carrying its own C library and its own copy of FFTW — differs from the native build by 67 samples of a 7.6-minute render, each by a single least-significant bit. On threshold-straddling material the limiter can quantize a difference that small into a localized one (measured at the -38 dBFS / two-samples class on a stress recipe — far below audibility, and ear-verified quality-neutral). So compare renders byte-for-byte freely within one set of library versions; after a glibc or FFTW upgrade, re-render anything you intend to keep comparing against.

## Hotkey reference

The reference is grouped by function. Everything is keyboard unless marked as a mouse gesture. Bindings are case-described: `Ctrl+S` means Control held with the `s` key, `Shift+B` means Shift held with `b`. Where a key does different things in warp view versus phase-reset view, both are given.

Bindings are matched exactly. A key pressed with a modifier this reference does not list for it does nothing at all — there are no near-miss chords that fall back to the unmodified binding, and no gesture has a modified variant that does a related-but-different thing. Two consequences worth knowing: the prompts' letter answers are case-sensitive — the paste confirmation's `Yes` answers to `y` and not `Y`; and inside a text editor the clipboard chords are `Ctrl+C` / `Ctrl+X` / `Ctrl+V` exactly, so the terminal habit of `Ctrl+Shift+C` does nothing there. Alt lives only in the five `Ctrl+Alt` chords (the two render chords, the two phase-reset propagate pastes and the measure propagate's paste, all documented below); on the mouse it has exactly one binding, `Alt`+wheel, which pans a tenth of a screen per detent — panning by drag is the plain drag — and no other binding uses it. Super (the Logo key) belongs to the window manager: while it is held no keypress starts a command, so a window-manager chord can never leak a keypress into the GUI — with one deliberate exception: bare `e` is the left mouse button rather than a key, so `Super`+`e` still clicks, exactly as `Super`+click does.

Keyboard commands act when the key goes DOWN, and the buttons on screen act when they come UP. That is the whole timing rule and it is deliberate: a button is a target, so it gives you the slide-away escape a target should have, while a key is an instrument, and the moment you can actually aim is the moment you press it — which matters on the warp side, where you are placing markers against music you are listening to. A key that repeats while held — the arrows, `PageUp`/`PageDown`, the zoom keys, the two waveform-magnification chords, `Tab`, undo and redo, and the history walk — acts at once when you press it, then waits your desktop's own key-repeat delay and runs on at your desktop's repeat rate until you let go; releasing adds nothing. Each repeat is its own act and reads the modifiers as they stand at that moment, so holding `Ctrl+Z` and adding `Shift` partway through carries the run on as redo. And a key, like a mouse gesture, cannot be called back: by the time it is down the command has run, and undo is the way out.

**Files and session.** The project is chosen at startup — on the command line (`warptempo_gui <audio_file>`), or, with no argument, the most recent one — and a load that fails prints the reason and exits. `Ctrl+O` opens another project in place, without relaunching: it brings up the project-open prompt described under Opening another project above, and the `File` menu's `Open project` row is that same command. There is no drag-and-drop. `Ctrl+S` saves all sidecar files. `Ctrl+Q` closes the window, routing through an unsaved-changes prompt when the session is dirty; it also works while the settings prompt or a paste-confirmation prompt is open (it abandons that prompt first, without committing it). On the tablet the system's own Back — the gesture or the button — is that same command: it asks the unsaved-changes question exactly as `Ctrl+Q` does and leaves once you have answered it, rather than taking the session away unasked. Being killed from the task switcher is not that road and asks nothing, so answer the question rather than swiping the app away. Every prompt takes over the bottom row: the transport buttons, the clock and the state text step aside for as long as it is up, and the state text is back the moment it closes — and the question reads from the left with its answers as real buttons right after it — `Save`, `Discard`, and `Cancel` on the unsaved-changes prompt (`Retry` replacing `Save` after a failed save), `Yes` and `Cancel` on the paste confirmation, `OK` and `Cancel` on the load-in-place confirmation. Every one of those buttons has a key, and hovering it names the key the way the icon row's tooltips do (`Save (s)`, `Discard (Delete)`, `Cancel (Escape)`): click a button or press its key — `s`, `r`, `y`, or `o` for the named acts, `Delete` for `Discard`, `Esc` for `Cancel` — the two do exactly the same thing. The one-line editors (settings, BPM, the commit message, and the paste-measures offset) take the row the same way: a label, a dark text field, and `OK` and `Cancel` buttons that are exactly the editor's `Enter` and `Esc` (every letter you type belongs to the field, which is why those two are on `Enter` and `Esc` and their tooltips say so). While any of these is up the rest of the window is inert — clicks, scrolls, and drags anywhere else do nothing, without exception, and it closes only by its own buttons and keys. The keyboard still lets a few commands through an editor: `Ctrl+S` saves with it open, and `Ctrl+Q` quits (or press the dialog's own `Cancel` first — the `File` menu cannot be opened while a dialog is up).

**The window layout.** The menu row sits at the very top of the window and the bottom toolbar along its very bottom edge. Everything else is one block: the tab row, the icon row, the overview strip, the trim bar, the ruler, the marker lane, and the waveform under them, all packed together with a thick line closing the waveform off at its foot. That block is placed so the middle of the waveform is the middle of the window, which leaves a band of blank ground above it and another below it on a tall screen; the waveform grows with the window up to a limit and then stops, the blank bands taking the rest. On a small screen — a 1024x600 panel, say — there is no room to centre anything, so the blank bands vanish and the waveform takes every pixel left over. Nothing in either blank band responds to the mouse or the wheel.

The rows at the top of the window are buttons, and every button except `File`, `Edit`, `Series` and `Settings` — the four that open menus — is a click-shaped spelling of a keyboard command, behaving identically to it. Every button acts when the mouse is released on it, not when it is pressed: press one, and while you hold it the button shows its pressed face for as long as the pointer stays on it; release on the button and it acts, drag off it first and releasing does nothing, drag off and back on and releasing still acts. Then play renders (`l`), load in place (`'`), and the READ-ONLY toggle — the first two both opening the render player outside the history view (see Playing renders). The read-only button is the padlock that used to sit in the tabs: it shows a closed lock and lights up while the ACTIVE tab is read-only and an open lock unlit while it is writable, and clicking it is exactly the `o` key — it locks a writable tab and unlocks a locked one. And finally the history group: the history button (`h`), then the pair that chooses which history you are reading — `Git` and `Session`, radio buttons on the `g` key — then the cumulative reading (`u`, a summation sign), revert (`Ctrl+H`), and the walk's two arrows (`,` and `.`, each taking `Shift` for the jump to that end of the walk). Those six do their work inside the history view and nowhere else, so they are greyed out whenever it is shut — the one place in this row where a button is dead at rest, and the cumulative button stays lit or unlit through the grey to show which way you are reading (see Checking history). Inside the view those six are truthful too: revert greys out while no difference flag is selected or focused and on a read-only tab (the lock refuses the act either way; since 2026-08-30 the view's own refusal says so first), and the two arrows grey out at the ends of the walk — the older arrow on the oldest checkpoint, the newer one on the newest, an empty walk greying both — since the jump their `Shift` reaches would land on the very checkpoint you are standing on. (They stayed lit there until 2026-08-30, revert's grey having been taken off on 2026-08-15 as a blink that followed every click in the marker lane.) Apart from those six, the lock's own one, zoom out and the two waveform magnifiers, these buttons never grey out — one that cannot act right now simply does nothing, exactly like its key — except inside the history view, where every button that view refuses greys out, `Save` among them when its moment has nothing to act on.

Every button except `File`, `Edit`, `Series`, `Settings`, and the three view buttons shows a small tooltip naming its action and key after the pointer rests on it for a moment; on `Render`, `Show trim region`, the history walk's two arrows, the play button and the drop-marker button — a second, smaller line names what the `Shift`+click does instead, which is also what holding the button for half a second does (see The top rows), and on the two skip buttons that second line names what the `Ctrl`+click does, which no hold reaches. A greyed-out button shows its tooltip too: a button that cannot act right now is exactly the one you may need told what it is for and when it works. The tooltip goes away the moment you act — any click, any key, any scroll — and none appears at all while a prompt or one of the editing prompts is up, since the action it would name is one those surfaces ignore.

**Notifications and the state text.** When something you asked for could not be done, or something you were not watching has gone wrong, the program says so in a small dark card at the top right of the window, just under the view buttons — a blue information glyph, the text, and a close button at its right. Since 2026-08-30 **a key that does nothing says why**: a chord swallowed because an editor is open, because a drag is in progress, or because the history view or a read-only tab is standing answers on a card that names the key you pressed and the reason, as in `Ctrl+Alt+R is not available on a read-only tab`. **A key that is not bound to anything does nothing and says nothing, which is how you can tell** — everything the program does refuse now has a sentence, so a press with no card and no visible change is a press with no command behind it. The same goes for a key the render player or the project list does not use while one of them is open, and for a `Ctrl`, `Alt` or `Shift` click on a surface that binds no such click. Typing into an editor is the editor's own business and says nothing, a greyed button stays silent because its grey is already the message, and `Esc` with nothing to close stays silent too. Since the same day **a command that cannot act says what it wanted**: a marker verb with nothing selected names what to select, a command used away from its home view names the view it belongs to (`Markers are placed in source view`), a nudge at the start or end of the piece says the marker is already at the edge, a copy or paste with the wrong selection says which selection it needs, a mode that will not open on the selection you have names the rule it broke, a marker walk with nothing ahead of it says there is nowhere to step, and `Ctrl+Z` with nothing recorded says so. Since the same day **the modes, the trim window, playback and the render commands answer too**: in the render player a `Play` with nothing loaded, a `Previous` or `Next` at the folder's first or last file, a seek before playback has started and a `Backspace` at the top all say which it is; in the project list, choosing the project already open says so as it closes, and opening the list over the render player or an editor says which to close first; in the history view, `h` while a checkpoint is publishing, a history that cannot be read, a walk step at the oldest or newest end, and a `Tab` with no changed markers left all say so, and `'` with nothing to load and `Ctrl+H` with nothing to revert each say that rather than that the key is unavailable. `Shift+[` with the window already whole says so, showing the trim over a whole-song window says what it is showing, a trim bound clicked onto or past its partner says it must stay inside, and a trim you collapsed to a point says the bounds crossed and the window went back to the whole song. `Space` says when the target preview is not ready yet, when there is nothing left to play from where the cursor sits, and when no audio device is there at all; a second `Shift+Space` says an audition is already running. And the render commands say when iteration mode is what refused `Ctrl+Alt+Shift+R`, when a sweep has no ranges authored, and when a batch folder could not be created. Each of these is one card for one press, never two. Ordinary cards leave by themselves after a few seconds, waiting while the pointer rests on them, or when you click their close button; the checkpoint failures described under Checking history carry the red error glyph instead and stay until you close them. Newer cards stack on top, and when the stack fills the window the oldest one leaves the bottom to make room; cards with the red error glyph are never pushed out that way and stay until you close them. A short sentence is one line; a longer one wraps and the card grows downward, up to three lines, with the two glyphs staying beside the first line — and a sentence longer than three lines is cut off at the end of the third rather than wrapped further. A card takes no key and stops nothing, and a click anywhere on it other than its close button does nothing at all. What is true right now rather than something that happened — a render's progress, or the history view's position while that view is open — is not a card: it is the **state text** on the bottom toolbar, immediately right of the clock, in the same lettering as the rest of that row. It is replaced as it changes and never times out. The two can both apply, and the history view's line wins while that view is open; the progress line is back the moment you leave it. While a prompt, one of the bottom row's editors, the render player or the project list is open, that row belongs to them and the state text is not shown — it reappears when they close.

**The bottom toolbar** (mouse). One more row of eighteen buttons sits along the very bottom edge of the window — permanent, the same on every machine, separated from the waveform above it by a thin line and, on a tall screen, by a band of blank ground (see The window layout). Like the top rows, every button is a click-shaped spelling of a keyboard command and behaves identically to it: a click that cannot act does nothing, exactly like the key. The buttons are the same size as the icon-row buttons above the waveform. On the left sit three: go to start (`Home`), play/stop (`Space`), and go to end (`End`), and then a thin separator with the clock immediately after it, and after the clock, at the same distance, the state text — the render's progress line, or the walk line while the history view is open (see Notifications and the state text). The two skip buttons take `Ctrl`: a `Ctrl`+click on either jumps to the very start or the very end of the piece instead of to the trim bound, the same act `Ctrl+Home` and `Ctrl+End` run. They are the only buttons that take `Ctrl`, and they take no `Shift` at all, so the long press does not reach this jump: everywhere else a press held for about half a second stands in for a held `Shift`, and here a held skip is the plain trim-bound jump like a tap. Play and stop are **one button** that shows whichever act is next — a play triangle while nothing is running, a stop square while an audition is — so pressing it always does what its glyph says, and playback ending on its own turns it back into play. The A/B audition counts as running for the whole sequence, its short silences between plays included: the button stays a stop square from its first play to its last, and a press on it there stops the sequence. It is the same `Space` the keyboard has, and `Space` still toggles. The play button does take `Shift`: a `Shift`+click, or a press held for about half a second, runs the A/B audition that `Shift+Space` runs (see Playback and playhead), whichever glyph the button is wearing. The **Drop marker** button takes `Shift` the same way: a `Shift`+click, or a press held for about half a second, runs the `Shift+S` phase-reset drop (see Phase reset authoring) instead of dropping a warp marker. Since 2026-08-30 a button on this row greys out whenever its press would do nothing — the same greys the icon row wears. Which buttons grey, and on what, is said with each button below; before that date only the read-only lock and the history view greyed anything here, on the grounds that a grey following the selection would blink with every click. The two skip buttons grey out only when no press of either kind would do anything at all: nothing is playing, there is no marker selection to drop and no trim region showing, and the cursor already rests where the plain jump *and* the `Ctrl` jump would land (in the history view both mean the piece's ends). Wherever the `Ctrl` jump would still move the cursor the button stays lit and its `Ctrl`+click works; a plain press whose jump is already home then says so on a card — `The playhead is already at the trim start` (or `trim end`), and the `Ctrl` form's card reads `…at the start of the song` / `…at the end of the song` — exactly as the keys do. Play greys out only when nothing it can do would play: the plain press would refuse — no audio device, or in target view no preview to play yet or the launch spot at or past the end of what the view plays (with a phase reset's lead-in ring showing, that launch spot is the half-window-ahead one `Space` actually uses, so the button and the key agree there too) — *and* the A/B audition its `Shift` half runs could not run either. Wherever the audition would still play, the button stays lit — the `Shift`+click and the long press reach it — and a plain press that plays nothing says why on a card, as `Space` does. While something plays, all three stay lit — stop, or a jump that stops. If you press play in target view with the playhead outside the trim window and neither tab could audition, the button says so, greyed; the audition there is the trimmed preview, so there is nothing to play. In source view playback runs to the end of the piece and the trim does not bound it, so play works wherever the playhead sits. Against the window's right edge sit three groups, separated from one another by thin lines. First the single-marker verbs: drop a marker (`s`), delete the selected markers (`Delete`, the red cross), toggle the selected markers' disabled flag (`Ctrl+D`, the crossed-out eye), and toggle inherit on the focused marker (`Ctrl+N`, the chain link — a pass marker links its tempo to its neighbor); each is its key exactly, with all the key's refusals, and all four grey out in a read-only tab because the lock refuses them. Next in that group is edit flag (`Enter`, the text cursor), which opens the focused marker's flag editor (see Warp marker authoring) — the third way in beside the key and the double-click, and the one a machine with no keyboard can reach; like the four verbs it greys out in a read-only tab, and it greys out too when no marker is focused or when the phase-reset markers are showing, since those have no flag editor (it simply did nothing then until 2026-08-30). Then measure (`/`, notes on a staff), which opens the focused marker's measure editor (see Marker measures); like the four verbs it greys out in a read-only tab — a measure is part of what gets saved — and with no marker focused, and unlike them it works on either kind of marker. Then copy resolved value (`j`, two stacked sheets), which copies the focused marker's resolved value to the clipboard, and which takes `Shift`: a `Shift`+click, or a press held for about half a second, goes to the marker that value comes from on the other tab instead (see Warp marker authoring). It is the one button in this group the lock leaves lit, since neither act changes anything; it greys out instead whenever the focused marker has no resolved value to copy — an owning marker, a disabled one, a phase reset, nothing focused, or iteration mode on (a marker whose reference points at nothing stays lit and copies nothing). Three of those four verbs work in either audio view (delete and disable on either kind of marker — phase resets too since 2026-08-30 — and toggle inherit on a warp marker); only the warp drop is bound to source view, dropping a warp marker being a placement, while a phase reset drops in either audio view. Delete and disable grey out with nothing selected — their one refusal now; toggle inherit greys out in the phase-reset view and with nothing focused. The drop never greys except on a read-only tab: with warp markers showing in target view a plain press only tells you which view that drop belongs to (`Markers are placed in source view`) while its `Shift` half — the held press on a touch panel — still crosses to target view and drops a phase reset; and with phase-reset markers showing the plain press drops in either audio view since 2026-08-30, `Shift+S` alone refusing there (`Already in phase reset view` — the chord is the crossing itself, and there is nothing to cross). Beside them, closing that group, is Add to Selection (`k`), which lights up while its mode is on (see Marker focus and selection). Then the marker walk, three buttons — previous marker (`Shift+Tab`), next marker (`Tab`), and walk both tabs (`Ctrl+Shift+Tab`) — each pressing exactly the key it names; the first two grey out whenever the step would land nowhere — an empty marker collection, one whose markers are all disabled, or no enabled marker past the playhead in that direction — and walk both tabs never greys, its tab switch always acting. Then the four arrows in one line — down, up, left, right — each pressing the bare arrow key it shows, with every rule those keys have: the playhead step, the marker-lane nudge with a selection, the `Up`/`Down` tempo step, the same refusals in a read-only tab. Up and down are the tempo step and nothing else, and tempo belongs to warp markers, so they grey out in the phase-reset marker view, with nothing selected or focused, and in a read-only tab — exactly where the keys refuse. Left and right are the playhead step and the marker nudge: with no marker selected they step the playhead, greying out only at the walls — left at the very start of the piece, right at its end, where the next painted column is the frame the playhead already rests on (while something plays they stay lit, a press then stopping it); with a marker selected they grey out where the nudge cannot act — a warp marker selected in target view, or a locked tab (a phase reset nudges in either audio view since 2026-08-30). (Until 2026-08-30 all four stayed lit through every one of those refusals, deliberately, so that the pair would not blink on and off with every selection; the architect reversed that, being deliberate with his presses.) These four repeat while you hold them. A click or a tap is still exactly one step, given when you let go, like every other button here; hold instead and after a short delay — the one this program uses for every deliberate hold, set to match your desktop's own key-repeat delay — the button starts stepping on its own at your desktop's key-repeat rate and goes on until you let go, the release at the end adding nothing further because the run has already given you the steps. That is what the touch panel needs, having no keyboard. Holding with the pointer slid off the button pauses the run and sliding back on resumes it, and if your desktop has key repeat switched off these buttons do not repeat either. They are the only buttons on this row that repeat, and the only others in the program are the waveform magnify and reduce pair up in the icon row, which repeat the same way (see The top rows). In the history view they no longer make way for anything: the four history buttons that used to take these slots live up in the icon row now, so the arrows stay where they are and grey out (see Checking history). At the row's left end, just past the separator that closes off the transport three, is the playhead time in monospace — one of the two monospace cells in the program, the render player's own clock being the other (see Playing renders): the position of the moving playhead while something is playing, and of the resting cursor otherwise. It is written `MM:SS.mmm`, and a source past 59:59.999 simply reads that. Its cell is sized for the widest digits, so the numbers never shift about as they count. The wide space between the clock and the right-hand groups is bare: what is true right now is on the state text below this row instead (see The interface at a glance). In the history view the buttons that view refuses grey out here too — play/stop, the four cardinal arrows, the four marker verbs, edit flag, measure, and Add to Selection — while go-to-start, go-to-end and all three marker-walk buttons keep working, walk both tabs among them: its paired march is the view's own, stepping the difference flags on one tab and then the other, as their keys do in there (in that view those two step the difference flags, exactly as `Tab` and `Shift+Tab` do). The buttons show the same resting tooltips as the top rows, appearing above the button instead of below it.

**The overview strip** (mouse). Between the icon row and the trim bar runs a slim strip showing the whole song at once — the piece's waveform in miniature, a thin light-grey box marking the part of the song the main view is showing, and a white tick marking the playhead (the moving position while something plays, the resting cursor otherwise). The box and the tick track everything you do: pan or zoom and the box moves and resizes, play and the tick crawls across the song. In target view the strip still shows the source recording — the box stretches or squeezes through the warp to mark the same music, so it can change shape a little as you edit tempos or switch views. The strip is worked by grabbing the box, and the box is the whole of it — everything you do here moves or resizes that box, and the zoom follows from how wide it ends up. Click inside the box and you grab it where it is, no jump, and drag it along the song with the main view following. Only sideways movement counts — the strip ignores up-and-down motion entirely, so a wobbly drag cannot change the zoom. The box's left and right edges are handles, like the trim bar's endcaps: drag one and that edge of the view follows the pointer while the other edge stays exactly put — dragging outward zooms out, inward zooms in, down to the deepest zoom with the edges never crossing. Each edge is grabbed with ten pixels of slack on either side, the trim endcaps' own target, so when you are zoomed deep enough that the box is only about twenty pixels wide the two handles cover it entirely and a press anywhere on it drags an edge rather than sliding the box; and when you are zoomed all the way out, where the box fills the strip and there is no outside left, the edges are still there to grab. Press outside the box and the view centers there at once, at the zoom you already have — and the same press has hold of the box from that moment, so a pointer that goes on moving goes on panning, exactly as it would had you pressed inside the box to begin with. Nothing waits for the release either way. The edges are still resized by their own handles and nowhere else. The pointer says which of these a press would do: an edge arrow over each of the box's edges, and the left-right resize arrows everywhere else on the strip, inside the box and outside it alike — outside it because a press out there ends up sliding the box too, once its centering has run. Every drag here keeps the shape it started with for the whole drag, wherever the pointer goes. `Ctrl` does nothing on the strip — there is no separate zoom drag here any more, because the box already controls the zoom directly. The scroll wheel over the strip works exactly as over the waveform — plain magnifies the drawn waveform, `Alt`+wheel pans and `Ctrl`+wheel zooms — and the strip works the same in the history view. It draws no region, selects nothing, and never moves the playhead — everything here moves the view alone, and like any pan it wins over follow mode for the rest of the audition. On a touchscreen it all carries over exactly, with nothing done differently: a tap outside the box centers the view there as the tap lands, a finger drag inside slides the box, a drag from an edge is that edge's resize, a drag started outside the box centers the view where the finger went down and then slides the box on from there, and nothing at all happens while a finger merely rests on the strip. Two fingers do nothing on the strip at all: a pinch there neither zooms the view nor moves the box, and a second finger put down during a one-finger strip drag is ignored whether that drag has begun moving or not, the drag carrying on as it was. The strip is a one-finger surface, and the three motions above are all of it — the trim bar is the other such lane, and both work this way for the same reason: they are slim, and one finger already does everything they do, precisely. The strip is the same slim height on every machine and at every window size — only the display scale changes it.

**Playback and playhead.** `Space` starts and stops playback from the cursor to the end of what is playable — the song's end in source view, the end of the rendered preview (the trim window) in target view (`Return` and keypad `Enter` are not playback keys — they open the flag editor on the focused marker; see Warp marker authoring). Playback always issues from the playhead. `Space` says why when it will not play: `Wait for the target preview to finish rendering` in target view before the preview exists, `There is nothing left to play from here` when the cursor is at or past the end of what is playable, and `Playback is unavailable on this device` when no audio device came up at all — the same three answer the waveform's audition click. A second `Shift+Space` while an audition is running says `An audition is already running`, and one that cannot run says `One of the two tabs has nothing to play from here`. The trim window is not a launch point — to audition a span, click its start on the waveform's lower half (see Trim and the region). Nothing loops: every audition plays once to its end and stops on its own. (The one exception anywhere in the program is the render player's `Repeat one` lamp, which repeats the file it is playing and nothing else; see Playing renders.) In source view that end is the song's end — the trim window does not bound listening, since what you hear there is the file itself. In target view it is the end of the rendered preview, which is the trim window. `Shift+Space` is the **A/B audition**, for comparing the two tabs' cued spots without the hand-work: it switches to the other tab, plays a short span from that tab's playhead twice with a short rest between the two, switches back to the tab you were on, rests a little longer there, and plays that same short span from its playhead twice with the same short rest between them — then it is done and you are back where you started, ready to adjust. Each half opens with `c` on the tab it is about to play: the press runs it on the tab you are on, the switch runs it on the tab it arrives at, and the switch back runs it again — the working zoom, centred, landing in the same instant the tab changes, so you never see the old view flick past and both spots are read at the same magnification. It is the `c` key exactly, focused marker and all. The rests are the pacing of doing this by hand: a moment between the two plays for the ear to catch one and hear it again, and a longer one where the tab changes. The tab flips the instant the play before it ends, so the longer rest is silence on the tab that is about to play. Neither playhead moves; each is an ordinary play that runs to its own end (nothing loops here either), the moving scanner shows it, and each tab plays what it always plays — the file in source view, the rendered preview in target view. Anything that would stop or restart playback ends the whole sequence where it is — `Space`, a tab switch, a playhead move, a marker edit, opening a prompt or editor, or in target view any change that re-renders the preview — and leaves you on whichever tab it was on; there is no return trip once you have acted. The rests count as part of the sequence: something that lands in one of them ends it exactly as it would mid-play, and the sequence stays the running transport throughout — the play button keeps its stop square for the whole act, and `Space` in one of the rests stops the sequence rather than starting a fresh playback. It does nothing at all if a sequence is already running, in the history view, or in target view when either tab has nothing to play (no preview yet, one still updating, or a playhead outside the preview); it works on a read-only tab. The play button's `Shift`+click and its long press are the same act (see The bottom toolbar). `Left` and `Right` move the playhead one pixel. With one or more markers selected they move it *in the marker lane* instead: the focused marker moves one pixel and the playhead rides along with it — one marker, never a group, so if several are selected the press first narrows the selection to the focused one and then steps it. The cursor is always drawn, so you see it ride: it stands on the focused flag and moves with each step. Dropping the selection hands the playhead back to the waveform, where the arrows step it freely again — any deselecting route does it: a click on the waveform, `Home`/`End`, or a trim edit. With nothing selected an arrow press moves the playhead one pixel, drops the marker focus, and hides a showing trim region. `Home` and `End` jump the playhead to the trim begin and trim end, and they drop the marker selection as they go. `Ctrl+Home` and `Ctrl+End` jump to the very start and the very end of the piece instead, whatever the trim window is — the way to reach audio the window has cut off without opening the window first — and they do everything else the plain pair does. A press that would change nothing at all — nothing playing, no selection to drop, no trim region showing, the cursor already on the spot — says so instead: `The playhead is already at the trim start` (or `trim end`), and the `Ctrl` pair's reads `…at the start of the song` / `…at the end of the song`; in the history view, where every jump means the piece's ends, the song sentences answer. A keyboard playhead move stops playback — but a command that only moves the view (zoom, `PageUp`/`PageDown`, and `0` from any zoom short of the full-song view) does not, and neither does the `Up`/`Down` tempo step, which leaves the selection and the audition standing; trim edits (`Shift+[` and every pointer trim gesture) stop playback in both audio views — a trim change redefines what an audition would play, while `[`, which only shows and hides the region and writes no bound, leaves an audition running. Mouse moves are different — a click on the waveform's upper half (or on the ruler, or on an empty spot in the marker lane — the three are one surface) moves the playhead to the clicked spot at the moment you release, reseeking live playback there instead of stopping it, and a plain drag on that same surface pans the view instead (see Zoom and view); nothing happens at the press itself, so the two never fight — a still click places, a moving drag pans. The waveform's lower half acts at the release too, and runs one act of its own there: it auditions instead of placing the playhead (the right button does nothing anywhere). A scrub click stops playback if a session is running, and a click on a stopped one starts the moving scanner from that spot, so auditioning a new place is stop-then-click (each start is a fresh audition, picking up any changes to what is playable) without touching the resting playhead, the selection, or a showing trim region; it is a one-shot per click, Ableton-style — holding or dragging does nothing further, and playback simply continues until stopped; `Space` stops it as always. (A top-strip click stops playback only when it actually does something — selecting or editing a marker, or setting a trim bound; a click that claims no gesture leaves playback alone entirely, and so does a plain trim-bar click that never becomes a drag — a bound or bar drag stops playback at its first actual bound change, not at the press.) `f` toggles follow mode, which scrolls the viewport to keep the playhead in view during playback — during only: when playback ends, whether you stop it with `Space` or it reaches the end on its own, the viewport stays exactly where it was and the moving line simply vanishes. The two endings are identical in every respect. Panning away during playback wins over the chase: any pan — the plain drag, `Alt`+wheel, the touchpad, `PageUp`/`PageDown`, the `Ctrl`+drag — switches follow off for that session, and the view stays where you put it until the next launch or an explicit `f` re-enable. There is no playback speed setting: everything plays at the recording's own rate. (There was one — `playback_speed`, ten values from 0.1 to 1.0 — and it was removed, along with its `.settings` key, on 2026-08-27.)

**Zoom and view.** Zoom is continuous: `Ctrl+=` and `Ctrl+-` step one whole level per press from wherever the zoom rests, `Ctrl`+wheel steps those same whole levels one per detent (wheel up zooms in), and the `Ctrl`+drag gesture below reaches every fractional level in between (the wheel on its own magnifies the waveform instead, and `Alt`+wheel pans — below). The deepest zoom is fixed; the shallowest is the file's own full-song view — zooming all the way out always rests with the whole song visible, exactly filling the width for any file longer than the deepest level's span at the current window width (1.2 s at the 1920 px deployment width; a shorter file rests at the deepest level instead, the remainder of the width showing past-EOF silence). `0` goes to that full zoom-out, whole song in the window, and it remembers where it came from: pressing it stamps the zoom level you were at, and pressing it again with the zoom already fully out runs the `c` command at that stamped level rather than at the working zoom — so `0` twice takes you out to the whole song and back in to the magnification you were working at, on the marker you are working on. The stamp is per tab and lasts the session; `0` is the only thing that writes it — not `Ctrl+=`/`Ctrl+-`, not the wheel, not a drag, not `c` — and nothing clears it, which is what makes the round trip predictable. With nothing stamped yet, which is the first `0` of a session and also a project that opens already zoomed all the way out, the second press is plain `c` exactly as it always was, landing on the working zoom. The same thing happens when the stamped level has stopped being reachable — flipping to the target view or widening the window can bring the whole song into view at a shallower level than the one you stamped — and rather than sit there doing nothing, the second press falls back to the working zoom. The first press is purely a view command, moving no playhead and leaving the selection and a showing region exactly as they were; the second is `c`, with everything `c` does. The working zoom — the fine-tuning view (a zoom level fixes time per pixel, so its span scales with window width: 2.4 s across the waveform at the 1920 px deployment width) — is where `c` lands instead. `c` jumps the playhead onto the focused marker when one exists, then snaps to the working zoom centered on it; with no focused marker it just snaps and centers on the playhead. The waveform's drag — either half, and equally on the ruler or an empty stretch of the marker lane — is ONE gesture with `Ctrl` as its zoom switch, the mouse's version of one finger versus two on a touchscreen: dragging plain pans the view, and while `Ctrl` is held the same drag zooms instead — sideways motion, right zooms in and left zooms out, about a pivot under the pointer — with up-and-down motion ignored, so a wobbly zoom cannot slide the view and a pan cannot drift the zoom. Both halves of the gesture read the same sideways motion, and that is the point: a pinch on a touchpad or a touchscreen is a sideways motion too, only with two fingers, so `Ctrl` changes what your sideways travel means rather than which way you have to move your hand. Right zooms in because the drag is standing in for a pinch: your mouse hand plays the part of your dominant finger, and spreading two fingers apart on glass sends that finger to the right — so right is apart, and apart is in. While `Ctrl` is held the pointer's own place on screen is held still, so the zoom's travel moves the view and never the pointer: press `Ctrl` again later in the same drag and the pivot seats at the column it seated at before (unless you panned in between), and let go there and the cursor comes back on that column rather than wherever the hand had wandered. The zoom's sideways travel is the unlimited one; up-and-down motion is simply not movement. Press or release `Ctrl` at ANY moment of the drag, as often as you like, without lifting the button: each press of `Ctrl` seats the pivot where the pointer is right then — that is all pressing `Ctrl` does — and each release hands the motion straight back to the pan, with no jump either way. Where the pivot lands is a place on the screen — press `Ctrl` and it seats wherever the pointer happens to be — but what it then holds on to is the place in the SONG under it. While you zoom, that piece of audio stays where it is and the view scales around it; and when the view runs into the start or the end of the piece and can go no further, the pivot keeps its grip on the audio and slides across the screen with it rather than standing still while the song walks out from under it. That is what makes a zoom reversible: drag back the other way and you come back to what you came from. If the pivot's audio would leave the screen altogether it pins at the edge instead and takes the content it finds there, so the thing you are zooming about is always something you can see. The pointer keeps its own place on screen even though it is hidden, and it travels without limit: when it would run off one edge of the waveform it comes back at the opposite edge and keeps going, carrying whatever was left of that move, so a drag of several screens leaves it somewhere ordinary rather than stranded on the last pixel. Let go and it reappears wherever it had got to. A dim vertical stem marks the zoom pivot for as long as `Ctrl` is down — from the moment you press the button if `Ctrl` was already held — so you can see where the zoom will pivot before you move; it appears and disappears with the key itself, with no need to move the mouse. The two-finger pinch on a touchscreen shows the same mark, in the same place on the waveform, so the pivot is visible whichever way you are zooming — including when it slides along with its audio at the ends of the piece, or pins at an edge. The drag moves the view and nothing else — it leaves the playhead, the marker selection and a showing region exactly as they were, in the history view as much as outside it. Travel is unlimited while the cursor is captured — the view keeps moving with your hand however far past the window edge it goes — and on release the cursor reappears at the stem's column if you were zooming when you let go, or wherever the pointer had got to if you were panning, with no special case for a long drag. Zoom is the `Ctrl` side of this drag — plus the overview strip's box edges, which set the view's span directly (see The overview strip), the `Ctrl+=`/`Ctrl+-` keys, `Ctrl`+wheel, and the two-finger pinch on a touchscreen — nothing else. Panning is the same drag with `Ctrl` up, on the whole waveform and both nav lanes: a smooth grab that captures the cursor for unlimited travel once the drag is under way. A plain drag that never moves more than a few pixels is not a pan at all — it is the click, placing the playhead at the release (see Playback and playhead). The scroll wheel pans too, a tenth of a screen per detent, over the waveform and the whole marker strip alike — and with `Ctrl` held the same wheel zooms one whole level per detent instead, on every surface the wheel is live — the `Ctrl+=`/`Ctrl+-` step exactly, centred on the playhead rather than on the pointer (the pointer-anchored pivot is the `Ctrl`+drag's). Double-click on the trim bar — the band above the ruler that carries the trim window's bar and its begin/end endcaps, anywhere along it — frames the trim window when it is narrower than the whole song, and the whole song when it is not — with a small margin around a window and none around the whole song. It is one-way and idempotent: a second double-click on the same view does nothing, but any pan or zoom in between re-frames. This differs from the `0` key, which only ever goes to the full-song view (and, from there, back to the level it stamped on the way out). `PageUp` and `PageDown` step the viewport back and forward by a tenth of a screen per press — the same stride as the wheel, so the keyboard and the wheel pan at one speed; hold for a continuous glide.

**Waveform magnification.** `=` and `-` make the drawn waveform taller and shorter, and so does the scroll wheel on its own — up taller, down shorter, one step per detent: the picture only, never the sound. Classical material has a dynamic range wide enough that a quiet passage draws as a hairline at the height a forte fills the lane, and this is how you bring one up to something you can read. Each press is A DOUBLING — the picture comes up to twice the height it had — and the ladder runs from normal to sixteen times, five positions, with a press at either end doing nothing. It is LINEAR at every one of them: the peaks are multiplied and then clipped flat at the top and bottom of the lane, so a loud passage goes to a solid block while its quiet troughs still dip. That clipping is the point rather than a cost: you place a marker on a transient, not in a sustain, and the transients are what stay visible. Hold either key to walk the ladder. There is no reset chord: `waveform_magnification_level=0` in the settings prompt returns to normal in one go from anywhere on it. The whole-song strip magnifies with it, since a 24-pixel band is where a quiet passage disappears first. NOTHING ABOUT THE AUDIO MOVES — playback is at the same level at every setting and a render is byte-identical — and nothing about the timing moves either: no marker, no trim and no viewport changes. The setting persists in `.settings` as `waveform_magnification_level`, the count of presses rather than the height it produces — it belongs to the piece, since how loud the picture should be drawn is a fact about the material — and it works on a read-only tab and inside the history view, both being pictures rather than the piece. On a touchscreen the two icon-row buttons beside the four magnifiers do the same two things, and holding either one walks the ladder as holding the key does.

**View toggles.** `t` switches the audio domain between source and target (S/T); `p` switches the marker collection between warp and phase reset (W/P). The bare digits jump straight to a combination: `1` is S+W, `2` is T+P, `3` is T+W (each applies whichever of the two switches it needs, with everything a `t` or `p` switch normally does; pressing the digit for the combination you are already in does nothing). The same three combinations sit as buttons at the right end of the top menu row — a click is exactly the digit (see The top rows). A `t` switch carries the selection across, on both sides, with the playhead landed on the focused marker — `t` shows the same markers in another domain, so the selection travels with them. A group crosses whole: `t` keeps every selected marker selected (a showing region stays showing, drawing the same window in the new domain) and lands the playhead exactly on the focused marker's position in the new domain. `c` keeps a group too — it jumps to the focused marker and re-zooms with the others still selected; `0`, the overview, is purely a view command and touches nothing (pressed with the whole song already in the window it is `c`, and then it is `c` that keeps the group). Switching the marker collection (`p`) or the tab (`Ctrl+Tab`) is different: those change which markers you are addressing at all, so they simply drop the selection. What you get back instead is automatic and comes from where the playhead is: on arrival, if the playhead is standing exactly on a marker of the newly active collection, that marker is selected for you; if it is standing anywhere else, nothing is selected and the cursor is your playhead as usual — being one frame off is being off, not close. The tab's remembered playhead is restored exactly as you left it, which is what makes that recovery predictable: leave a tab with a marker selected and the playhead on it, come back, and the same marker is lit. `Shift+j` uses that pair on purpose: on a `label_ref` or a pass it switches tabs and lands the other tab on the marker the value comes from, so the reference stands on one tab and its definition on the other and `Ctrl+Tab` reads back and forth between them (see Warp marker authoring). Opening a session works the same way, from the saved playhead — and so does loading a render in place with `'`. Group work does not cross a switch (select again on the other side, or lean on undo/redo, which re-selects a whole touched group). `o` toggles read-only on the active tab. What it protects is the piece itself — the markers and the engine settings — and nothing else: marker, tempo, and phase-reset authoring are locked out, while navigation, playback, the view toggles, the trim window, saving and rendering all stay available. The point is a finished section you want to stop nudging by accident, not a tab you cannot work with: lock it, then go on moving the trim window to compare a passage against your other tab, re-render, and save. One navigation gesture is not exempt: with a marker selected the horizontal arrows are in the marker lane, where the same press authors, so a locked tab refuses them outright rather than falling back to a plain playhead step. Drop the selection first — a waveform click, or `Home`/`End` — and they navigate again. Saving works: `Ctrl+S` saves from a read-only tab, writing the state the tab already holds — as does the close prompt's `Save` answer, which always did. Rendering works too: `Ctrl+Alt+R` and `Ctrl+Alt+Shift+R` read the authored state rather than change it. So does the whole trim window — the bound clicks, the endcap and bar drags on the slim bar and on the region alike, the `Shift`+drag sweep, `Shift+[`, and a typed `trim_begin=` / `trim_end=` all commit in a locked tab, trim being part of the tab's own view state (with the viewport, the zoom and the playhead) rather than part of the piece; and `[`, which writes no bound at all, is legal there for the same reason and more easily. Every propagation command is blocked — `Ctrl+P` copy and the `Ctrl+Alt+P` pastes, and the measure pair `Ctrl+/` and `Ctrl+Alt+/` with them — as are undo and redo (`Ctrl+Z` / `Ctrl+Shift+Z`); to undo an edit made from a read-only tab, `Ctrl+Tab` to the writable tab first. Also blocked: `Delete`, the marker drops and nudges, the flag, BPM and measure editors, `i`, and `'`. The settings prompt does not open at all in a read-only tab — it can set the engine keys, which is the piece — so `;` is refused with a notification naming the chord and the lock (`; is not available on a read-only tab`), and picking an item from the `Settings` menu closes the menu and says `This tab is read-only`. The menu items are not greyed out; they say why instead. `Ctrl+Tab` switches the active A/B navigation tab; `Ctrl+Shift+Tab` advances both tabs' marker focus in lockstep and lands on the opposite tab — it is short for a step, a tab switch and another step, so it works inside the history view too, where the step is a step along the differences instead.

**Marker focus and selection.** `Tab` and `Shift+Tab` (the latter also reachable as the ISO left-tab key some layouts send) cycle marker focus forward and backward, moving the playhead onto the focused marker. The view always recenters on the focused marker, at whatever zoom you are already at — the walk never changes the zoom, so a wide view stays wide; `c` is the command that snaps to the working zoom — and follow mode does not gate the cycle. A step with nowhere to go — no marker ahead of the playhead in that direction, and none the walk could land on at all — does nothing at all: it does not even re-seat the playhead on the marker you are already on, and it says so on a card. The matching toolbar arrow is greyed at the same moment, for the same reason. The walk skips disabled markers and operates on whichever collection the W/P toggle has active (trim bounds are not part of the walk — `Home`/`End` jump to them). A plain click on a marker's flag — the flag is the marker's one clickable part; its stem on the waveform is a visual cue only — is the third way to bring the playhead onto a marker: it selects the marker and seats the playhead on it without moving the view at all (unlike `Tab` and `c`, which both re-zoom and recenter); it works in both views and both collections, also in a read-only tab. Anything else that changes which marker is focused brings the playhead along too: opening an editor on a marker (`Enter`, a double-click, or `m`), `Ctrl+N`, and a propagate paste, which lands on the first reset it created (the `p` swap is different — it drops the selection outright, and only the arrival coincidence auto-select can hand it a marker again; see View toggles). The reasoning: the arrows move the focused marker while a selection exists, so the playhead keeps station on the focus — the cursor is always drawn, and it would otherwise visibly rest away from the marker your next arrow press is about to move, with `Space` playing from that stale spot. Opening an editor hides a showing trim region too, exactly as the marker click does. With several markers selected, a plain flag click on one of them behaves exactly like a click on any other marker: it selects that one marker and seats the playhead there the moment you press, and a drag from it moves that marker alone — dragging never moves a group, and the drag inherits that same single selection from the press it began with. `Alt`+clicking or `Alt`+dragging does nothing anywhere. Clicking an empty spot in the marker lane works like an upper-half waveform click — a motionless click clears the marker selection and places the playhead at the release, a plain drag pans the view, a `Shift`+drag sweeps a trim window and a `Ctrl`+drag zooms; double-clicking an empty spot creates a marker at that position, selects it, and seats the playhead on it — exactly the `s` drop, so warp gets a copy-previous-tempo marker and phase reset the lead-in seed — in the collection's home view only.

**Warp marker authoring (W view).** These author warp markers. The ones that MOVE a marker run in warp's home view — warp view in source audio view — and refuse silently in target view: `s` and its empty-lane double-click twin, the flag drag, the `Left` / `Right` nudge, and the `m` BPM command, which rewrites tempo across a whole span rather than editing one marker. Everything else on this list works in BOTH audio views, because none of it moves anything: `Up` / `Down`, `Ctrl+D`, `Ctrl+N`, `Delete`, and the flag editor through both of its openings. In target view each of those redraws the stretched waveform as it lands and carries the playhead onto the marker's new place, so the flag under the cursor stays the flag under the cursor. `Up` / `Down` keeps one refusal of its own there: an *owning* marker stacked with others on one frame refuses the step, since that stack renders as a single `1.00`, so fix its tempo back in the warp source view — and a pass or a label reference refuses in either view, having no tempo of its own to step.

`s` drops a marker at the playhead copying the previous marker's tempo (its shifted form, `Shift+S`, drops a PHASE RESET instead and takes you to target view to do it — see Phase reset authoring) — so the drop normally splits a section without changing how anything sounds, where a neutral `1.00` drop in the middle of a warped section would audibly change it. Two cases are not silent, both by design. Dropping onto a frame where an enabled marker already sits (which is where the playhead is sitting right after you click a marker) leaves two markers on one frame, and the render collapses any such stack to a single `1.00` — the markers involved turn red immediately, so you see it happen rather than discovering it later. And splitting a *label definition's* section shortens the definition, so every reference to that label changes duration too: a definition's span is its meaning, and halving it halves what the references reproduce. Where there is no usable previous tempo to copy — no earlier marker, a label reference, or a stack of markers on one frame (which renders as a single `1.00`) — the new marker takes `1.00` instead. A pass marker is not one of those cases: it resolves to whatever tempo is actually sounding there, which is exactly what keeps the drop silent. Edit the tempo afterwards in the flag editor if you want a different one.

`Ctrl+N` toggles pass (inherit) status on the focused marker. `Ctrl+D` toggles the disabled flag on every selected marker (this works in both W and P views). `Delete` deletes every selected marker — label definitions included, even with live references (the orphaned references render as `1.00` with a stderr line each). `Up` and `Down` nudge the focused marker's tempo by ±0.01 — and with several markers selected they step every selected marker's tempo together by the same ±0.01, refusing the whole press if any selected marker cannot take it: a pass, a label reference, a disabled marker, a stack sharing one frame, or one already at the 0.25 / 4.00 end (the single-marker press keeps its usual behavior, including converting a pass to an owning marker — a label reference is left untouched, and the press says so, as does a single-marker press on a marker already resting at a 0.25 / 4.00 end); a run of group steps is one undo entry, exactly like the single-marker burst. `Left` and `Right` nudge the focused marker's position by one pixel — and with several markers selected the press narrows the selection to the focused marker and steps that one: moving markers is always a one-marker act. A held arrow is one undo entry, and the marker stops at the song edges. A plain click on a marker's flag selects it; dragging the flag moves the marker (no modifier — the drag begins after a few pixels of motion, so a click stays a click) — and dragging moves that one marker, even when several are selected: the press selects the marker you grabbed and the drag carries it alone, the playhead follows it, and the drag has no cancel — `Esc` while dragging does nothing, the release commits where the marker stands, and `Ctrl+Z` is how you put it back.

`j` copies the focused marker's resolved value to the clipboard — the `base` or `base*scale` text a flag editor accepts, ready to paste into another marker's editor or into anything outside the program — and `Shift+j` goes to the marker that value **comes from**: the owner a pass inherits from, or the definition a `label_ref` points at. The jump centres THIS tab first — the working zoom on the marker you are reading from, with the playhead landing on it, so the tab you are leaving is left framed on the reference whether or not you come back to it — and then switches to the other tab, so the two tabs end up standing on the reference and its definition at once, one `Ctrl+Tab` apart; over there it lands the playhead on the source marker, selects it, and centres the view on it at the working zoom too. Both tabs end framed, each on its own half of the pair. Both work on either tab and in either audio view, both are allowed in a read-only tab (neither changes anything), and both do nothing at all — silently — on a marker that has no value to resolve: an owning marker (its own tempo is on its flag), a phase reset, anything while iteration mode is on, or nothing focused. `Shift+j` also does nothing when the value has no source to name — a first marker, a reference the render could not resolve. The bottom toolbar's **Copy resolved value** button is `j`, and a `Shift`+click or a press held for about half a second on it is `Shift+j`.

`Return` or keypad `Enter`, the **Edit flag** button at the bottom right, or a double-click on the flag — three ways in, all doing the same thing — open the focused marker's flag editor, the canonical-line surface where the whole marker line is edited as text: tempo, `label_def` / `label_ref`, per-marker scale, and (with iteration mode on) the iter bracket. It is the only surface for authoring labels and per-marker scale. The editor opens on a marker-colored background (the invalid-commit flash turns it red) with the whole line selected: typing replaces it, and a bare `Left` or `Right` jumps to the start or end. Inside the editor `Enter` commits (invalid input flashes red, keeps the editor open, and puts a notification at the top right saying what was wrong) and `Esc` exits without committing. While it is open the keyboard belongs to the editor: ordinary text-field gestures work — typing, `Left`/`Right` and `Home`/`End`, `Shift` with those to select, `Ctrl+Left`/`Ctrl+Right` by word, `BackSpace`/`Delete` and their `Ctrl` word-erase forms, `Ctrl+A`, `Ctrl+C`/`Ctrl+X`/`Ctrl+V`, double-click to select a word, and `Shift`+click to stretch the selection out to where you clicked (from the caret if nothing was selected yet), which a drag from there goes on doing. The clipboard is the real one, shared with the rest of the desktop: something copied here pastes into a browser or a terminal, and a URL copied in a browser pastes into a settings field. Pasting when there is nothing on the clipboard does nothing at all — it will not wipe the selection. `Ctrl` and `Shift` combine with the motion keys the way they do in any text field. Everything else does nothing at all — `Alt` with anything included — so a stray chord cannot throw the edit away on its way to a command. The two chords that reach through are `Ctrl+S` (saves, editor stays open) and `Ctrl+Q` (abandons the edit, then the usual close routing). `Esc` is not one of them — it is the editor's own cancel key, handled inside the editor rather than reaching past it. Note there is no undo *inside* the editor: `Ctrl+Z` does nothing there, so an unwanted edit is fixed by retyping or by `Esc` and reopening. The mouse is unaffected — clicking anywhere but the editor's own text closes it without committing, and the click then does its normal work (another marker's flag selects that marker; double-clicking the same marker again just reopens the editor). That includes the menu row: clicking `File` or `Settings` while a flag edit is open discards that edit, exactly as clicking away from it anywhere else does, and the menu then drops down as usual — a menu never stands over a live edit. The rest of the top strip's buttons are the one place a click leaves the edit alone: their clicks are their keys, so they meet the same gate the keyboard does and only `Save` (`Ctrl+S`) does anything while an edit is up — everything else there is inert, just as pressing its key would be. The bottom row's buttons are their keys in the same way, which is why the **Edit flag** button commits an open editor rather than closing it: it *is* `Enter`, so with an editor up it does what `Enter` does — commit, or flash red on text the line will not take. The BPM editor opens with its bracket text selected the same way.

On screen, each marker is a small colored flag in the lane directly above the waveform, carrying its text on the flag itself — the tempo or label for a warp marker, the words `phase reset` for a phase reset — anchored at the marker's exact frame, with its stem running from the flag down through the waveform. A text longer than nine characters shows shortened to its first nine followed by `...` on the flag, which is why a phase reset's flag reads `phase res...` — the one text in the program that spends that budget by itself rather than by being typed; an iteration bracket does not count against those nine and is never shortened — the flag grows to carry it whole, because the bracket is the thing you are reading while the mode is on. The full text lives in the flag editor, and a selected marker's resolved value is not shown anywhere — press `j` to copy it to the clipboard, ready to paste into another marker's flag editor or anywhere outside the program (see Warp marker authoring). Flags of nearby markers may overlap; the later marker in the file's order paints on top, and clicking lands on whichever flag you see. Every enabled marker's stem is always visible in the marker's own color; a disabled marker dims its flag and shows no stem at all. Selection is a brightness cue: the selected marker's flag brightens while its stem keeps the calm unselected color — a selected disabled marker brightens the same way inside its dim, so selection reads on a disabled marker too. The flag editor is the flag itself unrolled: it grows from the marker's own position to fit the full text, and for a very long text the view inside it scrolls as the caret moves. The playhead cursor is the white marker-style head sitting in the marker lane, its tip on the waveform's top edge, with its white stem below; a marker's flag paints over the head where the two coincide, and when the playhead stands exactly on a marker the marker's own stem shows in place of the white one — the cursor is still there, standing on the marker, and playback still launches from it (the phase-reset lead-in audition included). A marker that renders as the fallback tempo `1.00` paints its flag and stem red — a `label_ref` to a missing or out-of-range label, a pass that ends up inheriting from a reference, or a stack of markers sharing one frame (which collapse to a single `1.00`, the whole stack reddening as one) — and neither selection nor the disabled dim takes that red away: a disabled red marker is still recognisably red, and the warning is never masked; the same red marks a stack of coincident phase resets. The red is a live display cue, so a red stack you drag apart stays red until you release. In a read-only tab flag clicks still select and seat the playhead (dragging and the editor refuse).

`Shift`+flag-click selects an inclusive range, file-manager style: it selects every marker between the focused marker — the one last clicked, plain or `Shift` — and the clicked one, in either direction, with the clicked marker becoming the new focus and the playhead seating on it — `Space` then auditions from the playhead, standing on that new focus; with nothing focused it just selects and anchors on the clicked marker. `Ctrl`+flag-click toggles one marker's membership in the selection, seating the playhead on whichever marker ends up focused — emptying the selection leaves the playhead where it is. **Add to Selection** is a sticky `Ctrl` for that gesture: bare `k`, or the button closing the marker verbs at the bottom right, lights it, and while it is lit a plain click or tap on a flag does exactly what `Ctrl`+clicking it does — it adds or removes that one marker and leaves the rest of the selection standing, with the playhead landing on the focus it leaves behind. It is there for the touchscreen, which has no modifier keys and so had no way at all to build a selection up one marker at a time; it works the same under a mouse. It reaches flags and nothing else: a click on an empty stretch of marker lane is the ordinary click it always was, and a double-click there still creates a marker. A held `Shift` still wins, ranging as it always does. The mode is legal in a read-only tab — a selection is not part of the piece — and does nothing at all in the history view, whose flags have their own selection. It puts itself out the moment anything replaces or clears the selection, so it never lingers past the run of clicks you turned it on for. A plain marker click seats the playhead on that marker, and a `Shift`-range or `Ctrl`-toggle click seats it on the marker it leaves focused (`Tab`/`Shift+Tab` and `c` land too, additionally recentering; dropping a new marker with `s` seats it there as part of the drop, and a waveform click places the playhead but selects nothing). The playhead then follows the focused marker: a nudge or flag drag carries it along, so `Space` keeps auditioning from the marker.

**Marker measures (`/`).** Any marker — warp or phase reset — can carry a MEASURE: the bar of the score that marker sits on. It is always on screen, painting as a blue box continuing the marker's flag to the right, separated from the flag's own colour by a thin dark line, so one glance says which part is the marker's value and which part is its place in the score. There is no toggle and nothing to switch on; a marker with no measure simply has no such box. It is never shortened the way a flag's own text is: the box grows to hold it, and a later marker's flag paints over the tail of an earlier measure exactly as it paints over an over-long label.

Two spellings are accepted and nothing else. A **measure number** on its own — `12` — means the downbeat of bar 12; add a fraction after a single space — `12 7/8` — to sit part-way through it. The fraction must be a proper one in lowest terms, so half way through bar 12 is `12 1/2` and never `12 4/8`. An **offset** starts with a plus and counts from the marker before it in the same column: `+1` is one bar later than that marker, `+1/4` is a quarter of a bar later, `+2 1/2` is two and a half bars later. Offsets chain, so `12`, `+1`, `+1` puts the third marker at bar 14. Bar numbers run from 1 to 99999 and denominators go up to 99. Where a movement's printed numbering starts over — a menuetto's trio going back to bar 1, say — just type the number the page prints: where the marker sits already says which bar 12 you mean. Anything else is refused when you press `Enter`: the field flashes red and stays open with your text in it, so you can fix it, and a notification says what the grammar wanted. An offset whose chain does not lead back to a measure number is still perfectly legal — it simply has no bar to resolve to yet, and nothing complains.

Three ways in, all doing the same thing: `/` opens the measure editor on the focused marker, the measure button at the bottom right does the same, and double-clicking the blue box opens it on that marker. The blue box is otherwise part of the flag — clicking it selects the marker, dragging from it drags the marker, `Shift` and `Ctrl` clicks on it do what they do on the flag — and only the double-click tells the two halves apart: double-click the flag and you get the flag editor as always, double-click the measure and you get the measure editor. The editor is the blue box itself turned into a text field, with the flag left standing beside it, and it takes the same text-field gestures every other editor in the program takes, including the real clipboard. `Enter` commits, `Esc` leaves without committing, and **committing an empty field removes the measure**. Each commit is one undo step. Unlike the flag editor, this one is not tied to a marker's collection either: it works on warp markers and phase resets alike, in either audio view, wherever the flag is painted. A read-only tab refuses it — a measure is part of what gets saved.

Every measure belongs to the one marker you wrote it on. Nothing is inherited down a label: a label reference does not pick up the measure on its definition the way it picks up the definition's tempo, because a bar number is about WHERE the marker sits, and the same bar number is simply wrong a few references later. If you want the same measure in two places, write it in both. (The `+` offset is a different thing entirely — it counts from the marker immediately before it, not from a definition somewhere else.)

On disk the measure lives on the end of the marker's own line, after a space and two slashes: `44100|1.05 //12`, `#66150 //12 7/8`, `88200|1.00 //+1/4`. Editing it by hand is fine within those rules — one line, one of the two spellings above, at most 12 characters, and never a bare ` //` with nothing after it — and a file that breaks them refuses to load with the line number, exactly like any other malformed marker line.

**Phase reset authoring (P view).** These author phase resets, and since 2026-08-30 they run in *either* audio view — target view is where the lead-in and its overlay live, and source view authors too, plainly (the old block was ruled artificial; the missing overlay and the missing lead-in are the clues you are in source view, and a reset placed there is adjusted in target view). In target view `s` drops a phase reset seeded `N/2` samples earlier in target time than the playhead (clamped to the file start, snapped to the nearest whole source frame), and the playhead moves back onto the seeded reset — the one drop that relocates the playhead, so the next audition starts at the new reset: the overlap-add Hann synthesis lead-in means a reset's output reaches full scale about `N/2` samples after its authored frame, so placing the reset `N/2` before a perceived transient lands its full-scale output on the transient (this is the offset the output-domain overlay depicts, and it exists only in target view where that overlay does; the overlay shows for a single focused reset and hides while several markers are selected, and while the history view stands, where nothing about the live markers paints; a trim region showing beside it does not hide it). In source view `s` drops the reset exactly at the playhead's frame instead — no lead-in and no conversion, the `N/2` offset being a target-time length whose aim is only visible where the overlay is. `Shift+S` drops the same phase reset FROM ANY VIEW: it switches to target view and phase reset view for you, then drops the reset at the playhead's own musical instant there and leaves it selected with the playhead on it — so a reset noticed while you are looking at the warp column costs one key instead of a trip across and back. With the phase-reset markers already showing — in either audio view — `Shift+S` refuses instead and says `Already in phase reset view`: the chord is the crossing itself, and there is nothing to cross; use `s` there (in target view it is the same drop). It is refused on a read-only tab exactly as `s` is, and in the history view like every other authoring key; one press is one undo entry, and undoing it returns you to phase reset view in target audio view, where the reset was made. The bottom row's **Drop marker** button reaches it too: shift-click it, or press and hold it, and it runs `Shift+S`. Also in target view only, `Space` auditions that alignment by starting playback `N/2` samples ahead of the playhead without moving it — the resting playhead returns on stop. `Space` does this exactly when a phase reset is *focused* — the same condition that makes the overlay meaningful — so the states that drop the focus (no selected reset, a disabled one, several markers selected) also return `Space` to its ordinary behavior, playing from the playhead. A showing trim region is not one of them. It keys on that focus and not on whether the ring is currently *painted*, so scrolling the reset out of view, zooming until the band collapses, or opening the history view — which paints no ring at all — does not change what `Space` does. `Ctrl+D` toggles the disabled flag on every selected phase reset. `Delete` deletes every selected phase reset. `Left` and `Right` nudge the focused phase reset by one pixel — and with several selected the press narrows the selection to the focused reset and steps that one (the same one-marker rule the warp column follows), stopping at the song edges exactly as a warp marker does (a press that would overshoot lands on the edge; a press already on the edge does nothing); a held arrow is one undo entry.

**Phase-reset propagation (W view, anchored on a warp-marker selection).** These copy a labeled region's phase-reset layout from one occurrence of a label to another. `Ctrl+P` copies: with one or more warp markers selected, it captures the phase-reset layout of each selected marker's own section into the session clipboard — a marker's section runs to the next enabled marker, the final enabled marker's to the end of the song; the selected markers must form one consecutive run (unlabeled markers inside it simply contribute nothing), and a disabled selected marker contributes no section of its own — but it is not a boundary either: the span under a disabled marker belongs to the preceding enabled marker's section, so the phase resets lying there copy and paste with it (and a paste clears the destination's resets across that span like any other part of the matched range). `Ctrl+Alt+P` pastes: anchored on one selected warp marker, it materializes the clipboard's resets onto the destination region, scaled to the destination's durations, after a confirmation prompt. `Ctrl+Alt+Shift+P` pastes state only: it aligns the enabled/disabled state of the destination region's resets to the clipboard, in order, without moving anything and without a prompt. All three apply a 100 ms tolerance when deciding which block a phase reset belongs to: a reset falling within 100 ms before a block's owning warp marker counts as part of that block rather than the one before it. Copy captures such a reset with the block, and paste reproduces it at the same offset before the destination marker (clamped to the start of the file if that offset would fall before time zero). The tolerance is a fixed value, independent of the engine window size. All three are warp-view gestures and work from either audio view — the phase-reset propagate is the one authoring action that starts in the warp view and ends in the phase-reset target view (the measure propagate below switches no view): on completion it drops you into target view with the phase-reset collection active. `Ctrl+Alt+P`, when it materializes at least one reset, selects exactly those it just created — the first one focused, the playhead on it — so you can inspect the result by eye without an undo round-trip; `Ctrl+Alt+Shift+P` (it only flips flags on existing resets, creating none) and a `Ctrl+Alt+P` run that materializes nothing (an anchor with no eligible destination blocks) instead leave you with nothing selected at all — a paste that created nothing changes nothing — and the playhead resting on the anchoring warp marker's position in the target domain, where the view switch put it. On an empty clipboard or the wrong selection count they do nothing and say which it was. A paste that pairs no block at all — the destination produced none — also says so rather than leaving you looking at a fresh view of an unchanged piece; a run that paired blocks and simply had less to do than it might have stays quiet, having done what it had.

**Measure propagation (W view, anchored on a warp-marker selection).** The same idea for the measure boxes: it carries a run's bar numbers from one occurrence of a passage to another. `Ctrl+/` copies — with one or more warp markers selected, forming one consecutive run, it captures each selected marker's label and its measure into the session clipboard. Only LABELLED markers take part, on both sides: the label is what the paste matches on, so an unlabelled marker never carries a measure across, and a disabled marker is skipped exactly as the phase-reset propagate skips it. A marker with no measure at all is captured as an empty slot rather than being passed over.

`Ctrl+Alt+/` pastes — anchored on exactly one selected warp marker, it walks forward from there over the labelled markers and lays the clipboard onto them in order, stopping the moment a label does not match what the clipboard expects and telling you where in a notification. Before anything is written it asks for an OFFSET: a small dialog with `0` already in it, and whatever number you leave there is added to every plain bar number it writes. That is the whole point of it — pasting a repeat is offset `0`, pasting the same music into the recapitulation is the flat number of bars between them, and a negative number runs it the other way. `Enter` pastes, `Esc` abandons it. Measures written as a `+` offset are copied across unchanged, since they already count from the marker before them; an empty slot in the clipboard CLEARS the measure on the marker it lands on. If the offset would push any bar number below 1 or past 99999, nothing is written at all — the dialog flashes red and stays open so you can correct the number, with a notification saying so. Typing something that is not a plain whole number is refused the same way. The whole paste is one undo step, and unlike the phase-reset paste it leaves the view, the playhead and the selection exactly where they were.

**Trim and the region.** The trim window is what makes working on a passage quick: a render covers the window rather than the whole piece, so a stretch you are shaping comes back in a fraction of the time and can be heard again after every change — and in target view what you hear is that same window, from its start to its end. That is what the window is for, and the rest of this section is how you put it where you want it. The trim window and the region you draw on the waveform are one thing seen two ways. The window itself is a pair of bounds that always rests somewhere — it starts at the whole song, the begin endcap on the first frame and the end endcap on the last — and it is always on display in the trim band, the slim bar above the timestamp ruler with an endcap at each end. That bar is nine pixels tall, which is right for a pointer and hopeless for a fingertip, so the same window can also be drawn across the whole height of the waveform, where there is room to work with it: that drawing is the region. It is not a copy of the window and not a scratch span you commit later. It is painted from the trim window every frame, so the bar and the region can never disagree, and anything that moves one has moved the other already. `[` shows the region and hides it again, and it is the one way to do either by hand — the dashed-rectangle button in the icon row, **Show trim region**, is the same act, and it lights for as long as the region is up. The button keeps that one name whichever way the next press will go: the lamp is what tells you, exactly as the read-only padlock's does. Showing also brings the window into view: if the span fits at the zoom you are at, the view scrolls to it; if it does not, the zoom opens out until it does, exactly as undo does when it restores a group of markers you cannot see. Showing it over a window that is still the whole song works exactly the same way — the region simply covers everything — and a notification says `The trim covers the whole song`, so a drawing that reaches both edges does not read as a drawing that failed. Hiding discards nothing whatever — the trim window is untouched, and showing it again draws the identical region — which is what lets the program hide it for you the moment you turn to other work. Within the span the canvas lifts to a lighter shade and the waveform ink lifts with it, so the region reads as one lit stretch of the picture rather than as a pale ground behind unlit content; the playhead cursor is drawn straight across it as it is drawn anywhere else, and it selects no markers and launches nothing. Three motions on the region write the trim. Drag one of its two bounds and that bound follows the pointer while the other stays exactly put — it is the trim bar's own endcap drag on a bigger surface, so it stops on its partner, and releasing the two coincident opens the window back to the whole song. Drag anywhere inside it and the whole window slides, keeping its width, stopping when either end reaches the start or the end of the piece, so a window already covering everything simply does not move. And `Shift`+drag sweeps a new window outright, from where you pressed to wherever the pointer is, with nothing to commit afterwards and no need to have shown the region first: the press puts the playhead at the click and clears the marker selection, the drag writes the window live with the cursor riding the moving end, and the release parks the playhead at the new window's start. The region appears as you draw it, not as you touch down — it comes up with the first bit of the window the drag writes, so what you see is the stretch you are making and never the one you are replacing — and it goes away again the moment you let go. A still `Shift`+click, which writes no window at all, shows nothing: it is a playhead placement and nothing more. That is deliberate: a sweep says "this exact stretch", and once you have said it the big drawing is in the way rather than useful. The window itself stays, on the bar where it always is, and `[` brings the region straight back if you want to look at it or adjust it. The sweep works on the whole navigation surface — both halves of the waveform, the ruler, and the marker lane's empty stretches — while the other two are the waveform's alone, the ruler and the marker lane staying plain navigation surface even where the region covers their columns, so a pan and a zoom are always within reach. On a marker's flag, `Shift`+click is the range select instead (see Marker focus and selection). A sweep sets exactly the window you draw, however narrow — there is no minimum width. If the stroke ends where it began, so that the two bounds land on the same frame, the trim resets to the whole song: that is the same escape a bound drag has always had, where dragging one bound onto the other puts the whole piece back. A very short window is legal and simply renders short; if it comes out so short that it rounds away to nothing at the current tempo, the render says so on the terminal and gives you the untrimmed piece instead of failing. There is a consequence worth knowing about: a `Shift`+drag that wobbles more than eight pixels and comes back has still swept, and leaves that narrow window behind rather than the one you had. `Shift+[` is the way back. A plain drag on the waveform outside the region is the pan exactly as before, and a still click inside it is not an adjustment either — it is the ordinary waveform click for the half you clicked on: on the upper half it places the playhead and hides the region with it, which is also how you put away one that covers the whole piece, and on the lower half it auditions the span from the click and leaves the playhead and the region where they were. `Ctrl` still zooms wherever it zooms, `Shift` still sweeps a fresh window from wherever you press, inside the region or outside it, and `Esc` mid-drag does nothing — gestures have no cancel, the release rests what stands. Selecting markers draws no span of its own: a `Shift`-range or `Ctrl`-toggle multi-selection shows each member's brightened flag with the cursor standing on the focused one, and deleting selected markers leaves nothing behind. There is one rule for when the region goes away by itself, and it is worth learning instead of memorizing a list: **the region hides when you move the playhead, when you touch a marker, and when a sweep ends.** Moving the playhead means moving it in the music — a click that places it, `Home` or `End`, the arrow steps, a `Tab` walk, `c`, or any marker command that lands it. Touching a marker means clicking or tapping its flag, whichever button or modifier you use. And a sweep is the one gesture that puts the region up itself, so it is the one that takes it back down — a stroke that drew a window puts that window away at the release, and one that turned out to be a still click had nothing up to put away. `[` is the way to put the region away by hand — the same key that put it up. Everything else leaves it alone, and the reasons are worth having in the same order. **Moving the picture is not moving the playhead**: pans, the wheel, every zoom and the whole overview strip move the window you are looking through, not the cursor. **Changing what you are looking at is not moving it either**: a tab switch brings that tab's own cursor forward, and a switch between source and target maps the same musical instant into the other domain rather than moving it, so both leave the region up — as does switching between the warp and phase-reset collections, and a whole visit to the history view. That last one comes with an answer of its own: the history view plays nothing and renders nothing, so a window whose job is to shorten both has no work to do in there — `[` is inert and its button is greyed, and a region you carried in stays up until something hides it and then waits for you outside the view. **And trim's own gestures never hide it**, the sweep's ending aside: the region would vanish the instant you dragged its own bound — this holds even though every trim write parks the playhead, because that is the trim moving the cursor rather than you leaving. Auditions leave it alone too; playing a span is not moving the cursor.

Every trim write parks the playhead at the new trim start and clears the marker selection as it goes: the `Shift`+drag sweep at its release, the `Ctrl`/`Ctrl+Shift` bound-set clicks, an endcap or bridge drag when you release it — on the slim bar or on the region, they are the same two drags — `Shift+[`, a typed `trim_begin=`/`trim_end=` for the active tab, and the reset a crossed or coincident pair falls into (which lands the playhead at the song's start, that being the full window's). What you hear next starts there: in target view that is the window you just made, from its start, and in source view it is the song from that point on (source listening is not bounded by the trim window). A press that refuses moves nothing. The trim window is always set: it starts at the whole song and every trim state is a position of those two bounds, the bar and its endcaps always visible in the trim band. A window at the full song renders exactly the untrimmed render, and a narrower one renders its span. `Shift+[` maximizes the window back to the whole song and puts the playhead at frame 0 with it (an already-full press moves nothing and says `The trim already covers the whole song`), and it has three routes: the key, a `Shift`+click on the Show trim region button, and a press held on that button for about half a second — so the way out of a trim window never wants a keyboard. In the sidecar the four trim keys always carry actual frame numbers. The endcap drag cannot move a bound past its partner: the moving bound stops on the resting one, and releasing it there — the two coincident — resets the pair to the song edges and says so in a notification, which makes dragging one handle onto the other the quick way to clear the trim by hand. A pair set equal or crossed by other means (a typed settings value) resets to the song edges the same way at its commit. On the trim bar — the slim band above the timestamp ruler — `Ctrl`+click moves the begin bound to that spot and `Ctrl+Shift`+click the end bound — when you let go, this being the one click in the program that waits for the release, because the same press is also how you grab the bound to drag it — and dragging instead of letting go sets the bound and then carries on moving it, like an endcap drag (a click that would land a bound on or past its partner moves nothing and says `A trim bound must stay inside its partner`); when the window is wide enough, a small light square outline on the bar marks its midpoint — purely informational, it takes no clicks and disappears only when the bar is too narrow to hold it; a plain click on the band does nothing at all unless it becomes a drag — nothing on this bar summons the region on the waveform, that band being small enough to mean you have a pointer in your hand and a bar you can already see, and `[` is there when you do want the big surface; a bound or bridge drag deselects markers and stops playback at its first actual bound change, and moves the playhead only once, on release. A plain left-drag on a bound's endcap drags that bound (the thin cap is grabbed with ten pixels of slack on each side; on a trim window drawn narrower than about twenty-four pixels the two slack bands meet and cover the bar between them, so the bridge drag below needs a zoom in first — or the region, whose two bounds take the same ten pixels but whose middle is as wide as the window is on screen), and a plain drag on the bar between them drags the pair as a fixed-width window, preserving the gap during motion (a drag begins after a few pixels of motion; the ruler and the marker lane below are no part of the trim bar's grab band, and they stay plain navigation surface even where the region reaches across their columns). On the waveform a plain drag pans the view like anywhere else, unless the region is showing and the drag starts inside it. A trim bound's column on the waveform is not a handle of its own — with the region hidden, a click over it is just a waveform click — and the bounds are not selectable items either: no clicking, no `Tab` focus, no `Delete`. Trim sits outside undo: an edit is committed the moment you make it and no gesture has a cancel, which is the whole reason the big surface is worth having — it is where you can see what you are doing while you still have hold of it. Release snaps each moved bound independently to its painted pixel column, so the stored gap can change by at most one source frame. Only one trim falls back to an untrimmed render, with one stderr line: a window whose rendered span would round below one output sample. Trim is per-tab and excluded from undo and redo.

**Modes (W view).** Both modes author warp tempo, so both belong to the warp view and do nothing at all in phase-reset view. BPM mode is entered from warp's home view — warp view in source audio view — and in target view it refuses and says which view it belongs to. Iteration mode is not view-bound at all: `i` toggles it in warp view from either audio view, the mode and its brackets survive switching between source and target in both directions, `Ctrl+Alt+R` renders the sweep from either view, and a bracket is *typed* in either view too — it is typed in the flag editor, and the flag editor opens in both. Exiting iteration mode — by any route — clears every iteration bracket, so a bracket exists only while iteration mode paints it. Both modes have one place for the mouse, the `Series` menu in the menu row: `BPM` and `Iterations`, each row pressing exactly the key it names (see The top rows). `m` opens BPM mode on the selected markers' sections as an editor session on the bottom row: `Esc` abandons it (wiping the typed values), `Enter` dispatches the sweep and closes it; while the editor is open, `m` is just a typed character. Iteration and BPM modes are mutually exclusive — entering BPM mode forces iteration mode off (clearing its brackets). Both are front ends for the same workflow: render a spread of variants, audition them in the render player (`l`), and load the one you want in place as the new baseline (`'`; the render commands below cover playing and loading in place). They differ only in what they vary and how the variant is expressed.

Iteration mode varies a marker's base tempo by a small additive offset. With the mode on, a warp marker's flag edit accepts an inline bracket appended after the tempo token, `+[<start>,<end>]` with `start <= end` — for example `+[-0.02,+0.00]`, which enumerates the offsets −0.02, −0.01, and 0.00 (the range is stepped in 0.01 increments, inclusive of both ends; each bound is a signed two-decimal value within `[-4.00, +4.00]`, and the base tempo plus either bound must stay inside the tempo bracket `[0.25, 4.00]` or the commit red-flashes and says so). Several markers can each carry a range; `Ctrl+Alt+R` then renders the full Cartesian product, one file per combination, each marker's offset added in exact cents to its own base tempo for that cell, into a batch folder under `tmp/` ready to audition. While iteration mode is on, `Ctrl+Alt+R` means the sweep and nothing else — it is the same render key you already know, aimed at the mode you are in — and the sweep turns the mode off when it fires, which clears the brackets with it. To sweep a marker across a single value rather than a range, give a degenerate range like `+[-0.02,-0.02]` — it is still an iteration cell and still renders with the rest. The sign is mandatory and exactly two decimal places are required on every value, so `+0.00`, not `0` or `0.0`. Brackets are session-only and never serialized: removing the bracket (or committing the all-zero `+[+0.00,+0.00]`) clears the marker's range, and exiting iteration mode clears them all. A tempo change never clears a bracket on its own — the bracket rides the new base tempo instead, its bounds silently narrowing where needed so that the base plus either bound always stays inside the tempo bracket, so no sweep cell can ever leave it.

BPM mode varies the rendered tempo of an explicit span to hit a range of target BPMs. Select one or more consecutive warp markers and press `m`: the first selected marker owns the span, and the span covers each selected marker's own section — a marker's section runs to the next marker that takes part in the render, so a disabled marker never closes a section, and a marker with only disabled ones after it owns the section to the end of the song — so the last selected marker's section is included, and it runs on past any disabled markers trailing the selection. Disabled markers take no part in the act at all: they never close a section, so the span is measured as if they were not there, and no sweep cell writes to one — a disabled marker inside the span keeps its own tempo instead of being flattened to a pass, and a disabled marker outside the span is not rescaled. Re-enable one later and it carries the tempo it had when you disabled it. The enabled markers inside the span are the ones converted to a pass in every sweep cell, so the span renders at one tempo. None of the enabled markers in or bounding the span may be a `label_ref` — the span's tempo is rewritten on commit and a reference takes its tempo from its definition — the owning marker may not be disabled or share its frame with another enabled marker (a coincident stack renders as tempo 1.00, so a span owned from inside one cannot take a tempo), and every selected marker must either be a pass or carry the owner's own tempo (the same base tempo and the same typed scale — the span renders at one tempo, so a run of differing tempos has no single-span meaning), so `m` refuses in those cases, and in each of them a card names the rule the selection broke — the column, the view, an empty selection, a selection that is not one consecutive run, a label reference in or bounding the span, an owner that does not own its tempo or is disabled, an owner sharing its frame with another, or a run of differing tempos. One press, one card, naming the first rule it failed. The editor's field is authored as `<beats>@[<lo>,<hi>]` — for example `36@[210,220]`, meaning the span spans 36 beats and should be rendered once at each integer BPM from 210 to 220 inclusive (BPM bounds live in `[10, 400]`). The beat count and the span's measured duration (owner marker to the span end — the next enabled marker after the selection, or the end of the song) fix the source tempo, so each target BPM resolves to a concrete base-tempo-and-scale pair; a target whose derived base tempo would leave the tempo bracket is refused, never clamped. Each cell rewrites the span to that pair and then keeps the rest of the map in proportion: every enabled marker outside the span that owns its tempo is rescaled by the same ratio the owner's tempo changed by, rounded to the nearest cent (ties to even, as everywhere on this project's grids), while passes and references keep following what they follow — so re-tempoing one section re-tempos the whole piece uniformly instead of bending only the selected span; a target whose rescaling would push any marker out of the tempo bracket is refused at the commit too. Any refusal here — a bracket typed in some other shape, either of those two — flashes the field red, keeps it open, and puts a notification at the top right saying which of them it was. What the render normalizes to 1.00 on its own — the stretch before the first marker, a leading pass, a reference whose implied tempo leaves the render's envelope (a red flag) — stays at 1.00 in every cell, exactly as it does under any other tempo edit. `Enter` renders the sweep — one file per integer BPM in the range — into a batch folder under `tmp/`, wipes the typed values, and closes the mode; re-entering always opens on an empty field — the whole value is typed from nothing, and the editor never seeds a partial bracket. Loading a BPM cell in place (via `'`, by the cell's WAV entry name — the same load-in-place path as any render) rewrites the span's tempo: the entry's frozen sidecars already carry it, so the owner takes the computed base tempo, every enabled span-internal marker is set to pass so the span renders at one tempo, every enabled owning marker outside the span — the marker after the span included — takes its rescaled tempo, disabled markers keeping their own values wherever they sit, and the computed scale (full double precision) is written to the settings as the global scale. The settings `bpm` field records the render you loaded in place as a descriptor — for example `36 beats @ 220 bpm from 00:32.008 to 00:46.562` — for provenance only; the engine never reads it, though like every engine setting it participates in render identity, so editing it makes the next render fresh.

**Settings.** Bare `;` opens the settings prompt — the bottom row's editor, whose field takes a line typed as `key=value` — in a writable tab: a read-only tab does not open it at all, from `;` or from the `Settings` menu, since the prompt reaches the engine keys (see View toggles). The prompt accepts any printable character your keyboard produces, accented and other non-ASCII letters included (the free-text values — `title`, `bpm`, `notes`, `url`, `cover` and `projects_repo` — carry them verbatim through their file and back; the keys and the value vocabularies stay plain ASCII, as does a marker label), and the line is split on the first `=`, so the value may itself contain `=` — a `url=` carrying a `?v=` query parameter, for instance, commits intact. The key must be whitespace-free; keys with a restricted vocabulary reject an out-of-vocabulary value at commit with a red flash — the typed value boxed in the same filled red a marker flag turns — and a notification at the top right naming the reason: an unknown key, a value the vocabulary does not take, or a title that would make the render overwrite the source recording. Every key that can appear in a `.settings` file is settable here — the engine keys, and every GUI-kind key (`follow`, `waveform_magnification_level`, `active_audio_view`, `active_markers_view`, `active_tab_view`, and the per-tab `viewport_start` / `zoom` / `playhead_cursor` / `trim_begin` / `trim_end` / `read_only`) — and so are the two settings that belong to this computer rather than to the piece, `gui_scale` and `projects_repo`, which live in their own small config file along with `projects_path`, `last_project` and `sync_path` (see Per-device settings). A GUI-kind commit behaves exactly like the key's own gesture: it runs the same code, takes effect immediately, is not undoable, and persists on the next `Ctrl+S`; the two per-device settings settable here are written to their own file the moment you commit them, so `Ctrl+S` has nothing to do with them. Values follow the file's strict vocabulary: zoom must be a valid zoom level; trim bounds are whole source-frame numbers inside the audio — a bound committed onto or across its partner resets the pair to the song edges, and the `.settings` file mirrors this, always carrying the four trim lines as actual frames; trim commits like every other per-tab key wherever this prompt opens at all, trim being view state rather than part of the piece — though the prompt itself does not open in a read-only tab, so on a locked tab that means typing `tab_B_trim_begin=` for the OTHER, locked tab from your unlocked one; `gui_scale` is a whole number of percent from 50 to 350 — the interface's rendering scale, applied immediately at commit: the whole interface resizes by it, and the new value is written to the per-device config right there; `waveform_magnification_level` is a whole number from 0 to 4 — how many doublings of the waveform picture's height you want, 0 being normal (see Waveform magnification), applied immediately, with anything outside that range red-flashing and saying so. Keys for the inactive tab write that tab's stored state, picked up when you switch to it. `Tab` after a key fills in that key's current value for recall and editing — type `notes=` and press `Tab`, and the line becomes `notes=` followed by whatever is stored there. This works for every settable key. `Tab` follows one rule in every one of the bottom row's editors: it completes what you have typed if there is anything to complete, and otherwise steps between the text field and the `OK` and `Cancel` buttons — so a second `Tab`, or a `Tab` on something that completes to nothing (an unrecognised key, a value you have already started typing), moves the focus instead (`Left` and `Right` then move between the two buttons, and `Enter` presses the focused one). `Shift+Tab` always moves the focus backwards through the same stops and never completes anything. `Enter` (or the dialog's `OK` button) commits, `Esc` (or `Cancel`) cancels, and `Ctrl+Q` abandons the edit and closes.

Four settings fields are provenance: they are carried in `.settings` and never read by the engine, though like every engine setting they participate in render identity, so editing one makes the next render fresh. (Of the GUI-kind keys, the preference keys — follow, waveform magnification, and the two per-device ones, GUI scale and the projects repository — are not part of render identity and never force a render; the per-tab trim keys are part of the render recipe, and a trim or view-state commit re-previews exactly like its gesture.) `bpm` is written automatically when a BPM-sweep cell is loaded in place (described under Modes above); `url`, `notes`, and `cover` are free-text fields you type through the settings prompt. None of the four is value-validated — any value is accepted verbatim, including empty — though like every settings key the line itself is required (every canonical key is present in every `.settings`; a missing key fails the load). They annotate a render with its source, its target, working notes, or a cover-art reference. Each holds a single line, since the `.settings` format is line-based.

**Render dispatch.** `Ctrl+Alt+R` is the pipeline's destination. In iteration mode it is the iteration sweep (described under Modes above); everywhere else it is a single one-shot render of the current authoring state, written into the project's own `render/` folder — the WAV deliverable named by the `title` setting (`<title>.wav`), and the folder is created for you the first time; the frame-map pair goes to `~/.cache` as described under Output above. It is the only render that lands in `render/` rather than inside a `tmp/` batch folder — the final deliverable, as opposed to the audition outputs the other dispatches produce. A successful one also clears the folder of every other deliverable: `render/` holds the current title's `<title>.wav` and `.fingerprint` and nothing more, so changing the `title` setting and rendering again replaces the old pair rather than accumulating one per name (the render player's listing keeps the same rule; see Playing renders). The headless `warptempo_cli` writes the same deliverable but does no such clearing — after a CLI render under a new title the old pair stands until the GUI next lists the folder or renders into it. A render dispatch kills the running render and takes its place; `Esc` stops both the running render and any parked command behind it. (A dispatch identical to the running render simply restarts it — the `.fingerprint` reuse below then makes that restart finish immediately when the deliverable is already current, so an accidental re-press is still cheap.) An output path that resolves to the source audio itself is refused with an error rather than overwritten (change the `title` setting). Before rewriting an existing same-title deliverable, the render checks that output's `.fingerprint` sidecar: if the sidecar exactly matches the current authoring/render inputs and the on-disk WAV identity, the render finishes immediately and writes nothing, because the deliverable has proved it is already current; otherwise the normal render/reuse path publishes the current deliverable through staging and rename. The `.fingerprint` file appears next to deliverable WAVs and records the exact render identity used for reuse: source file identity, markers, phase resets, the full engine settings block — the naming/provenance fields (title, bpm, notes, url, cover) included — and trim bounds. Editing any engine setting, provenance included, makes the next dispatch render fresh; those fields change about once per movement, so the occasional redundant re-render is the accepted price of one simple identity rule. The file is not audio and is safe to delete; deleting it just prevents that output from proving it is already up to date, so a later `Ctrl+Alt+R` may re-render or republish. Do not hand-edit it.

The batch dispatches stage candidates for auditioning rather than producing the final file: the iteration and BPM sweeps are dispatched from their own modes (documented under Modes above) and render into a numbered batch folder under `tmp/` (`N_iterations` / `N_bpm`; pressing `Esc` between entries drops the remainder). `Ctrl+Alt+Shift+R` renders one miscellaneous cell (in iteration mode it renders nothing and says `Turn off iteration mode to render one file` — the miscellaneous render is a plain-mode act): the exact same render a plain-mode `Ctrl+Alt+R` would produce, but written as the next numbered WAV inside the most recent `N_miscellaneous` folder (a new one is created when the most recent batch folder is not miscellaneous), so one-off keepers accumulate as ordinary `tmp/` entries — auditionable in the player (`l`) and loadable in place with `'` — instead of overwriting the deliverable in `render/`. Pressing it again with unchanged state adds another identical cell (cheaply, via the render cache).

**Playing renders (`l`).** `l` opens the render player: an in-program player for the WAV files this project has produced. It needs no external program and it is the same on the laptop and on the tablet. A list appears across the lower part of the window, in the place the on-screen keyboard uses — always the same band, from the middle of the waveform down to the bottom row, whether the folder holds two files or forty — and the bottom row becomes the player's transport for as long as it stands. The list starts at the project's own two output folders — `render`, holding the deliverable, and `tmp`, holding the batch folders — and you walk into them the ordinary way; every folder below the top shows `..` as its first row. `render` is a one-file folder: it shows the current `title` setting's `<title>.wav` and nothing else, and listing it deletes any other `.wav` or `.fingerprint` sitting there, so a deliverable rendered under a name you have since changed is cleared away rather than offered. `render` does not appear at all when the current title's wav is not there. Each listing is read when you enter it, so a render that finishes while the player is open appears the next time you enter its folder.

**A click opens the row**, one click or one tap: a folder is entered, `..` goes up one, and a WAV starts playing from its beginning. `Enter` does the same to the highlighted row. The `Play` button and `Space` answer the transport and nothing else: while something is playing they pause it, while something is paused they carry on with it, and when nothing is going they play the current file from its start — the one that last played, whatever the list is showing. With nothing played yet they do nothing; click a file to start one. `Stop`, the button beside them or `v`, ends the playing and leaves the file at its beginning, so `Stop` then `Play` starts the track again from the top. (`v` is the stop key everywhere a media player has one — it is Audacious's and Winamp's, and this row is built after Audacious's; it used to be `s`, which is the key that drops a marker everywhere else in the program.) `Up` and `Down` move the highlight, the scroll wheel scrolls the list a row at a time, and `Backspace` goes up one folder.

What is playing and what is highlighted are two different things: the playing item keeps its own place, wears the play glyph on its row, and goes on playing while you look through other folders. `Previous` and `Next` (`,` and `.`) step through the WAVs of the PLAYING item's folder, and `Shift+,` and `Shift+.` — or a shift-click, or a long press, on those same two buttons — jump to the first and the last file of it. They are the same two keys the history view walks checkpoints with, shifted ends and all, so one pair of keys means "step through this list, and jump to its ends" wherever you are. When a file ends the next one in that same folder starts by itself. It never crosses into another folder and it never wraps — at the last file of a folder it simply stops, with the item back at its start. Pressing `Play` there starts the folder's FIRST file rather than replaying the last one, so a folder you have listened through is one press away from starting again. Whenever the player moves to another file on its own like this — stepping, jumping to an end, advancing at a file's end, or starting the folder over — the highlight goes with it, as long as the folder you are looking at is the one playing; if you have walked off into another folder, your place there is left alone. Nothing repeats on its own unless you ask it to: `Repeat one` (the last icon button on the row, or `r`) is a lamp you can leave lit, and while it is lit the playing file starts again at its own end instead of moving on. It is the one thing in the program that plays anything twice by itself, it is off every time the player opens, and there is no repeat-all — the end of a folder is one `Play` away from the top of it.

The transport row reads left to right: `Previous`, `Play`/`Pause`, `Stop` and `Next`, a divider, the progress bar, the clock — the position and the length of what is playing — another divider, the `Repeat one` lamp, and then, over at the right-hand end, `Load in place` and `Close`. The bar is the slider your desktop draws everywhere else: click anywhere on its track and the sound jumps there at once, or grab the round handle and drag it — the sound carries on where it was while you drag, and jumps when you let go. It is live only while something is playing or paused; with the transport stopped the bar rests where it is and a press on it says `Start playback before seeking`. Its blue dims while the window is not the focused one, as the rows at the top of the window do. `Left` and `Right` step five seconds back and forward, `Home` goes to the start of the item and `End` goes to its end — all four say `Start playback before seeking` while the transport is stopped, the same as the bar, since a stopped transport has no position to move, and all four say `No render is loaded to play` with nothing loaded at all. `End` is a seek and not a skip: it puts the playing file at its own end, and what happens next is what always happens when a file finishes — the next file in the folder starts, or the folder ends, or `Repeat one` plays it again. `Previous` and `Next` say which end of the folder you are at when you are already at it, and `Backspace` at the top of the player's folders says so. Since 2026-08-30 the row's buttons grey out whenever their press would do nothing, exactly as the toolbars above do: `Previous` and `Next` with nothing loaded and at the folder's ends (a greyed one takes no `Shift`+click either — the jump to that end would land where you already are), `Play` with nothing loaded at all, `Stop` when the transport is already stopped at the start of its file, and `Load in place` on a read-only tab or when the highlighted row is not a batch render; `Repeat one` and `Close` never grey. A greyed button's click does nothing and says nothing — the grey is the message — while the keys keep their own answers above. `Esc`, `l` again, or the `Close` button closes the player and hands playback back to the view you were in; `Ctrl+Q` and closing the window take it down first and then ask their usual question.

While the player stands it owns the window: every button outside it greys out and ignores the pointer, clicks anywhere else do nothing, and `Ctrl+S` (which saves as always) and `Ctrl+Q` are the only keys that reach past it. Opening another project is refused until you close it. The player refuses to open at all with nothing to play, saying "Nothing to play: no renders under render/ or tmp/"; a WAV that is not at the source's own sample rate and channel count is refused with a line of its own rather than converted, and nothing else changes. Nothing is ever rendered by the player, and a render running in the background carries on while you listen. `l` still works on a locked tab, and so does its icon-row button — playing a render changes nothing. Loading in place is what the lock refuses, saying `This tab is read-only`.

In the car, the point of it is to start a render parked, without leaving the program. On the tablet the car's own buttons work too over Bluetooth — play/pause, next and previous, and skipping forward and back — and the head unit shows what is playing; a car `Play` at the end of a folder starts that folder over, exactly as the button does.

**Loading a render in place (`'`).** Loading a render in place makes that render's recipe your new authoring baseline. Outside the history view, `'` opens the render player and the player's `Load in place` button does it on the highlighted batch cell (see Playing renders above) — `'` again inside the player is that button's key. It asks first: `Load` (the entry's name) `in place?` with `OK` and `Cancel`, where `Enter` is `OK` and `Esc` is `Cancel`, and only the batch cells under `tmp/` can be loaded — the deliverable in `render/` carries no recipe, and the button says so rather than doing nothing. When it succeeds the player closes. There is no other way to load a render in place: the player is the one road to it. Inside the history view `'` means the same verb over a different thing — it asks about the checkpoint or session state you are looking at and loads that instead of a render (see Checking history below), so the key reads the same everywhere and what it can reach depends on where you are. An entry is named by its path relative to `tmp/` — `<batch-folder>/<basename>.wav`, for example `1_iterations/01.wav`, always folder-qualified — and that is the name the player's confirmation shows you. A load is refused while a render is running or parked, with a notification that says `Cannot load in place while a render is running` — cancelling that render means closing the player first, since inside it `Esc` closes the player — and on a locked tab it is refused with `This tab is read-only`; if the chosen entry's WAV has gone missing or a sidecar is malformed, the load is refused, nothing changes, and the notification names the reason and the file (the full path goes to the terminal).

On a successful load-in-place you get the entry's RECIPE and nothing else: its markers and its engine settings, applied on top of what you have. Everything about where you are stays where you are — the view you are in, the marker column you are in, the tab you are on, the window you are looking at, your trim, and every preference. That is the whole rule, and it is worth stating as one: **a load in place writes exactly what one press of `Ctrl+Z` takes back.** Trim is outside it for that reason — trim has no undo, `Shift+[` being its recovery — so a load in place never moves a bound you set. The entry's sidecar does record the tab, the view and the window the render was queued from, because a settings file is always a whole one; the load simply reads past all of it. The load-in-place is one cross-file undo entry (the marker pair plus the outgoing engine settings), so `Ctrl+Z` puts back what you had and the history view will show you what the load changed. After it succeeds the `tmp/` folder is wiped — the batch outputs are stale once the baseline changes, and the render you loaded in place survives through the render cache, not as a folder artifact. The folder is moved to the desktop trash when `gio trash` is available, so a batch you did not mean to lose can be restored from there in one piece; where the trash cannot take it — no `gio`, or a filesystem it will not trash from — the folder is deleted outright instead, with one stderr line saying so. Nothing else the program removes goes to the trash. Regular renders, iteration cells, and BPM-sweep cells all load in place through this same path — for a BPM-sweep cell the frozen sidecars already carry the rewritten span markers, global scale, and `bpm` descriptor, so those arrive as part of the same full snapshot.

**Checking history (`h`).** The project's working checkpoints live in a git repository — the `projects_repo` setting names which one, and the program reads the local clone it was built from, so nothing here needs a network or a credential. Bare `h` opens the history view: the marker lane stops showing the session's markers and instead shows the difference between a committed checkpoint of this piece and something else. Two things choose what that comparison is: WHICH HISTORY you are reading, and HOW. WHICH HISTORY is chosen by two buttons in the icon row, sitting just behind the history button itself: `Git` and `Session`, a radio pair on the `g` key — the lit one names the walk on screen, and pressing the one already lit does nothing. `Git` reads the committed checkpoints; `Session` reads your own session instead, and is described a little further down. The `A`/`B` tabs stay the tabs in here and `Ctrl+Tab` switches them exactly as it does outside, this being another view of the same piece rather than a place apart — read-only, and silent for want of a trim to play against. `Ctrl+Shift+Tab` works in here too, and always did in spirit: the chord is short for a step, a tab switch and another step, so only what a step means changes with the view — in here it marches the differences on both tabs and lands you on the other one. HOW they are read is the `Cumulative` button in that same icon-row group, the summation sign after the two walk radios, or its key, `u`. Off — the way the program starts — is the ITERATIVE reading; on is the CUMULATIVE one, and the button lights while it is on. Unlike the walk, which starts every visit on `Git`, THIS ONE IS REMEMBERED: leave the view and come back and you are reading the same way, until you open another project or close the program. (The button is in the row whether the view is open or not, greyed out along with the rest of the group while it is shut but still lit or unlit to show you which way you are reading.) The iterative reading, which is where a fresh program starts, looks FORWARD: it compares the checkpoint you are looking at against the next one along toward the present — the checkpoint after it, or, at the newest checkpoint, what is authored in memory right now. It answers what happened after this checkpoint, one step at a time. The cumulative reading always compares against what is authored in memory right now, however far back you have stepped: it answers how your session differs from that checkpoint. In both readings green is the newer side and red the older, so the colours say one thing throughout — green flags are markers the newer side has that the older did not, red flags are markers the older side had that the newer dropped, and a marker present in both at the same frame with a different value is one double-width flag, red half then green half, the old value on the left. At the newest member the two readings are the same thing — both compare it against your session — so pressing `u` there changes only whether the button is lit. That is also why a project you have just loaded and not yet touched shows an empty lane in both: your session and the newest checkpoint agree, which is exactly what you want to see after committing. Warp flags carry the tempo value in the sidecar's own spelling (`[+]1.05`, the `#` prefix appearing when that side is disabled); phase resets carry the bare sign, their position being their whole identity. The `Session` walk reads the same kind of difference over a different history: your own session, counted as STATES rather than as actions. Every state you can reach with `Ctrl+Z` and `Ctrl+Shift+Z` is a stop on that walk, and so is the one you are standing in — so a file you have just opened and not touched reads `1/1`, one state compared against itself, and set a marker, move it, then `Ctrl+Z`, and it reads `2/3`: three states, and you are on the middle one. The view opens where your session is, so `,` steps back through what you have done and `.` steps forward — into states you have undone, when there are any, exactly the ones `Ctrl+Shift+Z` would redo. The iterative reading shows what one step did: each pair of neighbouring stops brackets a single edit, drawn as the flags it added, removed or changed — on the state you are standing in that is what the next redo would apply, one step back it is what `Ctrl+Z` would take away. The cumulative reading shows everything between that state and where you are now, which is what going there would give you; on the state you are standing in the lane is blank in both readings, since both sides are the same state. Green is the newer side throughout here too, undone states included. Nothing here touches git, and nothing is written: it is a way of reading what you have been doing. A step that changed nothing any file would carry — turning iteration brackets on or off, say — shows an empty lane, honestly, because there is nothing in it to show. Everything else in the view works the same way on this walk — the walk keys, both readings, the flag selection, `Tab`, `c`, the trim bar's double-click, and `Ctrl+H` to put a difference back, which on a session reading means undoing part of one step and keeping the rest. `'` works here too, over a different thing: it asks about the state you are standing on, by its number, and its `OK` applies that state's markers and engine settings on top of what you have now, as one more undoable step — it is not a rewind, so `Ctrl+Z` immediately after brings back what you left, which is what makes walking to the very first state and loading it a safe way to audition where you started. It carries only what an undo step carries: no trim, no tab settings, no preferences, and nothing is written to disk — which is what every `'` carries, here and on a checkpoint and on a render alike. The view closes as it loads, as it does for a checkpoint. One thing is the commit side's alone and says so: there is no commit id in the state text, a state of your own session having no name. `Save and Commit` is unaffected — it always commits your live state against the newest committed checkpoint, whichever walk you are on and whichever way you are reading. Each of the two histories remembers where you left it, so you can look at your last edit and go back to the checkpoint you were studying. The view opens on the newest checkpoint (on the `Session` walk, on the state your session is standing in); `,` steps to an older one and `.` back toward the newest, and holding either key down walks steadily in that direction. `Shift+,` and `Shift+.` go the whole way at once — to the oldest checkpoint and to the newest — for when you want the two ends rather than the steps between them. The two arrow buttons closing the icon row's history group are those keys — greyed out while the view is shut, live while it stands — so the walk can be driven with the mouse alone, `Shift`+click making the same jump the shifted key does. At either end of the walk the step simply does nothing, by key or by click, and so does a jump to the end you are already standing on; the arrows do not grey out there, since the state text already says where in the walk you are. It opens on whatever window you were already in: entering moves nothing — no pan, no zoom, no playhead — and neither does leaving. The view is yours throughout, and panning and zooming stay exactly where you leave them across every `,` and `.` and every switch of walk or reading, so you can settle on a passage and compare one stop against the next at the magnification you chose. Each tab keeps its own window as ever, so one can sit framed wide while the other sits zoomed in. To see where the differences fall in the piece as a whole, `0` takes you out to the whole song here as it does anywhere else — and a second `0` brings you back to the magnification you left, so the overview and the passage you were reading are one key apart in each direction. The trim bar above the ruler shows your own trim window in here, exactly as it does outside — it borrows nothing from the checkpoint and marks no span of differences — and double-clicking anywhere on it frames that window, the same framing the same double-click performs outside the view. A single click there does nothing, and the pointer keeps its plain arrow over the bar, the trim shapes being gone for the duration along with the trim gestures: the window is on display in here and nothing more. Your own view of the piece is not disturbed by any of this either: the view moves nothing at either edge, so where you are when you leave is simply where you had got to. (Your trim window is untouched throughout as well: no gesture in here can write a bound, and the view neither plays nor renders, so it has nothing to shorten anyway.) Only checkpoints the program could actually load are shown: one that would refuse the load in place — an incomplete set of the three sidecar files, or files predating the current format — is left out of the walk entirely, and the terminal notes how many were hidden. If that leaves nothing at all — a piece with checkpoints in the repository of which not one still loads, typically because they all predate a change to the settings file — the view still opens, on an empty walk: the state text reads `0/0`, the lane is blank, the walk keys and `'` have nothing to act on, and the terminal line says how many were hidden. `Save and Commit` is live there, and is how the walk gets a member again: commit once and the next `h` reads it. That is deliberate — a change to the file format empties every piece's walk at once, and the act that repairs it lives only in this view. A piece that has never been checkpointed at all opens the same way, at `0/0` with nothing behind it, and its first `Save and Commit` starts the history — nothing about that first checkpoint is done outside the program. WHERE IT GOES IS THE FOLDER THE PIECE IS IN, and that is the whole rule: make `projects/550 - 4/` yourself, keep the source inside it as the existing pieces are kept, and the checkpoints go there under the name you chose. A source that is not in a folder under `projects/` — one kept elsewhere on the disk, or dropped loose in `projects/` itself rather than in a folder of its own — has no history to read and no place to write one, so `h` says so and does nothing; the fix is to move the file into a folder, not to do anything in a terminal. Loading and editing such a file is unaffected: only the history view minds where it lives. Moving or renaming a folder later costs nothing, incidentally — the history is found by the file's name rather than by the folder's, and each checkpoint is read in the folder it was actually written from, so a piece keeps its whole past across any number of renames — move the folder in a file manager, as you would anything else, and the next checkpoint simply goes to the new place. (Renaming it with `git mv` in a terminal is the one way to confuse this: that commit changes two folders at once and is left out of the walk, with the terminal saying so.) The other side of that: if you keep a COPY of a piece in a second folder and checkpoint from there too, both sets of checkpoints are one history and appear interleaved in the walk, each showing the folder it came from. Nothing stops you, and nothing is lost — but it is one piece's history as far as the view is concerned. `h` also refuses when it could not read the history at all — git failing to run, say — rather than showing you an empty one; that reason goes to the terminal too, and is fixed there. If that happens while the view is already open, on a long history still being read in the background, the view closes itself and says so in a notification and on the terminal, since it can no longer show you what it opened to show. The walk is the piece's whole history, however long it has been going, and the program reads it in the background from the moment it starts — so `h` opens at once, and on a long history the older checkpoints keep arriving for a second or two after it does. You can start reading the newest ones immediately; the count on the state text grows as the rest land, and stepping past the oldest one you have yet simply does nothing until it turns up. Committing a new checkpoint refreshes the reading, so the next `h` sees it. The state text's left end names where you are — position in the walk, and on the two commit readings the commit's short id — and, only when the checkpoint's `scale` setting differs, its two values old and new (`Scale: [-]100 [+]125`); a scale that did not change is not mentioned at all. The view is read-only, and now literally so: authoring, undo, rendering, the menus and the editors are all inert while it stands, while panning and zooming work as ever, so you can look around a difference before deciding what to make of it. Switching audio or marker views in here — which you will, since a difference is line-shaped and each view shows one column of it — changes nothing in your work either; that switch used to clear any iteration brackets you were carrying, and since iteration mode stopped being tied to source view it does not. The view is also silent: it plays nothing at all. `Space` does nothing in here, neither mouse button scrubs, and a session already playing when you press `h` stops as the view opens — an audition of the piece is what the editor is for, and it costs a full render of the whole song from in here, since the view ignores your trim window. The buttons say so: everything in the icon row that cannot act while the view is open — undo, redo, `Render`, the Show trim region button, follow, listen, and the read-only toggle — is greyed out for the duration, as are the `Edit`, `Series` and `Settings` buttons up in the menu row (the BPM editor and iteration mode are `Series` rows now, and the view refuses both, which is exactly why that button greys with the other two), and none of them goes anywhere: the icon row's buttons are always all there. What still works is `Save`, the view radios, the zoom group, the load-in-place button when the walk has a member, the history button itself, and the six behind it that belong to this view — the two walk radios, the cumulative reading, revert, and the two walk arrows — which come to life as the view opens and grey out again as it closes. The bottom toolbar greys what it must too: play and stop, the four cardinal arrows, the six marker verbs (drop, delete, disable, toggle inherit, edit flag, and measure), and Add to Selection. Walk both tabs stays lit with the two marker-walk arrows beside it, all three stepping the differences in here. The `Settings` menu button (a labeled button, not an icon) greys out instead of vanishing. `File` opens as usual in here and all three of its rows act: `Quit` as its key does, `Open project` — `Ctrl+O` too — bringing up the project list over the view, and `Synchronize to external storage` mirroring the project as it does anywhere else. Cancelling the list leaves the view exactly as it stood; opening a project closes the whole session, the way `Quit` does. The sentences those two rows write — which project was refused and why, or how many files went to the stick — are notifications, and show in here exactly as they do outside. `Settings` is shut because its rows would open the settings editor, which has no place in a view that changes nothing. Nothing in the window changes job for the view any more: the tabs are the ordinary `A`/`B` tabs and switch as they always did, and the bottom toolbar's right-hand groups are the ordinary ones with the dead keys greyed. (The `o` key is inert in here as it always was — its button in the icon row greys out with the rest.) `Esc` keeps its ordinary job in here: it cancels a render started before the view opened, without leaving the view — `h` leaves it, and so does the commit act below, as soon as its save lands. A click on a diff flag brightens it and lands the playhead there — on the flag itself, in the marker lane; the line dropping from it into the waveform is a visual cue only, like every marker stem. Anywhere else, the waveform — either half, the halves being alike in here since there is no scrub to divide them — the ruler and the marker lane's empty stretches answer exactly as they do outside the view: a plain click that never becomes a drag moves the playhead to that spot at the release and drops the brightened flag as it goes, a plain drag pans, `Ctrl`+drag zooms, and `Shift`+drag carries the playhead along with it and nothing more — outside the view that sweep is the trim's own gesture, and the trim is frozen in here, so it writes nothing. A modifier held over the waveform names a view gesture, never a selection, in here exactly as outside. There is no reading mark of the view's own any more: a region is the trim window everywhere now, and the trim is frozen in here. The region is simply not offered in this view, for the reason the view is silent at all: the trim window is there to make a render of a passage quick, and nothing in here plays or renders, so there is no window to work and nothing to look at one for. `[` is inert and its button greys with the rest of what the view refuses. A region you left showing when you opened the view stays on screen drawing that same window, and it survives the whole visit — stepping to another checkpoint, switching the walk or the reading, switching tabs, and leaving all keep it. What still hides it is what hides it outside: a click on a diff flag, a playhead placement, or the end of the view's own shift sweep — and once it is down it stays down for the rest of the visit, which costs you nothing at all: your trim window is untouched, and `[` outside the view draws the identical region again. The marker selection you left behind when you opened the view is untouched by any of this. `Tab` and `Shift+Tab` walk the diff flags the same way they walk markers outside the view — each step brightens the next flag along, lands the playhead on it and recentres at the zoom you are already at, and with no flag brightened yet they start from the playhead, exactly as they do outside the view: `Tab` takes the first flag past it, `Shift+Tab` the last one before it. There is no wrap at either end, and with no differences to show — or with nothing left ahead of the playhead in the direction you pressed — they do nothing. `c` re-centres on the brightened flag at the working zoom, or on the playhead if none is brightened. `Home` and `End` jump to the very start and the very end of the song here — not to the trim bounds they jump to outside the view, since the view is about the whole piece — and they drop the brightened flag as they go; `Ctrl+Home` and `Ctrl+End` mean exactly the same thing in here, the chord asking for the piece's ends everywhere. `'` inside the view acts on THE MEMBER YOU ARE LOOKING AT — the one `,` and `.` have walked to, which is the one the lane is showing — and asks first: `Load` (its short commit id on the `Git` walk) `in place?` with `OK` and `Cancel`, where `Enter` is `OK` and `Esc` is `Cancel`, the same question the render player asks about a render. `OK` loads that checkpoint's markers and engine settings in place into memory — the same in-memory load-in-place a render entry takes, one undo entry, nothing written to disk, and nothing of the checkpoint's own trim, tabs or preferences. There is no list to pick from: stepping the walk is how you choose. A checkpoint that turns out to lack the piece's sidecars, or to predate the current file format, is refused — a notification and the terminal say why — and changes nothing. (On the `Session` walk the same key asks about the state you are standing on instead — see the `Session` walk above.) Differences can also be selected and put back. A plain click on a flag brightens that one and drops any other selection; `Shift`+click selects everything between the brightened flag and the one you click, and `Ctrl`+click adds or removes a single flag from the selection — on the flag itself, in the marker lane, that being where selecting is done in either view; every selected flag is brightened. Over the waveform those two modifiers keep their usual jobs (`Ctrl` the zoom-and-pan drag, `Shift` the sweep, which carries the playhead in here and writes nothing), and a stem answers nothing anywhere. Stepping to another checkpoint, switching the reading or the view, `Home`, `End`, `Tab` and a click anywhere else all drop the selection again, so it never outlives what it points at. `Ctrl+H` — the revert button in the icon row's history group — then applies those differences BACKWARDS into your session and closes the view: a green flag's marker is deleted, a red flag's marker is put back exactly as the checkpoint had it, and a two-colour flag's marker is set back to the checkpoint's value. With nothing selected it acts on the brightened flag alone, and with nothing brightened either, the key does nothing and the button — which stays lit, like the rest of its group while the view is open — does nothing when pressed. It is deliberately unguarded: nothing checks that the flags you picked make sense together, so you can quite easily build a state that is neither the checkpoint's nor the one you started with — reverting half of a change is exactly as possible as reverting all of it, and that freedom is the point. The whole act is one undo step, so `Ctrl+Z` takes it all back. Nothing is written to disk; a read-only tab refuses it, since it rewrites the piece's own markers — that lock stops the revert and `'`, but not `Save and Commit`, which only writes out and publishes what is already there. `h` closes the view.

The view can also publish. `Ctrl+S` inside it — the `Save` button, which wears the commit glyph while the view is open, its tooltip reading `Save and Commit` — saves and then commits the current authored state as a new checkpoint. That is the only thing `Ctrl+S` does in here: the plain save has no key of its own while the view is open, which matters only in the one case the button greys out for, and leaving the view with `h` gives it back. It asks one thing first, and it is worth answering: an editor opens on the bottom row with the commit message already filled in (`Update <folder name>`, the piece's folder), selected so that typing replaces it. `Enter` commits under whatever it holds, so the ordinary case is a single keystroke and the useful case is writing what you actually changed; `Esc` abandons and nothing happens. An empty message flashes red and waits, with a notification saying so — a checkpoint has to be called something. Then the program performs an ordinary `Ctrl+S` save, exactly as pressing it would (so the checkpoint is always what you have saved, and the unsaved-changes dot clears with it), and the view closes. If the save itself fails — a disk error, a full disk — the act stops there: it says so, nothing is committed or pushed, and the view stays exactly as it was so you can fix the reason and press again. Everything after the save happens in the background: writing the three sidecar files into the piece's `projects/` folder, committing them under your message, and pushing. You keep working while that runs — the window does not wait on the network. If any of it fails, a notification with the red error glyph appears at the top right of the window — nothing committed, the files written but not committed, committed but not pushed, or simply not confirmed — and STAYS there: unlike the ordinary notifications it does not leave by itself, it is not a prompt, it takes nothing away from what you are doing, and only its close button takes it down, whatever a later `Save and Commit` answers. The terminal carries the long version. The piece itself is saved in every one of those cases. THE FIX IS IN THE TERMINAL, deliberately: a checkpoint that committed but did not reach the remote is published with `git push` where you have git — the program does not retry the push for you, and it does not offer a button that would. The card stays until you close it either way: it is the record of what happened, not a light that a later success switches off. The same is true of a commit that git reported as failing while in fact landing (a slow hook can do that): the terminal shows what really happened. If a checkpoint that succeeded has nothing more to say it says nothing. The push uses the machine's own git identity and SSH setup, exactly as committing from a terminal would. Only one checkpoint publishes at a time: while one is still running the `Save` button is greyed out and its tooltip reads `Committing the checkpoint (Ctrl+S)` — wherever you are, not just in the view — `Ctrl+S` does nothing, and `h` will not open the history view either, since the view would be reading a repository that is being written to. Saving is deliberately held for those moments: the program is writing the same three files out to the repository just then, and two writers on one file is how files get damaged. It takes a moment and comes back by itself; quitting waits for it rather than abandoning it. (If you edit something during those moments and then quit, the unsaved-changes prompt's `Save` reports `Save failed.` for the same reason — pressing `Retry` once the checkpoint has landed saves normally.) The button also tells you in advance whether there is anything to commit: while the view is open it greys out whenever the session's markers and `scale` already match the newest checkpoint, and `Ctrl+S` does nothing then. On an empty walk there is no checkpoint to match, so the button is lit — there is by definition everything to commit — though it waits, greyed, for the moment or two the program takes to finish reading the history and be sure the walk really is empty. That answer covers the whole piece rather than the half you are looking at, so there is no need to switch views to check both. Only authored content counts — the view state the program also records in the settings file is not a change worth a checkpoint — so if that is all that has changed, leave the view and save to disk as usual. The checkpoints the program reads and writes live under the repository's `projects/` folder — one folder per piece, the three sidecar files named by the source's base name — so another repository works by carrying the same shape.

Moving the projects home to another git host takes two steps and nothing else: point the clone at the new remote (`git remote set-url origin <new url>`) and edit the `projects_repo` setting to match it. The program speaks only to local git and to whatever that remote turns out to be — there is no GitHub dependency anywhere in it, no account, no token, no service to sign up for.

**General.** `Ctrl+Z` undoes and `Ctrl+Shift+Z` redoes; settings edits and marker edits participate in the same undo history. Undo and redo show you what changed. The touched markers are re-selected (an undone insertion has no surviving marker, so that case clears the selection instead), and the view goes back to where the edit was made: the tab, the source/target audio view and the warp/phase-reset column are all put back the way they were when you made the change. The playhead keeps the place in the music it was standing on while all of that happens, even when the change was one that reshapes the target view's timeline under it. A single touched marker gets the full marker-click treatment: the playhead lands on it (a showing trim region hides, as it does for any landing playhead — the window itself is untouched), the viewport recenters only if it is offscreen, and its flag brightens — the ordinary single-selection cue, staying for as long as that marker is the one selected marker. A change that touched several markers re-selects the group — each member's flag brightens, the cursor standing on the earliest member where the playhead lands — scrolling into view whenever part of the group sits offscreen, zooming out only when the group cannot fit at the current zoom. Trim changes are excluded from undo and redo. Held nudges and tempo steps coalesce: holding the key down (`Left`/`Right` marker nudges, or `Up`/`Down` tempo steps, group steps included) collapses the whole held run into one undo entry, so a single `Ctrl+Z` reverts it, and a held arrow button in the bottom toolbar counts exactly the same way — and rapid separate taps of the same key merge the same way when they land within about half a second of each other with the same markers selected in the same tab; a slower press, a press after the selection changed, or a press that refuses (a nudge already at the song edge, say) opens its own entry.

**`Esc` does exactly seven things**, and nothing else anywhere: it ends a text-selection drag inside an editor (that same press goes on to close the editor, so the two happen together), it closes an open editor without committing, it dismisses a prompt, taking its rightmost response, it dismisses an open dropdown (any of the four menus), it closes the render player, it closes the project list, and it cancels all render work — the running render, a parked render command waiting behind it, and a pending target-view preview. That cancel always takes one press, whatever the trim region is doing: `Esc` used to hide a showing region first, and a region up meant two presses to reach the cancel; the region is `[`'s business now and `Esc` goes straight to the render. An open editor or a prompt takes priority, so the first `Esc` closes that and the next one cancels render work. While a pointer gesture is in flight `Esc` is swallowed like every other key and answers `Keys are ignored during a drag`: gestures have no cancel — let go and the gesture commits what stands, then `Ctrl+Z` takes it back (trim, which sits outside undo, commits for good). With nothing open, nothing rendering and nothing being dragged, `Esc` is simply a no-op: it does not deselect markers, does not move the playhead and does not touch the trim region. To leave a selection, click the waveform or press `Home`/`End`; to put the trim region away, press `[` again — or move the playhead, or touch a marker, or finish a sweep, which is the whole of the rule for when it goes by itself. Hiding it writes nothing: the window it was drawing is exactly where it was.

**Mouse.** One rule organizes the pointer: the whole waveform, the ruler, and the marker lane's empty stretches are a single navigation surface, and every plain or modified gesture means the same thing anywhere on it. A plain drag pans the view — a smooth grab, capturing the cursor for unlimited travel once the drag is under way. A plain click that never becomes a drag acts the moment you release (nothing happens at the press itself, so a click never pops anything while you decide, and a pan moves nothing but the view): on the upper half, the ruler, and the marker lane it places the playhead at the clicked spot, clearing the marker selection and hiding a showing trim region. `Shift`+drag sweeps a trim window and brings the region up as it draws it, and `Ctrl` turns the drag into the zoom — hold it, press it or release it at any point of a drag and the gesture switches between panning and zooming without lifting the button (see Trim and the region, Zoom and view); there is no `Alt` and no `Ctrl+Alt` gesture on the buttons — `Alt` binds the wheel and nothing else — and the right button does nothing at all. The waveform's lower half differs in that one act and nothing else: a plain click there scrubs playback instead of placing the playhead — it stops a running session, and on a stopped one the scanner starts there, one-shot per click, leaving the resting playhead, the marker selection, and a showing trim region exactly as they were (see Playback and playhead). The pan, the sweep, and the zoom all work from the lower half exactly as they do from the upper. The scroll wheel on its own magnifies the drawn waveform — one step per detent, up taller — over the waveform, the whole marker strip, and the overview strip alike, but not over the three button rows at the very top (menu, tabs, icon row) or the bottom toolbar, where the wheel does nothing at all. Hold `Alt` and the wheel pans instead, a tenth of a screen per detent, and hold `Ctrl` and it zooms, one whole level per detent — both wherever the plain wheel is live; no other modifier does anything on the wheel. The buttons themselves are covered under The top rows; the rest of those rows does nothing. The pointer tells you what a press would do, using your own cursor theme's cursors and no artwork of ours: a hand anywhere on the navigation surface, which is the whole waveform and both nav lanes (the pan — a still click needs no cursor of its own, whichever act it runs), a magnifier with `Ctrl` held anywhere the zoom drag works, which is the navigation surface and not the overview strip — on the strip `Ctrl` binds nothing at all, and the shapes there are the plain drag's: an edge arrow on the viewport box's own edges (see The overview strip) and the left-right resize arrow everywhere else on the lane, inside the box and outside it alike, the box sliding under a plain drag in either case — a press outside it centering the view there at once, as it lands, before it takes hold of the box — the same left-right resize arrows on a marker's flag, which is the marker's grab handle and slides the same way, and on the trim bar three shapes for three different acts — a left-edge arrow on the begin endcap, a right-edge arrow on the end endcap (each drags that one bound), and the left-right resize arrow on the bar between them (which drags both together). `Ctrl` and `Ctrl+Shift` over the trim bar show the same two edge arrows, matched to the bound each one sets. An I-beam marks editable text: the flag editor's box when one is open, and the field inside a prompt or editor dialog. Everywhere else — the button rows, the trim bar's bare ground — it is the ordinary arrow, and so it is wherever the gesture would not run: while a menu, a prompt, or one of the editor dialogs is open (the dialog's own field and buttons are then the pointer's only targets, and the field shows the I-beam), while any drag other than a trim drag is in progress, with `Shift` held (the sweep shows no cursor of its own), and on a `Ctrl` or `Ctrl+Shift` trim click that would land on or past the other bound, which does nothing. If your cursor theme is missing one of these, that one shape falls back to the arrow and everything still works. The cue changes the instant you press or release `Ctrl`, without moving the mouse; other changes with no mouse movement under them — a file finishing loading, a menu closing with `Esc` — show up the moment you move the mouse next. While you drag a trim endcap, the bar between them, the overview box — by an edge or by sliding it — or a marker by its flag, the pointer keeps the shape it started with, the matching edge arrow or the resize arrow, for the whole drag, wherever the pointer goes. During any other drag the cursor is the plain arrow, or hidden entirely for the pan and the zoom drag, which capture it so the gesture can travel without limit — while it is hidden it comes back at the opposite edge of the waveform whenever it would run off one, so it is never left stranded there (see Zoom and view). When one of those ends, the pointer comes back as the hand or the magnifier to match what the drag was doing when you let go — panning or zooming, and at the place the hidden pointer had reached. A click on a marker's flag — the flag is the marker's one clickable part; its stem on the waveform is a visual cue only, and no click or drag can land on it — selects that marker and seats the playhead on it at the moment you press, a flag press being able to mean only that — and dragging the flag moves that one marker with the playhead following, whether or not others were selected. A drag simply carries on from there: the press has already selected the marker and stopped playback, and the move begins once the pointer travels a few pixels. That is the opposite of the waveform, the ruler and the empty marker lane, where a press could equally be the start of a pan and so nothing happens until you let go. Double-clicking the flag opens the flag editor, on the second press rather than after it; `Shift`+clicking range-selects from the focused marker and `Ctrl`+clicking toggles membership, both seating the playhead on the marker they leave focused (see Marker focus and selection). `Tab`/`Shift+Tab` and `c` also bring the playhead to a marker, recentering the view as they do; a nudge or flag drag carries the playhead along with the focused marker, and dropping a new marker with `s` or the empty-lane double-click seats the playhead on it as part of the drop, hiding a showing trim region like any other way of putting the playhead somewhere. Double-clicking inside any text editor selects the run under the click, the standard desktop way: a word (underscore counts as part of it), a run of punctuation (a `.`, `=`, or `::` selects just that), or a run of spaces — the selection never crosses from one kind into another. Trim bounds are dragged by their begin/end endcaps and the bar between them, plain like everything else — a drag begins after a few pixels of motion; the begin endcap sits with its left edge on the bound and the end endcap with its right edge, so both are fully visible even at the very start and end of the file. The marker drag and the double-click-to-edit refuse — the flag click still selects — both in a read-only tab and when the marker collection is away from its home audio view (a warp marker in target view, a phase reset in source view; see View axes): a flag click off its home view selects the marker and seats the playhead, and no drag can begin from it. The trim drags work in a read-only tab: trim is view state, not part of the piece. The `e` key IS the left mouse button: pressing it presses the button at the pointer position, holding it holds the button (so `e`+motion drags, and modifier state rides along exactly as for a physical button), and releasing it releases the button — except while a text editor is open, when `e` types the letter as normal. The press acts only while the pointer is over the window. One thing outranks the pan on the waveform: while the trim region is showing, a plain drag inside it slides the window and a plain drag within ten pixels of one of its bounds moves that bound, and the pointer says so — the left-right resize arrow inside the span (it slides side to side, like the trim bar between its endcaps) and the matching edge arrow on each of its bounds (see Trim and the region). Outside the span, and on the ruler and the marker lane wherever the span reaches, the hand and the pan are exactly as before, and `Shift` and `Ctrl` are untouched everywhere.

**Touch.** On a touchscreen, one finger is the mouse — a tap is a left click at the moment the finger lifts, and every gesture, refusal, and rule in the sections above applies unchanged; the program does not distinguish the two devices. On the navigation surface — the whole waveform plus the ruler and the marker lane's empty stretches, the same surface the mouse's plain drag pans — a one-finger drag pans the view directly, the way it does on a phone; a tap acts as the mouse's click does, placing the playhead at the tap point (or, on the waveform's lower half, scrubbing there); hold a finger still for about half a second and then drag, and you sweep a trim window instead — the mouse's `Shift`+drag by another route, and it sets the trim outright, no modifier and no second step, the region coming up at the stroke's first write so you can see the stretch you are drawing — never the one you are replacing — and going away again when the finger lifts (tap **Show trim region** to bring it back), the playhead riding the moving end through the drag and parking at the new window's start when the finger lifts (a hold released without moving just places the playhead and writes nothing); and a double-tap on an empty stretch of the marker lane creates a marker there, selects it, and lands the playhead on it, exactly as the mouse's double-click does. Zooming on a touchscreen is the two-finger pinch, over the waveform — over the two slim lanes, the overview strip and the trim bar, two fingers do nothing at all. Those two are one-finger surfaces: they are narrow, and everything they do is done precisely by one finger, so once a finger is down on either of them a second finger is ignored completely and the first finger's drag simply carries on — the same thing a third finger does during a pinch on the waveform. A pinch begun on one of those lanes does nothing whatever, neither zooming the view nor moving anything on the lane. A showing trim region is the one part of the waveform the one-finger pan gives up, and it gives it up so that you can work the trim with a finger: drag inside it to slide the window, drag on one of its bounds to move that bound, and tap it to do exactly what a mouse click there would do — which splits by half, as it does everywhere else on the waveform: a tap on the UPPER half places the playhead and hides the region with it, while a tap on the LOWER half auditions the span and deliberately leaves both the playhead and the region where they were. The upper half is therefore the way to put the region away, and it is always available: a span covering the whole window still covers both halves. That is what makes the trim window workable on glass at all — tap **Show trim region** (the dashed rectangle in the icon row) and the window appears as a span hundreds of pixels tall instead of a nine-pixel bar, with its two bounds and its middle all under a fingertip. Nothing has to be committed afterwards: each of those motions is the trim itself, and the slim bar shows the result as you go. And the way back out is on that same button — a `Shift`+tap, or a press held for about half a second, opens the window to the whole song, so the one step that used to want a keyboard does not any more. The half-second hold that sweeps a new window is a pan-surface gesture, so it does not reach inside a showing region: start the hold outside the span (you can sweep straight through it), or tap its upper half once to put the region away first. The ruler and the marker lane still pan and still take the hold wherever a span reaches across them. Off that surface a finger behaves as the left button everywhere: a tap on a marker's flag selects it, a drag from a flag moves that marker, a drag between the trim bar's endcaps moves the whole trim window, a drag from an endcap extends that bound, a double-tap on the trim bar frames the span, and a brief press-and-hold is the held button for every press-and-hold gesture. The prompts and the editor dialogs are as tappable as everything else — their buttons answer a tap, so a question the program asks can be answered entirely on glass, no keyboard needed. Two fingers zoom, and only zoom: spread or pinch them and the view zooms, while sliding both fingers across the glass together moves nothing — panning is the one-finger drag, so the two-finger gesture never scrolls. What it zooms about is the piece of audio your fingers took hold of: the moment the pinch first registers, it takes the point of the song under the middle of the two fingers and keeps it, wherever the fingers go from there. Move only one finger and the view still scales about that original point rather than about the moving midpoint; and when the view runs into the start or the end of the piece and can go no further, the pinch keeps its grip on the audio and lets it slide across the glass rather than standing still while the song walks out from under it — which is what makes the pinch reversible, so pinching back the other way brings you back to what you came from. If that piece of audio would leave the screen altogether it pins at the edge and takes the content it finds there, so you are always zooming about something you can see. A dim vertical stem marks that point for as long as the pinch lasts — the same mark the mouse's `Ctrl`+drag shows — so you can watch it hold its audio, slide along with it at the ends of the piece, and pin at an edge. Lift one finger and that pinch is finished — the drag carries on as the surviving finger's pan, and putting a second finger back down starts a fresh pinch on whatever the two are holding then. This is the same pivot the mouse's `Ctrl`+drag holds (see Zoom and view): your dominant hand does the same thing on both, and on the laptop `Ctrl` is your other hand playing the second finger's part. A second finger added mid-pan joins it seamlessly, a second finger added to a held (not yet dragged) finger does too, and lifting one finger of the two hands the motion back to the surviving finger's pan just as seamlessly — add and drop the second finger as often as you like within one touch, with no jump at any switch. The laptop mirrors this exactly: the plain drag pans, and `Ctrl` is the second finger — hold it and the drag zooms, drop it and the drag pans again, mid-drag and as often as you like. Nothing else is bound to touch.

**The on-screen keyboard.** On a device with no keys of its own, opening any text editor — a flag's value, a marker's measure, the settings editor, the BPM bracket, a commit title, the measure paste offset — brings up a keyboard across the bottom of the window, just above the bottom row, and it goes away again when the edit ends. The render player's list and the `Open project` list use that same band, and a list and the keyboard are never up together: no list needs typing, so it takes the keyboard's place while it stands. A list is always the same height, whatever it holds: it stands from the middle of the waveform down to the bottom toolbar, so a short listing leaves bare ground below its rows and a long one scrolls. Its rows are the size of the buttons in the rows above — one glyph and a name, on the highlight's blue band when they are picked — and a name too long for the line runs off the edge rather than being shortened. It types into whatever editor raised it; nothing else changes. Every key acts the instant you touch it, the way a key does and not the way the program's buttons do, and holding one down repeats it, so backspace held clears a field. Every key says what it is in words — `Shift`, `Backspace`, `Space`, `Cancel`, `Enter` — in the same lettering as the letter keys. `Shift` is one-shot: tap it and the next letter is a capital, then it lets go by itself; tap it again while it is lit to change your mind. While it is armed the key is lit the way a lit button in the rows above is, and every letter on the keyboard shows its capital. `&123` swaps the letters for the digits and the punctuation the program's own grammars use — the tempo dot, the disable `#`, the iteration bracket, the measure's slash and space, the underscores and colons of settings keys — and the same key, now reading `abc`, swaps them back. The two keys at the right are the edit's own two answers: `Enter` commits it and `Cancel` throws it away, exactly as `Enter` and `Esc` do on a keyboard. There is no hide key and no language key, and the space between keys is dead — a finger that misses a key does nothing rather than reaching the waveform underneath. On the laptop this keyboard does not exist at all.

### Migrating an older project folder

A checklist for bringing a folder from before the project model — a bare `.warpmarkers` / `.phaseresetmarkers` pair, possibly still in the legacy `MM:SS.mmm` timestamp form, and a `renders/` folder or a stray output wav sitting in the root — into the current layout:

1. Make a folder for the project directly under `projects_path`, named for what you want the project called.
2. Copy the source wav into it.
3. Copy the `.warpmarkers` and `.phaseresetmarkers` files in beside it.
4. If those sidecars are still timestamps rather than frames, build the conversion tool. It is not part of the product build and no executable ships in `tools/` — that folder is its source. From the project root:
   ```bash
   cmake -B build-tools -S tools && cmake --build build-tools
   ```
5. Convert the sidecars with the tool you just built — the warp file first, then the phase-reset file, since the phase-reset conversion needs the completed warp map to land its positions correctly:
   ```bash
   build-tools/migrate_sidecar_to_frames <sample_rate> <stem>.warpmarkers
   build-tools/migrate_sidecar_to_frames <sample_rate> <stem>.phaseresetmarkers <stem>.wav
   ```
   `<sample_rate>` is the source's own rate (`44100`, for instance); the tool rewrites each file in place at its original path and keeps the untouched original beside it as `<path>.bak`.
6. Delete the old `.settings` rather than bringing it across — it is all but certain to carry a key the current schema refuses (see below), and the first open of the new folder writes a fresh template in its place. Re-enter `title`, `notes`, `url`, and `cover` by hand from the old file's lines.
7. Rename any `renders/` folder to `tmp/` (`mv renders tmp`).
8. Move any `<title>.wav` and its `.fingerprint` sitting in the project root into `render/`. Move only the current `title` setting's pair: `render/` is kept to that one deliverable, so anything else you put in there — a wav under an old title, a keeper you meant to hold on to — is deleted the first time the render player lists the folder or a render publishes into it. Keep those somewhere else in the project.

A `.settings` that still carries `gui_scale`, `audio_player`, `projects_repo`, or `playback_speed` refuses to load outright — those became per-device settings (or, `playback_speed` and later `audio_player`, were retired outright), and a sidecar naming any of them is an unknown key. The fix is deleting those lines by hand, not migration. The per-device config file has the same rule in both directions: one carrying `audio_player=` — every config written before 2026-08-28 does — stops the program at startup, and the fix is deleting that one line; and one written before 2026-08-30 is MISSING `sync_path=`, which stops the program the same way, so add the line by hand — `sync_path=/run/media/<you>/<label>` on the laptop, pointing at the stick's own mount folder, or a bare `sync_path=` on a machine with nowhere to synchronize to.
