# warptempo_gui

This is the user guide: install and build, first run, the conceptual model, output and the limiter, and the complete hotkey reference. Reading the conceptual model first will make the reference make sense; the reference is where every key and gesture lives.

## Dependencies

Build requires a C++23 toolchain (GCC 12+ or Clang 16+), CMake 3.20+, pkg-config, and the development headers for fftw3. That is the complete dependency set for the headless render interface (`warptempo_cli`); none of the GUI packages below are needed for it.

The default GUI build additionally requires the wayland-scanner tool and the development headers for cairo, wayland-client, wayland-cursor, wayland-protocols, libxkbcommon, and JACK. JACK can be the native jackd2 server or a PipeWire-shimmed JACK provider (modern distros default to the latter).

The `std::expected`-based parser is what pins the compiler floor at GCC 12 / Clang 16. On distributions whose default compiler is older — Ubuntu 22.04 ships GCC 11, for example — install a newer toolchain (`g++-12` or later) and select it with `-DCMAKE_CXX_COMPILER=g++-12`.

Arch Linux:

```bash
sudo pacman -S base-devel cmake pkgconf \
    cairo fftw \
    wayland wayland-protocols libxkbcommon \
    pipewire-jack
```

Debian / Ubuntu:

```bash
sudo apt install build-essential cmake pkg-config \
    libcairo2-dev libfftw3-dev \
    libwayland-dev wayland-protocols libxkbcommon-dev \
    libjack-jackd2-dev
```

The libwayland-dev package on Debian ships wayland-scanner and the client / cursor headers in one piece.

Fedora:

```bash
sudo dnf install gcc gcc-c++ cmake pkgconf-pkg-config \
    cairo-devel fftw-devel \
    wayland-devel wayland-protocols-devel libxkbcommon-devel \
    pipewire-jack-audio-connection-kit-devel
```

For a headless build — `warptempo_cli` with no GUI — only the core dependencies are needed. Omit the cairo / wayland / wayland-protocols / libxkbcommon / JACK packages from the lists above and configure with `-DWARPTEMPO_BUILD_GUI=OFF` (see the Build section). On Debian / Ubuntu the dependency set reduces to:

```bash
sudo apt install build-essential cmake pkg-config \
    libfftw3-dev
```

A Wayland compositor is required at runtime — there is no X11 backend — and it must offer server-side window decorations (the xdg-decoration protocol): the GUI exits with an error at startup if the compositor does not offer the protocol. labwc, the compositor the program is developed on, always can; so can the other wlroots-based compositors (sway, Hyprland) and KDE Plasma. GNOME's compositor does not implement the protocol, so the GUI will not start there. The headless CLI needs no compositor and no audio server; it reads and writes files only.

Windows (WSL2): the project builds and runs under WSL2 with a Debian or Ubuntu userland — install the Debian / Ubuntu dependencies above inside the WSL distribution and build normally. The headless CLI behaves as on any Linux host. The GUI is not supported under WSL: WSLg provides a Wayland compositor but routes audio through PulseAudio, and the application has no non-JACK audio path.

macOS is not supported: the GUI is a Wayland-native client and has no macOS build at all. The headless CLI is neither built nor tested there and carries no support claim either.

## Build

Standard out-of-tree CMake build from the repository root:

```bash
cmake -B build -S .
cmake --build build -j$(nproc)
```

The default build produces one binary: the `warptempo_gui` application — a Cairo/Wayland front end over the in-tree parser, engine, prepost, and audio-io sources. All audio container I/O is in-tree, WAV only, with no third-party codec. There are no library archives; each binary compiles the shared source lists directly. `-O3 -march=native -ffp-contract=off` is always on for GCC and Clang, so every binary is tuned for the host CPU and is not portable across machines — rebuild on the target host. A rebuilt binary is not a new rendering reference, though: with the same compiler and the same libraries underneath it, a fresh build renders exactly what the previous one did, byte for byte (see Reproducibility below).

One opt-in binary, default OFF: `warptempo_cli` (`-DWARPTEMPO_BUILD_CLI=ON`) is the headless insurance render path — exactly the terminal `Ctrl+Alt+R`. It takes just the source audio path, reads the project's `.warpmarkers`, `.phaseresetmarkers`, and `.settings` beside it (all three required; the GUI creates them on source load), and writes the warped WAV the GUI would render for the same project at the same path — `<title>.wav` beside the source — byte-identical to the GUI by shared pipeline stages. The trim applied is the active tab's (the persisted `active_tab_view` key), matching the GUI. Like the GUI, it also drops the render's frame-map pair into `~/.cache/warptempo_gui/<pid>/` (see Output below).

To build the CLI on a headless host that has none of the GUI's Wayland / Cairo / JACK packages, add `-DWARPTEMPO_BUILD_GUI=OFF -DWARPTEMPO_BUILD_CLI=ON`; the GUI dependency discovery is skipped entirely.

There is no `make install` target. The binary is self-contained: copy it anywhere on `$PATH` (typically `~/.local/bin/` or `/usr/local/bin/`) to make it available system-wide.

```bash
install -Dm755 build/warptempo_gui ~/.local/bin/warptempo_gui
```

A `.desktop` file is shipped in `packaging/warptempo_gui.desktop`. To register `warptempo_gui` with the system's application launcher and as a handler for audio files, install it to the user-level application directory and refresh the desktop database:

```bash
install -Dm644 packaging/warptempo_gui.desktop \
    ~/.local/share/applications/warptempo_gui.desktop
update-desktop-database ~/.local/share/applications
```

The shipped `.desktop` file uses the freedesktop `audio-x-generic` icon name, which resolves to whatever the active icon theme provides — no icon file is bundled. Replace the `Icon=` line with a different freedesktop name or an absolute path to a custom SVG to override.

## First run

`warptempo_gui` takes a single argument: the path to a source audio file.

```bash
warptempo_gui "path/to/source.wav"
```

Source inputs are stereo WAV only, 16- or 24-bit PCM, at 44100 Hz or above — anything else refuses to load with the reason on stderr. Material in any other format or layout — FLAC, Opus, MP3, mono — is converted once at acquisition with an external tool (e.g. ffmpeg), and the converted WAV becomes the project source.

The project's data lives in three sidecar files beside the audio, named by appending `.warpmarkers`, `.phaseresetmarkers`, and `.settings` to the audio file's basename. They are program-written and strictly validated at load: a hand-edited or corrupt sidecar fails the load with the first error on stderr.

On launch, the program opens a window, reads any existing sidecar files for the given audio file, and presents the source waveform across the full window width. With no sidecar files present, you start with a single warp marker at frame zero carrying tempo `1.00` and no phase reset markers. With sidecar files present, the prior session is restored verbatim — viewport, zoom, playhead, active view selectors, and all marker positions and flags.

The repository's `projects/` directory ships reference movements with complete sidecar files. The Symphony No. 40 mvt I directory (`projects/550 - 1/`) is the recommended first load — it exercises every form and syntax used in the project. The audio itself is not included (the corpus is commercially licensed); you supply the source recording and place it in the project directory under the basename the sidecar files expect. See the Projects section at the end of this document.

## Conceptual model

### The engine

`warptempo_gui` drives a phase vocoder — a faithful, centered implementation of Prusa-Holighaus phase-gradient heap integration (PGHI, from ltfatnote050, "Phase Vocoder Done Right"). The gradient method enforces phase coherence in both time and frequency without peak-picking or transient detection, which is what lets a high stretch ratio preserve upper-band detail and transient impact rather than dulling them. Per-frame phase correction keeps bins coherent within each frame, so steady-state content — held strings, sustained winds, room tone — stretches without smearing into a chorused or phasey artifact.

The FFT size `N` is fixed at 4096 and the synthesis hop `R_s` is derived as `N/4` (75% overlap). These parameters match the authors' released PGHI implementation (github.com/ltfat/pvdoneright) parameter-for-parameter — window length 4096, `M=2N=8192`, synthesis step 1024, tolerance `1e-6` — giving the gradient integration its finest frequency resolution and the fullest low-frequency body. The engine inherits the source recording's sample rate.

### Relation to the published algorithm

The engine implements the published algorithm faithfully: origin-centered zero-padded analysis (`M=2N`, matching the paper's ~2x padding), centered finite differences for both phase derivatives, trapezoidal integration in all three propagation directions, the max-heap significance ordering, and the published tolerance. Where the implementation deviates from or extends the paper, the differences are deliberate:

- Variable analysis hop. The paper fixes one analysis step for the whole file (constant stretch ratio). This engine derives the analysis hop per frame from the warp-marker frame map; each half of the centered time-derivative is normalized by its own actual hop, and the frequency-direction step uses the per-frame ratio. This is the extension that makes free-tempo warping possible and is the project's reason to exist.
- Phase resets. The paper has no mid-stream re-grounding; transient handling is left to detection-based methods it cites. This engine's manual phase-reset markers re-seat the synthesis phase to the analysis phase at user-chosen frames — operator judgment in place of detection.
- Output timing contract. The paper does not specify output alignment; this engine pins it. Synthesis trims exactly `N/2` samples from the head — the alignment latency the origin-centered analysis contributes — so source frame 0 maps to output frame 0, and a feature at source frame `S` lands at output sample `tgt(S)` from the frame map. Total output length is the target-frame position of the last source sample. The overlap-add ramps at head and tail are amplitude-only fades that move no alignment. This establishes a contract: any future engine consuming the same warp markers (and, if it supports them, the same phase-reset markers) can match this engine's output 1:1 in frame timing at the start and through the body. The tail's final incomplete-overlap ramp is deliberately outside the contract.
- Remaining boundary choices, unspecified by the paper: the first frame (and the frame each phase reset selects — the frame whose analysis window centers on the authored position) seeds synthesis phase from analysis phase, the seed that serves the timing contract and the reset model above; the first frame's time-derivative uses the forward difference only; the frequency-derivative is one-sided at DC and Nyquist.
- Quiet-bin randomness. The paper assigns unspecified "random values" to sub-tolerance bins. This engine pins the choice: uniform phase in (-pi, pi) from a per-channel deterministically seeded generator, so identical renders are byte-identical — the property the project's verification protocol depends on.
- Real-signal realization. The spectrum is held as the Hermitian half (`M/2+1` bins) rather than the paper's full-`M` complex formulation — mathematically identical for real input and output.

### Warp markers, labels, and phase resets

Variable-rate time-stretching with user-placed warp markers exists in other tools — DAWs have shipped warp-marker editing on top of their bundled time-stretch algorithms for years. What separates this project is per-marker tempo locking through label definitions and references. A marker can declare a named label; a later marker can reference that label by name; the two markers and every other reference to the same label render at the same effective tempo, and editing the def's tempo updates every ref that cites it. The mechanism is described in the warp marker model below. The use case it was built around is the sonata-form exposition/recapitulation relationship in classical orchestral repertoire, where the same musical material returns multiple times across a movement and should hold a coherent tempo relationship across all occurrences regardless of how the surrounding material is edited.

Per-frame phase coherence is what keeps steady-state content clean. It is also exactly what a transient defeats. An attack — oboe entry, pizzicato, timpani strike — is a moment where the spectrum reorganizes within a few hops, and the phase relationships the vocoder has been propagating no longer correspond to the acoustic event arriving. The attack smears across surrounding frames. The mitigation is a phase reset: at a user-chosen position, the synthesis phase is reset rather than propagated, sacrificing local coherence in exchange for a clean transient. Phase reset markers are the authoring surface for this. They are a separate marker collection from warp markers, visible and edited in their own view, because they parameterize a distinct engine concern: warp markers shape the frame map, phase reset markers protect transients.

### View axes

The interface carries three independent toggles, each shown in the rows at the top of the window: the source/target pair and the warp/phase-reset pair sit in the icon row as radio buttons (the current side wears the toggled-on face), and the `A`/`B` pair is the tab row itself (the active tab wears the blue top trim). The right end of the topmost row also carries a small blue bar of three view buttons — `S+W`, `T+P`, `T+W` — with the one matching the current view combination lit (none lights in the fourth combination, source+phase; see View toggles in the reference). All combinations are valid; the GUI's state is the product of all three selections plus whatever modes happen to be active on top. The playhead time sits in the middle of the bottom toolbar, in monospace. The bottom line below it shows prompts, editors, and status messages, running from the left edge to the right margin, where an over-long message is cut. Unsaved work shows as an asterisk in the window title, after the project name — the title is the source file's parent folder ("K551 - warptempo_gui", becoming "K551 * - warptempo_gui" while unsaved changes exist).

The first pair, **source vs target**, selects the audio domain of the waveform under the playhead. Source view (S) shows the unprocessed source recording with warp markers drawn at the times you authored them. Target view (T) shows the same audio after the engine has applied the live frame map — the waveform is stretched and compressed to reflect what the render will sound like, with markers drawn at their post-stretch positions. The two views serve different stages of the same authoring task. Source view is where warp markers are authored — placing them, enabling and disabling them, editing their tempo and labels — because pinning a marker's time against an acoustic event, and editing a marker in the very map it deforms, both belong in the unprocessed recording. Target view is where you judge the warp by ear and make the one authoring adjustment that wants to be heard: tempo. Nudge an *owning* marker's tempo up or down with `Up` / `Down` — an owning marker stacked with others on one frame refuses the step here, since that stack renders as a single `1.00`, so fix its tempo back in the warp source view; a pass or a label reference refuses too, having no tempo of its own to step. With several markers selected the step moves every selected marker's own tempo together by the same 0.01, refusing the whole press if any one of them cannot take it. That is the only warp edit target view allows. Iteration mode is not an edit and is fully available here — `i` toggles it, the brackets stay on the flags across a view switch either way, and `Ctrl+Alt+R` renders the sweep — but typing a bracket means going back to source view with the rest of the flag editing (see Modes). Everything else warp-related there is display and navigation — selection, `Tab` cycling, the selection readout — and refuses silently: a flag press selects the marker and seats the playhead on it, and arms nothing at all; the horizontal arrows do nothing while a marker is selected, and dragging a flag sideways does nothing either. Target view is always available. Trim narrowed to the section under revision keeps target renders fast enough for this loop to feel immediate.

The second pair, **warp vs phase reset**, selects which marker collection is visible and edited. Warp markers (W) drive the frame map. Phase reset markers (P) protect transients. The two collections are stored, authored, and rendered independently; toggling between them swaps which collection the marker hotkeys operate on but changes nothing else. Authoring proceeds in warp view first, since phase resets have no useful position until the frame map exists. Each collection is edited in its home audio view and only there: warp markers author in source view (see above), and phase resets author in target view, where the stretch is audible and their `N/2` lead-in aligns to the output-domain overlay. In its away view a collection is display and navigation only — phase resets are read-only in source view, warp markers all-but-tempo in target — so a gesture that would author the away collection refuses silently, exactly as a read-only tab does. (Iteration mode is the one thing that sits outside this rule without breaking it: the mode is a state rather than an edit, so it toggles and sweeps from either audio view, while the bracket editing it enables stays in source view with every other flag edit.)

Beyond the data-model difference, both collections want anticipation — placement a little ahead of the acoustic event rather than dead on it — though for different reasons. Warp markers anticipate to make A/B synchronization reliable: rather than landing exactly on a transient, place the marker slightly earlier, in the fading tail of the previous material. The fading tail is a far more dependable alignment cue than the silence or volume dip just before a transient, because the tail can be placed to start at an audible point, whereas a silence or dip is very hard to line up across the A/B tab pair. The lead-in matters most for label-bearing markers and for markers adjacent to label-bearing ones, where the tempo precision the label mechanism enforces only pays off if the underlying timing is itself precise; it also matters for quiet, slow, or legato onsets, where the acoustic event has no sharp attack to pin to — pinning against the louder fade of the prior note beats guessing where the quiet onset begins. The A/B tab pair (below) is the natural way to set these lead-ins precisely, matching the lead-up across paired sections.

Phase reset markers anticipate to give the reset an `N/2` lead-in into the transient. The reset fires at the authored frame — its analysis window centers there — and the overlap-add Hann synthesis takes about `N/2` samples to build the reset's effect to full scale, so authoring the reset `N/2` before the transient lets that lead-in complete right as the transient arrives. In target view, `s` seeds a reset `N/2` before the playhead in target time — clamped to the file start and committed to the nearest whole source frame — and `Space` auditions it by starting playback `N/2` ahead (see the reference); the output-domain overlay depicts the same `N/2` region. The two offsets are deliberate inverses, so dropping with `s` and then pressing `Space` auditions from exactly where the cursor was sitting. This is the only phase-reset drop there is — target view only, like every phase-reset authoring gesture. `N/2` is only the nominal figure, though: if that placement produces an audible discontinuity, nudging the reset with `Left` / `Right` usually clears it — each press moves the reset one painted pixel column (tens of samples even at the finest zoom, more when zoomed out), so drop to the deepest zoom for the smallest available step. Phase resets are placed only where loud transient content provides masking; quiet, exposed passages should carry one phase reset at their start and nothing else, since a reset during exposed material has nothing to hide behind.

The third pair, **tab A vs tab B**, selects between two snapshots of viewport, zoom, playhead, and trim region. A snapshot holds positions and view settings only — never a selection, which belongs to the moment rather than to the tab. Marker stores and engine settings are shared across both tabs; only navigation state differs. The two-tab layout gets used throughout authoring, not just for aligning sections that exist already. Repeated phrases within a single passage benefit from label-locked tempos, and laying those labels down reliably means parking one tab at the first occurrence and the other at the second, then walking the lead-ins forward together to confirm the matching reference point. The same pattern applies at every scale — phrase repeats, sectional repeats, and the exposition-recapitulation relationship a sonata movement turns on. The second tab earns its place from the first repeated phrase onward.

### Warp marker model

A default warp marker is seeded at the file's first frame on first load, carrying tempo `1.00`. A render does not actually require it: when no enabled marker sits at exactly frame zero, the render silently behaves as if a plain `1.00` owner were there, and the opening span plays unstretched until the first real marker. More generally, ambiguous marker arrangements never block anything — two or more enabled markers on the same exact frame collapse to a single `1.00` owner for the render, a reference whose definition was deleted renders as `1.00`, and each such normalization prints one stderr line naming the timestamp. What you see in the GUI is your authored store; the stderr line is the signal that a spot needs attention.

The classical phase-vocoder use case — one constant stretch ratio for the whole file — requires no warp-marker authoring at all: the global stretch ratio is set entirely through the settings `scale` field, and the frame map remains a single constant. Warp markers as an authoring surface come into play when you want phrase-level tempo variation. Each one carries three independent pieces of state.

**Tempo source.** A marker either owns its own tempo or inherits the tempo from the nearest earlier owning marker. An owning marker presents an explicit numeric value; an inheriting marker (a "pass" marker) carries no tempo of its own and resolves its presentation tempo live by walking backward through the marker list. The walk passes over disabled markers and stops at owners; a pass never inherits through a reference — an enabled label reference encountered before any owner ends the walk at the neutral `1.00` instead (a reference owns a duration equation, not a rate, so there is no rate to inherit; the render prints one stderr line per such pass). Because the resolution is live, deleting or disabling an owner re-resolves every dependent pass to the next earlier owner; nothing is frozen on the pass itself.

**Label relationship.** A marker can declare itself a label origin (a `label_def`) or cite an existing label by name (a `label_ref`). A `label_ref` marker inherits its tempo from the named def rather than from positional walk-back. Changing the def's tempo updates every ref that cites it. This is the mechanism for tempo locking across recapitulated material: a sonata-form exposition section receives a `label_def`, the corresponding recapitulation section receives a `label_ref` back to that def, and the two sections will always render at the same tempo regardless of subsequent tempo edits. A reference imposes its definition's target duration on its own segment whatever local stretch ratio that implies, within reason: an implied effective tempo outside `[0.125, 8]` — beyond what any directly authored marker could express — is treated as a mismatch and renders as a plain `1.00` instead, with one stderr line; matching reference segments to their definitions sensibly remains the author's concern. A marker carries at most one of `label_def` or `label_ref`; neither is the unlabeled default.

**Disabled flag.** A marker can be disabled, which silences its tempo contribution as if the marker were not present. Disabling a `label_def` cascades: every `label_ref` citing that def is treated as disabled too. Disabling a non-def marker is local and does not propagate.

An owning marker's tempo is a base value times a scale. The base value is exactly two decimals (the `N.NN` spelling is the on-disk grammar) in the bracket `[0.25, 4.00]` and expresses the headline stretch ratio relative to the source recording — `1.00` is no stretch, `1.05` is 5% faster, `0.95` is 5% slower. The base value's precision is deliberately coarse; you author at the resolution you would set a metronome, not finer. The scale is a separate full-precision multiplier in the bracket `[0.5, 2.0]`, defaulting to `1.0000` (written shortest round-trip, padded to at least four decimals). Its intended use is fine-tuning a marker's effective tempo to approximate a neighboring section's effective tempo when that neighbor uses a `label_ref`: read the neighbor's resolved `base*scale` off the bottom-strip readout while that neighbor is selected, and apply a matching scale to the marker being authored. Scale can serve any other purpose inside the bracket; out-of-bracket values are rejected at the editor with a red flash. The reference project in `projects/550 - 1/` shows both fields in use across a complete movement.

Phase reset markers carry two pieces of state: a position and a disabled flag. They have no tempo, no labels, no scale, no mode. The engine concern they parameterize is *where to reset* — re-grounding the synthesis phase at the transient that opens the segment. The reset fires at the authored position, with the analysis window centered on it.

## Output and the limiter

The render product is a finished WAV: 24-bit PCM, brought to a delivery ceiling by the built-in limiter — a transparent spectral stage at -0.3 dBFS, then a 0 dBFS lookahead peak limiter with a hard-clip backstop. The limiter is unconditional; there is no bypass and no output-format choice.

As future-proofing for later engines, every archival render — the GUI's `Ctrl+Alt+R`, the sweeps' batch cells, and the CLI — also writes the full frame-map pair: `<wav-stem>.warpframemap` (whitespace-separated `<src> <tgt>` frame pairs, precise double breakpoints) and `<wav-stem>.phaseresetframemap` land in `~/.cache/warptempo_gui/<pid>/` (batch cells under a subdirectory mirroring their batch folder). Together they are exactly the engine's input for the full (untrimmed) render of that recipe, with the phase resets already compiled into the engine's origin-centered query domain; trim never affects the pair — a trimmed render feeds the engine a trimmer-translated pair, and the cached pair is deliberately the full one — and the limiter does not apply to map files. Any time-stretch library that accepts a sample-domain warp map could be driven from these files. Retrieve them between the render and program close: the GUI removes its per-process directory when it exits, and CLI-written directories and orphans from dead processes are swept at the next GUI launch, so nothing accumulates. The pair is written all-or-nothing — a write failure removes both files rather than leaving a mixed-generation pair.

## Reproducibility

Rendering is deterministic per machine and binary: the same project rendered twice on the same host with the same build produces byte-identical WAV output, every time. This is a hard guarantee — the whole pipeline is fixed-order and free of timing- or scheduling-dependent math. GUI and CLI from one build on one system state are byte-identical, unconditionally.

Across builds the boundary is not the compiler's code generation but the libraries underneath it. Floating-point contraction is switched off in the build, so how the compiler lays the arithmetic out no longer touches a single output bit: the same project renders byte-identically whether the binary was tuned for this CPU or built generically, and on another machine of the same architecture — same compiler, same glibc and FFTW — it renders those same bytes again. What does move the output is a change in those libraries, and the movement is tiny. For a sense of scale at the far end: a completely different toolchain on a different architecture — a WebAssembly build of the same engine, carrying its own C library and its own copy of FFTW — differs from the native build by 67 samples of a 7.6-minute render, each by a single least-significant bit. On threshold-straddling material the limiter can quantize a difference that small into a localized one (measured at the -38 dBFS / two-samples class on a stress recipe — far below audibility, and ear-verified quality-neutral). So compare renders byte-for-byte freely within one set of library versions; after a glibc or FFTW upgrade, re-render anything you intend to keep comparing against.

## Hotkey reference

The reference is grouped by function. Everything is keyboard unless marked as a mouse gesture. Bindings are case-described: `Ctrl+S` means Control held with the `s` key, `Shift+B` means Shift held with `b`. Where a key does different things in warp view versus phase-reset view, both are given.

Bindings are matched exactly. A key pressed with a modifier this reference does not list for it does nothing at all — there are no near-miss chords that fall back to the unmodified binding, and no gesture has a modified variant that does a related-but-different thing. Two consequences worth knowing: the prompts are case-sensitive, so a `[Y]es` prompt wants `y` and not `Y` — the capital in the label marks which letter answers, the way pacman's `Y/n` does, not that shift is required; and inside a text editor the clipboard chords are `Ctrl+C` / `Ctrl+X` / `Ctrl+V` exactly, so the terminal habit of `Ctrl+Shift+C` does nothing there. Alt lives only in the four `Ctrl+Alt` chords (the two render chords and the two phase-reset propagate pastes, all documented below); it does nothing on the mouse — panning is the plain drag and the plain wheel — and no other binding uses it. Super (the Logo key) belongs to the window manager: while it is held no key reaches any command, so a window-manager chord can never leak a keypress into the GUI — with one deliberate exception: bare `e` is the left mouse button rather than a key, so `Super`+`e` still clicks, exactly as `Super`+click does.

**Files and session.** The source is chosen on the command line (`warptempo_gui <audio_file>`); there is no in-session file open or drag-and-drop, so switching sources means relaunching, and a load that fails prints the reason and exits. `Ctrl+S` saves all sidecar files. `Ctrl+Q` closes the window, routing through an unsaved-changes prompt when the session is dirty; it also works while the settings prompt or a paste-confirmation prompt is open (it abandons that prompt first, without committing it).

**The top rows** (mouse). The rows at the top of the window are buttons, and every button except `Settings` and `Navigation` — the two that open menus — is a click-shaped spelling of a keyboard command, behaving identically to it. From the top:

- The menu row holds `Quit`, `Navigation`, and `Settings` on the left and the view bar on the right. `Quit` lights up under the pointer, and a plain click on it is the same close as `Ctrl+Q`, unsaved-changes prompt included; it works even while a file is still loading. `Settings` opens a small dropdown of the settings you edit by hand — `GUI scale` and `Playback speed`, then `Title`, `Notes`, `URL`, and `Cover` — and picking one opens the settings prompt with that key and its current value already filled in, ready to edit (the `;` key still opens the bare settings prompt directly). Neither door opens it in a read-only tab: the prompt can set the engine keys, so a lock closes it, and picking an item there just closes the menu. `Navigation` opens a second dropdown, of view and stepping commands with their keys shown beside them — `Zoom in` (`=`), `Zoom out` (`-`), `Overview` (`0`), and `Center on focus` (`C`), then `Next marker` (`Tab`), `Previous marker` (`Shift+Tab`), and `Walk both tabs` (`Ctrl+Shift+Tab`) — and picking one does exactly what its key does, no more and no less; an item whose command cannot act right now simply does nothing, like the key. This menu also opens in the history view, where every item works — the marker steps and `Center on focus` walking that view's difference flags, as their keys do in there — except `Walk both tabs`, which greys out: in that view `Ctrl+Shift+Tab` steps the `Remote`/`Local` tabs instead, so the item would not do what its name says. The `Settings` menu does not open in the history view at all. Both menus behave the same way: the item runs when you release the mouse on it, `Esc` or a click anywhere else dismisses the menu, the button whose menu is open stays lit for as long as it is up, and only one dropdown is ever open. You can press on one item and slide to another before letting go — the highlight follows the pointer, so exactly one item is ever lit and it is always the one you are on, and releasing runs whatever is lit at that moment. Slide onto the line between the two groups, onto the menu's edge, or off the box altogether and nothing is lit; release there and nothing runs, with the menu still up so you can try again, and sliding back onto an item lights it again. The hold can start on the button itself: press `Settings` or `Navigation`, keep the button down, drag into the menu that drops, and release on the item you want, all in one motion. Let go back on the button, or anywhere else that lights nothing, and the menu simply stays up — which is why a plain click on it still just opens the menu. With one menu up you can switch to the other simply by moving the pointer onto its button — no click needed, and the button you slide onto lights as its menu appears. Moving onto `Quit` or the view bar instead CLOSES the open menu, and that button lights the moment it does: only one button in the menu row is ever lit, so a command button and an open menu never stand together. After that first click the two menu buttons answer the pointer alone, the way a menu bar does everywhere else: with a menu having been opened from this row, moving onto `Settings` or `Navigation` opens that menu with no click at all — so sliding onto `Quit` to put a menu away and then sliding back brings it up again, and you can walk both menus with the mouse without pressing anything. That lasts until you dismiss or walk away. Putting a menu away deliberately ends it: `Esc`, picking an item, clicking the open menu's own button, or a click anywhere else. With no menu showing, so does anything else you do — any click that is not on `Settings` or `Navigation` themselves, any key you press, and taking the pointer off the menu row, down to the waveform, say, or out of the window from anywhere below that row. Sliding straight up off the row onto the titlebar does not: that is a step out of the window, not out of the row, so the button you left keeps its highlight and coming back down finds the menus still answering the pointer. After any of those the next menu takes a click again, exactly as the first one did. Those last three are about the quiet row, though: while a menu is actually up, that menu's own rules are what decide, and it takes more than a stray key or a wandering pointer to end things. Press a key the menu ignores and it stays open with the row still answering the pointer; leave the window and the menu is still standing when you come back, so moving onto the other button still switches with no click. Before the first click the row is quiet: the pointer crossing `Settings` or `Navigation` does nothing whatever, so a menu never springs open at a pointer merely passing through. While a menu is up nothing else in the window lights under the pointer — the rows the menu hangs over stay unlit until it closes. Because the hover has usually switched already, a click on the other button lands on a menu that is now open and closes it, exactly as clicking an open menu's own button does. The view bar is a small blue bar of three buttons — `S+W`, `T+P`, and `T+W` — each a click-shaped spelling of the matching digit key (`1`, `2`, `3`; see View toggles): a plain click jumps straight to that view combination, the button matching the current combination wears a toggled-on face and clicking it does nothing, and none lights while in the fourth combination (source+phase), which has no button or key. The bar highlights under the pointer and dims to grey while the window is not the focused one.
- The toolbar row carries `Save` (`Ctrl+S`), `Undo` (`Ctrl+Z`), `Redo` (`Ctrl+Shift+Z`), and `Render` (`Ctrl+Alt+R`). A button that cannot act right now — during a load, `Undo`/`Redo` in a read-only tab or with nothing left to step — greys out and ignores the pointer entirely; `Save` and `Render` stay live in a read-only tab, because a lock is about the piece's markers and settings, not about writing out or rendering what is already there; a live one lights a thin outline under the pointer and fills while the mouse button is held. `Render` takes `Shift`: a `Shift`+click renders into the numbered miscellaneous folder exactly like `Ctrl+Alt+Shift+R`, while a plain click is the ordinary `Ctrl+Alt+R` render (`Shift` on the other toolbar buttons does nothing). In iteration mode the button reads `Render Iterations` and clicking it runs the sweep; `Shift` does nothing there, and the hover hint drops its shift line to say so. While one of the renders you asked for is actually running — a plain render, a `Shift` miscellaneous render, or an iteration sweep — the button changes again: it reads `Cancel`, wears the cancel glyph, and clicking it stops the running work — plain or `Shift`+click alike, one face, one act. The automatic preview updates in target view (the brief `Updating...` moments) are not one of these: they never show the cancel face, and they need no cancelling — any edit that affects them replaces them by itself. This is the one button whose click is not its key while that face is up: `Ctrl+Alt+R` on the keyboard keeps its own behavior during a render (it stops the running render and starts a fresh one), and `Esc` still cancels from the keyboard as always — the button is simply the cancel itself, and goes back to being `Render` the moment the work ends. In the history view `Render` cannot act at all — nothing in there renders — so it greys out with the rest of the buttons the view switches off. `Save` is the button that changes there instead: it reads `Save and Commit`, wears the commit glyph, and clicking it saves the piece and then commits the checkpoint, both described under Checking history; it greys out whenever the session already matches the newest checkpoint, since there would be nothing to commit. And while a checkpoint is publishing in the background, `Save` reads `Committing...` and is greyed out wherever you are — saving is held for those few moments, because the program is writing the same files out to the repository at that instant; it comes back by itself the moment the checkpoint lands.
- The tab row carries the two Breeze-style tabs, `A` and `B` (in the history view the same two slots become the history switch instead, reading `Remote` and `Local`; see Checking history): the active tab wears the blue top trim, and clicking the other one switches tabs exactly like `Ctrl+Tab` — same selection clearing, same view restore, no difference at all; clicking the active tab does nothing. Each tab also carries a small lock beside its letter: a bright closed lock when that tab is read-only, a dimmed open one when it is writable. Clicking the lock on the active tab toggles its read-only state exactly like the `o` key; on the inactive tab the whole tab, lock included, is the switch.
- The icon row holds seventeen small buttons in six groups: the source/target pair switches the audio view (the `t` key) and the warp/phase-reset pair the marker view (the `p` key) — the first two are a document with an arrow leaving it and one with an arrow entering it, the next two a speedometer gauge (warping is a speed change) and a stopwatch; in each pair the current side shows a toggled-on face and clicking it does nothing, radio-style; then, in a group of its own, set trim from region (the `x` key) — a pair of scissors, cutting the piece down to the span; then copy phase resets (`Ctrl+P`) and paste (`Ctrl+Alt+P`, with `Shift`+click for the flags-only paste, `Ctrl+Alt+Shift+P`), the BPM editor (the `m` key), iteration mode (`i`), and follow (`f`) — the last two showing a toggled-on face while their mode is on; then listen to renders (`l`) and the load editor (`'`); and finally, set off by a small gap, the history group: the history view (`h`), which shows a toggled-on face while the view is open, then the cumulative reading (`u`), which shows a toggled-on face while that reading is on, then revert (`Ctrl+H`), then the two arrows that walk the history, older (`,`) and newer (`.`), each taking `Shift` for the jump to that end of the walk exactly as the keys do. These buttons never grey out — one that cannot act right now simply does nothing, exactly like its key — with two exceptions, both about the history view: while it is open, the buttons that view refuses grey out and ignore the pointer, and the other way round, the two walk arrows, the revert button and the cumulative toggle are greyed out and ignore the pointer whenever the view is closed, their keys meaning nothing outside it. The cumulative toggle still SHOWS its setting out there — greyed but lit when the reading is cumulative — since that setting is remembered whether the view is open or not. Revert is greyed out inside the view as well whenever no difference is selected, since there would be nothing to revert (see Checking history).

Every button in the top rows except `Quit`, `Settings`, `Navigation`, and the three view buttons shows a small tooltip naming its action and key after the pointer rests on it for a moment; on `Render`, the paste button and the two walk arrows — the four where `Shift` changes the action — a second, smaller line names what the `Shift`+click does instead. A greyed-out button shows its tooltip too: a button that cannot act right now is exactly the one you may need told what it is for and when it works. The tooltip goes away the moment you act — any click, any key, any scroll — and none appears at all while a prompt or one of the editing prompts is up, since the action it would name is one those surfaces ignore.

**The bottom toolbar** (mouse). One more row of buttons sits at the bottom of the window, between the waveform and the status line — permanent, the same on every machine. Like the top rows, every button is a click-shaped spelling of a keyboard command and behaves identically to it: a click that cannot act does nothing, exactly like the key. Two groups of buttons with the clock between them. On the left, the transport: go to start (`Home`), play (`Space`), stop (`Space`), and go to end (`End`). Play and stop split the one `Space` binding between them — while nothing is playing the stop button is greyed out and play starts the audition; while one runs, play greys out and stop stops it — so the pair always shows which half is available (playback ending on its own swaps them back by itself). On the right, four arrow buttons in one line — left, down, up, right — each pressing the bare arrow key it shows, with every rule those keys have: the playhead step, the marker-lane nudge with a selection, the `Up`/`Down` tempo step, the same refusals in a read-only tab. Holding an arrow button repeats it exactly like holding the key — the same initial pause, the same rate — for as long as the pointer stays on the button; slide off and the repeating pauses, slide back on while still holding and it resumes. The transport buttons do not repeat. Between the two groups, centred in the window, is the playhead time in monospace — the only monospace text in the program: the position of the moving playhead while something is playing, and of the resting cursor otherwise. It is written `MM:SS.mmm`, and a source past 59:59.999 simply reads that. Its cell is sized for the widest digits, so the numbers never shift about as they count. In the history view the buttons that view refuses grey out here too — play, stop and the four arrows — while go-to-start and go-to-end keep working, as their keys do in there. The buttons show the same resting tooltips as the top rows, appearing above the button instead of below it.

**Playback and playhead.** `Space` starts and stops playback from the cursor to the end of what is playable — the song's end in source view, the end of the rendered preview (the trim window) in target view (`Return` and keypad `Enter` are not playback keys — they open the flag editor on the focused marker; see Warp marker authoring). Playback always issues from the playhead; a highlighted region is not a launch point — to audition a span, click its start on the waveform's lower half (see Region select and trim). Nothing loops: every audition plays once to its end and stops on its own. In source view that end is the song's end — the trim window does not bound listening, since what you hear there is the file itself. In target view it is the end of the rendered preview, which is the trim window. `Left` and `Right` move the playhead one pixel. With one or more markers selected they move it *in the marker lane* instead: the focused marker moves one pixel and the playhead rides along with it — one marker, never a group, so if several are selected the press first narrows the selection to the focused one and then steps it. The cursor is always drawn, so you see it ride: it stands on the focused flag and moves with each step. Dropping the selection hands the playhead back to the waveform, where the arrows step it freely again — any deselecting route does it: a click on the waveform, `Home`/`End`, or a trim edit. With nothing selected an arrow press moves the playhead one pixel, drops the marker focus, and dissolves any highlight. `Home` and `End` jump the playhead to the trim begin and trim end, and they drop the marker selection as they go. A keyboard playhead move stops playback — but a command that only moves the view (zoom, `PageUp`/`PageDown`, and `0` from any zoom short of the full-song view) does not, and neither does the `Up`/`Down` tempo step, which leaves the selection and the audition standing; trim edits (`x`, `Shift+X`, and every pointer trim gesture) stop playback in both audio views — a trim change redefines what an audition would play. Mouse moves are different — a click on the waveform's upper half (or on the ruler, or on an empty spot in the marker lane — the three are one surface) moves the playhead to the clicked spot at the moment you release, reseeking live playback there instead of stopping it, and a plain drag on that same surface pans the view instead (see Zoom and view); nothing happens at the press itself, so the two never fight — a still click places, a moving drag pans. The waveform's lower half is the scrub surface, and there the click acts the moment you press (the right button does nothing anywhere). A scrub click stops playback if a session is running, and a click on a stopped one starts the moving scanner from that spot, so auditioning a new place is stop-then-click (each start is a fresh audition, picking up any changes to what is playable) without touching the resting playhead, selection, or highlight; it is a one-shot per click, Ableton-style — holding or dragging does nothing further, and playback simply continues until stopped; `Space` stops it as always. (A top-strip click stops playback only when it actually does something — selecting or editing a marker, or setting a trim bound; a click that claims no gesture leaves playback alone entirely, and so does a plain trim-bar click that never becomes a drag — a bound or bar drag stops playback at its first actual bound change, not at the press.) `f` toggles follow mode, which scrolls the viewport to keep the playhead in view during playback — during only: when playback ends, whether you stop it with `Space` or it reaches the end on its own, the viewport stays exactly where it was and the moving line simply vanishes. The two endings are identical in every respect. Panning away during playback wins over the chase: any pan — the plain drag, the wheel, the touchpad, `PageUp`/`PageDown`, the `Ctrl`+drag — switches follow off for that session, and the view stays where you put it until the next launch or an explicit `f` re-enable. Playback speed is set through the settings prompt — `:playback_speed=0.5` — with the ten one-decimal values 0.1 through 1.0 as the only accepted speeds; the default is 0.7. Set in target view, the value stores silently and becomes audible on the return to source view (target view always plays the authored warp at its natural rate).

**Zoom and view.** Zoom is continuous: `=` and `-` step one whole level per press from wherever the zoom rests, and the `Ctrl`+drag gesture below reaches every fractional level in between (the wheel does not zoom — it pans, below). The deepest zoom is fixed; the shallowest is the file's own full-song view — zooming all the way out always rests with the whole song visible, exactly filling the width for any file longer than the deepest level's span at the current window width (1.2 s at the 1920 px deployment width; a shorter file rests at the deepest level instead, the remainder of the width showing past-EOF silence). `0` goes to that full zoom-out, whole song in the window; pressed again with the zoom already there it does exactly what `c` does — so `0` twice takes you out to the whole song and back in to the working zoom on the marker you are working on. The first press is purely a view command, moving no playhead and leaving the selection and any highlight exactly as they were; the second is `c`, with everything `c` does. The working zoom — the fine-tuning view (a zoom level fixes time per pixel, so its span scales with window width: 2.4 s across the waveform at the 1920 px deployment width) — is where `c` lands instead. `c` jumps the playhead onto the focused marker when one exists, then snaps to the working zoom centered on it; with no focused marker it just snaps and centers on the playhead. `Ctrl`+drag on the waveform — either half, and equally on the ruler or an empty stretch of the marker lane — swallows the mouse cursor and works both axes at once, anchored on the song position where the click landed — vertical motion zooms (down zooms in) and horizontal motion pans. A dim vertical stem marks the anchor: it appears the moment you press, so you can see the pivot before you move, and if panning pushes it to a screen edge it pins there and takes on that edge's content. The drag moves the view and nothing else — it leaves the playhead, the marker selection and any highlight exactly as they were, in the history view as much as outside it. Travel is unlimited while the cursor is captured, and on release the cursor reappears at the stem's column. Zoom is this drag, the `=`/`-` keys, and the two-finger pinch on a touchscreen — nothing else. Panning alone is the PLAIN drag, on the same surface the zoom drag covers minus the waveform's lower half (which scrubs): a smooth grab that captures the cursor for unlimited travel once the drag is under way, the cursor reappearing where the drag left it. A plain drag that never moves more than a few pixels is not a pan at all — it is the click, placing the playhead at the release (see Playback and playhead). The scroll wheel pans too, a tenth of a screen per detent, over the waveform and the whole marker strip alike. Double-click on the trim bar — the band above the ruler that carries the trim window's bar and its begin/end endcaps, anywhere along it — frames a span: a highlighted region if there is one, otherwise the trim window when it is narrower than the whole song, otherwise the whole song — with a small margin around a region or trim and none around the whole song. It is one-way and idempotent: a second double-click on the same view does nothing, but any pan or zoom in between re-frames. This differs from the `0` key, which only ever goes to the full-song view (and, from there, to `c`). `PageUp` and `PageDown` step the viewport back and forward by a tenth of a screen per press — the same stride as the wheel, so the keyboard and the wheel pan at one speed; hold for a continuous glide.

**View toggles.** `t` switches the audio domain between source and target (S/T); `p` switches the marker collection between warp and phase reset (W/P). The bare digits jump straight to a combination: `1` is S+W, `2` is T+P, `3` is T+W (each applies whichever of the two switches it needs, with everything a `t` or `p` switch normally does; pressing the digit for the combination you are already in does nothing). The same three combinations sit as buttons at the right end of the top menu row — a click is exactly the digit (see The top rows). A `t` switch carries the selection across, on both sides, with the playhead landed on the focused marker — `t` shows the same markers in another domain, so the selection travels with them. A group crosses whole: `t` keeps every selected marker selected (a resting highlight does not travel — its ends are positions in the domain you just left) and lands the playhead exactly on the focused marker's position in the new domain. `c` keeps a group too — it jumps to the focused marker and re-zooms with the others still selected; `0`, the overview, is purely a view command and touches nothing (pressed with the whole song already in the window it is `c`, and then it is `c` that keeps the group). Switching the marker collection (`p`) or the tab (`Ctrl+Tab`) is different: those change which markers you are addressing at all, so they simply drop the selection. What you get back instead is automatic and comes from where the playhead is: on arrival, if the playhead is standing exactly on a marker of the newly active collection, that marker is selected for you; if it is standing anywhere else, nothing is selected and the cursor is your playhead as usual — being one frame off is being off, not close. The tab's remembered playhead is restored exactly as you left it, which is what makes that recovery predictable: leave a tab with a marker selected and the playhead on it, come back, and the same marker is lit. Opening a session works the same way, from the saved playhead — and so does loading a render in place with `'`. Group work does not cross a switch (select again on the other side, or lean on undo/redo, which re-selects a whole touched group). `o` toggles read-only on the active tab. What it protects is the piece itself — the markers and the engine settings — and nothing else: marker, tempo, and phase-reset authoring are locked out, while navigation, playback, the view toggles, the trim window, saving and rendering all stay available. The point is a finished section you want to stop nudging by accident, not a tab you cannot work with: lock it, then go on moving the trim window to compare a passage against your other tab, re-render, and save. One navigation gesture is not exempt: with a marker selected the horizontal arrows are in the marker lane, where the same press authors, so a locked tab refuses them outright rather than falling back to a plain playhead step. Drop the selection first — a waveform click, or `Home`/`End` — and they navigate again. Saving works: `Ctrl+S` saves from a read-only tab, writing the state the tab already holds — as does the `[S]ave` answer to the close prompt, which always did. Rendering works too: `Ctrl+Alt+R` and `Ctrl+Alt+Shift+R` read the authored state rather than change it. So does the whole trim window — the bound clicks, the endcap and bar drags, `x` and `Shift+X`, and a typed `trim_begin=` / `trim_end=` all commit in a locked tab, trim being part of the tab's own view state (with the viewport, the zoom and the playhead) rather than part of the piece. Both propagation commands — `Ctrl+P` copy and the `Ctrl+Alt+P` pastes — are blocked, as are undo and redo (`Ctrl+Z` / `Ctrl+Shift+Z`); to undo an edit made from a read-only tab, `Ctrl+Tab` to the writable tab first. Also blocked: `Delete`, the marker drops and nudges, the flag and BPM editors, `i`, and `'`. The settings prompt does not open at all in a read-only tab — it can set the engine keys, which is the piece — so `;` does nothing and so does picking an item from the `Settings` menu: the menu closes and nothing happens. The menu items are not greyed out; they simply have nothing to do there. `Ctrl+Tab` switches the active A/B navigation tab; `Ctrl+Shift+Tab` advances both tabs' marker focus in lockstep and lands on the opposite tab.

**Marker focus and selection.** `Tab` and `Shift+Tab` (the latter also reachable as the ISO left-tab key some layouts send) cycle marker focus forward and backward, moving the playhead onto the focused marker. The view always recenters on the focused marker, at whatever zoom you are already at — the walk never changes the zoom, so a wide view stays wide; `c` is the command that snaps to the working zoom — and follow mode does not gate the cycle. A step with no marker to focus does nothing at all. The walk skips disabled markers and operates on whichever collection the W/P toggle has active (trim bounds are not part of the walk — `Home`/`End` jump to them). A plain click on a marker's flag — the flag is the marker's one clickable part; its stem on the waveform is a visual cue only — is the third way to bring the playhead onto a marker: it selects the marker and seats the playhead on it without moving the view at all (unlike `Tab` and `c`, which both re-zoom and recenter); it works in both views and both collections, also in a read-only tab. Anything else that changes which marker is focused brings the playhead along too: opening an editor on a marker (`Enter`, a double-click, or `m`), `Ctrl+N`, and a propagate paste, which lands on the first reset it created (the `p` swap is different — it drops the selection outright, and only the arrival coincidence auto-select can hand it a marker again; see View toggles). The reasoning: the arrows move the focused marker while a selection exists, so the playhead keeps station on the focus — the cursor is always drawn, and it would otherwise visibly rest away from the marker your next arrow press is about to move, with `Space` playing from that stale spot. Opening an editor clears a resting highlight too, exactly as the marker click does (a highlight only ever rests with nothing selected, so routes that start from a selection never find one). With several markers selected, a plain flag click on one of them behaves exactly like a click on any other marker: it selects that one marker and seats the playhead there at press time, and a drag from it moves that marker alone — dragging never moves a group. `Alt`+clicking or `Alt`+dragging does nothing anywhere. Clicking an empty spot in the marker lane works like an upper-half waveform click — a motionless click clears the marker selection and places the playhead at the release, a plain drag pans the view, a `Shift`+drag selects a region and a `Ctrl`+drag zooms; double-clicking an empty spot creates a marker at that position, selects it, and seats the playhead on it — exactly the `s` drop, so warp gets a copy-previous-tempo marker and phase reset the lead-in seed — in the collection's home view only.

**Warp marker authoring (W view, source).** These author warp markers, so they run in warp's home view — warp view in source audio view. In target view every one of them refuses silently except the one tempo adjustment available there: `Up` / `Down` on an *owning* marker (a pass or label reference refuses, since it has no tempo of its own to step; an owning marker stacked with others on one frame refuses too — that stack renders as a single `1.00`, so fix its tempo back in the warp source view). The horizontal arrows do nothing at all in warp target view with a marker selected, and dragging a flag sideways does nothing there either — `Up` / `Down` is the whole of tempo authoring, identical in both audio views.

`s` drops a marker at the playhead copying the previous marker's tempo — so the drop normally splits a section without changing how anything sounds, where a neutral `1.00` drop in the middle of a warped section would audibly change it. Two cases are not silent, both by design. Dropping onto a frame where an enabled marker already sits (which is where the playhead is sitting right after you click a marker) leaves two markers on one frame, and the render collapses any such stack to a single `1.00` — the markers involved turn red immediately, so you see it happen rather than discovering it later. And splitting a *label definition's* section shortens the definition, so every reference to that label changes duration too: a definition's span is its meaning, and halving it halves what the references reproduce. Where there is no usable previous tempo to copy — no earlier marker, a label reference, or a stack of markers on one frame (which renders as a single `1.00`) — the new marker takes `1.00` instead. A pass marker is not one of those cases: it resolves to whatever tempo is actually sounding there, which is exactly what keeps the drop silent. Edit the tempo afterwards in the flag editor if you want a different one.

`Ctrl+N` toggles pass (inherit) status on the focused marker. `Ctrl+D` toggles the disabled flag on every selected marker (this works in both W and P views). `Delete` deletes every selected marker — label definitions included, even with live references (the orphaned references render as `1.00` with a stderr line each). `Up` and `Down` nudge the focused marker's tempo by ±0.01 — and with several markers selected they step every selected marker's tempo together by the same ±0.01, refusing the whole press if any selected marker cannot take it: a pass, a label reference, a disabled marker, a stack sharing one frame, or one already at the 0.25 / 4.00 end (the single-marker press keeps its usual behavior, including converting a pass to an owning marker — a label reference is left untouched); a run of group steps is one undo entry, exactly like the single-marker burst. `Left` and `Right` nudge the focused marker's position by one pixel — and with several markers selected the press narrows the selection to the focused marker and steps that one: moving markers is always a one-marker act. A held arrow is one undo entry, and the marker stops at the song edges. A plain click on a marker's flag selects it; dragging the flag moves the marker (no modifier — the drag begins after a few pixels of motion, so a click stays a click) — and dragging moves that one marker, even when several are selected: the press selects the marker you grabbed and the drag carries it alone, the playhead follows it, and the drag has no cancel — `Esc` while dragging does nothing, the release commits where the marker stands, and `Ctrl+Z` is how you put it back.

`Return` or keypad `Enter`, or a double-click on the flag, opens the focused marker's flag editor — the canonical-line surface where the whole marker line is edited as text: tempo, `label_def` / `label_ref`, per-marker scale, and (with iteration mode on) the iter bracket. It is the only surface for authoring labels and per-marker scale. The editor opens on a marker-colored background (the invalid-commit flash turns it red) with the whole line selected: typing replaces it, and a bare `Left` or `Right` jumps to the start or end. Inside the editor `Enter` commits (invalid input flashes red and keeps the editor open) and `Esc` exits without committing. While it is open the keyboard belongs to the editor: ordinary text-field gestures work — typing, `Left`/`Right` and `Home`/`End`, `Shift` with those to select, `Ctrl+Left`/`Ctrl+Right` by word, `BackSpace`/`Delete` and their `Ctrl` word-erase forms, `Ctrl+A`, `Ctrl+C`/`Ctrl+X`/`Ctrl+V`, and double-click to select a word. The clipboard is the real one, shared with the rest of the desktop: something copied here pastes into a browser or a terminal, and a URL copied in a browser pastes into a settings field. Pasting when there is nothing on the clipboard does nothing at all — it will not wipe the selection. `Ctrl` and `Shift` combine with the motion keys the way they do in any text field. Everything else does nothing at all — `Alt` with anything included — so a stray chord cannot throw the edit away on its way to a command. The two chords that reach through are `Ctrl+S` (saves, editor stays open) and `Ctrl+Q` (abandons the edit, then the usual close routing). `Esc` is not one of them — it is the editor's own cancel key, handled inside the editor rather than reaching past it. Note there is no undo *inside* the editor: `Ctrl+Z` does nothing there, so an unwanted edit is fixed by retyping or by `Esc` and reopening. The mouse is unaffected — clicking anywhere but the editor's own text closes it without committing, and the click then does its normal work (another marker's flag selects that marker; double-clicking the same marker again just reopens the editor). That includes the menu row: clicking `Settings` or `Navigation` while a flag edit is open discards that edit, exactly as clicking away from it anywhere else does, and the menu then drops down as usual — a menu never stands over a live edit. The rest of the top strip's buttons are the one place a click leaves the edit alone: their clicks are their keys, so they meet the same gate the keyboard does and only `Save` (`Ctrl+S`) and `Quit` (`Ctrl+Q`) do anything while an edit is up — everything else there is inert, just as pressing its key would be. The BPM editor opens with its bracket text selected the same way.

On screen, each marker is a small colored flag in the lane directly above the waveform, carrying its text on the flag itself — the tempo or label for a warp marker, `p` for a phase reset — anchored at the marker's exact frame, with its stem running from the flag down through the waveform. A text longer than nine characters shows shortened to its first nine followed by `...` on the flag; an iteration bracket does not count against those nine and is never shortened — the flag grows to carry it whole, because the bracket is the thing you are reading while the mode is on. The full text lives in the flag editor, and a selected marker's resolved value shows in the bottom strip's readout (`Ctrl+C` copies it to the clipboard, ready to paste into another marker's flag editor or anywhere outside the program). Flags of nearby markers may overlap; the later marker in the file's order paints on top, and clicking lands on whichever flag you see. Every enabled marker's stem is always visible in the marker's own color; a disabled marker dims its flag and shows no stem at all. Selection is a brightness cue: the selected marker's flag brightens while its stem keeps the calm unselected color — a selected disabled marker brightens the same way inside its dim, so selection reads on a disabled marker too. The flag editor is the flag itself unrolled: it grows from the marker's own position to fit the full text, and for a very long text the view inside it scrolls as the caret moves. The playhead cursor is the white marker-style head sitting in the marker lane, its tip on the waveform's top edge, with its white stem below; a marker's flag paints over the head where the two coincide, and when the playhead stands exactly on a marker the marker's own stem shows in place of the white one — the cursor is still there, standing on the marker, and playback still launches from it (the phase-reset lead-in audition included). A marker that renders as the fallback tempo `1.00` paints its flag and stem red — a `label_ref` to a missing or out-of-range label, a pass that ends up inheriting from a reference, or a stack of markers sharing one frame (which collapse to a single `1.00`, the whole stack reddening as one) — and neither selection nor the disabled dim takes that red away: a disabled red marker is still recognisably red, and the warning is never masked; the same red marks a stack of coincident phase resets. The red is a live display cue, so a red stack you drag apart stays red until you release. In a read-only tab flag clicks still select and seat the playhead (dragging and the editor refuse).

`Shift`+flag-click selects an inclusive range, file-manager style: it selects every marker between the focused marker — the one last clicked, plain or `Shift` — and the clicked one, in either direction, with the clicked marker becoming the new focus and the playhead seating on it — `Space` then auditions from the playhead, standing on that new focus; with nothing focused it just selects and anchors on the clicked marker. `Ctrl`+flag-click toggles one marker's membership in the selection, seating the playhead on whichever marker ends up focused — emptying the selection leaves the playhead where it is. A plain marker click seats the playhead on that marker, and a `Shift`-range or `Ctrl`-toggle click seats it on the marker it leaves focused (`Tab`/`Shift+Tab` and `c` land too, additionally recentering; dropping a new marker with `s` seats it there as part of the drop, and a waveform click places the playhead but selects nothing). The playhead then follows the focused marker: a nudge or flag drag carries it along, so `Space` keeps auditioning from the marker.

**Phase reset authoring (P view, target).** These author phase resets, so they run in phase reset's home view — phase reset view in target audio view. In source view they refuse silently (phase resets are read-only there); selection, `Tab` cycling, and the readout still work. `s` drops a phase reset in target view only, seeding it `N/2` samples earlier in target time than the playhead (clamped to the file start, snapped to the nearest whole source frame), and the playhead moves back onto the seeded reset — the one drop that relocates the playhead, so the next audition starts at the new reset: the overlap-add Hann synthesis lead-in means a reset's output reaches full scale about `N/2` samples after its authored frame, so placing the reset `N/2` before a perceived transient lands its full-scale output on the transient (this is the offset the output-domain overlay depicts, and it exists only in target view where that overlay does; the overlay shows for a single focused reset and hides while several markers are selected, and while the history view stands, where nothing about the live markers paints; a region highlight resting beside it does not hide it). Also in target view only, `Space` auditions that alignment by starting playback `N/2` samples ahead of the playhead without moving it — the resting playhead returns on stop. `Space` does this exactly when a phase reset is *focused* — the same condition that makes the overlay meaningful — so the states that drop the focus (no selected reset, a disabled one, several markers selected) also return `Space` to its ordinary behavior, playing from the playhead. A resting highlight is not one of them. It keys on that focus and not on whether the ring is currently *painted*, so scrolling the reset out of view, zooming until the band collapses, or opening the history view — which paints no ring at all — does not change what `Space` does. `Ctrl+D` toggles the disabled flag on every selected phase reset. `Delete` deletes every selected phase reset. `Left` and `Right` nudge the focused phase reset by one pixel — and with several selected the press narrows the selection to the focused reset and steps that one (the same one-marker rule the warp column follows), stopping at the song edges exactly as a warp marker does (a press that would overshoot lands on the edge; a press already on the edge does nothing); a held arrow is one undo entry.

**Phase-reset propagation (W view, anchored on a warp-marker selection).** These copy a labeled region's phase-reset layout from one occurrence of a label to another. `Ctrl+P` copies: with one or more warp markers selected, it captures the phase-reset layout of each selected marker's own section into the session clipboard — a marker's section runs to the next enabled marker, the final enabled marker's to the end of the song; the selected markers must form one consecutive run (unlabeled markers inside it simply contribute nothing), and a disabled selected marker contributes no section of its own — but it is not a boundary either: the span under a disabled marker belongs to the preceding enabled marker's section, so the phase resets lying there copy and paste with it (and a paste clears the destination's resets across that span like any other part of the matched range). `Ctrl+Alt+P` pastes: anchored on one selected warp marker, it materializes the clipboard's resets onto the destination region, scaled to the destination's durations, after a confirmation prompt. `Ctrl+Alt+Shift+P` pastes state only: it aligns the enabled/disabled state of the destination region's resets to the clipboard, in order, without moving anything and without a prompt. All three apply a 100 ms tolerance when deciding which block a phase reset belongs to: a reset falling within 100 ms before a block's owning warp marker counts as part of that block rather than the one before it. Copy captures such a reset with the block, and paste reproduces it at the same offset before the destination marker (clamped to the start of the file if that offset would fall before time zero). The tolerance is a fixed value, independent of the engine window size. All three are warp-view gestures and work from either audio view — propagate is the one authoring action that starts in the warp view and ends in the phase-reset target view: on completion it drops you into target view with the phase-reset collection active. `Ctrl+Alt+P`, when it materializes at least one reset, selects exactly those it just created — the first one focused, the playhead on it — so you can inspect the result by eye without an undo round-trip; `Ctrl+Alt+Shift+P` (it only flips flags on existing resets, creating none) and a `Ctrl+Alt+P` run that materializes nothing (an anchor with no eligible destination blocks) instead leave you with nothing selected at all — a paste that created nothing changes nothing — and the playhead resting on the anchoring warp marker's position in the target domain, where the view switch put it. They silently do nothing on an empty clipboard or the wrong selection count.

**Region select and trim.** `Shift`+drag selects a region: the span's background lifts to a lighter shade — the waveform ink itself is unchanged, only the ground behind it recolors — extending live as you drag. It is the one mouse gesture that draws a region, and it works on the waveform's upper half, on the ruler, and on the marker lane's empty stretches alike (on a marker's flag, `Shift`+click is the range select instead — see Marker focus and selection); the waveform's lower half draws no region at all, with or without `Shift`. The region is a temporary selection of what could become the trim window. It selects no markers, launches nothing by itself, and the playhead cursor is drawn straight across it like anywhere else. The press puts the playhead at the click and clears the marker selection; the drag then extends the region from that point with the playhead riding the moving edge — the cursor follows the pointer through the drag and lands where you release — leaving the marker selection empty throughout: a highlight only ever rests with nothing selected. A `Shift` click that never moves simply places the playhead and leaves no highlight, and a released highlight narrower than the drag threshold (a few pixels) dissolves — hand jitter never leaves a sliver window. To audition the span, click inside it on the waveform's lower half (the scrub surface — playback runs from the click to the end of what is playable, once: the song's end in source view, the rendered preview's in target); to commit it, press `x`. The plain drag on those same surfaces is the pan and never touches a highlight, and the plain motionless click places the playhead — which dissolves one (see Zoom and view, Playback and playhead). `Esc` mid-drag does nothing — gestures have no cancel, the release rests what stands. Selecting markers highlights nothing: a `Shift`-range or `Ctrl`-toggle multi-selection shows each member's brightened flag with the cursor standing on the focused one — there is no span highlight for a selection — and deleting selected markers likewise leaves no highlight behind. A highlight rests until something clears it: `Esc` is the direct way (see General — it clears the highlight and touches nothing else), auditions, pans and view-only commands (zoom, paging, the wheel, the plain-drag pan, and `0` short of the full-song view) leave it alone, and everything else — any playhead jump or click, a marker click, an editor open, a marker drop, undo/redo, a view or tab switch, a settings commit, and every trim write, which moves the playhead to the new trim start — dissolves it; `x` consumes it.

Every trim write parks the playhead at the new trim start, and clears any highlight as it goes: bare `x`, the `Ctrl`/`Ctrl+Shift` bound-set clicks, an endcap or bar drag when you release it, `Shift+X`, a typed `trim_begin=`/`trim_end=` for the active tab, and the reset a crossed or coincident pair falls into (which lands the playhead at the song's start, that being the full window's). What you hear next starts there: in target view that is the window you just made, from its start, and in source view it is the song from that point on (source listening is not bounded by the trim window). A press that refuses moves nothing. Bare `x` sets the trim from the highlight: it trims to the span, replacing the existing window, clears the marker selection (`x` is a trim setter, and every trim setter deselects — you are done aiming), and the highlight clears with the commit — the bar and its endcaps show the result. It refuses silently with no highlight, and refuses a span so compressed that both ends land on the same source frame (committing it would produce a zero-length window). The trim window is always set: it starts at the whole song — the begin endcap on the first frame, the end endcap on the last — and every trim state is a position of those two bounds; the bar and its endcaps are always visible in the trim band. A window at the full song renders exactly the untrimmed render, and a narrower one renders its span. `Shift+X` maximizes the window back to the whole song and puts the playhead at frame 0 with it (an already-full press does nothing at all). In the sidecar the four trim keys always carry actual frame numbers. The endcap drag cannot move a bound past its partner: the moving bound stops on the resting one, and releasing it there — the two coincident — resets the pair to the song edges, which makes dragging one handle onto the other the quick way to clear the trim. A pair set equal or crossed by other means (a typed settings value) resets to the song edges the same way at its commit. On the trim bar — the band above the timestamp ruler, drawn half again as tall as its old slim self so the endcaps and the bar are a larger grab target — `Ctrl`+click moves the begin bound to that spot and `Ctrl+Shift`+click the end bound, and holding after the click drags the bound onward like an endcap drag (a click that would land a bound on or past its partner does nothing at all); when the window is wide enough, a small light square outline on the bar marks its midpoint — purely informational, it takes no clicks and disappears only when the bar is too narrow to hold it; a plain click on the band does nothing unless it becomes a drag (the window needs no highlighting — it is always on display); a bound or bar drag deselects markers and stops playback at its first actual bound change, and moves the playhead only once, on release. A plain left-drag on a bound's endcap drags that bound (the thin cap is grabbed with a few pixels of slack on each side), and a plain drag on the bar between them drags the pair as a fixed-width window, preserving the gap during motion (a drag begins after a few pixels of motion; the ruler and marker lane below are not part of the trim grab region — the waveform is for the playhead and region select, never a trim handle). On the waveform between the bounds a plain drag pans the view like anywhere else. Trim bounds never intercept plain or `Shift` presses (a click over a bound is just a waveform click), are not selectable items — no clicking, no `Tab` focus, no `Delete` — and sit outside undo: a trim edit is committed the moment you make it, and no gesture has a cancel. Release snaps each moved bound independently to its painted pixel column, so the stored gap can change by at most one source frame. Only one trim falls back to an untrimmed render, with one stderr line: a window whose rendered span would round below one output sample. Trim is per-tab and excluded from undo and redo.

**Modes (W view).** Both modes author warp tempo, so both belong to the warp view and do nothing at all in phase-reset view. BPM mode is entered from warp's home view — warp view in source audio view — and refuses silently in target. Iteration mode is not view-bound: `i` toggles it in warp view from either audio view, the mode and its brackets survive switching between source and target in both directions, and `Ctrl+Alt+R` renders the sweep from either view. What you cannot do in target view is *type* a bracket — the flag editor is a source-view surface, as it is for every other kind of edit — so a bracket is read and swept there, and authored in source. Exiting iteration mode — by any route — clears every iteration bracket, so a bracket exists only while iteration mode paints it. `m` opens BPM mode on the selected markers' sections as a bottom-strip editor session: `Esc` abandons it (wiping the typed values), `Enter` dispatches the sweep and closes it; while the editor is open, `m` is just a typed character. Iteration and BPM modes are mutually exclusive — entering BPM mode forces iteration mode off (clearing its brackets). Both are front ends for the same workflow: render a spread of variants, audition them in an external player (`l`), and load the one you want in place as the new baseline (`'`; the render commands below cover listening and loading in place). They differ only in what they vary and how the variant is expressed.

Iteration mode varies a marker's base tempo by a small additive offset. With the mode on, a warp marker's flag edit accepts an inline bracket appended after the tempo token, `+[<start>,<end>]` with `start <= end` — for example `+[-0.02,+0.00]`, which enumerates the offsets −0.02, −0.01, and 0.00 (the range is stepped in 0.01 increments, inclusive of both ends; each bound is a signed two-decimal value within `[-4.00, +4.00]`, and the base tempo plus either bound must stay inside the tempo bracket `[0.25, 4.00]` or the commit red-flashes). Several markers can each carry a range; `Ctrl+Alt+R` then renders the full Cartesian product, one file per combination, each marker's offset added in exact cents to its own base tempo for that cell, into a batch folder under `renders/` ready to audition. While iteration mode is on, `Ctrl+Alt+R` means the sweep and nothing else — it is the same render key you already know, aimed at the mode you are in — and the sweep turns the mode off when it fires, which clears the brackets with it. To sweep a marker across a single value rather than a range, give a degenerate range like `+[-0.02,-0.02]` — it is still an iteration cell and still renders with the rest. The sign is mandatory and exactly two decimal places are required on every value, so `+0.00`, not `0` or `0.0`. Brackets are session-only and never serialized: removing the bracket (or committing the all-zero `+[+0.00,+0.00]`) clears the marker's range, and exiting iteration mode clears them all. A tempo change never clears a bracket on its own — the bracket rides the new base tempo instead, its bounds silently narrowing where needed so that the base plus either bound always stays inside the tempo bracket, so no sweep cell can ever leave it.

BPM mode varies the rendered tempo of an explicit span to hit a range of target BPMs. Select one or more consecutive warp markers and press `m`: the first selected marker owns the span, and the span covers each selected marker's own section — a marker's section runs to the next marker, and the final marker in the piece owns the section to the end of the song — so the last selected marker's section is included. Selected markers inside the span may be disabled; each is converted to a pass in every sweep cell, so the span renders at one tempo. None of the markers in or bounding the span may be a `label_ref` — the span's tempo is rewritten on commit and a reference takes its tempo from its definition — and the owning marker may not be disabled, so `m` is a silent no-op in those cases (a selection that is not one consecutive run is also a no-op). The bottom-strip editor is authored as `<beats>@[<lo>,<hi>]` — for example `36@[210,220]`, meaning the span spans 36 beats and should be rendered once at each integer BPM from 210 to 220 inclusive (BPM bounds live in `[10, 400]`). The beat count and the span's measured duration (owner marker to the span end — the next marker after the selection, or the end of the song) fix the source tempo, so each target BPM resolves to a concrete base-tempo-and-scale pair; a target whose derived base tempo would leave the tempo bracket is refused, never clamped. `Enter` renders the sweep — one file per integer BPM in the range — into a batch folder under `renders/`, wipes the typed values, and closes the mode; re-entering always seeds blank. Loading a BPM cell in place (via `'`, by the cell's WAV entry name — the same load-in-place path as any render) rewrites the span's tempo: the entry's frozen sidecars already carry it, so the owner takes the computed base tempo, every span-internal marker (including disabled ones) is set to pass so the span renders at one tempo, the marker after the span (when the span does not run to the song end) is left unchanged, and the computed scale (full double precision) is written to the settings as the global scale. The settings `bpm` field records the render you loaded in place as a descriptor — for example `36 beats @ 220 bpm from 00:32.008 to 00:46.562` — for provenance only; the engine never reads it, though like every engine setting it participates in render identity, so editing it makes the next render fresh.

**Settings.** Bare `;` opens the settings prompt in the bottom strip, where a line is typed as `key=value` — in a writable tab: a read-only tab does not open it at all, from `;` or from the `Settings` menu, since the prompt reaches the engine keys (see View toggles). The prompt accepts any printable character your keyboard produces, accented and other non-ASCII letters included (the free-text values — `title`, `bpm`, `notes`, `url`, `cover`, and `audio_player` — carry them verbatim through the file and back; the keys and the value vocabularies stay plain ASCII, as does a marker label), and the line is split on the first `=`, so the value may itself contain `=` — a `url=` carrying a `?v=` query parameter, for instance, commits intact. The key must be whitespace-free; keys with a restricted vocabulary reject an out-of-vocabulary value at commit with a red flash — the typed value boxed in the same filled red a marker flag turns. Every key that can appear in a `.settings` file is settable here — the engine keys, and every GUI-kind key (`playback_speed`, `follow`, `gui_scale`, `audio_player`, `active_audio_view`, `active_markers_view`, `active_tab_view`, and the per-tab `viewport_start` / `zoom` / `playhead_cursor` / `trim_begin` / `trim_end` / `read_only`). A GUI-kind commit behaves exactly like the key's own gesture: it runs the same code, takes effect immediately, is not undoable, and persists on the next `Ctrl+S`. Values follow the file's strict vocabulary: playback speeds are the ten one-decimal values 0.1–1.0; zoom must be a valid zoom level; trim bounds are whole source-frame numbers inside the audio — a bound committed onto or across its partner resets the pair to the song edges, and the `.settings` file mirrors this, always carrying the four trim lines as actual frames; trim commits like every other per-tab key wherever this prompt opens at all, trim being view state rather than part of the piece — though the prompt itself does not open in a read-only tab, so on a locked tab that means typing `tab_B_trim_begin=` for the OTHER, locked tab from your unlocked one; `gui_scale` is a whole number of percent from 50 to 200 — the interface's rendering scale, applied immediately at commit: the whole interface resizes by it. Keys for the inactive tab write that tab's stored state, picked up when you switch to it. With a key typed and the value left empty (`notes=`), `Tab` fills in that key's current value for recall and editing — this works for every settable key — and leaves a value you have already started typing untouched. `Enter` commits, `Esc` cancels, and `Ctrl+Q` abandons the edit and closes.

Four settings fields are provenance: they are carried in `.settings` and never read by the engine, though like every engine setting they participate in render identity, so editing one makes the next render fresh. (Of the GUI-kind keys, the preference keys — playback speed, follow, GUI scale, the audio player — are not part of render identity and never force a render; the per-tab trim keys are part of the render recipe, and a trim or view-state commit re-previews exactly like its gesture.) `bpm` is written automatically when a BPM-sweep cell is loaded in place (described under Modes above); `url`, `notes`, and `cover` are free-text fields you type through the settings prompt. None of the four is value-validated — any value is accepted verbatim, including empty — though like every settings key the line itself is required (every canonical key is present in every `.settings`; a missing key fails the load). They annotate a render with its source, its target, working notes, or a cover-art reference. Each holds a single line, since the `.settings` format is line-based.

**Render dispatch.** `Ctrl+Alt+R` is the pipeline's destination. In iteration mode it is the iteration sweep (described under Modes above); everywhere else it is a single one-shot render of the current authoring state, written next to the source as a sibling — the WAV deliverable named by the `title` setting (`<title>.wav`); the frame-map pair goes to `~/.cache` as described under Output above. It is the only render that lands beside the source rather than inside a `renders/` batch folder — the final deliverable, as opposed to the audition outputs the other dispatches produce. A render dispatch kills the running render and takes its place; `Esc` stops both the running render and any parked command behind it. (A dispatch identical to the running render simply restarts it — the `.fingerprint` reuse below then makes that restart finish immediately when the deliverable is already current, so an accidental re-press is still cheap.) An output path that resolves to the source audio itself is refused with an error rather than overwritten (change the `title` setting). Before rewriting an existing same-title deliverable, the render checks that output's `.fingerprint` sidecar: if the sidecar exactly matches the current authoring/render inputs and the on-disk WAV identity, the render finishes immediately and writes nothing, because the deliverable has proved it is already current; otherwise the normal render/reuse path publishes the current deliverable through staging and rename. The `.fingerprint` file appears next to deliverable WAVs and records the exact render identity used for reuse: source file identity, markers, phase resets, the full engine settings block — the naming/provenance fields (title, bpm, notes, url, cover) included — and trim bounds. Editing any engine setting, provenance included, makes the next dispatch render fresh; those fields change about once per movement, so the occasional redundant re-render is the accepted price of one simple identity rule. The file is not audio and is safe to delete; deleting it just prevents that output from proving it is already up to date, so a later `Ctrl+Alt+R` may re-render or republish. Do not hand-edit it.

The batch dispatches stage candidates for auditioning rather than producing the final file: the iteration and BPM sweeps are dispatched from their own modes (documented under Modes above) and render into a numbered batch folder under `renders/` (`N_iterations` / `N_bpm`; pressing `Esc` between entries drops the remainder). `Ctrl+Alt+Shift+R` renders one miscellaneous cell (in iteration mode it does nothing at all — the miscellaneous render is a plain-mode act): the exact same render a plain-mode `Ctrl+Alt+R` would produce, but written as the next numbered WAV inside the most recent `N_miscellaneous` folder (a new one is created when the most recent batch folder is not miscellaneous), so one-off keepers accumulate as ordinary `renders/` entries — `l`-auditionable and loadable in place with `'` — instead of overwriting the deliverable beside the source. Pressing it again with unchanged state adds another identical cell (cheaply, via the render cache).

**Auditioning renders (`l`).** There is no in-app render browser; you audition the batch outputs in an external player. `l` ("Listen to renders") launches the program named by the `audio_player` setting with every WAV under `renders/`, in numeric order (batch folder, then entry). Set `audio_player` in the settings editor — `:audio_player=audacious` (a binary name on `$PATH`) or an absolute path — which commits it directly and persists it on the next `Ctrl+S`; `:audio_player=` (empty value) clears it. It is a global launch preference, also loaded from `.settings` at startup. With no `audio_player` set, or no renders present, `l` shows a one-line bottom-strip status and does nothing. The launch is fire-and-forget — the GUI's own playback is unaffected, and closing the external player has no effect on the GUI.

**Loading a render in place (`'`).** `'` opens the `Load: ./renders/` bottom-strip editor: type an entry's name and press `Enter` to load that render in place as the new authoring baseline. An entry is named by its path relative to `renders/`: `<batch-folder>/<basename>.wav` (e.g. `1_iterations/01.wav`), always folder-qualified. `Tab` autocompletes: it extends what you have typed to the longest common prefix of the matching entries, completing fully when only one matches, and does nothing when nothing matches or the common prefix adds nothing. The line red-flashes (and stays open) if the name matches no entry, or if the chosen entry's WAV is missing or a sidecar is malformed. The editor is refused while a render is running or parked (`Esc` cancels the render first), and does not open with no source loaded or an empty `renders/`.

On a successful load-in-place the entry's frozen dispatch-time sidecars are applied to the live state exactly as a fresh source load of those sidecars would be — markers, engine block, recipe trim, both tab bands, the tab letter, the W/P mode, and the session prefs, with nothing carved out — landing in target view on the entry's dispatch tab at the exact position the project had when the render was queued. The load-in-place is one cross-file undo entry (the marker pair plus the outgoing engine settings; the inherited prefs and view state ride outside undo). After it succeeds the `renders/` folder is wiped — the batch outputs are stale once the baseline changes, and the render you loaded in place survives through the render cache, not as a folder artifact. The folder is moved to the desktop trash when `gio trash` is available, so a batch you did not mean to lose can be restored from there in one piece; where the trash cannot take it — no `gio`, or a filesystem it will not trash from — the folder is deleted outright instead, with one stderr line saying so. Nothing else the program removes goes to the trash. Regular renders, iteration cells, and BPM-sweep cells all load in place through this same path — for a BPM-sweep cell the frozen sidecars already carry the rewritten span markers, global scale, and `bpm` descriptor, so those arrive as part of the same full snapshot.

**Checking history (`h`).** The project's working checkpoints live in a git repository — the `projects_repo` setting names which one, and the program reads the local clone it was built from, so nothing here needs a network or a credential. Bare `h` opens the history view: the marker lane stops showing the session's markers and instead shows the difference between a committed checkpoint of this piece and something else. Two things choose what that comparison is: WHICH HISTORY you are reading, and HOW. The tabs at the top of the window choose the history for as long as the view stands — while it is open they stop being the `A`/`B` tabs and read `Remote` and `Local`, the lit one naming the walk on screen, and clicking the other switches to it (`Ctrl+Tab` does the same from the keyboard, instead of switching tabs; `Ctrl+Shift+Tab` is the same step back, which with two tabs comes to the same thing). `Remote` reads the committed checkpoints; `Local` reads your own session instead, and is described a little further down. HOW they are read is the `Cumulative` button in the icon row, immediately right of the history button, or its key, `U`. Off — the way the program starts — is the ITERATIVE reading; on is the CUMULATIVE one, and the button lights while it is on. Unlike the tab, THIS ONE IS REMEMBERED: leave the view and come back and you are reading the same way, until the program closes. The button shows the setting even when the view is shut, greyed out, because the key only works inside the view — a lit but greyed button means "cumulative, next time you look". The iterative reading, which is where a fresh program starts, looks FORWARD: it compares the checkpoint you are looking at against the next one along toward the present — the checkpoint after it, or, at the newest checkpoint, what is authored in memory right now. It answers what happened after this checkpoint, one step at a time. The cumulative reading always compares against what is authored in memory right now, however far back you have stepped: it answers how your session differs from that checkpoint. In both readings green is the newer side and red the older, so the colours say one thing throughout — green flags are markers the newer side has that the older did not, red flags are markers the older side had that the newer dropped, and a marker present in both at the same frame with a different value is one double-width flag, red half then green half, the old value on the left. At the newest member the two readings are the same thing — both compare it against your session — so pressing `U` there changes only whether the button is lit. That is also why a project you have just loaded and not yet touched shows an empty lane in both: your session and the newest checkpoint agree, which is exactly what you want to see after committing. Warp flags carry the tempo value in the sidecar's own spelling (`[+]1.05`, the `#` prefix appearing when that side is disabled); phase resets carry the bare sign, their position being their whole identity. The `Local` tab reads the same kind of difference over a different history: your own session, counted as STATES rather than as actions. Every state you can reach with `Ctrl+Z` and `Ctrl+Shift+Z` is a stop on that walk, and so is the one you are standing in — so a file you have just opened and not touched reads `1/1`, one state compared against itself, and set a marker, move it, then `Ctrl+Z`, and it reads `2/3`: three states, and you are on the middle one. The view opens where your session is, so `,` steps back through what you have done and `.` steps forward — into states you have undone, when there are any, exactly the ones `Ctrl+Shift+Z` would redo. The iterative reading shows what one step did: each pair of neighbouring stops brackets a single edit, drawn as the flags it added, removed or changed — on the state you are standing in that is what the next redo would apply, one step back it is what `Ctrl+Z` would take away. The cumulative reading shows everything between that state and where you are now, which is what going there would give you; on the state you are standing in the lane is blank in both readings, since both sides are the same state. Green is the newer side throughout here too, undone states included. Nothing here touches git, and nothing is written: it is a way of reading what you have been doing. A step that changed nothing any file would carry — turning iteration brackets on or off, say — shows an empty lane, honestly, because there is nothing in it to show. Everything else in the view works the same way on this tab — the walk keys, both readings, the flag selection, `Tab`, `c`, the trim bar's span and its double-click, and `Ctrl+H` to put a difference back, which on a local reading means undoing part of one step and keeping the rest. `'` works here too, with a different question: the editor opens with the number of the state you are looking at, and any state's number in `1..N` is accepted (anything else flashes red). `Enter` applies that state's markers and engine settings on top of what you have now, as one more undoable step — it is not a rewind, so `Ctrl+Z` immediately after brings back what you left, which is what makes walking to the very first state and loading it a safe way to audition where you started. It carries only what an undo step carries: no trim, no tab settings, no preferences, and nothing is written to disk. The view closes as it loads, as it does for a checkpoint. One thing is the commit side's alone and says so: there is no commit id in the corner, a state of your own session having no name. `Save and Commit` is unaffected — it always commits your live state against the newest committed checkpoint, whichever tab you are on and whichever way you are reading. Each of the two histories remembers where you left it, so you can look at your last edit and go back to the checkpoint you were studying. The view opens on the newest checkpoint (on the `Local` tab, on the state your session is standing in); `,` steps to an older one and `.` back toward the newest, and holding either key down walks steadily in that direction. `Shift+,` and `Shift+.` go the whole way at once — to the oldest checkpoint and to the newest — for when you want the two ends rather than the steps between them. The two arrow buttons beside the history button in the icon row are those keys — they come alive when the view opens and are greyed out and pointer-dead the rest of the time (their tooltips still work, so you can read what they are for from outside) — so the walk can be driven with the mouse alone, `Shift`+click making the same jump the shifted key does. At either end of the walk the step simply does nothing, by key or by click, and so does a jump to the end you are already standing on; the arrows do not grey out there, since the corner readout already says where in the walk you are. It opens zoomed all the way out, with the whole song in the window — where the differences sit in the piece is part of what you are reading, which is why the whole song is the starting point. After that the view is yours: panning and zooming stay exactly where you leave them across every `,` and `.` and every switch of tab or reading, so you can settle on a passage and compare one stop against the next at the magnification you chose. Leaving the view puts back the pan, zoom and playhead you had before you opened it. The trim bar above the ruler marks the span they cover, its two handles on the first and last difference, for as long as the view is open — and double-clicking anywhere on that bar zooms to exactly that span, which is how you go from the overview to the changes and back. It is the same double-click that frames a span outside the view, on the same bar, with the differences as its span; a single click there does nothing, and the pointer keeps its plain arrow over the bar, the trim shapes being gone for the duration along with the trim gestures. A checkpoint with nothing to show gives the bar the whole window and the double-click nothing to do. Your own view of the piece is not disturbed by any of this: the pan, the zoom and the playhead you had when you pressed `h` come back when you leave, whatever the view did with them in between. (Your trim window is untouched throughout — the bar is only borrowed for the display, and it is display and nothing else, the view having nothing to play.) Only checkpoints the program could actually load are shown: one that would refuse the load in place — an incomplete set of the three sidecar files, or files predating the current format — is left out of the walk entirely, and the terminal notes how many were hidden. If that leaves nothing at all — a piece with checkpoints in the repository of which not one still loads, typically because they all predate a change to the settings file — the view still opens, on an empty walk: the corner reads `0/0`, the lane is blank, the walk keys and `'` have nothing to act on, and the terminal line says how many were hidden. `Save and Commit` is live there, and is how the walk gets a member again: commit once and the next `h` reads it. That is deliberate — a change to the file format empties every piece's walk at once, and the act that repairs it lives only in this view. A piece that has never been checkpointed at all opens the same way, at `0/0` with nothing behind it, and its first `Save and Commit` starts the history — nothing about that first checkpoint is done outside the program. WHERE IT GOES IS THE FOLDER THE PIECE IS IN, and that is the whole rule: make `projects/550 - 4/` yourself, keep the source inside it as the existing pieces are kept, and the checkpoints go there under the name you chose. A source that is not in a folder under `projects/` — one kept elsewhere on the disk, or dropped loose in `projects/` itself rather than in a folder of its own — has no history to read and no place to write one, so `h` says so and does nothing; the fix is to move the file into a folder, not to do anything in a terminal. Loading and editing such a file is unaffected: only the history view minds where it lives. Moving or renaming a folder later costs nothing, incidentally — the history is found by the file's name rather than by the folder's, and each checkpoint is read in the folder it was actually written from, so a piece keeps its whole past across any number of renames — move the folder in a file manager, as you would anything else, and the next checkpoint simply goes to the new place. (Renaming it with `git mv` in a terminal is the one way to confuse this: that commit changes two folders at once and is left out of the walk, with the terminal saying so.) The other side of that: if you keep a COPY of a piece in a second folder and checkpoint from there too, both sets of checkpoints are one history and appear interleaved in the walk, each showing the folder it came from. Nothing stops you, and nothing is lost — but it is one piece's history as far as the view is concerned. `h` also refuses when it could not read the history at all — git failing to run, say — rather than showing you an empty one; that reason goes to the terminal too, and is fixed there. If that happens while the view is already open, on a long history still being read in the background, the view closes itself and says so on the terminal, since it can no longer show you what it opened to show. The walk is the piece's whole history, however long it has been going, and the program reads it in the background from the moment it starts — so `h` opens at once, and on a long history the older checkpoints keep arriving for a second or two after it does. You can start reading the newest ones immediately; the count in the corner grows as the rest land, and stepping past the oldest one you have yet simply does nothing until it turns up. Committing a new checkpoint refreshes the reading, so the next `h` sees it. The bottom-left corner names where you are — position in the walk, and on the two commit readings the commit's short id — and, only when the checkpoint's `scale` setting differs, its two values old and new (`Scale: [-]100 [+]125`); a scale that did not change is not mentioned at all. The view is read-only, and now literally so: authoring, undo, rendering, the menus and the editors are all inert while it stands, while panning and zooming work as ever, so you can look around a difference before deciding what to make of it. Switching audio or marker views in here — which you will, since a difference is line-shaped and each view shows one column of it — changes nothing in your work either; that switch used to clear any iteration brackets you were carrying, and since iteration mode stopped being tied to source view it does not. The view is also silent: it plays nothing at all. `Space` does nothing in here, neither mouse button scrubs, and a session already playing when you press `h` stops as the view opens — an audition of the piece is what the editor is for, and it costs a full render of the whole song from in here, since the view ignores your trim window. The buttons say so: everything that cannot act while the view is open — undo, redo, `Render`, copy and paste, the BPM editor, iteration mode, follow, listen, and the `Settings` menu — greys out and ignores the pointer, and the ones that stay lit are exactly the ones that still work, the two walk arrows among them. `Navigation` is the one menu that stays live in here: zooming and centring are exactly what you want while reading a difference, so it opens as usual and its rows work, with the single exception of `Walk both tabs`, which greys out because that key is the history switch while the view stands rather than the walk the row names. `Settings` is shut because its rows would open the settings editor, which has no place in a view that changes nothing. The tabs are the one part of the window that changes job rather than going dead: they are the history switch described above, so their padlocks are gone for the duration (`Ctrl+Tab` and `Ctrl+Shift+Tab` step between `Remote` and `Local` rather than switching or marching tabs, and the `o` key is inert in here as it always was). `Esc` keeps its ordinary jobs in here: it cancels a render started before the view opened and clears a highlight — one left over from before, or one you drew in the view — without leaving the view — `h` leaves it, and so does the commit act below, as soon as its save lands. A click on a diff flag brightens it and lands the playhead there — on the flag itself, in the marker lane; the line dropping from it into the waveform is a visual cue only, like every marker stem. Anywhere else, the waveform — either half, the halves being alike in here since there is no scrub to divide them — the ruler and the marker lane's empty stretches answer exactly as they do outside the view: a plain click that never becomes a drag moves the playhead to that spot at the release and drops the brightened flag as it goes, a plain drag pans, `Ctrl`+drag zooms, and `Shift`+drag highlights a stretch, the playhead riding the moving edge. A modifier held over the waveform names a view gesture, never a selection, in here exactly as outside. The highlight is a reading mark here rather than a trim you are aiming: `x` is inert in the view, and the highlight is local to it — clicking a diff flag clears it, exactly as any click that moves the playhead does outside, and stepping to another checkpoint, switching the reading, and leaving all clear it too, so a highlight never outlives the difference you drew it against and never follows you back to the editor. `Esc` clears it too. The marker selection you left behind when you opened the view is untouched by any of this. `Tab` and `Shift+Tab` walk the diff flags the same way they walk markers outside the view — each step brightens the next flag along, lands the playhead on it and recentres at the zoom you are already at, with `Tab` from nowhere starting at the first flag and `Shift+Tab` at the last; there is no wrap at either end, and with no differences to show they do nothing. `c` re-centres on the brightened flag at the working zoom, or on the playhead if none is brightened. `Home` and `End` jump to the very start and the very end of the song here — not to the trim bounds they jump to outside the view, since the view is about the whole piece — and they drop the brightened flag as they go. `'` inside the view opens the load editor prefilled with the viewed member: on the `Remote` tab that is the checkpoint's commit id, and pressing `Enter` loads that checkpoint's whole sidecar state in place into memory — the same in-memory load-in-place a render entry takes, one undo entry, nothing written to disk — and any commit id the repository can resolve may be typed or pasted in its place. A commit that lacks the piece's sidecars, or predates the current file format, refuses with a red flash and changes nothing. (On the `Local` tab the same key asks for a state number instead — see the `Local` tab above.) Differences can also be selected and put back. A plain click on a flag brightens that one and drops any other selection; `Shift`+click selects everything between the brightened flag and the one you click, and `Ctrl`+click adds or removes a single flag from the selection — on the flag itself, in the marker lane, that being where selecting is done in either view; every selected flag is brightened. Over the waveform those two modifiers keep their usual jobs (`Ctrl` the zoom-and-pan drag, `Shift` the region former), and a stem answers nothing anywhere. Stepping to another checkpoint, switching the reading or the view, `Home`, `End`, `Tab` and a click anywhere else all drop the selection again, so it never outlives what it points at. `Ctrl+H` — the revert button in the icon row — then applies those differences BACKWARDS into your session and closes the view: a green flag's marker is deleted, a red flag's marker is put back exactly as the checkpoint had it, and a two-colour flag's marker is set back to the checkpoint's value. With nothing selected it acts on the brightened flag alone, and with nothing brightened either the key does nothing and the button is greyed out. It is deliberately unguarded: nothing checks that the flags you picked make sense together, so you can quite easily build a state that is neither the checkpoint's nor the one you started with — reverting half of a change is exactly as possible as reverting all of it, and that freedom is the point. The whole act is one undo step, so `Ctrl+Z` takes it all back. Nothing is written to disk; a read-only tab refuses it, since it rewrites the piece's own markers — that lock stops the revert and `'`, but not `Save and Commit`, which only writes out and publishes what is already there. `h` closes the view.

The view can also publish. `Ctrl+S` inside it — the `Save` button, which reads `Save and Commit` while the view is open — saves and then commits the current authored state as a new checkpoint. That is the only thing `Ctrl+S` does in here: the plain save has no key of its own while the view is open, which matters only in the one case the button greys out for, and leaving the view with `h` gives it back. It asks one thing first, and it is worth answering: a one-line editor opens at the bottom of the window with the commit message already filled in (`Update <folder name>`, the piece's folder), selected so that typing replaces it. `Enter` commits under whatever it holds, so the ordinary case is a single keystroke and the useful case is writing what you actually changed; `Esc` abandons and nothing happens. An empty message flashes red and waits — a checkpoint has to be called something. Then the program performs an ordinary `Ctrl+S` save, exactly as pressing it would (so the checkpoint is always what you have saved, and the unsaved-changes dot clears with it), and the view closes. If the save itself fails — a disk error, a full disk — the act stops there: it says so, nothing is committed or pushed, and the view stays exactly as it was so you can fix the reason and press again. Everything after the save happens in the background: writing the three sidecar files into the piece's `projects/` folder, committing them under your message, and pushing. You keep working while that runs — the window does not wait on the network. If any of it fails, a short red message appears at the LEFT END OF THE BOTTOM ROW and STAYS there — nothing committed, the files written but not committed, committed but not pushed, or simply not confirmed. There is nothing to dismiss and no key to press: it is not a prompt, it takes nothing away from what you are doing, and it does not go away by being noticed. It stays for the rest of the session unless a later `Save and Commit` comes back with the repository in order — either it published a new checkpoint, or it found nothing to commit and the branch already in step with the remote — which is what clears it. The failure is about the repository, and a newer answer replaces the old one. Everything else on that row moves right to make space for it, and the terminal carries the long version. The piece itself is saved in every one of those cases. THE FIX IS IN THE TERMINAL, deliberately: a checkpoint that committed but did not reach the remote is published with `git push` where you have git, and the next `Save and Commit` sees it and takes the message down — the program does not retry the push for you, and it does not offer a button that would. The same is true of a commit that git reported as failing while in fact landing (a slow hook can do that): the terminal shows what really happened. If a checkpoint that succeeded has nothing more to say it says nothing. The push uses the machine's own git identity and SSH setup, exactly as committing from a terminal would. Only one checkpoint publishes at a time: while one is still running the `Save` button reads `Committing...` and is greyed out — wherever you are, not just in the view — `Ctrl+S` does nothing, and `h` will not open the history view either, since the view would be reading a repository that is being written to. Saving is deliberately held for those moments: the program is writing the same three files out to the repository just then, and two writers on one file is how files get damaged. It takes a moment and comes back by itself; quitting waits for it rather than abandoning it. (If you edit something during those moments and then quit, the unsaved-changes prompt's `[S]ave` reports `Save failed.` for the same reason — pressing `[R]etry` once the checkpoint has landed saves normally.) The button also tells you in advance whether there is anything to commit: while the view is open it greys out whenever the session's markers and `scale` already match the newest checkpoint, and `Ctrl+S` does nothing then. On an empty walk there is no checkpoint to match, so the button is lit — there is by definition everything to commit — though it waits, greyed, for the moment or two the program takes to finish reading the history and be sure the walk really is empty. That answer covers the whole piece rather than the half you are looking at, so there is no need to switch views to check both. Only authored content counts — the view state the program also records in the settings file is not a change worth a checkpoint — so if that is all that has changed, leave the view and save to disk as usual. The checkpoints the program reads and writes live under the repository's `projects/` folder — one folder per piece, the three sidecar files named by the source's base name — so another repository works by carrying the same shape.

Moving the projects home to another git host takes two steps and nothing else: point the clone at the new remote (`git remote set-url origin <new url>`) and edit the `projects_repo` setting to match it. The program speaks only to local git and to whatever that remote turns out to be — there is no GitHub dependency anywhere in it, no account, no token, no service to sign up for.

**General.** `Ctrl+Z` undoes and `Ctrl+Shift+Z` redoes; settings edits and marker edits participate in the same undo history. Undo and redo show you what changed. The touched markers are re-selected (an undone insertion has no surviving marker, so that case clears the selection instead), and if the edit belongs to the other tab the view switches to that tab first. A single touched marker gets the full marker-click treatment: the playhead lands on it (any resting highlight clears — undo and redo start you from a clean span state), the viewport recenters only if it is offscreen, and its flag brightens — the ordinary single-selection cue, staying for as long as that marker is the one selected marker. A change that touched several markers re-selects the group — each member's flag brightens, the cursor standing on the earliest member where the playhead lands — scrolling into view whenever part of the group sits offscreen, zooming out only when the group cannot fit at the current zoom. Trim changes are excluded from undo and redo. Held nudges and tempo steps coalesce: holding the key down (`Left`/`Right` marker nudges, or `Up`/`Down` tempo steps, group steps included) collapses the whole held run into one undo entry, so a single `Ctrl+Z` reverts it — and rapid separate taps of the same key merge the same way when they land within about half a second of each other with the same markers selected in the same tab; a slower press, a press after the selection changed, or a press that refuses (a nudge already at the song edge, say) opens its own entry.

**`Esc` does exactly five things**, and nothing else anywhere: it closes an open editor without committing, it dismisses a prompt, taking its rightmost response, it dismisses an open dropdown (either menu), it clears a resting region highlight (and a visible highlight absorbs the press, so cancelling render work while one rests takes two presses), and it cancels all render work in one press — the running render, a parked render command waiting behind it, and a pending target-view preview. An open editor or a prompt takes priority, so the first `Esc` closes that and the next one cancels render work. While a pointer gesture is in flight `Esc` is swallowed and does nothing: gestures have no cancel — let go and the gesture commits what stands, then `Ctrl+Z` takes it back (trim, which sits outside undo, commits for good). With nothing open, nothing rendering, no highlight resting and nothing being dragged, `Esc` is simply a no-op: it does not deselect markers and does not move the playhead. To leave a selection, click the waveform or press `Home`/`End`; to clear a highlight, press `Esc` — or do anything that moves the playhead to a point, or consume it with `x`.

**Mouse.** One rule organizes the pointer: the waveform's upper half, the ruler, and the marker lane's empty stretches are a single navigation surface, and every plain or modified gesture means the same thing anywhere on it. A plain drag pans the view — a smooth grab, capturing the cursor for unlimited travel once the drag is under way. A plain click that never becomes a drag places the playhead at the clicked spot the moment you release, clearing the marker selection and any highlight (nothing happens at the press itself, so a click never pops anything while you decide, and a pan moves nothing but the view). `Shift`+drag selects a region and `Ctrl`+drag zooms and pans, both axes at once (see Region select and trim, Zoom and view); there is no `Alt` and no `Ctrl+Alt` pointer or wheel gesture, and the right button does nothing at all. The waveform's lower half is the exception surface: a plain click there scrubs playback at the press — it stops a running session, and on a stopped one the scanner starts there, one-shot per click, the resting playhead staying put (see Playback and playhead) — and it takes no pan, no region, and no placement (`Ctrl`+drag still zooms from there). The scroll wheel pans — a tenth of a screen per detent, over the waveform and the whole marker strip alike — but not over the four button rows at the very top (menu, toolbar, tabs, icon row) or the bottom toolbar, where the wheel does nothing at all; the wheel does not zoom. The buttons themselves are covered under The top rows; the rest of those rows does nothing. The pointer tells you what a press would do, using your own cursor theme's cursors and no artwork of ours: a hand anywhere on the navigation surface (the pan — a still click needs no cursor of its own), a crosshair on the waveform's lower half (the scrub — the audition starts at the column under the crosshair's centre), a magnifier with `Ctrl` held anywhere the zoom drag works, and on the trim bar three shapes for three different acts — a left-edge arrow on the begin endcap, a right-edge arrow on the end endcap (each drags that one bound), and the left-right resize arrow on the bar between them (which drags both together). `Ctrl` and `Ctrl+Shift` over the trim bar show the same two edge arrows, matched to the bound each one sets. Everywhere else — the marker flags, the button rows, the trim bar's bare ground — it is the ordinary arrow, and so it is wherever the gesture would not run: while a menu or a bottom-strip editor is open, while any drag other than a trim drag is in progress, with `Shift` held (the region former shows no cursor of its own), and on a `Ctrl` or `Ctrl+Shift` trim click that would land on or past the other bound, which does nothing. If your cursor theme is missing one of these, that one shape falls back to the arrow and everything still works. The cue changes the instant you press or release `Ctrl`, without moving the mouse; other changes with no mouse movement under them — a file finishing loading, a menu closing with `Esc` — show up the moment you move the mouse next. While you drag a trim endcap or the bar between them, the pointer keeps the shape it started with — the matching edge arrow or the resize arrow — for the whole drag, wherever the pointer goes. During any other drag the cursor is the plain arrow, or hidden entirely for the pan and the zoom drag, which capture it so the gesture can travel without limit. When one of those two ends, the pointer comes back with the shape it had when the capture began — the hand or the magnifier — and if you released `Ctrl` before the button, the shape catches up the moment you move the mouse next. A click on a marker's flag — the flag is the marker's one clickable part; its stem on the waveform is a visual cue only, and no click or drag can land on it — selects that marker and seats the playhead on it at the press, and dragging the flag moves that one marker with the playhead following, whether or not others were selected (marker work keeps its immediacy: flag clicks act at press time, unlike the navigation surface's deferred click); double-clicking the flag opens the flag editor; `Shift`+clicking range-selects from the focused marker and `Ctrl`+clicking toggles membership, both seating the playhead on the marker they leave focused (see Marker focus and selection). `Tab`/`Shift+Tab` and `c` also bring the playhead to a marker, recentering the view as they do; a nudge or flag drag carries the playhead along with the focused marker, and dropping a new marker with `s` or the empty-lane double-click seats the playhead on it as part of the drop, clearing a resting highlight like any other way of putting the playhead somewhere. Double-clicking inside any text editor selects the run under the click, the standard desktop way: a word (underscore counts as part of it), a run of punctuation (a `.`, `=`, or `::` selects just that), or a run of spaces — the selection never crosses from one kind into another. Trim bounds are dragged by their begin/end endcaps and the bar between them, plain like everything else — a drag begins after a few pixels of motion; the begin endcap sits with its left edge on the bound and the end endcap with its right edge, so both are fully visible even at the very start and end of the file. The marker drag and the double-click-to-edit refuse — the flag click still selects — both in a read-only tab and when the marker collection is away from its home audio view (a warp marker in target view, a phase reset in source view; see View axes): a flag press off its home view selects the marker, seats the playhead, and arms nothing at all. The trim drags work in a read-only tab: trim is view state, not part of the piece. The `e` key IS the left mouse button: pressing it presses the button at the pointer position, holding it holds the button (so `e`+motion drags, and modifier state rides along exactly as for a physical button), and releasing it releases the button — except while a text editor is open, when `e` types the letter as normal. The press acts only while the pointer is over the window.

**Touch.** On a touchscreen, one finger is the mouse — a tap is a left click at the moment the finger lifts, and every gesture, refusal, and rule in the sections above applies unchanged; the program does not distinguish the two devices. On the navigation surface — the waveform's upper half plus the ruler and the marker lane's empty stretches, the same surface the mouse's plain drag pans — a one-finger drag pans the view directly, the way it does on a phone; a tap places the playhead at the tap point; hold a finger still for about half a second and then drag, and you sweep a region instead — the mouse's `Shift`+drag by another route, the playhead riding the moving end and landing where the finger lifts (a hold released without moving just places the playhead); and a double-tap on an empty stretch of the marker lane creates a marker there, selects it, and lands the playhead on it, exactly as the mouse's double-click does. Zooming on a touchscreen is the two-finger pinch and nothing else. Off that surface a finger behaves as the left button everywhere: a tap on a marker's flag selects it, a drag from a flag moves that marker, a drag between the trim bar's endcaps moves the whole trim window, a drag from an endcap extends that bound, a double-tap on the trim bar frames the span, a press in the waveform's lower half scrubs — that half is reserved for scrubbing — and a brief press-and-hold there is the held button for every other press-and-hold gesture. Two fingers navigate: moving them pans the view, and spreading or pinching them zooms about the point between them, the same pan-and-zoom the `Ctrl`+drag performs — a second finger added mid-pan joins it seamlessly, and a second finger added to a held (not yet dragged) finger does too. Nothing else is bound to touch.
