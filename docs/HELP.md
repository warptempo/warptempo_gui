# warptempo_gui

warptempo_gui time-warps an audio recording toward the tempos you choose — built for taking a commercial orchestral recording to a historically informed tempo reading, phrase by phrase, by ear. This is the user guide: install and build, first run, the conceptual model and the output contract, and the interface reference. Read the conceptual model before the reference; the reference is where every key and gesture lives.

One habit the program is built around: when a key or a click refuses, the program normally says why, in a small card at the top right of the window. What stays silent is a chord with no command behind it, and a **one-dimensional command already at its state** — one that moves a single thing in a single place, so one glance at that place already tells you nothing happened. The playhead already at the end it would jump to, a walk already at its last marker or its last checkpoint, a ladder step already at its limit, a tempo already at the bracket's edge, the selector for the view you are already in, a click on the radio button already selected: all silent. A command whose effect would have spread across the screen still says why even with nothing to do — undo and redo over an empty stack, a tempo step over a selection one marker cannot take. So silence with no visible change means the press was either unbound or had nothing left to change in the one place you were watching. The manual therefore does not list every state in which every command refuses — the program tells you, at the moment it matters. What the manual gives you instead is what each thing is *for*, how it works, and the refusal sentences worth knowing in advance.

## Dependencies

Build requires a C++23 toolchain (GCC 12+ or Clang 16+), CMake 3.20+, pkg-config, and the development headers for fftw3. That is the complete dependency set for the headless render interface (`warptempo_cli`); none of the GUI packages below are needed for it.

The default GUI build — the Linux desktop product, and what the rest of this guide describes — additionally requires the wayland-scanner tool and the development headers for cairo, wayland-client, wayland-cursor, wayland-protocols, libxkbcommon, and JACK. JACK can be the native jackd2 server or a PipeWire-shimmed JACK provider (modern distros default to the latter).

The `std::expected`-based parser is what pins the compiler floor at GCC 12 / Clang 16. On distributions whose default compiler is older — Ubuntu 22.04 ships GCC 11, for example — install a newer toolchain (`g++-12` or later) and select it with `-DCMAKE_CXX_COMPILER=g++-12`.

Arch Linux:

```bash
sudo pacman -S base-devel cmake pkgconf \
    cairo fftw \
    wayland wayland-protocols libxkbcommon \
    pipewire-jack
```

Debian / Ubuntu:

```bash
sudo apt install build-essential cmake pkg-config \
    libcairo2-dev libfftw3-dev \
    libwayland-dev wayland-protocols libxkbcommon-dev \
    libjack-jackd2-dev
```

The libwayland-dev package on Debian ships wayland-scanner and the client / cursor headers in one piece.

Fedora:

```bash
sudo dnf install gcc gcc-c++ cmake pkgconf-pkg-config \
    cairo-devel fftw-devel \
    wayland-devel wayland-protocols-devel libxkbcommon-devel \
    pipewire-jack-audio-connection-kit-devel
```

For a headless build — `warptempo_cli` with no GUI — only the core dependencies are needed. Omit the cairo / wayland / libxkbcommon / JACK packages and configure with `-DWARPTEMPO_BUILD_GUI=OFF` (see Build). On Debian / Ubuntu that reduces to:

```bash
sudo apt install build-essential cmake pkg-config \
    libfftw3-dev
```

A Wayland compositor is required at runtime for the desktop build — there is no X11 backend — and it must offer server-side window decorations (the xdg-decoration protocol): the GUI exits with an error at startup if the compositor does not offer it. labwc, the compositor the program is developed on, always can; so can the other wlroots-based compositors (sway, Hyprland) and KDE Plasma. GNOME's compositor does not implement the protocol, so the GUI will not start there. The headless CLI needs no compositor and no audio server; it reads and writes files only.

Windows (WSL2): the project builds and runs under WSL2 with a Debian or Ubuntu userland — install the Debian / Ubuntu dependencies above inside the WSL distribution and build normally. The headless CLI behaves as on any Linux host. The GUI is not supported under WSL: WSLg provides a Wayland compositor but routes audio through PulseAudio, and the application has no non-JACK audio path.

macOS is not supported: the GUI has a Wayland backend and an Android one, and no macOS backend at all. The headless CLI is neither built nor tested there and carries no support claim either.

## Build

Standard out-of-tree CMake build from the repository root:

```bash
cmake -B build -S .
cmake --build build -j$(nproc)
```

The default build produces one binary: the `warptempo_gui` application — a Cairo/Wayland front end over the in-tree parser, engine, prepost, and audio-io sources. All audio container I/O is in-tree, WAV only, with no third-party codec. There are no library archives; each binary compiles the shared source lists directly. `-O3 -march=native -ffp-contract=off` is always on for GCC and Clang, so every binary is tuned for the host CPU and is not portable across machines — rebuild on the target host. A rebuilt binary is not a new rendering reference, though: with the same compiler and the same libraries underneath it, a fresh build renders exactly what the previous one did, byte for byte (see Reproducibility).

One opt-in binary, default OFF: `warptempo_cli` (`-DWARPTEMPO_BUILD_CLI=ON`) is the headless insurance render path — exactly the terminal `Ctrl+Alt+R`. It takes just the source audio path, reads the project's `.warpmarkers`, `.phaseresetmarkers`, and `.settings` beside it (all three required; the GUI creates them on source load), and writes the warped WAV the GUI would render for the same project — `<title>.wav` in the project's own `render/` folder, exactly where the GUI publishes its deliverable (the folder is created for you the first time, as it is in the GUI) — byte-identical to the GUI by shared pipeline stages. The trim applied is the active tab's (the persisted `active_tab_view` key), matching the GUI. Like the GUI, it also drops the render's frame-map pair into `~/.cache/warptempo_gui/<pid>/` (see Output and the limiter).

To build the CLI on a headless host that has none of the GUI's Wayland / Cairo / JACK packages, add `-DWARPTEMPO_BUILD_GUI=OFF -DWARPTEMPO_BUILD_CLI=ON`; the GUI dependency discovery is skipped entirely.

**Android.** The same GUI also builds as an Android APK — one interface over two backends, not a second program. `bash android/app/build_apk.sh` cross-compiles it against the static dependencies in `android/prebuilt/` and packages a signed APK; `adb install -r android/app/build-android/warptempo.apk` puts it on the device. That build needs the Android SDK and NDK, installed outside the repository as `android/toolchain/` expects. Nothing of Wayland or JACK is involved there: the window comes from the Android framework and the audio from AAudio. Everything this guide says about the interface holds on both, and where a gesture or a behaviour differs the text says so.

There is no `make install` target. The binary is self-contained: copy it anywhere on `$PATH` to make it available system-wide.

```bash
install -Dm755 build/warptempo_gui ~/.local/bin/warptempo_gui
```

A `.desktop` file is shipped in `packaging/warptempo_gui.desktop`. To register the program with the system's application launcher and as a handler for audio files:

```bash
install -Dm644 packaging/warptempo_gui.desktop \
    ~/.local/share/applications/warptempo_gui.desktop
update-desktop-database ~/.local/share/applications
```

The shipped `.desktop` file uses the freedesktop `audio-x-generic` icon name, which resolves to whatever the active icon theme provides — no icon file is bundled. Replace the `Icon=` line with a different freedesktop name or an absolute path to a custom SVG to override.

## First run

`warptempo_gui` takes no argument, or one.

With no argument, it opens the project it had open last — the device config's `last_project` — or, when that name is empty or its folder is gone or is not a project by the folder rules below, the first valid project folder under `projects_path` in name order (what is judged is the folder's SHAPE and its name, never what is written inside a sidecar — a folder that looks like a project and holds a broken sidecar is still the one chosen, and the load then refuses with that file's own reason); with no valid project at all, it refuses on stderr (`No project under <projects_path>`) and exits. This is the tablet's only road in, and the laptop's own bare launch.

With one argument, the argument must be a project's source `.wav` — a file inside a project folder that sits directly under `projects_path`, resolving as that folder's source; anything else refuses with the reason on stderr.

```bash
warptempo_gui "path/to/source.wav"
```

**The project folder model.** `projects_path` is a per-device setting (below) whose subfolders are the projects, one folder per project; the folder's name is the project's name. A folder is a project one of two ways: it carries a sidecar set — any of `<stem>.warpmarkers`, `<stem>.phaseresetmarkers`, `<stem>.settings` — naming its source by that shared stem, and `<stem>.wav` exists beside them; or it carries no sidecar at all and holds exactly one `.wav`, which makes it a new project — that wav is the source, and the first open writes the sidecar template beside it. Any other shape refuses to open with the reason stated. A `.wav` in the project root that is not the source is a leftover — the refusal names it and tells you to move it into `render/`. A folder's name also has to be one the program can remember: the name of every opened project is written into the config's `last_project=` line, which holds one plain folder name — so a folder called `.` or `..`, one whose name begins or ends with any ASCII whitespace byte — space, tab, newline, vertical tab, form feed or carriage return — or one containing a line break is not a project on any road. Rename the folder and it is a project again.

Two folders beside the source hold everything the program writes, and neither is itself a project or a candidate source:

- `render/` holds the deliverable — `<title>.wav` and its `.fingerprint`, written by the render command (`Ctrl+Alt+R`; the CLI writes to the same place) — and nothing else: the folder is kept to the current `title` setting's one pair, and any other `.wav` or `.fingerprint` in there is deleted the next time a render publishes into it, so renaming the piece does not leave the old deliverable lying around. A render that *fails* clears the pair instead of publishing one, so an empty `render/` after a failure is the expected state.
- `tmp/` holds the disposable batch renders — the grid and BPM iterations and the miscellaneous cells — that the render player (bare `'` or `L`) walks and its `Load in Place` button loads. `tmp/` is the whole of what the player shows: it never lists `render/`, the deliverable there being for sharing outside the program rather than for auditioning in it.

Source inputs are stereo WAV only, 16- or 24-bit PCM, at 44100 Hz or above — anything else refuses to load with the reason on stderr. Material in any other format or layout — FLAC, Opus, MP3, mono — is converted once at acquisition with an external tool (e.g. ffmpeg), and the converted WAV becomes the project source.

The project's data lives in three sidecar files beside the audio, named by appending `.warpmarkers`, `.phaseresetmarkers`, and `.settings` to the audio file's basename. They are program-written and strictly validated at load: a hand-edited or corrupt sidecar fails the load with the first error on stderr.

**Per-device settings.** Five settings are about the computer you are on rather than about the piece, and they live in their own small file: `$XDG_CONFIG_HOME/warptempo_gui/config` (`~/.config/warptempo_gui/config` when that variable is unset). It holds exactly five lines, written in this order:

| Key | What it is | Written by |
|---|---|---|
| `gui_scale=` | the interface's rendering scale, an integer percent from 50 to 350 | the settings prompt, at commit |
| `projects_repo=` | the repository that is your projects home for the history view | the settings prompt, at commit |
| `projects_path=` | the absolute folder whose subfolders are the projects | the settings prompt, at commit (in force for the next `Open Project` and the next launch) |
| `last_project=` | the folder name opened last | the program itself, at every successful open |
| `sync_path=` | the folder Synchronize to external storage mirrors into | the settings prompt, at commit |

The first run on a machine writes the file with values that suit it — on the laptop `gui_scale=100` and a `projects_path` under the home directory, on the tablet `gui_scale=225` and the app's own external files directory — with `last_project=` and `sync_path=` blank. Both path keys are absolute paths that may not begin or end with whitespace; `sync_path` may be left empty, which means this machine has nowhere to synchronize to yet. The four keys other than `last_project` are edited in the app: `Settings` → `GUI Scale`, `Projects Repository`, `Projects Path` or `Sync Path` opens the settings prompt on that key with its current value filled in, and on the two path keys `Tab` completes the folder you are typing against the disk, one folder name at a time. A value the key refuses turns the field red and says why on a notification; a `projects_path` commit is kept for the next `Open Project` and the next launch, the open project staying open, and says so. The file can also be edited by hand — quit first: the program keeps its own copy and rewrites the whole file at every commit, so a line edited while it runs is overwritten by the next one. The file is strictly validated exactly as a sidecar is: a hand edit that breaks it stops the program at startup with the offending line named on stderr, and no window opens. The point of the arrangement is that a project synced between two machines carries no opinion about either one's screen, and each machine remembers its own place in your work independently. `Ctrl+S` has nothing to do with this file — each key writes at its own commit.

On launch, the program opens a window, reads the sidecar files, and presents the source waveform across the full window width. With no sidecar files present, you start with a single warp marker at frame zero carrying tempo `1.00` and no phase reset markers. With sidecar files present, the prior session is restored verbatim — viewport, zoom, playhead, active view selectors, and all marker positions and flags.

**Opening another project.** `Ctrl+O`, or File → `Open Project`, brings up a list of your projects across the window below the menu row, with `Cancel` at the right of the bottom row under it. It owns the window the way the render player does: everything between the menu row and the bottom row is the list, and the menu row stays in view above it with `File` still open and the rest greyed — the same partition the history view has always had. There is nothing to type: the list holds one row per folder that is actually a project (a folder that will not open is simply not in it). Click a project to open it — one click, or one tap. `Up` and `Down` move the highlight and `Return` opens the highlighted one; those are the same act as the click. The list is read when it opens; the highlight starts on the project you have open. Scroll it with the wheel, or drag it with a finger. Opening reopens the program around that folder, exactly as choosing a project at startup does; an unsaved tab asks first, the same prompt `Ctrl+Q` raises; opening the project already open just closes the list, with nothing to say — the window title names it. A folder that turns out not to open reports the reason in a notification and leaves the list open; `Return` on an empty list — every folder under `projects_path` refused by the model — answers `Choose a project first`. `Esc` or `Cancel` closes it. On the tablet the gesture is two taps: File → `Open Project`, then tap the project.

**Synchronizing to a stick.** `\` — the backslash key — or File → `Synchronize to External Storage` mirrors the open project's rendered wav files into the folder `sync_path` names — on the laptop that is the stick's own mount folder, something like `/run/media/<you>/<label>` — under a folder of the project's own name: whatever wav files the project's `render/` folder holds, directly, plus each batch of renders under its own folder exactly as it sits in the project; wav files only. What it copies is simply what those folders contain, so the stick ends up holding the same wav files the project does. It is a mirror of that one folder and nothing more: anything already there that is not part of the current set is deleted afterward, so running it again after a fresh render brings the stick back in step rather than piling up old copies, and any other project's folder on the stick is left alone. Renaming the piece leaves the old rendered wav in place until you render again — a render clears it from `render/`, and the next synchronization then clears it from the stick.

It goes where you told it and looks for nothing: set `sync_path` once per machine, in `Settings` → `Sync Path` (or by hand in the config file, with the program quit). If it is empty, a notification says `sync_path is not set` and nothing runs. The folder has to be there — the command never creates it — so with the stick unplugged or the path mistyped, a notification names the path and says it is not a directory. Anything else that goes wrong stops the act where it stands, with the offending path in a notification and the full path on the terminal. The order of operations protects your data: nothing is deleted until every file has copied, and a file being replaced is written beside its old copy and swapped in only once it has arrived whole — so a stick pulled mid-copy costs you the new version, never the old one. Running the command again is the retry, and it mirrors from wherever the last one stopped. When it works it says nothing at all: the command is quiet on success exactly as a finished render is, and the only thing it ever tells you is what went wrong. If anything on the way is a symlink rather than a real folder or file, the act says so and does nothing — it will not read, write or delete through one, on either side. And because the stick cannot tell `My Title.wav` from `my title.wav` while your disk can, two such files heading for the same folder on the stick would land on one name: the act names both and does nothing rather than shipping one of them and calling it a success.

On the tablet, a stick has to be mounted where apps can see it, and the current One UI build does not mount an OTG stick that way — there is no folder to point `sync_path` at, so the tablet's stays empty and the command refuses there.

The repository's `projects/` directory ships reference movements with complete sidecar files. The Symphony No. 40 first-movement directory (`projects/550 - 1/`) is the recommended first load — it exercises every form and syntax used in the project. The audio itself is not included (the corpus is commercially licensed); you supply the source recording and place it in the project directory under the basename the sidecar files expect. See Projects at the end of this document.

## Conceptual model

### The engine

`warptempo_gui` drives a phase vocoder — a faithful, centered implementation of Prusa-Holighaus phase-gradient heap integration (PGHI, from ltfatnote050, "Phase Vocoder Done Right"). The gradient method enforces phase coherence in both time and frequency without peak-picking or transient detection, which is what lets a high stretch ratio preserve upper-band detail and transient impact rather than dulling them. Per-frame phase correction keeps bins coherent within each frame, so steady-state content — held strings, sustained winds, room tone — stretches without smearing into a chorused or phasey artifact.

The FFT size `N` is fixed at 4096 and the synthesis hop `R_s` is derived as `N/4` (75% overlap). These parameters match the authors' released PGHI implementation (github.com/ltfat/pvdoneright) parameter-for-parameter — window length 4096, `M=2N=8192`, synthesis step 1024, tolerance `1e-6` — giving the gradient integration its finest frequency resolution and the fullest low-frequency body. The engine inherits the source recording's sample rate.

### Relation to the published algorithm

The engine implements the published algorithm faithfully: origin-centered zero-padded analysis (`M=2N`, matching the paper's ~2x padding), centered finite differences for both phase derivatives, trapezoidal integration in all three propagation directions, the max-heap significance ordering, and the published tolerance. Where the implementation deviates from or extends the paper, the differences are deliberate:

- Variable analysis hop. The paper fixes one analysis step for the whole file (constant stretch ratio). This engine derives the analysis hop per frame from the warp-marker frame map; each half of the centered time-derivative is normalized by its own actual hop, and the frequency-direction step uses the per-frame ratio. This is the extension that makes free-tempo warping possible and is the project's reason to exist.
- Phase resets. The paper has no mid-stream re-grounding; transient handling is left to detection-based methods it cites. This engine's manual phase-reset markers re-seat the synthesis phase to the analysis phase at user-chosen frames — operator judgment in place of detection.
- Output timing contract. The paper does not specify output alignment; this engine pins it. Synthesis trims exactly `N/2` samples from the head — the alignment latency the origin-centered analysis contributes — so source frame 0 maps to output frame 0, and a feature at source frame `S` lands at output sample `tgt(S)` from the frame map. Total output length is the target-frame position of the last source sample. The overlap-add ramps at head and tail move no alignment. The head ramp is not only a fade, though: the two analysis frames that would have to read from before the first sample are taken as silence, so a render fades in over about 70 ms and its opening phase is seeded from that silence — which is why a phase reset placed inside roughly the first 46 ms of a piece does nothing at all. On lead-in silence, which is what these recordings have, none of that is audible; a recording cut hard on its first note would open a little under level. This establishes a contract: any future engine consuming the same warp markers (and, if it supports them, the same phase-reset markers) can match this engine's output 1:1 in frame timing at the start and through the body. The tail's final incomplete-overlap ramp is deliberately outside the contract.
- Remaining boundary choices, unspecified by the paper: the first frame (and the frame each phase reset selects — the frame whose analysis window centers on the authored position) seeds synthesis phase from analysis phase, the seed that serves the timing contract and the reset model above; the first frame's time-derivative uses the forward difference only; the frequency-derivative is one-sided at DC and Nyquist.
- Quiet-bin randomness. The paper assigns unspecified "random values" to sub-tolerance bins. This engine pins the choice: uniform phase in (-pi, pi) from a per-channel deterministically seeded generator, so identical renders are byte-identical — the property the project's verification protocol depends on.
- Real-signal realization. The spectrum is held as the Hermitian half (`M/2+1` bins) rather than the paper's full-`M` complex formulation — mathematically identical for real input and output.

### Warp markers, labels, and phase resets

Variable-rate time-stretching with user-placed warp markers exists in other tools — DAWs have shipped warp-marker editing on top of their bundled time-stretch algorithms for years. What separates this project is per-marker tempo locking through label definitions and references. A marker can declare a named label; a later marker can reference that label by name; the two markers and every other reference to the same label render at the same effective tempo, and editing the def's tempo updates every ref that cites it. The use case it was built around is the sonata-form exposition/recapitulation relationship in classical orchestral repertoire, where the same musical material returns multiple times across a movement and should hold a coherent tempo relationship across all occurrences regardless of how the surrounding material is edited.

Per-frame phase coherence is what keeps steady-state content clean. It is also exactly what a transient defeats. An attack — oboe entry, pizzicato, timpani strike — is a moment where the spectrum reorganizes within a few hops, and the phase relationships the vocoder has been propagating no longer correspond to the acoustic event arriving. The attack smears across surrounding frames. The mitigation is a phase reset: at a user-chosen position, the synthesis phase is reset rather than propagated, sacrificing local coherence in exchange for a clean transient. Phase reset markers are the authoring surface for this. They are a separate marker collection from warp markers, visible and edited in their own view, because they parameterize a distinct engine concern: warp markers shape the frame map, phase reset markers protect transients.

### The three view axes

The interface carries three independent toggles: **source vs target** audio (S/T), **warp vs phase reset** markers (W/P), and **tab A vs tab B**. All combinations are valid; the GUI's state is the product of the three plus whatever modes are active on top. The S/T and W/P pairs sit in the icon row as radio buttons; the A/B pair is the tab row itself. The right end of the menu row carries three view buttons — `S+W`, `T+P`, `T+W` — one per working combination, each a click-shaped spelling of its digit key (`1`, `2`, `3`).

**Source vs target** selects the audio domain under the playhead. Source view shows the unprocessed recording with warp markers at the times you authored them; it is where a marker's *position* is authored — placing, dragging, nudging — because pinning a marker against an acoustic event belongs in the unprocessed recording. Target view shows the same audio after the engine has applied the live frame map — the waveform stretched and compressed to what the render will sound like, markers drawn at their post-stretch positions; it is where you judge the warp by ear, and everything that does not *move* a warp marker works there: the tempo step, disable, inherit, delete, the flag editor, the measure, grid iterations. Each edit reshapes the stretched picture as it lands, and the playhead follows the marker it was standing on into its new place. What target view refuses is moving a warp marker — the drop and the nudge answer `Markers are placed in source view` / `Markers are moved in source view`, and a flag drag simply never begins. Trim narrowed to the section under revision keeps target renders fast enough for the edit-listen loop to feel immediate.

**Warp vs phase reset** selects which marker collection is visible and edited. The two collections are stored, authored, and rendered independently; toggling swaps which collection the marker hotkeys operate on and changes nothing else. Warp positions author in source view; phase resets author in either audio view, though target view — where the stretch is audible and the lead-in overlay paints — is where their placement is judged. Warp markers' *values* are edited from either view; the measure, which reaches no engine concern at all, is editable on either collection from either view.

Both collections want **anticipation** — placement a little ahead of the acoustic event — for different reasons. Warp markers anticipate to make A/B synchronization reliable: rather than landing exactly on a transient, place the marker slightly earlier, in the fading tail of the previous material, which is a far more dependable alignment cue than the silence or volume dip just before a transient. The lead-in matters most for label-bearing markers and their neighbors, where the label mechanism's tempo precision only pays off if the underlying timing is itself precise, and for quiet, slow, or legato onsets with no sharp attack to pin to. Phase reset markers anticipate to give the reset an `N/2` lead-in into the transient: the engine seeds a reset from the synthesis window whose centre lies at or just before it — the last window that has not yet passed the reset — and replays that window's content as it stands, and the crossover from the old phase to the new one dips in level for about a hop on either side of that centre; both are over about `N/2` samples after the reset, so authoring the reset `N/2` before the transient means the transient itself arrives at full level, with the new phase fully settled, placed on the map by the ordinary synthesis rather than by the seed's own copy. The drop and the audition do this arithmetic for you (see Phase reset authoring).

**Tab A vs tab B** selects between two snapshots of viewport, zoom, playhead, and trim window. A snapshot holds positions and view settings only — never a selection, which belongs to the moment rather than to the tab. Marker stores and engine settings are shared across both tabs; only navigation state differs. The second tab earns its place from the first repeated phrase onward: park one tab at the first occurrence and the other at the second, then walk the lead-ins forward together to confirm the matching reference point — the same pattern at every scale, from phrase repeats to the exposition-recapitulation relationship a sonata movement turns on.

### The warp marker model

A default warp marker is seeded at the file's first frame on first load, carrying tempo `1.00`. A render does not actually require it: when no enabled marker sits at exactly frame zero, the render silently behaves as if a plain `1.00` owner were there. More generally, ambiguous marker arrangements never block anything — two or more enabled markers on the same exact frame collapse to a single `1.00` owner for the render, a reference whose definition was deleted renders as `1.00`, and each such normalization prints one stderr line naming the timestamp. What you see in the GUI is your authored store; a red flag is the display cue that a spot needs attention.

The classical phase-vocoder use case — one constant stretch ratio for the whole file — requires no warp-marker authoring at all: set the global ratio through the settings `scale` field and the frame map stays a single constant. Warp markers come into play when you want phrase-level tempo variation. Each one carries three independent pieces of engine state, and one piece that reaches the engine not at all — its measure, the bar of the score it sits on (see Marker measures).

**Tempo source.** A marker either owns its own tempo or inherits the tempo from the nearest earlier owning marker. An owning marker presents an explicit numeric value; an inheriting marker (a "pass") carries no tempo of its own and resolves its presentation tempo live by walking backward through the marker list. The walk passes over disabled markers and stops at owners; a pass never inherits through a reference — an enabled label reference encountered before any owner ends the walk at the neutral `1.00` instead (a reference owns a duration equation, not a rate, so there is no rate to inherit). Because the resolution is live, deleting or disabling an owner re-resolves every dependent pass to the next earlier owner; nothing is frozen on the pass itself.

**Label relationship.** A marker can declare itself a label origin (a `label_def`) or cite an existing label by name (a `label_ref`). A ref inherits its tempo from the named def rather than from positional walk-back; changing the def's tempo updates every ref that cites it. This is the mechanism for tempo locking across recapitulated material: the exposition section receives a `label_def`, the recapitulation a `label_ref` back to it, and the two always render at the same tempo regardless of subsequent edits. A reference imposes its definition's target duration on its own segment whatever local stretch ratio that implies, within reason: an implied effective tempo outside `[0.125, 8]` — beyond what any directly authored marker could express — is treated as a mismatch and renders as a plain `1.00` instead, with one stderr line; matching reference segments to their definitions sensibly remains the author's concern. A marker carries at most one of `label_def` or `label_ref`; neither is the unlabeled default.

**Disabled flag.** A marker can be disabled, which silences its tempo contribution as if the marker were not present. Disabling a `label_def` cascades: every ref citing it is treated as disabled too. Disabling a non-def marker is local and does not propagate.

An owning marker's tempo is a base value times a scale. The base value is exactly two decimals (the `N.NN` spelling is the on-disk grammar) in the bracket `[0.25, 4.00]` and expresses the headline stretch ratio relative to the source — `1.00` is no stretch, `1.05` is 5% faster, `0.95` is 5% slower. The precision is deliberately coarse; you author at the resolution you would set a metronome. The scale is a separate full-precision multiplier in the bracket `[0.5, 2.0]`, defaulting to `1.0000`. Its intended use is fine-tuning a marker's effective tempo to approximate a neighboring section's effective tempo when that neighbor uses a `label_ref`: select the neighbor and press `J`, which copies its resolved `base*scale` to the clipboard, then apply a matching scale to the marker being authored. Out-of-bracket values are rejected at the editor with a red flash and a notification saying why. The reference project in `projects/550 - 1/` shows both fields in use across a complete movement.

Phase reset markers carry two pieces of engine state: a position and a disabled flag. No tempo, no labels, no scale. Like warp markers they may carry a measure, which is a note about the score, not a parameter. The engine concern they parameterize is *where to reset* — the reset fires at the authored position, seeded from the analysis window whose centre lies at or just before it.

### A working method

How a movement actually gets authored, in the order that works:

1. Find the introduction measures that define the tempo. Set warp markers there, set the corresponding phase reset markers, then run BPM iterations and pick the tempo that sits right.
2. Work down the piece in chronological order, toggling between the three working views: `1` (source + warp) to place markers, `2` (target + phase reset) to protect the transients, and `3` (target + warp) for tempo adjustments by ear.
3. Once some headway is made, copy label definitions into references — the exposition into the repeat and the recapitulation — and paste the definition's phase resets and measures across with the propagate commands.
4. Phase resets are set with `Shift+S` and nudged only when the phase alignment causes an audible dip, pop, or crackle.
5. The A/B audition (`Shift+Space`) is crucial for confirming that label references match their definitions — the crux of the tempo-locking mechanism, which lets precise timing be replicated in the sonata-form fashion of repeated rhythmic motifs and phrases, at both large and small scale.
6. Iterations, trimmed target previews, and the history view carry the rest: render a spread, listen, load the winner in place, checkpoint.

On timing: the scanner's smooth movement plus the waveform magnification let a warp marker land essentially at the onset of an attack — zoom in, magnify the picture until the transient stands out of the quiet material around it, and place against what you see and hear together. The Symphony No. 40 first movement (`projects/550 - 1/`) is the worked demonstration of this.

## Output and the limiter

The render product is a finished WAV: 24-bit PCM, brought to a delivery ceiling by the built-in limiter — a transparent spectral stage at -0.3 dBFS, then a 0 dBFS lookahead peak limiter with a hard-clip backstop. The limiter is unconditional; there is no bypass and no output-format choice.

As future-proofing for later engines, every archival render — the GUI's `Ctrl+Alt+R`, the sweeps' batch cells, and the CLI — also writes the full frame-map pair: `<wav-stem>.warpframemap` (whitespace-separated `<src> <tgt>` frame pairs, precise double breakpoints) and `<wav-stem>.phaseresetframemap` land in `~/.cache/warptempo_gui/<pid>/` (batch cells under a subdirectory mirroring their batch folder). Together they are exactly the engine's input for the full (untrimmed) render of that recipe, with the phase resets already compiled into the engine's origin-centered query domain; trim never affects the pair, and the limiter does not apply to map files. Any time-stretch library that accepts a sample-domain warp map could be driven from these files. Retrieve them between the render and program close: the GUI removes its per-process directory when it exits, and CLI-written directories and orphans from dead processes are swept at the next GUI launch. The pair is written all-or-nothing — a write failure removes both files rather than leaving a mixed-generation pair.

## Reproducibility

Rendering is deterministic per machine and binary: the same project rendered twice on the same host with the same build produces byte-identical WAV output, every time. This is a hard guarantee — the whole pipeline is fixed-order and free of timing- or scheduling-dependent math. GUI and CLI from one build on one system state are byte-identical, unconditionally.

Across builds the boundary is not the compiler's code generation but the libraries underneath it. Floating-point contraction is switched off in the build, so how the compiler lays the arithmetic out no longer touches a single output bit: the same project renders byte-identically whether the binary was tuned for this CPU or built generically, and on another machine of the same architecture — same compiler, same glibc and FFTW — it is expected to render those same bytes again, though that is a derivation and not a measurement: only one machine has ever been rendered on. The term the derivation leaves out is glibc's own dispatch of `libm`/`libmvec` by CPU feature, which can differ between two machines carrying the same library version, so treat every host as its own reference and re-render rather than compare. What does move the output is a change in those libraries, and the movement is tiny. For a sense of scale at the far end: a completely different toolchain on a different architecture — a WebAssembly build of the same engine, carrying its own C library and its own copy of FFTW — differs from the native build by 67 samples of a 7.6-minute render, each by a single least-significant bit. On threshold-straddling material the limiter can quantize a difference that small into a localized one (measured at the -38 dBFS / two-samples class on a stress recipe — far below audibility, and ear-verified quality-neutral). So compare renders byte-for-byte freely within one set of library versions; after a glibc or FFTW upgrade, re-render anything you intend to keep comparing against.

## The interface

The reference is grouped by function. Everything is keyboard unless marked as a mouse gesture. A key is named by the cap it wears, so a letter is written capital whether or not `Shift` is part of the chord — where `Shift` belongs it is always spelled out, and the program's own tooltips and cards name keys the same way. Where a key does different things in warp view versus phase-reset view, both are given.

Three rules organize everything, and they are worth reading before the sections:

**Bindings are matched exactly.** A key pressed with a modifier the reference does not list for it does nothing at all — no near-miss chords fall back to the unmodified binding. Inside a text editor the clipboard chords are `Ctrl+C` / `Ctrl+X` / `Ctrl+V` exactly, so the terminal habit of `Ctrl+Shift+C` does nothing there. `Ctrl+C` reaches one surface outside the editors: the AV sync panel, where it copies the whole page. `Alt` lives only in the five `Ctrl+Alt` chords (the two render chords, the two phase-reset propagate pastes, and the measure propagate's paste) and one mouse binding, `Alt`+wheel; nothing else uses it. `Meta` (the Super or Logo key) belongs to the window manager: while it is held no keypress starts a command — with one deliberate exception: bare `E` is the left mouse button rather than a key, so `Meta`+`E` still clicks, exactly as `Meta`+click does.

**A press that does something is silent; a press that refuses normally says why; a press with no command behind it says nothing.** A bound key that cannot act answers on a notification card naming the key and the reason (`Ctrl+Z is not available on a read-only tab`). What stays silent is a chord with no command behind it — the history view's own keys, pressed outside the view, included — and a **one-dimensional command already at its state** — one that moves a single thing in a single place, so one glance at that place already answers whether anything happened: the playhead already at the end it would jump to, a walk already at its last marker or its last checkpoint, a scroll already at the edge of the piece, a ladder step already at its end, a tempo already at the bracket's edge, a marker already against a wall, a trim already covering the whole song, the selector for the view you are already in, a click on the radio button already selected. A command whose effect spreads across the screen keeps its sentence even where it has nothing to do — undo and redo over an empty stack, a tempo step over a selection one marker cannot take — because there is no single place to glance at. So silence with no visible change means the press was either unbound or had nothing left to change. Where a button spells the same step, its grey face says so ahead of the press; a greyed button stays silent too, the grey being the message.

**Keys act when they go down; buttons act when the mouse comes up.** A button is a target, so it gives you the slide-away escape a target should have — press, drag off, release, and nothing happens; drag back on and release, and it acts. A key is an instrument, and the moment you can aim is the moment you press — which matters on the warp side, where you are placing markers against music you are listening to. A key that repeats while held — the arrows, `PgUp`/`PgDown`, the zoom keys, the two waveform-magnification chords, `Tab`, undo and redo, and the history walk — acts at once, then waits your desktop's own key-repeat delay and runs at your desktop's repeat rate; each repeat reads the modifiers as they stand at that moment, so holding `Ctrl+Z` and adding `Shift` partway through carries the run on as redo. A key, like a mouse gesture, cannot be called back: by the time it is down the command has run, and undo is the way out.

Two button conventions ride on that. Wherever a keyboard command has a `Shift` version and its plain version has a button, that button takes the `Shift` version too: `Shift`+click it, or hold the press about half a second before letting go — the hold is there for the touchscreen, which has no `Shift`, and works the same with a mouse. (Two exceptions prove it. The playhead skip buttons' modifier is `Ctrl`, which only a real `Ctrl`+click reaches — no hold. And the four arrows take both modifiers, `Shift` for a three-step and `Ctrl` for a ten, but neither by hold: they repeat while held, so a long press on one gives the stream of single steps.) And six buttons repeat while held instead of waiting for the release: the four cardinal arrows on the bottom toolbar and the waveform magnify/reduce pair in the icon row, which step steadily for as long as you hold them — how a touchscreen walks a ladder.

### Notifications and the state text

When something you asked for could not be done, or something you were not watching finished badly, the program says so in a small dark card at the top right of the window — a blue information glyph, the text, and a close button. The card answers the press that raised it: a chord swallowed because an editor is open, a marker verb with nothing selected, a command used away from its home view, a mode that will not open on the selection you have — each names what it wanted, one card per press. Press the same refused key twice and you get two cards: the count is there so you can see that each press was read, which is what you want when you are stepping something deliberately and watching for the wall. *Holding* is the exception, and it reads the same whether you hold a key or one of the six buttons that repeat while held — the repeats stream at the keyboard's own rate, and they re-push the one card rather than burying the screen in copies of one sentence. Hold `Up` on a marker that cannot take the step and you get one card; hold the up-arrow button on that same marker and you get one card. Cards are all one width unless the sentence is long enough to need more, so two answers that differ by a word do not shift under each other as you press.

A command that worked says nothing, as long as the screen shows what it did — and the one thing the screen cannot show is the clipboard. So the four copies say so themselves: `J` reports `Copied the resolved value`, `Ctrl+P` `Copied the selected markers' phase resets`, `Ctrl+/` `Copied the selected markers' measures`, and the AV sync panel's `Copy to Clipboard` `Copied the AV sync stats`; a copy whose selection held nothing to take says that instead, and a copy the clipboard did not take says so too — `The clipboard did not take the copy`, on either machine, if the system refused it. An editor's own `Ctrl+C` stays quiet, because the text it did not take is still sitting there selected; its `Ctrl+X` does not, because a cut that could not copy must not delete either — it keeps the selection and says `The clipboard did not take the cut`. Everything else you can see: the region going up over the whole song is its own answer, and so are the trim bar's endcaps jumping to the ends when a drawing collapses. Saving, rendering and synchronizing stay silent when they work: on the desktop the asterisk leaving the window title is the save's answer, and the finished file is the other two's; the tablet has no window title, so a save there passes with no sign at all.

Ordinary cards leave by themselves after a few seconds, waiting while the pointer rests on them, or when you click their close button. The checkpoint failures described under Checking history carry the red error glyph instead and stay until you close them. `Esc` closes cards too — the whole stack at once, and it takes the red cards as readily as the ordinary ones. It is the last thing `Esc` does, so anything it would otherwise close, or a render it would cancel, comes first: with an editor, prompt, menu, player or list open, the first press closes that and a later one reaches the cards. With no cards standing it does nothing and says nothing. Newer cards stack on top; when the stack fills the window the oldest ordinary card leaves to make room, and the red ones never leave that way. A longer sentence wraps, up to three lines. A card stops nothing, and a click anywhere on it other than its close button does nothing at all.

What is true right now — a render's progress (`Loading...`, `Rendering...`, `Updating...`), or the history view's position while that view is open — is not a card: it is the **state text** on the bottom toolbar, which runs on from the clock in the clock's own monospace, after a pipe — `00:00.100 | Updating...`. It is replaced as it changes and never times out; the history view's line wins while that view is open. While a prompt, one of the bottom row's editors, the render player, the project list or the AV sync panel holds the bottom row, the state text steps aside and returns when they close.

### The window

The bottom toolbar sits along the very bottom edge. Everything else is one block: the menu row, the tab row, the icon row, the overview strip, the trim bar, the ruler, the marker lane, and the waveform under them. The block is placed so the middle of the waveform is the middle of the window; on a tall screen the waveform grows to a limit and blank bands take the rest — the one above the menu row wears the menu row's own colour, so the row reads as a tall band with its buttons along its foot, and the one above the bottom toolbar is plain ground — and nothing in those bands responds to the mouse. On the desktop, unsaved work shows as an asterisk in the window title after the project name; the tablet has no title to carry it.

**The bottom row is the modal surface.** Prompts and the one-line editors (settings, BPM, the commit message, and the paste-measures offset) take the whole bottom row while they are open — the transport, the clock and the state text step aside — and while one is up the rest of the window is inert: clicks, scrolls, and drags anywhere else do nothing, and it closes only by its own buttons and keys. The mechanics are the same for all of them:

- A prompt reads from the left with its answers as real buttons after it — `Save`, `Discard`, `Cancel` on the unsaved-changes prompt (`Retry` replacing `Save` after a failed save), `Yes` / `Cancel` on the paste confirmation, `OK` / `Cancel` on the load-in-place confirmation. Every button has a key, named in its tooltip (`Save (S)`, `Discard (Del)`, `Cancel (Esc)`); a tooltip names the key cap, and the letter answers are typed plain — `Shift` does not answer a prompt.
- An editor is a label, a dark text field, and `OK` / `Cancel` buttons that are exactly the editor's `Return` and `Esc`. It opens with the keyboard in the field; the field carries the blue outline while the keyboard is in it, scrolls sideways to keep the cursor in view, and takes the ordinary text-field gestures (see the flag editor under Warp marker authoring — all editors share them, the clipboard described there included).
- `Tab` moves the keyboard around the ring of field and buttons, `Shift+Tab` the other way; in a field with something to complete, `Tab` completes first and walks the ring only when there was nothing to complete. `Return` or `Space` presses the focused button. A prompt opens with its *last* button focused — the one `Esc` would pick, so `Return` takes the safe answer — with one exception: the load-in-place confirmation opens on `OK`, because a load is one `Ctrl+Z` away.
- The two chords that reach through any of them are `Ctrl+S` (saves; the surface stays) and `Ctrl+Q` (abandons it, then the usual close routing).

`Ctrl+S` saves all sidecar files; if one of them cannot be written — a full disk, a permission the folder no longer gives — a notification names the file it could not write, the work stays unsaved, and the asterisk stays in the title, so `Ctrl+Q` still offers to retry. `Ctrl+Q` closes the window, routing through the unsaved-changes prompt when the session is dirty. On the tablet the system's own Back — gesture or button — is that same command; being killed from the task switcher is not, and asks nothing, so answer the question rather than swiping the app away.

### Menus

The menu row holds `File`, `Edit`, `Iterations`, `Settings` and `Help` on the left and the view bar on the right. All five open dropdowns; the item runs when you release the mouse on it, `Esc` or a click anywhere else dismisses the menu, and you can press on the button, drag into the menu, and release on an item in one motion. Once a menu has been opened, moving the pointer onto another menu button switches to its menu with no click. In `File`, `Edit`, `Iterations` and `Help` each row shows its key beside it and does exactly what the key does; `Settings` is the one menu whose rows have no key of their own — each opens the settings prompt on one setting.

- `File`: `Open Project` (`Ctrl+O`), `Synchronize to External Storage` (`\`), then, past a line, `Quit` (`Ctrl+Q`). All three work inside the history view too. `File` is also the one menu that stays open over the render player, the project list and the AV sync panel: `Quit` and `Synchronize` work from there, and `Open Project` does nothing while one of those stands.
- `Edit`: the five propagate commands — `Copy Phase Resets` (`Ctrl+P`), `Paste Phase Resets` (`Ctrl+Alt+P`), `Paste Phase Reset State` (`Ctrl+Alt+Shift+P`), then `Copy Measures` (`Ctrl+/`) and `Paste Measures` (`Ctrl+Alt+/`). This menu is the mouse's one road to them.
- `Iterations`: the two sweep modes — `BPM Iterations` (`M`) and `Grid Iterations` (`I`). The `Grid Iterations` row shows no tick when the mode is on; it does not need one — the mode puts a bracket field on every warp flag on screen, and the `Render` button's tooltip changes to `Render Grid Iterations`. If the mode has nothing to sweep the button greys and its tooltip says which refusal a press would have met.
- `Settings`: the settings you edit by hand — `Title`, `Notes`, `URL`, `Cover`, then the per-device keys `GUI Scale`, `Projects Repository`, `Projects Path`, `Sync Path` — each opening the settings prompt with that key and its current value filled in (`;` opens the bare prompt directly; the waveform magnification has its own keys, wheel and buttons, and its row left the menu). On the two path rows `Tab` completes the folder being typed against the disk. Every row opens on a read-only tab; it is the commit that answers there — the four per-device keys go through, and the four keys belonging to the piece say `This tab is read-only` and leave the field red.
- `Help`: one row, `AV Sync Stats` (`Shift+L`), which opens the panel described below.

**The AV sync panel.** `Help` → `AV Sync Stats` — or `Shift+L`, which opens and closes it the way `L` opens and closes the render player, the two sharing one letter because they share one band — opens a page of text across the window below the menu row, in the same band the render player and the project list use, with `Copy to Clipboard` and `Close` on the bottom row (`Ctrl+C` is the copy's key, and `Esc` or `Shift+L` closes the panel). The `Play renders` button reaches it too — `Shift`+click it, or hold the press about half a second, which is the touchscreen's road in. The menu row stays above it with `File` open and the rest greyed, as it does under the other two. Its lines are in a fixed-width face, so the figures line up; the render player's and the project list's rows are in the ordinary one. The copy takes the whole page — every line, in the order it is painted — and a card says it went to the clipboard, so the figures can be pasted straight into a note or a message; there is nothing to pick out by hand and no part of the page is copied on its own. It reports what the audio device says about itself — which sound system is in use, its rate, the block it asks for at a time, and, where the system reports one, how long after the program hands over a sound that sound is actually heard — and what the display says about itself: which screen the window is on, its refresh, and how long after the program paints a frame that frame turns into light. The last group is the one worth reading: a single line saying how far ahead of the sound the playhead runs, in words rather than a bare number, and by how much more the start of each playback can vary. Where a figure is not available the panel says so and prints no combined line, rather than showing a number made out of half a measurement — on the tablet the display side and the output latency are both unavailable, and it says which.

**It measures only while it is open.** Nothing is being timed, sampled or asked of the audio server or the compositor while the panel is closed; opening it starts the measurements and closing it stops them. Expect the display figures to read as waiting for a moment after it opens — they fill in as soon as the screen has shown a frame or two.

The view bar is the three view buttons — `S+W`, `T+P`, `T+W` — each a click-shaped spelling of its digit key; the button matching the current combination wears a toggled-on face, and none lights in the fourth combination (source + phase), which has no button or key.

### The two toolbars

Every button in the icon row and on the bottom toolbar is a click-shaped spelling of a keyboard command and behaves identically to it. Buttons never appear or disappear; a button whose press would do nothing greys out instead — the greys are truthful, so a grey face is the program telling you in advance what a card would tell you after. The radio pairs are the exception: the selected half of a pair stays lit and simply ignores a click, having nothing to switch to. A greyed button still shows its tooltip: a button that cannot act right now is exactly the one you may need told what it is for. Every button shows a small tooltip naming its action and key after the pointer rests on it; where the button takes a `Shift`+click (or a `Ctrl`+click, on the two skips), a second line names that act.

The icon row, left to right: `Save` (`Ctrl+S`), `Undo` (`Ctrl+Z`), `Redo` (`Ctrl+Shift+Z`), `Render` (`Ctrl+Alt+R`); the source/target pair (`T`) and the warp/phase-reset pair (`P`), radio-style; the view group — **Toggle Trim Region** (`[`, taking `Shift` for `Shift+[`), zoom in (`Ctrl+=`), zoom out (`Ctrl+-`), full zoom out (`0`), center (`C`), **Magnify Waveform** (`=`) and **Reduce Waveform** (`-`), **Toggle Follow** (`F`, a lamp), and **Toggle Centered Viewport** (`Y`, a lamp); play renders (`L`, taking `Shift` for the AV sync panel) and the read-only padlock (**Toggle Read-Only**, `O`, showing and toggling the active tab's lock); and the history group — **Toggle History View** (`H`), the `Git` / `Session` walk radios (`G`), **Toggle Cumulative** (`U`), revert (`V`), the walk's two arrows (`,` and `.`, each taking `Shift` for the jump to that end), and load in place (`'`). Load in place sits with the history buttons because that is the only place it is a button: it loads the checkpoint or session state the view is showing, and outside the view it is grey — press `'` there and you get the render player, which has its own load button. It is grey on a locked tab too, and over a piece with no history to walk. `Render` takes `Shift` (the miscellaneous render, `Ctrl+Alt+Shift+R`) and wears the cancel glyph while a render you asked for is running — clicking it then stops the work. In the history view `Save` wears the commit glyph and reads `Save and Commit`.

The bottom toolbar, left to right: go to start (`Home`), play/stop (`Space` — one button showing whichever act is next, taking `Shift` for the A/B audition), go to end (`End`); the clock, in monospace, with the state text running on after a pipe in the same lettering; then, against the right edge: the marker verbs — drop (`S`, taking `Shift` for the phase-reset drop), delete (`Del`), toggle disabled (`Ctrl+D`), toggle inherit (`Ctrl+N`), edit flag (`Return`), measure (`/`), copy resolved value (`J`, taking `Shift` for the jump to the defining marker), and toggle add to selection (`K`, a lamp); the marker walk — previous (`Shift+Tab`), next (`Tab`), walk both tabs (`Ctrl+Shift+Tab`); and the four arrows, which hold-repeat and take `Shift` for the three-step and `Ctrl` for the ten. The two skip buttons take `Ctrl`: a `Ctrl`+click jumps to the very start or end of the piece instead of the trim bound, the same act as `Ctrl+Home` / `Ctrl+End`. Every tooltip says what the press will do right now: a lamp's names its toggle, a skip's says `At the trim start` when the playhead is already there and only the `Ctrl` form would move it, full zoom out at its ceiling reads `Back to Working Zoom` or `Back to Previous Zoom`, center with nothing focused reads `Center on Playhead` — and a second line appears only where `Shift` or `Ctrl` would do something different in that state (no `Press Shift for the whole song` over a trim that already is the whole song, no `Press Ctrl` line where the trim bound and the song's end coincide).

Locking a tab greys the buttons the lock actually refuses: on the bottom toolbar the four single-marker verbs, edit flag, measure, and the four arrows — up and down whenever the tab is locked, left and right only while a marker is selected (with none selected they still step the playhead) — and, in the history view, the icon row's load in place (outside that view it is grey anyway, and for a different reason). `Save` and `Render` stay live on a locked tab: a lock is about the piece's markers and settings, not about writing out or rendering what is already there.

### Playback and playhead

`Space` starts and stops playback from the playhead to the end of what is playable — the song's end in source view, the end of the rendered preview (the trim window) in target view. The moving playhead is drawn from where playback started and runs on the clock, so on a device with output latency the line runs a little ahead of what you hear, by an amount that varies slightly from launch to launch. Nothing loops: every audition plays once to its end and stops on its own (the one exception anywhere in the program is the render player's `Repeat one` lamp). When `Space` will not play it says why: `Wait for the target preview to finish rendering` in target view before the preview exists — and if that preview render fails outright, a card says `Target render failed` and target view has nothing to play — and `Playback is unavailable on this device` when no audio device came up at all — or, on the tablet, when a route that dropped (a headphone pulled, a Bluetooth route gone) could not be reopened: a play press there reopens the device first and says this only if that fails. With the cursor at or past the end of what is playable it simply does nothing — the playhead resting there is the answer, and the Play button is grey. If playback instead does nothing at all — no sound, the playhead staying on its start frame — and the program then freezes at the next stop, the audio device is dead or its sink is stuck in the audio server; fix that and relaunch, as the program hangs there on purpose rather than pretending to play.

`Home` and `End` jump the playhead to the trim begin and trim end, dropping the marker selection as they go; `Ctrl+Home` and `Ctrl+End` jump to the very start and end of the piece, whatever the trim window is — the way to reach audio the window has cut off without opening the window first. A press that would change nothing does nothing and says nothing: the playhead is already sitting where the jump would put it, and the skip button is grey.

A keyboard playhead move stops playback; a command that only moves the view (zoom, `PgUp`/`PgDown`, `0` short of the full-song view) does not, and neither does the `Up`/`Down` tempo step. Trim edits stop playback in both audio views — a trim change redefines what an audition would play — while `[`, which only shows and hides the region, leaves an audition running.

The mouse is different: a click on the waveform's **upper half** (or the ruler, or an empty spot in the marker lane — the three are one surface) moves the playhead at the release, reseeking live playback there instead of stopping it; a plain drag on that same surface pans instead, and the two never fight — a still click places, a moving drag pans. A click on the waveform's **lower half** auditions instead of placing: it stops a running session, and on a stopped one the moving scanner starts from the clicked spot — one-shot per click, Ableton-style, without touching the resting playhead, the selection, or a showing trim region.

`F` toggles follow mode, which scrolls the viewport to keep the playhead in view during playback — during only: when playback ends, the viewport stays where it was. Panning away during playback wins over the chase: any pan switches follow off for that session.

`Y` is **Toggle Centered Viewport** — a lamp beside follow's, and a stronger promise than the chase: while it is lit the view holds the playhead at the center of the window, at whatever zoom is standing (press `C` once and the lamp holds that picture). At rest, whatever moves the playhead — a click, a marker walk, a jump, undo — brings the view along; during playback the waveform scrolls under a playhead that stands still in the middle of the screen. At the song's two ends the playhead walks off-center, there being no waveform left to scroll in. The lamp never touches the zoom: `C`, `0` and the zoom keys all work as usual, each landing with the playhead still centered. Panning during playback wins here exactly as it does over follow — the pin lets go for that session and the next play re-engages it — and so does a click that reseeks the playhead during playback, aiming being what the click is for; either way switching the lamp off and on again (or pressing `F`) takes the camera back at once. A pan at rest simply works until the playhead next moves. The A/B audition ignores the lamp — its four plays hold the view still, the way they do with the lamp unlit — and the pin picks up again the moment the sequence ends. The preference is saved with the piece, like follow; with the lamp lit, follow has nothing left to do during playback and rests. It works on a read-only tab and in the history view.

**The A/B audition** (`Shift+Space`, or the play button's `Shift`+click or long press) compares the two tabs' cued spots without the hand-work: it switches to the other tab, plays a short span from that tab's playhead twice with a short rest between, switches back, rests a little longer, and plays the same short span from this tab's playhead twice — then you are back where you started, ready to adjust. Each half opens with `C` on the tab it is about to play, so both spots are read at the working zoom, centred, focused marker and all. The centered lamp is disregarded for the whole sequence — the view stays where `C` put it and the playhead travels across it, rather than the waveform sliding under a fixed line — and the lamp, untouched, takes hold again when the sequence ends. Neither playhead moves; each play is an ordinary one that runs to its own end, and each tab plays what it always plays — the file in source view, the rendered preview in target. Anything that would stop or restart playback ends the whole sequence where it stands — `Space`, a tab switch, a playhead move, a marker edit — and the rests count as part of it: the play button wears its stop square from first play to last, and `Space` in a rest stops the sequence. `Shift+Space` is a toggle like the transport it rides: press it again while one runs — or shift-click or long-press the play button again — and the sequence stops where it stands, with no new one started. One that cannot run says `One of the two tabs has nothing to play from here`. It works on a read-only tab.

`Left` and `Right` move the playhead one pixel — unless markers are selected, in which case they move the *focused marker* instead (see Warp marker authoring). With nothing selected an arrow press also drops the marker focus and hides a showing trim region.

**The step ladder** — one rule for all four arrows, and it is the same rule wherever an arrow acts. A modifier scales the step and changes nothing else: bare is one unit, `Shift` is three, `Ctrl` is ten. The unit is whatever the plain arrow already steps — a pixel column for `Left`/`Right` (the playhead here, the focused marker in the marker lane) and `0.01` of tempo for `Up`/`Down`. Everything else about the press is untouched: the same walls (a long step near an edge lands exactly on the edge rather than overshooting — except the tempo step over a *group*, which refuses whole where any member cannot take the full step, as it does at any size), the same read-only rules, the same one-undo-entry-per-run, and a held modified arrow repeats *its own* step. `Ctrl+Shift` together mean nothing. The four arrow buttons on the bottom toolbar carry the ladder too — `Shift`+click one for the three-step and `Ctrl`+click it for the ten — but only from a keyboard: those four repeat while held, so a long press on a touchscreen gives the stream of single steps rather than the shifted twin.

### Zoom and view

Zoom is continuous. `Ctrl+=` and `Ctrl+-` step one whole level per press, `Ctrl`+wheel steps the same levels one per detent (wheel up zooms in), and the `Ctrl`+drag below reaches every fractional level in between. The deepest zoom is fixed (1.2 s across the waveform at the 1920 px deployment width — a zoom level fixes time per pixel, so the span scales with window width); the shallowest is the whole song exactly filling the width.

`0` goes to that full zoom-out — and remembers where it came from: pressing it stamps the level you were at, and pressing it again with the zoom already fully out runs the `C` command at that stamped level. So `0` twice takes you out to the whole song and back in to the magnification you were working at, on the marker you are working on. The stamp is per tab, lasts the session, and only `0` writes it. With nothing stamped — or a stamp no longer reachable — the second press is plain `C` at the working zoom.

`C` snaps to the working zoom (2.4 s at 1920 px) centered on the focused marker, jumping the playhead onto it; with no focused marker it centers on the playhead.

**The one drag** (mouse). The waveform's drag — either half, and equally on the ruler or an empty stretch of the marker lane — is one gesture with `Ctrl` as its zoom switch, the mouse's version of one finger versus two on a touchscreen. Plain, it pans — a smooth grab that captures the cursor for unlimited travel. With `Ctrl` held, the same sideways motion zooms instead — right zooms in, left out, about a pivot seated where the pointer was when `Ctrl` went down; up-and-down motion is ignored in both halves, so a wobbly zoom cannot slide the view and a pan cannot drift the zoom. Press or release `Ctrl` at any moment of the drag, as often as you like: each press seats the pivot under the pointer, each release hands the motion back to the pan, with no jump either way. The pivot holds the *audio* under it — the view scales around that piece of the song, and at the edges of the piece the pivot slides with its audio rather than letting the song walk out from under it, which is what makes a zoom reversible. A dim vertical stem marks the pivot for as long as `Ctrl` is down; the two-finger pinch shows the same mark. The drag moves the view and nothing else — playhead, selection, and a showing region stay exactly as they were.

The scroll wheel on its own magnifies the drawn waveform (below). `Alt`+wheel pans, a tenth of a screen per detent; `Ctrl`+wheel zooms one level per detent, centred on the playhead. `PgUp` and `PgDown` step the viewport by the same tenth of a screen; hold for a glide.

Double-click on the trim bar frames the trim window when it is narrower than the whole song, and the whole song when it is not.

**The overview strip** (mouse). Between the icon row and the trim bar runs a slim strip showing the whole song at once — the piece's waveform in miniature, a thin box marking what the main view is showing, and a white tick marking the playhead. The strip is worked by grabbing the box: drag inside it to pan, drag an edge to resize — that edge follows while the other stays put, so dragging outward zooms out and inward zooms in — and press outside it to center the view there at once, the same press then holding the box so a pointer that keeps moving keeps panning. Each edge is grabbed with ten pixels of slack. That figure — like the trim bar's nine-pixel height and its own grab bands below — is an authored pixel scaled by `gui_scale`, so on the tablet's 225% it is about twenty-two. Only sideways motion counts. The wheel works over the strip as over the waveform. It draws no region, selects nothing, and never moves the playhead; like any pan it wins over follow mode. On a touchscreen it carries over exactly, one finger only — a second finger on the strip (or the trim bar) is ignored entirely.

### Waveform magnification

`=` and `-` make the drawn waveform taller and shorter, and so does the scroll wheel on its own — one step per detent: the picture only, never the sound. Classical material has a dynamic range wide enough that a quiet passage draws as a hairline at the height a forte fills the lane; this is how you bring one up to something you can read. Each press is a doubling, from normal to sixteen times — five positions, a press at either end doing nothing. The scaling is linear at every step: peaks are multiplied and clipped flat at the lane's edges, so a loud passage goes to a solid block while its quiet troughs still dip — and that clipping is the point: you place a marker on a transient, not in a sustain, and the transients are what stay visible. The whole-song strip magnifies with it. Nothing about the audio or the timing moves — playback is at the same level at every setting and a render is byte-identical. The setting persists in `.settings` as `waveform_magnification_level` (the count of doublings, 0–4) — it belongs to the piece, since how loud the picture should be drawn is a fact about the material — and it works on a read-only tab and in the history view. The two icon-row buttons do the same and repeat while held; `waveform_magnification_level=0` in the settings prompt is the one-step reset.

### View toggles

`T` switches the audio domain (S/T); `P` switches the marker collection (W/P); the bare digits jump straight to a combination — `1` is S+W, `2` is T+P, `3` is T+W — each applying whichever of the two switches it needs. `Ctrl+Tab` switches the A/B tab. `Ctrl+Shift+Tab` advances both tabs' marker focus in lockstep and lands on the opposite tab — it is short for a step, a tab switch and another step, which is also why it works inside the history view, where a step is a step along the differences.

A `T` switch carries the selection across — the same markers in another domain — and lands the playhead on the focused marker's position in the new domain; a showing region stays showing, drawing the same window. Switching the marker collection (`P`) or the tab (`Ctrl+Tab`) is different: those change which markers you are addressing at all, so they drop the selection. What you get back is automatic and comes from where the playhead is: on arrival, if it stands exactly on a marker of the newly active collection, that marker is selected for you; anywhere else, nothing is — being one frame off is being off. The tab's remembered playhead is restored exactly as you left it, which makes that recovery predictable: leave a tab with a marker selected and the playhead on it, come back, and the same marker is lit.

`O` toggles read-only on the active tab. What it protects is the piece itself — the markers and the engine settings — and nothing else: navigation, playback, the view toggles, the whole trim window, saving and rendering all stay available. The point is a finished section you want to stop nudging by accident, not a tab you cannot work with: lock it, then go on moving the trim window to compare a passage against the other tab, re-render, and save. Blocked on a locked tab: the marker drops, drags and nudges, the tempo step, `Del`, the flag, BPM and measure editors, `I`, `'` in the history view (where it loads a state over your session; outside the view the same key just opens the render player and works fine — the player's own load button is what refuses there), every propagate command, undo and redo (an entry is refused when ITS OWN tab is locked, so the recovery is to unlock that tab with `O` — switching tabs does not help, the entry keeps the tab it was made on), and the settings prompt's own keys — `;` answers `; is not available on a read-only tab`, and the `Settings` menu's rows still open the prompt, where committing one of the piece's keys (`Title`, `Notes`, `URL`, `Cover`, or any engine key typed by hand) says `This tab is read-only` while the four per-device keys commit as usual. One navigation gesture is not exempt: with a marker selected the horizontal arrows are in the marker lane, where the same press authors, so a locked tab refuses them outright in every step size — drop the selection first and they navigate again.

### Marker focus and selection

`Tab` and `Shift+Tab` cycle marker focus forward and backward, moving the playhead onto the focused marker and recentering at whatever zoom you are already at — the walk never changes the zoom; `C` is the command that snaps to the working zoom. The walk skips disabled markers and operates on whichever collection the W/P toggle has active. A step with nowhere to go does nothing and says nothing — a walk already at its last marker is one of the one-dimensional refusals — and the matching toolbar arrow greys at the same moment, which is the whole cue.

A plain click on a marker's flag — the flag is the marker's one clickable part; its stem on the waveform is a visual cue only — selects the marker and seats the playhead on it the moment you press, without moving the view. It works in both views, both collections, and on a read-only tab. `Shift`+flag-click selects an inclusive range, file-manager style, from the anchor — the marker that was focused when you began shift-clicking — to the clicked one, which becomes the new focus; a second shift-click ranges from that same anchor again, not from the marker the first one focused with the playhead on it. `Ctrl`+flag-click toggles one marker's membership, seating the playhead on whichever marker ends up focused. With several markers selected, a plain click on one of them selects that one alone — and a drag from any flag moves that one marker only; dragging never moves a group.

**Add to selection** (`K`, or its bottom-row lamp, **Toggle Add to Selection**) is a sticky `Ctrl` for that gesture: while it is lit, a plain click or tap on a flag does exactly what `Ctrl`+clicking it does — adds or removes that one marker and leaves the rest standing. It is there for the touchscreen, which has no modifier keys; it works the same under a mouse. It reaches flags and nothing else, a held `Shift` still wins, and it puts itself out the moment anything replaces or clears the selection.

The playhead follows the focused marker: anything that changes which marker is focused brings the playhead along — the walk, the clicks, opening an editor, `Ctrl+N`, a propagate paste — and a nudge or flag drag carries it, so `Space` keeps auditioning from the marker your next press is about to move. Clicking an empty spot in the marker lane works like an upper-half waveform click; double-clicking an empty spot creates a marker there — exactly the `S` drop, in the collection's home view only.

On screen, each marker is a small colored flag in the lane above the waveform, carrying its text — the tempo or label for a warp marker, the words `phase reset` for a phase reset — with its stem running down through the waveform. Text longer than nine characters is shortened to nine plus `...`; an iteration bracket never shortens — the flag grows to carry it whole. Flags of nearby markers may overlap; the later marker paints on top, and clicking lands on whichever flag you see. A disabled marker dims its flag and shows no stem — and, with grid iterations on, shows no bracket: its bracket is kept dormant and comes back when the marker is re-enabled. Selection is a brightness cue: the selected flag brightens while its stem keeps the calm color. A marker that renders as the fallback tempo `1.00` paints its flag and stem **red** — a `label_ref` to a missing or out-of-range label, a pass that inherits from a reference, or a stack of markers sharing one frame (the whole stack reddens as one) — and neither selection nor the disabled dim masks the red. The playhead cursor is the white marker-style head in the marker lane with its white stem below; when it stands exactly on a marker, the marker's own stem shows in place of the white one — the cursor is still there, and playback still launches from it.

### Warp marker authoring (W view)

The commands that *move* a warp marker run in warp's home view — warp markers in source audio view — and everything else works from both audio views (see The three view axes). Movers: `S` and its empty-lane double-click twin, the flag drag, the `Left`/`Right` nudge, and the `M` BPM command. The keyboard movers answer off home with `Markers are placed in source view` / `Markers are moved in source view`; a flag drag simply never begins there.

`S` drops a marker at the playhead copying the previous marker's tempo — so the drop normally splits a section without changing how anything sounds, where a neutral `1.00` drop in the middle of a warped section would audibly change it. (Its shifted form, `Shift+S`, drops a phase reset instead — see Phase reset authoring.) Two cases are not silent, both by design: dropping onto a frame where an enabled marker already sits leaves two markers on one frame, which the render collapses to a single `1.00` — the markers turn red immediately, so you see it happen; and splitting a *label definition's* section shortens the definition, so every reference to that label changes duration too — a definition's span is its meaning. Where there is no usable previous tempo to copy — no earlier marker, a label reference, or a coincident stack — the new marker takes `1.00`; a pass is not one of those cases, resolving to whatever tempo is actually sounding there, which is exactly what keeps the drop silent.

`Up` / `Down` nudge the focused marker's tempo by ±0.01, from either audio view — or by ±0.03 with `Shift` and ±0.10 with `Ctrl`, the step ladder — target view is exactly where you want to hear a tempo change. In source view the single-marker press also converts a pass to an owning marker, frozen at the value it was resolving to — but not a label *reference*, which answers `A label reference has no tempo of its own` in either view, its tempo belonging to the definition it points at; in target view only a marker that already owns its tempo can be stepped — a pass or a reference answers `In target view only a marker that owns its tempo can be stepped`, and a coincident owner answers `That marker shares its frame with another` (the stack renders as `1.00` and is fixed in source view). With several markers selected the step moves every selected marker's own tempo together by the same ±0.01, all or nothing: if any member is a pass, a reference, coincident, or could not take the whole step without leaving `[0.25, 4.00]`, the press refuses whole with `One of the selected markers cannot take this tempo change` — which is why a `Ctrl` step can refuse a group the plain step would have moved, group members never being clamped apart from one another. A disabled member is invisible to the group step, as it is to BPM iterations: it is neither stepped nor a wall, the rest step together, and a selection made only of disabled markers has nothing to step and says `Select a warp marker to change its tempo`. A held run is one undo entry. The two arrow buttons say all of that ahead of the press: the up arrow greys once the focused marker rests on `4.00` and the down arrow at `0.25` — and one press or ten, the answer is the same, so a greyed arrow is greyed for every version of it, and with several selected both grey whenever that whole-press refusal stands — the card and the grey together, because a group step would have moved every selected value and there is no single place to glance at.

`Left` / `Right` nudge the focused marker's position by one painted pixel column — three with `Shift`, ten with `Ctrl`, the step ladder — and moving markers is always a one-marker act: with several selected, the press first narrows the selection to the focused one and then steps it. The marker stops at the song edges, and the matching arrow button greys once it is resting on one — the same truthfulness the pair already has with nothing selected, where they grey at the ends of the piece. With several markers selected they stay live even at an edge: that press still narrows the selection and brings the playhead to the focused marker, which is a change whether or not the marker then moves. A held arrow is one undo entry. A plain press moves one pixel column — tens of samples even at the finest zoom — so drop to the deepest zoom for the smallest step, and reach for `Shift` or `Ctrl` when the marker has a long way to go.

`Ctrl+N` toggles pass (inherit) status on the focused marker. `Ctrl+D` toggles the disabled flag on every selected marker. `Del` deletes every selected marker — label definitions included, even with live references (the orphaned refs render as `1.00`, red-flagged). All three work on either kind of marker where the kind carries the state (`Ctrl+N` is warp-only).

Dragging a flag moves that one marker — no modifier; the drag begins after a few pixels of motion, so a click stays a click — with the playhead following. The drag has no cancel: `Esc` while dragging does nothing, the release commits where the marker stands, and `Ctrl+Z` puts it back.

`J` copies the focused marker's resolved value to the clipboard — the `base` or `base*scale` text a flag editor accepts, ready to paste into another marker's editor or anywhere outside the program. `Shift+J` goes to the marker that value *comes from* — the owner a pass inherits from, or the definition a ref points at — on the other tab: it centres this tab on the reference first, then switches, lands the playhead on the source marker, selects it, and centres there too, so the reference stands on one tab and its definition on the other, one `Ctrl+Tab` apart. Both are read-only-legal and work with grid iterations on. An ineligible focus — an owner, a disabled marker, nothing focused — answers `The focused marker has no resolved value to copy` (or, for `Shift+J`, `The focused marker has no resolved value` / `There is no source marker to jump to`); a pass or a ref sharing its exact frame with another marker answers `The focused marker shares its frame with another, so its value is not what the render applies` — the render collapses such a stack to a plain 1.00, so the value the flag would resolve to is not the one you hear — and the button greys with the same reason on its tooltip. The bottom toolbar's **Copy resolved value** button is `J`, its `Shift`+click or long press `Shift+J`.

**The flag editor.** `Return` or keypad `Enter` — one key to this program — the **Edit Flag** button, or a double-click on the flag opens the focused marker's flag editor — the canonical-line surface where the whole marker line is edited as text: tempo, `label_def` / `label_ref`, per-marker scale, and (with grid iterations on) the iteration bracket. It is the only surface for authoring labels and per-marker scale. It opens with the whole line selected, so typing replaces it; `Return` commits — invalid input flashes the field red, keeps it open, and a notification says what was wrong — and `Esc` exits without committing. While it is open the keyboard belongs to the editor, and the ordinary text-field gestures work: typing, `Left`/`Right`, `Home`/`End`, `Shift` with those to select, `Ctrl+Left`/`Ctrl+Right` by word, `Backspace`/`Del` and their `Ctrl` word-erase forms, `Ctrl+A`, `Ctrl+C`/`Ctrl+X`/`Ctrl+V`, double-click to select a word, `Shift`+click to stretch the selection. The clipboard is the system's own on both machines, shared with every other program on them — what you copy here pastes into a browser or a note, and what you copy there pastes in here. `Ctrl+X` is the one clipboard chord that can refuse: if the system will not take the text, the cut keeps your selection and says `The clipboard did not take the cut` rather than deleting text that went nowhere. Everything else does nothing at all, so a stray chord cannot throw the edit away; the two chords that reach through are `Ctrl+S` and `Ctrl+Q`. There is no undo inside the editor. The mouse closes it: clicking anywhere but the editor's own text abandons the edit, and the click then does its normal work. These text-field gestures are shared by every editor in the program — the bottom row's dialogs and the measure editor alike. Every field has a byte cap of its own (twelve for a measure, longer for the others): typing into a full one says `This field is full`, and a paste too long for what is left says `The pasted text is too long for this field` and pastes nothing.

### Marker measures (`/`)

Any marker — warp or phase reset — can carry a **measure**: the bar of the score it sits on. It paints as a blue box continuing the marker's flag to the right, always visible, never shortened; a marker with no measure has no box. It reaches no part of the engine — it is about *where* the marker sits in the printed score — which is why it is editable on either collection, from either view, wherever the flag is painted. A read-only tab refuses it: a measure is part of what gets saved.

Two spellings are accepted and nothing else. A **measure number** — `12` — means the downbeat of bar 12; add a proper fraction in lowest terms after a single space — `12 7/8` — to sit part-way through it. An **offset** starts with a plus and counts from the marker before it in the same column: `+1` is one bar later, `+1/4` a quarter of a bar, `+2 1/2` two and a half. Offsets chain: `12`, `+1`, `+1` puts the third marker at bar 14. Bar numbers run 1 to 99999, denominators up to 99. Where a movement's printed numbering starts over — a menuetto's trio going back to bar 1 — just type the number the page prints: where the marker sits already says which bar 12 you mean. Anything else is refused at `Return` with a red flash and a notification saying what the grammar wanted. An offset whose chain does not lead back to a measure number is legal — it simply has no bar to resolve to yet.

Three ways in: `/` opens the measure editor on the focused marker, the measure button does the same, and double-clicking the blue box opens it on that marker. The box is otherwise part of the flag — clicking selects, dragging drags — and only the double-click tells the halves apart: double-click the flag for the flag editor, the measure for the measure editor. `Return` commits, `Esc` leaves without committing, and **committing an empty field removes the measure**. Each commit is one undo step.

Every measure belongs to the one marker you wrote it on. Nothing is inherited down a label: a reference does not pick up its definition's measure the way it picks up its tempo, because a bar number is about where the marker sits, and the same number is simply wrong a few references later. If you want the same measure in two places, write it in both — or use the paste (see Propagation). On disk the measure lives at the end of the marker's own line, after a space and two slashes: `44100|1.05 //12`, `#66150 //12 7/8`, `88200|1.00 //+1/4`. Hand-editing within those rules is fine — one of the two spellings, at most 12 characters.

### Phase reset authoring (P view)

These author phase resets, in *either* audio view — target view is where the lead-in and its overlay live, and source view authors too, plainly: the missing overlay and the missing lead-in are the clues you are in source view, and a reset placed there is adjusted in target view.

In target view, `S` drops a phase reset seeded `N/2` samples earlier in target time than the playhead (clamped to the file start, snapped to the nearest whole source frame), and the playhead moves back onto the seeded reset — the one drop that relocates the playhead, so the next audition starts at the new reset. The lead-in arithmetic is the engine's: a reset seeds from the synthesis window whose centre lies at or just before it, whose content is replayed as it stands and whose crossover into the new phase dips for about a hop after the reset; both are over about `N/2` samples past the reset, so placing it `N/2` before the point you marked is the least that puts that point past the crossover and outside the seed's own window — at full level, with the new phase settled, and on the map. One hop is not enough: the marked point would still sit inside the seed's tail. The output-domain overlay depicts the seed's remaining extent, for a single focused reset in target view: from the reset to where its window ends, on the engine's own hop lattice, so the band's far edge stands still as a reset is nudged within one hop — the band shortening or lengthening toward that edge as the marker itself moves — and the far edge jumps a whole hop when the reset crosses into the next — the moment the render actually changes; its widest is about `N/2`. In source view, `S` drops the reset exactly at the playhead's frame — no lead-in and no conversion.

`Shift+S` drops the same phase reset **from any view**: it switches to target view and phase reset view for you, then drops the same lead-in reset **for** the playhead's own musical instant — `N/2` ahead of the reset, exactly as `S` does in target view — and leaves it selected with the playhead seated on the reset — so a reset noticed while you are looking at the warp column costs one key instead of a trip across and back. With the phase-reset markers already showing it refuses and says `Already in phase reset view` — the chord *is* the crossing, and there is nothing to cross; use `S` there. One press is one undo entry, and undoing it returns you to the view where the reset was made. The bottom row's **Drop marker** button reaches it too: `Shift`+click, or press and hold.

In target view, `Space` auditions the alignment by starting playback `N/2` samples ahead of the playhead without moving it — past the seed's window, on the point the drop protects. It does this exactly when a phase reset is *focused* — the same condition that makes the overlay meaningful — and the drop's offset and the audition's are deliberate inverses, so dropping with `S` and pressing `Space` auditions from where the cursor was sitting — exactly so when the piece is being sped up, and within a couple of samples when it is being slowed, the reset having been snapped to a whole source frame in between.

`Ctrl+D`, `Del`, and the `Left`/`Right` nudge work on phase resets exactly as on warp markers, in either audio view, with the same one-marker nudge rule. Coincident phase resets on one frame paint red, like a warp stack.

Placement judgment: phase resets go where loud transient content provides masking; a quiet, exposed passage should carry one phase reset at its start and nothing else, since a reset during exposed material has nothing to hide behind. Nudge a reset only when the phase alignment causes an audible dip, pop, or crackle — each press moves one painted pixel column, so drop to the deepest zoom for the smallest step.

### Propagation

Five chords carry a labeled region's phase resets and measures from one occurrence of a label to another — the Edit menu is their one mouse home. All five anchor on a warp-marker selection and are refused on a read-only tab.

**Phase resets.** `Ctrl+P` copies: with one or more warp markers selected, forming one consecutive run, it captures the phase-reset layout of each selected marker's own section into the session clipboard — a marker's section runs to the next enabled marker, the final one's to the end of the song; unlabeled markers inside the run contribute nothing, and a disabled selected marker contributes no section of its own (the span under it belongs to the preceding enabled marker's section, so the resets lying there travel with it). `Ctrl+Alt+P` pastes: anchored on exactly one selected warp marker, it materializes the clipboard's resets onto the destination region, scaled to the destination's durations, after a confirmation prompt. `Ctrl+Alt+Shift+P` pastes state only: it aligns the enabled/disabled flags of the destination region's existing resets to the clipboard, in order, moving nothing, with no prompt. All three apply a 100 ms tolerance when deciding which block a reset belongs to: one falling within 100 ms before a block's owning warp marker counts as part of that block, is captured with it, and is reproduced at the same offset before the destination marker. The propagate is the one authoring action that starts in warp view and ends in the phase-reset target view: a paste that did something leaves you in target view with the phase-reset collection active, one that created resets selecting exactly those it created with the playhead on the first. A paste that got nowhere does not move you — one that found no block to work on, or that stopped on a mismatch at the very first block, leaves the view exactly where it stood and says so on a card (`Nothing matched, so nothing was pasted`, or where it stopped), rather than changing the scene in a way that would look like a paste. A paste that did work on a block takes you across even where it found everything already as the clipboard wanted it. A copy or paste with the wrong selection says which selection it needs (`Select one consecutive run of markers`, `Select exactly one marker to paste onto`); a paste with nothing captured says `Nothing has been copied yet`.

**Measures.** `Ctrl+/` copies each selected marker's label and measure, on the same one-consecutive-run selection; only *labelled* markers take part on both sides — the label is what the paste matches on — and a marker with no measure is captured as an empty slot. `Ctrl+Alt+/` pastes, anchored on exactly one selected warp marker: it walks forward over the labelled markers and lays the clipboard onto them in order, stopping the moment a label does not match and telling you where. Before writing it asks for an **offset**: a small dialog with `0` already in it, added to every plain bar number it writes — pasting a repeat is offset `0`, pasting into the recapitulation is the flat number of bars between them, and a negative number runs the other way. `+` measures copy across unchanged (they already count from the marker before them); an empty slot in the clipboard clears the measure it lands on; an offset that would push any bar number out of range is refused whole, red-flashing the dialog. The whole paste is one undo step, and unlike the phase-reset paste it leaves the view, the playhead and the selection exactly where they were.

### Trim and the region

The trim window is what makes working on a passage quick: a render covers the window rather than the whole piece, so a stretch you are shaping comes back in a fraction of the time — and in target view, what you hear is that same window, start to end. The window is a pair of bounds that always rests somewhere — it starts at the whole song — and it is always on display in the trim band, the slim bar above the ruler with an endcap at each end. That bar is nine pixels tall, which is right for a pointer and hopeless for a fingertip, so the same window can also be drawn across the whole height of the waveform: that drawing is the **region**. It is not a copy and not a scratch span you commit later — it is painted from the trim window every frame, so the bar and the region can never disagree, and anything that moves one has moved the other already.

`[` shows the region and hides it again — the **Toggle Trim Region** button is the same act, lit while the region is up. Showing also brings the window into view: the view scrolls to the span, or opens the zoom out until it fits. Showing it over a whole-song window works too — the region simply covers everything, its two bounds sitting at the song's own edges where they are still grabbable. Hiding discards nothing: the window is untouched, and showing again draws the identical region.

Three motions on the region write the trim. Drag one of its two bounds and that bound follows while the other stays put — the trim bar's own endcap drag on a bigger surface. Drag anywhere inside it and the whole window slides, keeping its width. And `Shift`+drag sweeps a new window outright, from where you pressed to wherever the pointer is, with nothing to commit afterwards and no need to have shown the region first: the region appears with the first bit of window the drag writes — so what you see is the stretch you are making, never the one you are replacing — and goes away again the moment you let go: a sweep says "this exact stretch", and once you have said it the big drawing is in the way. `[` brings it straight back. The sweep works on the whole navigation surface (both waveform halves, the ruler, the marker lane's empty stretches); on a marker's flag, `Shift`+click is the range select instead. A sweep sets exactly the window you draw, however narrow — there is no minimum width — and a stroke that ends where it began resets the trim to the whole song, the same escape a bound drag has: dragging one bound onto the other and releasing them coincident opens the window back to the whole song. Nothing is said about it — the trim bar's endcaps jumping to the song's ends is the answer, and a whole-song window changes nothing about what a render produces.

Every trim write parks the playhead at the new trim start and clears the marker selection: the sweep at its release, the bound-set clicks, an endcap or bridge drag at its release, `Shift+[`, and a typed `trim_begin=`/`trim_end=`. What you hear next starts there. `Shift+[` maximizes the window back to the whole song and puts the playhead at frame 0 (already full, it does nothing and says nothing — the trim bar spanning the window is the answer); it has three routes — the key, a `Shift`+click on the Show trim region button, and a long press on it — so the way out of a trim never wants a keyboard. Trim sits outside undo: an edit commits the moment you make it and no gesture has a cancel; `Shift+[` is the recovery. Trim is per-tab view state — every trim gesture works on a read-only tab.

**When the region goes away by itself** — one rule, worth learning instead of a list: the region hides when you move the playhead, when you touch a marker, and when a sweep ends. Moving the playhead means moving it *in the music* — a click that places it, `Home`/`End`, the arrow steps, a `Tab` walk, `C`, any marker command that lands it. Moving the *picture* is not moving the playhead: pans, the wheel, every zoom and the overview strip leave it up. Changing what you are looking at is not moving it either: tab switches, the S/T and W/P switches, and a visit to the history view all leave it up. And trim's own gestures never hide it mid-work — dragging its bound parks the playhead, but that is the trim moving the cursor, not you leaving.

**The trim bar** (mouse). `Ctrl`+click moves the begin bound to that spot and `Ctrl+Shift`+click the end bound — at the release, and dragging instead of letting go carries the bound on like an endcap drag; a click that would land a bound on or past its partner moves nothing and says `A trim bound must stay inside its partner`. A plain drag on an endcap drags that bound (ten pixels of slack each side); a plain drag on the bar between them drags the pair as a fixed-width window; a plain click that never becomes a drag does nothing — nothing on this bar summons the region, that band being small enough to mean you have a pointer in your hand. When the window is wide enough, a small square outline marks its midpoint, purely informational. A window drawn narrower than about twenty-four pixels puts the two endcap slack bands over the whole bar, so the bridge drag needs a zoom in first — or the region, whose middle is as wide as the window is on screen. Release snaps each moved bound to its painted pixel column. Only one trim falls back to an untrimmed render: a window whose rendered span would round below one output sample — a refusal at the render, never a failed render. It says so on a card, `Trim window too small to render; rendering untrimmed`, when you enter target view with such a window standing and when you press either render chord.

### Grid iterations (`I`)

Both modes below are front ends for one workflow: render a spread of variants into `tmp/`, audition them in the render player (`L`), and load the one you want in place as the new baseline (`'`). They differ in what they vary. Both author warp tempo, so both belong to the warp column and answer `Grid iterations work on warp markers` / `BPM iterations work on warp markers` from the phase-reset column; both are refused on a read-only tab; and they are mutually exclusive — entering BPM iterations forces grid iterations off, clearing its brackets. The `Iterations` menu is their mouse home.

Grid iterations vary a marker's base tempo by a small additive offset. `I` toggles the mode, from either audio view; the mode and its brackets survive S/T switches. With the mode on, a warp marker's flag edit accepts an inline bracket appended after the tempo token: `+[<start>,<end>]` with `start <= end` — for example `+[-0.02,+0.00]`, which enumerates the offsets −0.02, −0.01, and 0.00. The range steps in 0.01 increments, inclusive; each bound is a signed two-decimal value within `[-4.00, +4.00]`, the sign and both decimals mandatory (`+0.00`, not `0`), and the base tempo plus either bound must stay inside the tempo bracket `[0.25, 4.00]` or the commit red-flashes and says so. Several markers can each carry a range; `Ctrl+Alt+R` then renders the full Cartesian product, one file per combination, into a batch folder under `tmp/`, and turns the mode off as it fires. A disabled marker is invisible to the sweep, as it is to BPM iterations: its range is kept but dormant — off its flag, out of the product, no cell named for it — and it counts again the moment the marker is re-enabled; the flag editor still shows and edits a disabled marker's range. The product is capped at 1,000 cells: a wider one is refused before any folder is made, with the mode and its brackets left standing so you can narrow them and fire again. A sweep that finishes short — some cell failed to write — says `Rendered N of M` on a card at the end, counting the cells it dispatched; a complete sweep, and one you cancel, say nothing. Both of those states — no bracket authored anywhere, and a product past the cap — grey the `Render` button while the mode is on, and its tooltip carries the sentence the key would answer with; `Ctrl+Alt+R` still says it on a card. A degenerate range like `+[-0.02,-0.02]` sweeps a single value. Brackets are session-only and never serialized; exiting the mode by any route clears them all. A tempo change never clears a bracket — the bracket rides the new base tempo, its bounds silently narrowing where needed so the base plus either bound stays in the tempo bracket. `Ctrl+N` does clear it: a marker turned into a pass has no tempo of its own to sweep, so its range goes with the ownership.

### BPM iterations (`M`)

**What it is for.** You have a stretch of the piece — say the first 36 beats of the recapitulation — and you want to hear it at 210, 211, ... 220 BPM to pick the one that sits right. Instead of computing a tempo factor by hand for each, you tell the program how many beats the stretch holds and the BPM range you want, and it renders one file per BPM into `tmp/` for the render player to audition; the one you like, you load in place as the new baseline.

**What a span is.** Every warp marker owns a section: from itself to the next marker that actually takes part in the render. Disabled markers don't count — they never close a section, so a section runs straight past them, and a marker followed only by disabled ones owns everything to the end of the song. The span you sweep is the run of sections owned by the markers you select: the first selected marker is the owner — its tempo is what gets rewritten — and the span ends where the last selected marker's section ends, at the next enabled marker after the selection or at the song's end.

**What happens per cell.** For each BPM in your range the program takes the span's measured length in the source and your beat count and works out the base tempo and the scale that reach it. The owner marker takes the base tempo, its own per-marker scale cleared; the scale goes to the cell's global `scale` setting. Every other enabled marker inside the span becomes a pass, so the whole span plays at one tempo. Then it keeps the rest of the piece in proportion: every enabled owning marker outside the span is rescaled by the same ratio the owner's tempo moved, rounded to the nearest cent — so re-tempoing one section re-tempos the whole piece uniformly instead of bending only the selected span. Disabled markers are untouched inside and out, and keep their old tempo for when you re-enable them. What the render normalizes to `1.00` on its own — the stretch before the first marker, a leading pass, a red-flagged reference — stays at `1.00` in every cell.

**The refusals** — the cards the program shows, each naming the first rule the selection broke:

- `BPM iterations work on warp markers` — the phase-reset column has no tempo to sweep.
- `BPM iterations work in source view` — the mode derives tempo from source durations.
- `Select the markers whose sections to sweep` — nothing is selected.
- `The selection no longer matches the markers` — a stale selection, a belt you should not see in practice.
- `Select one consecutive run of markers` — a disjoint set has no single-span meaning.
- `A label reference lies inside or at the end of the span` — a reference takes its tempo from its definition, so it can neither be rewritten nor bound the span.
- `The first selected marker must own its tempo and be enabled` — a pass, a reference or a disabled marker cannot own the span.
- `The first selected marker shares its frame with another` — a coincident stack renders as `1.00`, so a span owned from inside one cannot take a tempo.
- `Selected markers carry different tempos` — the span renders at one tempo, so every selected marker must be a pass or carry the owner's own value.

**The editor.** `M` on a valid selection opens the BPM editor on the bottom row; the field is authored as `<beats>@[<lo>,<hi>]` — for example `36@[210,220]`, meaning the span holds 36 beats and should render once at each integer BPM from 210 to 220 inclusive (BPM bounds live in `[10, 400]`). The beat count and the span's measured duration fix the source tempo, so each target BPM resolves to a concrete base-tempo-and-scale pair. `Return` renders the sweep — one file per BPM, into a numbered batch folder under `tmp/` — and closes the mode; `Esc` abandons it, and re-entering always opens on an empty field. A commit whose derived tempo or scale would leave its bracket at either end of the range, or whose rescaling would push any marker outside the tempo bracket, is refused whole with a red flash and a card — never clamped, which would silently mistune the span. The mouse road is Iterations → `BPM Iterations`.

Loading a BPM cell in place (via `'`) rewrites the span's tempo: the cell's frozen sidecars carry the rewritten markers, the computed global scale, and a `bpm` descriptor in the settings — for example `36 beats @ 220 bpm from 00:32.008 to 00:46.562` — recorded for provenance only; the engine never reads it, though like every engine setting it participates in render identity.

### Settings (`;`)

Bare `;` opens the settings prompt — the bottom row's editor, whose field takes a line typed as `key=value` — in a writable tab (a locked tab refuses; the prompt reaches the engine keys). The line splits on the first `=`, so the value may itself contain `=`. The prompt accepts any printable character; the free-text values (`title`, `bpm`, `notes`, `url`, `cover`, `projects_repo`) carry them verbatim, while keys and restricted vocabularies stay plain ASCII. A value the key does not take is refused at commit with a red flash and a card naming the reason.

Every key that can appear in a `.settings` file is settable here — the engine keys and every GUI-kind key (`follow`, `centered`, `waveform_magnification_level`, `active_audio_view`, `active_markers_view`, `active_tab_view`, and the per-tab `viewport_start` / `zoom` / `playhead_cursor` / `trim_begin` / `trim_end` / `read_only`) — plus the four per-device settings `gui_scale`, `projects_repo`, `projects_path` and `sync_path`, which are written to their own config file the moment you commit them. A GUI-kind commit behaves exactly like the key's own gesture: same code, immediate effect, not undoable, persisted on the next `Ctrl+S`. Keys for the inactive tab write that tab's stored state — which is also how you set a locked tab's trim from the unlocked one (`tab_b_trim_begin=...`). A trim bound committed onto or across its partner resets the pair to the song edges, exactly as the gesture does.

`Tab` after a key fills in that key's current value for recall and editing — type `notes=`, press `Tab`, and the line becomes `notes=` plus whatever is stored. `Tab` follows one rule in every bottom-row editor: it completes if there is anything to complete, and otherwise steps between the field and the buttons. `Return` (or `OK`) commits, `Esc` (or `Cancel`) cancels.

Four settings fields are provenance: carried in `.settings`, never read by the engine, but part of render identity, so editing one makes the next render fresh. `bpm` is written automatically when a BPM cell is loaded in place; `url`, `notes`, and `cover` are free text you type here. None is value-validated — any single line is accepted, empty included — though like every key the line itself must be present in the file.

### Rendering (`Ctrl+Alt+R`)

`Ctrl+Alt+R` is the pipeline's destination. With grid iterations on it renders the whole grid; everywhere else it is a single one-shot render of the current authoring state, written into the project's `render/` folder — the WAV deliverable named by the `title` setting, the folder created for you the first time, the frame-map pair going to `~/.cache` (see Output and the limiter). It is the only render that lands in `render/`; everything else goes into `tmp/` batch folders. A successful one also clears `render/` of every other pair, so changing `title` and rendering again replaces rather than accumulates. (The headless CLI writes the same deliverable but does no clearing.) A **failed** one says so — `Render failed: <reason>` on a notification card — and takes its own output with it: the deliverable wav and its `.fingerprint` are removed, so `render/` is left empty rather than holding a wav that no longer matches what you authored. The missing audio is the clue. A render you cancel yourself leaves the old deliverable alone; a successful render says nothing at all.

A render dispatch kills the running render and takes its place; `Esc` stops both the running render and any parked command behind it. A dispatch identical to the running render simply restarts it — cheaply, through the fingerprint reuse below. An output path that resolves to the source audio itself is refused rather than overwritten (change the `title` setting).

Before rewriting an existing same-title deliverable, the render checks that output's `.fingerprint` sidecar: if it exactly matches the current authoring inputs and the on-disk WAV identity, the render finishes immediately and writes nothing — the deliverable has proved it is already current. The `.fingerprint` records the exact render identity: source identity, markers, phase resets, the full settings block (provenance fields included), and trim bounds. It is not audio and is safe to delete; deleting it just prevents that output from proving itself current. Do not hand-edit it.

`Ctrl+Alt+Shift+R` renders one **miscellaneous cell**: the exact same render a plain-mode `Ctrl+Alt+R` would produce, but written as the next numbered WAV inside the most recent `N_miscellaneous` folder under `tmp/` — so one-off keepers accumulate as ordinary batch entries, auditionable in the player and loadable in place, instead of overwriting the deliverable. With grid iterations on it renders nothing and says `Turn off grid iterations to render one file`. The `Render` button's `Shift`+click is this chord.

The batch dispatches — the grid and BPM iterations — render into numbered folders under `tmp/` (`N_iterations` / `N_bpm`); `Esc` between entries drops the remainder.

### The render player (`L`)

`L` opens the render player: an in-program player for the WAV files this project has produced — open it, see the renders, start one, with no external program and no leaving the app; it is the same on the laptop, on the tablet, and in the car. It refuses to open with nothing to play, saying `Nothing to play: no renders under tmp/`.

A list appears across the window — always the same band, everything between the menu row and the bottom row, the menu row staying in view with `File` still open and the rest greyed — and the bottom row becomes the player's transport for as long as it stands. The list starts inside `tmp/`, at the project's batch folders; walk into them the ordinary way and the `Up` button — or `Backspace` — walks back out. `tmp/` is as far up as it goes, and the `Up` button is grey there. The deliverable in `render/` is not listed at all: it is the file you hand to someone else, and it carries no recipe to load in place. Each listing is read when you enter it. While the player stands it owns the whole window above the bottom row: every button is covered or greyed, and clicks anywhere else do nothing. The one exception is the `File` menu, which stays open above it — `Quit` and `Synchronize to External Storage` work from there, `Open Project` does nothing. `Ctrl+S` and `Ctrl+Q` are the only keys that reach past the player — saving still works, and `Ctrl+Q` quits with the player closing first. On the tablet, closing it is the `Close` button, and File → `Quit` is the only way to quit from in there. A running render carries on in the background while you listen. `L` and `'` both work on a locked tab — playing a render changes nothing; loading in place is what the lock refuses.

**A click opens the row** — one click or one tap: a folder is entered, a WAV starts playing from its beginning. `Return` does the same to the highlighted row; `Up`/`Down` move the highlight, the wheel scrolls a row per detent, and `Backspace` — or the `Up` button on the transport row — goes up a folder. What is playing and what is highlighted are two different things: the playing item keeps its own place, wears the play glyph on its row, and goes on playing while you look through other folders.

The transport row reads left to right: skip back (`Home`), `Play`/`Pause` (`Space`), skip forward (`End`) — the same three buttons on the same three keys as the main window's transport — the progress bar, the clock (`<position> / <length>`, in the toolbar clock's own monospace), the `Toggle Repeat One` lamp (`R`), `Up` (`Backspace`, grey at `tmp/` itself), then load in place — a checkmark, the same one the icon row wears for the act (`'`) — and close, an X (`Esc`), at the right. Every button on the row is an icon; hover one for its name and key.

- `Play`/`Space` goes wherever the highlight is pointing, and falls back on the transport: on a folder it opens it, on a WAV that is not the one playing it plays that file — even in the middle of something else — and on the playing file itself, or with the highlight nowhere, it pauses what is playing, resumes what is paused, and starts the current file from its beginning when nothing is going. So `Return` is the spatial key and `Space` the temporal one, and they part company in one place only: on the file that is already playing, `Return` restarts it and `Space` pauses it. The button says which: it wears the pause bars only when a press would pause, and the play triangle whenever a press would play something.
- At the end of a folder the player simply stops on the last file, at its beginning, and the next `Play` plays that last file again. To hear the folder from the top, `Shift+Home` (or a `Shift`+click or long press on the skip-back button) goes to its first file.
- `Home` goes to the start of the playing file — and inside the file's first three seconds, to the *previous* file of its folder, the way a car stereo does it, so a second `Home` steps back a track however slowly you press; the button's tooltip reads `Previous File` or `Go to Start` accordingly, and the play button's reads `Open Folder`, `Play`, `Pause` or `Resume` for whatever its press would do. The two skips' `Shift` lines name the first and last file of the *playing* folder and disappear while the playing file already is that file. `End` goes to the file's end. What happens next depends on what the transport was doing: while the file is playing, it plays its last frames out and the next file in the folder starts by itself, exactly as it would at a natural finish; while it is paused, `End` only moves the rest, and the next `Play` starts this file again from its beginning; with nothing playing, the seek is refused. Auto-advance never crosses into another folder and never wraps — at the folder's last file it stops, the item back at its start.
- `Shift+Home` / `Shift+End` — or a `Shift`+click or long press on the two skip buttons — jump to the first and last file of the playing item's folder.
- Whenever the player moves to another file on its own, the highlight follows it — as long as the folder you are looking at is the one playing; if you have walked elsewhere, your place is left alone.
- `Toggle Repeat One` is a lamp: while lit, the playing file starts again at its own end instead of moving on. It is the one thing in the program that plays anything twice by itself, and it is off every time the player opens. There is no repeat-all.
- The progress bar is the desktop's own slider: click the track and the sound jumps there; grab the handle and drag, and it jumps at the release. `Left` / `Right` step five seconds. Every seek is refused while nothing is playing or paused — a freshly opened player, or one resting after a folder's last file — and refused with nothing loaded at all: silently in both, the resting bar and the zeroed clock being the answer.
- `Esc`, `L`, or `Close` closes the player and hands playback back to the view you were in.

A WAV not at the source's own sample rate and channel count is refused with a line of its own rather than converted. In the car, the point is to start a render parked, without leaving the program: on the tablet the head unit's buttons work over Bluetooth — play/pause, previous/next (the player's two skips, so `previous` restarts the track and, inside its first three seconds, steps back one), stop (the sound stops and the file goes back to its beginning, so the next `Play` starts it from the top — it never changes track), and seeking — and the head unit shows what is playing.

### Loading a render in place (`'`)

Loading a render in place makes that render's recipe your new authoring baseline. Outside the history view, `'` opens the render player, and the player's load-in-place button — the checkmark, or `'` again on the highlight — does it on the highlighted batch cell. It asks first: `Load '<entry>' in place?` with `OK` and `Cancel`, `Return` answering `OK`. Only the batch cells under `tmp/` can be loaded, and they are the only thing the player lists — the deliverable in `render/` carries no recipe. When it succeeds the player closes. Inside the history view `'` is the same verb over a different thing — the checkpoint or session state you are looking at (see Checking history).

On a successful load you get the entry's **recipe** and nothing else: its markers and its engine settings, applied on top of what you have. Everything about where you are stays — the view, the marker column, the tab, the window, your trim, every preference, and `Grid iterations` if it is on: the loaded markers carry no brackets, so its flags read blank until you type some, and `Ctrl+Z` brings the old markers back with theirs. The whole rule in one sentence: **a load in place writes exactly what one press of `Ctrl+Z` takes back.** Trim is outside it for that reason — trim has no undo, `Shift+[` being its recovery — so a load in place never moves a bound you set. The load is one cross-file undo entry, so `Ctrl+Z` puts back what you had, and the history view's session walk will show you what the load changed.

After it succeeds, `tmp/` is wiped — the batch outputs are stale once the baseline changes; the render you loaded survives through the render cache. The folder goes to the desktop trash when `gio trash` is available, so a batch you did not mean to lose can be restored in one piece; where the trash cannot take it, the folder is deleted outright with one stderr line saying so.

A load is refused while a render is running or parked (`Cannot load in place while a render is running`) and on a locked tab (`This tab is read-only`); if the entry's WAV has gone missing or a sidecar is malformed, nothing changes and the notification names the reason and the file.

### Checking history (`H`)

The project's working checkpoints live in a git repository — the `projects_repo` setting names which one, and the program reads the local clone, so nothing here needs a network or a credential until the push. **On the tablet there is no history view at all**: the Android build carries no git, so `H` answers `History is unavailable: <reason>` on a card — the reason being that git could not be asked — and the view's own buttons stay grey. Checkpoints are a laptop act. Bare `H` opens the history view: the marker lane stops showing the session's markers and shows the *difference* between a committed checkpoint of this piece and something else. The view is read-only and silent — it plays nothing, renders nothing, and none of the authoring gestures reach a marker or a bound; its three deliberate writes are the revert (`V`), the load in place (`'`) and Save and commit (`Ctrl+S`), all below. Panning and zooming work as ever, each tab keeps its own window, and entering and leaving move nothing at all.

Two choices set what the comparison is. **Which history** is the `Git` / `Session` radio pair (`G`): `Git` reads the committed checkpoints; `Session` reads your own session, counted as states — every state `Ctrl+Z` / `Ctrl+Shift+Z` can reach is a stop on that walk, plus the one you are standing in, so a fresh file reads `1/1` and one edit plus an undo reads `2/3`. **How** is the `Cumulative` button (`U`): off is the iterative reading, which compares the viewed checkpoint against the next one toward the present — what happened after this checkpoint, one step at a time; on is the cumulative reading, which always compares against what is authored in memory right now — how your session differs from that checkpoint. The cumulative bit is remembered across visits; the walk starts every visit on `Git`.

In both readings green is the newer side and red the older: green flags are markers the newer side has, red flags markers the older side had, and a marker present in both at the same frame with a different value is one double-width flag, red half then green half, old value on the left. Warp flags carry the tempo in the sidecar's own spelling; phase resets carry the bare sign. A just-loaded, untouched project shows an empty lane — your session and the newest checkpoint agree, which is exactly what you want to see after committing.

`,` steps to an older member and `.` back toward the newest, holding either walks steadily; `Shift+,` / `Shift+.` jump to the ends. The two arrow buttons in the icon row are those keys. The state text's left end names where you are in the walk, with the commit's short id on the git readings, and — only when the checkpoint's `scale` differs — the two values old and new. `Tab` / `Shift+Tab` walk the difference flags, `C` recentres on the brightened one, `Ctrl+Shift+Tab` marches the differences on both tabs. `Home` / `End` jump to the piece's ends here — the view is about the whole piece. The `A`/`B` tabs stay the tabs, `Ctrl+Tab` switches them, and the S/T and W/P switches work — a difference is line-shaped, and each view shows one column of it.

Differences can be selected and put back. A plain click on a diff flag brightens it and lands the playhead there; `Shift`+click ranges, `Ctrl`+click toggles. `V` — the revert button — applies the selected differences *backwards* into your session and closes the view: a green flag's marker is deleted, a red flag's put back as the checkpoint had it, a two-colour flag's set back to the checkpoint's value. It is deliberately unguarded — reverting half of a change is exactly as possible as reverting all of it, and that freedom is the point. The whole act is one undo step. A read-only tab refuses it, and `'`, but not Save and commit.

`'` inside the view asks about the member you are looking at — `Load '<id>' in place?` — and its `OK` loads that checkpoint's (or session state's) markers and engine settings in place: the same in-memory load a render entry takes, one undo entry, nothing written to disk, nothing of the checkpoint's trim, tabs or preferences; the view closes as it loads. It is not a rewind — `Ctrl+Z` immediately after brings back what you left, which is what makes walking to the very first state and loading it a safe way to audition where you started.

**Save and commit.** `Ctrl+S` inside the view — the `Save` button, wearing the commit glyph — saves and then commits the current authored state as a new checkpoint. It asks one thing first: an editor opens with the commit message already filled in (`Update <folder name>`), selected so typing replaces it; `Return` commits under whatever it holds — the ordinary case is a single keystroke, the useful case is writing what you actually changed — and `Esc` abandons. Then the program saves exactly as `Ctrl+S` would, the view closes, and everything after — writing the sidecars into the repository's `projects/` folder, committing, pushing — happens in the background; you keep working. If any of it fails, a notification with the red error glyph appears and *stays* until you close it — nothing committed, committed but not pushed, or not confirmed — with the long version on the terminal. The fix is in the terminal, deliberately: a checkpoint that committed but did not reach the remote is published with `git push`; the program does not retry for you. Only one checkpoint publishes at a time: while one runs, `Save` is greyed everywhere, its tooltip reading `Committing the checkpoint (Ctrl+S)`, and `H` will not open the view; it comes back by itself, and quitting waits for it. The button greys too whenever the session's markers and `scale` already match the newest checkpoint — the answer covers the whole piece, both columns.

Only checkpoints the program could actually load are shown; ones that would refuse (incomplete sidecar sets, files predating the current format) are left out of the walk, the terminal noting how many were hidden. If that leaves nothing, the view opens on an empty walk — `0/0`, blank lane — and `Save and Commit` is live there: commit once and the next `H` reads it. A piece never checkpointed opens the same way, and its first Save and commit starts the history. The checkpoints live under the repository's `projects/` folder, one folder per piece, sidecars named by the source's basename; the piece's folder there is where its history goes. Moving the projects home to another git host takes two steps: point the clone at the new remote (`git remote set-url origin <new url>`) and edit `projects_repo` to match. The program speaks only to local git and whatever that remote is — no GitHub dependency, no account, no token.

### Undo and redo

`Ctrl+Z` undoes and `Ctrl+Shift+Z` redoes; settings edits and marker edits share one history. Undo and redo show you what changed: the touched markers are re-selected, and the view goes back to where the edit was made — the tab, the audio view and the marker column are all put back as they were when you made the change, the playhead keeping its place in the music while the map and the views are restored under it. Then the restore lands on what it brought back: a single touched marker gets the full marker-click treatment — playhead landed on it, flag brightened, viewport recentred only if it was offscreen; a group re-selects whole and lands the playhead on its earliest touched member, scrolling or zooming out just enough to show the set. A settings-only restore lands nothing and leaves the playhead where it stands.

Trim is excluded. Held nudges and tempo steps coalesce: a held run is one undo entry, and rapid separate taps of the same key merge when they land within about half a second with the same markers selected on the same tab; a slower press, one after the selection changed, or one after a save opens its own entry. A merged run that ends exactly where it started leaves no entry at all — tap `Right` then `Left` inside that window and the pair cancels, the history and the unsaved-changes dot going back to what they were before the first tap. What it does not put back is the redo branch: the first tap of the run discarded it, as any edit made partway back through the history does.

### Esc

`Esc` does exactly nine things, and nothing else anywhere. In rank order: it ends a text-selection drag inside an editor (that same press goes on to close the editor); it closes an open editor without committing; it dismisses a prompt, taking its rightmost answer; it dismisses an open menu; it closes the render player; it closes the project list; it closes the AV sync panel; it cancels all render work — the running render, a parked command behind it, and a pending target-view preview; and, with none of those standing, it clears the whole notification stack, red cards included. An open editor or prompt takes priority, so the first `Esc` closes that and the next one cancels render work. `Esc` with a modifier does nothing anywhere — see Notifications.

While a pointer gesture is in flight `Esc` is swallowed like every other key and answers `Keys are ignored during a drag`: gestures have no cancel — let go and the gesture commits what stands, then `Ctrl+Z` takes it back (trim, which sits outside undo, commits for good). With nothing open, nothing rendering, nothing being dragged and no card standing, `Esc` is a no-op: it does not deselect markers, does not move the playhead and does not touch the trim region. To leave a selection, click the waveform or press `Home`/`End`; to put the region away, press `[`.

### Mouse, touch, and the on-screen keyboard

One rule organizes the pointer: the whole waveform, the ruler, and the marker lane's empty stretches are a single navigation surface, and every gesture means the same thing anywhere on it. Plain drag pans; a plain click that never becomes a drag acts at the release — placing the playhead on the upper half, ruler and lane, scrubbing on the lower half; `Shift`+drag sweeps a trim window; `Ctrl` turns the drag into the zoom, live at any moment of it. The right button does nothing anywhere; `Alt` binds the wheel and nothing else on the mouse. While the trim region is showing, a plain drag inside it slides the window and a drag on one of its bounds moves that bound — the one thing that outranks the pan — while the ruler and the marker lane stay plain navigation surface even where the region reaches across them.

The pointer cue tells you what a press would do, using your own cursor theme: a hand on the navigation surface, a magnifier with `Ctrl` held, edge arrows on the overview box's and trim bar's bounds, the resize arrow on a marker's flag and on anything that slides, an I-beam on editable text, the plain arrow wherever a gesture would not run. A live drag keeps the cue it started with; the pan and zoom drags hide the cursor and capture it for unlimited travel, wrapping it at the waveform's edges, and hand it back where it had got to.

`E` **is the left mouse button**: pressing it presses the button at the pointer position, holding it holds (so `E`+motion drags, modifiers riding along), releasing releases — except while a text editor is open, when it types the letter instead.

On a touchscreen, one finger is the mouse — a tap is a left click at the moment the finger lifts, and every gesture, refusal, and rule above applies unchanged — with three additions. A one-finger drag on the navigation surface pans directly, the way it does on a phone. Hold a finger still for about half a second and then drag, and you sweep a trim window — the mouse's `Shift`+drag by another route (a hold released without moving just places the playhead). And two fingers pinch-zoom, and only zoom: the pinch takes hold of the audio under the two fingers' midpoint the moment it registers and scales about it — the same pivot the mouse's `Ctrl`+drag holds, marked by the same dim stem — while sliding both fingers together moves nothing, panning being the one-finger drag. Add and drop the second finger as often as you like within one touch. The two slim lanes — the overview strip and the trim bar — are one-finger surfaces: a second finger there is ignored entirely. A showing trim region works by finger exactly as by mouse: drag inside to slide, drag a bound to move it, tap the upper half to put it away; the **Show trim region** button and its long press (`Shift+[`) are the way in and the way out.

On a device with no keys of its own, opening any text editor brings up an on-screen keyboard across the bottom of the window, and it goes away when the edit ends. Every key acts the instant you touch it, and the keys that repeat on a real keyboard repeat here too — everything that types, and `Backspace` — held down at the program's own repeat rate. The one-shot commands do not: `Return` and `Esc` act once however long you hold them, and `Shift` is one-shot by design — tap it and the next letter is a capital; `&123` swaps to the digits and the punctuation the program's own grammars use; `Return` commits the edit and `Esc` throws it away, exactly as they do on a keyboard. The render player's list and the project list use that same band — no list needs typing, so a list and the keyboard are never up together. On the laptop this keyboard does not exist at all.

### Migrating an older project folder

A checklist for bringing a folder from before the project model — a bare `.warpmarkers` / `.phaseresetmarkers` pair, possibly still in the legacy `MM:SS.mmm` timestamp form, and a `renders/` folder or a stray output wav in the root — into the current layout:

1. Make a folder for the project directly under `projects_path`, named for what you want the project called.
2. Copy the source wav into it.
3. Copy the `.warpmarkers` and `.phaseresetmarkers` files in beside it.
4. If those sidecars are still timestamps rather than frames, build the conversion tool. It is not part of the product build and no executable ships in `tools/` — that folder is its source. From the project root:
   ```bash
   cmake -B build-tools -S tools && cmake --build build-tools
   ```
5. Convert the sidecars — the warp file first, then the phase-reset file, since the phase-reset conversion needs the completed warp map to land its positions correctly:
   ```bash
   build-tools/migrate_sidecar_to_frames <sample_rate> <stem>.warpmarkers
   build-tools/migrate_sidecar_to_frames <sample_rate> <stem>.phaseresetmarkers <stem>.wav
   ```
   `<sample_rate>` is the source's own rate (`44100`, for instance); the tool rewrites each file in place and keeps the untouched original beside it as `<path>.bak`.
6. Delete the old `.settings` rather than bringing it across — it is all but certain to carry a key the current schema refuses (see below), and the first open writes a fresh template. Re-enter `title`, `notes`, `url`, and `cover` by hand from the old file's lines.
7. Rename any `renders/` folder to `tmp/` (`mv renders tmp`).
8. Move any `<title>.wav` and its `.fingerprint` sitting in the project root into `render/`. Move only the current `title` setting's pair: `render/` is kept to that one deliverable, and anything else you put there is deleted the first time a render publishes into it. Keep keepers somewhere else in the project.

A `.settings` that still carries `gui_scale`, `audio_player`, `projects_repo`, or `playback_speed` refuses to load outright — an unknown key is an unknown key; the fix is deleting those lines by hand, not migration. The per-device config file has the same strictness in both directions: one carrying an `audio_player=` line stops the program at startup — delete the line — and one missing its `sync_path=` line stops it the same way — add the line by hand (with the program quit), a bare `sync_path=` on a machine with nowhere to synchronize to, and then set the real path from `Settings` → `Sync Path` once it runs.
