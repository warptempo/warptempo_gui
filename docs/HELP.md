# warptempo_gui

warptempo_gui time-warps an audio recording toward the tempos you choose — built for taking a commercial orchestral recording to a historically informed tempo reading, phrase by phrase, by ear. This is the user guide: install and build, first run, the conceptual model and the output contract, and the interface reference. Read the conceptual model before the reference; the reference is where every key and gesture lives.

One habit the program is built around: when a key or a click refuses, the program normally says why, in a small card at the top right of the window. What stays silent is a chord with no command behind it, and a **one-dimensional command already at its state** — one that moves a single thing in a single place, so one glance at that place already tells you nothing happened. The playhead already at the end it would jump to, a walk already at its last marker or its last checkpoint, a ladder step already at its limit, a tempo already at the bracket's edge, the selector for the view you are already in, a click on the radio button already selected: all silent. A command whose effect would have spread across the screen still says why even with nothing to do — undo and redo over an empty stack (a held `Ctrl+Z` that runs out of history just stops), a tempo step over a selection one marker cannot take. So silence with no visible change means the press was either unbound or had nothing left to change in the one place you were watching. The manual therefore does not list every state in which every command refuses — the program tells you, at the moment it matters. What the manual gives you instead is what each thing is *for*, how it works, and the refusal sentences worth knowing in advance.

## Dependencies

Build requires a C++23 toolchain (GCC 12+ or Clang 16+), CMake 3.20+, pkg-config, and the development headers for fftw3. That is the complete dependency set for the headless render interface (`warptempo_cli`); none of the GUI packages below are needed for it.

The default GUI build — the Linux desktop product, and what the rest of this guide describes — additionally requires the wayland-scanner tool and the development headers for cairo (including its FreeType backend, cairo-ft), HarfBuzz, wayland-client, wayland-cursor, wayland-protocols, libxkbcommon, and JACK. JACK can be the native jackd2 server or a PipeWire-shimmed JACK provider (modern distros default to the latter).

The `std::expected`-based parser is what pins the compiler floor at GCC 12 / Clang 16. On distributions whose default compiler is older — Ubuntu 22.04 ships GCC 11, for example — install a newer toolchain (`g++-12` or later) and select it with `-DCMAKE_CXX_COMPILER=g++-12`.

Arch Linux:

```bash
sudo pacman -S base-devel cmake pkgconf \
    cairo harfbuzz fftw \
    wayland wayland-protocols libxkbcommon \
    pipewire-jack
```

Debian / Ubuntu:

```bash
sudo apt install build-essential cmake pkg-config \
    libcairo2-dev libharfbuzz-dev libfftw3-dev \
    libwayland-dev wayland-protocols libxkbcommon-dev \
    libjack-jackd2-dev
```

The libwayland-dev package on Debian ships wayland-scanner and the client / cursor headers in one piece.

Fedora:

```bash
sudo dnf install gcc gcc-c++ cmake pkgconf-pkg-config \
    cairo-devel harfbuzz-devel fftw-devel \
    wayland-devel wayland-protocols-devel libxkbcommon-devel \
    pipewire-jack-audio-connection-kit-devel
```

For a headless build — `warptempo_cli` with no GUI — only the core dependencies are needed. Omit the cairo / HarfBuzz / wayland / libxkbcommon / JACK packages and configure with `-DWARPTEMPO_BUILD_GUI=OFF` (see Build). On Debian / Ubuntu that reduces to:

```bash
sudo apt install build-essential cmake pkg-config \
    libfftw3-dev
```

A Wayland compositor is required at runtime for the desktop build — there is no X11 backend — and it must offer server-side window decorations (the xdg-decoration protocol): the GUI exits with an error at startup if the compositor does not offer it. labwc, the compositor the program is developed on, always can; so can the other wlroots-based compositors (sway, Hyprland) and KDE Plasma. GNOME's compositor does not implement the protocol, so the GUI will not start there. The headless CLI needs no compositor and no audio server; it reads and writes files only.

Windows (WSL2): the project builds and runs under WSL2 with a Debian or Ubuntu userland — install the Debian / Ubuntu dependencies above inside the WSL distribution and build normally. The headless CLI behaves as on any Linux host. The GUI is not supported under WSL: WSLg provides a Wayland compositor but routes audio through PulseAudio, and the application has no non-JACK audio path.

macOS is not supported: the GUI has a Wayland backend and an Android one, and no macOS backend at all. The headless CLI is neither built nor tested there and carries no support claim either.

## Build

Standard out-of-tree CMake build from the repository root:

```bash
cmake -B build -S .
cmake --build build -j$(nproc)
```

The default build produces one binary: the `warptempo_gui` application — a Cairo/Wayland front end over the in-tree parser, engine, prepost, and audio-io sources. All audio container I/O is in-tree, WAV only, with no third-party codec. There are no library archives; each binary compiles the shared source lists directly. `-O3 -march=native -ffp-contract=off` is always on for GCC and Clang, so every binary is tuned for the host CPU and is not portable across machines — rebuild on the target host. A rebuilt binary is not a new rendering reference, though: with the same compiler and the same libraries underneath it, a fresh build renders exactly what the previous one did, byte for byte (see Reproducibility).

One opt-in binary, default OFF: `warptempo_cli` (`-DWARPTEMPO_BUILD_CLI=ON`) is the headless insurance render path — exactly the terminal `Ctrl+Alt+R`. It takes just the source audio path, reads the project's `.warpmarkers`, `.phaseresetmarkers` and `.settings` beside it (all three required; the GUI creates them on a new project's first open; other files beside the audio are ignored), and writes the warped WAV the GUI would render for the same project — `<title>.wav` in the project's own `render/` folder, exactly where the GUI publishes its deliverable (the folder is created for you the first time, as it is in the GUI) — byte-identical to the GUI by shared pipeline stages. The trim applied is the active tab's (the persisted `active_tab_view` key), matching the GUI. Like the GUI, it also drops the render's frame-map pair into `~/.cache/warptempo_gui/<pid>/` (see Output and the limiter).

To build the CLI on a headless host that has none of the GUI's Wayland / Cairo / JACK packages, add `-DWARPTEMPO_BUILD_GUI=OFF -DWARPTEMPO_BUILD_CLI=ON`; the GUI dependency discovery is skipped entirely.

**Android.** The same GUI also builds as an Android APK — one interface over two backends, not a second program. `bash android/app/build_apk.sh` cross-compiles it against the static dependencies in `android/prebuilt/` and packages a signed APK; `adb install -r android/app/build-android/warptempo.apk` puts it on the device. That build needs the Android SDK and NDK, installed outside the repository as `android/toolchain/` expects. Nothing of Wayland or JACK is involved there: the window comes from the Android framework and the audio from AAudio. Everything this guide says about the interface holds on both, and where a gesture or a behaviour differs the text says so.

There is no `make install` target. The binary is self-contained: copy it anywhere on `$PATH` to make it available system-wide.

```bash
install -Dm755 build/warptempo_gui ~/.local/bin/warptempo_gui
```

A `.desktop` file is shipped in `packaging/warptempo_gui.desktop`. To register the program with the system's application launcher and as a handler for audio files:

```bash
install -Dm644 packaging/warptempo_gui.desktop \
    ~/.local/share/applications/warptempo_gui.desktop
update-desktop-database ~/.local/share/applications
```

The shipped `.desktop` file uses the freedesktop `audio-x-generic` icon name, which resolves to whatever the active icon theme provides — no icon file is bundled. Replace the `Icon=` line with a different freedesktop name or an absolute path to a custom SVG to override.

## First run

`warptempo_gui` takes no argument, or one.

With no argument, it opens the project it had open last — the device config's `last_project` — or, when that name is empty or its folder is gone or is not a project by the folder rules below, the first valid project folder under `projects_path` in name order (what is judged is the folder's SHAPE and its name, never what is written inside a sidecar — a folder that looks like a project and holds a broken sidecar is still the one chosen, and the load then refuses with that file's own reason); with no valid project at all, it refuses on stderr (`No project under <projects_path>`) and exits. This is the tablet's only road in, and the laptop's own bare launch.

With one argument, the argument must be a project's source `.wav` — a file inside a project folder that sits directly under `projects_path`, resolving as that folder's source; anything else refuses with the reason on stderr.

```bash
warptempo_gui "path/to/source.wav"
```

**The project folder model.** `projects_path` is a per-device setting (below) whose subfolders are the projects, one folder per project; the folder's name is the project's name. A folder is a project one of two ways: it carries a sidecar set — any of `<stem>.warpmarkers`, `<stem>.phaseresetmarkers`, `<stem>.settings` — naming its source by that shared stem, and `<stem>.wav` exists beside them; or it carries no sidecar at all and holds exactly one `.wav`, which makes it a new project — that wav is the source, and the first open writes the three sidecar templates beside it. A folder that carries some sidecars must carry all three: a missing one refuses to open, naming the file, and nothing is written for you. Any other shape refuses to open with the reason stated. A `.wav` in the project root that is not the source is a leftover — the refusal names it and tells you to move it into `render/`. A folder's name also has to be one the program can remember: the name of every opened project is written into the config's `last_project=` line, which holds one plain folder name — so a folder called `.` or `..`, one whose name begins or ends with any ASCII whitespace byte — space, tab, newline, vertical tab, form feed or carriage return — or one containing a line break is not a project on any road. Rename the folder and it is a project again.

Two folders beside the source hold everything the program writes, and neither is itself a project or a candidate source:

- `render/` holds the deliverable — `<title>.wav` and its `.fingerprint`, written by the render command (`Ctrl+Alt+R`; the CLI writes to the same place) — and nothing else: the folder is kept to the current `title` setting's one pair, and any other `.wav` or `.fingerprint` in there is deleted the next time a render publishes into it, so renaming the piece does not leave the old deliverable lying around. A render that *fails* clears the pair instead of publishing one, so an empty `render/` after a failure is the expected state.
- `tmp/` holds the disposable batch renders — the grid and BPM iterations and the miscellaneous cells — that the render player (bare `'` or `L`) walks and its `Load in Place` button loads. `tmp/` is the whole of what the player shows: it never lists `render/`, the deliverable there being for sharing outside the program rather than for auditioning in it.

Source inputs are stereo WAV only, 16- or 24-bit PCM, at 44100 Hz or above — anything else refuses to load with the reason on stderr. Material in any other format or layout — FLAC, Opus, MP3, mono — is converted once at acquisition with an external tool (e.g. ffmpeg), and the converted WAV becomes the project source.

The project's data lives in three sidecar files beside the audio, named by appending `.warpmarkers`, `.phaseresetmarkers` and `.settings` to the audio file's basename. All three are required, even when empty, and every save writes all three. They are program-written and strictly validated at load: a hand-edited or corrupt sidecar fails the load with the first error on stderr. Other files beside the audio are ignored.

**Per-device settings.** Six settings are about the computer you are on rather than about the piece, and they live in their own small file: `$XDG_CONFIG_HOME/warptempo_gui/config` (`~/.config/warptempo_gui/config` when that variable is unset). It holds exactly six lines, written in this order:

| Key | What it is | Written by |
|---|---|---|
| `gui_scale=` | the interface's rendering scale, an integer percent from 50 to 350 | the settings prompt, at commit |
| `max_waveform_height=` | the waveform's maximum height in unscaled pixels, 0 to 9999 (`0` removes the cap) | the settings prompt, at commit (in force at once) |
| `projects_repo=` | the repository that is your projects home for the history view | the settings prompt, at commit |
| `projects_path=` | the absolute folder whose subfolders are the projects | the settings prompt, at commit (in force for the next `Open Project`, and for the next launch once the file is written) |
| `last_project=` | the folder name opened last | the program itself, at every successful open |
| `sync_path=` | the folder Synchronize to external storage mirrors into | the settings prompt, at commit |

The first run on a machine writes the file with values that suit it — on the laptop `gui_scale=100` and a `projects_path` under the home directory, on the tablet `gui_scale=225` and the app's own external files directory — with `max_waveform_height=500` on both, `last_project=` and `sync_path=` blank. `max_waveform_height` caps how tall the waveform grows, scaled with `gui_scale`, and `0` removes the cap so the waveform takes all the height the window has. Both path keys are absolute paths that may not begin or end with whitespace; `sync_path` may be left empty, which means this machine has nowhere to synchronize to yet. The five keys other than `last_project` are edited in the app: `Settings` → `GUI Scale`, `Max Waveform Height`, `Projects Repository`, `Projects Path` or `Sync Path` opens the settings prompt on that key with its current value filled in, and on the two path keys `Tab` completes the folder you are typing against the disk, one folder name at a time. A value the key refuses turns the field red and says why on a notification; a `projects_path` commit is kept for the next `Open Project` and the next launch, the open project staying open, and says so — unless the file could not be written, which it tells you instead, the new folder then holding only until you quit. The file can also be edited by hand — quit first: the program keeps its own copy and rewrites the whole file at every commit, so a line edited while it runs is overwritten by the next one. The file is strictly validated exactly as a sidecar is: a hand edit that breaks it stops the program at startup with the offending line named on stderr, and no window opens. The point of the arrangement is that a project synced between two machines carries no opinion about either one's screen, and each machine remembers its own place in your work independently. `Ctrl+S` has nothing to do with this file — each key writes at its own commit.

On launch, the program opens a window, reads the sidecar files, and presents the source waveform across the full window width. With no sidecar files present, you start with a single warp marker at frame zero carrying tempo `1.00` and no phase reset markers. With sidecar files present, the prior session is restored verbatim — viewport, zoom, playhead, active view selectors, and all marker positions and flags.

**Opening another project.** `Ctrl+O`, or File → `Open Project`, brings up a list of your projects across the window below the toolbar, with `Cancel` at the right of the bottom row under it. It owns the window the way the render player does: everything between the icon row and the bottom row is the list, and the menu row and the icon row stay in view above it with `File` still open and the rest greyed — the same partition the history view has always had. There is nothing to type: the list holds one row per folder that is actually a project (a folder that will not open is simply not in it). Click a project to open it — one click, or one tap. `Up` and `Down` move the highlight and `Return` opens the highlighted one; those are the same act as the click. The list is read when it opens; the highlight starts on the project you have open. Scroll it with the wheel, or drag it with a finger. Opening reopens the program around that folder, exactly as choosing a project at startup does; an unsaved tab asks first, the same prompt `Ctrl+Q` raises; opening the project already open just closes the list, with nothing to say — the window title names it. A folder that turns out not to open reports the reason in a notification and leaves the list open; `Return` on an empty list — every folder under `projects_path` refused by the model — answers `Choose a project first`. `Esc` or `Cancel` closes it. On the tablet the gesture is two taps: File → `Open Project`, then tap the project.

**Reverting to the saved project.** `Ctrl+Alt+O`, or File → `Revert`, reopens the project you have open exactly as it was last saved, throwing away unsaved changes and the undo history; if anything is unsaved it first asks `Discard unsaved changes and reload?`, with `OK` focused.

**Synchronizing to a stick.** `\` — the backslash key — or File → `Synchronize to External Storage` mirrors the open project's rendered wav files into the folder `sync_path` names — on the laptop that is the stick's own mount folder, something like `/run/media/<you>/<label>` — under a folder of the project's own name: whatever wav files the project's `render/` folder holds, directly, plus each batch of renders under its own folder exactly as it sits in the project; wav files only. What it copies is simply what those folders contain, so the stick ends up holding the same wav files the project does. It is a mirror of that one folder and nothing more: anything already there that is not part of the current set is deleted afterward, so running it again after a fresh render brings the stick back in step rather than piling up old copies, and any other project's folder on the stick is left alone. Renaming the piece leaves the old rendered wav in place until you render again — a render clears it from `render/`, and the next synchronization then clears it from the stick. While it runs, the bottom row says `Synchronizing...` beside the clock — unless a render is saying something there, which wins for as long as it does, the word coming back the moment the render's line goes — and the word leaves for good as soon as the copying is done. **Quitting waits for it.** `Ctrl+Q`, `File` → `Quit`, the window's close button and the tablet's back gesture all refuse while a synchronization is running and say `A synchronization is already running` instead: the copying cannot be stopped part-way, so the program will not let the window go while it is happening. It is seconds; press again when the word leaves the bottom row.

It goes where you told it and looks for nothing: set `sync_path` once per machine, in `Settings` → `Sync Path` (or by hand in the config file, with the program quit). If it is empty, a notification says `sync_path is not set` and nothing runs. The folder has to be there — the command never creates it — so with the stick unplugged or the path mistyped, a notification names the path and says it is not a directory. Anything else that goes wrong stops the act where it stands, with the offending path in a notification and the full path on the terminal. The order of operations protects your data: nothing is deleted until every file has copied, and a file being replaced is written beside its old copy and swapped in only once it has arrived whole — so a stick pulled mid-copy costs you the new version, never the old one. Running the command again is the retry, and it mirrors from wherever the last one stopped. When it works it says nothing at all: the command is quiet on success exactly as a finished render is, and the only thing it ever tells you is what went wrong. If anything on the way is a symlink rather than a real folder or file, the act says so and does nothing — it will not read, write or delete through one, on either side. And because the stick cannot tell `My Title.wav` from `my title.wav` while your disk can, two such files heading for the same folder on the stick would land on one name: the act names both and does nothing rather than shipping one of them and calling it a success.

On the tablet, a stick has to be mounted where apps can see it, and the current One UI build does not mount an OTG stick that way — there is no folder to point `sync_path` at, so the tablet's stays empty and the command refuses there.

The repository's `projects/` directory ships reference movements with complete sidecar files. The Symphony No. 40 first-movement directory (`projects/550 - 1/`) is the recommended first load — it exercises every form and syntax used in the project. The audio itself is not included (the corpus is commercially licensed); you supply the source recording and place it in the project directory under the basename the sidecar files expect. See Projects at the end of this document.

## Conceptual model

### The engine

`warptempo_gui` drives a phase vocoder — a faithful, centered implementation of Prusa-Holighaus phase-gradient heap integration (PGHI, from ltfatnote050, "Phase Vocoder Done Right"). The gradient method enforces phase coherence in both time and frequency without peak-picking or transient detection, which is what lets a high stretch ratio preserve upper-band detail and transient impact rather than dulling them. Per-frame phase correction keeps bins coherent within each frame, so steady-state content — held strings, sustained winds, room tone — stretches without smearing into a chorused or phasey artifact.

The FFT size `N` is fixed at 4096 and the synthesis hop `R_s` is derived as `N/4` (75% overlap). These parameters match the authors' released PGHI implementation (github.com/ltfat/pvdoneright) parameter-for-parameter — window length 4096, `M=2N=8192`, synthesis step 1024, tolerance `1e-6` — giving the gradient integration its finest frequency resolution and the fullest low-frequency body. The engine inherits the source recording's sample rate.

### Relation to the published algorithm

The engine implements the published algorithm faithfully: origin-centered zero-padded analysis (`M=2N`, matching the paper's ~2x padding), centered finite differences for both phase derivatives, trapezoidal integration in all three propagation directions, the max-heap significance ordering, and the published tolerance. Where the implementation deviates from or extends the paper, the differences are deliberate:

- Variable analysis hop. The paper fixes one analysis step for the whole file (constant stretch ratio). This engine derives the analysis hop per frame from the warp-marker frame map; each half of the centered time-derivative is normalized by its own actual hop, and the frequency-direction step uses the per-frame ratio. This is the extension that makes free-tempo warping possible and is the project's reason to exist.
- Phase resets. The paper has no mid-stream re-grounding; transient handling is left to detection-based methods it cites. This engine's manual phase-reset markers re-seat the synthesis phase to the analysis phase at user-chosen frames — operator judgment in place of detection.
- Output timing contract. The paper does not specify output alignment; this engine pins it. Synthesis trims exactly `N/2` samples from the head — the alignment latency the origin-centered analysis contributes — so source frame 0 maps to output frame 0, and a feature at source frame `S` lands at output sample `tgt(S)` from the frame map. Total output length is the target-frame position of the last source sample. The overlap-add ramps at head and tail move no alignment. The head ramp is not only a fade, though: the two analysis frames that would have to read from before the first sample are taken as silence, so a render fades in over about 70 ms and its opening phase is seeded from that silence — which is why a phase reset placed inside roughly the first 46 ms of a piece does nothing at all. On lead-in silence, which is what these recordings have, none of that is audible; a recording cut hard on its first note would open a little under level. This establishes a contract: any future engine consuming the same warp markers (and, if it supports them, the same phase-reset markers) can match this engine's output 1:1 in frame timing at the start and through the body. The tail's final incomplete-overlap ramp is deliberately outside the contract.
- Remaining boundary choices, unspecified by the paper: the first frame (and the frame each phase reset selects — the frame whose analysis window centers on the authored position) seeds synthesis phase from analysis phase, the seed that serves the timing contract and the reset model above; the first frame's time-derivative uses the forward difference only; the frequency-derivative is one-sided at DC and Nyquist.
- Quiet-bin randomness. The paper assigns unspecified "random values" to sub-tolerance bins. This engine pins the choice: uniform phase in (-pi, pi) from a per-channel deterministically seeded generator, so identical renders are byte-identical — the property the project's verification protocol depends on.
- Real-signal realization. The spectrum is held as the Hermitian half (`M/2+1` bins) rather than the paper's full-`M` complex formulation — mathematically identical for real input and output.

### Warp markers, labels, and phase resets

Variable-rate time-stretching with user-placed warp markers exists in other tools — DAWs have shipped warp-marker editing on top of their bundled time-stretch algorithms for years. What separates this project is per-marker tempo locking through label definitions and references. A marker can declare a named label; a later marker can reference that label by name; the two markers and every other reference to the same label render at the same effective tempo, and editing the def's tempo updates every ref that cites it. The use case it was built around is the sonata-form exposition/recapitulation relationship in classical orchestral repertoire, where the same musical material returns multiple times across a movement and should hold a coherent tempo relationship across all occurrences regardless of how the surrounding material is edited.

Per-frame phase coherence is what keeps steady-state content clean. It is also exactly what a transient defeats. An attack — oboe entry, pizzicato, timpani strike — is a moment where the spectrum reorganizes within a few hops, and the phase relationships the vocoder has been propagating no longer correspond to the acoustic event arriving. The attack smears across surrounding frames. The mitigation is a phase reset: at a user-chosen position, the synthesis phase is reset rather than propagated, sacrificing local coherence in exchange for a clean transient. Phase reset markers are the authoring surface for this. They are a separate marker collection from warp markers, visible and edited in their own view, because they parameterize a distinct engine concern: warp markers shape the frame map, phase reset markers protect transients.

### The three view axes

The interface carries three view axes: the **audio domain** (source or target), the **marker column** (warp or phase reset), and the **A/B tab**. The A/B tab is independent of the other two and the tab row is its surface. The audio domain and the marker column are not: the phase reset column lives in target view alone, because a phase reset can only be heard accurately there. So the pairs that exist are exactly `S+W`, `T+P` and `T+W`. Going to source view from `T+P` puts you on the warp column, and a `.settings` file naming source view beside the phase reset column is refused at load. You reach a pair by naming it whole rather than by flipping an axis: the bare digits `1` / `2` / `3` select one each. The right end of the menu row carries three view buttons — `S+W`, `T+P`, `T+W` — one per working combination, each a click-shaped spelling of its key (`1`, `2`, `3`).

**Source vs target** selects the audio domain under the playhead. Source view shows the unprocessed recording with warp markers at the times you authored them; it is where a marker's *position* is authored — placing, dragging, nudging — because pinning a marker against an acoustic event belongs in the unprocessed recording. Target view shows the same audio after the engine has applied the live frame map — the waveform stretched and compressed to what the render will sound like, markers drawn at their post-stretch positions; it is where you judge the warp by ear, and everything that does not *move* a warp marker works there: the value step, disable, inherit, delete, the flag editor, grid iterations — which live in target view alone. Each edit reshapes the stretched picture as it lands, and the playhead follows the marker it was standing on into its new place. What target view refuses is moving a warp marker — the drop and the nudge answer `Markers are placed in source view` / `Markers are moved in source view`, and dragging a warp flag there changes its tempo instead of moving it (the value drag, under Markers). Trim narrowed to the section under revision keeps target renders fast enough for the edit-listen loop to feel immediate.

**The marker column** selects which marker collection is visible and edited. The collections are stored, authored, and rendered independently; switching swaps which collection the marker hotkeys operate on and changes nothing else. Warp positions author in source view; phase resets author in target view, the only view their column appears in — where the stretch is audible and the lead-in overlay paints. Warp markers' *values* are edited from either view.

Both collections want **anticipation** — placement a little ahead of the acoustic event — for different reasons. Warp markers anticipate to make A/B synchronization reliable: rather than landing exactly on a transient, place the marker slightly earlier, in the fading tail of the previous material, which is a far more dependable alignment cue than the silence or volume dip just before a transient. The lead-in matters most for label-bearing markers and their neighbors, where the label mechanism's tempo precision only pays off if the underlying timing is itself precise, and for quiet, slow, or legato onsets with no sharp attack to pin to. Phase reset markers anticipate to give the reset an `N/2` lead-in into the transient: the engine seeds a reset from the synthesis window whose centre lies at or just before it — the last window that has not yet passed the reset — and replays that window's content as it stands, and the crossover from the old phase to the new one dips in level for about a hop on either side of that centre; both are over about `N/2` samples after the reset, so authoring the reset `N/2` before the transient means the transient itself arrives at full level, with the new phase fully settled, placed on the map by the ordinary synthesis rather than by the seed's own copy. The drop and the audition do this arithmetic for you (see Phase reset authoring).

**Tab A vs tab B** selects between two snapshots of viewport, zoom, playhead, and trim window. A snapshot holds positions and view settings only — never a selection, which belongs to the moment rather than to the tab. Marker stores and engine settings are shared across both tabs; only navigation state differs. The second tab earns its place from the first repeated phrase onward: park one tab at the first occurrence and the other at the second, then walk the lead-ins forward together to confirm the matching reference point — the same pattern at every scale, from phrase repeats to the exposition-recapitulation relationship a sonata movement turns on.

### The warp marker model

A default warp marker is seeded at the file's first frame on first load, carrying tempo `1.00`. A render does not actually require it: when no enabled marker sits at exactly frame zero, the render silently behaves as if a plain `1.00` owner were there. More generally, ambiguous marker arrangements never block anything — two or more enabled markers on the same exact frame collapse to a single `1.00` owner for the render, a reference whose definition was deleted renders as `1.00`, and each such normalization prints one stderr line naming the timestamp. What you see in the GUI is your authored store; a red flag is the display cue that a spot needs attention.

The classical phase-vocoder use case — one constant stretch ratio for the whole file — requires no warp-marker authoring at all: set the global ratio through the settings `scale` field and the frame map stays a single constant. Warp markers come into play when you want phrase-level tempo variation. Each one carries three independent pieces of engine state.

**Tempo source.** A marker either owns its own tempo or inherits the tempo from the nearest earlier owning marker. An owning marker presents an explicit numeric value; an inheriting marker (a "pass") carries no tempo of its own and resolves its presentation tempo live by walking backward through the marker list. The walk passes over disabled markers, other passes and label references alike and stops at the nearest earlier owner, taking that owner's tempo (a reference owns a duration equation, not a rate, so there is no rate for a pass to take from it); with no owner before it, a pass plays at `1.00`. Because the resolution is live, deleting or disabling an owner re-resolves every dependent pass to the next earlier owner; nothing is frozen on the pass itself. An owning marker's tempo may be written as a main speed followed by up to sixteen signed adjustments — `1.23+0.01-0.02` — which sounds exactly like the `1.22` it adds up to but keeps the section's main speed visible beside the changes you made to it; `Up` / `Down` move the last adjustment rather than the main speed, a pass or a label reference never carries one, and each adjustment stays within ±4.00 while the total stays within `[0.25, 4.00]`.

**Label relationship.** A marker can declare itself a label origin (a `label_def`) or cite an existing label by name (a `label_ref`). A ref inherits its tempo from the named def rather than from positional walk-back; changing the def's tempo updates every ref that cites it. This is the mechanism for tempo locking across recapitulated material: the exposition section receives a `label_def`, the recapitulation a `label_ref` back to it, and the two always render at the same tempo regardless of subsequent edits. A reference imposes its definition's target duration on its own segment whatever local stretch ratio that implies, within reason: an implied effective tempo outside `[0.125, 8]` — beyond what any directly authored marker could express — is treated as a mismatch and renders as a plain `1.00` instead, with one stderr line; matching reference segments to their definitions sensibly remains the author's concern. A marker carries at most one of `label_def` or `label_ref`; neither is the unlabeled default.

**Disabled flag.** A marker can be disabled, which silences its tempo contribution as if the marker were not present. Disabling a `label_def` cascades: every ref citing it is treated as disabled too. Disabling a non-def marker is local and does not propagate.

An owning marker's tempo is a base value times a scale. The base value is exactly two decimals (the `N.NN` spelling is the on-disk grammar) in the bracket `[0.25, 4.00]` and expresses the headline stretch ratio relative to the source — `1.00` is no stretch, `1.05` is 5% faster, `0.95` is 5% slower. The precision is deliberately coarse; you author at the resolution you would set a metronome. The scale is a separate full-precision multiplier in the bracket `[0.5, 2.0]`, defaulting to `1.0000`. Its intended use is fine-tuning a marker's effective tempo to approximate a neighboring section's effective tempo when that neighbor uses a `label_ref`: select the neighbor and press `J`, which copies its resolved `base*scale` to the clipboard, then apply a matching scale to the marker being authored. Out-of-bracket values are rejected at the editor with a red flash and a notification saying why. The reference project in `projects/550 - 1/` shows both fields in use across a complete movement.

Phase reset markers carry two pieces of engine state: a position and a disabled flag. No tempo, no labels, no scale. The engine concern they parameterize is *where to reset* — the reset fires at the authored position, seeded from the analysis window whose centre lies at or just before it.

### A working method

How a movement actually gets authored, in the order that works:

1. Find the introduction measures that define the tempo. Set warp markers there, set the corresponding phase reset markers, then run BPM iterations and pick the tempo that sits right.
2. Work down the piece in chronological order, toggling between the three working views: `1` (source + warp) to place markers, `2` (target + phase reset) to protect the transients, and `3` (target + warp) for tempo adjustments by ear.
3. Once some headway is made, copy label definitions into references — the exposition into the repeat and the recapitulation — and paste the definition's phase resets across with the propagate commands.
4. Phase resets are set with `Shift+S` and nudged only when the phase alignment causes an audible dip, pop, or crackle.
5. The A/B audition (`Shift+Space`) is crucial for confirming that label references match their definitions — the crux of the tempo-locking mechanism, which lets precise timing be replicated in the sonata-form fashion of repeated rhythmic motifs and phrases, at both large and small scale.
6. Iterations, trimmed target previews, and the history view carry the rest: render a spread, listen, load the winner in place, checkpoint.

On timing: the scanner's smooth movement lets a warp marker land essentially at the onset of an attack — place against what you see and hear together. The Symphony No. 40 first movement (`projects/550 - 1/`) is the worked demonstration of this.

## Output and the limiter

The render product is a finished WAV: 24-bit PCM, brought to a delivery ceiling by the built-in limiter — a transparent spectral stage at -0.3 dBFS, then a 0 dBFS lookahead peak limiter with a hard-clip backstop. The limiter is unconditional; there is no bypass and no output-format choice.

As future-proofing for later engines, every archival render — the GUI's `Ctrl+Alt+R`, the sweeps' batch cells, and the CLI — also writes the full frame-map pair: `<wav-stem>.warpframemap` (whitespace-separated `<src> <tgt>` frame pairs, precise double breakpoints) and `<wav-stem>.phaseresetframemap` land in `~/.cache/warptempo_gui/<pid>/` (batch cells under a subdirectory mirroring their batch folder). Together they are exactly the engine's input for the full (untrimmed) render of that recipe, with the phase resets already compiled into the engine's origin-centered query domain; trim never affects the pair, and the limiter does not apply to map files. Any time-stretch library that accepts a sample-domain warp map could be driven from these files. Retrieve them between the render and program close: the GUI removes its per-process directory when it exits, and CLI-written directories and orphans from dead processes are swept at the next GUI launch. The pair is written all-or-nothing — a write failure removes both files rather than leaving a mixed-generation pair.

## Reproducibility

Rendering is deterministic per machine and binary: the same project rendered twice on the same host with the same build produces byte-identical WAV output, every time. This is a hard guarantee — the whole pipeline is fixed-order and free of timing- or scheduling-dependent math. GUI and CLI from one build on one system state are byte-identical, unconditionally.

Across builds the boundary is not the compiler's code generation but the libraries underneath it. Floating-point contraction is switched off in the build, so how the compiler lays the arithmetic out no longer touches a single output bit: the same project renders byte-identically whether the binary was tuned for this CPU or built generically, and on another machine of the same architecture — same compiler, same glibc and FFTW — it is expected to render those same bytes again, though that is a derivation and not a measurement: only one machine has ever been rendered on. The term the derivation leaves out is glibc's own dispatch of `libm`/`libmvec` by CPU feature, which can differ between two machines carrying the same library version, so treat every host as its own reference and re-render rather than compare. What does move the output is a change in those libraries, and the movement is tiny. For a sense of scale at the far end: a completely different toolchain on a different architecture — a WebAssembly build of the same engine, carrying its own C library and its own copy of FFTW — differs from the native build by 67 samples of a 7.6-minute render, each by a single least-significant bit. On threshold-straddling material the limiter can quantize a difference that small into a localized one (measured at the -38 dBFS / two-samples class on a stress recipe — far below audibility, and ear-verified quality-neutral). So compare renders byte-for-byte freely within one set of library versions; after a glibc or FFTW upgrade, re-render anything you intend to keep comparing against.

## The interface

The reference is grouped by function. Everything is keyboard unless marked as a mouse gesture. A key is named by the cap it wears, so a letter is written capital whether or not `Shift` is part of the chord — where `Shift` belongs it is always spelled out, and the program's own tooltips and cards name keys the same way. Where a key does different things in warp view versus phase-reset view, both are given.

Three rules organize everything, and they are worth reading before the sections:

**Bindings are matched exactly.** A key pressed with a modifier the reference does not list for it does nothing at all — no near-miss chords fall back to the unmodified binding. Inside a text editor the clipboard chords are `Ctrl+C` / `Ctrl+X` / `Ctrl+V` exactly, so the terminal habit of `Ctrl+Shift+C` does nothing there. `Ctrl+C` reaches one surface outside the editors: the AV sync panel, where it copies the whole page. `Alt` lives only in the five `Ctrl+Alt` chords (the two render chords, the two phase-reset propagate pastes, and `Revert`); nothing else uses it. `Meta` (the Super or Logo key) belongs to the window manager: while it is held no keypress starts a command — with one deliberate exception: bare `E` is the left mouse button rather than a key, so `Meta`+`E` still clicks, exactly as `Meta`+click does.

**A press that does something is silent; a press that refuses normally says why; a press with no command behind it says nothing.** A bound key that cannot act answers on a notification card naming the key and the reason (`Ctrl+Z is not available on a read-only tab`). What stays silent is a chord with no command behind it — the history view's own keys, pressed outside the view, included — and a **one-dimensional command already at its state** — one that moves a single thing in a single place, so one glance at that place already answers whether anything happened: the playhead already at the end it would jump to, a walk already at its last marker or its last checkpoint, a scroll already at the edge of the piece, a ladder step already at its end, a tempo already at the bracket's edge, a marker already against a wall, a trim already covering the whole song, the selector for the view you are already in, a click on the radio button already selected. A command whose effect spreads across the screen keeps its sentence even where it has nothing to do — undo and redo over an empty stack (a held `Ctrl+Z` that runs out of history just stops), a tempo step over a selection one marker cannot take — because there is no single place to glance at. So silence with no visible change means the press was either unbound or had nothing left to change. Where a button spells the same step, its grey face says so ahead of the press; a greyed button stays silent too, the grey being the message.

**Keys act when they go down; buttons act when the mouse comes up.** A button is a target, so it gives you the slide-away escape a target should have — press, drag off, release, and nothing happens; drag back on and release, and it acts. A key is an instrument, and the moment you can aim is the moment you press — which matters on the warp side, where you are placing markers against music you are listening to. A key that repeats while held — the arrows, `PgUp`/`PgDown`, `Tab`, undo and redo, and the history walk — acts at once, then waits your desktop's own key-repeat delay and runs at your desktop's repeat rate; each repeat reads the modifiers as they stand at that moment, so holding `Ctrl+Z` and adding `Shift` partway through carries the run on as redo. A key, like a mouse gesture, cannot be called back: by the time it is down the command has run, and undo is the way out.

Two button conventions ride on that. Wherever a keyboard command has a `Shift` version and its plain version has a button, that button takes the `Shift` version too: `Shift`+click it, or hold the press about half a second before letting go — the hold is there for the touchscreen, which has no `Shift`, and works the same with a mouse. The button's tooltip is the clock: it appears exactly as the hold becomes long enough, so let go once you see it and the `Shift` act is what you get. (Two exceptions prove it. The playhead skip buttons' modifier is `Ctrl`, which only a real `Ctrl`+click reaches — on the tablet, a tap with the pen's side button held — never a hold. And the up and down arrows take both modifiers, `Shift` for a ten-step and `Ctrl` for a three, but neither by hold: they repeat while held, so a long press on one gives the stream of single steps; the left and right arrows take no modifier at all.) The marker walk button takes `Ctrl` as well as `Shift`, pressing its own key under both, and its hold composes with the pen: with the pen's side button held, a tap is `Ctrl+Tab` and a long press `Ctrl+Shift+Tab`. And six buttons repeat while held instead of waiting for the release: the four cardinal arrows on the bottom toolbar and Undo / Redo in the icon row, which step steadily for as long as you hold them — how a touchscreen walks a ladder.

### Notifications and the state text

When something you asked for could not be done, or something you were not watching finished badly, the program says so in a small dark card at the top right of the window — a blue information glyph, the text, and a close button. The card answers the press that raised it: a chord swallowed because an editor is open, a marker verb with nothing selected, a command used away from its home view, a mode that will not open on the selection you have — each names what it wanted, one card per press. Press the same refused key twice and you get two cards: the count is there so you can see that each press was read, which is what you want when you are stepping something deliberately and watching for the wall. *Holding* is the exception, and it reads the same whether you hold a key or one of the six buttons that repeat while held — the repeats stream at the keyboard's own rate, and they re-push the one card rather than burying the screen in copies of one sentence. Hold `Up` on a marker that cannot take the step and you get one card; hold the up-arrow button on that same marker and you get one card. Cards are all one width unless the sentence is long enough to need more, so two answers that differ by a word do not shift under each other as you press.

A command that worked says nothing, as long as the screen shows what it did — and the one thing the screen cannot show is the clipboard. So the three copies say so themselves: `J` reports `Copied the resolved value '1.28*1.0112'` with the value it copied, `Ctrl+P` `Copied the selected markers' phase resets`, and the AV sync panel's `Copy to Clipboard` `Copied the AV sync stats`; a copy whose selection held nothing to take says that instead, and a copy the clipboard did not take says so too — `The clipboard did not take the copy`, on either machine, if the system refused it. An editor's own `Ctrl+C` stays quiet, because the text it did not take is still sitting there selected; its `Ctrl+X` does not, because a cut that could not copy must not delete either — it keeps the selection and says `The clipboard did not take the cut`. Everything else you can see: the region going up over the whole song is its own answer, and so are the trim bar's endcaps jumping to the ends when a drawing collapses. Saving, rendering and synchronizing stay silent when they work: the `*` leaving the clock on the bottom toolbar is the save's answer, and the finished file is the other two's. That mark is the only place unsaved work shows, on either machine — the window title names the project and nothing more.

Ordinary cards leave by themselves after a few seconds, waiting while the pointer rests on them, or when you click their close button. The checkpoint failures described under Checking history carry the red error glyph instead and stay until you close them. `Esc` closes cards too — the whole stack at once, and it takes the red cards as readily as the ordinary ones. It is the last thing `Esc` does, so anything it would otherwise close, or a render it would cancel, comes first: with an editor, prompt, menu, player or list open, the first press closes that and a later one reaches the cards. With no cards standing it does nothing and says nothing. Newer cards stack on top; when the stack fills the window the oldest ordinary card leaves to make room, and the red ones never leave that way. A longer sentence wraps, up to three lines. A card stops nothing, and a click anywhere on it other than its close button does nothing at all.

What is true right now — a render's progress (`Loading...`, `Rendering...`, `Updating...`), or the history view's position while that view is open — is not a card: it is the **state text** on the bottom toolbar, which runs on from the clock in the clock's own monospace, after a pipe — `00:00.100 | Updating...`. It is replaced as it changes and never times out; the history view's line wins while that view is open. **Unsaved work shows there too**, as `*` immediately after the clock — `00:00.100* | Rendering...` — so the mark is on the row whether or not anything else is being said, and it goes out the moment you save. While a prompt, one of the bottom row's editors, the render player, the project list or the AV sync panel holds the bottom row, the state text steps aside and returns when they close.

### The window

The menu row and the icon row sit along the very top edge, the icon row directly under the menu row, and the bottom toolbar along the very bottom edge. Everything else is one block: the tab row, the trim bar, the ruler, the marker lane, and the waveform under them. The block is placed so the middle of the waveform is the middle of the window; on a tall screen the waveform grows to a limit and blank bands take the rest — the one between the icon row and the tabs wears the tab row's own colour, so the tabs read as sitting at the foot of a tall band, and the one above the bottom toolbar is plain ground — and nothing in those bands responds to the mouse. The tabs are Breeze's: the selected tab wears a blue cap and grey sides and opens straight into the strip below, and the other tab is a flat panel that runs under the selected tab's rounded corner. Unsaved work shows as `*` after the clock on the bottom toolbar, on both machines, and only there — the window title carries the project name alone.

**The bottom row is the modal surface.** Prompts and the one-line editors (settings, BPM and the commit message) take the whole bottom row while they are open — the transport, the clock and the state text step aside — and while one is up the rest of the window is inert: clicks, scrolls, and drags anywhere else do nothing, and it closes only by its own buttons and keys. The mechanics are the same for all of them:

- A prompt reads from the left with its answers as real buttons after it — `Save`, `Discard`, `Cancel` on the unsaved-changes prompt (`Retry` replacing `Save` after a failed save), `Yes` / `Cancel` on the paste confirmation, `OK` / `Cancel` on the load-in-place confirmation. Every button has a key, named in its tooltip (`Save (S)`, `Discard (Del)`, `Cancel (Esc)`); a tooltip names the key cap, and the letter answers are typed plain — `Shift` does not answer a prompt.
- An editor is a label, a dark text field, and `OK` / `Cancel` buttons that are exactly the editor's `Return` and `Esc`. It opens with the keyboard in the field; the field carries the blue outline while the keyboard is in it, scrolls sideways to keep the cursor in view, and takes the ordinary text-field gestures (see the flag editor under Warp marker authoring — all editors share them, the clipboard described there included).
- `Tab` moves the keyboard around the ring of field and buttons, `Shift+Tab` the other way; in a field with something to complete, `Tab` completes first and walks the ring only when there was nothing to complete. `Return` or `Space` presses the focused button. A prompt opens with its *last* button focused — the one `Esc` would pick, so `Return` takes the safe answer — with one exception: the load-in-place confirmation opens on `OK`, because a load is one `Ctrl+Z` away.
- The two chords that reach through any of them are `Ctrl+S` (saves; the surface stays) and `Ctrl+Q` (abandons it, then the usual close routing).

`Ctrl+S` saves all sidecar files; if one of them cannot be written — a full disk, a permission the folder no longer gives — a notification names the file it could not write, the work stays unsaved, and the mark stays where it was, so `Ctrl+Q` still offers to retry. `Ctrl+Q` closes the window, routing through the unsaved-changes prompt when the session is dirty. On the tablet the system's own Back — gesture or button — is that same command; being killed from the task switcher is not, and asks nothing, so answer the question rather than swiping the app away.

### Menus

The menu row holds `File`, `Edit` and `Settings` on the left and the view bar on the right, along the very top of the window, with the icon row directly under it. All three open dropdowns; the item runs when you release the mouse on it, `Esc` or a click anywhere else dismisses the menu, and you can press on the button, drag into the menu, and release on an item in one motion. Once a menu has been opened, moving the pointer onto another menu button switches to its menu with no click. In `File` and `Edit` each row shows its key beside it and does exactly what the key does; `Settings` is the one menu whose rows have no key of their own — each opens the settings prompt on one setting. A row whose command could not act right now is greyed, the way the buttons are; clicking a greyed row does nothing and leaves the menu open, and a menu whose rows are all greyed has its own button greyed too. While a project is loading everything is greyed but `File`, whose `Quit` still works.

- `File`: `Open Project` (`Ctrl+O`), `Revert` (`Ctrl+Alt+O`), `Synchronize to External Storage` (`\`), then, past a line, `Quit` (`Ctrl+Q`). All four work inside the history view too. `File` is also the one menu that stays open over the render player, the project list and the AV sync panel: `Quit` and `Synchronize` work from there, and `Open Project` and `Revert` are greyed while one of those stands.
- `Edit`: `Copy Phase Resets` (`Ctrl+P`), `Paste Phase Resets` (`Ctrl+Alt+P`) and `Paste Phase Reset State` (`Ctrl+Alt+Shift+P`). This menu is the mouse's one road to them.
- `Settings`: the settings you edit by hand — `Title`, `Notes`, `URL`, `Cover`, then the per-device keys `GUI Scale`, `Max Waveform Height`, `Projects Repository`, `Projects Path`, `Sync Path` — each opening the settings prompt with that key and its current value filled in (`;` opens the bare prompt directly). On the two path rows `Tab` completes the folder being typed against the disk. Every row opens on a read-only tab; it is the commit that answers there — the five per-device keys go through, and the four keys belonging to the piece say `This tab is read-only` and leave the field red.

**The AV sync panel.** `Shift+L` — which opens and closes it the way `L` opens and closes the render player, the two sharing one letter because they share one band — opens a page of text across the window below the toolbar, in the same band the render player and the project list use, with `Copy to Clipboard` and `Close` on the bottom row (`Ctrl+C` is the copy's key, and `Esc` or `Shift+L` closes the panel). The `Play renders` button reaches it too — `Shift`+click it, or hold the press about half a second, which is the touchscreen's road in; there is no menu row for it. The menu row and the icon row stay above it with `File` open and the rest greyed, as they do under the other two. Its lines are in a fixed-width face, so the figures line up; the render player's and the project list's rows are in the ordinary one. The page is the same size from the moment it opens: every line is there straight away, a figure that is still being measured says so and fills in where it stands rather than pushing the lines below it down, and the numbers are padded to a fixed width so no column moves as they change. The copy takes the whole page — every line, in the order it is painted — and a card says it went to the clipboard, so the figures can be pasted straight into a note or a message; there is nothing to pick out by hand and no part of the page is copied on its own. It reports what the audio device says about itself — which sound system is in use, its rate, the block it asks for at a time, and, where the system reports one, how long after the program hands over a sound that sound is actually heard — and what the display says about itself: which screen the window is on, its refresh, and how long after the program paints a frame that frame turns into light. The last group is the one worth reading: a single line saying how far ahead of the sound the playhead runs, in words rather than a bare number, and by how much more the start of each playback can vary. Where a figure is not available the panel says so and prints no combined line, rather than showing a number made out of half a measurement — on the tablet the display side and the output latency are both unavailable, and it says which.

**It measures only while it is open.** Nothing is being timed, sampled or asked of the audio server or the compositor while the panel is closed; opening it starts the measurements and closing it stops them. Expect the display figures to read as waiting for a moment after it opens — they fill in as soon as the screen has shown a frame or two.

The view bar is the three view buttons — `S+W`, `T+P`, `T+W` — each a click-shaped spelling of its key (`1`, `2`, `3`); the button matching the current combination wears a toggled-on face, and exactly one is always lit — the three are every combination there is.

### The two toolbars

Every button in the icon row and on the bottom toolbar is a click-shaped spelling of a keyboard command and behaves identically to it. Buttons never appear or disappear; a button whose press would do nothing greys out instead — the greys are truthful, so a grey face is the program telling you in advance what a card would tell you after. The radio buttons are the exception: the lit tab, and the lit view button at the right of the menu row, simply ignore a click, having nothing to switch to. A greyed button still shows its tooltip, and the tooltip still names the ACT: a button that cannot act right now is exactly the one you may need told what it is for. What it will never say is WHY it is dead — not which mode refuses it, not which state it is in. A tooltip is the act's name; the grey is the message, and the reason is the key's: press the key and the program tells you on a card. Every button shows a small tooltip naming its action and key after the pointer rests on it — and a finger resting on a button is a pointer resting on it, so the tooltip comes up under a long press too, at the moment the hold has lasted long enough for the `Shift` act; where the button takes a `Shift`+click (or a `Ctrl`+click, on the two skips and the up and down arrows), a second line names that act.

The icon row, left to right: `Save` (`Ctrl+S`), `Undo` (`Ctrl+Z`), `Redo` (`Ctrl+Shift+Z`), `Render` (`Ctrl+Alt+R`); the view group — full zoom out (`0`, taking `Shift` to reset the trim to the whole song), center (`C`), **Toggle Waveform Magnification** (the backtick, `` ` ``, a lamp that shows the waveform magnified while lit, in either view), **Toggle Follow** (`F`, a lamp), and **Toggle Restrict Undo to Current View** (`Z`, a lamp — it decides where the view may be taken, so it sits with the other view lamps rather than with the two buttons it governs); the iteration group — **BPM Iterations** (`Ctrl+B`), **Toggle Grid Iterations** (`I`, a lamp lit while the mode is on) and **Flatten** (`Ctrl+F`, taking `Shift` to collapse the tempo deviations into one), which sits here because it too works on the whole piece: it takes off the deviations a grid sweep put on; play renders (`L`, taking `Shift` for the AV sync panel) and the read-only padlock (**Toggle Read-Only**, `O`, showing and toggling the active tab's lock); and the history group — **Toggle History View** (`H`), **Toggle History Walk** (`G`, a lamp lit on the `Session` walk), **Toggle Cumulative** (`U`), revert (`V`), the walk's two arrows (`,` and `.`, each taking `Shift` for the jump to that end), and load in place (`'`). Load in place sits with the history buttons because that is the only place it is a button: it loads the checkpoint or session state the view is showing, and outside the view it is grey — press `'` there and you get the render player, which has its own load button. It is grey on a locked tab too, and over a piece with no history to walk. `Render` takes `Shift` (the miscellaneous render, `Ctrl+Alt+Shift+R`) and wears the cancel glyph while a render you asked for is running — clicking it then stops the work. In the history view `Save` wears the commit glyph and reads `Save and Commit`.

The bottom toolbar, left to right: go to start (`Home`), play/stop (`Space` — one button showing whichever act is next, taking `Shift` for the A/B audition), go to end (`End`); the clock, in monospace, wearing `*` while there is unsaved work, with the state text running on after a pipe in the same lettering; then, against the right edge: the marker verbs — drop (`S`, taking `Shift` for the phase-reset drop), delete (`Del`), toggle disabled (`Ctrl+D`), toggle inherit (`Ctrl+N`), edit flag (`Return`), copy resolved value (`J`, taking `Shift` for the jump to the defining marker), and toggle add to selection (`K`, a lamp); the marker walk (`Tab`, taking `Shift` for the previous marker, `Ctrl` for the other tab — `Ctrl+Tab` — and `Ctrl`+`Shift` for the march over both tabs, `Ctrl+Shift+Tab`; with a modifier, a button presses its own key with that modifier); and the four arrows, which hold-repeat, up and down taking `Shift` for the ten-step and `Ctrl` for the three. The two skip buttons take `Ctrl`: a `Ctrl`+click jumps to the very start or end of the piece instead of the trim bound, the same act as `Ctrl+Home` / `Ctrl+End`. Every tooltip names what the press will do right now: a lamp's names its toggle, full zoom out reads `Back to Previous View` while it has a view to go back to, center with nothing focused reads `Center on Playhead` — and a second line appears only where `Shift` or `Ctrl` would do something different in that state (no `Press Shift for the whole song` over a trim that already is the whole song, no `Press Ctrl` line where the trim bound and the song's end coincide).

Locking a tab greys the buttons the lock actually refuses: in the icon row the iteration group's three buttons; on the bottom toolbar the four single-marker verbs, edit flag, and the four arrows — up and down whenever the tab is locked, left and right only while a marker is selected (with none selected they still step the playhead) — and, in the history view, the icon row's load in place (outside that view it is grey anyway, and for a different reason). `Save` and `Render` stay live on a locked tab: a lock is about the piece's markers and settings, not about writing out or rendering what is already there. **You cannot lock a tab while grid iterations is on, and you cannot turn grid iterations on while either tab is locked** — the two locks never stand together, and the exclusion is about the whole piece rather than the tab you are standing on, the two A/B tabs sharing the same markers. So the padlock greys and `O` says `Turn off grid iterations first` while that lamp is lit, and **Toggle Grid Iterations** greys and `I` says `I is not available on a read-only tab` while either tab wears the lock. **A greyed button never explains itself**: its tooltip names the act as always, and the reason is what the KEY says on a card — the grey tells you it will not work, the key tells you why.

**Grid iterations locks the piece the same way**, for a different reason: with that lamp lit the range cells are the only thing you can author, so the same buttons grey — and undo and redo grey with them, and so does **Add to selection**, which would turn the plain click the range cells are reached by into a membership toggle (turning the mode ON puts that lamp out for you, so you meet this refusal only from the other side), and **BPM Iterations**; the view bar's three buttons — `S+W`, `T+P`, `T+W` — stop answering a click for that same reason, and the two you are NOT in dim their labels while the one you are in stays bright. Three buttons stay live: **Toggle Grid Iterations**, which is the one way out of the mode, and **Edit Flag** and the up/down arrows, but only while a range cell is the bright one — there they work on the range and on nothing else. The keys say `Turn off grid iterations first` where the buttons go grey, and undo and redo say `Turn off grid iterations to undo` / `… to redo`. No tab can ALSO be locked: the padlock greys while the lamp is lit, and a typed `tab_A_read_only=true` or `tab_B_read_only=true` refuses in the settings prompt for the same reason. Nothing else about the tabs changes — `Ctrl+Tab`, the A/B audition and the `Shift+J` jump all switch tabs under the lamp exactly as they always do, there being no locked tab left to reach.

### Playback and playhead

`Space` starts and stops playback from the playhead to the end of what is playable — the song's end in source view, the end of the rendered preview (the trim window) in target view. The moving playhead is drawn from where playback started and runs on the clock, so on a device with output latency the line runs a little ahead of what you hear, by an amount that varies slightly from launch to launch. Nothing loops: every audition plays once to its end and stops on its own (the two exceptions anywhere in the program are the render player's `Repeat one` lamp and a play started from the car's dashboard, which loops the trim). In target view before the preview exists `Space` simply does nothing: the bottom row's state text is already saying `Updating...` beside the clock while that render runs, and the Play button is grey, so there is nothing a message could add — a click in the lower half of the waveform is refused the same way and as quietly. Where `Space` will not play and nothing on screen says why, it says so itself: if that preview render fails outright, a card says `Target render failed` and target view has nothing to play — and `Playback is unavailable on this device` when no audio device came up at all — or, on the tablet, when a route that dropped (a headphone pulled, a Bluetooth route gone) could not be reopened: a play press there reopens the device first and says this only if that fails. With the cursor at or past the end of what is playable it simply does nothing — the playhead resting there is the answer, and the Play button is grey. If playback instead does nothing at all — no sound, the playhead staying on its start frame — and the program then freezes at the next stop, the audio device is dead or its sink is stuck in the audio server; fix that and relaunch, as the program hangs there on purpose rather than pretending to play.

`Home` and `End` jump the playhead to the trim begin and trim end, dropping the marker selection as they go; `Ctrl+Home` and `Ctrl+End` jump to the very start and end of the piece, whatever the trim window is — the way to reach audio the window has cut off without opening the window first. A press that would change nothing does nothing and says nothing: the playhead is already sitting where the jump would put it, and the skip button is grey.

A keyboard playhead move stops playback; a command that only moves the view (zoom, `PgUp`/`PgDown`, `0` short of the full-song view) does not — `0`'s return stops it only when it puts the playhead back somewhere else — and neither does the `Up`/`Down` value step. Trim edits stop playback in both audio views — a trim change redefines what an audition would play.

The mouse is different: a click on the waveform's **upper half**, the ruler, or an empty spot in the marker lane moves the playhead at the release, reseeking live playback there instead of stopping it; a plain drag on the waveform pans instead, and the two never fight — a still click places, a moving drag pans. On the ruler and the marker lane a drag does nothing: they are for placing only. A click on the waveform's **lower half** auditions instead of placing: the moving scanner starts from the clicked spot, every click — a running session, the A/B audition and the car's loop included, is stopped and replaced by the new one — one-shot per click, Ableton-style, without touching the resting playhead or the selection.

**Follow** is `F`, **Toggle Follow**, a lamp in the icon row. While it is lit, every play of the project turns the page with the playhead, keeping it in view; it stays lit across plays and stops until you press `F` again, and it is off every time you open a project. Pressing it during a play takes effect at once. Moving the view yourself during a play — a pan, a drag, a pinch, `0` — leaves the view where you put it for the rest of that play, the lamp staying lit, and the next play follows again (pressing `F` twice picks the following back up at once). A click that moves the playhead does not stop it: the view follows on from where you clicked. When playback ends the viewport stays where it was. The A/B audition and the render player never follow. The car's play of the trim follows too while the lamp is lit.

A `Left`/`Right` nudge of the marker or the playhead leaves the view where it is while the thing you are moving stays on screen, and when a step would carry it off the edge the view follows so it stands at that edge. **After an explicit centring** — `C`, `Ctrl+Shift+Tab`, a `Tab` walk step that centred its marker, or `Shift+J` — the nudges instead keep the thing you are moving in the same place on screen and slide the waveform under it, so every step shows; one that was off screen comes in at the edge it was past and stays there as you keep nudging. That lasts until the view moves some other way (a pan, a drag, a zoom, `0`, a click that moves the playhead) — playing and stopping, and an undo or redo that brings back a single marker leave it standing (that undo or redo keeps the playhead in the same place on screen too, sliding the waveform under it, just as a nudge would; one that brings back several markers ends it) — and while it lasts the playhead's head above the marker lane turns from grey to white. At the very start or end of the piece the view cannot slide any further and the marker or playhead moves instead. Neither changes the zoom, and the zoom changes neither.

**The A/B audition** (`Shift+Space`, or the play button's `Shift`+click or long press) compares the two tabs' cued spots without the hand-work: it switches to the other tab, plays a short span from that tab's playhead twice with a short rest between, switches back, rests a little longer, and plays the same short span from this tab's playhead twice — then you are back where you started, ready to adjust. Each half opens with `C` on the tab it is about to play, so both spots are read at the working zoom, centred, focused marker and all. Neither playhead moves; each play is an ordinary one that runs to its own end, and each tab plays what it always plays — the file in source view, the rendered preview in target. Anything that would stop or restart playback ends the whole sequence where it stands — `Space`, a tab switch, a playhead move, a marker edit — and the rests count as part of it: the play button wears its stop square from first play to last, and `Space` in a rest stops the sequence. `Shift+Space` is a toggle like the transport it rides: press it again while one runs — or shift-click or long-press the play button again — and the sequence stops where it stands, with no new one started. One that cannot run says `One of the two tabs has nothing to play from here`. A device that goes away while one is running — a headphone pulled, a Bluetooth route dropped — ends the sequence where it stands and says `Playback is unavailable on this device`, the same sentence as a device that was never there. It works on a read-only tab.

`Left` and `Right` move the playhead one pixel (one hop in the phase-reset column) — unless markers are selected, in which case they move the *focused marker* instead (see Warp marker authoring). With nothing selected an arrow press also drops the marker focus.

**The step ladder** — `Up` / `Down` only. A modifier scales the step and changes nothing else: bare is one unit, `Shift` is ten — the long stride — and `Ctrl` is three, the unit being one unit of the bright cell's value (`0.01` of tempo, a bar). Everything else about the press is untouched: the same walls (a long step near an edge lands exactly on the edge rather than overshooting — except the tempo step over a *group*, which refuses whole where any member cannot take the full step, as it does at any size), the same read-only rules, the same one-undo-entry-per-run, and a held modified arrow repeats *its own* step. `Ctrl+Shift` together mean nothing. The two arrow buttons carry the ladder too — `Shift`+click for the ten-step and `Ctrl`+click for the three — but only from a keyboard: a held arrow button repeats, so a long press on a touchscreen gives the stream of single steps rather than the shifted twin. `Left` / `Right` have no ladder — placement is judged by eye, not counted in columns — and take no modifier at all; hold them for a longer run. Their one step is a pixel column, except in the phase-reset column, where it is one **hop** — exactly one hop of the lattice the engine seeds resets on, for a reset and for the playhead alike.

### Zoom and view

Zoom is continuous: the `Ctrl`+drag below, the two-finger pinch, or the pen's button-held drag. A zoom gesture leaves the view where it ends. The deepest zoom is fixed (1.2 s across the waveform at the 1920 px deployment width — a zoom level fixes time per pixel, so the span scales with window width), one level closer than the working zoom (2.4 s); the shallowest is the whole song exactly filling the width.

`0` is a toggle. Pressed short of the full-song view it remembers the view you are leaving — the zoom, the playhead and where the view stood — and zooms out to the whole song; pressed again it puts all three back exactly as they were, even if you moved the playhead while zoomed out. The full zoom out button's tooltip reads "Back to Previous View" while there is a view to go back to. The memory is per tab and lasts the session, and it belongs to the audio view it was taken in: switch between source and target view while zoomed out and `0` does nothing until you switch back. With nothing to go back to — the whole song already in view without `0` putting it there, or a view remembered in the other audio view — `0` does nothing and its button greys (it stays lit while there is a trim for its `Shift`-click to reset). (`Shift+0` — or the full zoom out button's `Shift`-click or long press — is something else: it resets the trim to the whole song — see Trim and the region.)

`C` snaps to the working zoom (2.4 s at 1920 px) centered on the focused marker, jumping the playhead onto it; with no focused marker it centers on the playhead.

**The one drag** (mouse). The waveform's drag — either half, and only the waveform — is one gesture with `Ctrl` as its zoom switch, the mouse's version of one finger versus two on a touchscreen. Plain, it pans — a smooth grab that captures the cursor for unlimited travel. With `Ctrl` held, the same sideways motion zooms instead — right zooms in, left out, about a pivot seated where the pointer was when `Ctrl` went down; up-and-down motion is ignored in both halves, so a wobbly zoom cannot slide the view and a pan cannot drift the zoom. Press or release `Ctrl` at any moment of the drag, as often as you like: each press seats the pivot under the pointer, each release hands the motion back to the pan, with no jump either way. The pivot holds the *audio* under it — the view scales around that piece of the song, and at the edges of the piece the pivot slides with its audio rather than letting the song walk out from under it, which is what makes a zoom reversible. A dim vertical stem marks the pivot for as long as `Ctrl` is down; the two-finger pinch shows the same mark. The drag moves the view and nothing else — playhead and selection stay exactly as they were.

The scroll wheel pans, a tenth of a screen per detent — except over a marker's flag, where it selects the marker and steps the box under the pointer (see Warp marker authoring). `Ctrl`, `Alt` and `Shift` with the wheel do nothing. `PgUp` and `PgDown` step the viewport by the same tenth of a screen; hold for a glide.

Double-click on the trim bar frames the trim window when it is narrower than the whole song, and the whole song when it is not.

### Waveform magnification

The backtick (`` ` ``), or the **Toggle Waveform Magnification** button after Center, lights a lamp that draws the waveform magnified — every quiet passage brought up toward the edge of the lane so its onsets show as plainly as a loud one's, loud passages simply clipping flat at the edge — in source and target view alike. In front of it the recording's own waveform stands in a lighter colour, thinned in loud passages, over the magnified one drawn behind it in the plain waveform's colour, so how thick the front waveform is against the one around it tells the quiet parts from the loud ones. Dark, the waveform is its plain self, and the lamp starts dark each time a project opens. The amount is worked out from the recording itself just after the project opens, and the button stays grey until it is: there is nothing to set, draw or save, both tabs always show the same picture, and it only changes what the waveform looks like, never a render.

### View toggles

The three view keys jump straight to a combination of the two axes — `1` is S+W, `2` is T+P, `3` is T+W — applying whichever of the two switches (the audio domain S/T, the marker collection W/P) actually changes; the view bar's three buttons do the same by pointer. These three keys and the view bar are the one road onto both axes. `Ctrl+Tab` switches the A/B tab. `Ctrl+Shift+Tab` advances both tabs' marker focus to the next marker in lockstep and leaves you on the tab you started from: the other tab steps and is centred the way `C` centres, then this one does the same, all in one go, so you never see the other tab (to hear the two side by side, use the A/B audition, `Shift+Space`). Both tabs end at the working zoom. It works the same inside the history view, where a step is a step along the differences and both tabs end on the same one. `Shift`+click or long-press the other tab to do it by pointer — it still leaves you on this tab — or `Ctrl+Shift`+click the marker walk button (on the tablet, a long press with the pen's side button held), whose `Ctrl`+click is `Ctrl+Tab`; grid iterations refuses it, since its tab switches could never walk the range cells honestly.

An audio-domain switch (S/T) carries the selection across — the same markers in another domain — and lands the playhead on the focused marker's position in the new domain. Switching the marker collection (W/P) or the tab (`Ctrl+Tab`) is different: those change which markers you are addressing at all, so they drop the selection. What you get back is automatic and comes from where the playhead is: on arrival, if it stands exactly on a marker of the newly active collection, that marker is selected for you; anywhere else, nothing is — being one frame off is being off. The tab's remembered playhead is restored exactly as you left it, which makes that recovery predictable: leave a tab with a marker selected and the playhead on it, come back, and the same marker is lit.

`O` toggles read-only on the active tab. What it protects is the piece itself — the markers and the engine settings — and nothing else: navigation, playback, the view toggles, the whole trim window, saving and rendering all stay available. The point is a finished section you want to stop nudging by accident, not a tab you cannot work with: lock it, then go on moving the trim window to compare a passage against the other tab, re-render, and save. Blocked on a locked tab: the marker drops, drags and nudges, the value step, `Del`, the flag and BPM editors, `'` in the history view (where it loads a state over your session; outside the view the same key just opens the render player and works fine — the player's own load button is what refuses there), every propagate command, undo and redo (an entry is refused when ITS OWN tab is locked, so the recovery is to unlock that tab with `O` — switching tabs does not help, the entry keeps the tab it was made on), and the settings prompt's own keys — `;` answers `; is not available on a read-only tab`, and the `Settings` menu's rows still open the prompt, where committing one of the piece's keys (`Title`, `Notes`, `URL`, `Cover`, or any engine key typed by hand) says `This tab is read-only` while the four per-device keys commit as usual. One navigation gesture is not exempt: with a marker selected the horizontal arrows are in the marker lane, where the same press authors, so a locked tab refuses them outright in every step size — drop the selection first and they navigate again. **`I` is refused by a lock on EITHER tab**, and it is the one key that is: the two tabs share the same markers, so a lock anywhere is a lock on what grid iterations would tune, and the lamp will not light while either padlock is on.

### Marker focus and selection

`Tab` and `Shift+Tab` cycle marker focus forward and backward, moving the playhead onto the focused marker; the walk never changes the zoom (`C` is the command that centres at the working zoom). At the working zoom or closer in, every marker the walk lands on is centred, on screen or not; at a wider zoom a marker already on screen leaves the view where it is, and one off screen is brought in just past the left edge. The walk skips disabled markers and operates on whichever collection the W/P toggle has active. A step with nowhere to go does nothing and says nothing — a walk already at its last marker is one of the one-dimensional refusals — and the walk button stays live regardless, since its `Ctrl` form switches the A/B tab and always acts; an exhausted walk is simply a silent no-op.

With grid iterations on, `Tab` and `Shift+Tab` stop on each range cell as well: the flag, then its lower bound, then its upper, then the next marker. A flag showing no cells is walked exactly as it is with the lamp off. `Shift+Tab` walks the same stops backward, which means it enters a marker from its right, on the upper cell. Stepping between the cells of one marker moves only the bright cell and narrows the selection to that marker — the playhead stays where it is and the picture holds still, there being no new marker to centre on — so a walk across a marker's cells is also the way to reach a range editor without the mouse: `Return` opens whichever cell is bright. `Ctrl+Shift+Tab`, the both-tabs march, does not do this and is refused while the lamp is lit: its own tab switch drops the selection, so its second tab could not honestly land on the cell the first one did.

A plain click on a marker's flag — the flag is the marker's one clickable part; its stem on the waveform is a visual cue only — selects the marker and seats the playhead on it the moment you press, without moving the view. It works in both views, both collections, and on a read-only tab. `Shift`+flag-click selects an inclusive range, file-manager style, from the anchor — the marker that was focused when you began shift-clicking — to the clicked one, which becomes the new focus; a second shift-click ranges from that same anchor again, not from the marker the first one focused with the playhead on it. `Ctrl`+flag-click toggles one marker's membership, seating the playhead on whichever marker ends up focused. With several markers selected, a plain click on one of them selects that one alone — and a drag from any flag moves that one marker only; dragging never moves a group.

**Add to selection** (`K`, or its bottom-row lamp, **Toggle Add to Selection**) is a sticky `Ctrl` for that gesture: while it is lit, a plain click or tap on a flag's own box does exactly what `Ctrl`+clicking it does — adds or removes that one marker and leaves the rest standing. It is there for the touchscreen, which has no modifier keys; it works the same under a mouse. It reaches flags and nothing else, a held `Shift` still wins for that click and leaves the lamp lit, and it stays lit until you press `K` again, or until **an act spends the selection you built**: a value step, a delete, `Ctrl+D`, `Ctrl+N`, the copy, either paste, opening BPM iterations, turning grid iterations on, or the history view's revert. That is the whole of it — if you have acted on the markers you gathered, the gathering is over. Nothing else puts it out: not a walk, not a click somewhere else, not an undo, not loading a render in place, and not a refused act, which spent nothing. Opening another project starts every lamp dark, exactly as launching does — **Add to selection** and **Restrict Undo to Current View** (`Z`) are one family that way, postures you hold over the piece that is open rather than anything belonging to it. **It reaches the flag's own box and stops there.** A `Ctrl`+click or `Shift`+click on a range cell does nothing at all — no selection change, no playhead, nothing — and that is unchanged. But a PLAIN click on a range cell is a plain click however this lamp stands: it selects the marker, brightens the cell you clicked and lands the playhead as always, and it can start that cell's value drag. The lamp only folds the flag's own box into a `Ctrl`+click. **So it stands lit under grid iterations**, and that is the point of the rule — the range cells are the only surface that mode authors on, and a lamp whose whole job is to gather several markers has nothing to say about them, so gathering markers with a fingertip and then tying them is one uninterrupted pass. It used to refuse in there, back when the fold took the whole flag and would have made those cells unreachable by pointer. The other direction is unchanged: turning grid iterations ON puts this lamp out for you, because raising the cells is an act that ends a gathering. The pointer tells you which you are on — over a flag's box while this is lit it shows the ordinary arrow, since the press will toggle membership and start nothing; over a range cell it shows whatever that cell's press will actually do.

**The value drag.** In target view, dragging a flag up or down changes its tempo; under grid iterations it drags the range cells, on either column. There is no key and no button for it — where you are decides it: in source view, and on the phase-reset column with grid iterations off, a flag drag moves the marker as always. Up raises; every eight pixels is one plain arrow step, and the walls are the arrows' walls. A pass drags too, becoming an owning marker as the arrows make it; a label reference or a coincident stack does not (the arrows' own rule), while a disabled marker does, and a flag it cannot change simply does not drag, and the pointer shows the up-down arrow only over the ones it can. A tempo drag is one undo step; a range-cell drag, like every range change, is not undoable.

The playhead follows the focused marker: anything that changes which marker is focused brings the playhead along — the walk, the clicks, opening an editor, `Ctrl+N`, a propagate paste — and a nudge or flag drag carries it, so `Space` keeps auditioning from the marker your next press is about to move. Clicking an empty spot in the marker lane works like an upper-half waveform click; double-clicking an empty spot creates a marker there — exactly the `S` drop, in the collection's home view only.

On screen, each marker is a small colored flag in the lane above the waveform, carrying its text — the tempo or label for a warp marker, the word `reset` for a phase reset — with its stem running down through the waveform. Text longer than nine characters is shortened to nine plus `...`. With grid iterations on — and in the column you turned them on in — a warp marker that owns its tempo grows two more cells to the right of its flag, in the flag's own colour — its range's lower bound, then its upper bound, each a signed value like `+0.00` or `-0.02`. Flags of nearby markers may overlap; the later marker paints on top, and clicking lands on whichever flag you see. A disabled marker dims its flag and shows no stem — and shows no range cells, because a disabled marker can never carry a range: you cannot disable anything while the lamp is lit, and a marker disabled before you turned it on shows no cells to author. Selection is a brightness cue: the selected flag brightens and so does its stem, so the selected markers stand out on the waveform even when zoomed far out. A marker that renders as the fallback tempo `1.00` paints its flag and stem **red** — a `label_ref` to a missing or out-of-range label, or a stack of markers sharing one frame (the whole stack reddens as one) — and neither selection nor the disabled dim masks the red — a selected red flag brightens like any other, in red; markers sharing one frame stay red on either column even when some of them are disabled, since two markers on one frame is always an accident. The playhead cursor is the white marker-style head in the marker lane with its white stem below, painted over the markers' stems so a dense run of markers never hides it; when it stands exactly on a marker, the marker's own stem shows in place of the white one — the cursor is still there, and playback still launches from it.

### Warp marker authoring (W view)

The commands that *move* a warp marker run in warp's home view — warp markers in source audio view — and everything else works from both audio views (see The three view axes). Movers: `S` and its empty-lane double-click twin, the flag drag, the `Left`/`Right` nudge, and the `Ctrl+B` BPM command. The keyboard movers answer off home with `Markers are placed in source view` / `Markers are moved in source view`; a flag drag there is the value drag instead, changing the tempo rather than the position.

`S` drops a marker at the playhead copying the previous marker's tempo — so the drop normally splits a section without changing how anything sounds, where a neutral `1.00` drop in the middle of a warped section would audibly change it. (Its shifted form, `Shift+S`, drops a phase reset instead — see Phase reset authoring. With the phase-reset column showing, `S` itself drops on that column.) Two cases are not silent, both by design: dropping onto a frame where an enabled marker already sits leaves two markers on one frame, which the render collapses to a single `1.00` — the markers turn red immediately, so you see it happen; and splitting a *label definition's* section shortens the definition, so every reference to that label changes duration too — a definition's span is its meaning. A label reference just before the playhead is skipped, exactly as a pass skips it: the drop copies the tempo of the marker behind the reference, never the reference's implied rate. Where there is no usable previous tempo to copy — no earlier marker other than references, or a coincident stack — the new marker takes `1.00`; a pass is not one of those cases, resolving to whatever tempo is actually sounding there, which is exactly what keeps the drop silent.

`Up` / `Down` step the value of the focused marker's bright box — its tempo unless you clicked a range cell (see Grid iterations). On the tempo they step by ±0.01, from either audio view — or by ±0.10 with `Shift` and ±0.03 with `Ctrl`, the step ladder — target view is exactly where you want to hear a tempo change. In either view the single-marker press also converts a pass to an owning marker, frozen at the value it was resolving to — but not a label *reference*, which answers `A label reference has no tempo of its own`, its tempo belonging to the definition it points at; in target view a coincident marker answers `That marker shares its frame with another` (the stack renders as `1.00` and is fixed in source view). With several markers selected the step moves every selected marker's own tempo together by the same ±0.01, all or nothing: if any member is a pass, a reference, coincident, or could not take the whole step without leaving `[0.25, 4.00]`, the press refuses whole with `One of the selected markers cannot take this tempo change` — which is why a `Shift` step can refuse a group the plain step would have moved, group members never being clamped apart from one another. A disabled marker steps like any other — alone, in a group, or dragged — its tempo waiting for the day you enable it again. A held run is one undo entry. The two arrow buttons say all of that ahead of the press: both arrows grey on a label reference, and in target view on a coincident marker, while the key still says why; the up arrow greys once the focused marker rests on `4.00` and the down arrow at `0.25` — and one press or ten, the answer is the same, so a greyed arrow is greyed for every version of it, and with several selected both grey whenever that whole-press refusal stands — the card and the grey together, because a group step would have moved every selected value and there is no single place to glance at.

With grid iterations on, `Up` / `Down` can step a marker's range instead of its tempo — and on the phase-reset column a reset's range instead of nothing at all, in hops rather than cents (the reset ranges paragraph below). Each flag grows two range cells — the lower bound, then the upper — and a click on a cell makes it the marker's bright one: the arrows step whichever cell of the focused marker is bright, so click a range cell and the arrows step that bound by the same ladder, click the flag itself and they step the tempo again. Only a clicked cell and a `Tab` walk's own stop brighten a cell; a marker reached any other way — `Shift+J`, a switch of tab or column, an undo — is bright on its main payload, so the arrows step its tempo. A range starts at `+0.00` to `+0.00`, so the first step authors it — and stepping back until both cells read `+0.00` again clears it, exactly as typing `+0.00` into both cells does, so two `+0.00` cells mean no range at all. The lower bound never rises above the upper and the upper never falls below the lower, and neither leaves the window the base tempo allows. The arrows step **the focused marker and nothing else** — ranges are a single-marker business by design, and every way of making a range cell the bright one selects just that marker, so a range step never reaches a group. It stops at those walls silently, the arrow button greying there; a marker without a range answers `Only a marker that owns its tempo has a range` (a pass or a label reference) or `A disabled marker has no range`, and with nothing selected `Select a warp marker to change its range`. ON THE PHASE-RESET COLUMN it is the same paragraph with two words changed: every reset has a range, so the only refusal about the reset itself is `A disabled phase reset has no range`, an empty selection says `Select a phase reset to change its range`, the walls are the reset's own hop walls rather than a tempo window, and the arrows clamp at them silently just the same. The two arrow buttons follow the bright cell on either column — `Lower Bound Up`, `Upper Bound Down` — and a held run simply steps: **a range change is not recorded at all**. It writes no undo entry, so there is nothing to undo it with, and it never marks the piece dirty and never re-renders — a range is not part of the map, moves no marker, and is transient by design. The arrows step a range only in the column grid iterations were turned on in — the other column shows no cells and its flags step tempo as usual, and the `Tab` walk stops on no cells there either. Leaving grid iterations puts a bright range cell back on the payload and clears both columns' ranges at once.

**The wheel over a flag.** A plain wheel detent over any box of a flag selects that marker exactly as a plain click does — landing the playhead on it — and then steps the box under the pointer as `Up` / `Down` would, wheel up raising. It needs no prior selection and works in every view; where the step cannot act the wheel just selects, saying nothing. A run of detents is one undo step. Everywhere else the wheel pans; in the history view it pans over flags too.

`Left` / `Right` nudge the focused marker's position by one painted pixel column (they take no modifier; after an explicit centring they hold the marker's place on screen, above; hold the key or the button for a longer run) — and moving markers is always a one-marker act: with several selected, the press first narrows the selection to the focused one and then steps it. The marker stops at the song edges, and the matching arrow button greys once it is resting on one — the same truthfulness the pair already has with nothing selected, where they grey at the ends of the piece. With several markers selected they stay live even at an edge: that press still narrows the selection and brings the playhead to the focused marker, which is a change whether or not the marker then moves. A held arrow is one undo entry. A plain press moves one pixel column — tens of samples even at the finest zoom — so drop to the deepest zoom for the smallest step, and hold the arrow, or drag the flag, when the marker has a long way to go.

`Ctrl+N` toggles pass (inherit) status on the focused marker. `Ctrl+D` toggles the disabled flag on every selected marker. `Del` deletes every selected marker — label definitions included, even with live references (the orphaned refs render as `1.00`, red-flagged). All three work on either kind of marker where the kind carries the state (`Ctrl+N` is warp-only).

`Ctrl+F` **flattens** every warp marker in the piece: the tempo deviations go, and each marker keeps the number they added up to — `1.23+0.01-0.02` reads `1.22`. `Ctrl+Shift+F` **flattens the deviations** instead: they collapse into one, so `1.23+0.01-0.02` reads `1.23-0.01` and deviations that cancel read `1.23+0.00`. **Both act on the whole piece.** Nothing needs selecting first, a selection is not read at all, and there is no way to narrow either one to part of the piece. Neither changes what you hear — the tempo is the same number either way, so no render and no preview moves — and neither touches a pass or a label reference, which carry no deviations. A marker with none is left alone by both, and one with a single deviation is left alone by `Ctrl+Shift+F`. Both undo as one step. The icon row's **Flatten** button, beside the two iteration buttons, is `Ctrl+F`, its `Shift`+click or long press `Ctrl+Shift+F`.

Dragging a flag moves that one marker — no modifier; the drag begins after a few pixels of motion, so a click stays a click — with the playhead following. The drag has no cancel: `Esc` while dragging does nothing, the release commits where the marker stands, and `Ctrl+Z` puts it back.

`J` copies the focused marker's resolved value to the clipboard — the `base` or `base*scale` text a flag editor accepts, ready to paste into another marker's editor or anywhere outside the program. `Shift+J` goes to the marker that value *comes from* — the owner a pass inherits from, or the definition a ref points at — on the other tab: it centres this tab on the reference first, then switches, lands the playhead on the source marker, selects it, and centres there too, so the reference stands on one tab and its definition on the other, one `Ctrl+Tab` apart. Both are read-only-legal and work with grid iterations on. An ineligible focus — an owner, a disabled marker, nothing focused — answers `The focused marker has no resolved value to copy` (or, for `Shift+J`, `The focused marker has no resolved value` / `There is no source marker to jump to`); a pass or a ref sharing its exact frame with another marker answers `The focused marker shares its frame with another, so its value is not what the render applies` — the render collapses such a stack to a plain 1.00, so the value the flag would resolve to is not the one you hear — and the button greys, the key saying that reason on a card. The bottom toolbar's **Copy resolved value** button is `J`, its `Shift`+click or long press `Shift+J`.

**The flag editor.** `Return` or keypad `Enter` — one key to this program — the **Edit Flag** button, or a double-click on the flag opens the focused marker's flag editor — the canonical-line surface where the marker's line is edited as text: tempo, `label_def` / `label_ref`, per-marker scale. It is the only surface for authoring labels and per-marker scale, and it never carries a range: each range cell is a mini flag with an editor of its own (see Grid iterations), and `Return` opens whichever cell of the focused marker is bright — the flag's own unless you clicked a cell, the **Edit Flag** button's tooltip naming which. It opens with the whole line selected, so typing replaces it; `Return` commits — invalid input flashes the field red, keeps it open, and a notification says what was wrong — and `Esc` exits without committing. While it is open the keyboard belongs to the editor, and the ordinary text-field gestures work: typing, `Left`/`Right`, `Home`/`End`, `Shift` with those to select, `Ctrl+Left`/`Ctrl+Right` by word, `Backspace`/`Del` and their `Ctrl` word-erase forms, `Ctrl+A`, `Ctrl+C`/`Ctrl+X`/`Ctrl+V`, double-click to select a word, `Shift`+click to stretch the selection. With the mouse, dragging across the text selects it. On the tablet, dragging a finger across the text moves the cursor along with the finger instead — a tap places it, a double-tap selects a word, and there are no selection handles. On both, a double-click or double-tap that goes straight into a drag extends the selection a word at a time. The clipboard is the system's own on both machines, shared with every other program on them — what you copy here pastes into a browser or a note, and what you copy there pastes in here. `Ctrl+X` is the one clipboard chord that can refuse: if the system will not take the text, the cut keeps your selection and says `The clipboard did not take the cut` rather than deleting text that went nowhere. Everything else does nothing at all, so a stray chord cannot throw the edit away; the two chords that reach through are `Ctrl+S` and `Ctrl+Q`. There is no undo inside the editor. While it is open the marker's other boxes — its range cells, with grid iterations on — stand where they always do, at the field's right edge, sliding along as it grows and shrinks. **Every editor on the row works this way**, whichever box you opened: the box you are editing becomes the field, the boxes to its left stay exactly where they are, and the boxes to its right ride the field's edge and slide as you type. Open the lower cell and the upper one rides; open the upper cell and nothing rides. The editor opens at its own box's width, so nothing on the row shifts until you type — with one exception: if the label was long enough to be shortened to nine characters plus `...` (see above), the flag editor opens showing the whole untrimmed label, so the boxes to its right shift immediately, before you type anything. Short of that one case, each box opens as exactly the box you clicked, and only their colour and their grammar tell them apart. Emptying a field leaves the smallest possible box, on any of them. A field near the edge of the window is not pushed back on-screen: it opens where its box is and the window cuts it off, exactly as it cuts off a flag sitting half off the edge — pan the view to read the rest, which works while the editor is open, and the field travels with its marker. The mouse closes it: clicking anywhere but the editor's own text abandons the edit, and the click then does its normal work — those boxes included, since they are still the marker's own cells: clicking one closes the editor and brightens that cell exactly as clicking it at rest would, and double-clicking one opens its own editor. These text-field gestures are shared by every editor in the program — the bottom row's dialogs and the marker boxes' editors alike. Every field has a byte cap of its own, and the cap is the longest thing that field can accept — no field lets you type further than it will commit (five for a warp marker's range cell and two for a phase reset's — a sign and one digit is all a hop cell can hold — sixty-eight for a flag line, forty-four for the BPM bracket; the free-text fields are simply generous): typing into a full one says `This field is full`, and a paste too long for what is left says `The pasted text is too long for this field` and pastes nothing.

### Phase reset authoring (P view)

These author phase resets, in target view — the only view the phase reset column appears in, and where the lead-in and its overlay live.

In target view, `S` drops a phase reset seeded `N/2` samples earlier in target time than the playhead (clamped to the file start, snapped to the nearest whole source frame), and the playhead moves back onto the seeded reset — the one drop that relocates the playhead, so the next audition starts at the new reset. The lead-in arithmetic is the engine's: a reset seeds from the synthesis window whose centre lies at or just before it, whose content is replayed as it stands and whose crossover into the new phase dips for about a hop after the reset; both are over about `N/2` samples past the reset, so placing it `N/2` before the point you marked is the least that puts that point past the crossover and outside the seed's own window — at full level, with the new phase settled, and on the map. One hop is not enough: the marked point would still sit inside the seed's tail. The output-domain overlay depicts the seed's remaining extent, for a single focused reset in target view: from the reset to where its window ends, on the engine's own hop lattice, so the band's far edge stands still as a reset is nudged within one hop — the band shortening or lengthening toward that edge as the marker itself moves — and the far edge jumps a whole hop when the reset crosses into the next — the moment the render actually changes; its widest is about `N/2`.

`Shift+S` drops the same phase reset **from any view**: it switches to target view and phase reset view for you, then drops the same lead-in reset **for** the playhead's own musical instant — `N/2` ahead of the reset, exactly as `S` does in target view — and leaves it selected with the playhead seated on the reset — so a reset noticed while you are looking at the warp column costs one key instead of a trip across and back. With the phase-reset markers already showing it refuses and says `Already in phase reset view` — the chord *is* the crossing, and there is nothing to cross; use `S` there. One press is one undo entry, and undoing it returns you to the view where the reset was made. The bottom row's **Drop marker** button reaches it too: `Shift`+click, or press and hold.

In target view, `Space` auditions the alignment by starting playback `N/2` samples ahead of the playhead without moving it — past the seed's window, on the point the drop protects. It does this exactly when a phase reset is *focused* — the same condition that makes the overlay meaningful — and the drop's offset and the audition's are deliberate inverses, so dropping with `S` and pressing `Space` auditions from where the cursor was sitting — exactly so when the piece is being sped up, and within a couple of samples when it is being slowed, the reset having been snapped to a whole source frame in between.

`Ctrl+D`, `Del`, and the `Left`/`Right` nudge work on phase resets exactly as on warp markers, with the same one-marker nudge rule — except that on the phase-reset column each press is one HOP, for the reset and for the playhead with nothing selected alike (`Right` then `Left` puts a reset back where it was): a reset only changes what you hear when it moves to another hop, so that is the column's step. Coincident phase resets on one frame paint red, like a warp stack.

Placement judgment: phase resets go where loud transient content provides masking; a quiet, exposed passage should carry one phase reset at its start and nothing else, since a reset during exposed material has nothing to hide behind. Nudge a reset only when the phase alignment causes an audible dip, pop, or crackle — each press moves one painted pixel column, so drop to the deepest zoom for the smallest step.

### Propagation

**Three chords carry a labeled region's phase resets** from one occurrence of a label to another: they anchor on a warp-marker selection and are refused on a read-only tab, the copy wants a consecutive RUN, and **the two pastes want exactly one marker and refuse a multi-marker selection whole**, on a card — they never quietly take the first of several. All three live in the Edit menu, their one mouse home, and all three put the **Add to selection** lamp out — a copy or a paste being an act on the selection you had gathered.

**Phase resets.** `Ctrl+P` copies: with one or more warp markers selected, forming one consecutive run, it captures the phase-reset layout of each selected marker's own section into the session clipboard — a marker's section runs to the next enabled marker, the final one's to the end of the song; unlabeled markers inside the run contribute nothing, and a disabled selected marker contributes no section of its own (the span under it belongs to the preceding enabled marker's section, so the resets lying there travel with it). `Ctrl+Alt+P` pastes: anchored on exactly one selected warp marker, it materializes the clipboard's resets onto the destination region after a confirmation prompt. What is scaled to the destination's durations is not where each reset *sits* but where it was *aimed* — the point `N/2` ahead of it, which is the point `S` and `Shift+S` place it for — and the destination's own reset is then worked back from that point exactly as a drop works it back from the playhead. So a reset dropped on a marker comes out the same lead-in ahead of the corresponding destination marker however far apart the two sections' tempos are, and one sitting elsewhere in its section keeps its proportion of the section as before. `Ctrl+Alt+Shift+P` pastes state only: it aligns the enabled/disabled flags of the destination region's existing resets to the clipboard, in order, moving nothing, with no prompt. All three apply a 100 ms tolerance when deciding which block a reset belongs to, and they measure it at the aimed-at point: one aimed within 100 ms before a block's owning warp marker counts as part of that block and is captured with it. A reset dropped on the marker needs no tolerance — it is aimed at the marker — so what the tolerance is really for is one you have nudged off a boundary by hand. The aimed-at point is a musical point, so it is allowed to fall past the end of its own section and is scaled as it stands; the only thing clamped is the resulting position, to the file's own start and end. The propagate is the one authoring action that starts in warp view and ends in the phase-reset target view: a paste that did something leaves you in target view with the phase-reset collection active, one that created resets selecting exactly those it created with the playhead on the first. A paste that got nowhere does not move you — one that found no block to work on, or that stopped on a mismatch at the very first block, leaves the view exactly where it stood and says so on a card (`Nothing matched, so nothing was pasted`, or where it stopped), rather than changing the scene in a way that would look like a paste. A paste that did work on a block takes you across even where it found everything already as the clipboard wanted it. A copy or paste with the wrong selection says which selection it needs (`Select one consecutive run of markers`, `Select exactly one marker to paste onto`); a paste with nothing captured says `Nothing has been copied yet`.

### Trim and the region

The trim window is what makes working on a passage quick: a render covers the window rather than the whole piece, so a stretch you are shaping comes back in a fraction of the time — and in target view, what you hear is that same window, start to end. The window is a pair of bounds that always rests somewhere — it starts at the whole song — and it is always on display in the trim band, the slim bar above the ruler with an endcap at each end. That bar is nine pixels tall, which is right for a pointer and hopeless for a fingertip, so while you sweep a new window the waveform draws it across its whole height: that drawing is the **region**. It is not a copy and not a scratch span you commit later — it is painted from the trim window every frame, so the bar and the region can never disagree.


The trim is written on the trim bar — drag an endcap to move that bound, drag between them to slide the whole window keeping its width, `Ctrl`+click / `Ctrl+Shift`+click to set the begin / end — or swept outright: `Shift`+drag sweeps a new window from where you pressed to wherever the pointer is, with nothing to commit afterwards. The region appears with the first bit of window the drag writes — so what you see is the stretch you are making, never the one you are replacing — and goes away again the moment you let go: a sweep says "this exact stretch", and once you have said it the big drawing is in the way. The region exists only while a sweep draws it; there is no key that shows it at rest. The sweep works on the whole waveform, both halves; on the ruler and the marker lane's empty stretches a `Shift`+click just places the playhead, and on a marker's flag `Shift`+click is the range select instead. A sweep sets exactly the window you draw, however narrow — there is no minimum width — and a stroke that ends where it began resets the trim to the whole song, the same escape a bound drag has: dragging one bound onto the other and releasing them coincident opens the window back to the whole song, and so does `Shift+0` (the full zoom out button's `Shift`-click or long press). Nothing is said about it — the trim bar's endcaps jumping to the song's ends is the answer, and a whole-song window changes nothing about what a render produces.

Every trim write parks the playhead at the new trim start and clears the marker selection: the sweep at its release, the bound-set clicks, an endcap or bridge drag at its release, `Shift+0`, and a typed `trim_begin=`/`trim_end=`. What you hear next starts there. `Shift+0` resets the window to the whole song and puts the playhead at frame 0 (already full, it does nothing and says nothing — the trim bar spanning the window is the answer). Without a keyboard, drag one endcap onto the other on the trim bar: releasing them coincident opens the window back to the whole song. Trim sits outside undo: an edit commits the moment you make it and no gesture has a cancel; `Shift+0` is the recovery. Trim is per-tab view state — every trim gesture works on a read-only tab.


**The trim bar** (mouse). `Ctrl`+click moves the begin bound to that spot and `Ctrl+Shift`+click the end bound — at the release, and dragging instead of letting go carries the bound on like an endcap drag; a click that would land a bound on or past its partner moves nothing and says `A trim bound must stay inside its partner`. A plain drag on an endcap drags that bound (ten pixels of slack each side); a plain drag on the bar between them drags the pair as a fixed-width window; a plain click that never becomes a drag does nothing — nothing on this bar summons the region, that band being small enough to mean you have a pointer in your hand. When the window is wide enough, a small square outline marks its midpoint, purely informational. A window drawn narrower than about twenty-four pixels puts the two endcap slack bands over the whole bar, so the bridge drag needs a zoom in first. Release snaps each moved bound to its painted pixel column. Only one trim falls back to an untrimmed render: a window whose rendered span would round below one output sample — a refusal at the render, never a failed render. It says so on a card, `Trim window too small to render; rendering untrimmed`, when you enter target view with such a window standing and when you press either render chord.

### Grid iterations (`I`)

Both modes below are front ends for one workflow: render a spread of variants into `tmp/`, audition them in the render player (`L`), and load the one you want in place as the new baseline (`'`). They differ in what they vary. BPM iterations author warp tempo and so belong to the warp column, answering `BPM iterations work on warp markers` from the phase-reset column; grid iterations work in BOTH columns — a warp marker's range varies its tempo, a phase reset's range varies its position — and refuse in neither, though one press of `I` lights them for ONE column, the one you were looking at. Both are refused on a read-only tab, and they are mutually exclusive **by refusal**: with grid iterations lit, `Ctrl+B` says `Turn off grid iterations first` and **BPM Iterations** greys, so you leave the mode with `I` yourself — nothing turns a lamp off for you, and no range is ever cleared behind your back. Their mouse home is the icon row's iteration pair — **BPM Iterations** and **Toggle Grid Iterations**, the first two buttons behind their own separator just before play renders.

Grid iterations vary a marker's base tempo by a small additive offset. `I` toggles the mode, from either column; pressed in source view it switches to target view first, grid iterations living in target view alone. The icon row's **Toggle Grid Iterations** lamp lights while it is on — greyed while EITHER tab is locked, where it says `I is not available on a read-only tab`, because the two tabs share the same markers and a lock anywhere is a lock on what the ranges tune, and no longer greyed by **Add to selection** at all — turning the mode on PUTS that lamp out, raising the range cells being exactly the moment a selecting pass has ended; the switch back to source view and the W/P switch are both refused while the lamp is lit (**The ranges land wherever you are looking**, below). The lock runs the other way too: with the lamp lit `O` refuses on either tab and the padlock greys, so you can never end up locked and lit at once.

**While the mode is on, the piece is locked. Anything you want to do, do before turning grid iterations on.** The ranges are the only thing you can author with the lamp lit: the cells, their arrows and their editors work, and nothing else that would change the piece does. Dropping, deleting, disabling, moving, editing a flag, pasting, changing an engine setting, loading a render in place, opening the history view, switching the marker column, walking both tabs and opening BPM iterations — all of them refuse while the lamp is on, on a card that says `Turn off grid iterations first`, and their buttons go grey. (**Add to selection** was on that list until 2026-09-19 and is not any more: it stands lit in here now, and gathering markers with a fingertip is how you build a tie.) So do **undo and redo**: `Ctrl+Z` says `Turn off grid iterations to undo` and `Ctrl+Shift+Z` says `… to redo`. Everything that does not change the piece still works exactly as it always does — playing, the A/B audition, moving around, zoom, the A/B tabs, trim, saving, both render chords, the clipboard copies, Synchronize, opening another project, and quitting. One key is admitted BECAUSE it leaves the mode: `I` itself. The BPM opener (`M` then, `Ctrl+B` now) was a second until the swap it did was ruled out — it turned grid iterations off and opened BPM iterations in one press — and it now refuses like everything else, so `I` is the one way out. One other lamp refuses while this one is lit — **Add to selection** was the one exception until 2026-09-19, when the sticky `Ctrl` narrowed to the flag's own box and stopped taking the plain press the range cells are reached by, so `K` is admitted in here and the two lamps stand together; turning the mode ON still puts that lamp out for you, a raised range cell ending a gathering. It is the read-only lock's shape with the range cells let through, and the two never overlap: locking EITHER tab refuses while the lamp is lit — `O`, and a typed `tab_A_read_only=true` or `tab_B_read_only=true` — and the lamp will not light while either tab is already locked. The tabs themselves are untouched: `Ctrl+Tab`, `Shift+Space` and `Shift+J` all switch tabs under the lamp exactly as they always do. Turning the lamp off is always one press of `I` away.

**Ranges are not remembered.** They are transient by design: they never go in the undo history, they never light the unsaved mark on the clock, and nothing about them is written to a sidecar — what a sweep leaves behind is the files in `tmp/`. So a range exists only while it is on screen, and turning the lamp off is the end of it: there is no undo that brings one back. That is also why the lock is as wide as it is — with the ranges outside the history, an edit made under the lamp could not be told from one made before it.

**The ranges land wherever you are looking.** `I` lights the mode for the column you press it in — warp or phase reset — and that is where the cells appear, where the arrows and the cell editors work, and what `Ctrl+Alt+R` sweeps. **You cannot leave that column while the lamp is on**: the view keys `1` / `2` / `3` and a typed `active_markers_view=W` or `active_markers_view=P` in the settings editor all refuse with `Turn off grid iterations first`. The view bar's three buttons stop answering the mouse too — a click on `S+W`, `T+P` or `T+W` does nothing at all while the lamp is lit — and the two views you are NOT in dim their labels to say so, while the view you ARE in keeps its bright label, since where you stand is still true. The outline that normally follows the pointer stops with the press, and pressing the key says it in words. A typed `active_audio_view=S` refuses too, the mode living in target view, while `Ctrl+Tab` still works, the two A/B tabs sharing one set of markers, so a range belongs to both. `Ctrl+Shift+Tab`, the march that walks both tabs at once, is the one tab chord that refuses, and for its own reason rather than the column's: it switches tabs in the middle of itself, which drops the selection, so its second step could never land on the cell the first one did. Its buttons — the other tab's `Shift` press and the marker walk's `Ctrl+Shift` press — stay lit, since their plain `Ctrl+Tab` still works, and say the same sentence. Press `I` again and the mode goes off, clearing every range as it always has: for good, nothing about a range being kept in the undo history.

With the mode on and the warp column lit, every warp marker that owns its tempo shows its range as two cells beside its flag — the lower bound, then the upper — and each cell is a mini flag of its own, authored three ways. Stepped: click a cell and press `Up` / `Down` to step that bound (the arrows paragraph above has the details). Dragged: drag the cell up or down — the same eight pixels to a step, the same walls. The flag itself does not drag while the mode is on, the piece being locked; the range cells are the only thing a drag can move. Typed: double-click a cell — or click it and press `Return` — to open its editor, which holds that one bound as a signed two-decimal value, the sign and both decimals mandatory (`+0.00`, not `0`); `Return` commits it, `Esc` leaves it, and committing an empty field clears the whole range. A typed bound must keep the lower at or below the upper and the base tempo plus the bound inside the tempo bracket `[0.25, 4.00]`, or the cell red-flashes and says which. The range steps in 0.01 increments, inclusive: cells reading `-0.02` and `+0.00` enumerate the offsets −0.02, −0.01, and 0.00. Several markers can each carry a range; `Ctrl+Alt+R` then renders the full Cartesian product of the lit column's ranges — one file per combination, into a batch folder under `tmp/` — and turns the mode off as it fires. A disabled marker is invisible to the sweep, as it is to BPM iterations, and it can never carry a range in the first place: you cannot disable anything while the lamp is on. The product is capped at 1,000 cells: a wider one is refused before any folder is made, with the mode and its brackets left standing so you can narrow them and fire again. A sweep that finishes short — some cell failed to write — says `Rendered N of M` on a card at the end, counting the cells it dispatched; a complete sweep, and one you cancel, say nothing. Both of those states — no bracket authored anywhere, and a product past the cap — grey the `Render` button while the mode is on; `Ctrl+Alt+R` says which on a card. A degenerate range whose two cells agree — `-0.02` and `-0.02` — sweeps a single value; a range stepped or typed back to two zeroes clears, so two `+0.00` cells mean no range at all. Ranges are session-only and never serialized; exiting the mode by any route clears them all, and nothing brings them back. There is no such thing as a tempo change under a range any more, nor a `Ctrl+N` or a `Ctrl+D` under one: the lock refuses all three while the lamp is lit, so a range always sits on the marker and the base tempo you left it on.

**Tying markers into one axis.** Select two or more markers and press `Ctrl+Shift+N` — or `Shift`+click or long-press **Toggle Inherit** — to tie them into ONE axis of the sweep: every cell then applies the same offset to each tied marker, relative to that marker's own value, and the grid shrinks by exactly the axes the tie absorbs — three markers with the first two tied make a 3 × 2 grid rather than 3 × 3 × 2. The file names follow: one entry per axis, the tie's standing where its first member does, so those six cells read `-0.02,+0.00` through `+0.00,+0.01`. A tied marker shows the first member's range in its cells, greyed, and nothing is authored there — the first member's cells are the tie's one range, and its walls are the tightest member's, so no cell can put any of them outside the tempo bracket. `Ctrl+Shift+N` again unties them; ties work on either column and are session-only like the ranges themselves.

**Ranges on phase resets.** Press `I` in the phase-reset column and every enabled reset shows the same two cells, in the reset's own blue — but its range varies its POSITION, not a tempo, and it counts in **hops**. One hop is one step of the analysis lattice the engine seeds a reset on: nudging a reset within one hop renders exactly the same audio, and one hop is the smallest move that changes anything. So a cell holds a whole signed number and no decimals — `+2`, `-3`, `+0` — which is how you tell a reset's cells from a marker's at a glance, and the range is capped at a single digit each way: past nine hops it is no longer the reset you placed. A cell at `+2` moves the reset exactly two hops later, keeping where it sat inside its hop, so every cell is your own placement carried along the lattice. `Up` / `Down` step the addressed cell by hops, and a double-click — or `Return` on a clicked cell — opens the same editor, holding a sign and one digit (`+0`, not `0`); an empty commit clears the whole range, as on the warp column.

A typed hop bound must be a sign and one digit, must keep the lower at or below the upper, and must not send the reset off the piece: before the first frame, or past the last. The cell red-flashes and says which — `a hop bound is a sign and one digit, as +0`, `the cell would leave the piece`. There is no typed way past nine: the field holds two characters and the editor takes one digit, so a tenth hop cannot be spelled at all — the single-digit cap is what `Up` / `Down` stop at, and they clamp at the piece's ends the same way instead of refusing. A reset cannot be disabled while the lamp is on. Ranges on neighbouring resets may cross or meet, and nothing refuses them: a cell where two resets land on one frame renders them as one reset, exactly as two coincident resets at rest do, and a cell where they cross renders both where the cells put them. Your ear is the judge — if two ranges that close is a contortion, you will hear it, and the way back is the same as ever.

The walls are checked as you author, and they stay put: nothing that could move one — nudging or dragging the reset, editing a warp marker's tempo, undo — is admitted while a range stands. So a range you typed inside its walls is still inside them when you fire.

A sweep is one column's, so the file names carry one list: a warp sweep is named as it always was (`03_+1.50,-0.50`) and a reset sweep reads `03_+2,-3`, the decimals telling the two apart at a glance. Loading a cell in place recalls the whole recipe, a displaced reset included. Reset ranges are session-only like marker ranges: they are never written to the sidecars, and exiting the mode by any route clears both columns at once.

### BPM iterations (`Ctrl+B`)

**What it is for.** You have a stretch of the piece — say the first 36 beats of the recapitulation — and you want to hear it at 210, 211, ... 220 BPM to pick the one that sits right. Instead of computing a tempo factor by hand for each, you tell the program how many beats the stretch holds and the BPM range you want, and it renders one file per BPM into `tmp/` for the render player to audition; the one you like, you load in place as the new baseline.

**What a span is.** Every warp marker owns a section: from itself to the next marker that actually takes part in the render. Disabled markers don't count — they never close a section, so a section runs straight past them, and a marker followed only by disabled ones owns everything to the end of the song. The span you sweep is the run of sections owned by the markers you select: the first selected marker is the owner — its tempo is what gets rewritten — and the span ends where the last selected marker's section ends, at the next enabled marker after the selection or at the song's end.

**What happens per cell.** For each BPM in your range the program takes the span's measured length in the source and your beat count and works out the base tempo and the scale that reach it. The owner marker takes the base tempo, its own per-marker scale cleared; the scale goes to the cell's global `scale` setting. Every other enabled marker inside the span becomes a pass, so the whole span plays at one tempo. Then it keeps the rest of the piece in proportion: every enabled owning marker outside the span is rescaled by the same ratio the owner's tempo moved, rounded to the nearest cent — so re-tempoing one section re-tempos the whole piece uniformly instead of bending only the selected span. Disabled markers are untouched inside and out, and keep their old tempo for when you re-enable them. What the render normalizes to `1.00` on its own — the stretch before the first marker, a leading pass, a red-flagged reference — stays at `1.00` in every cell.

**The refusals** — the cards the program shows, each naming the first rule the selection broke:

- `BPM iterations work on warp markers` — the phase-reset column has no tempo to sweep.
- `BPM iterations work in source view` — the mode derives tempo from source durations.
- `Select the markers whose sections to sweep` — nothing is selected.
- `The selection no longer matches the markers` — a stale selection, a belt you should not see in practice.
- `Select one consecutive run of markers` — a disjoint set has no single-span meaning.
- `A label reference lies inside or at the end of the span` — a reference takes its tempo from its definition, so it can neither be rewritten nor bound the span.
- `The first selected marker must own its tempo and be enabled` — a pass, a reference or a disabled marker cannot own the span.
- `The first selected marker shares its frame with another` — a coincident stack renders as `1.00`, so a span owned from inside one cannot take a tempo.
- `Selected markers carry different tempos` — the span renders at one tempo, so every selected marker must be a pass or carry the owner's own value.

**The editor.** `Ctrl+B` on a valid selection opens the BPM editor on the bottom row; the field is authored as `<beats>@[<lo>,<hi>]` — for example `36@[210,220]`, meaning the span holds 36 beats and should render once at each integer BPM from 210 to 220 inclusive (BPM bounds live in `[10, 400]`). Every part of it has one spelling: the beat count is a plain positive number with no leading zeros — `036` is refused exactly as a malformed bound is — and each bound is written the way the program writes it, so `210` and `210.5` are accepted where `210.0` and `210.50` are not. The beat count and the span's measured duration fix the source tempo, so each target BPM resolves to a concrete base-tempo-and-scale pair. `Return` renders the sweep — one file per BPM, into a numbered batch folder under `tmp/` — and closes the mode; `Esc` abandons it, and re-entering always opens on an empty field. A commit whose derived tempo or scale would leave its bracket at either end of the range, or whose rescaling would push any marker outside the tempo bracket, is refused whole with a red flash and a card — never clamped, which would silently mistune the span. The mouse road is the icon row's **BPM Iterations** button, which greys whenever `Ctrl+B` would refuse — so the grey says in advance that a press would have been answered by one of the cards below — and greys while that other lamp is lit, where `Ctrl+B` says `Turn off grid iterations first`.

Loading a BPM cell in place (via `'`) rewrites the span's tempo: the cell's frozen sidecars carry the rewritten markers, the computed global scale, and a `bpm` descriptor in the settings — for example `36 beats @ 220 bpm from 00:32.008 to 00:46.562` — recorded for provenance only; the engine never reads it, though like every engine setting it participates in render identity.

### Settings (`;`)

Bare `;` opens the settings prompt — the bottom row's editor, whose field takes a line typed as `key=value` — in a writable tab (a locked tab refuses; the prompt reaches the engine keys). The line splits on the first `=`, so the value may itself contain `=`. The prompt accepts any printable character; the free-text values (`title`, `bpm`, `notes`, `url`, `cover`, `projects_repo`) carry them verbatim, while keys and restricted vocabularies stay plain ASCII. A value the key does not take is refused at commit with a red flash and a card naming the reason.

Every key that can appear in a `.settings` file is settable here — the engine keys and every GUI-kind key (`active_audio_view`, `active_markers_view`, `active_tab_view`, and the per-tab `viewport_start` / `zoom` / `playhead_cursor` / `trim_begin` / `trim_end` / `read_only`) — plus the five per-device settings `gui_scale`, `max_waveform_height`, `projects_repo`, `projects_path` and `sync_path`, which are written to their own config file the moment you commit them. A GUI-kind commit behaves exactly like the key's own gesture: same code, immediate effect, not undoable, persisted on the next `Ctrl+S`. Keys for the inactive tab write that tab's stored state — which is also how you set a locked tab's trim from the unlocked one (`tab_b_trim_begin=...`). A trim bound committed onto or across its partner resets the pair to the song edges, exactly as the gesture does.

`Tab` after a key fills in that key's current value for recall and editing — type `notes=`, press `Tab`, and the line becomes `notes=` plus whatever is stored. `Tab` follows one rule in every bottom-row editor: it completes if there is anything to complete, and otherwise steps between the field and the buttons. `Return` (or `OK`) commits, `Esc` (or `Cancel`) cancels.

Four settings fields are provenance: carried in `.settings`, never read by the engine, but part of render identity, so editing one makes the next render fresh. `bpm` is written automatically when a BPM cell is loaded in place; `url`, `notes`, and `cover` are free text you type here. None is value-validated — any single line is accepted, empty included — though like every key the line itself must be present in the file.

### Rendering (`Ctrl+Alt+R`)

`Ctrl+Alt+R` is the pipeline's destination. With grid iterations on it renders the whole grid; everywhere else it is a single one-shot render of the current authoring state, written into the project's `render/` folder — the WAV deliverable named by the `title` setting, the folder created for you the first time, the frame-map pair going to `~/.cache` (see Output and the limiter). It is the only render that lands in `render/`; everything else goes into `tmp/` batch folders. A successful one also clears `render/` of every other pair, so changing `title` and rendering again replaces rather than accumulates. (The headless CLI writes the same deliverable but does no clearing.) A **failed** one says so — `Render failed: <reason>` on a notification card — and takes its own output with it: the deliverable wav and its `.fingerprint` are removed, so `render/` is left empty rather than holding a wav that no longer matches what you authored. The missing audio is the clue. A render you cancel yourself leaves the old deliverable alone; a successful render says nothing at all.

A render dispatch kills the running render and takes its place; `Esc` stops both the running render and any parked command behind it. A dispatch identical to the running render simply restarts it — cheaply, through the fingerprint reuse below. An output path that resolves to the source audio itself is refused rather than overwritten (change the `title` setting).

Before rewriting an existing same-title deliverable, the render checks that output's `.fingerprint` sidecar: if it exactly matches the current authoring inputs and the on-disk WAV identity, the render finishes immediately and writes nothing — the deliverable has proved it is already current. The `.fingerprint` records the exact render identity: source identity, markers, phase resets, the full settings block (provenance fields included), and trim bounds. It is not audio and is safe to delete; deleting it just prevents that output from proving itself current. Do not hand-edit it.

`Ctrl+Alt+Shift+R` renders one **miscellaneous cell**: the exact same render a plain-mode `Ctrl+Alt+R` would produce, but written as the next numbered WAV inside the most recent `N_miscellaneous` folder under `tmp/` — so one-off keepers accumulate as ordinary batch entries, auditionable in the player and loadable in place, instead of overwriting the deliverable. With grid iterations on it renders nothing and says `Turn off grid iterations to render one file`. The `Render` button's `Shift`+click is this chord.

The batch dispatches — the grid and BPM iterations — render into numbered folders under `tmp/` (`N_iterations` / `N_bpm`); `Esc` between entries drops the remainder.

### The render player (`L`)

`L` opens the render player: an in-program player for the WAV files this project has produced — open it, see the renders, start one, with no external program and no leaving the app; it is the same on the laptop, on the tablet, and in the car. It refuses to open with nothing to play, saying `Nothing to play: no renders under tmp/`. It also refuses while a render is running, saying `Render player is unavailable while rendering`.

A list appears across the window — always the same band, everything between the icon row and the bottom row, the menu row and the icon row staying in view with `File` still open and the rest greyed — and the bottom row becomes the player's transport for as long as it stands. **It opens inside the newest batch folder** — the one from the most recent sweep or single render — with the highlight on its first file, rather than on `tmp/`'s own list of every batch folder the project has ever produced; a project with no batch folder yet, or whose newest one holds nothing playable, opens on `tmp/` itself instead, exactly as before. Walk into a folder the ordinary way and the `Up` button — or `Backspace` — walks back out. Going up stops whatever is playing and unloads it, leaving the player as it is when it has just opened, with nothing loaded — and the highlight lands on the folder you just came out of, so `Return` (or `Play`) walks straight back into it and the next `Play` starts its first file from the beginning. Walking *into* a folder remembers nothing: the highlight sits at the folder's top, or on the file that is playing when it lives in there. `tmp/` is as far up as it goes, and the `Up` button is grey there. The deliverable in `render/` is not listed at all: it is the file you hand to someone else, and it carries no recipe to load in place. Each listing is read when you enter it. While the player stands it owns the whole window above the bottom row: every button is covered or greyed, and clicks anywhere else do nothing. The one exception is the `File` menu, which stays open above it — `Quit` and `Synchronize to External Storage` work from there, `Open Project` and `Revert` are greyed. `Ctrl+S` and `Ctrl+Q` are the only keys that reach past the player — saving still works, and `Ctrl+Q` quits with the player closing first. On the tablet, closing it is the `Close` button, and File → `Quit` is the only way to quit from in there. A running render carries on in the background while you listen. `L` and `'` both work on a locked tab — playing a render changes nothing; loading in place is what the lock refuses.

**A click opens the row** — one click or one tap: a folder is entered, a WAV starts playing from its beginning. `Return` does the same to the highlighted row; `Up`/`Down` move the highlight — and only that, stopping silently at the top and the bottom of the listing — the wheel scrolls a row per detent, and `Backspace` — or the `Up` button on the transport row — goes up a folder. The head unit's previous button goes up a folder too, from the top of a listing or from the first file of a playing folder (see the car, below); nothing on the tablet's keyboard does but `Backspace`. What is playing and what is highlighted are two different things: the playing item keeps its own place, wears the play glyph on its row, and goes on playing while you move the highlight and while you walk into a folder. Going *up* is the one move that stops the sound, and it unloads the file with it — nothing is left loaded.

The transport row reads left to right: previous (`Home`), `Play`/`Pause` (`Space`), next (`End`) — the same three buttons on the same three keys as the main window's transport, though the right one plays the next file here rather than jumping to the end — the progress bar, the clock (`<position> / <length>`, in the toolbar clock's own monospace), the `Toggle Repeat One` lamp (`R`), `Up` (`Backspace`, grey at `tmp/` itself), then load in place — a checkmark, the same one the icon row wears for the act (`'`) — and close, an X (`Esc`), at the right. Every button on the row is an icon; hover one for its name and key.

- `Play`/`Space` goes wherever the highlight is pointing, and falls back on the transport: on a folder it opens it, on a WAV that is not the one playing it plays that file — even in the middle of something else — and on the playing file itself, or with the highlight nowhere, it pauses what is playing, resumes what is paused, and starts the current file from its beginning when nothing is going. So `Return` is the spatial key and `Space` the temporal one, and they part company in one place only: on the file that is already playing, `Return` restarts it and `Space` pauses it. The button says which: it wears the pause bars only when a press would pause, and the play triangle whenever a press would play something.
- At the end of a folder, with `Toggle Repeat One` off, the player simply stops on the last file, at its beginning, and the next `Play` plays that last file again. To hear the folder from the top, `Shift+Home` (or a `Shift`+click or long press on the skip-back button) goes to its first file.
- `Home` and `End` are previous and next. `Home` goes to the start of the playing file — and inside its first three seconds, to the *previous* file of its folder, the way a car stereo does it, so a second `Home` steps back a track however slowly you press. `End` plays the **next file** of the playing folder from its beginning, with `Toggle Repeat One` lit as well (the lamp decides what happens when a file *reaches its end*, and pressing next is not that), and stops at the folder's last file. Both work whether something is playing, paused or idle, and **neither ever leaves a folder** — that is `Backspace`, the `Up` button, and the head unit's previous. Bare `Up` never leaves one either: the arrows only move the highlight. The buttons' tooltips say which act each press will run, and they grey when it would do nothing; the play button's reads `Open Folder`, `Play`, `Pause` or `Resume` for whatever its press would do. The two skips' `Shift` lines name the first and last file of the *playing* folder and disappear wherever the plain press already reaches that file. There is no wrap anywhere. Auto-advance never crosses into another folder and never wraps either — at the folder's last file it stops, the item back at its start.
- `Shift+Home` / `Shift+End` — or a `Shift`+click or long press on the two skip buttons — jump to the first and last file of the playing item's folder.
- Whenever the player moves to another file on its own, the highlight follows it — as long as the folder you are looking at is the one playing; if you have walked elsewhere, your place is left alone. Walking off a *paused* file's row gives up its resume point: play it again after the walk and it starts over from the beginning rather than picking up where it stopped. A paused file the highlight never leaves resumes exactly as before.
- `Toggle Repeat One` is a lamp: while lit, the playing file starts again at its own end instead of moving on. It is one of only two things in the program that play anything twice by themselves — the other is the car's play of the trim in the main window, below — and it **starts lit every time the player opens** — repeating the one file is the default. Press `R`, or the lamp on the row, to turn it off for the rest of the session: files then advance to the next one in the folder and stop at the folder's end. The player forgets either way when it closes, and there is no repeat-all.
- The progress bar is the desktop's own slider: click the track and the sound jumps there; grab the handle and drag, and it jumps at the release. `Left` / `Right` step five seconds. Every seek is refused while nothing is playing or paused — a freshly opened player, or one resting after a folder's last file — and refused with nothing loaded at all: silently in both, the resting bar and the zeroed clock being the answer.
- `Esc`, `L`, or `Close` closes the player and hands playback back to the view you were in.

A WAV not at the source's own sample rate and channel count is refused with a line of its own rather than converted. **In the car the dashboard is its own interface**, not a remote control for the tablet's keys. The point is to start a render parked, without leaving the program: on the tablet the head unit's buttons work over Bluetooth. The one play/pause button is a plain toggle — it pauses what is playing, and otherwise does what the tablet's `Play` button does, opening a highlighted folder, playing a highlighted file or resuming the paused one, so nothing has to be started on the glass first. Rewind and fast-forward are previous and next. While something is playing they skip files — previous plays the file before this one if the position is within its first three seconds, otherwise it restarts this one; next plays the folder's next file and stops at its last. Paused presses walk the list again, exactly as idle ones do — previous up, next down and stopping at the bottom — and a paused file the list has moved away from and back to starts over from the beginning when played again, never resuming where it stopped. **Previous is what goes up a folder**, at the top of a listing or within the first three seconds of a folder's first file, so the folders can be moved through from the dashboard with nothing to press on the tablet. A console's own Fast-Forward and Rewind, where it has them as buttons apart from the wheel, just seek five seconds. Stop, if a console has one, stops the sound and puts the file back at its beginning without changing track, and seeking works. A dashboard that sends a bare *play* of its own when the link comes up — the Accord does, about a second after connecting — starts nothing on either road: that key only reopens the audio route, so the car never begins playing by itself and every press you make is the toggle.

**The head unit always shows a track playing, and its clock keeps running.** That is deliberate: a car stereo hears the Bluetooth link, which carries silence when nothing is playing, and believes that over anything the app tells it — so a paused display never stuck, and the pause button stuck with it. The dashboard is now told what it already believes, which makes its one button a reliable toggle. Its three lines are the project, the folder and the name: the console lays the album line above the title, dim, and the artist line below it, so the album is always the project — the least important of the three — and the artist is the folder — `tmp` at the top level, the folder's own name inside one, and while something plays it is that file's folder — and the track name is the bare name of the playing file or, with nothing playing, of the row the highlight is on, counting up from zero with no length: that is the silence you hear while walking the folders. **The tablet itself tells the truth** — its own play button, clock and progress bar say exactly what the sound is doing.

**With the player closed the dashboard drives the main window.** The same three buttons act on the piece you are editing. Play/pause plays **the trim, in a loop** — always from the trim's start, around and around until you stop it, which is the one thing in the main window that repeats itself. Pause is simply stop: nothing is remembered, so pause then play is how you start again from the top. Previous is undo and next is redo — exactly `Ctrl+Z` and `Ctrl+Shift+Z`, refusals and notifications included (on a locked tab, for instance, they say so) — and each one **then plays the trim**, so you hear the state you just stepped to without reaching for the play button. A step that was refused plays nothing and leaves a running loop alone; and in a target view, stepping onto a state that has not been rendered yet simply plays as soon as that render lands. Fast-forward, rewind and the console's own seek do nothing here. **Each of the three buttons is its key**, so under a flag editor or a mouse drag they answer exactly as the keys do: previous and next say `Keys are ignored during a drag` or `Close the editor first` on a card, and play does nothing at all, which is what `Space` does there too — the editor is typing a space with it. The dashboard shows the project on its top line, where you stand in your work as the track name, and the tab and view you are in (`A) T+W`) beneath it, with the clock counting through each lap of the loop. The loop's track length is the trim, so the dashboard's progress bar fills across the trim and refills at every lap, the way it does for a media file — and, with nothing playing, the length is unknown again and the clock simply runs. The track name is spelled the way a batch cell's file name is — a number, an underscore, a value: the number is which state of the session you are standing in, the same one the history view's session walk shows, and the value is how far that state is from your last save, always signed — `+` after it, `+0` at it, `-` behind it. Open, make two changes, save, make two more, and it reads `5_+2`; press previous twice and it reads `3_+0`, back at the save; twice more and it reads `1_-2`. A fresh project you have not touched reads `1_+0` — opening counts as the save until you make one. When the save is out of reach (you undid past it and then changed something) the value reads `?`. Opening the render player hands the dashboard over to it and closing the player hands it straight back.

### Loading a render in place (`'`)

Loading a render in place makes that render's recipe your new authoring baseline. Outside the history view, `'` opens the render player, and the player's load-in-place button — the checkmark, or `'` again on the highlight — does it on the highlighted batch cell. It asks first: `Load '<entry>' in place?` with `OK` and `Cancel`, `Return` answering `OK`. Only the batch cells under `tmp/` can be loaded, and they are the only thing the player lists — the deliverable in `render/` carries no recipe. When it succeeds the player closes. Inside the history view `'` is the same verb over a different thing — the checkpoint or session state you are looking at (see Checking history).

On a successful load you get the entry's **recipe** and nothing else: its markers and its engine settings, applied on top of what you have. Everything about where you are stays — the view, the marker column, the tab, the window, your trim, and every preference. `Grid iterations` cannot be on: a load in place is one of the things the lamp refuses, so turn it off first. The whole rule in one sentence: **a load in place writes exactly what one press of `Ctrl+Z` takes back.** Trim is outside it for that reason — trim has no undo, `Shift+0` being its recovery — so a load in place never moves a bound you set. The load is one cross-file undo entry, so `Ctrl+Z` puts back what you had, and the history view's session walk will show you what the load changed.

After it succeeds, `tmp/` is wiped — the batch outputs are stale once the baseline changes; the render you loaded survives through the render cache. The folder goes to the desktop trash when `gio trash` is available, so a batch you did not mean to lose can be restored in one piece; where the trash cannot take it, the folder is deleted outright with one stderr line saying so.

A load is refused while a render is running or parked (`Cannot load in place while a render is running`) and on a locked tab (`This tab is read-only`); if the entry's WAV has gone missing or a sidecar is malformed, nothing changes and the notification names the reason and the file.

### Checking history (`H`)

The project's working checkpoints live in a git repository — the `projects_repo` setting names which one, and the program reads the local clone, so nothing here needs a network or a credential until the push. **On the tablet you read the history the laptop exported for it**: the Android build carries no git, so the sync script writes the project's committed checkpoints out as a folder inside the project and ships them with everything else. The view walks that export exactly as it walks the repository here — the same members, the same short ids, the same comparisons, the same load in place — and it opens on it by itself wherever the export is there. What it cannot do is add to it: an export is a copy of the history, not the history, so `Save and Commit` is grey there and `Ctrl+S` answers `An exported history takes no checkpoint`. Checkpoints are a laptop act. A project with no exported history and no repository behind it opens on the session walk described below — your own undo/redo timeline, which needs neither — with the walk lamp grey and `G` telling you why. Bare `H` opens the history view: the marker lane stops showing the session's markers and shows the *difference* between a committed checkpoint of this piece and something else. The view is read-only and silent — it plays nothing, renders nothing, and none of the authoring gestures reach a marker or a bound; its three deliberate writes are the revert (`V`), the load in place (`'`) and Save and commit (`Ctrl+S`), all below. Panning and zooming work as ever, each tab keeps its own window, and entering and leaving move nothing at all.

Two choices set what the comparison is. **Which history** is the walk lamp (`G`, lit on `Session`): `Git` reads the committed checkpoints; `Session` reads your own session, counted as states. Where neither can be read — a project with no exported history and no repository behind it — the view opens on `Session` and stays there, the lamp grey and `G` telling you why — every state `Ctrl+Z` / `Ctrl+Shift+Z` can reach is a stop on that walk, plus the one you are standing in, so a fresh file reads `1/1`, two drops read `3/3`, and an undo after them reads `2/3` — with `U` steps behind you and `R` ahead, the state you are standing in is `U + 1` of `U + R + 1`. **How** is the `Cumulative` button (`U`): off is the iterative reading, which compares the viewed checkpoint against the next one toward the present — what happened after this checkpoint, one step at a time; on is the cumulative reading, which always compares against what is authored in memory right now — how your session differs from that checkpoint. The cumulative bit is remembered across visits; the walk starts every visit on `Git`.

In both readings green is the newer side and red the older: green flags are markers the newer side has, red flags markers the older side had, and a marker present in both at the same frame with a different value is one double-width flag, red half then green half, old value on the left. Warp flags carry the tempo in the sidecar's own spelling; phase resets carry the bare sign. A just-loaded, untouched project shows an empty lane — your session and the newest checkpoint agree, which is exactly what you want to see after committing.

`,` steps to an older member and `.` back toward the newest, holding either walks steadily; `Shift+,` / `Shift+.` jump to the ends. The two arrow buttons in the icon row are those keys. The state text's left end names where you are in the walk, with the commit's short id on the git readings, and — only when the checkpoint's `scale` differs — the two values old and new. **The members are numbered from the oldest**, so `1` is the earliest one the walk carries and the highest number is the newest; `,` therefore counts down and `.` counts up. On the git readings the walk fills in behind you while the program reads the history at startup, so both numbers can grow for a moment after the view opens. `Tab` / `Shift+Tab` walk the difference flags, `C` recentres on the brightened one, `Ctrl+Shift+Tab` marches the differences on both tabs. `Home` / `End` jump to the piece's ends here — the view is about the whole piece. The `A`/`B` tabs stay the tabs, `Ctrl+Tab` switches them, and the S/T and W/P switches work — a difference is line-shaped, and each view shows one column of it.

Differences can be selected and put back. A plain click on a diff flag brightens it and lands the playhead there; `Shift`+click ranges, `Ctrl`+click toggles. **Add to selection works here too**, and it is how a touchscreen gathers two differences at once: with its lamp lit a plain click on a diff flag does what `Ctrl`+clicking it does, adding or removing that one flag and leaving the rest standing. The revert below puts the lamp out again. `V` — the revert button — applies the selected differences *backwards* into your session and closes the view: a green flag's marker is deleted, a red flag's put back as the checkpoint had it, a two-colour flag's set back to the checkpoint's value. It is deliberately unguarded about the music — reverting half of a change is exactly as possible as reverting all of it, and that freedom is the point: markers land on top of each other, sections stretch, red flags appear, all of it yours to fix. What it will not do is write a file the program could not read back. Two things stop it, and both refuse the *whole* press rather than part of it, leaving the view open, your selection standing and nothing changed: a revert whose finished markers would give the same label to two markers (a disabled one counts) answers `Revert refused: label '<name>' is already defined at another marker`, and one that would put a marker past the end of this recording — a checkpoint taken against a longer file — answers `Revert refused: warp marker past end of audio at <time>` (`phase reset marker` in the other column). Otherwise the whole act is one undo step. A read-only tab refuses it, and `'`, but not Save and commit.

`'` inside the view asks about the member you are looking at — `Load '<id>' in place?` — and its `OK` loads that checkpoint's (or session state's) markers and engine settings in place: the same in-memory load a render entry takes, one undo entry, nothing written to disk, nothing of the checkpoint's trim, tabs or preferences; the view closes as it loads. It is not a rewind — `Ctrl+Z` immediately after brings back what you left, which is what makes walking to the very first state and loading it a safe way to audition where you started.

**Save and commit.** `Ctrl+S` inside the view — the `Save` button, wearing the commit glyph — saves and then commits the current authored state as a new checkpoint. It asks one thing first: an editor opens with the commit message already filled in (`Update <folder name>`), selected so typing replaces it; `Return` commits under whatever it holds — the ordinary case is a single keystroke, the useful case is writing what you actually changed — and `Esc` abandons. Then the program saves exactly as `Ctrl+S` would, the view closes, and everything after — writing the sidecars into the repository's `projects/` folder, committing, pushing — happens in the background; you keep working. If any of it fails, a notification with the red error glyph appears and *stays* until you close it — nothing committed, files written but not committed, or committed but not pushed — with the long version, in git's own words, on the terminal. The fix is in the terminal, deliberately: a checkpoint that committed but did not reach the remote is published with `git push`; the program does not retry for you, though the next Save and commit does — it pushes a branch it finds still unpublished, so a later checkpoint takes the earlier one with it. Only one checkpoint publishes at a time: while one runs, `Save` is greyed everywhere and `H` will not open the view; it comes back by itself, and quitting waits for it. The button greys too whenever the session's markers and `scale` already match the newest checkpoint — the answer covers the whole piece, both columns.

Only checkpoints the program could actually load are shown; ones that would refuse (an incomplete sidecar set, or files predating the current format — a `.settings` saved in the retired magnification level view among them) are left out of the walk, while a checkpoint that also carries an old `.magnificationlevelmarkers` file is read on its other three and that file ignored; the terminal noting how many were hidden. If that leaves nothing, the view opens on an empty walk — `0/0`, blank lane — and `Save and Commit` is live there: commit once and the next `H` reads it. A piece never checkpointed opens the same way, and its first Save and commit starts the history. The checkpoints live under the repository's `projects/` folder, one folder per piece, sidecars named by the source's basename; the piece's folder there is where its history goes. Moving the projects home to another git host takes two steps: point the clone at the new remote (`git remote set-url origin <new url>`) and edit `projects_repo` to match. The program speaks only to local git and whatever that remote is — no GitHub dependency, no account, no token.

### Undo and redo

`Ctrl+Z` undoes and `Ctrl+Shift+Z` redoes; settings edits and marker edits share one history. Held — the keys or the `Undo` / `Redo` buttons — they step on through the history at the keyboard's repeat rate. Undo and redo show you what changed: the touched markers are re-selected, and the view goes back to where the edit was made — the tab, the audio view and the marker column are all put back as they were when you made the change, the playhead keeping its place in the music while the map and the views are restored under it. Then the restore lands on what it brought back: a single touched marker gets the full marker-click treatment — playhead landed on it, flag brightened — and the view stays put while it is on screen, and otherwise centres it, at any zoom (after an explicit centring, the playhead instead keeps its place on screen and the waveform slides under it, as with a nudge); a group re-selects whole, lands the playhead on its earliest touched member and does the same for the whole set, zooming out (and centring it) only when the set would not fit with a little room at each edge, never zooming in. The view follows the markers, never the playhead, except that single-marker case after a centring. A step that brings nothing back (undoing a drop, say) and a settings-only restore land nothing and leave the view where it is.

`Z` is **Toggle Restrict Undo to Current View** — a lamp at the end of the icon row's view group, where it sits because it too is about where the view may go; the pair it governs is `Undo` and `Redo`. It starts off, and it is off again at every launch: it is not saved with the piece and it is in no settings file, being a posture you take for a few minutes rather than a property of the music. Lit, a step that would switch the view does not run at all: nothing is undone, nothing is redone, the history is left exactly as it was, and you get `That undo would switch the view` or `That redo would switch the view` on a card. Both buttons grey at the same moment, so you can see, before you press anything, whether the next step would take you to another view; the reason is on the card the key raises, the tooltip naming the act as every tooltip does. Use it when you are working in one view and want to take a few edits back without being carried to the other tab, audio view or marker column; switch it off and the same step runs normally.

A step switches the view when it was made on the other tab, in the other audio view or in the other marker column — the view the step landed in, which is the one a redo would put back too. A settings-only step is judged on its tab and audio view alone. Steps that do run are unchanged in every respect: the selection, the playhead and the centring all come back as they always do — the lamp refuses whole steps, it never half-restores one. On a read-only tab the lock answers first, `Ctrl+Z` being blocked there anyway. The lamp itself works on a read-only tab; in the history view it is grey, the undo history being frozen while that view stands.

Trim is excluded. Held nudges and value steps coalesce, and so does a run of wheel detents over a marker's box: a held run is one undo entry, and rapid separate taps of the same key merge when they land within about half a second with the same markers selected on the same tab; a slower press, one after the selection changed, or one after a save opens its own entry. A merged run that ends exactly where it started leaves no entry at all — tap `Right` then `Left` inside that window and the pair cancels, the history and the unsaved-changes dot going back to what they were before the first tap. What it does not put back is the redo branch: the first tap of the run discarded it, as any edit made partway back through the history does.

### Esc

`Esc` does exactly nine things, and nothing else anywhere. In rank order: it ends a text-selection drag inside an editor (that same press goes on to close the editor); it closes an open editor without committing; it dismisses a prompt, taking its rightmost answer; it dismisses an open menu; it closes the render player; it closes the project list; it closes the AV sync panel; it cancels all render work — the running render, a parked command behind it, and a pending target-view preview; and, with none of those standing, it clears the whole notification stack, red cards included. An open editor or prompt takes priority, so the first `Esc` closes that and the next one cancels render work. `Esc` with a modifier does nothing anywhere — see Notifications.

While a pointer gesture is in flight `Esc` is swallowed like every other key and answers `Keys are ignored during a drag`: gestures have no cancel — let go and the gesture commits what stands, then `Ctrl+Z` takes it back (trim, which sits outside undo, commits for good). With nothing open, nothing rendering, nothing being dragged and no card standing, `Esc` is a no-op: it does not deselect markers, does not move the playhead and does not touch the trim. To leave a selection, click the waveform or press `Home`/`End`.

### Mouse, touch, and the on-screen keyboard

One rule organizes the pointer: the whole waveform is a single navigation surface, and every gesture means the same thing anywhere on it. Plain drag pans; a plain click that never becomes a drag acts at the release — placing the playhead on the upper half, scrubbing on the lower half; `Shift`+drag sweeps a trim window; `Ctrl` turns the drag into the zoom, live at any moment of it. The ruler and the marker lane's empty stretches are for placing: a click there places the playhead at the release, a double-click on the empty marker lane creates a marker, and a drag there does nothing — on the mouse and the touchscreen alike. The right button does nothing anywhere, and the wheel takes no modifier. While the trim region is showing, a plain drag inside it slides the window and a drag on one of its bounds moves that bound — the one thing that outranks the pan — while the ruler and the marker lane stay placing surfaces even where the region reaches across them.

The pointer cue tells you what a press would do, using your own cursor theme: a hand on the waveform, a magnifier with `Ctrl` held, edge arrows on the trim bar's bounds, the resize arrow on a marker's flag and on anything that slides, an I-beam on editable text, the plain arrow wherever a gesture would not run. A live drag keeps the cue it started with; the pan and zoom drags hide the cursor and capture it for unlimited travel, wrapping it at the waveform's edges, and hand it back where it had got to.

`E` **is the left mouse button**: pressing it presses the button at the pointer position, holding it holds (so `E`+motion drags, modifiers riding along), releasing releases — except while a text editor is open, when it types the letter instead.

On a touchscreen, one finger is the mouse — a tap on the waveform is a left click at the moment the finger lifts, a touch anywhere else is the click the moment it lands (a tap inside an open text field lands at the lift instead), and every gesture, refusal, and rule above applies unchanged — with three additions. A one-finger drag on the waveform pans directly, the way it does on a phone. Hold a finger still for about half a second and then drag, and you sweep a trim window — the mouse's `Shift`+drag by another route (a hold released without moving just places the playhead). And two fingers pinch-zoom, and only zoom: the pinch takes hold of the audio under the two fingers' midpoint the moment it registers and scales about it — the same pivot the mouse's `Ctrl`+drag holds, marked by the same dim stem — while sliding both fingers together moves nothing, panning being the one-finger drag. Add and drop the second finger as often as you like within one touch. A second finger counts only when the first landed on the waveform; anywhere else, the trim bar included, it is ignored entirely. The trim bar itself is best reached with the tablet's pen. The pen is a finger with its side button as `Ctrl`: held during a drag on the waveform it turns the pan into the zoom about the pen's point (let go and it pans again), a button-held tap on a flag toggles it as `Ctrl`+click does and one on a skip button jumps to the piece's end as `Ctrl`+click does, the pen is never half of a pinch, and hovering it over the buttons shows their tooltips.

On a device with no keys of its own, opening any text editor brings up an on-screen keyboard across the bottom of the window, and it goes away when the edit ends. Every key acts the instant you touch it, and the keys that repeat on a real keyboard repeat here too — everything that types, and `Backspace` — held down at the program's own repeat rate. The one-shot commands do not: `Return` and `Esc` act once however long you hold them, and `Shift` is one-shot by design — tap it and the next letter is a capital; `&123` swaps to the digits and the punctuation the program's own grammars use; `Return` commits the edit and `Esc` throws it away, exactly as they do on a keyboard. The render player's list and the project list use that same band — no list needs typing, so a list and the keyboard are never up together. On the laptop this keyboard does not exist at all.

### Migrating an older project folder

A checklist for bringing a folder from before the project model — a bare `.warpmarkers` / `.phaseresetmarkers` pair, possibly still in the legacy `MM:SS.mmm` timestamp form, and a `renders/` folder or a stray output wav in the root — into the current layout:

1. Make a folder for the project directly under `projects_path`, named for what you want the project called.
2. Copy the source wav into it.
3. Copy the `.warpmarkers` and `.phaseresetmarkers` files in beside it.
4. If those sidecars are still timestamps rather than frames, build the conversion tool. It is not part of the product build and no executable ships in `tools/` — that folder is its source. From the project root:
   ```bash
   cmake -B build-tools -S tools && cmake --build build-tools
   ```
5. Convert the sidecars — the warp file first, then the phase-reset file, since the phase-reset conversion needs the completed warp map to land its positions correctly:
   ```bash
   build-tools/migrate_sidecar_to_frames <sample_rate> <stem>.warpmarkers
   build-tools/migrate_sidecar_to_frames <sample_rate> <stem>.phaseresetmarkers <stem>.wav
   ```
   `<sample_rate>` is the source's own rate (`44100`, for instance); the tool rewrites each file in place and keeps the untouched original beside it as `<path>.bak`.
6. Do not bring the old `.settings` across — it is all but certain to carry a key the current schema refuses (see below). A folder with some sidecars must carry all three, so get fresh templates first: move the converted `.warpmarkers` and `.phaseresetmarkers` aside, open the project with the wav alone (the first open writes all three templates), quit, and copy the two converted files back over their templates. Re-enter `title`, `notes`, `url`, and `cover` by hand from the old file's lines.
7. Rename any `renders/` folder to `tmp/` (`mv renders tmp`).
8. Move any `<title>.wav` and its `.fingerprint` sitting in the project root into `render/`. Move only the current `title` setting's pair: `render/` is kept to that one deliverable, and anything else you put there is deleted the first time a render publishes into it. Keep keepers somewhere else in the project.

A `.settings` that still carries `gui_scale`, `audio_player`, `projects_repo`, `playback_speed`, `follow`, `centered`, or `center_on_next_marker` refuses to load outright — an unknown key is an unknown key; the fix is deleting those lines by hand, not migration. The per-device config file has the same strictness in both directions: one carrying any retired line stops the program at startup — delete the line. The retired lines are `audio_player=`; any `waveform_gain_…=` or `waveform_expander_…=` line (the eleven waveform picture lines of September 2026); the three colour lines `waveform_ink=`, `waveform_magnified_ink=` and `waveform_ghost_ink=`; and the six level lines `waveform_magnified_gain=`, `waveform_ghost_reduction=`, `waveform_magnified_gain_db=`, `waveform_ghost_gain_db=`, `waveform_magnification_foreground_db=` and `waveform_magnification_background_db=`; and the two compressor lines `waveform_compressor_threshold_db=` and `waveform_compressor_ratio=`; and the four colour-tuning lines `fg_color=`, `bg_color=`, `fg_blend_loud=` and `fg_blend_quiet=`. One missing its `sync_path=` or `max_waveform_height=` line stops it the same way — add the line by hand (with the program quit): a bare `sync_path=` on a machine with nowhere to synchronize to, then the real path from `Settings` → `Sync Path` once it runs; `max_waveform_height=500` for the standing cap.
