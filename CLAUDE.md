# Warptempo GUI

Custom C++23 in-process PGHI phase-vocoder GUI (Arch / labwc / Wayland / JACK, plus an Android build for one tablet) for time-warping audio toward historically-informed tempos. Single developer and user (the architect); one authoring laptop, one authoring tablet. THE PROJECT IS COMPLETE (architect 2026-09-30): what remains is small bug fixes and layout refinement, never new scope. THE ONE RECORDED EXCEPTION (architect 2026-10-07: the in-app color picker and the palette files, "the logical conclusion: we're inheriting themes, but we cannot inherit a waveform theme that doesn't exist, so we have to create it") WAS REVERSED 2026-10-14 ("remove picker and preset file road": the families landed are what exists; the compiled-in presets are chosen by the Settings menu's Chrome and Caption rows, ordinary line editors since 2026-10-14 (the drop-downs removed, Tab completing a typed prefix over the built-in names)) — the picker's record in the Standing Rules below is history. THE CODE COMMENTS ARE THE AUTHORITATIVE RECORD of every rule and its reason, each at the symbol that owns it; `docs/engineering/closed_questions.md` lists, one line each, every question the architect has closed — read it before proposing anything, and never re-propose a line of it. This file carries the build, the process rules and a map of where to look. `docs/INSTALL.md` is the runbook (installing, building, the tablet, upkeep); `docs/HELP.md` the user's concepts; the interface's own words are its tooltips.

## Build Commands

```bash
cmake -B build -S . -DWARPTEMPO_BUILD_CLI=ON          # configure (first time or after CMakeLists changes)
cmake --build build -j$(nproc)                        # no CMAKE_BUILD_TYPE: asserts live; -O3 -march=native -ffp-contract=off always on
cmake -B build-debug -S . -DCMAKE_BUILD_TYPE=Debug    # debug goes in its own dir; never reconfigure build/ with -O0
cmake -B build-nogit -S . -DWARPTEMPO_GUI_GIT=OFF -DWARPTEMPO_CANVAS=cpu   # a build host without libgit2 or Mesa's EGL (the cloud): graphical work only, the git road a stub, the cairo canvas; the two devices build ON / gl
bash android/app/build_apk.sh                         # the tablet: cross-build + APK against android/prebuilt (the GL canvas, WARPTEMPO_CANVAS=gl, the same option on the laptop)
WT_CANVAS=cpu bash android/app/build_apk.sh           # the tablet's CPU-canvas reference build (build-android-cpu/warptempo-cpu.apk), for the screencap identity proof alone — never a device key
adb -s 192.168.1.87:5555 install -r android/app/build-android/warptempo.apk
adb -s 192.168.1.87:5555 shell am start -n com.warptempo.gui/.MainActivity
```

`build/warptempo_gui` is the default build's only product. No library archives: four per-directory source-list variables each binary compiles directly. `warptempo_cli` (opt-in; a headless host adds `-DWARPTEMPO_BUILD_GUI=OFF`) is the headless insurance render, byte-identical to the GUI through the shared stages. `tools/` holds standalone one-shot utilities with no link path from product targets. `-ffp-contract=off` is load-bearing: renders are byte-reproducible across rebuilds and `-march` choices (`docs/engineering/perf_campaign_2026_07.md` §15). One build host (the laptop) builds both products over the one portable GUI (`GuiPlatform`, `src/gui/platform.h`). Linux binaries are not portable (`-march=native`); the APK is. The tablet (Galaxy Tab S10 FE) is adb-drivable (install, launch, screencap, single-touch, logcat); multi-touch and feel are the architect's own glass pass.

## Running

```bash
./build/warptempo_gui                      # opens last_project from the device config, else the first valid project folder
./build/warptempo_gui <project source.wav>  # must be a project's SOURCE directly under projects_path (else a refusal, exit 1)
```

labwc on Arch; 1920x1080@60 laptop. No portability shims, no X11 fallback.

## Testing / Verification

There is NO automated test suite and that is a constraint: Wayland exposes no input-injection path. Do not propose automated tests, regression harnesses or commercial-tool comparisons. THE ONE PROOF ROAD ON THE TABLET (2026-10-13): adb's `input tap` on buttons and `screencap` of the composited frame, two builds driven through the same states and compared byte for byte (the GPU canvas's identity proof, `docs/engineering/gpu_canvas_2026_10.md` §5; the planner's script lives in tmp/, untracked) — a measurement of a change's claim, never a test suite. The CLI shares the stages with the GUI byte-identically; the architect runs cmp-null and audio verification against it and owns labwc verification.
